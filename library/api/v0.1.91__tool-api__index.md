## The Pattern

Every tool is a **JavaScript API first, UI second**.

When a tool implements the JS API Primitive pattern:
- It creates a `SgToolApi` instance, registers its methods, and calls `activate()`
- The instance is published to `window.__tool` and `window.__tools[instanceId]`
- The UI is **one consumer** — Playwright, the browser console, LLM agents, and other
  components are equal consumers with identical access

This enables headless testing, agentic driving, and Playwright-based CI with zero
special tooling. Any consumer that can run JavaScript on the page can drive the tool.

---

## Three-File Core

| File | Responsibility |
|------|---------------|
| `sg-tool-api.js` | `SgToolApi` class — register, activate, invoke, log, meta |
| `sg-tool-api-events.js` | Frozen `SGA_TOOL` event name constants; exposed on `window.SGA_TOOL` |
| `sg-tool-api-registry.js` | `window.__tools`, `window.__tool`, `window.__tool_registry` |

---

## Three UI Components (auto-bind to any tool)

| Component | Purpose |
|-----------|---------|
| `sg-tool-api-console` | Dev panel — call any method, see result + call history |
| `sg-tool-api-explorer` | Browse methods, read SKILL files, inspect health |
| `sg-tool-api-manifest` | Render the tool's manifest.json in readable form |

These components listen for `tool:ready` and bind automatically. No per-tool wiring needed.

---

## Three SKILL Files (per tool)

| File | Audience |
|------|---------|
| `SKILL-human.md` | End user guide — what the tool does and how to use the UI |
| `SKILL-browser.md` | Developer/Playwright guide — full JS API with code examples |
| `SKILL-api.md` | Precise API spec — method signatures, events, limitations |

SKILL files are served as static assets. The `meta.getSkills()` API fetches them at runtime.
