# Deep Technical Debrief — Running sgit (sg-send-cli) in the Browser via Pyodide

**Prepared for:** the agent building the **sgit.ai** website
**From:** SGraph-AI__Tools (Explorer) — research pass over the tools repo, 17 Jun 2026
**Scope:** what already exists for Python-in-browser, what is reusable, the CORS situation for `*.tools.sgraph.ai`, and exactly what you'd change to run **today's sgit** in a browser. Nothing here is aspirational unless labelled — the code + debriefs referenced all exist in the repo, and the CORS headers were confirmed live.

## 0. TL;DR

1. **It's been done and proven.** A browser terminal ran the real `sg-send-cli` Python package under **Pyodide** (CPython→WASM) and did a full **clone → commit → push** that a **native** CLI then **pulled** — round-trip confirmed, all crypto client-side. (`existing-debriefs/v0.1.2__sg-send-cli-in-browser-debrief.md`.)
2. **The Pyodide foundation is a reusable, deployed module** — `core/pyodide/…/sg-pyodide.js` — importable cross-origin from sgit.ai.
3. **CORS for `*.tools.sgraph.ai` is `*` — confirmed live.** You can `import` the modules directly from `https://tools.sgraph.ai/…`. (§2.)
4. **Two flavours shipped:** the *current* registered tool (`v0.1.53`) is a polished **in-memory** demo (no network); the **real-remote** transport (the interesting bit for a live site) is in the *original* `v0.1.2` tool via an **XMLHttpRequest monkey-patch** (Pyodide has no sockets). Both are in `reusable-code/tools/`.
5. **The one thing to update for *today's* sgit:** the browser code installs the **`sg-send-cli`** PyPI wheel and imports `sg_send_cli.*`. If the package is now published as **`sgit`** with new module paths, swap the wheel name + imports (the mechanics are identical). (§6.)

## 2. CORS — the direct answer

**`*.tools.sgraph.ai` serves `Access-Control-Allow-Origin: *` — verified live** on the actual module URL:

```
$ curl -I -H "Origin: https://sgit.ai" https://tools.sgraph.ai/core/pyodide/v1/v1.0/v1.0.0/sg-pyodide.js
HTTP/2 200
content-type: text/javascript
access-control-allow-origin: *
access-control-expose-headers: *
```
Same on `dev.tools.sgraph.ai`. So **sgit.ai can `import` `sg-pyodide.js` (and every other module/tool asset) directly**, no proxy, no build step. It's the public-CDN model (documented in `library/api/v0.1.92__sg-layout__full-inventory.md` §14 and the canonical-component-library brief).

**Two different CORS surfaces — don't conflate them:**
- **`tools.sgraph.ai` (the code you import):** `*` ✅ (above).
- **`send.sgraph.ai` (the vault backend the browser XHRs to for real clone/push/pull):** CORS is enforced **server-side by that CDN's config**, *not* in the static assets. The `v0.1.2` demo hit `dev.send.sgraph.ai` successfully, so it was enabled there. **For your target send endpoint you must confirm its CORS allows the sgit.ai origin** (and the methods/headers the CLI uses). If you run a private `send.sgraph.ai`, set its CORS to match your consumer origins (`library/api/v0.1.92__vault__full-inventory.md`).

## 3. How to run it — the bootstrap + wheel-install recipe

The non-obvious part is installing a package with a **compiled** dependency (`cryptography`) under `micropip`. This is the sequence that ships (from `existing-debriefs/v0.1.2__debrief__pyodide-support-and-mvps.md` §2, after **six** failed iterations):

```js
import { loadPyodide, installPackages } from 'https://tools.sgraph.ai/core/pyodide/v1/v1.0/v1.0.0/sg-pyodide.js';

const py = await loadPyodide({ onProgress: e => console.log(e.stage, e.detail) });

// 1) cryptography has NO pure-Python wheel → use Pyodide's built-in WASM package
await py.loadPackage('cryptography');

// 2) pure-Python deps install normally
const micropip = py.pyimport('micropip');
await micropip.install('osbot-utils');

// 3) the CLI wheel: fetch in JS, write to Pyodide FS, install from emfs:// with deps=False
const meta  = await (await fetch('https://pypi.org/pypi/sg-send-cli/json')).json();  // ← swap 'sg-send-cli' → 'sgit' if renamed
const wheel = meta.urls.find(u => u.filename.endsWith('.whl'));
const bytes = new Uint8Array(await (await fetch(wheel.url)).arrayBuffer());
py.FS.writeFile('/tmp/' + wheel.filename, bytes);
await micropip.install.callKwargs('emfs:///tmp/' + wheel.filename, { deps: false });  // ← callKwargs is REQUIRED

// 4) import and go
await py.runPythonAsync(`from sg_send_cli.sync.Vault__Sync import Vault__Sync`);       // ← module path if renamed
```

**The four discoveries that cost hours (do not re-derive them):**
1. **`cryptography` has no pure-Python wheel** → pre-load Pyodide's built-in *before* `micropip` tries to resolve it.
2. **`micropip.install(pkg, {deps:false})` silently ignores the JS object.** You MUST use **`micropip.install.callKwargs(pkg, {deps:false})`** — JS objects aren't auto-converted to Python kwargs.
3. **Do the wheel `fetch` in JS, not inside `runPythonAsync`.** `await micropip.install()` nested in a Pyodide async context triggers event-loop errors. JS `fetch` + synchronous `py.FS.writeFile` + `emfs://` sidesteps it.
4. **`hashlib.pbkdf2_hmac` is NOT compiled into Pyodide.** Key derivation must try/except-fallback to `cryptography`'s `PBKDF2HMAC` (both paths verified byte-identical). `sg-pyodide.js`'s `deriveVaultKeysPython()` already does this.

## 4. Real remote (clone/push/pull) — the XHR transport

Pyodide has **no sockets / no SSL** → Python's `urllib.request.urlopen()` fails on `https://` with `unknown url type: https`. The `v0.1.2` tool solves it by monkey-patching the CLI's HTTP methods to use the browser's **synchronous `XMLHttpRequest`** via Pyodide's JS bridge:

```python
from js import XMLHttpRequest
xhr = XMLHttpRequest.new()
xhr.open(method, url, False)                 # synchronous
xhr.setRequestHeader(k, v)
xhr.send(pyodide.ffi.to_js(body_bytes))      # Python bytes → JS for the body
# JSON:   json.loads(xhr.responseText)
# Binary: xhr.overrideMimeType('text/plain; charset=x-user-defined')
#         data = bytes(ord(c) & 0xFF for c in xhr.responseText)
```
Patch the CLI's `Vault__API._request()` / `_request_bytes()` (or whatever sgit's HTTP layer is now called) to route through this. **This is the piece to lift from `sg-send-cli__v0.1.2__REAL-REMOTE-xhr-recipe.html`.** It requires the `send.sgraph.ai` CORS in §2.

**Filesystem:** Pyodide's in-memory **memfs** (`/tmp/sg_cli_*/`). Ephemeral — lost on refresh; the remote persists. (No localStorage/IndexedDB persistence shipped.)

## 5. Performance (set expectations / loading UX)

From the shipped tools (`…pyodide-support-and-mvps.md` §8):
- **First load: 50–90 s**, dominated by the **~20 MB Pyodide** download. Subsequent loads **15–30 s** (browser HTTP-cached).
- Runtime: PBKDF2 600 k iters **200–300 ms**; vault init ~0.5–0.8 s; commit ~0.8–1.2 s.
- **Not yet optimised:** caching Pyodide + the wheel via a **Service Worker** or **`core/sg-wasm-cache`** (Cache-API) was flagged but not shipped — a low-hanging win to cut cold-start. Also consider hosting the wheel on your own CDN instead of PyPI at runtime.

## 6. The one real gap for *today's* sgit: the rename

The browser code targets **`sg-send-cli`** (the debrief cites PyPI **v0.5.0**) and imports **`sg_send_cli.*`**. sgit is the **new name** for that CLI. So before this runs current sgit, verify + swap:
1. **PyPI package name** — is it published as `sgit` (or still `sg-send-cli`)? Update the `fetch('https://pypi.org/pypi/<name>/json')` and the wheel install.
2. **Import paths** — `sg_send_cli.sync.Vault__Sync` etc. → the new module namespace.
3. **Is the wheel pure-Python** and are its deps Pyodide-compatible? (The old one was, minus `cryptography` which uses Pyodide's built-in. Re-run `checkVaultCompatibility()` / `test-sg-send-cli-install.html` against the new wheel.)
4. **HTTP layer method names** for the XHR patch (§4) may have moved.

Nothing structural changes — same Pyodide, same install trick, same XHR transport. It's a name/paths refresh + a compat re-check.

## 7. Recommended path for the sgit.ai site

1. **Import `sg-pyodide.js` from `tools.sgraph.ai`** (don't re-implement the loader) — CORS `*` confirmed.
2. **Confirm the current sgit PyPI package** (name/version/pure-python) and update the install (§6).
3. **For a real, network-backed terminal:** lift the **XHR transport** from the `v0.1.2` file (§4) and adapt it to sgit's HTTP layer; **confirm `send.sgraph.ai` CORS** for the sgit.ai origin.
4. **Cut cold-start:** cache Pyodide + the wheel (Service Worker or `core/sg-wasm-cache`); show a progress UI (the loader emits `onProgress` stages).
5. **Consider packaging** a `core/sg-sgit-browser` (or a Web Component) that bundles loader + wheel-install + XHR transport, so sgit.ai (and vaults) import one thing — mirrors how TTS became `core/sg-tts-openrouter`. (Ask the tools team; it's a well-scoped extraction.)
