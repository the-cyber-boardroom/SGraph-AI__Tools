## Architect Notes

**Why this matters:** Once a tool has the API, it can be:
- Driven by Playwright for CI smoke tests with zero UI dependencies
- Called by other tools (e.g. agentic loop driving infographic-gen headlessly via `renderUI:false`)
- Scripted from the browser console during development
- Documented via auto-discovered SKILL files that LLM agents can read at runtime via `meta.getSkills()`

**The pattern scales.** Every tool gets the dev panel (console/explorer/manifest) for free
the moment it calls `activate()`. No per-tool UI work needed.

**Key invariant:** The UI must never be the only path to tool functionality. If something
can only be done through clicking the UI, it is not yet part of the API.

**SKILL files are the weakest link.** Many tools have the API registered but missing or
incomplete SKILL files (playbooklm, sg-video-editor, auth-mvp). SKILL files are what make
the tool discoverable and driveable by LLM agents — they are as important as the methods.

## Dev Notes

**Effort per tool:** ~1–3 hours to add the API layer to an existing tool.
- The implementation functions already exist — `register()` wraps them.
- The hard part is writing complete SKILL files (especially SKILL-api.md and SKILL-browser.md).

**Recommended approach:** Add API to one tool per sprint alongside normal IFD work.
The `api/` + `ui/` split (video-creator pattern) is now the default layout.

**Next candidates:**
1. `chat` — highest traffic, methods are obvious from existing UI
2. `playbooklm` — already has 27 registered methods; just needs SKILL-browser.md + SKILL-api.md written
3. `sg-video-editor` — registered methods exist; needs SKILL files
