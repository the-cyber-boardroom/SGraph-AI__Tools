# Capability Debrief — Infographic tooling & Google OAuth as a user secret store

**From:** SGraph-AI__Tools · **Date:** 13 Aug 2026 · code-verified against the repo
**For:** the `*.voicedebrief.ai` project — specifically, whether Google OAuth can hold a user's OpenRouter (and other) API keys.
**Two parts:** §1–3 infographic generation · §4–8 Google OAuth + secret storage.

---

## TL;DR

**Infographics:** `infographic-gen` is the repo's **most complete tool** — a full `SgToolApi` implementation with **12 registered methods**, 6 window events with UUID call-correlation, a manifest, and all three SKILL files. It is headless-drivable (`renderUI: false`), so another site can drive it end-to-end from the console or Playwright. Two reusable components ship with it: a model picker and an exporter (PNG/SVG download, clipboard, Web Share).

**Google OAuth as a secret store:** **yes — and we already do exactly this today.** `vault-mgr` stores **vault master keys** in a `vaults.json` file in the user's **Google Drive App Data folder**, via `core/drive-appdata`. Holding an OpenRouter key for voicedebrief.ai is the same move with a different filename.

**Three things to know before you build on it:**
1. The `drive.appdata` scope is **non-sensitive** — basic verification only, not the painful Drive review.
2. The App Data folder is **per Google Cloud project, not per origin** — so `*.voicedebrief.ai` and `tools.sgraph.ai` share a secret store only if they share a Cloud project.
3. **It is not zero-knowledge.** appData is hidden from the Drive UI and from other apps, but Google can read it and so can any XSS on your origin. We have the pieces to fix this (§7) — but the current `vault-store.js` writes **plaintext**.

## 2. The API surface (all 12 methods)

`window.__tool` / `window.__tools['infographic-generator:root']`, per `SKILL-api.md`:

| Method | Signature |
|---|---|
| `connect` | `{ apiKey?, model? }` → `{ model, provider }` — 15 s timeout, **skip-if-same-key** short-circuit |
| `generate` | `{ prompt?, model?, renderUI? }` → `{ callId, generationId, model, duration, imageSrc }` |
| `getState` | → `{ mode, prompt, model, connected, activeGenerations, systemPrompt, document, image }` |
| `getGenerations` | `{ n }` → full records incl. `request.messages`, `response.{content,promptTokens,completionTokens,latencyMs,finishReason,images,rawResponse}` |
| `setPrompt` / `getPrompt` · `setModel` / `getModel` · `setSystemPrompt` / `getSystemPrompt` | prompt & model control |
| `setTemplate` | → the resolved prompt text |
| `stop` | cancel in-flight generation |

**Events:** `tool:ready`, `tool:connected`, `tool:generation:{started,complete,error,cancelled}`.

**Two design details worth copying:** every `generate()` mints a **`callId` UUID** threaded through all events and the returned Promise, so **concurrent generations correlate without FIFO assumptions**; and **`renderUI: false`** runs the request fully headless — no result tab created. That combination is what makes the tool scriptable by an agent.

## 3. How voicedebrief.ai would consume it

- Pairs naturally with the TTS doc (`v0.1.94`): a Journalist Agent generating both **narration audio** and a **cover infographic** per update.

## 5. `core/drive-appdata` — the mechanism

The Google Drive **App Data folder** is a hidden, per-user, per-application folder. The user's Drive UI never shows it; other apps cannot see it.

```js
import { requestAccess, DriveAppData, DRIVE_APPDATA_SCOPE }
  from 'https://tools.sgraph.ai/core/drive-appdata/v0/v0.1/v0.1.0/sg-drive-appdata.js';

const token = await requestAccess(clientId, { hint: email, prompt: '' }); // '' = silent
const drive = new DriveAppData(token);

await drive.writeFile('secrets.json', JSON.stringify({ openrouter: 'sk-or-v1-…' }));
const raw   = await drive.readFile('secrets.json');   // → string | null
await drive.listFiles();                              // [{ id, name, modifiedTime, size }]
await drive.deleteFile(fileId);
```

`requestAccess()` waits up to 3 s for GIS to load (it is loaded asynchronously by `sg-auth-google`), and `prompt: ''` attempts a **silent** re-grant — important because access tokens last only ~1 hour.

## 6. We already store real secrets this way

**`tools/v0/v0.1/v0.1.51/en-gb/vault-mgr/api/vault-store.js`** — `class VaultStore(drive)` persists a `vaults.json` registry to App Data containing, per entry:

```js
{ vaultId, displayName, apiBaseUrl, vaultKey: '{48-hex}:{16-hex}', createdAt, lastUsed }
```

`vaultKey` is a **live master key**. So the pattern you are asking about is not speculative — it is shipping. Drive App Data / OAuth is also already used by `youtube-upload`, `youtube-editor`, and `google-photos-cors`.

## 7. Applying this to voicedebrief.ai — and the honest caveats

**Where the OpenRouter key lives today:** `localStorage['sg-openrouter-mgmt-key']`, used by `sg-openrouter-key-manager`, `audio-transcribe`, and `live-transcribe`. That is per-origin, per-browser, per-device; it vanishes on "clear site data" and never follows the user to a second machine. Moving it to App Data fixes all of that.

### Storage options compared

| Option | Survives reload | Follows user across devices | Google can read | Verification burden |
|---|---|---|---|---|
| **localStorage** (today) | ✅ | ❌ | ❌ | none |
| **Drive App Data** (proposed) | ✅ | ✅ | ⚠️ **yes, if plaintext** | basic only |
| **Password manager** (`sg-credential-store`) | ✅ | ✅ (if browser sync on) | ❌ | none |
| **SG/Send vault** | ✅ | ✅ | ❌ (zero-knowledge) | none |

### Four things that will bite you

1. **The App Data folder is scoped per Google Cloud project, not per origin.** A client ID in a *different* project gets a *different* folder. If you want one secret store shared by `*.voicedebrief.ai` and `tools.sgraph.ai`, they must **share the Cloud project**; otherwise you get separate silos. **Verify this against your project layout before writing code** — it is the decision that is expensive to reverse.
2. **OAuth client IDs are origin-bound.** Every `*.voicedebrief.ai` origin must be added to *Authorized JavaScript origins* in the Cloud console.
3. **Tokens are short-lived (~1 h)** and GIS is an implicit flow — there is **no refresh token**. Plan for silent re-request (`prompt: ''` with `hint`) and a visible re-consent path.
4. **This is not zero-knowledge.** App Data is *hidden*, not *encrypted*. Google can read it; an XSS on your origin can read the OAuth token out of localStorage and then read the secrets. `vault-store.js` writes **plaintext today** — do not copy that part.

### Two mitigations, both already available in-repo

- **Encrypt before writing.** `core/crypto` (AES-256-GCM) + `core/pbkdf2` are already here. Derive a key from a user passphrase, store ciphertext in App Data → Google holds an opaque blob. Cost: the user must enter a passphrase per device.
- **Use OpenRouter provisioned sub-keys.** `sg-openrouter-key-manager` already does full CRUD on OpenRouter provisioned keys **with credit limits**. Issuing a capped, individually revocable sub-key per user/device means a leaked key is bounded and killable — arguably a stronger practical control than encryption alone, and it is already built.

**Best combination for voicedebrief.ai:** a capped OpenRouter **sub-key**, **encrypted**, stored in **App Data**, with the **password manager** as the local fast path.

## 8. 🟡 PROPOSED — what doesn't exist yet

| Gap | Proposal |
|---|---|
| No unified secret API | **`core/sg-secret-store`** — one interface (`get/set/list/remove`) over providers `drive-appdata \| password-manager \| localStorage \| vault`, mirroring the `sg-vfs` provider pattern |
| App Data blobs are plaintext | Encrypt-at-rest option in that store, using `core/crypto` + `core/pbkdf2` |
| OAuth token sits in localStorage | Honour `sg-auth-tokens`' own stated intent and move to vault-backed storage |
| No silent-refresh helper | Wrap `requestAccess(clientId, {prompt:'', hint})` with expiry tracking and a re-consent fallback |

**Suggested sequence for voicedebrief.ai:** (0) confirm the Cloud-project/App-Data-sharing question in §7.1 → (1) stand up `sg-auth-google` + `core/drive-appdata` against a voicedebrief client ID, using `auth-mvp` as the reference harness → (2) write `secrets.json` following `vault-store.js`, **with encryption added** → (3) migrate the OpenRouter key off `localStorage['sg-openrouter-mgmt-key']`, keeping it as fallback → (4) extract `core/sg-secret-store` once a second consumer appears.
