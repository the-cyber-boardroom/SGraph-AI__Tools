## How to Read This Document

- **Layer** = core / component / tool (tool = user-facing page)
- **IFD versions** = count of patch versions shipped via IFD overlay methodology
- **Latest** = highest version number found in the directory tree
- **Status** = active (multiple IFD versions, clearly used) / stable (v1.0.0, no overlays) / experimental (v0.1.0 only, no overlays)
- **Manifest** = whether a `manifest.json` exists (✅ / ❌)
- Components without manifests are flagged — manifests are required for discoverability

## 5. Findings & Recommendations

### 5.1 Missing Manifests (HIGH PRIORITY)

**23 modules/components lack `manifest.json` files.** This is the single biggest discoverability problem. Without manifests, a Dev or Architect starting a new session cannot quickly determine what exists, what it exports, or what it depends on.

Affected: C-07 (vault-write), C-11 (sg-layout), C-12 (sg-sandbox), C-13 (sg-tree), C-14 (sg-vfs), L-13 (bundle-viewer), all 7 OpenRouter components (O-01→O-07), all 3 vault components (V-01→V-03), both VFS components (VF-01→VF-02), all 6 agentic components (A-01→A-06).

### 5.2 Potential Duplications

| Items | Issue | Action |
|-------|-------|--------|
| `sg-header`/`sg-footer` vs `sg-site-header`/`sg-site-footer` | Two generations of header/footer. Old ones are tools-specific; new ones are cross-domain. | Assess if old can be retired. Check which tool pages still import them. |
| `sg-llm-attachments` (L-15) vs `sg-llm-attachment-manager` (L-14) | Both handle file attachments. L-14 has 4 IFD versions; L-15 has 1. | L-15 may be superseded. Verify and deprecate if so. |
| `sg-llm-output` (L-06) vs `sg-llm-chat-history` (L-04) | Both render LLM responses. Chat-history has 10 IFD versions; output has 1. | Clarify if output is for one-shot mode only, or superseded. |
| Vault Browser custom JS (T-07) vs Vault components (V-01/V-02/V-03) | T-07 has 12+ inline JS modules; T-17 uses proper components. | T-07's inline modules should be assessed for extraction or retirement. |

### 5.3 Non-Standard Directory Structure

| Module | Issue |
|--------|-------|
| `core/sg-layout/v0.1.0/` | Uses flat `v0.1.0/` instead of IFD `v0/v0.1/v0.1.0/` structure |
| `core/sg-vfs/v0/v0.1/v0.1.0/` | Correct IFD structure ✅ |
| `core/sg-tree/v0/v0.1/v0.1.0/` | Correct IFD structure ✅ but v0.1.1+ use filename-versioning (`sg-tree--v0.1.1.js`) instead of directory-versioning |

### 5.4 High-Churn Components (Refactoring Candidates)

| Component | IFD Versions | Notes |
|-----------|-------------|-------|
| `sg-llm-chat-history` | 10 | Highest churn. Core chat UX — may benefit from extracting rendering/markdown/scroll into sub-modules. |
| `sg-llm-bundle` | 8 | Storage model iterated heavily. Storage backend may need stabilising. |
| `sg-llm-request` | 5 | Multi-provider fetch — stable API surface but frequent internal changes. |
| `sg-llm-connection` | 5 | Provider config — tracks provider API changes. |
| `sg-llm-chat-input` | 5 | Input UX — attachment/paste handling evolved. |

### 5.5 Dependency Graph Summary

```
Foundation:  sg-component → sg-tokens
Crypto:      sg-crypto, sg-pbkdf2, sg-wordlist, sg-ssh, sg-send-crypto
Vault:       sg-vault-client → sg-vault-write
             sg-vault-connect → (vault-client + vault-write)
             sg-vault-tree    → vault-client
             sg-vault-viewer  → (vault-client + vault-write)
LLM:         sg-llm-events (shared bus — all LLM components depend on this)
             sg-llm-request (sole API caller)
             sg-llm-connection → sg-llm-model-picker
             sg-llm-chat-history ↔ sg-llm-chat-input (bidirectional via events)
             sg-llm-bundle ← sg-llm-bundle-list
VFS:         sg-vfs-core ← sg-vfs-bus ← sg-vfs-event-viewer
Agentic:     sg-agentic-loop → (sg-llm-request + sg-tool-runner)
             sg-tool-runner → sg-sandbox + sg-vfs-bus
```
