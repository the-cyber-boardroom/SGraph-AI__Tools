## 1. What we are building (in one screen)

A composition tool at `tools.sgraph.ai/.../agent-with-tools/` that lets an LLM (Ollama by default, OpenRouter optional) drive six host-side tools — read/write/delete/list files, run bash, fetch URLs — via a tiny FastAPI bridge running in Docker on the same host (laptop or EC2).

Three processes:

```
┌─ Browser tool (tools.sgraph.ai)  ┐         ┌─ FastAPI bridge (Docker, :8000) ┐
│  sg-llm-chat-input/history       │  CORS   │  /file/{read,write,delete,list} │
│  sg-agentic-loop                 │ ──────▶ │  /bash/exec                     │
│  sg-tool-runner (builtins=none)  │         │  /curl/fetch                    │
│  sg-tool-definition              │         │  /ping                          │
│  sg-local-bridge  🆕 ~250 LOC    │         │  Volume: ./_sgraph-workspace    │
│  sg-llm-request (Ollama path) ───┼──────┐  └─────────────────────────────────┘
└──────────────────────────────────┘      │
                                          ▼
                                   ┌─ Ollama (:11434) ────────────────────────┐
                                   │  /api/chat · qwen2.5-coder:7b            │
                                   └──────────────────────────────────────────┘
```

**Net new code:**
- 1 headless Web Component: `sg-local-bridge` (~250 LoC split into shell + client)
- 1 tool page: `agent-with-tools` (composition, ~150–200 LoC of JS for the SgToolApi + dev panel)
- 1 FastAPI service: `sgraph_bridge` (~6 endpoints + safety helper + tests, ~400 LoC Python)
- 3 SKILL files + manifest + landing-page tile

Everything else is composition of v0.2.54 modules.

## 3. Contracts (locked)

### 3.1 FastAPI HTTP contract

All POST except `/ping`. JSON in/out. CORS enabled. `path` is **relative to the mounted workspace** (`/workspace` inside the container).

| Endpoint | Request | Response (200) | Errors |
|---|---|---|---|
| `GET /ping` | — | `{ ok, version, workspace, started_at }` | — |
| `POST /file/read` | `{ path }` | `{ path, content, size, mtime, is_text }` | 404 `file_not_found`, 415 `binary_file_not_supported_yet`, 403 `path_outside_workspace` |
| `POST /file/write` | `{ path, content, create_dirs?: true }` | `{ path, bytes_written, created }` | 403 |
| `POST /file/delete` | `{ path }` | `{ path, deleted }` | 404, 403 |
| `POST /file/list` | `{ path, recursive?: false }` | `{ path, entries: [{name,type,size,mtime}] }` | 404, 403 |
| `POST /bash/exec` | `{ command, cwd?, timeout_s?: 30 }` | `{ command, cwd, exit_code, stdout, stderr, duration_ms, truncated }` | 408 `bash_timeout`, 403 |
| `POST /curl/fetch` | `{ url, method?: 'GET', headers?, body? }` | `{ url, status, headers, body, content_type, duration_ms }` | 502 `curl_failed` |

Error envelope (4xx/5xx): `{ error_code: string, message: string, detail?: any }`.

**Path safety helper** (`safety.py`):
```python
def resolve_in_workspace(p: str, workspace: Path) -> Path:
    """Resolve p (relative or absolute) against workspace, follow symlinks,
       reject anything that escapes. Used by every file/bash endpoint."""
```
Behaviour: reject absolute paths that don't start with workspace, reject after `..`/symlink resolution if outside, reject NUL bytes. `bash/exec` `cwd` is checked the same way. **Container is the security boundary** — beyond path safety we do not sandbox commands.

**Bash truncation:** stdout/stderr capped at 200 KB each; set `truncated: true` if hit.

**CORS:** `Access-Control-Allow-Origin` whitelist of `https://tools.sgraph.ai`, `http://localhost:*`, `http://127.0.0.1:*`. Methods: GET, POST, OPTIONS. Allow credentials: false.

### 3.2 `sg-local-bridge` Web Component contract

Headless. Lives inside `[data-llm-bus]`. On `connectedCallback`:
1. If `auto-connect`, calls `GET /ping`. On success, fires `sg-local-bridge:status` and registers the six tools on the nearest `sg-tool-runner` (via `runner.register(name, fn)`).
2. On failure, fires `sg-local-bridge:error`; tools are not registered.

**Attributes:**

| Attribute | Default | Purpose |
|---|---|---|
| `endpoint` | `http://localhost:8000` | FastAPI base URL |
| `workspace` | `/workspace` | Display only |
| `auto-connect` | (absent = off) | Ping on mount |
| `tools` | `*` | CSV of tool names to expose (`lb_read_file,lb_write_file,...` or `*`) |
| `timeout-ms` | `30000` | Per-request fetch timeout |

**Registered tools (LLM-visible):**

| Tool | Args (JSON Schema, abbreviated) | Bridge call |
|---|---|---|
| `lb_read_file` | `{ path: string }` | POST `/file/read` |
| `lb_write_file` | `{ path: string, content: string, create_dirs?: boolean }` | POST `/file/write` |
| `lb_delete_file` | `{ path: string }` | POST `/file/delete` |
| `lb_list_folder` | `{ path: string, recursive?: boolean }` | POST `/file/list` |
| `lb_run_bash` | `{ command: string, cwd?: string, timeout_s?: number }` | POST `/bash/exec` |
| `lb_fetch_url` | `{ url: string, method?: string, headers?: object, body?: string }` | POST `/curl/fetch` |

Each `runner.register(name, async fn)` returns the JSON the bridge returned (success or error envelope). The agentic loop feeds that back to the LLM as tool result.

**Bus events:**
- `sg-local-bridge:status` — `{ ok, version, workspace, latency_ms }`
- `sg-local-bridge:tool-call` — `{ name, args, result, ms }` (for the inspector)
- `sg-local-bridge:error` — `{ message, detail }`

**Size budget:** `sg-local-bridge.js` ≤ 180 lines (component shell + tool registration), `sg-local-bridge-client.js` ≤ 120 lines (six typed `fetch` wrappers + ping). Hard ceiling 300 per file; do not exceed.

### 3.3 Tool page (`agent-with-tools`) SgToolApi

`window.__tool` exposes:

| Method | Description |
|---|---|
| `connect()` → Promise<{ok,version,workspace}> | Force-ping the bridge |
| `chat(msg: string)` → Promise<string> | Send a chat message, await final assistant text |
| `getTranscript()` → Array<turn> | Full turn array (user/assistant/tool) |
| `getBridgeStatus()` → {ok, latency_ms, workspace} | Last known bridge status |
| `setProvider(name)` → void | `'ollama'` \| `'openrouter'` |
| `setModel(name)` → void | e.g. `'qwen2.5-coder:7b'` |
| `clearChat()` → void | Reset turns |

Three SKILL files written per the `infographic-gen` v0.1.37 reference.

## 9. Conversation turn shape (contract)

The agentic loop sends a growing array of turns to `sg-llm-request` on each round. Every tool call and its result must appear in that array before the next LLM call. Here is the locked shape:

### 9.1 Turn types

| Role | `type` | When emitted |
|---|---|---|
| `user` | `text` | Human message from `sg-llm-chat-input` |
| `assistant` | `text` | LLM prose response |
| `assistant` | `tool_calls` | LLM's tool-invocation request (one or more) |
| `tool` | `tool_result` | Result fed back for each tool call |

### 9.2 Turn objects (JSON)

**User message:**
```json
{ "role": "user", "content": "Read README.md and add an emoji to the title." }
```

**Assistant tool-call (native format, qwen2.5-coder / OpenRouter):**
```json
{
  "role": "assistant",
  "content": null,
  "tool_calls": [
    {
      "id": "call_abc123",
      "type": "function",
      "function": {
        "name": "lb_read_file",
        "arguments": "{\"path\":\"README.md\"}"
      }
    }
  ]
}
```

**Tool result (appended by `sg-tool-runner` after `sg-local-bridge` returns):**
```json
{
  "role": "tool",
  "tool_call_id": "call_abc123",
  "content": "{\"path\":\"README.md\",\"content\":\"# SGraph Tools\\n…\",\"size\":412}"
}
```

**Assistant prose (final response after all tool calls resolved):**
```json
{ "role": "assistant", "content": "Done. The title now reads \"# 🛠️ SGraph Tools\"." }
```

### 9.3 Multi-call round

If the LLM emits multiple `tool_calls` in one response, `sg-tool-runner` executes them (serially or concurrently based on its implementation) and appends one `tool_result` turn per call before the loop fires the next LLM request. The order of `tool_result` turns must match the order of `tool_calls` entries.

### 9.4 JSON-in-content fallback (Phase 4)

When a model emits tool calls as JSON embedded in `content` (not in the native `tool_calls` field), the Phase 4 shim re-parses the `content` string, extracts the call(s), and normalises them into the same turn shape above. The shim lives in `sg-local-bridge-client.js` or a sibling `sg-local-bridge-shim.js`. The rest of the loop is unaffected.

### 9.5 What `sg-llm-request` sends to the LLM

`sg-llm-request` transmits the full turn array plus the system message (§11 of the prompts doc) on every round. For Ollama: `POST http://localhost:11434/api/chat` with `model`, `messages` (the full turn array prepended with the system turn), `tools` (the JSON schema array for all enabled `lb_*` tools), and `stream: true`.

## 10. UI behaviour for tool turns

### 10.1 What `sg-llm-chat-history` renders per turn type

| Turn type | Rendered as | Notes |
|---|---|---|
| `user` text | Right-aligned user bubble | Existing |
| `assistant` text | Left-aligned prose | Existing |
| `assistant` tool_calls | Collapsible `⚙ name(args)` chip per call | **Existing in v0.1.10** |
| `tool` result | `→ N bytes · Xms` inline in the chip, expand to see full JSON | **Existing in v0.1.10** |

No new rendering code needed for the happy path — `sg-llm-chat-history` v0.1.10 already supports tool-call bubbles. The implementer must confirm the chip expands to show the raw result JSON and does not error on large stdout payloads (e.g. 200 KB from bash).

### 10.2 Bridge status indicator (new — in `ui/ui-shell.js`)

A small status dot in the header driven by `sg-local-bridge:status` and `sg-local-bridge:error` bus events:

| State | Dot colour | Label |
|---|---|---|
| Not yet connected | Grey | `Bridge` |
| Connecting (ping in-flight) | Amber | `Bridge` |
| Connected | Green | `Bridge · /workspace` |
| Error / unreachable | Red | `Bridge offline` |

On hover: show latency in ms and bridge version. Clicking the dot re-triggers `connect()`.

### 10.3 Loop status strip (new — in `ui/ui-shell.js`)

A one-line strip below the chat input, driven by `sg-agentic-loop` events:

| Loop state | Content |
|---|---|
| Idle | `● idle · {N} tool calls · ${cost}` |
| Running | `● running · iter {n}/{max} · ${cost}` |
| Paused (human-approval) | `● waiting · approve or stop ↓` |
| Error | `● error: {message}` |

Show `Stop` button while running; show `Approve` and `Stop` while paused. When Ollama is the provider cost stays `$0.00`.

### 10.4 Model panel (right sidebar, in `ui/ui-shell.js`)

Static display populated from `sg-llm-connection` events:

```
Provider:   Ollama
Model:      qwen2.5-coder:7b
Endpoint:   localhost:11434
Streaming:  ✓
Speed:      18 tok/s          ← live, from sg-llm-stats events
```

### 10.5 What happens when a tool call fails

If the FastAPI bridge returns a 4xx/5xx, `sg-local-bridge` passes the error envelope back to `sg-tool-runner` as the result content (JSON string). `sg-tool-runner` appends it as a normal `tool_result` turn — the LLM sees the error and can decide to retry, apologise, or ask for help. The chip in the chat history shows `→ error` in red.

No special error-modal needed. The conversation is the error report.
