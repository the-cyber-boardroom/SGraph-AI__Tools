## Finding-by-finding

### Finding 1 — Read API (`getItems`/`getItem`) — ✅ addressed (was deploy-drift)
- In the current source, `getItems()` returns `state.getItems()` (an **array**)
  and `getItem({id})` returns the live item — they were never broken in the repo.
  The `{}` the brief saw is the **deployed v0.1.14** build diverging from source
  (Finding 4). I'm **not** changing the getters (they're correct).
- **Landed:** a CI contract test — `addFiles → getItems(array) → transcribeItem →
  getItem(live)` — in `tests/audio-transcribe-smoke.js`, and the manifest now
  states `getItems` is **authoritatively an ARRAY** (answers the open question
  "array or id-keyed map?": **array**). This guards the shape against future drift.

### Finding 2 — OpenRouter TTS HTTP 400 — ✅ done (v0.1.15, before this brief)
- Fixed already. Root cause confirmed exactly as the brief states: `stream:true` +
  `audio.format:'wav'` is rejected. **Answer to the brief's open question** ("is
  there a streaming-safe format, or is non-streaming the answer?"): there **is** a
  streaming-safe format — **`pcm16`**. We request `pcm16` and wrap the streamed PCM
  chunks in a WAV header in-browser (24 kHz mono, `pcm16ToWav()`), so we keep
  streaming (no latency regression) rather than falling back to non-streaming.

### Finding 3 — `sg-wasm-cache` vault-safety — ✅ done (v0.1.17)
- Exactly right and important. `isCacheApiAvailable()` did an unguarded
  `typeof caches`, which **throws** `SecurityError` (not returns `undefined`) in a
  sandboxed `srcdoc` frame without `allow-same-origin`. Now wrapped in try/catch →
  returns `false`. Storage is treated as **best-effort, never required**. Guarded
  by a smoke test that simulates the throwing `caches`.
- **Audit (the brief's wider ask):** I checked the tool's own storage use — it is
  already safe: `localStorage` access (`setApiKey`/key persistence) is wrapped in
  try/catch; the tool uses no `indexedDB`/service workers; `Worker` is only via
  `sg-tts` (local TTS), an explicit user action, not boot. **Push-back / hand-off:**
  `core/vault-cache` also has a `typeof caches` — but that's a **vault-team module**;
  I flag it for them rather than editing it here. A repo-wide guard audit of *all*
  components is a Librarian/Architect sweep, not in this tool's scope.

### Finding 4 — API/manifest drift + versioning — ✅ supported, partly process
- I agree the manifest is authoritative and the JS API must be versioned. **Landed:**
  manifest + `SgToolApi` version bumped on every shape change (now `0.1.17`), the
  contract smoke test above, and the changelog (`releases.js` / `getReleases()`)
  records each shape change. **Push-back (not a code fix):** "**deploy ≤ repo**" and
  "run the contract test in CI **before deploy**" are **CI/DevOps gates** — they
  belong in the deploy pipeline (DevOps role), not the tool. I can hand the contract
  test to DevOps to wire as a pre-deploy gate, but enforcing "don't ship ahead of
  repo" is a release-process control, not something the tool can self-enforce.

### Finding 5 — Chat is UI-only — ✅ done (v0.1.17)
- **Landed:** `ask({ text, model?, context? })` on `window.__tool` — headless,
  scriptable, embeddable. Default system prompt is built from the done transcripts
  (override with `context`); returns `{ text, model, generationId, usage }`. Kept
  thin (one call over the existing isolated transport), as the brief's Risk 3
  recommends, and versioned in the manifest. Verified via Playwright against the
  real served page.
- On the **handle drift** the brief notes (class-as-handle, shadow-DOM history): I
  treat `ask()` as the **supported** automation surface, so embedders should drive
  chat through it rather than DOM handles. I'm **not** committing to freezing the
  internal chat-UI DOM ids — those are UI internals and reserve the right to change;
  documenting `ask()` as the contract is the stable answer. (History is shadow DOM:
  verify via `shadowRoot`/screenshot, not `textContent` — noted for QA.)

### Finding 6 — Per-transcript cost / generation id — ✅ done (v0.1.17)
- **Landed:** `transcribeItem()` now returns `generationId` **and**
  `usage:{promptTokens,completionTokens,costUsd}`, so an embedder can do its own
  `GET /api/v1/generation` follow-up and show real cost. `ask()` returns the same.
  Bonus from the same release: **Live mode** now surfaces **per-segment cost** (each
  live poll is a real billed request) on the `at:live:segment` event + the Debug
  panel — relevant because live mode's growing-window re-sends add up.
- **Answer to the brief's open question** ("where does cost display live — tool,
  embedder, or both?"): **both** — the tool shows it (per transcription / file /
  session / live-segment), and now returns `generationId`+`usage` so the embedder
  can too. Exposure of the id is sufficient for the embedder; we go further and
  resolve the exact figure ourselves (deferred `openrouter-cost.js`).

### Finding 7 — Embedding & key-injection contract — ⚠️ split (tool seam ✅ / vault 🔲)
- **Tool side (support ✅):** `setApiKey({apiKey,model})` is the documented injection
  entry point — it persists + connects, masks the key in the dev console, and works
  headlessly. That's the supported way for an embedder/host to supply the SG-API
  secret. Documented in the manifest + SKILL.
- **Push-back to vault level 🔲:**
  - **Key distribution / SG-API-secret minting / the admin vault** are NOT the
    tool's job. The tool is BYOK-by-default + a single `setApiKey` seam; *where the
    key comes from and how it's bounded* is the vault/SG-API layer (see the related
    v0.2.69 review of the release + strategy briefs).
  - **The BYO / early-adopter-key UI choice** I'll build **on top of** `setApiKey`
    **once a key source for option 2 exists** — today there's nothing to wire the
    "sponsored key" radio to, so it's blocked on the vault layer, not on the tool.
  - **Graceful secret exhaustion** is a **shared** contract. The *detection* of
    TTL/usage-count exhaustion lives in the SG-API-secret layer (the tool can't know
    a key's budget). What the **tool** can do is **map provider auth/quota responses
    to typed errors** when OpenRouter returns 401/402/429. **Proposed typed-error
    vocabulary** (answering the brief's open question): `key-invalid` (401),
    `budget-exceeded` (402), `rate-limited` (429), and `key-exhausted` as the generic
    "the distributed secret is no longer usable". **Caveat:** this needs
    `sg-llm-request` to surface the HTTP **status** in its error detail (today the
    transport gets a message string). So the honest status is: **typed-error mapping
    is 🔲 PROPOSED, blocked on `sg-llm-request` exposing the status code** — I don't
    want to string-match error text (brittle). I'll raise that as a small ask on the
    LLM component; once it lands, the mapping in the tool is a few lines.

   tool's decode path).

   component team; unblocks the tool's typed key-exhaustion mapping.

decode path **more** robust in a vault frame, not less.
