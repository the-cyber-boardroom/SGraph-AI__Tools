# PART A — Source Map (SGraph-AI__App__Send)

## A.1 Headline

Send has a **production-quality browser PKI PoC** built on **pure Web Crypto**
(no forge/jsrsasign/PKI.js) + **IndexedDB** for private keys, plus a **FastAPI
admin-lambda key registry** with an **append-only hash-chained transparency
log**. It is **identity/messaging PKI**, not classical X.509:

- **Algorithms:** RSA-OAEP 4096 (encryption), ECDH P-256 (key agreement), ECDSA P-256 (signing); AES-256-GCM as the symmetric data layer; SHA-256 fingerprints.
- **No** X.509 certificates, **no** CSR, **no** CA hierarchy, **no** CRL/OCSP.

# PART B — Migration & Decomposition Plan (this repo) — PROPOSED

All of Part B is **PROPOSED — does not exist yet.** It says how Send's PoC maps
onto this repo's three-tier, vanilla-ES-module, no-build conventions, and where
it intersects this repo's *existing* PKI assets (per `…__pki-support-map.md`).

## B.1 Fit assessment

Send's PoC is an **excellent fit**: pure Web Crypto + ES modules + web components,
no frameworks, no bundler — exactly this repo's stack. The main refactor work is
**not rewriting crypto** but **re-tiering**: splitting the admin-coupled
`pki-common.js` god-module into pure `core/` modules, turning the IFD/EventBus
components into self-contained `components/`, and turning the admin shell into a
standalone `tools/` page. The backend registry is the one piece with **no home
here** (this repo is static/CDN) — see B.4.

This repo already has adjacent pieces to reuse, not duplicate:
- `core/ssh/.../sg-ssh.js` — Ed25519 keygen + PEM/SSH formatting (shares encoding helpers).
- `core/crypto/.../sg-crypto.js` — AES-256-GCM (the symmetric layer `hybridEncrypt` needs).
- `tools/.../vault-browser/.../vault-schema-pki-key.js` — already renders `pki_public_key` (label/fingerprint/PEM) — the natural display target.
- `core/vault-client` — the encrypted container for storing private keys (alternative to / alongside IndexedDB).

## B.2 Tier 1 — `core/` modules (PROPOSED, pure JS, no UI, named exports)

Split Send's `pki-common.js` by concern (target <300 lines each):

| Proposed module | Path | Lifts from Send | Responsibility |
|---|---|---|---|
| `sg-pki` | `core/pki/v1/v1.0/v1.0.0/sg-pki.js` | `generateKey`, sign/verify | Keygen (RSA-OAEP 4096, ECDH P-256, ECDSA P-256), `sign()`/`verify()`. Reuse `sg-crypto` for AES. |
| `sg-pki-encoding` | `core/pki/.../sg-pki-encoding.js` | export/import PEM, b64 | SPKI/PEM/DER + JWK + base64; auto-detect RSA vs EC. Share helpers with `sg-ssh`. |
| `sg-pki-fingerprint` | `core/pki/.../sg-pki-fingerprint.js` | `computeFingerprint` | SHA-256 SPKI → `sha256:xxxx` (fills the missing fingerprint helper noted in the existing PKI map §3.5). |
| `sg-pki-hybrid` | `core/pki/.../sg-pki-hybrid.js` | `hybridEncrypt`/`hybridDecrypt` | RSA-OAEP-wraps-AES-256-GCM encrypt-then-sign payload v2 `{v,w,i,c,sig}`. |
| `sg-pki-store` | `core/pki/.../sg-pki-store.js` | `PKIDatabase` | IndexedDB keystore (keys + contacts). Optional `sg-vault-client` backend for encrypted-at-rest private keys. |
| `sg-pki-registry-client` | `core/pki/.../sg-pki-registry-client.js` | `admin-api-keys.js` | HTTP client for publish/lookup/unpublish/list/log (points at whatever backend B.4 picks). |

## B.4 Tier 3 — `tools/` (PROPOSED) + the backend question

- **`tools/.../pki-manager/`** — a standalone tool page composing the components
  above into the admin shell's PKI workflow, **plus the mandatory JS Tool API**
  (`SgToolApi.register()` + `activate()` + three SKILL files) per `.claude/CLAUDE.md`.
  This is the headless-testable, agent-drivable surface.

- **Backend / registry — DECISION NEEDED.** This repo is **static/CDN with no
  server** (Key Rule §12: client-side only). The Send registry is a FastAPI
  admin lambda. Options to resolve before any registry code:
  1. **Client-only first** — ship keygen/sign/verify/encrypt/contacts entirely
     client-side (no registry). This is fully in-scope for a static repo and
     covers most of the lifecycle. *(Recommended first slice.)*
  2. **Registry stays in Send** — tools repo ships `sg-pki-registry-client`
     pointing at the existing Send admin-lambda endpoints (CORS permitting).
  3. **Registry on send.sgraph.ai / a new service** — new infra; out of this
     repo's static scope; needs a separate brief.

## B.5 The gaps to fill (beyond a straight port)

Send itself is missing the classical-PKI half. Whether to build it depends on a
real consumer (none today — do not build speculatively):
- **CSR generation** + **self-signed X.509** + **cert parse/validate** — would
  need ASN.1/DER encoding. This is the largest net-new effort and is **MISSING in
  both repos**. Recommend a separate brief only when a code-signing / S/MIME
  consumer appears.
- **Ed25519/X25519** identity keys — aligns with this repo's existing `sg-ssh`
  Ed25519 work and the auth-mvp Phase 2 vault identity key. Cheaper than X.509
  and more consistent with the platform direction.
- **Formal revocation (CRL/OCSP)** — only if certificates are introduced.

## B.6 Recommended sequencing (PROPOSED)

1. **core/pki foundation** — `sg-pki` + `sg-pki-encoding` + `sg-pki-fingerprint`
   + `sg-pki-hybrid` + `sg-pki-store` (client-only; reuse `sg-crypto`/`sg-ssh`).
2. **Components** — `<sg-pki-keys>`, `<sg-pki-contacts>`, `<sg-pki-encrypt>`,
   wired to `vault-schema-pki-key` for display.
3. **Tool** — `pki-manager` page with SgToolApi + SKILL files (client-only slice).
4. **Registry slice** — only after the B.4 backend decision; add
   `sg-pki-registry-client` + `<sg-pki-publish/lookup/registry/log>`.
5. **Net-new (separate briefs)** — Ed25519 identity alignment; X.509/CSR/CA only
   on a concrete driver.

Each step: small files (<300 lines), land minimal-then-extend, and update the
reality docs + the existing `…__pki-support-map.md` (move items from PROPOSED to
EXISTS) in the same commit.
