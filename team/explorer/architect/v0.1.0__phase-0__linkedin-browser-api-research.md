# Research — Browser-from-LinkedIn API patterns (Phase 0)

**Date:** 26 Apr 2026
**Author:** Research agent (general-purpose) dispatched by claude-code session
**Trigger:** Phase 0 probes confirmed CORS-block on `api.linkedin.com` + `oauth/v2/accessToken` from `dev.tools.sgraph.ai`. Before picking between Option A (managed proxy) and Option B (BYO proxy) per brief 2/5, we needed to know what actually exists in the wild.

---

## TL;DR

**Pick Option A — single managed Cloudflare Worker on `tools.sgraph.ai`.** Direct probes today (26 Apr 2026) covered every relevant LinkedIn endpoint — `/v2/userinfo`, `/v2/me`, `/oauth/v2/accessToken`, even `/oauth/.well-known/openid-configuration` — and **none** return any `Access-Control-Allow-*` header; the preflight to `accessToken` even returns 404. There is no browser-direct path on any LinkedIn surface, no public reusable LinkedIn proxy worth mirroring, and the entire SaaS publisher and Chrome-extension ecosystem either runs server-side or scrapes the LinkedIn DOM — confirming Option D is closed and BYO-proxy (B) is unjustified friction for v1 with zero precedent users will recognise.

**Migration path A→B is cheap.** Build A; expose a `proxyUrl` config that defaults to `https://linkedin-proxy.tools.sgraph.ai`; power users can override. No architectural rework later.

## Endpoint-level findings (all probed 26 Apr 2026)

| Endpoint | CORS? | Notes |
|---|---|---|
| `/v2/userinfo` (OIDC) | **Blocked.** | Returns 401 with **zero** `Access-Control-Allow-*` headers. Browser-direct fails even with a valid Bearer. |
| `/v2/me` | **Blocked.** | Same shape: 401, no CORS headers. |
| `/rest/posts` | **Blocked.** | Confirmed by our own Phase 0 probe. |
| `/oauth/v2/accessToken` | **Blocked.** | Bonus finding: `OPTIONS` preflight returns **HTTP 404 from Cloudflare** (LinkedIn fronts the OAuth host with Cloudflare and doesn't register an OPTIONS handler). This is why the browser saw `ERR_FAILED 401`; it couldn't preflight at all, so the body 401 was the simple-CORS attempt failing on the response. |
| `/oauth/.well-known/openid-configuration` | **Blocked too.** | Public discovery doc, 200 OK, but no `Access-Control-Allow-Origin`. Even the JWKS-pointer document can't be fetched client-side. |
| `/oauth/openid/jwks` | Not re-probed but assume blocked. | Same host. **Consequence:** if you want to verify `id_token` signatures in the browser, the proxy must also serve JWKS (cached). |

### OIDC silver lining (does NOT remove the proxy need, but trims the auth panel's API surface)

The `id_token` returned alongside `access_token` in the token-exchange response already contains:

```
sub, name, given_name, family_name, picture, email, email_verified, locale
```

So **once the proxy completes the token exchange, the auth panel does NOT need to call `/v2/userinfo` at all.** A plain JWT decode in the browser is enough for displaying the signed-in user. Signature verification is the only thing that still needs JWKS — and even that can be skipped if the id_token came over TLS from our own proxy (treat as trusted).

## Recommended proxy reference

**Mirror [`gr2m/cloudflare-worker-github-oauth-login`](https://github.com/gr2m/cloudflare-worker-github-oauth-login)** (ISC, ~50 LOC). Cleanest reference for "POST `code` from SPA → Worker exchanges with provider → return token + CORS headers." Required changes for LinkedIn:

1. Retarget upstream URL → `https://www.linkedin.com/oauth/v2/accessToken`
2. Body format → `application/x-www-form-urlencoded` (per LinkedIn docs)
3. Add CORS headers on response: `Access-Control-Allow-Origin: https://tools.sgraph.ai` (and `dev.tools.sgraph.ai`), `Access-Control-Allow-Headers: Authorization, Content-Type, LinkedIn-Version, X-Restli-Protocol-Version`, `Access-Control-Allow-Methods: GET, POST, OPTIONS`
4. Add a second route that forwards `/rest/*` calls — pass through `Authorization: Bearer …` from the browser, plus inject `LinkedIn-Version: 202504` and `X-Restli-Protocol-Version: 2.0.0` server-side
5. Handle `OPTIONS` preflight explicitly (return 204 with the CORS headers)

## Risks / gotchas surfaced

- **Client secret placement:** LinkedIn's auth-code exchange requires `client_secret` even with PKCE (PKCE is opt-in per app, gated by LinkedIn support per docs). In Option A the secret lives in the Worker — fine. In Option B every BYO user needs their own LinkedIn app + secret in their own Worker, multiplying the verification-approval burden across users. **This alone tilts strongly toward A.**
- **Rate-limit blast radius for A:** all users' calls share `tools.sgraph.ai`'s LinkedIn app daily quota and IP. Mitigation: have the Worker forward the user's token only (never act with the app's own creds beyond the token swap), so per-user quotas apply, not app-wide.
- **JWKS fetching:** if we want to verify `id_token` signatures in-browser, the proxy must expose a cached `/jwks` route. Otherwise treat the id_token as opaque-but-trusted because it came over TLS from our own Worker. Reasonable for v1.
- **`LinkedIn-Version` header and Restli quirks:** the `/rest/*` API is versioned monthly and the Worker must allow those headers in `Access-Control-Allow-Headers` AND forward them upstream. Easy to miss; will manifest as opaque 426 / 400 errors.
- **Cloudflare's bot-management on LinkedIn's edge:** the OAuth host is fronted by Cloudflare (`server: cloudflare`, `cf-ray`, `__cf_bm` cookie). Server-to-server traffic from another Cloudflare Worker is typically fine, but aggressive call rates from a single Worker colo can be challenged. Use exponential backoff and surface 4xx/429 cleanly to the UI.
