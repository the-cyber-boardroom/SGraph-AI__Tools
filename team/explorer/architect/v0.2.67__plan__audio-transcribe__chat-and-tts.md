# Plan — Audio Transcribe extensions: Chat-with-transcript & Text-to-Speech

**Version:** v0.2.67
**Type:** Planning / exploration (architecture + product)
**Status:** PROPOSED — neither feature exists yet. Cross-checked against the
Reality Document. Building blocks referenced below DO exist today (✅); the new
wiring is labelled 🔲 PROPOSED.

---

## 0. Purpose

Two natural extensions to `audio-transcribe`, both reusing the same workflow +
building blocks the tool already leans on (the SgToolApi primitive, the isolated
LLM transport, sg-layout tabs, sg-audio-viz, the per-recording panel):

- **A. Chat with the transcription** — a chatbot whose system prompt carries
  context + the actual transcript, so a user can ask questions of / summarise /
  reformat a voice note.
- **B. Text-to-Speech** — generate audio from text (for demos, for full
  round-trip testing, and as a user feature that could spin out into a standalone
  `voice-gen` tool).

Both are ~90% reuse. Neither needs a server (chat is BYOK OpenRouter; TTS is
local Kokoro WASM).

---

## A. Chat with the transcription 🔲

### What
A chat panel seeded with a **system prompt = context + transcript(s)**. Two
scopes:
- **Per-recording** — chat about one item's selected transcript (lives as a
  sub-section / "💬 Chat" of the per-recording detail panel).
- **Session** — chat across *all* transcripts (a "💬 Chat" tab in the right
  stack, next to Queue/Debug), system prompt concatenates every done transcript
  with file-name headers.

### Reuse (✅ exists)
- `components/llm/sg-llm-chat-history` + `sg-llm-chat-input` — the chat UI
  (already used by `agent-with-tools` / `multi-agent-chat`).
- `components/llm/sg-llm-request` — the OpenRouter fetch engine (text models).
- The tool's **isolated transport** pattern + the persisted OpenRouter key
  (`setApiKey`) — chat reuses the same key + a text model.
- `sg-llm-events` bus contract (`llm:connected` / `llm:send` / `llm:request-complete`).

### Design notes
- **Models:** chat uses *text* models (e.g. `google/gemini-3.5-flash`,
  `anthropic/claude-haiku-4.5`) — a separate small curated list (or reuse
  `sg-llm-model-picker`), NOT the audio-input list. Add `chat-models.js`.
- **System prompt template:** `"You are helping the user work with a transcript.
  Context: {context}. Transcript(s):\n{transcripts}"` — editable in an Advanced
  field for power users.
- **Transport:** reuse `makeIsolatedTransport` (rename to a shared helper) — chat
  is conversational (multi-turn), so each turn is one isolated request; history
  is held client-side in `sg-llm-chat-history`.
- **Cost & provenance:** route chat turns through the same exchange log so the
  Debug panel shows them too; add chat cost into `getCostSummary` (a separate
  bucket).

### JS API 🔲
`startChat({ scope:'item'|'session', id?, context? })`, `chat({ chatId, message })
→ { reply }`, `getChat({ chatId })`. Events `at:chat:*`.

### Phasing
1. Per-recording chat sub-panel (one transcript) + `chat()` action.
2. Session chat tab (all transcripts) + editable system prompt.
3. Provenance + cost integration; export chat to the bundle `.zip`.

## B. Text-to-Speech (voice from text) 🔲

### What
Type/paste text → synthesise speech → play (with a waveform), download a `.wav`,
**or drop it straight into the transcription queue** (round-trip testing). The
"known text in → audio → transcribe → compare" loop is gold for QA and for
generating the real-speech samples the tool currently lacks.

### Reuse (✅ exists)
- `core/sg-tts/v0/v0.1/v0.1.0/sg-tts.js` — Kokoro 82M ONNX TTS (8-worker pool),
  **already used by `video-creator`**. Local, free, no server; ~160 MB model
  cached on first use (via the existing cache pattern).
- `core/sg-audio-decode` WAV encoder + `components/sg-audio-viz` (playback viz).
- The tool's existing `samples.js` ingest path (`buildSampleFile` → `addFiles`).

### Design notes
- **Where:** start as a small "🗣 Create voice" panel inside audio-transcribe
  (left stack, alongside Source) so the round-trip (TTS → queue → transcribe) is
  one click. Keep the code in a self-contained `api/tts.js` + `ui/ui-tts.js` so
  it can be **lifted into a standalone `voice-gen` tool** later with no rewrite.
- **Round-trip test harness:** a dev action `roundTrip({ text, model })` that
  TTS-synthesises `text`, transcribes it, and reports a similarity score — a
  cheap, deterministic-ish end-to-end check (and a way to auto-generate sample
  audio for the repo).
- **Cost:** TTS is **free/local** (no OpenRouter) — a nice contrast to the
  transcription cost; show generation time instead.

### JS API 🔲
`synthesize({ text, voice?, model? }) → { blob, durationMs }`,
`addSynthesized({ text, voice? })` (synth → addFiles), `roundTrip({ text })`.

### Phasing
1. `api/tts.js` (load model lazily, synthesise → WAV blob) + a minimal panel
   (text in → play + download).
2. "Add to queue" + `roundTrip()` (the testing/demo win).
3. Extract to a standalone `voice-gen` tool; audio-transcribe imports it or links.

## C. Shared considerations

- **One LLM transport, two lists.** Factor `makeIsolatedTransport` into a shared
  helper used by transcription *and* chat. Keep `audio-models.js` (audio-in) and
  a new `chat-models.js` (text) separate.
- **Provenance everywhere.** Both features should emit `at:llm:exchange` so the
  Debug panel is the one place to see *all* model traffic.
- **No new server.** Chat = BYOK OpenRouter (existing key); TTS = local Kokoro.
- **Versioning/docs discipline** (per the tool README): bump version + add a
  `RELEASES` entry + a Node smoke test + a Playwright check, per feature.
- **Standalone potential.** TTS is the most spin-out-able (a `voice-gen` tool);
  build it self-contained from day one.

## D. Open questions

1. **Chat scope default** — per-recording first, or session-wide first?
2. **Chat model list** — curate a tiny text list, or reuse `sg-llm-model-picker`'s
   full OpenRouter list?
3. **TTS home** — in-tool panel first (fastest round-trip), or straight to a
   standalone `voice-gen` tool?
4. **Round-trip scoring** — exact match, normalised WER, or an LLM-judge?
5. **Voices** — expose Kokoro's voice set, or one default to start?

---

## E. Next step

Recommend: **A1 (per-recording chat)** and **B1 (in-tool TTS panel + round-trip)**
as the first slices — both are small, reuse-heavy, and immediately useful (chat
for working with a transcript; TTS for generating the real-speech test samples
the tool needs). Each ships as its own versioned release with tests, following
the audio-transcribe README's dev checklist.
