## 1. The one reconciliation that matters

Both briefs talk about "the vault" distributing keys and hosting the tool. That
collapses **three different layers** into one word. Keeping them separate is the
whole point of this review:

| Layer | What it is | Where it lives | Status here |
|---|---|---|---|
| **A. The tool** | audio-transcribe — record/drop/Live → transcribe via OpenRouter, client-side | THIS repo (`tools/…/audio-transcribe/`) | ✅ EXISTS |
| **B. Key source** | where the OpenRouter key comes from | (i) user paste — BYOK; (ii) an **admin vault** handing a sponsored/shared key | (i) ✅ EXISTS · (ii) 🔲 PROPOSED |
| **C. Hosting + observability** | "vault-powered-websites" serving the page; an observability vault collecting append-mode usage logs | SEPARATE infra (vault/admin services) | 🔲 PROPOSED, out of this repo |

**Today the tool only knows Layer A + Layer B(i).** It calls
`https://openrouter.ai/api/v1/chat/completions` **directly from the browser**
with a key the user pasted (persisted in `localStorage 'sg-openrouter-mgmt-key'`,
the rule-7 exception). It never sees a vault, a server, or an observability log.
The briefs are mostly describing **B(ii) + C**, which are real programme goals
but are **not wired into this tool**.

This is the same fork already analysed in `v0.2.66` §2 ("where does the
OpenRouter call happen?"). Nothing in the new briefs changes that the **managed
path needs infrastructure this repo does not contain.**

## 2. Dev-brief claims → reality

**B(ii) — key distribution via an admin vault (SG API secrets).**
The brief proposes the page fetch a sponsored/shared OpenRouter key from an
**admin vault** (SG API secrets), so an "early adopter" never pastes a key.
- 🔲 PROPOSED. No vault fetch, no admin-vault client, no secrets endpoint exists
  in the tool. The hook that *does* exist: **`setApiKey({apiKey, model})`** ✅ — a
  registered SgToolApi action (added v0.1.8) for agentic/headless callers to
  inject a key programmatically. A future vault-bootstrap script could call
  `window.__tool.setApiKey()` after retrieving a key — **that is the clean seam**,
  and it already works. The tool needs **no change** to be driven this way; the
  vault-fetch code is the new (separate) piece.
- ⚠️ Security note unchanged from v0.2.66 §2: a **shared** key handed to a browser
  is exfiltratable. "Sponsored early-adopter key from a vault" only differs from
  "paste your own key" in *who pays*; it does **not** make a browser-held shared
  key safe. A spend cap / proxy is still the only real control. Label this
  honestly in any UI: an early-adopter key is a **trust-limited convenience**, not
  a security boundary.

**"Bring-your-own-or-early-adopter-key" UI choice.**
- 🔲 PROPOSED as a *choice*, but **half of it exists**: BYOK is the entire current
  Model & Cost flow ✅. Adding a radio ("use my key" / "use a sponsored key") is a
  small UI change *once* a key source for option 2 exists. Without B(ii) infra
  there is nothing to wire the second radio to — so this is **blocked on C/B(ii),
  not on the tool.**

**Three-component "vault-powered-websites" hosting.**
- 🔲 PROPOSED, **out of scope for this repo.** This tool is served as flat static
  assets via S3 + CloudFront (the project's hosting model). Whether the *page* is
  later served by a vault-powered-website host is an **operations/hosting**
  decision that does not touch the tool's code. The tool is already
  "host-agnostic": pure static ES modules, no server assumptions.

**Two-vault split (admin vault + observability vault) + append-mode logs.**
- 🔲 PROPOSED, out of this repo. The tool has **no telemetry** — by design
  (security rules 12–13: client-side only, no data exfiltration). The closest
  EXISTING primitive is the in-memory **provenance log** (`getExchanges()` +
  `at:llm:exchange`, v0.1.8) ✅: every LLM request/response this session (model,
  prompt, tokens, cost, generation id, raw response — **never audio bytes**), kept
  in memory, surfaced in the Debug tab. An observability-vault integration would
  **subscribe to `at:llm:exchange`** and append records to a vault — again a clean,
  already-emitted seam, with the vault writer living **outside** the tool. Any such
  integration must respect rule 13: usage metadata is one thing, **user audio /
  transcripts must not be shipped** without explicit consent.

**"Get users to spend a few dollars" as the validation metric.**
- Product metric, not code. Worth noting it **requires the managed/credits path**
  (Model 2 in v0.2.66) to be *us* billing — under pure BYOK the user spends on
  *their own* OpenRouter account and we measure nothing. So this metric is
  **coupled to B(ii)+C + a proxy/credits backend** (🔲, see v0.2.66 §6). Under
  BYOK today we can only observe *session* cost in-browser (`getCostSummary()` ✅),
  never aggregate spend.

## 3. Strategy-brief claims → reality

**Shift "from primitives to experience"; max-visibility / max-simplicity.**
- Directionally already underway ✅. v0.1.10–0.1.15 were mostly *experience* work:
  visible version badge, Stop button + live seconds, per-recording chat with
  auto-context, 3-level cost display, and the new **Live tab**.

**"Big button to start, drop the file here."**
- **"Big button to start" → now EXISTS ✅** as of v0.1.15: the **🔴 Live tab is a
  single large start/stop button** — arguably the most "experience-first" surface
  in the tool. This directly realises the strategy-brief's headline gesture.
- **"Drop the file here" → EXISTS ✅**: the Source tab is a multi-file
  drop/upload zone (incl. WhatsApp `.opus`). What's PROPOSED 🔲 is making the drop
  zone the *primary, full-bleed* hero of a stripped-down landing variation (see
  next point) rather than one tab among several.

**"Build multiple variations."**
- 🔲 PROPOSED. Today there is **one** tool page (a tabbed sg-layout shell). The
  briefs want several **focused single-purpose variations** (e.g. a bare
  "drop → transcript" page; a bare "talk → transcript" Live page). The
  architecture **supports this cheaply** ✅: the **JS Tool API is the product, the
  UI is one consumer** (CLAUDE.md "JS Tool API Primitive"). A variation is a new
  thin `index.html` + a minimal `ui-*` that drives the **same** `window.__tool`
  (`addFiles`/`transcribeAll` or `startLive`/`stopLive`). No core/api changes
  needed — this is the recommended next experiment and is **low-risk**.

**Competitive mapping (WhatsApp-audio transcription tools).**
- Research input, no code impact. The tool's existing **`.opus` three-tier
  never-fail decode** ✅ is the relevant moat to lean on competitively (most
  browser tools choke on WhatsApp `.opus` on Safari/iOS; this one doesn't).

## 4. What I'd actually build next (recommendation)

Ordered by value/effort, **all client-side, no new backend** (keeps within this
repo + the reality rules):

1. **A "Live-first" minimal variation** 🔲 — a new bare page that is *just* the
   🔴 Live big button (+ the drop zone as the only alternative). Pure new
   consumer of the existing API; directly tests the strategy-brief's
   "max-simplicity" thesis. **Smallest, highest-signal experiment.**
2. **Sponsored-key seam, documented not built** 🔲 — keep `setApiKey()` as the
   single injection point; write the SKILL/README note that a vault bootstrap
   calls it. Do **not** add vault-fetch code here; that belongs to the
   vault/admin layer. Add the BYOK-vs-sponsored radio **only when** a key source
   exists.
3. **Observability hook, opt-in** 🔲 — document that `at:llm:exchange` is the
   subscribe point for an external observability-vault writer; ship nothing that
   exfiltrates by default (rule 13). Audio/transcripts stay local unless the user
   explicitly bundles/sends (the existing `sendViaSgSend` path ✅).

**Explicitly NOT in this repo:** the proxy/credits backend, Stripe, the admin
vault, the observability vault, and vault-powered-website hosting. Those are the
v0.2.66 "managed credits" dependencies and the programme's vault services — real,
but separate. This tool stays a clean, host-agnostic, BYOK-by-default client that
**already exposes the exact seams** (`setApiKey`, `at:llm:exchange`,
`getCostSummary`) those layers need.

---

## 5. One-line summary

The briefs are sound programme direction, but most of what they describe
(key-distribution vault, observability vault, vault hosting, credits/spend
metric) is **separate infrastructure, 🔲 PROPOSED, outside this repo**. What the
tool owes — and **already provides** — are clean seams: **BYOK + `setApiKey()`**
for keys, **`at:llm:exchange`** for observability, and a **JS-API-first design**
so the "experience" variations are cheap. The strategy-brief's headline gesture
("big button to start") **shipped today as the 🔴 Live tab**.
