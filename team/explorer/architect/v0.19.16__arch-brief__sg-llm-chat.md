# Architecture Brief: sg-llm-chat — Traditional Multi-Turn Chat Components

**Version:** v0.19.16
**Date:** 31 March 2026
**Role:** Architect (Explorer team)
**Type:** Architecture brief + component spec
**Status:** Pre-implementation — approved for build
**Follows:** v0.19.11 (one-shot component family)

---

## 1. Why A Separate Chat Component Family?

The one-shot component family (`sg-llm-reality`, `sg-llm-output` etc.) is engineered for **precision, single-request engineering** — you build the entire model universe before sending, control costs exactly, and never accumulate drift.

Traditional chat serves a different use case: **exploratory, iterative conversation**. The user types a message, gets a reply, responds to it, and the model carries context forward automatically. Conversation history grows with each turn.

These are complementary, not competing. The same underlying components (`sg-llm-request`, `sg-llm-connection`, `sg-llm-stats`) serve both workflows.

## 2. New Components

Two new components extend the `components/llm/` family:

### `sg-llm-chat-history` — Conversation Display + State Manager

**Tag:** `<sg-llm-chat-history>`

**Responsibility:** Owns and renders the conversation. Displays alternating user/assistant bubbles. Handles streaming (assistant bubble updates live). Tracks the full turn array and assembles the messages array for SEND. Optionally shows a collapsible system prompt editor.

**UI:**
```
┌─ System (optional, collapsible) ──────────────────┐
│  You are a helpful assistant...            [close] │
└───────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────┐
│                          [User bubble] ▶ You     │
│  ┌─────────────────────────────────────────────┐ │
│  │ Hello! How can I help you today?            │ │
│  │                         [Assistant bubble]  │ │
│  └─────────────────────────────────────────────┘ │
│                          [User bubble] ▶ You     │
│  ┌─────────────────────────────────────────────┐ │
│  │ Let me explain...          ░░ (streaming)   │ │
│  └─────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────┘
```

**Public API:**
```js
history.getMessages()          // → [{role, content}] — full array for SEND
history.setSystemPrompt(text)  // programmatic system prompt
history.clear()                // wipe conversation
history.exportMarkdown()       // → string (conversation as markdown)
```

**Consumes (on parentElement):**
- `llm:chat-message` — `{ text, attachments }` — adds user bubble, emits SEND with full history
- `llm:connected` — stores model/provider for SEND event
- `llm:model-changed` — updates stored model
- `llm:request-start` — shows streaming indicator in last assistant bubble
- `llm:request-chunk` — updates streaming bubble with `accumulated`
- `llm:request-complete` — finalises assistant bubble, adds turn to `_turns`
- `llm:request-error` — shows error state in bubble
- `llm:request-cancel` — marks bubble cancelled

**Emits (on parentElement):**
- `llm:send` — `{ messages[], model, provider, mode: 'build' }` — full conversation array

**Internal state:**
```js
this._turns   = []          // [{ role, content, attachments? }] — completed turns
this._model   = ''
this._provider = ''
this._systemPrompt = ''
this._streamingEl = null    // the currently-streaming assistant bubble element
```

**Turn → messages array assembly:**
```js
// For each completed turn:
// - user turn with text only  → { role: 'user', content: text }
// - user turn with images     → { role: 'user', content: [{ type:'text', text }, { type:'image_url', image_url:{ url } }] }
// - user turn with text files → text content appended with "--- Attachment: name ---\n{content}\n"
// - assistant turn            → { role: 'assistant', content: text }
// Prepend system if _systemPrompt set
```

### `sg-llm-chat-input` — Message Input Bar

**Tag:** `<sg-llm-chat-input>`

**Responsibility:** Accepts user text input and file/image attachments. Emits `llm:chat-message` when user submits. Disables during in-flight requests (shows Cancel instead of Send).

**UI:**
```
┌─ Attachments (if any) ───────────────────────────┐
│ [📎 file.pdf ✕]  [🖼 image.png ✕]               │
└───────────────────────────────────────────────────┘
┌─ Input area ──────────────────────────────────┬──┐
│  Type a message... (shift+enter=newline)      │▶ │
│                                               │  │
│  [📎]                                        │  │
└───────────────────────────────────────────────┴──┘
```

**Public API:**
```js
input.clear()           // programmatic clear
input.focus()           // focus the textarea
input.setDisabled(bool) // enable/disable (called by REQUEST_START/COMPLETE)
```

**Consumes (on parentElement):**
- `llm:request-start`   — disables input, shows Cancel button
- `llm:request-complete`— re-enables input, hides Cancel
- `llm:request-error`   — re-enables input
- `llm:request-cancel`  — re-enables input

**Emits (on parentElement):**
- `llm:chat-message` — `{ text, attachments: [{id, name, type, size, dataUrl?, textContent?}] }`
- `llm:cancel`       — when user clicks Cancel during streaming

**Attachment handling:**
- Attach button → `<input type="file" multiple>` picker (images + text files)
- Drag-and-drop onto input area
- Clipboard paste (Ctrl+V — images become dataUrl, text stays as text)
- Preview thumbnails for images, filename badges for text files
- `✕` to remove individual attachments

## 3. Custom Event

The chat components introduce one new event name not in `sg-llm-events.js` v0.1.0:

```js
const CHAT_MESSAGE = 'llm:chat-message';  // { text, attachments[] }
```

This is defined as a module-level constant within each component — it does NOT require modifying `sg-llm-events.js` (which is frozen).

| Component | Why not used |
|-----------|--------------|

| `sg-llm-output` | Replaces with inline bubbles in sg-llm-chat-history |
| `sg-llm-attachments` | Replaces with inline attachment picker in sg-llm-chat-input |
| `sg-llm-debug` | Optional — could be added but excluded from v0.1.0 |
| `sg-llm-infographic` | Not relevant for general chat |

## 7. Differences From One-Shot

| Aspect | One-Shot Chat | Traditional Chat |
|--------|--------------|-----------------|
| History | User constructs manually (history blocks) | Accumulates automatically per turn |
| Context control | Explicit (token count per block) | Implicit (total grows with conversation) |
| Cost | Predictable before send | Grows unpredictably as conversation extends |
| Memory | User-managed (memory block + Mode 2) | None (full history sent every time) |
| Bundle save | Full reality snapshot | Conversation turns + connection config |
| Drift risk | None (you engineer each reality) | High (model carries forward all context) |
| Best for | Precision engineering, cost control | Exploration, debugging, quick iteration |

The one-shot tool and the chat tool are different doors into the same underlying request engine.

## 9. Bundle Shape for Chat

```js
{
    id: 'uuid',
    timestamp: 'ISO-8601',
    parent_id: 'previous-bundle-id',
    config: { provider, model, streaming },
    reality: {
        turns: [
            { role: 'user',      content: 'Hello' },
            { role: 'assistant', content: 'Hi there!' },
        ],
        systemPrompt: 'You are a helpful assistant.'
    },
    response: { text, tokens: { prompt, completion, total }, cost, duration_ms, finish_reason }
}
```

Note: `reality.turns` (not `reality.blocks`) distinguishes chat bundles from one-shot bundles.
