## 4. The hard problems, and how we solve them

### 4.1 ⚠️ S3 CORS is a hard prerequisite — flag this before any code is written

**This is the one genuine constraint on the brief as specified.** A no-backend browser app **cannot** read a private S3 bucket unless **that bucket carries a CORS policy naming our origin**. Valid credentials are not sufficient — the browser will block the response regardless. There is no client-side workaround; it is the bucket owner's one-time config change:

```json
[{
  "AllowedOrigins": ["https://tools.sgraph.ai", "http://localhost:8000"],
  "AllowedMethods": ["GET", "HEAD"],
  "AllowedHeaders": ["*"],
  "ExposeHeaders":  ["ETag","Content-Length","Content-Range","Content-Type",
                     "x-amz-request-id","x-amz-id-2","Last-Modified"],
  "MaxAgeSeconds":  3000
}]
```

`ExposeHeaders` matters as much as `AllowedOrigins`: without **`ETag`** exposed, our whole cache-key strategy (§5) is blind, and without `Content-Range` we lose ranged reads.

**If the bucket CORS cannot be changed**, the honest options are (a) front the bucket with a CloudFront distribution that adds CORS, or (b) a minimal signing/proxy worker — which breaks the "no backend" requirement. Recommendation: **make CORS a Phase 0 go/no-go check**, and ship `<sg-s3-connect>` with a diagnostic that distinguishes "CORS not configured" from "bad credentials" from "access denied", because those three failures are otherwise indistinguishable in the browser and will burn hours.

**Useful lever:** a **presigned URL** (query-string signing) is a *simple request* — no custom headers → **no CORS preflight**, and it works directly in `<a download>`, `<img>`, `<video>`. Header-signed requests always preflight because `x-amz-date` / `x-amz-content-sha256` are custom headers. Presigning still needs `AllowedOrigins` for `fetch()` to read the body, but it removes the `OPTIONS` round-trip per object — a real speed win when opening hundreds of log files. **Plan: presign by default for object GETs, header-sign for LIST.**

### 4.2 Credentials in a browser

The brief says assume an AWS token is available. Two things to hold to:

- **Prefer STS temporary credentials** (`accessKeyId` + `secretAccessKey` + **`sessionToken`**), scoped to `s3:GetObject`/`s3:ListBucket` on the one bucket, with a short TTL. The signer must support `x-amz-security-token`. Long-lived IAM user keys pasted into a browser are a standing liability — support them, but surface the expiry/scope in the UI.
- **Never `localStorage` for the secret.** Use `sg-credential-store` (browser password manager) or in-memory-only for the session. `sanitiseParams` on the `SgToolApi` `connect` method so keys never reach the execution log.

### 4.3 Listing at log-bucket scale

Log buckets routinely hold millions of objects. `ListObjectsV2` returns **≤1000 keys per call** with a `ContinuationToken`.

- Always list with **`Delimiter: '/'`** → `CommonPrefixes` gives pseudo-folders, so we page one directory level at a time instead of walking the whole bucket.
- **Exploit the date partitioning.** AWS log layouts are `.../{yyyy}/{mm}/{dd}/` — so a date picker maps directly to a prefix and skips the tree walk entirely. This should be a first-class UI control, not an afterthought; it is the single biggest determinant of perceived speed.
- Lazy-expand per node; cache each page (§5); infinite-scroll the object list with a "load next 1000" sentinel.

### 4.4 Compression — most AWS logs are `.gz`

Native, zero-dependency:

```js
const ds  = new DecompressionStream('gzip');
const txt = await new Response(blob.stream().pipeThrough(ds)).text();
```

Verified: **nothing in this repo uses `DecompressionStream` yet** — new ground, but it is a browser built-in (Chrome/Edge/Firefox; Safari 16.4+). Feature-detect and degrade with a clear message. Do the decompress **in a Web Worker** so a 200 MB expansion never janks the UI.

### 4.5 Large objects

- **Plain (uncompressed) logs:** `Range: bytes=…` for head/tail — open a 2 GB S3 access log instantly by fetching the last 1 MB. This is the "tail" experience.
- **Gzipped logs:** honest limitation — **you cannot range-read into the middle of a gzip stream**; it must be decompressed from the start. Mitigate by decompressing in a worker with progressive line emission, so the viewer paints the first lines while the rest streams.
- Viewer renders a **window** of lines, never the whole file, mirroring `sg-tree` v0.1.2.

### 4.6 AWS log formats to support

| Format | Typical key | Wire format |
|---|---|---|
| **CloudTrail** | `AWSLogs/{acct}/CloudTrail/{region}/{y}/{m}/{d}/…json.gz` | JSON, `{ Records: [...] }` |
| **ALB/ELB access** | `AWSLogs/{acct}/elasticloadbalancing/{region}/…log.gz` | space-separated, quoted fields |
| **CloudFront** | `{dist}.{yyyy-mm-dd-hh}.{hash}.gz` | TSV with `#Version` / `#Fields` header |
| **S3 server access** | `{prefix}{yyyy-mm-dd-HH-MM-SS}-{hash}` | space-separated, quoted, **uncompressed** |
| **VPC Flow Logs** | `AWSLogs/{acct}/vpcflowlogs/{region}/…log.gz` | space-separated + header line |
| **WAF** | `…` | gzipped JSON-lines |

`detectFormat()` keys off the **object key path first** (cheap and reliable, since AWS layouts are fixed) and falls back to sniffing the first bytes. Unknown formats degrade to the raw text viewer — never a dead end.

## 5. The cache design (sg-vfs + IndexedDB) — the core of the brief

**Why this is a good fit:** S3 log objects are **write-once and immutable**. Their **ETag** is a content hash. So an ETag-addressed cache entry is *permanently valid and never needs invalidating* — precisely the reasoning already proven in `sg-vault-cache` with its `-imm-` guard. We reuse the reasoning, on the VFS.

### Layout inside the VFS

```
/s3/{region}:{bucket}/
    listings/{prefixHash}.json     ← ListObjectsV2 page  (MUTABLE → TTL)
    objects/{etag}.txt             ← decompressed body   (IMMUTABLE → never expires)
    parsed/{etag}.json             ← normalised records  (IMMUTABLE, optional 2nd tier)
    index.json                     ← etag → { key, bytes, storedAt, lastUsed, format }
```

### Provider stack

```js
const layered = new LayeredProvider();
layered.addProvider(new MemoryProvider(),                       0);  // session-hot, ns
layered.addProvider(new IndexedDbProvider({dbName:'sg-s3-cache'}), 1);  // durable, cross-visit
const vfs = new VirtualFileSystem(layered, { bus });
await vfs.init();
```

Reads waterfall RAM → IndexedDB → S3, back-filling upward automatically; writes go through both. **This is free** — it is what `LayeredProvider` already does.

### Read-through flow (`core/s3-vfs-cache`)

1. `headObject(key)` → `ETag` *(or reuse the ETag already in the cached listing — saves a round-trip)*.
2. `vfs.exists('/s3/{b}/objects/{etag}.txt')` → **hit**: return, touch `lastUsed`. Done, zero network.
3. **Miss**: presigned `getObject` → (gunzip in worker) → `vfs.writeFile(...)` → update `index.json`.
4. Listings: same, but with a **TTL** (~5 min; configurable, and 0 for "live tail" prefixes) since new log objects keep landing.

### Two honest gaps in the VFS we must fill in `s3-vfs-cache`

1. **No quota accounting or eviction.** The VFS has neither. We maintain `index.json` ourselves, track bytes (the providers already compute `size` via `TextEncoder`), read `navigator.storage.estimate()`, enforce a configurable cap (default **200 MB**), and evict **LRU**.
2. **The VFS stores strings, not binary.** So cache the **decompressed text**, not the `.gz` bytes — it is what the viewer wants anyway and avoids base64's 33% inflation. Trade-off to state plainly: gzip logs expand ~10×, so the byte cap must be applied to *expanded* size. For genuinely huge objects, cache only the fetched **ranges** plus a metadata stub rather than the whole body.

**Side benefit worth naming:** S3 charges ~$0.0004/1000 GETs and ~$0.005/1000 LISTs. A warm cache over a browsing session cuts both request cost and latency; the `sg-vfs-event-viewer` panel makes the saving visible.

## 8. Testing

- **SigV4** — AWS publishes canonical request/signature test vectors; run them as **Node tests**, no AWS account, no network. This is the highest-value test in the whole build.
- **Cache logic** — Node tests against `MemoryProvider` (works headless; `IndexedDbProvider` needs a browser), then a Playwright pass for the real IndexedDB path incl. reload-persistence.
- **Parsers** — small fixture files per log format committed alongside; pure functions, trivially unit-tested.
- **End-to-end** — Playwright smoke driving `window.__tool` against a **mock S3** (intercept `fetch` and serve fixture XML/gz), so CI never needs AWS credentials.

## 9. Risks & open decisions

| Risk | Severity | Mitigation |
|---|---|---|
| **Bucket CORS not configurable** | 🔴 blocking | Phase 0 go/no-go; CloudFront fallback; explicit diagnostic in `<sg-s3-connect>` |
| Long-lived keys pasted in a browser | 🟠 high | Push STS temp creds; password-manager storage; sanitise logs; show expiry |
| Gzip cannot be range-read | 🟡 medium | Worker + progressive line emission; range-read only plain logs |
| IndexedDB quota exhaustion | 🟡 medium | LRU + `storage.estimate()` + visible cache panel + configurable cap |
| Clock skew breaks SigV4 (`RequestTimeTooSkewed`) | 🟡 medium | Read `Date` from an S3 error response and offset; surface clearly |
| Very wide log lines / 10M-line files | 🟡 medium | Virtualised rendering only; never build full DOM |

**Open decisions for you:**
1. **Credential model** — STS temporary only, or also accept long-lived IAM keys?
2. **Scope of Phase 5** — all six log formats, or start with CloudTrail + ALB (the two most asked for)?
3. **Cache cap default** — 200 MB proposed; log workloads may want more.
4. **Multi-bucket/multi-account** in v1, or single bucket first?

---

## 10. Recommendation

Build **Phase 0 first and alone.** Everything else in this plan is well-understood composition over components that already exist and work — the tree, the panels, the VFS cache, the JSON viewer, the tool API. The only genuine unknown is whether the target bucket will talk to a browser at all, and that is answered by a one-page spike in well under a session. Do not invest in UI until CORS is proven against the real bucket.
