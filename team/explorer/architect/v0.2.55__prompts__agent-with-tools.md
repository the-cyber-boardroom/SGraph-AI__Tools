**Version:** v0.2.55
**Date:** 2026-05-13
**Companion to:** `v0.2.55__arch-brief__agent-with-tools.md`

This document defines every prompt used by the `agent-with-tools` tool: the system message, tool-schema injection format, tool-call and tool-result conversation shapes, the JSON-in-content fallback (Phase 4), and per-model notes.

## 1. System prompt (runtime-loaded)

Loaded at startup by `agent-with-tools-api.js` via `fetch('./prompts/system.md')`. Stored as plain Markdown so it can be tuned without a JS deploy.

File path: `tools/v0/v0.1/v0.1.58/en-gb/agent-with-tools/prompts/system.md`

### 1.1 Template

```
You are an autonomous agent running inside a browser tool. You have access to a
set of tools that let you interact with the user's computer: read and write files,
list directories, run bash commands, and fetch URLs. All file paths are relative
to the user's workspace directory.

## How to use your tools

Call tools by name using the tool_calls format. You may call multiple tools in
a single response if the task requires it. Wait for all tool results before
calling tools again.

When you have finished the task — or cannot proceed without more information from
the user — reply with plain text explaining what you did and what (if anything)
the user should do next.

## Workspace rules

- Every file path you use must be relative (e.g. "README.md", "src/app.py").
- Do not attempt to access paths outside the workspace (e.g. "../", "/etc/").
- Do not run commands that could damage the host system (e.g. `rm -rf /`).
- If a task requires a destructive operation (delete, overwrite), confirm the
  specific path before acting.

## Workspace location

The workspace is mounted at {WORKSPACE_PATH} inside the Docker container. From
your perspective, all paths start from this root.

## Available tools

{TOOL_LIST}

## Style

- Be concise. Do not narrate each tool call — just call the tool and report the
  outcome in one sentence.
- If a tool call fails, describe the error briefly and either retry (if the fix
  is obvious) or ask the user what to do.
- When writing files, preserve existing formatting unless the user asks you to
  change it.
```

### 1.2 Placeholder substitution (done in `agent-with-tools-api.js`)

| Placeholder | Replaced with |
|---|---|
| `{WORKSPACE_PATH}` | The value of `sg-local-bridge`'s `workspace` attribute (e.g. `/workspace`) |
| `{TOOL_LIST}` | Markdown bullet list of enabled tools, generated from `sg-tool-definition`'s current schema — one line per tool: `` - `lb_read_file(path)` — Read a text file from the workspace. `` |

The substitution happens once on `tool:ready` and again whenever `llm:tool-defs-changed` fires.

## 2. Tool schema injection (sent with every LLM request)

`sg-llm-request` sends an `tools` array in the request body alongside `messages`. Each entry is a JSON Schema object. Below are the six locked schemas.

```json
[
  {
    "type": "function",
    "function": {
      "name": "lb_read_file",
      "description": "Read a text file from the local workspace. Returns the file content as a string.",
      "parameters": {
        "type": "object",
        "properties": {
          "path": { "type": "string", "description": "File path relative to the workspace root." }
        },
        "required": ["path"]
      }
    }
  },
  {
    "type": "function",
    "function": {
      "name": "lb_write_file",
      "description": "Write (overwrite) a file in the local workspace. Creates parent directories if needed.",
      "parameters": {
        "type": "object",
        "properties": {
          "path":        { "type": "string",  "description": "File path relative to the workspace root." },
          "content":     { "type": "string",  "description": "Full content to write. Must be plain text." },
          "create_dirs": { "type": "boolean", "description": "Create missing parent directories. Default true." }
        },
        "required": ["path", "content"]
      }
    }
  },
  {
    "type": "function",
    "function": {
      "name": "lb_delete_file",
      "description": "Delete a file from the local workspace.",
      "parameters": {
        "type": "object",
        "properties": {
          "path": { "type": "string", "description": "File path relative to the workspace root." }
        },
        "required": ["path"]
      }
    }
  },
  {
    "type": "function",
    "function": {
      "name": "lb_list_folder",
      "description": "List entries in a workspace folder. Returns names, types (file/directory), sizes, and modification times.",
      "parameters": {
        "type": "object",
        "properties": {
          "path":      { "type": "string",  "description": "Folder path relative to the workspace root. Use \".\" for the root." },
          "recursive": { "type": "boolean", "description": "Include sub-folders recursively. Default false." }
        },
        "required": ["path"]
      }
    }
  },
  {
    "type": "function",
    "function": {
      "name": "lb_run_bash",
      "description": "Run a bash command inside the workspace container. Returns stdout, stderr, and exit code. Commands run as the container user — do not attempt to escape the container.",
      "parameters": {
        "type": "object",
        "properties": {
          "command":   { "type": "string",  "description": "The bash command to run." },
          "cwd":       { "type": "string",  "description": "Working directory relative to workspace root. Defaults to workspace root." },
          "timeout_s": { "type": "number",  "description": "Timeout in seconds. Default 30, max 120." }
        },
        "required": ["command"]
      }
    }
  },
  {
    "type": "function",
    "function": {
      "name": "lb_fetch_url",
      "description": "Fetch a URL and return the response body. Use for reading documentation, APIs, or any HTTP resource.",
      "parameters": {
        "type": "object",
        "properties": {
          "url":     { "type": "string", "description": "The URL to fetch." },
          "method":  { "type": "string", "description": "HTTP method. Default GET.", "enum": ["GET","POST","PUT","PATCH","DELETE"] },
          "headers": { "type": "object", "description": "Optional request headers as key-value pairs." },
          "body":    { "type": "string", "description": "Optional request body (for POST/PUT)." }
        },
        "required": ["url"]
      }
    }
  }
]
```

The `sg-tool-definition` component manages which tools are enabled. When a tool is disabled its schema is removed from the array before the request is sent.

## 3. Conversation format — full worked example

This is the exact turn array sent to the LLM for the README-emoji demo (three rounds).

### Round 1 — user message

```json
[
  { "role": "system", "content": "<system prompt from §1>" },
  { "role": "user",   "content": "Read README.md, add an emoji to the title line, and write it back." }
]
```

LLM responds with a tool call:

```json
{
  "role": "assistant",
  "content": null,
  "tool_calls": [
    {
      "id": "call_r1t1",
      "type": "function",
      "function": { "name": "lb_read_file", "arguments": "{\"path\":\"README.md\"}" }
    }
  ]
}
```

### Round 2 — tool result appended, re-sent

```json
[
  { "role": "system",    "content": "…" },
  { "role": "user",      "content": "Read README.md, add an emoji to the title line, and write it back." },
  { "role": "assistant", "content": null, "tool_calls": [{ "id": "call_r1t1", … }] },
  { "role": "tool",      "tool_call_id": "call_r1t1",
    "content": "{\"path\":\"README.md\",\"content\":\"# SGraph Tools\\nThis repo…\",\"size\":412}" }
]
```

LLM responds with another tool call:

```json
{
  "role": "assistant",
  "content": null,
  "tool_calls": [
    {
      "id": "call_r2t1",
      "type": "function",
      "function": {
        "name": "lb_write_file",
        "arguments": "{\"path\":\"README.md\",\"content\":\"# 🛠️ SGraph Tools\\nThis repo…\"}"
      }
    }
  ]
}
```

### Round 3 — write result appended, re-sent

```json
[
  { "role": "system",    "content": "…" },
  { "role": "user",      "content": "Read README.md, add an emoji to the title line, and write it back." },
  { "role": "assistant", "content": null, "tool_calls": [{ "id": "call_r1t1", … }] },
  { "role": "tool",      "tool_call_id": "call_r1t1", "content": "{…read result…}" },
  { "role": "assistant", "content": null, "tool_calls": [{ "id": "call_r2t1", … }] },
  { "role": "tool",      "tool_call_id": "call_r2t1",
    "content": "{\"path\":\"README.md\",\"bytes_written\":421,\"created\":false}" }
]
```

LLM responds with prose (no tool calls → agentic loop terminates this chain):

```json
{ "role": "assistant", "content": "Done. The title now reads \"# 🛠️ SGraph Tools\"." }
```

## 4. Tool-call format sent by the LLM — two variants

### 4.1 Native `tool_calls` (preferred — qwen2.5-coder:7b, OpenRouter)

The LLM returns a `tool_calls` array in the message object. `sg-llm-request` already parses this in `sg-llm-request-parsers.js`. No extra handling needed in Phase 3.

### 4.2 JSON-in-content fallback (Phase 4 — older / fine-tuned Ollama models)

Some models emit tool calls as JSON embedded in the `content` string, often inside a code block:

```
I'll read the file now.

```json
{"tool": "lb_read_file", "parameters": {"path": "README.md"}}
```
```

Or without the prose prefix:

```json
[
  {"tool": "lb_read_file", "parameters": {"path": "README.md"}},
  {"tool": "lb_list_folder", "parameters": {"path": "."}}
]
```

The **Phase 4 shim** (`sg-local-bridge-shim.js`, ≤120 lines) detects this pattern and normalises it into the native `tool_calls` shape before the loop processes the response. Detection heuristic: if `tool_calls` is empty/absent AND `content` contains a JSON object or array with a `"tool"` key, attempt parse.

Normalisation map:

| JSON-in-content key | Maps to `tool_calls` field |
|---|---|
| `tool` | `function.name` |
| `parameters` | `function.arguments` (re-serialised to string) |
| `id` (optional) | `id` (generated if absent: `call_{Date.now()}`) |

The shim never mutates the stored turn array — it outputs a normalised copy used only for the tool-runner invocation and for appending the `tool_result` turn.

## 5. Error tool results (what the LLM sees when a tool fails)

When `sg-local-bridge` receives a 4xx/5xx from the bridge, it constructs an error result string and passes it to `sg-tool-runner` as the content of the `tool_result` turn:

```json
{
  "role": "tool",
  "tool_call_id": "call_abc",
  "content": "{\"error_code\":\"file_not_found\",\"message\":\"No such file: README.md\",\"detail\":null}"
}
```

The LLM reads this and decides what to do next. No special handling needed — the loop continues.

## 6. Per-model notes

| Model | Tool-call format | System prompt variant | Notes |
|---|---|---|---|
| `qwen2.5-coder:7b` | Native `tool_calls` | §1 (default) | Default model. Fast, good at file/code tasks. |
| `llama3.1:8b` | Native `tool_calls` | §1 (default) | Good general reasoning. Slower at 7B-equivalent speed. |
| `mistral:7b` | JSON-in-content | §1 + fallback shim | Needs Phase 4 shim. Works but verbose. |
| `codellama:7b` | JSON-in-content | §1 + fallback shim | Needs Phase 4 shim. Focused on code, poor at prose. |
| OpenRouter (any Claude) | Native `tool_calls` | §1 (default) | Fastest, highest quality, requires API key + internet. |
| OpenRouter (GPT-4o) | Native `tool_calls` | §1 (default) | Requires API key + internet. |

**Testing matrix for Phase 4:** run the README-emoji demo against `qwen2.5-coder:7b` (should pass without shim in P3), then against `mistral:7b` (requires shim, validates Phase 4).

## 7. Conversation length management (v0.1.0 guidance)

`sg-agentic-loop` sends the full turn array on every round. For long sessions this will eventually hit the model's context window.

- `qwen2.5-coder:7b` context: 32 k tokens (Ollama default)
- One agentic session with 15 iterations and modest file contents: typically 5–15 k tokens — well within limit for v0.1.0
- No truncation logic needed in v0.1.0; add `max-turns` attribute to `sg-agentic-loop` in a future patch if sessions grow large
- `window.__tool.clearChat()` resets the turn array when the user starts a new task

```

  prompts/
    system.md          ← §1 template with placeholders; loaded via fetch() at startup
    json-fallback.md   ← human-readable doc of the JSON-in-content format; used as reference

`agent-with-tools-api.js` fetches `./prompts/system.md`, substitutes `{WORKSPACE_PATH}` and `{TOOL_LIST}`, and stores the result as the system turn. On `llm:tool-defs-changed` it regenerates the `{TOOL_LIST}` section and updates the stored system turn for the next request.
