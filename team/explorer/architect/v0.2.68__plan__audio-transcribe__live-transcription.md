# Plan — Live (near-realtime) transcription for audio-transcribe

**Version:** v0.2.68
**Type:** Planning / brief review (architecture + product)
**Status:** PROPOSED — live mode does not exist yet. This reviews an external
brief ("OpenRouter interactive STT architecture", by Perplexity) against the
**actual** audio-transcribe tool and reality document, corrects assumptions the
brief couldn't know, and proposes a client-side, reuse-first plan.

> The brief was written **without access to this repo or the work done on this
> tool**. It is directionally excellent on the *technique* (chunked pseudo-
> streaming) but assumes a **server/backend** architecture we don't use. Most of
> its "build this" list **already exists here** (✅).

---

## 0. TL;DR

- The brief's core idea — **pseudo-streaming**: capture short overlapping audio
  chunks, transcribe each via normal request/response, merge into a live
  transcript — is sound and matches OpenRouter's documented capabilities. ✅ Adopt.
- The brief's **backend/gateway/proxy** layer is **not needed**: this tool is
  **client-side, BYOK (the user's OpenRouter key), no server** by design. Collapse
  the gateway + "WebSocket/SSE push" + "don't expose the key" sections into "the
  browser calls OpenRouter directly" (our established pattern). 🔁 Adapt.
- A large fraction of the brief's requirements **already ship**: the
  Debug/provenance panel, parallel multi-model runners, per-item cost capture,
  the recording waveform, the isolated transport. We're reusing, not building
  from scratch. ✅
- The genuinely-new piece is **Live mode**: a chunk scheduler + a merge/assembler
  + live/stable transcript views. 🔲 Build (phased).

| Recording waveform / capture state | ✅ `sg-audio-viz` live waveform already wired into recording. |

## 2. Architecture (client-side, no backend)

```
mic ─▶ ChunkScheduler (≈800ms + 250ms overlap)
          │  emits {seq, blob, startMs, durMs, overlapMs}
          ▼
     per-chunk transcription            ◀── reuses the isolated transport
       Runner A (fast)  ─┐                   + chat input_audio (today) OR
       Runner B (accurate)├─ parallel        /audio/transcriptions (new runner)
       Runner C (cleanup) ┘  (transcribeModels-style)
          ▼
     Assembler (merge unstable tail; stable-after-2)
          ▼   (optional) Synthesizer = small text model reconciles candidates
     Live view (stable + grey "live" tail)   +   Debug: chunk timeline / replay / merge
```

All of this runs in the browser. The user's OpenRouter key (already persisted +
`setApiKey`) authorises the per-chunk calls. No server, no WS/SSE.

### Reuse map (what we plug into)
- **Capture/chunking:** `core/sg-audio` already records via MediaRecorder with a
  segment callback; a chunk scheduler (or `segmentDurationMs ≈ 800` + overlap
  bookkeeping) emits chunks. `sg-audio-viz` shows the live waveform.
- **Per-chunk transcribe:** the existing `runVersion`/transport path (chat
  `input_audio`), or a new `/audio/transcriptions` runner. Parallel = the same
  isolated transport that powers `transcribeModels`.
- **Merge/assembler:** new tool-local module (`api/live-merge.js`): longest-common-
  suffix overlap on the unstable tail; mark stable after 2 unchanged updates.
- **Synthesizer:** reuse the text-LLM path (`sg-llm-request`) with a tiny token
  budget over just the unstable tail.
- **Debug:** extend `ui/ui-debug.js` (provenance) with a chunk timeline + per-chunk
  `<audio>` replay + a merge inspector. Most of the per-runner/cost data is
  already captured by the exchange log.

## 3. Phasing (each = a versioned release with tests, per the README checklist)

- **Phase 1 — Live MVP 🔲**: a "🔴 Live" mode in the Source panel — chunked capture
  (≈800ms, no overlap yet), one fast runner on the working chat `input_audio`
  path, naive append, and **live + stable transcript views**. Chunks logged in the
  Debug panel. No backend, no synthesizer.
- **Phase 2 — Merge quality 🔲**: 250ms overlap + the suffix/prefix merge (stable
  tail), per-chunk replay in Debug, a chunk timeline.
- **Phase 3 — Parallel + synthesis 🔲**: multiple runners per chunk (reuse the
  isolated transport / `transcribeModels`), an optional text-model synthesizer
  over the unstable tail, and the **dedicated `/audio/transcriptions`** endpoint
  wired as a runner (un-gating the Whisper/GPT-4o-transcribe entries).
- **Phase 4 — Metrics 🔲**: p50/p95 latency, revision rate, timeout/error rate,
  cost/min — extending the cost/provenance we already capture.

Recommended first slice: **Phase 1** only (chunked capture + one runner + live/
stable views + chunks in Debug). It proves the perceived-latency win with minimal
new surface, and everything downstream (parallel, merge, synthesis, metrics) is an
extension of code we already have.

## 4. Decisions / open questions

1. **Endpoint for live:** start on chat `input_audio` (works today, no new module)
   and add `/audio/transcriptions` in Phase 3 — or build the dedicated endpoint
   first? (Recommend: chat path first; it's already proven.)
2. **Where Live lives:** a new "🔴 Live" sub-mode of the Source panel, or its own
   tab? (Recommend: Source sub-mode — it's a recording variant.)
3. **Rate limits:** frequent chunks × parallel runners × BYOK = many requests/min.
   Need a concurrency cap + backpressure (drop/coalesce chunks if behind).
4. **Persisting a live session:** does a finished live session become a normal
   queue item (full audio + final transcript) so it flows into bundle/send/chat?
   (Recommend: yes — converge with the existing queue.)
5. **Synthesizer model:** reuse the chat text-model list; bound output to the last
   ~10–20 words.

---

## 5. What we explicitly DROP from the brief (and why)

- The **backend gateway, WebSocket/SSE push, server-side key proxy** — we are
  client-side BYOK. (If a *managed* offering is ever wanted, that's the separate
  credit-proxy proposal in `v0.2.66`, not this.)
- **Server-side session persistence** — sessions are in-browser (like the current
  queue), exported via the existing bundle/`.zip` if needed.

Everything else in the brief maps onto features we already have or the phased
build above.
