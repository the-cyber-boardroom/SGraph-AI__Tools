## How to run the probes

1. Deploy this branch to `dev.tools.sgraph.ai`.
2. Open `https://dev.tools.sgraph.ai/en-gb/linkedin-publisher/`. Probes run automatically on load; the Re-run button repeats them.
3. Open DevTools → Network tab and screenshot the four requests so we have the raw response headers as evidence.
4. Paste the decision matrix and the raw log below.

**Why the deployed origin matters:** running locally (e.g. `localhost`) will report all three CORS probes as fail, but that result is not specific to LinkedIn — it's just that LinkedIn doesn't whitelist any browser origin. The probes need to run from the registered redirect origin (`dev.tools.sgraph.ai`) to give an answer that drives the architecture choice.

## Decision matrix

| Question | Answer | Implies |
|---|---|---|
| Does `api.linkedin.com` accept browser requests? | **No — CORS-blocked.** DevTools: *"Access to fetch at 'https://api.linkedin.com/rest/posts?…' from origin 'https://dev.tools.sgraph.ai' has been blocked by CORS policy: Response to preflight request doesn't pass access control check: No 'Access-Control-Allow-Origin' header is present on the requested resource."* Plus `net::ERR_FAILED` on the underlying GET. | All REST/v2 calls (posts, userinfo, list, read) must go through a proxy. |
| Does `oauth/v2/authorization` accept cross-origin GET? | **No — CORS-blocked**, but **expected and irrelevant**. The probe even saw `200 OK` come back from LinkedIn before the browser dropped it (`net::ERR_FAILED 200 (OK)`); production flow uses `window.open()` for top-level navigation, which bypasses CORS entirely. | No architecture impact. Popup-with-postMessage still fine. |
| Does `oauth/v2/accessToken` accept browser POST? | **No — CORS-blocked.** Notably the request DID reach LinkedIn (response status `401 Unauthorized` came back in the network layer) but the response had no `Access-Control-Allow-Origin` header so the browser rejected it. | Token-exchange (PKCE code → access token) must go through the proxy. |
| Can the browser produce S256 PKCE challenges? | **Yes.** Verifier 43 chars, challenge 43 chars (S256). | Use PKCE; no client secret needed in the browser. The proxy can be a public-client passthrough. |

✗ Access to fetch at 'https://www.linkedin.com/oauth/v2/accessToken' from origin 'https://dev.tools.sgraph.ai' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource.

Two evidentially-important observations:

1. The `oauth/v2/authorization` GET came back as `200 OK` at the network layer before the browser blocked it — confirms LinkedIn happily serves the URL but with no CORS headers, which doesn't matter because production uses popup navigation.
2. The `oauth/v2/accessToken` POST got a real `401 Unauthorized` from LinkedIn (it actually processed the bogus PKCE form body and rejected the fake code) — proving the request reaches LinkedIn's auth service. The browser dropped the response purely on the missing CORS header. **A proxy that strips the browser-origin header and forwards the request body unchanged will work.**

## Architect verdict

**Proxy strategy chosen: Option A — single managed Cloudflare Worker on `tools.sgraph.ai`.**

**Reasoning** (full research in [`v0.1.0__phase-0__linkedin-browser-api-research.md`](./v0.1.0__phase-0__linkedin-browser-api-research.md)):

1. **Every LinkedIn surface is CORS-blocked**, including the OIDC `/v2/userinfo`, `/v2/me`, and even the public `.well-known/openid-configuration` discovery doc. There is no browser-direct path on any endpoint, so D is dead.
2. **No reusable LinkedIn proxy worth mirroring** exists publicly (the only `linkedin-cors-proxy` repo is an abandoned 0-star Go fragment). Every SaaS publisher (Buffer, Hootsuite, Zapier, Make, IFTTT) and every Chrome extension with the LinkedIn API either runs server-side or scrapes the DOM. We're charting our own path here.
3. **Recommended reference implementation:** `gr2m/cloudflare-worker-github-oauth-login` (~50 LOC, ISC) retargeted at LinkedIn's `accessToken` URL.
4. **Option B is wrong tradeoff for v1.** LinkedIn's auth-code exchange requires `client_secret` even with PKCE (PKCE is opt-in per app, support-gated). In B, every BYO user would need their own LinkedIn app + secret + verification approval — that's enormous friction for zero precedent users will recognise.
5. **Migration A→B remains cheap.** Build A; expose a `proxyUrl` config field defaulting to `https://linkedin-proxy.tools.sgraph.ai`; power users can override and self-host. No architectural rework later.

**Bonus finding that simplifies the auth panel:** the `id_token` returned alongside `access_token` already contains `sub`, `name`, `picture`, `email`, etc. — so once the proxy completes token exchange, the browser decodes the JWT and skips the userinfo call entirely. One fewer round-trip, one fewer endpoint to proxy.

**Phase 1 (member-mode core + auth) unblocked?** Yes — with a revised order. Ship the Cloudflare Worker FIRST, then the core module + auth panel. The Worker is small enough (~50–100 LOC) to land in the same session.
