## Why This Exists

All current LLM tool pages (`v0.1.6`–`v0.1.8`) use a hand-crafted CSS Grid with
`grid-template-areas` on a `#bus` div. This works but is a dead end:

- Layout is **static** — user cannot resize, reorder, or add panels
- Each tool is a **different HTML file** — adding a new panel means editing HTML
- No panel titles, close buttons, or tab stacking
- Components cannot request focus or signal that they want to be visible

`sg-layout` is already in `core/` and fully tested. It provides resizable panels,
tab stacks, drag-to-dock, fractal nesting, and a serialisable layout tree.
This brief specifies how to adopt it for the LLM tool family.

---

## The Problem: Event Bus vs SG Layout

The current LLM architecture depends on **all sg-llm-* components being direct
children of the same parent element** — that parent IS the event bus
(`this._bus() = this.parentElement`). CSS Grid keeps them in one flat DOM level.

SG Layout wraps components inside panel divs — each component is mounted inside
a shadow DOM panel, not as a sibling of the others. This breaks the shared
`parentElement` bus.

### Solution: Named Bus Element

Replace the implicit `parentElement` bus with an explicit named bus element.

**Current:**
```js
_bus() { return this.parentElement || document; }
```

**New pattern:**
```js
_bus() {
    // Walk up to find the nearest element with data-llm-bus attribute,
    // OR fall back to parentElement for backwards compatibility.
    let el = this.parentElement;
    while (el) {
        if (el.hasAttribute('data-llm-bus')) return el;
        el = el.parentElement;
    }
    return this.parentElement || document;
}
```

The tool page places an invisible `<div id="llm-bus" data-llm-bus>` in the DOM.
`sg-layout` sits inside it. Each component, no matter how deeply nested in
layout panels, dispatches events on the same bus by walking up to
`[data-llm-bus]`.

```html
<div id="llm-bus" data-llm-bus style="flex:1; display:flex; flex-direction:column;">
    <!-- Headless components live directly on the bus (not in layout panels) -->
    <sg-llm-request></sg-llm-request>
    <sg-llm-bundle auto-save></sg-llm-bundle>

    <!-- sg-layout manages all visible panels -->
    <sg-layout id="layout" style="flex:1;"></sg-layout>
</div>
```

Headless components (`sg-llm-request`, `sg-llm-bundle`) stay as direct children
of the bus div — they have no UI, so they don't need to be in layout panels.

## Component Upgrade Pattern

Each sg-llm-* component needs two small changes:

### 1. Updated `_bus()` method

```js
_bus() {
    let el = this.parentElement;
    while (el) {
        if (el.hasAttribute('data-llm-bus')) return el;
        el = el.parentElement;
    }
    return this.parentElement || document;
}
```

### 2. Optional: `setLayoutState` / `getLayoutState`

sg-layout calls `setLayoutState(state)` on a component when restoring a
serialised layout. Components that have user-configurable state (e.g.
`sg-llm-connection`'s selected provider, `sg-llm-reality`'s blocks) can
implement these to persist across page reloads.

```js
setLayoutState(state) { /* restore from state object */ }
getLayoutState()      { /* return serialisable state object */ }
```

This is optional — components without state work fine without it.

## Tool Page Template

All tool pages using sg-layout follow this pattern:

```html
<!DOCTYPE html>
<html lang="en-GB">
<head>
    <!-- ... meta, title, styles ... -->
    <style>
        html, body { height: 100%; margin: 0; display: flex; flex-direction: column; overflow: hidden; }
        sg-site-header { flex-shrink: 0; }
        #llm-bus { flex: 1; display: flex; flex-direction: column; min-height: 0; }
        sg-layout { flex: 1; min-height: 0; }
        sg-llm-request, sg-llm-bundle { display: none !important; }
    </style>
</head>
<body>
<sg-site-header site="Tools" home-url="../../"></sg-site-header>

<div id="llm-bus" data-llm-bus>
    <!-- Headless -->
    <sg-llm-request></sg-llm-request>
    <sg-llm-bundle auto-save></sg-llm-bundle>

    <sg-layout id="layout" layout='{ ... json ... }'></sg-layout>
</div>

<script type="module">
import '/components/llm/sg-llm-events/v0/v0.1/v0.1.0/sg-llm-events.js';
/* import all v0.1.1 components */
</script>
</body>
</html>
```

The layout JSON can be inlined in the `layout` attribute, loaded from a JS
file, or built programmatically after the page loads.

## Chat History + Attachment Manager Integration

With sg-layout, `sg-llm-chat-input` and `sg-llm-attachment-manager` sit in
separate panels. The chat-history component needs to know about attachments
when it fires SEND.

**New flow:**

1. `sg-llm-attachment-manager` emits `llm:attachment-added/removed/cleared` on
   the named bus.
2. `sg-llm-chat-history` (v0.1.2) listens to those events and maintains an
   internal `_attachments` array.
3. When `llm:chat-message` fires, chat-history combines the text with its
   tracked attachments for the SEND payload.
4. After SEND, chat-history emits `llm:attachments-cleared` so
   attachment-manager can reset its UI.

This keeps the components decoupled — neither knows about the other's DOM.

## Migration Path

Phase 1 (this brief): Update `_bus()` in all components. No tool page changes yet.

Phase 2: New tool pages at `v0.1.9` using `sg-layout` with the JSON layouts
above. Old `v0.1.8` pages unchanged.

Phase 3 (future): Add `setLayoutState`/`getLayoutState` to key components for
layout persistence. Add component discovery panel.
