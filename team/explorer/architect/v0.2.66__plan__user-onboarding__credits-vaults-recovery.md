## 0. Purpose & framing

We have a working (in-progress) **audio-transcribe** tool (arch brief `v0.2.65`) that calls **OpenRouter** audio models client-side. Right now it assumes the user already has an OpenRouter API key (BYOK). That is fine for us and a handful of insiders. It is **not** fine for "somebody else" — a stranger who lands on the page and wants to transcribe a WhatsApp voice note without ever having heard of OpenRouter.

This doc plans the journey for **that stranger**, and the parallel journey for **early invited users** we sponsor. The end-state we want:

> A new user opens the tool → gets a small number of free credits (or buys more via Stripe) → their files/prompts/keys/transcripts live in a vault they own → they can walk away, come back on a different device, and recover everything → they never have to understand OpenRouter, base64 keys, or "bring your own key" unless they choose to.

Two journeys must both work:

- **Journey A — Sponsored early user.** We hand them a credential. They click, they're in, they're spending *our* shared OpenRouter budget under a cap. Zero friction, zero payment. Used to get the first 10–50 users trying the product.
- **Journey B — Full self-serve.** A cold visitor does the whole thing themselves: gets free trial credits, buys more with a card, owns their own vault, recovers it later. No human in the loop on our side.

The good news (see §3): the **vault primitives we need already exist** ✅. The gaps are **credits/billing (Stripe)**, an **identity/recovery story**, and a **server-side proxy** so we never ship a shared key to a browser.

---

## 1. The journey, step by step

```
        ┌─────────────────────────────────────────────────────────────┐
        │  1. OPEN          user lands on tools.sgraph.ai/audio-transcribe
        │  2. IDENTITY      "who are you?" → anonymous device-vault  OR  sign in
        │  3. CREDITS       see balance · claim free trial · buy more (Stripe)
        │  4. VAULT         materials/files/prompts/keys auto-stored, encrypted
        │  5. USE           record / drop audio → transcribe (spends credits)
        │  6. RECOVER       new browser/tab/device → restore vault → continue
        └─────────────────────────────────────────────────────────────┘
```

Each step maps to a concrete decision below. The hard ones are **2 (identity/recovery)** and **3 (credits + who holds the OpenRouter key)** — they're coupled, so I treat them together.

## 2. The central tension: where does the OpenRouter call happen?

Everything downstream depends on this one fork. Today, audio-transcribe calls `https://openrouter.ai/api/v1/chat/completions` **directly from the browser** with the user's key (✅ via `components/llm/sg-llm-request`). For a self-serve credit model, that breaks: **you cannot sell credits if the user holds the key**, and **you cannot put a shared key in a browser** (it's instantly exfiltrated).

So there are two viable models. We will likely support **both**, addressed by user type.

### Model 1 — BYOK (Bring Your Own Key) — *exists today* ✅
- User pastes their own OpenRouter key. We never see it. Call goes straight to OpenRouter.
- **No credits, no Stripe, no proxy.** We bill nothing; OpenRouter bills them.
- **Keep this forever** as the "power user / no-signup" path. It is the current behaviour and costs us nothing.

### Model 2 — Managed credits (the new work) 🔲 PROPOSED
- We hold the OpenRouter key **server-side**. The browser calls **our proxy**, not OpenRouter.
- Proxy checks the user's credit balance → forwards to OpenRouter → measures real cost → debits credits at a markup → returns the transcript.
- This is what enables Stripe, free trials, sponsored users, and "never explain OpenRouter to the user."
- **Requires a server.** This is the single biggest new dependency in the whole plan — see §6.

> **Recommendation:** ship **Model 2** as the default front-door for strangers, keep **Model 1** as an advanced toggle ("I have my own OpenRouter key"). Sponsored early users (Journey A) are just Model 2 with credits we pre-funded.

## 3. The vault — what we store and how (mostly ✅ already)

The "user vault" is where the user's working set lives so it survives across sessions. The **vault system already exists** ✅ and is a strong fit:

- Vaults live at `send.sgraph.ai`, content-addressed, **AES-256-GCM encrypted**, decrypted **client-side** — the key never leaves the device. (`core/vault-client` v1.2.2, `core/vault-write` v1.1.1, `core/vault-session` v1.0.0.)
- A vault has a **vault-id** + a **read-key**; a **write-key** lets the holder mutate it.
- `core/vault-init.createVault(config)` ✅ programmatically bootstraps a new vault → `{ token, vaultId, keys, commitId, treeId }`.
- `core/vault-mutations` ✅ gives nine file/folder ops (add/update/remove/rename/move/copy).
- `<sg-vault-manager>` ✅ is a multi-vault registry with the BYOK key pattern; `<sg-vault-create>` ✅ is a creation form.

### Proposed vault layout for an audio-transcribe user
```
user-vault/
  profile.json            # display name, created-at, preferences
  credits.json            # CACHE ONLY — authoritative balance lives server-side (§4)
  keys/
    openrouter.key        # only if BYOK; encrypted at rest in the vault
  prompts/
    *.md                  # saved transcription/cleanup prompts
  materials/
    <session-id>/
      audio/*.opus|wav    # the source audio (optional — may be large)
      transcripts/*.md    # the outputs
      manifest.json       # what model, when, cost
```

**Key point:** the vault gives us **storage + encryption + sync + recovery for free** ✅. We do **not** need to build a storage layer. What the vault does *not* give us is **identity** (which vault is "mine"?) and **an authoritative credit balance** (a vault is user-controlled, so it can't be the source of truth for money). Those are §4 and §5.

> ⚠️ Never store the authoritative credit balance in the vault — the user controls the vault and could edit it. The vault holds a *cached* balance for display; the server is the ledger.

## 4. Credits & Stripe 🔲 PROPOSED

### The economic model
- We pre-pay OpenRouter. OpenRouter charges us per-token/per-second of audio.
- We sell **credits** to users at a **small markup** (e.g. cost × 1.2–1.5, TBD) to cover Stripe fees + margin.
- 1 credit = a fixed fraction of a US cent, so a typical voice-note transcription costs "a few credits" and the number feels concrete, not scary.

### The ledger (server-side, authoritative)
A minimal credits service:
```
POST /credits/grant     { user, amount, reason }      # free trial, sponsor top-up
POST /credits/quote     { model, audioSeconds }        # estimate before spend
POST /credits/debit     { user, actualCostUSD }        # called by the proxy after a real call
GET  /credits/balance   { user } -> { credits, usdValue }
```
The **proxy (§6) is the only thing that debits** — it knows the real OpenRouter cost from the response, applies markup, and writes the ledger. This closes the "user lies about cost" hole.

### Stripe flow
1. User clicks **Buy credits** → picks a pack ($5 / $20 / $50).
2. Browser hits `POST /billing/checkout` → server creates a **Stripe Checkout Session** → redirect.
3. User pays on Stripe-hosted page (we never touch card data — PCI stays with Stripe).
4. Stripe **webhook** → our server → `credits/grant` → balance updated.
5. User returns to the tool; balance refreshes.

**Free trial:** on first identity creation, auto-`grant` a small amount (e.g. 50 credits ≈ a handful of transcriptions). No card required. This is what makes Journey B feel magical.

### Reuse note
`components/openrouter/sg-openrouter-key-stats` and `sg-openrouter-log-viewer` ✅ already parse OpenRouter usage/cost fields (`byok_usage_inference`, tokens, cost). The **cost-measurement logic for the proxy's debit step can be lifted from these** rather than written fresh.

## 5. Identity & recovery — the multi-option exploration

This is the question the user flagged as open: *what do we use to store/recover the user's "audio vault"?* The vault holds the data; **identity is how we find the right vault on a fresh browser** and **how the server knows who to bill**. Four options, roughly in increasing weight:

### Option A — Anonymous device-vault + recovery phrase 🔲
- On first visit, silently `createVault()` ✅. Store `{vaultId, writeKey}` in `localStorage`.
- To recover elsewhere, the user must have saved a **recovery phrase** (the vault token / friendly passphrase from `vault-init` ✅) and paste it on the other device.
- **Pros:** zero signup, no third party, works today with existing primitives, maximally private. **Cons:** if the user loses the phrase *and* clears the browser, the vault is gone (by design — we can't recover what we can't decrypt). Credits would need to be tied to the vault-id, so a lost vault = lost credits unless the server also keys credits to something recoverable.
- **Best for:** the no-friction trial and BYOK power users.

### Option B — Google OAuth (sign in with Google) 🔲  ← user's suggestion
- "Sign in with Google" → we get a stable `sub` (Google user id) + email.
- Server maps `google_sub → {vaultId, credit ledger}`. On any new browser, sign in → server hands back the vault pointer → vault auto-restores.
- **Where the vault bytes live, two sub-variants:**
  - **B1 — vault stays on send.sgraph.ai**, Google is *only* identity. Simplest; we keep full control of storage; we still hold an (encrypted) pointer. The vault's read/write keys can be wrapped to the user and stored server-side or re-derived.
  - **B2 — Google Drive `appDataFolder`** (a hidden per-app folder in the user's own Drive). The encrypted vault blob is stored in **the user's own Google account**, invisible to them, scoped to our app, not counting against normal Drive UX. We never run storage infra for it; recovery is "sign in with Google, we read your appDataFolder." This is the "Google User App Space" the user referred to.
- **Pros:** recovery is trivial and familiar; no recovery phrase to lose; ties credits to a real identity (good for anti-abuse on free trials). **Cons:** requires Google OAuth setup + consent screen; B2 adds Drive API scope (`drive.appdata`) which some users distrust; not everyone has/will-use Google.
- **Best for:** the mainstream self-serve user who wants "it just works across my devices."

### Option C — Email magic-link / passkey 🔲
- Passwordless email link, or WebAuthn passkey, → server session → vault pointer (same as B1 but without Google).
- **Pros:** no Google dependency, works for everyone with an email; passkeys are phishing-resistant. **Cons:** we run the auth/email infra; more to build than leaning on Google.

### Option D — "Vault that creates vaults" (sponsored onboarding) 🔲 ← user's other point
- A **parent/admin vault** that we control holds: a **shared OpenRouter budget** + a list of invited early users. It can **mint child vaults** for them (via `createVault()` ✅ — the primitive already exists; `vault-session`'s two-branch model supports fork-like flows).
- Flow: we send an early user a single link with an embedded token → the link's child-vault is pre-provisioned with N sponsored credits drawn from the shared budget → they're transcribing in one click, no signup, no card.
- This is **Journey A**, and it's largely buildable **today** on existing vault primitives — the only new piece is the credit cap enforcement (which, if we route through the §6 proxy, comes for free).
- **Best for:** getting the first cohort of real users without asking them for anything.

### Recommendation
- **Phase 1:** Option **A** (anonymous device-vault + recovery phrase) + Option **D** (sponsored parent-vault) — both sit on primitives that exist today ✅, minimal new build, lets us onboard the first cohort and dogfood credits.
- **Phase 2:** add Option **B1** (Google OAuth as identity, vault stays on send.sgraph.ai) for mainstream cross-device recovery.
- **Phase 3 (optional):** Option **B2** (Drive `appDataFolder`) for users who want their data in their own Google account, and Option **C** for the Google-averse.

Storage-backend decision restated plainly: **default to send.sgraph.ai vaults (we already have them) and use the identity provider only as a *pointer/lookup*, not as the storage.** Drive `appDataFolder` is a nice *opt-in* later, not the default — it adds an OAuth scope and a second storage path to maintain.

## 6. The one big new dependency: the credit proxy 🔲 PROPOSED

Models 2, credits, Stripe, sponsored caps, and "never show the user a key" **all require a small server-side proxy.** It is unavoidable: a browser cannot safely hold a shared key or be trusted with a money ledger. Scope it tiny:

```
Browser ──audio+model──▶  /transcribe (our proxy)
                              │ 1. authn (vault-id / Google sub / session)
                              │ 2. check balance (credits ledger)
                              │ 3. forward to OpenRouter with OUR key
                              │ 4. read real cost from OpenRouter response
                              │ 5. debit credits (cost × markup)
                              ◀ 6. return transcript + new balance
```
- Stateless except for the ledger + Stripe webhook handling.
- Could be a single serverless function set (Cloudflare Worker / Lambda) — fits the "static-first" ethos by staying minimal and out of the static asset path.
- The **client stays almost identical**: audio-transcribe just points `sg-llm-request` at our proxy base-URL instead of `openrouter.ai` for managed-credit users, and at `openrouter.ai` for BYOK users. **One config switch.** ✅ The request engine already supports a configurable `baseUrl`.

> This proxy is the gate. Until it exists, only BYOK (Model 1) and pre-funded sponsored vaults that *still ultimately need a non-browser key holder* are truly safe. **Flag for Dinis:** are we willing to run one small always-on service? If "static-only, no servers ever," then the credit/Stripe model is off the table and we're BYOK-only — that decision cascades through everything above.

## 8. Phased delivery

- **Phase 0 (now):** audio-transcribe ships BYOK-only (current trajectory of `v0.2.65`). Strangers can't use credits yet, but the tool works for us.
- **Phase 1 — Sponsored cohort:** parent-vault that mints child vaults with sponsored credits (Option D) + anonymous device-vault + recovery phrase (Option A) + the minimal credit proxy (§6) using *our* OpenRouter key under a hard cap. First real external users, no Stripe yet.
- **Phase 2 — Self-serve payments:** Stripe checkout + webhooks + free-trial grant + balance UI. Now a cold stranger completes Journey B end-to-end.
- **Phase 3 — Mainstream identity:** Google OAuth (B1) for painless cross-device recovery; optional Drive `appDataFolder` (B2) and email/passkey (C).

## 9. Open questions for Dinis

1. **Will we run one small always-on service (the proxy)?** This is the load-bearing decision (§6). Yes → credits/Stripe/sponsored caps all unlock. No → we are BYOK-forever and this whole plan collapses to "make BYOK nicer."
2. **Markup & credit-unit:** what multiple over OpenRouter cost, and what does "1 credit" map to in cents? (Affects the whole pricing UX.)
3. **Identity default:** comfortable making **Google OAuth** the mainstream recovery path, or do we want a Google-free default (email/passkey) for the privacy-first audience?
4. **Drive `appDataFolder` — appetite?** Storing the user's encrypted vault in *their* Google account is elegant but adds a Drive scope. Default to send.sgraph.ai and offer Drive as opt-in?
5. **Sponsored cohort size & cap:** how many early users, and what hard credit ceiling on the shared OpenRouter budget before it auto-stops?
6. **Free-trial amount:** how many free credits on first visit, and how do we stop one person farming trials (this is where a real identity in Phase 3 helps)?
