## 1. The Proposed 6-Phase Plan

The impl brief proposes:

| Phase | Content | Estimate |
|-------|---------|----------|
| 1 | sg-tool-api core + window events | 1 day |
| 2 | Tool-specific API extraction | 1 day |
| 3 | SKILL files + manifest | 0.5 day |
| 4 | Explorer + Logger + Footer UI components | 1-2 days |
| 5 | Console + Tester + Manifest viewer | 1-2 days |
| 6 | Validation (parallel gen, API workflow) | 0.5 day |

Total: 5-7 days.

## 2. Is the Order Right?

Mostly yes. Three observations:

### 2.1 Phase 3 (content) should move earlier, not later

Phase 3 (SKILL files + manifest) is listed after Phase 2 (API extraction). This implies the
content is written after the code is done. The problem: SKILL-api.md and the `api.actions` section
of manifest.json are the **contract specification** for the API. Writing them after implementation
means the implementation was written without a published contract. Bugs and omissions will appear
only at Phase 6 validation.

Recommendation: write a draft `manifest.json` with the `api.actions` schema (see manifest review)
as the first artefact of Phase 2, before extracting any implementation. The manifest becomes the
spec the code implements against. `SKILL-api.md` can follow at end of Phase 2 once the actual
return shapes are confirmed.

### 2.2 Phase 6 validation is not a phase — it is acceptance criteria

"Validation" as a phase implies it is optional or can be skipped if time runs short. Rename it
"Acceptance gate." Make each criterion a hard pass/fail. The most important tests:

- `__tool.generate({ await: true })` completes and returns `generationId`
- `Promise.all()` across 3 models fires 3 `generation:complete` events with distinct `generationId`
- `__tool.meta.getManifest()` returns parseable JSON with `api.actions` populated
- No polling loops remain in the slide-deck workflow

If these tests fail, the MVP is not shippable regardless of what else works.

### 2.3 Phase 1 quick win is real and should be isolated

The highest immediate value is adding two lines to the SEND interceptor (lines 491-508 of
`infographic-gen.js`) to dispatch `generation:complete` and `generation:error` on `window`. This
does not require `SgToolApi` at all. It unblocks the Playwright automation immediately while the
rest is built.

This micro-step should be called out explicitly as "Phase 0: Window Events" — a 30-minute change
that ships immediately and provides proof that the event contract works before committing to the
full refactor.

## 3. Risks in the Current Plan

### Risk 1: `generate()` extraction is the hardest piece, not the easiest

The impl brief estimates Phase 2 at 1 day and treats `generate()` extraction as one of five
parallel items. In reality, extracting `generate()` from the SEND interceptor (lines 434-557 of
`infographic-gen.js`) is a significant architectural change:

- The interceptor creates a new `sg-layout` tab (via `layout.addTabToStack`)
- It creates a mini-bus div appended to `document.body`
- It uses `setupResultFractal()` and `setupLoadingState()` from `panels.js`
- It fires on the `bus` capture listener

Extracting this cleanly requires the `renderUI: true|false` option from the impl brief — a
non-trivial conditional that needs careful testing. The `connect()` and `setTemplate()` extractions
are 30 minutes each. `generate()` is a full day on its own. Adjust the estimate.

### Risk 2: The mini-bus pattern conflicts with the API pattern

The current architecture uses isolated per-request mini-bus divs to handle concurrent generations
(each generation gets its own `data-llm-bus` element with its own `sg-llm-request` child). This is
clever and works well for the UI-centric use case.

The API pattern needs `generate()` to return a Promise. But the Promise resolves when an event
fires on a mini-bus that is created *inside* `generate()`. This is fine for `await: true` mode.
For `await: false` mode, the mini-bus is created, the generation starts, and control returns. But
the mini-bus div only lives until `finish()` calls `miniBus.remove()` (line 488). The caller
listening to `window` for `generation:complete` works fine. The caller who subscribed to
`window` *before* calling generate and then called generate with `await: false` will see the
event. No issue.

The actual risk: `renderUI: false` requires suppressing the `layout.addTabToStack()` call. The
outer `layout` variable is module-level in `infographic-gen.js`. The extracted `generate()`
function will need access to it (or a flag to skip it). This is coupling between the API layer and
the UI layer. The brief says to extract it cleanly — the implementation needs to be explicit about
how `generate()` knows whether to create a tab.

Recommendation: pass `context` into the generate implementation at registration time using a
closure:

```javascript
api.register('generate', (params) => generateImpl(params, { layout, rightStack: 's-right' }), {
    async: true, events: ['generation:started','generation:complete','generation:error']
});
```

The API core does not know about the layout. The tool-specific closure provides it. `renderUI: false`
sets `layout` to null in the closure and skips tab creation.

### Risk 3: Phases 4 and 5 are lower-priority than they appear

The UI components (`sg-tool-api-explorer`, `sg-tool-api-console`, `sg-tool-api-tester`) are
genuinely useful for development and debugging. But they are not required to unblock the automation
use case. If timeline pressure exists, Phases 4 and 5 can be deferred without affecting the
core contract.

The acceptance criteria the brief marks as Phase 4/5 deliverables:
- `sg-tool-api-explorer` renders methods — nice to have, not blocking
- `sg-tool-api-console` with autocomplete — nice to have

The acceptance criteria that actually matter for the stated goal (replacing Playwright polling):
- All Phase 1-3 criteria
- `Promise.all()` parallel generation (Phase 6)

Phases 4 and 5 should be re-labelled as Phase 2 deliverables for a **future sprint**, not the MVP.

## 4. Suggested Revised Sequence

```
Phase 0 (30 min): Window events only
  → Add window.dispatchEvent('generation:complete'/error) to infographic-gen.js
  → No SgToolApi yet. Immediate value. Verifiable in Playwright today.

Phase 1 (1 day): sg-tool-api core module
  → sg-tool-api.js with register/activate/_emit/_log
  → sg-tool-api-events.js constants
  → Wire infographic-gen to use SgToolApi
  → meta API returns valid data

Phase 2 (2 days, not 1): Tool-specific API extraction
  → Write manifest.json api.actions section FIRST (spec before code)
  → Extract connect(), setTemplate(), getState() (easy — 2h)
  → Extract exportPng(), getCost() (medium — 2h)
  → Extract generate() with renderUI flag (hard — full day)

Phase 3 (0.5 day): SKILL files
  → SKILL-api.md (most important — write from manifest)
  → SKILL-human.md (reuse existing docs)
  → SKILL-browser.md (add data-automation-* attrs)

Phase 4 (acceptance gate): Validation
  → All acceptance criteria from the impl brief, Phases 1-3
  → Parallel generation test
  → Slide deck workflow without polling
  → Ship only when gate passes

Phase 5 (future sprint): UI Components
  → sg-tool-api-explorer, logger, footer, console, tester
```

## 5. The "Second Tool" Criterion

Acceptance criterion 20 in the impl brief: "A second tool (vault) can adopt SgToolApi with zero
code duplication."

This is the right test of whether the abstraction is general enough. Vault is a good candidate
because it is already component-based and has a clean dependency manifest. However, testing this
as part of the same MVP sprint is risky — it doubles the implementation scope. Recommendation:
include this as a Phase 5 validation step (after UI components), not Phase 6 of the MVP. The
infographic generator MVP should prove the pattern works; the vault adoption proves it generalises.

## 6. Effort Calibration

The brief estimates 5-7 days total. More realistic breakdown:

| Phase (revised) | Effort |
|-----------------|--------|
| Phase 0: window events | 30 min |
| Phase 1: sg-tool-api core | 1 day |
| Phase 2: API extraction (generate is hard) | 2-3 days |
| Phase 3: SKILL files | 0.5 day |
| Phase 4: acceptance gate | 0.5 day |
| **MVP total** | **4-5 days** |
| Phase 5: UI components | 3-5 days additional |
| Phase 6: vault adoption | 1 day additional |

The brief's 5-7 day estimate covers the MVP if Phase 5 (UI) is explicitly deprioritised. The
risk is that UI components become scope creep during the MVP and delay the automation unblock.

## 7. Not-Yet-Existing Items

Everything in these briefs is PROPOSED — does not exist yet:
- `core/sg-tool-api/` (any version or file)
- `window.__tool` / `window.__tools` convention (no tool currently sets these)
- `generation:complete` / `generation:error` on `window` (events currently fire only on mini-bus)
- SKILL files for any tool
- `api.actions` section in any manifest.json
- Any of the six UI components
