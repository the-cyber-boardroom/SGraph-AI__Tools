## Resolutions

### Resolution 1 — ES module execution order + window.SgTree pattern (was BLOCKING 1 + 2)

Two approaches are available. **Approach B (override queue) is recommended.**

#### Approach A — Two `type="module"` scripts in DOM order

```html
<script type="module" src=".../sg-tree.js"></script>
<script type="module" src=".../sg-tree--v0.1.1.js"></script>
```

`<script type="module">` tags at the top level execute in **document order** (the HTML spec defers them identically to `defer`, fetching in parallel but executing sequenced). `window.SgTree` is set by the first module before the second executes.

**Caveat:** Only works for top-level script tags. Breaks if overrides use `import` dependencies that create their own module graph ordering. Simpler to implement but fragile under dynamic loading.

#### Approach B — Override queue pattern ✅ RECOMMENDED

Classic `<script>` tags (not `type="module"`) run **during HTML parsing**, before any deferred/module scripts execute. Use this to pre-register override functions; the base module drains and rewires the queue on load:

```js
// sg-tree--v0.1.1.js  (classic <script>, runs first during parsing)
(window._SgTreeQ = window._SgTreeQ || []).push(function(SgTree) {
    const _orig = SgTree.prototype._renderRow;
    SgTree.prototype._renderRow = function(node, depth) {
        const el = _orig.call(this, node, depth);
        if (this._editable) { /* add edit affordances */ }
        return el;
    };
    SgTree.prototype._startRename = function(id) { /* ... */ };
});
```

```js
// sg-tree.js  (type="module", runs after parsing — base class)
export class SgTree extends HTMLElement { /* ~800 lines */ }
customElements.define('sg-tree', SgTree);

// Drain pre-registered overrides, then make future .push() live-apply
const q = window._SgTreeQ || [];
q.forEach(fn => fn(SgTree));
window._SgTreeQ = { push: fn => fn(SgTree) };
```

Consumer HTML:
```html
<!-- Overrides first (classic scripts — run during parsing, register into queue) -->
<script src=".../sg-tree--v0.1.1.js"></script>
<script src=".../sg-tree--v0.1.2.js"></script>

<!-- Base last (module — deferred, drains queue on load) -->
<script type="module" src=".../sg-tree.js"></script>
```

**Why this is better than Approach A:**
- Deterministic regardless of network timing or module graph resolution
- Override functions receive `SgTree` as a parameter — no `window.SgTree` exposed at all
- The `window._SgTreeQ` idiom is the proven `window.dataLayer` pattern (Google Analytics, etc.)
- Works for dynamic override loading: any script pushing after the base loads is applied immediately
- No cross-version import dependencies; no `customElements.define` double-call risk

**This also resolves the window.SgTree contradiction (was BLOCKING 2).** The override functions receive the class as a parameter from the queue runner — `window.SgTree` is never needed. sg-tree.js remains a pure ES module (`export class SgTree`) without any `window.*` assignments, consistent with sg-layout.

### Resolution 2 — `getScrollTop` / `setScrollTop` (was BLOCKING 3 / MAJOR)

Add both methods to the sg-tree v0.1.0 public API directly. These are simple one-liners wrapping `this._viewport.scrollTop`. They belong in the base class as they are needed for serialisation state round-trips.

```
| `getScrollTop()` | number | Viewport scroll offset in px. For state serialisation only. |
| `setScrollTop(px)` | void  | Restore viewport scroll position. For state restoration only. |
```

**Note for sg-layout:** `getLayoutState()` / `setLayoutState()` is the right integration protocol. `scrollTop` serialisation will be proposed as a standard addition to sg-layout v2+ — components that implement `getLayoutState` should be able to include `scrollTop` in their state object and have sg-layout call `setScrollTop` on restoration. Flag for the next sg-layout version.

## Strengths

### 1. File naming collision is now resolved

The prior review (v0.1.5) flagged that every version using the same `sg-tree.js` filename would cause `build_ifd_latest.py` to destroy the base class by overwriting it with the final override. The v0.19.11 brief adopts the version-stamped filename convention from `v1.3.0__ifd__surgical-overrides-version-stamped-filenames.md`:

- Base: `v0.1.0/sg-tree.js` (canonical, no stamp)
- Overrides: `v0.1.1/sg-tree--v0.1.1.js`, `v0.1.2/sg-tree--v0.1.2.js`, etc.

All files survive the `_latest/` merge. This is correct and consistent with the IFD convention document.

### 2. API contract is well-scoped and internally consistent

The public method surface (`setData`, `getData`, `select`, `expand`, `collapse`, `expandAll`, `collapseAll`, `expandPath`, `scrollTo`, `filter`, `getExpandedIds`, `setExpandedIds`, `getSelectedId`) maps directly to the three consumer migration use cases without exposing internals. The method set is sufficient for SG/Send, SG/Vault, and SG/Workspace adoption. No obviously missing methods for the target consumers.

### 3. Canonical data format is correct

`{id, label, type, children, icon, meta, badge, disabled}` with the `meta` pass-through is the right shape. The `meta` opaque payload pattern means sg-tree never needs updating when a consumer's domain model changes. The `id` uniqueness rule (consistent with sg-layout tab ids) is correctly documented.

### 4. Event architecture follows sg-layout exactly

`SGT_EVENTS` as a frozen `Object.freeze({})` with `sg-tree:verb-noun` naming, `bubbles: true, composed: true` — identical to `SGL_EVENTS`. The `NODE_SELECTED` / `NODE_DESELECTED` / `SELECTION_CHANGED` trio is well thought-out (single select uses all three; multi-select uses `SELECTION_CHANGED`). The `NODE_ACTIVATED` separation from `NODE_SELECTED` (double-click / Enter on leaf) is the correct distinction for consumers that treat click and double-click differently.

### 5. sg-layout integration protocol is correct

`getLayoutState()` / `setLayoutState()` matching sg-layout's serialisation protocol is the right integration point. sg-layout already calls these on hosted components. Section 9 serialisation examples are accurate.

### 6. Test accumulation strategy is superior to sg-layout's

The per-version test page running all prior assertions before adding new ones is the correct way to guarantee v0.2.0 consolidation works. This improves on sg-layout's pattern and should become standard for all new components.

### 7. Flat row rendering is the right architecture

The shift from nested `<div>` trees to a flat list with `padding-left` indentation is architecturally sound. Nested DOM trees at depth cause layout thrashing in Chromium's stacking context reflows. The flat model is also a prerequisite for the v0.1.2 virtual scrolling override, which requires a uniform row height and contiguous DOM layout.

### 8. v0.2.0 consolidation gate before consumer migration

The brief correctly mandates that all v0.1.x versions are built and tested before any consumer (send-browse, vault-tree-view, vault-panel) migrates. This prevents consumers from depending on prototype-patched code.

## Concerns / Gaps

### 1. ✅ RESOLVED — ES module loading order (was BLOCKING)

Resolved by the **override queue pattern** documented in §Resolutions above. No proof-of-concept needed before implementation. The queue pattern eliminates the dependency on module execution order entirely.

### 2. ✅ RESOLVED — `window.SgTree` contradicts sg-layout (was BLOCKING)

Resolved as a consequence of the queue pattern. Override functions receive `SgTree` as a parameter; `window.SgTree` is never assigned. sg-tree.js remains a pure ES module consistent with sg-layout.

### 3. ✅ RESOLVED — `getScrollTop` / `setScrollTop` absent from public API (was MAJOR)

Add both methods to sg-tree v0.1.0 directly. Flag `scrollTop` serialisation for sg-layout v2+. See §Resolutions above.

### 3. `scrollTo(id)` vs `setScrollTop(px)` — two scroll APIs with no boundary (MINOR)

The public API table lists `scrollTo(id)` (scroll to make a specific node visible), and Section 9 implies `setScrollTop(px)` / `getScrollTop()` for raw pixel offset (used in state restoration). These are different concerns and should both be documented, but the distinction is not explicit in the brief. Add a note to the API table clarifying: `scrollTo(id)` is the high-level node-based scroll; `getScrollTop()` / `setScrollTop()` are for serialisation of raw scroll position only.

### 4. Virtual scrolling (v0.1.2) overrides `_renderVisibleRows` — but flat row rendering in v0.1.0 may need row height API (MINOR)

Section 11 specifies that v0.1.2 overrides `_renderVisibleRows` and adds `_onScroll`, `_visibleRange`, and `_rowHeight` measurement. For virtual scrolling to work, `_rowHeight` must be uniform. The v0.1.0 base class must either enforce a fixed row height (via `--sgt-row-height`) or measure it on first render and cache it.

The brief mentions `--sgt-row-height: 28px` as a CSS custom property (Section 5.4), but the base class does not expose `_rowHeight` as a readable property that v0.1.2 can use. The v0.1.0 README placeholder (created per Section 10.2) should specify: "Expose `_rowHeight` (default: 28) as an internal property so that v0.1.2 virtual scrolling can read it without measuring the DOM."

This is a design-time concern that should be documented in the v0.1.0 README before implementation, not left for v0.1.2 to discover.

### 5. `SELECTION_CHANGED` event detail inconsistency (MINOR)

Section 6.1 defines:
- `NODE_SELECTED: 'sg-tree:node-selected'` with detail `{ id, node, path }`
- `NODE_DESELECTED: 'sg-tree:node-deselected'` with detail `{ id }`
- `SELECTION_CHANGED: 'sg-tree:selection-changed'` with detail `{ selectedIds }`

For single-select mode (the v0.1.0 base), `SELECTION_CHANGED` fires with `{ selectedIds: [id] }` — an array of one. But `NODE_SELECTED` fires with `{ id, node, path }` — the full node detail. `SELECTION_CHANGED` carries only ids, not nodes.

A consumer that listens to `SELECTION_CHANGED` (rather than `NODE_SELECTED`) gets less information — they have the id but must call `getData()` and walk the tree to recover the node object. This is acceptable for multi-select (where passing full node objects for each selection change would be expensive), but it should be explicitly documented. The event table comment (currently just `{ selectedIds }`) should read: `{ selectedIds }  // ids only — call getData() to recover node objects`.

### 6. `filter(fn)` is in v0.1.0 public API but implementation is deferred to v0.1.6 (MINOR)

Section 5.2 lists `filter(fn)` in the public API. Section 11 assigns `filter(fn)` implementation to the v0.1.6 surgical override. Section 12 (Test Plan) includes test #26: `filter(fn) hides non-matching nodes`.

If `filter(fn)` is in the v0.1.0 public API table, the v0.1.0 base class must expose it — even if the implementation is a stub that calls the full implementation once v0.1.6 is loaded. Either:

- **Option A:** Implement `filter(fn)` in v0.1.0 (it is ~15 lines — a simple pass over `_buildVisibleList` that skips non-matching nodes).
- **Option B:** Move `filter(fn)` out of the Section 5.2 table and document it as "added in v0.1.6".

Given that the v0.1.0 test plan includes test #26, Option A is clearly the intent. Move the `filter(fn)` implementation into the v0.1.0 base and remove it from the v0.1.6 scope. The v0.1.6 surgical override can then focus on `sortFn` and connector lines only.

## Questions for the author

1. **Execution order guarantee:** Which specific mechanism guarantees that `window.SgTree` is assigned before `sg-tree--v0.1.1.js` reads it? The brief asserts this works but does not specify the mechanism. Is the plan to use explicit import chaining in override files? If so, does `import '../v0.1.0/sg-tree.js'` resolve correctly from within the `_latest/` merged output where there are no subdirectories?

2. **`customElements.define` in override files:** If an override file imports the base (to guarantee order), and the base calls `customElements.define('sg-tree', SgTree)` on load, does the import in the override trigger a second call to `customElements.define`? The Web Components spec throws `NotSupportedError` on duplicate registration. How is this avoided?

3. **`filter(fn)` scope clarification:** Is `filter(fn)` intended to be in v0.1.0 (as the test plan implies) or v0.1.6 (as the IFD sequence implies)? These are inconsistent in the brief.

4. **Expandable custom types:** Section 5.3 documents `expandableTypes: string[]` defaulting to `['folder']`. But the Section 4 data format says "Custom types ('entity', 'component', 'test') allowed." There is no example of registering a custom type as expandable via `expandableTypes`. Should the v0.1.0 test plan include a test for custom expandable types? (Test #25 covers `iconMap`, but nothing tests `expandableTypes`.)

5. **`badge` on expandable nodes:** The brief shows `badge: String(this._countFiles(folder))` in the SG/Send adapter example. Is `badge` expected on both leaf and folder nodes? The Section 4 data format lists it but the rendering spec (Section 8.3) does not address it. Confirm: badge renders on all node types, right-aligned, regardless of expand/collapse state.

## Recommendations

### R1 — ✅ RESOLVED — Use the override queue pattern

The surgical override model is approved with the queue pattern (`window._SgTreeQ`). No proof-of-concept needed — the mechanism is deterministic. The brief should be updated to show classic `<script>` tags for overrides and `type="module"` for the base, with the queue drain at the end of sg-tree.js.

### R2 — Add `getScrollTop` / `setScrollTop` to Section 5.2

The serialisation code in Section 9 uses these methods. They must appear in the public API table. Suggested addition:

```
| `getScrollTop()` | number | Get the current scroll offset of the viewport (px). Used in state serialisation. |
| `setScrollTop(px)` | void  | Set the viewport scroll position. Used in state restoration. |
```

### R3 — Move `filter(fn)` to v0.1.0 scope

The v0.1.0 test plan already includes test #26 for `filter(fn)`. Implement it in the base class. It is approximately 15 lines (a predicate applied during `_buildVisibleList`). This simplifies v0.1.6, which can then be "connectors + sort" only.

### R4 — Add `_rowHeight` to v0.1.0 README scope

The v0.1.0 README (to be created per Section 10.2) should specify: "The base class MUST expose `_rowHeight` as an internal numeric property (default: 28) readable by later surgical overrides." This makes the v0.1.2 virtual scrolling override's contract explicit from day one.

### R5 — Clarify `SELECTION_CHANGED` event detail comment

In Section 6.1, update the comment for `SELECTION_CHANGED` from `// { selectedIds }` to `// { selectedIds }  // array of id strings only; call getData() to recover node objects`. This prevents the common mistake of expecting node objects in the event detail.

### R6 — Add `expandableTypes` test to v0.1.0 test plan

Extend the test plan with a test for custom expandable types:

```
| 31 | Custom expandableType | Set expandableTypes=['folder','category'], tree with type:'category' nodes → category nodes are expandable, emit NODE_EXPANDED |
```

## Implementation sequencing

The IFD sequence in the brief (v0.1.0 → v0.1.6 → v0.2.0) is sound. Minor adjustments based on the concerns above:

**Ready to implement.** The queue pattern resolves the blocking concerns. No proof-of-concept required before v0.1.0 work begins.

**v0.1.0 (base class) — no change to sequence, but expand scope:**
- Add `getScrollTop` / `setScrollTop` (Recommendation R2)
- Add `filter(fn)` implementation (Recommendation R3)
- Expose `_rowHeight` internal property (Recommendation R4)
- Add test #31 for `expandableTypes`

**v0.1.1 (editor mode) — no change**

**v0.1.2 (virtual scrolling) — no change**

**v0.1.3 (multi-select) — no change, but verify `getSelectedId()` backward-compat note:**
The brief says `getSelectedId` → `getSelectedIds` is "backwards-compatible: single select returns `[id]`". This is backwards-incompatible — callers of `getSelectedId()` expect a string, not an array. The brief means that `getSelectedId()` remains available (returning a string) alongside the new `getSelectedIds()` (returning an array). The v0.1.3 README should explicitly state: "Do NOT remove or change the signature of `getSelectedId()`. Add `getSelectedIds()` as a new method alongside it."

**v0.1.4 (drag within tree) — no change**

**v0.1.5 (cross-tree drag) — candidate for post-v0.2.0 deferral:**
No current consumer requires cross-tree drag. The vault's drag-and-drop is within a single tree. This version adds complexity and a new event constants file (`sg-tree-events--v0.1.5.js`), which adds a new loading dependency. Recommend deferring v0.1.5 to v0.3.x (post-consolidation) unless a real use case is confirmed before implementation starts.

**v0.1.6 (connectors + sort) — simplified if `filter` moves to v0.1.0:**
With `filter(fn)` in v0.1.0, v0.1.6 becomes connectors + custom `sortFn`. This is a cleaner version scope.

**v0.2.0 (consolidation) — no change to process, but verify:**
The consolidation process described in Section 11 is correct. The v0.2.0.test.html running all ~84 assertions against the single merged file is the right validation gate. Ensure the process document explicitly states: the consolidated file is written from scratch (or by manual merge), NOT by concatenating the override files in order — the prototype patches must be integrated back into the class body.
