# Architect Review — SgToolApi Core Class Design

**Version:** v0.20.38
**Date:** 9 Apr 2026
**Author:** Architect (Explorer team)
**Briefs reviewed:**

---

## 1. Summary Assessment

The `SgToolApi` class design is sound. The `register/activate` pattern is clean and follows the project's
existing conventions (compare: `VfsProviderBase`, `SgLlmRequest`). The execution log is a genuine addition to
observability. Three specific concerns need resolution before implementation starts.

---

## 2. Class Interface Assessment

### 2.1 The register/activate pattern

The proposed interface from the impl brief:

```javascript
const api = new SgToolApi({ name, version, manifest, skills });
api.register('generate', generateImpl, { async: true, events: [...] });
api.activate(); // → window.__tool, window.__tools['name'], fires tool:ready
```

This is good. The two-phase construction (register → activate) separates wiring from publication.
It also means tools can register all methods before any external consumer can call them — no race
condition between `tool:ready` and method availability.

**One concern:** the `activate()` call sets `window.__tool` as an alias. When multiple tools coexist
on a page (SG Layout multi-panel), whichever activates last owns `window.__tool`. This is mentioned
in the arch brief but the resolution is implicit. Make it explicit in the implementation:
`window.__tool` is set only if no other tool has claimed it, or it is always the last activator.
Pick one rule and document it.

### 2.2 Execution Log

Proposed: every method call logged with `{ timestamp, method, params, result, duration, error? }`.

This is correct and maps directly to what `sg-tool-api-logger` needs. Two issues to resolve:

**Issue A — param sanitisation.** The `connect({ apiKey })` call will log the API key in plaintext.
The registry needs a sanitisation hook:

```javascript
api.register('connect', connectImpl, {
    sanitiseParams: (p) => ({ ...p, apiKey: '••••' })
});
```

Without this, the logger becomes a credential exfiltration risk when screenshared or when logs are
exported. This is not optional — it must be in the initial design.

**Issue B — log size.** An unbounded in-memory log is fine for interactive use. For batch/parallel
workflows (5 models × N slides), the log grows without limit. Cap the log at a configurable
`maxEntries` (default 500) with a ring-buffer replacement strategy. The logger component should
expose this cap as an attribute.

### 2.3 Meta API completeness

The proposed meta methods (`getManifest`, `getMethods`, `getSkills`, `getVersion`, `getEvents`,
`health`) cover the use cases. One gap: `health()` is described as returning
`{ status, dependencies, ready }` but the implementation detail for checking dependency readiness
is undefined.

Recommendation: for MVP, `health()` returns a static object derived from the registered methods and
the `manifest.json` load status. Do not attempt to re-fetch or validate dependency URLs at runtime —
that requires network calls and complicates the contract. Document this limitation explicitly.

### 2.4 Alignment with existing codebase patterns

The project already has:
- `EventBus` (internal to `sg-layout.js` lines 53-58) — a simple on/off/emit map
- `SGL_LLM` frozen constants in `sg-llm-events.js`
- `SGL_EVENTS` frozen constants in `sg-layout-events.js`

`SgToolApi._emit()` should follow the same frozen-constants pattern. Create
`sg-tool-api-events.js` as a sibling export with a `SGA_EVENTS` frozen object. Do not use
string literals for event names in the core module itself.

## 3. The `window.__tool` Registration: One Issue the Brief Overlooked

The brief shows `window.__tools[name]` for multi-tool pages and `window.__tool` as the primary alias.
Both are correct. However, the infographic generator currently fires events on the `bus` div
(a scoped `data-llm-bus` element), not on `window`. When the API wraps generate, the events must
move to `window` as stated. But the mini-bus pattern (lines 473-557 of `infographic-gen.js`) creates
a _new_ div per request to isolate concurrent generations.

This creates a mapping problem: `generation:complete` on `window` needs to carry a `generationId`
to distinguish which of five parallel generations completed. The arch brief correctly includes
`generationId` in the event detail. The impl brief confirms this. No issue — but the Dev needs to
confirm the `generationId` is stable before the `generate()` Promise is returned (i.e., OpenRouter
returns it in the initial response, not just at completion).

Looking at line 503 of `infographic-gen.js`:

```javascript
const genId = ev.detail?.rawResponse?.id
           ?? ev.detail?.rawChunks?.find(c => c?.id)?.id
           ?? null;
```

The `genId` is extracted only at `REQUEST_COMPLETE`. This means there is currently no `generationId`
available to return from a fast `generate({ await: false })` call. The impl brief's `generate()`
API assumes you get a `generationId` back immediately. **This is a gap the brief does not address.**

Options:
1. Generate a client-side UUID as the `generationId` at call time. Map it to the OpenRouter ID
   internally when `REQUEST_COMPLETE` fires. Surface both in events.
2. Accept that `await: false` returns `{ generationId: null }` initially, and the true ID comes
   in the `generation:started` event.

Option 1 is the right architecture. A client-generated ID is always available; the OpenRouter ID
is a bonus for cost lookup. Recommend this explicitly in the impl.

## 4. localStorage vs In-Memory State

The impl brief correctly states that `sg-tool-api` core must not use `localStorage`. The execution
log is in-memory. However, the infographic-gen already uses `localStorage` for `apiKey` and
`lastPrompt` (lines 33-34, 48, 583-586 of `infographic-gen.js`). These are in the tool-specific
layer, not the core. This is acceptable and does not need to change — just confirm the boundary:
`SgToolApi` core = no storage, tool implementations = storage permitted where needed.

## 5. File Location

The impl brief proposes:

```
core/sg-tool-api/v0/v0.1/v0.1.0/
    sg-tool-api.js
    sg-tool-api-events.js
    sg-tool-api-registry.js
```

This follows the IFD folder convention used by `core/sg-vfs/v0/v0.1/v0.1.0/` and is correct.
`sg-tool-api-registry.js` as a separate file is optional for MVP — the registry logic is five lines
and could live in `sg-tool-api.js` initially. Split it only when a use case requires importing the
registry without the full `SgToolApi` class.

## 6. Not-Yet-Existing Items

PROPOSED — does not exist yet:
- `core/sg-tool-api/` module (any version)
- `window.__tool` / `window.__tools` registration pattern
- `sg-tool-api-events.js` constants
- Execution log
- Any SKILL files or `manifest.json` on the infographic generator beyond the existing
  dependency-only manifest at `v0.1.25/en-gb/infographic-gen/` (if that even exists — not in
  reality doc)

All UI components (`sg-tool-api-explorer`, `sg-tool-api-console`, etc.) are PROPOSED.
