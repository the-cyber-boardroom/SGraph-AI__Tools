# IFD Surgical Overrides with Version-Stamped Filenames

**Version:** v0.1.5
**Date:** 29 March 2026
**Role:** Architect + Dev (Explorer team)
**Session:** `claude/start-tools-explorer-session-WariD`
**Context:** How to apply IFD surgical overrides in the __Tools repo, compatible with the `build_ifd_latest.py` layering system. Informed by SG/Send's v0.3.1 prototype override pattern.

---

## The Problem

The IFD (Incremental Feature Development) methodology says:
- Each version folder contains only its **deltas** (new/changed files)
- The build system layers all versions in order to produce the deployable state
- Later versions overwrite earlier versions' files with the same name

But for **surgical prototype overrides** (like sg-tree's planned v0.1.1–v0.1.6), we need BOTH the base class AND the overrides to exist in the final `_latest/` directory. If both are named `sg-tree.js`, the override (80 lines) destroys the base (800 lines).

---

## The Solution: Version-Stamped Filenames

Each surgical override file includes the version number in its filename:

```
core/sg-tree/
  v0/v0.1/
    v0.1.0/
      sg-tree.js                    ← full base class (~800 lines)
      sg-tree-events.js             ← frozen event constants
      sg-tree.css                   ← optional external theme
    v0.1.1/
      sg-tree--v0.1.1.js            ← surgical override: editor mode (~80 lines)
    v0.1.2/
      sg-tree--v0.1.2.js            ← surgical override: virtual scrolling (~60 lines)
    v0.1.3/
      sg-tree--v0.1.3.js            ← surgical override: multi-select (~50 lines)
```

After `build_ifd_latest.py` layers them into `_latest/`, the result is:

```
_latest/
  sg-tree.js                       ← from v0.1.0 (PRESERVED — no collision)
  sg-tree-events.js                ← from v0.1.0
  sg-tree.css                      ← from v0.1.0
  sg-tree--v0.1.1.js               ← from v0.1.1 (unique filename)
  sg-tree--v0.1.2.js               ← from v0.1.2 (unique filename)
  sg-tree--v0.1.3.js               ← from v0.1.3 (unique filename)
```

All files survive the merge. The base is never overwritten.

## How Surgical Overrides Work with ES Modules

The base class registers the custom element and exposes itself for patching:

```javascript
// v0.1.0/sg-tree.js (ES module)
export class SgTree extends HTMLElement {
    _renderRow(node, depth) { /* base implementation */ }
    _onKeydown(e) { /* base implementation */ }
    // ... 800 lines
}

customElements.define('sg-tree', SgTree);

// Expose for surgical overrides — the class is just an object,
// prototype patching works after define()
window.SgTree = SgTree;
```

Each surgical override imports or accesses the class and patches specific methods:

```javascript
// v0.1.1/sg-tree--v0.1.1.js (ES module)
// Surgical override: adds editor mode (rename, delete, create folder)

const { SgTree } = window;  // access the already-defined class

// Wrap _renderRow to add edit affordances when editable="true"
const _originalRenderRow = SgTree.prototype._renderRow;
SgTree.prototype._renderRow = function(node, depth) {
    const el = _originalRenderRow.call(this, node, depth);
    if (this._editable) {
        // Add edit button, inline rename input, etc.
    }
    return el;
};

// Add new methods (no wrapping needed — they don't exist on the base)
SgTree.prototype._startRename = function(id) { /* ... */ };
SgTree.prototype._commitRename = function(id, newLabel) { /* ... */ };
```

**Why this works:**
- `customElements.define()` registers the class — but the class is a living JS object
- Modifying `SgTree.prototype` after `define()` affects all existing and future instances
- ES modules CAN access `window.SgTree` — module scope isolation only prevents automatic global pollution, not explicit reads from `window`
- The constraint is that `customElements.define('sg-tree', ...)` can only be called **once** — but we only call it in v0.1.0

## Loading Order

Consumers load the base + overrides in order:

```html
<!-- Load base class (registers <sg-tree> custom element) -->
<script type="module" src="/core/sg-tree/v0/v0.1/v0.1.0/sg-tree.js"></script>

<!-- Load surgical overrides (patch SgTree.prototype) -->
<script type="module" src="/core/sg-tree/v0/v0.1/v0.1.1/sg-tree--v0.1.1.js"></script>
<script type="module" src="/core/sg-tree/v0/v0.1/v0.1.2/sg-tree--v0.1.2.js"></script>
```

**After v0.2.0 consolidation**, consumers load a single file:

```html
<script type="module" src="/core/sg-tree/v0/v0.2/v0.2.0/sg-tree.js"></script>
```

## How This Compares to SG/Send's v0.3.1 Pattern

SG/Send uses the same prototype override approach but with a slightly different naming convention:

| Aspect | SG/Send (v0.3.1) | SGraph Tools (proposed) |
|---|---|---|
| **Base file** | `send-browse.js` | `sg-tree.js` |
| **Override file** | `send-browse-v031.js` | `sg-tree--v0.1.1.js` |
| **Naming pattern** | `{name}-v{MMm}.js` (no dots) | `{name}--v{M}.{m}.{p}.js` (with dots, double dash) |
| **Override technique** | IIFE wrapping: `(function(original) { return function() {...} })(proto.method)` | Same technique |
| **Module type** | Plain `<script>` | `<script type="module">` (access via `window.SgTree`) |
| **Class exposure** | `SendBrowse` already on window (non-module script) | Explicit `window.SgTree = SgTree` |

**Why we prefer `sg-tree--v0.1.1.js` over `sg-tree-v011.js`:**
- The double dash `--` clearly separates the component name from the version suffix
- Full semver in the filename (`v0.1.1` not `v011`) directly maps to the IFD folder name
- Easier to grep: `sg-tree--v0.1.*` finds all overrides
- No ambiguity: `sg-tree-events.js` is a different file (single dash), `sg-tree--v0.1.1.js` is an override (double dash)

## IFD Layering Compatibility

The `build_ifd_latest.py` script copies files by relative path. With version-stamped filenames:

```python
# v0.1.0/sg-tree.js       → _latest/sg-tree.js         ✓ (base preserved)
# v0.1.1/sg-tree--v0.1.1.js → _latest/sg-tree--v0.1.1.js ✓ (unique, no collision)
# v0.1.2/sg-tree--v0.1.2.js → _latest/sg-tree--v0.1.2.js ✓ (unique, no collision)
```

If a later version needs to UPDATE the base (not just patch it), it can include its own `sg-tree.js` which will overwrite the v0.1.0 base — this is the normal IFD overwrite behaviour. But surgical overrides use unique filenames so they coexist.

---

## Rules for Version-Stamped Files

1. **The base class file has NO version stamp** — `sg-tree.js`, not `sg-tree--v0.1.0.js`. This is the canonical name that consumers import.

2. **Surgical override files ALWAYS have a version stamp** — `sg-tree--v0.1.1.js`. The `--` prefix + full semver makes them unambiguous.

3. **Event/CSS files are NOT version-stamped** unless a later version adds new constants. If v0.1.5 adds new events, it creates `sg-tree-events--v0.1.5.js` with ONLY the additions. The base `sg-tree-events.js` from v0.1.0 is never modified.

4. **The version stamp matches the IFD folder name exactly** — `v0.1.1/sg-tree--v0.1.1.js`. No ambiguity about which version introduced which override.

5. **At consolidation (v0.2.0)**, all overrides are merged into a single `sg-tree.js`. The version-stamped files are no longer needed. v0.2.0 contains `sg-tree.js` (complete, self-contained) which overwrites the v0.1.0 base via normal IFD layering.

---

## Applicability Beyond sg-tree

This pattern applies to ANY component that needs surgical IFD overrides:

- `sg-layout--v0.1.5.js` — could add closable/fixedSize as a surgical overlay
- `sg-image-editor--v1.0.1.js` — could add rotation as a surgical overlay
- `sg-video-splitter--v1.0.1.js` — could add visual timeline as a surgical overlay

The convention is universal: `{component-name}--v{version}.js` for surgical overrides, `{component-name}.js` for the base or consolidated version.
