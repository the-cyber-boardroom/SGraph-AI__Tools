## What Went Right

1. **Single-session implementation.** The entire restructure — 31 files, 1900+ lines — was completed and deployed in one session. No partial states or deferred items.

2. **Cross-team debrief model worked.** The SG/Send team's code-level review caught exactly the right issues. The debrief was actionable enough for the Tools team to execute without further clarification (except on 5 questions Dinis answered directly).

3. **Script reuse.** Copying `deploy_static_site.py` verbatim from Send eliminated the risk of reimplementation bugs. The i18n generator adaptation was minimal (changed `UI_BASE` and reduced locale list).

4. **Starter locale strategy.** Starting with 5 locales (en-gb + 4 generated) instead of all 17 is the right call. Proves the pipeline without the overhead of 17 translation files to maintain.

## Remaining Gaps

### 1. Root URL Returns 404 (High Priority)

`dev.tools.sgraph.ai/` shows a 404. The site content lives at `/tools/v0/v0.1/v0.1.0/en-gb/`. Need either:
- A root-level `index.html` in `sgraph_ai__tools/` that redirects to the tools landing page
- CloudFront default root object configuration

**Recommendation:** Add `sgraph_ai__tools/index.html` with a redirect. This is the simplest fix and matches how Send handles it.

### 2. Header Does Not Match sgraph.ai (High Priority)

The current `sg-header` web component uses a custom design. The sgraph.ai website uses a different header with `SG/` branding, navigation links (Product, Pricing, Architecture, Team), and a locale picker. For tools.sgraph.ai to be linked from sgraph.ai, it needs to adopt the same header.

**Recommendation:** Replace `sg-header` with the sgraph.ai header pattern. The code exists in `sgraph_ai__website/_common/css/style.css` + `_common/js/i18n.js`.

### 3. No `inject_build_version.py` Adaptation

The `inject_build_version.py` was copied from Send but still references `sgraph_ai_app_send/version` as the app version source. It needs to be adapted for the Tools repo.

### 4. Crypto/SSH Modules Remain Unverified

Per the debrief, these should eventually be replaced with exact copies from Send's deployed code or imported via `static.sgraph.ai` URLs. For the MVP this is acceptable, but should be resolved before any consumer (send, vault, workspace) imports from tools.sgraph.ai.

### 5. Three-Tier Import Path Question

The current architecture has tools importing core modules via absolute paths from the site root:
```html
<script src="/components/header/v1/v1.0/v1.0.0/sg-header.js"></script>
```

This works when the entire `sgraph_ai__tools/` folder is the deployed root. But it means core modules and tools are deployed as a single unit. If we later want to version and deploy modules independently, the import strategy will need to change to CDN URLs from `static.sgraph.ai`.

**Recommendation:** This is fine for the MVP. Revisit when we need independent module deployments.
