**Version:** v0.1.0

**Author:** Architect (Explorer team)

---

## 1. Summary

The Tools repo has been restructured from a flat-versioned skeleton with no deployment infrastructure to a fully IFD-compliant static site, live at `dev.tools.sgraph.ai`. This review assesses the architectural quality of the restructure, its alignment with SG/Send conventions, and what remains to be done.

**Verdict: The restructure successfully addresses every critical structural gap identified by the SG/Send debrief.** The folder hierarchy, version paths, CI workflows, i18n structure, and deployment pattern now match the conventions used across the SGraph ecosystem. The site is deployed and serving live pages.

## 2. What Was Built

### 2.1 Folder Structure -- IFD Compliant

The repo now follows the canonical SG pattern:

```
sgraph_ai__tools/                          # Deployable root (synced to S3)
  core/
    crypto/v1/v1.0/v1.0.0/                # IFD nested version path
      sg-crypto.js
      manifest.json
    ssh/v1/v1.0/v1.0.0/
      sg-ssh.js
      manifest.json
  components/
    header/v1/v1.0/v1.0.0/
      sg-header.js
      manifest.json
    footer/v1/v1.0/v1.0.0/
      sg-footer.js
      manifest.json
  tools/
    v0/v0.1/v0.1.0/
      _common/css/tools.css               # Shared design tokens + base styles
      en-gb/                              # Source locale (in git)
        index.html                        # Landing page
        ssh-keygen/index.html             # SSH keygen tool
      i18n/                               # Translation JSON files
        en-gb.json, en-us.json, fr-fr.json, de-de.json, es-es.json
      index.html                          # Locale redirect
      404.html
      manifest.json
      robots.txt
      sitemap.xml
```

This matches the SG/Send pattern at every level:
- `sgraph_ai__tools/` as deployable root (cf. `sgraph_ai_app_send__ui__user/`)
- IFD nested version paths `v{major}/v{major}.{minor}/v{major}.{minor}.{patch}/`
- `_common/` for shared assets
- `en-gb/` as source locale
- `i18n/` for translation JSON files
- Root-level `index.html` for locale redirect
- `manifest.json` per module

### 2.2 CI/CD Pipeline

Two GitHub Actions workflows now exist:
- `deploy-tools__dev.yml` -- triggers on push to `dev` branch, deploys to `websites/tools-sgraph-ai/dev/`
- `deploy-tools__main.yml` -- triggers on push to `main` branch, deploys to `websites/tools-sgraph-ai/main/`

Supporting scripts:
- `scripts/deploy_static_site.py` -- copied from SG/Send (handles content-type, cache headers, release versioning, `latest/` alias creation, CloudFront invalidation)
- `scripts/generate_tools_i18n_pages.py` -- adapted from Send's i18n generator for 4 target locales
- `scripts/inject_build_version.py` -- adapted for Tools repo paths

The `version` file at repo root contains `v0.1.0`, consumed by CI to determine deployment paths.

### 2.3 i18n Architecture

The i18n implementation follows Send's v0.2.0 pattern:
- 35 translation keys covering both the landing page and SSH keygen tool
- `data-i18n` attributes on all translatable HTML elements
- 5 starter locales: en-gb (source, in git) + en-us, fr-fr, de-de, es-es (CI-generated pages)
- Locale auto-detection in the root `index.html` redirect page

### 2.4 Manifest Files

Every module now has a `manifest.json` declaring:
- Module name and version
- Exported symbols
- Dependencies (if any)
- Module type (core, component, or tool)

This enables tooling to programmatically discover what each module provides, which is a prerequisite for automated dependency resolution and documentation generation.

| Locale redirect at root | `index.html` with auto-detect | `index.html` with auto-detect | Yes |
| `deploy_static_site.py` | Reused directly | Copied from Send | Yes |

| S3 path isolation by env | `websites/{site}/{env}/` | `websites/tools-sgraph-ai/{env}/` | Yes |
| `manifest.json` per module | Used in Send | Added to all 5 modules | Yes |
| SEO files (robots.txt, sitemap.xml) | Present in Send UIs | Present | Yes |

### What Diverges (Intentionally)

| Pattern | SG/Send | Tools | Rationale |
|---------|---------|-------|-----------|
| Component CSS | Separate `.css` files | Inline CSS in JS | SG/Send debrief recommends keeping inline for now; separate files when extracting components from Send/Vault |
| Component template loading | Loads `.html` template files | Builds DOM in JS | Simpler for small components; revisit when components grow |
| Base component class | `send-component.js` | No base class | Tools components are simpler; base class adds overhead without benefit at this scale |
| Number of locales | 17 locales | 5 locales | Start small, expand once pipeline is proven |

These divergences are all explicitly sanctioned by the SG/Send debrief and represent pragmatic simplifications for the MVP.

## 5. Architectural Strengths

### 5.1 Clean Separation of Deployable and Non-Deployable Content

The `sgraph_ai__tools/` boundary is a clear architectural line. Everything inside it deploys to S3. Everything outside it (team/, briefs/, .claude/, .github/, scripts/) stays in the repo. This makes the CI pipeline a simple `aws s3 sync sgraph_ai__tools/ s3://bucket/websites/tools-sgraph-ai/{env}/releases/{ifd_path}/`.

### 5.2 Version Path Hierarchy Enables Future Flexibility

The IFD nested path `v1/v1.0/v1.0.0/` is more than a naming convention. It creates a physical folder hierarchy that enables:
- **Major version browsing:** list `v1/` to see all minor versions
- **Minor version browsing:** list `v1/v1.0/` to see all patches
- **Surgical patches:** `v1/v1.0/v1.0.1/` can contain only changed files (delta from v1.0.0)
- **S3 prefix queries:** efficiently list all versions of a module

### 5.3 i18n Architecture is Forward-Compatible

The `data-i18n` attribute approach with JSON translation files is the same pattern used by SG/Send. Adding new locales requires only:
1. Adding a new JSON file to `i18n/`
2. Updating the CI generator script's locale list

No changes to HTML templates are needed when expanding the locale set.

### 5.4 Shared CSS with Design Tokens

Extracting `tools.css` into `_common/css/` with CSS custom properties (design tokens) means all tools share consistent spacing, colors, and typography. New tools inherit the visual system without duplicating styles.

## 6. Remaining Gaps

### 6.1 Root URL Does Not Resolve (Priority: High)

`dev.tools.sgraph.ai/` returns a 404. Users navigating to the bare domain see nothing. This needs either:
- An `index.html` at the S3 site root that redirects to `tools/v0/v0.1/v0.1.0/en-gb/index.html`
- An S3 redirect rule or CloudFront function that handles the root path
- A `latest/` alias at the root that points to the current release

**Recommendation:** Add a root `index.html` in `sgraph_ai__tools/` that redirects to the latest tools landing page. This file lives in git and deploys with every release.

### 6.2 SGraph Navigation Header Not Integrated (Priority: High)

The site currently uses the basic `sg-header` component, which is specific to tools.sgraph.ai. The shared sgraph.ai navigation bar (Product, Pricing, Architecture, Team) used across sgraph.ai, send.sgraph.ai, and vault.sgraph.ai is not yet integrated.

**Recommendation:** Import the sgraph.ai header from `static.sgraph.ai` (where it is already deployed) or build a compatible version. This is important for brand consistency and cross-site navigation.

### 6.3 CORS Headers Not Configured (Priority: Medium)

For the dependency inversion to work (send.sgraph.ai importing from tools.sgraph.ai), the S3 bucket or CloudFront distribution must return appropriate CORS headers allowing cross-origin imports from `*.sgraph.ai` domains.

**Recommendation:** Configure CORS on the S3 bucket:
```json
{
  "AllowedOrigins": ["https://*.sgraph.ai"],
  "AllowedMethods": ["GET"],
  "AllowedHeaders": ["*"],
  "MaxAgeSeconds": 86400
}
```

### 6.4 Cross-Project Import Not Yet Tested (Priority: Medium)

The architecture's core value proposition is that send.sgraph.ai, vault.sgraph.ai, and other consumers import modules from tools.sgraph.ai. This has not been tested. Until a cross-origin ES module import is verified working, the dependency inversion is theoretical.

**Recommendation:** Create a minimal test page on another *.sgraph.ai domain that imports `sg-ssh.js` from `dev.tools.sgraph.ai` and calls `generateSSHKeyPair()`. This proves the entire pipeline end to end.

### 6.5 Per-Module CI Granularity (Priority: Low)

The current CI workflows trigger on any change to `sgraph_ai__tools/**`. The architecture brief specifies per-module pipelines where a change to `core/crypto/` does not trigger a rebuild of `components/header/`. For a static site with no build step, this is less critical (there is no "rebuild" -- just a re-sync to S3), but it becomes important as the module count grows.

**Recommendation:** Defer until the module count exceeds 10. At that point, split into per-tier or per-module workflows.

### 6.6 Crypto and SSH Code Unverified (Priority: Low for now)

The SG/Send debrief flagged that `sg-crypto.js` was written from scratch and has not been tested against Send's production crypto. The SSH module only supports Ed25519 (Send also supports RSA-4096). For the MVP, where these modules are only used by the SSH keygen tool, this is acceptable. It becomes a priority when cross-project imports begin.

**Recommendation:** Before any consumer imports `sg-crypto.js` from tools.sgraph.ai, run a compatibility test against Send's `sg-send-crypto.js` to verify wire-format compatibility. For SSH, add RSA-4096 support when the tool needs it.

### 6.7 Import Path Strategy for Independent Module Deployment

Tools currently import core modules via absolute paths from the site root:
```html
<script src="/components/header/v1/v1.0/v1.0.0/sg-header.js"></script>
```

This works when the entire `sgraph_ai__tools/` folder is the deployed root. But it means core modules and tools are deployed as a single unit. If we later want to version and deploy modules independently, the import strategy will need to change to full CDN URLs from `static.sgraph.ai`.

**Recommendation:** Fine for MVP. Revisit when independent module deployments are needed.

## 9. Conclusion

The IFD restructure is a milestone for the Tools project. It transforms the repo from a structurally non-compliant skeleton into a production-deployed site that follows every SG convention. The previous architect review identified deployment infrastructure as the single highest-priority gap -- that gap is now closed.

The architectural foundation is solid. The folder structure, version paths, CI pipeline, i18n system, and deployment pattern are all proven and live. What remains is building on this foundation: integrating the shared header, enabling cross-project imports, and beginning the module migration from Send.

The fact that this was accomplished in a single session -- triggered by a cross-team debrief from the SG/Send agentic team -- demonstrates the value of the IFD methodology's rapid iteration model and the benefit of cross-team architectural reviews.
