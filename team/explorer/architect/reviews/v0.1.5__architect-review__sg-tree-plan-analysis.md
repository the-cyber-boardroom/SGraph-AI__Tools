## 1. What's Good

The brief gets several things right. These should be preserved regardless of how the implementation mechanics change.

**API contract.** The public surface (`setData`, `getData`, `select`, `expand`, `filter`, `getExpandedIds`/`setExpandedIds`) is well-scoped. The method set maps directly to the three consumer use cases (SG/Send browse, SG/Vault tree view, SG/Workspace vault panel) without leaking implementation details.

**Canonical data format.** `{id, label, type, children, icon, meta, badge, disabled}` is the right shape. The `meta` pass-through is particularly good -- it means sg-tree never needs to know about zip entries, vault pointers, or workspace file objects. Each consumer's adapter maps its domain into this format and gets its domain data back in events.

**Event architecture.** The `SGT_EVENTS` frozen object pattern is proven (sg-layout uses the identical pattern with `SGL_EVENTS`). The event names follow the `sg-tree:verb-noun` convention. `composed: true` for Shadow DOM boundary crossing is correct.

**Keyboard navigation spec.** Full tree-view keyboard model (arrows, j/k vim-style, Home/End, `*` for expand siblings). This is more complete than any of the three current implementations. SG/Send only has j/k for files; vault and workspace have no keyboard nav at all.

**Consumer migration plan.** The phased approach (build sg-tree first, consolidate to v0.2.0, THEN migrate consumers) is correct. The adapter examples (`zipToTree`, `vaultToTree`) are realistic and the estimated line reductions (~200 lines removed from send-browse.js) are credible.

**Test accumulation strategy.** Each version's test page running ALL prior assertions before adding its own is the right way to guarantee the v0.2.0 consolidation works. This is an improvement over sg-layout, which only tested the current version's features.

**sg-layout integration.** `getLayoutState()`/`setLayoutState()` for hosting inside sg-layout panels is the correct protocol. sg-layout already calls these methods on child components during serialisation.

## 2. The File Naming Problem (BLOCKING)

The brief proposes that every version from v0.1.0 through v0.1.6 contains a file called `sg-tree.js`:

```
core/sg-tree/v0/v0.1/v0.1.0/sg-tree.js    (full base class, ~800 lines)
core/sg-tree/v0/v0.1/v0.1.1/sg-tree.js    (surgical override, ~100 lines)
core/sg-tree/v0/v0.1/v0.1.2/sg-tree.js    (surgical override, ~70 lines)
...
```

**This is incompatible with the `_latest` layering model.**

`scripts/build_ifd_latest.py` (lines 91-100) builds the `_latest` directory by iterating version folders in order and copying files with matching relative paths. The key line:

```python
rel = src_path.relative_to(version_dir)
dst = latest_dir / rel
shutil.copy2(src_path, dst)
```

When two version folders contain the same relative path (`sg-tree.js`), the later version's file **overwrites** the earlier version's file in `_latest/`. After layering, `_latest/sg-tree.js` would be the v0.1.6 override (~50 lines of prototype patches) with NO base class. The component would be broken.

This is by design. The tools pages use the same model: `v0.1.2/en-gb/index.html` overwrites `v0.1.0/en-gb/index.html` in `_latest/` because each version's `index.html` is a complete replacement. The IFD layering model is **replace**, not **augment**.

The brief's surgical override model requires **sequential loading of all files**, which is the opposite of what `_latest` does.

### Proposed Solutions

**Option A: Version-stamped filenames.** Each override gets a unique filename:

```
v0.1.0/sg-tree.js                  (base class)
v0.1.1/sg-tree--v0.1.1.js          (editor mode override)
v0.1.2/sg-tree--v0.1.2.js          (virtual scroll override)
...
```

After `_latest` layering, ALL files coexist:

```
_latest/sg-tree.js
_latest/sg-tree--v0.1.1.js
_latest/sg-tree--v0.1.2.js
...
```

Consumers load them in order. This works with the existing build script but is ugly and couples filenames to version numbers.

**Option B: Abandon surgical overrides; use the sg-layout model.** sg-layout's `v0.1.0/sg-layout.js` is a single 2,163-line file that contains ALL features from v0.1.0 through v0.1.3. Each IFD version that adds features does so by creating a new COMPLETE version of the file. The v0.1.1 folder's `sg-layout.js` is a complete replacement that includes the v0.1.0 base plus tabs. This is exactly how IFD layering is designed to work.

For sg-tree, this would mean:
- `v0.1.0/sg-tree.js` = base class (~800 lines)
- `v0.1.1/sg-tree.js` = base + editor mode (~900 lines, complete replacement)
- `v0.1.2/sg-tree.js` = base + editor + virtual scroll (~970 lines, complete replacement)
- ...and so on

The v0.2.0 consolidation still happens but is mechanical (copy v0.1.6 to v0.2.0, clean up any accumulated cruft).

**Option C: Don't use IFD layering for core/sg-tree at all.** Treat the v0.1.x sequence as a development plan only (not a deployment artifact). Develop in a feature branch, merge to `core/sg-tree/v0/v0.1/v0.1.0/` as a single growing file, and cut v0.2.0 when all features are done.

**Recommendation: Option B.** It follows the proven sg-layout pattern, works with the existing build infrastructure, and each version folder is independently deployable. The "surgical override" concept is valuable as a *development discipline* (each version only adds specific methods) but the *file artifact* should be a complete replacement, not a patch.

## 3. The Surgical Override Mechanism

Even if we solve the file naming problem, the prototype monkey-patching approach has technical issues with ES modules.

### The module/script mismatch

The brief proposes loading the base as `type="module"` (line 441 of the brief) and overrides as plain `<script>` tags (lines 442-447):

```html
<script type="module" src=".../v0.1.0/sg-tree.js"></script>
<script src=".../v0.1.1/sg-tree.js"></script>
```

This has a fundamental problem: ES modules run in strict mode with their own scope. A class exported from a module is not available on `window` for a plain `<script>` to patch. The override scripts would need to either:

1. Import the class from the module (making them also modules, with deferred execution ordering issues), or
2. Have the base module explicitly attach the class to `window` (an anti-pattern for ES modules)

The brief cites the SG/Send v0.3.1 pattern (`send-browse-v031.js` wrapping `SendBrowse.prototype`) as precedent. But that pattern works because send-browse.js is loaded as a plain script that registers on `window`. In an ES module world, prototype patching from external files is awkward.

### The execution order problem

Even if both base and overrides are `type="module"`, ES modules have deferred execution. The HTML spec does not guarantee that `v0.1.0/sg-tree.js` finishes executing before `v0.1.1/sg-tree.js` starts -- both are fetched and executed based on their dependency graph, not their position in the HTML. To guarantee order, you would need an explicit import chain:

```js
// v0.1.1/sg-tree.js
import { SgTree } from '../v0.1.0/sg-tree.js';
SgTree.prototype._renderRow = ...;
```

This creates cross-version import dependencies, which defeats the purpose of IFD isolation.

### What sg-layout actually does

sg-layout does NOT use surgical overrides. It is a single file (`sgraph_ai_tools__static/core/sg-layout/v0.1.0/sg-layout.js`, 2163 lines) that contains the full class with all features. The file header documents the version history:

```js
/**
 * sg-layout.js
 * v0.1.3 — drag to dock
 * v0.1.2 — fractal registration
 * v0.1.1 — tab stacks
 * v0.1.0 — row/column layout, resize handles, registration protocol, serialisation.
 */
```

Each IFD version replaced the entire file. This is the pattern that works.

### Recommendation

Do not use prototype monkey-patching via separate files. Use the sg-layout model: each version is a complete, self-contained `sg-tree.js`. Maintain the surgical override *discipline* (each version's diff should only touch the methods specified) but produce a complete file each time.

## 4. Placement: core/ vs components/

The brief places sg-tree in `core/sg-tree/`. This needs scrutiny.

### Current convention in this codebase

| Directory | Contents | Pattern |
|---|---|---|
| `core/` | Pure JS modules with no UI: sg-crypto, sg-ssh, sg-pbkdf2, sg-image, sg-video, sg-vault-client, sg-pyodide, sg-send-crypto | Functions and classes, no `HTMLElement`, no Shadow DOM |
| `core/` (exception) | sg-layout | Web Component with Shadow DOM -- but sg-layout is infrastructure, not a visual component |
| `components/` | All Web Components with Shadow DOM: sg-header, sg-footer, sg-site-header, sg-site-footer, sg-locale-picker, sg-upload-dropzone, sg-key-generator, sg-image-editor, sg-video-splitter, sg-send-drop | `extends HTMLElement`, Shadow DOM, visual UI |

sg-tree is a Web Component (`extends HTMLElement`) with Shadow DOM, CSS custom properties, and visual rendering. By the current convention, it belongs in `components/`.

### The sg-layout precedent

sg-layout is also a Web Component in `core/`. The implicit distinction seems to be: `core/` is for foundational infrastructure that other components compose (sg-layout is a window manager that hosts other components), while `components/` is for leaf-level UI elements.

sg-tree occupies a middle ground. It is a reusable infrastructure component (like sg-layout) that consumers compose into their layouts. It is also a visual UI element (like the components). The brief positions it as infrastructure ("same model as sg-layout"), and three separate products will import it.

### Recommendation

`core/` is acceptable given the sg-layout precedent, but this should be a conscious decision, not an assumption. If sg-tree goes in `core/`, the convention becomes: "core/ contains both pure JS modules AND foundational Web Components that are consumed by multiple SGraph products." If it goes in `components/`, it follows the Web Component convention but sits alongside leaf components like sg-footer.

I lean toward `components/sg-tree/` because it has a visual DOM, Shadow DOM, CSS theming, and renders content that users see and interact with. sg-layout is arguably the exception, not the rule. But this is a judgment call for the human.

## 5. Version Scope: Are 7 IFD Versions Too Many?

The brief proposes v0.1.0 through v0.1.6 (7 versions) before any consumer uses sg-tree. No consumer migrates until v0.2.0 consolidation.

### Analysis

Some of these versions could be combined without loss of clarity:

| Brief version | Feature | Could combine with |
|---|---|---|
| v0.1.0 | Core tree, expand/collapse, selection, keyboard | Must be standalone |
| v0.1.1 | Editor mode | Standalone -- different concern |
| v0.1.2 | Virtual scrolling | Could defer -- 500 nodes render in <100ms without virtualisation. Only needed at 5000+ |
| v0.1.3 | Multi-select | Could merge with v0.1.0 if selection mode is parameterised from the start |
| v0.1.4 | Drag within tree | Must be standalone -- complex |
| v0.1.5 | Cross-tree drag | Must follow v0.1.4 |
| v0.1.6 | Connectors, sort, filter | Could merge with v0.1.0 (sort/filter are natural parts of the base) |

### What consumers actually need

- **SG/Send browse:** Read-only tree, single select, keyboard nav. Needs: v0.1.0 only.
- **SG/Vault tree view:** Read-only tree, single select, drag-and-drop. Needs: v0.1.0 + v0.1.4.
- **SG/Workspace vault panel:** Read-only tree, single select. Needs: v0.1.0 only.
- **Zip editor (future tool):** Editor mode, drag-and-drop. Needs: v0.1.0 + v0.1.1 + v0.1.4.

None of the three current consumers need virtual scrolling (vault trees are typically <200 nodes), multi-select, or cross-tree drag. These are speculative features.

### Recommendation

Reduce to 4 IFD versions before consolidation:

| Version | Scope |
|---|---|
| v0.1.0 | Core tree + selection + keyboard + sort/filter + connectors (the complete read-only tree) |
| v0.1.1 | Editor mode (rename, delete, create) |
| v0.1.2 | Drag-and-drop (within tree + cross-tree) |
| v0.1.3 | Multi-select + virtual scrolling |
| v0.2.0 | Consolidation |

This gives us a useful component at v0.1.0 that two of three consumers can migrate to immediately. Editor mode and drag are added when needed. Virtual scrolling and multi-select are deferred until there is a real use case with thousands of nodes or multi-selection.

## 6. Questions for the Human

1. **core/ or components/?** sg-tree is a Web Component with Shadow DOM (like everything in `components/`), but it is also foundational infrastructure consumed by three products (like sg-layout in `core/`). Where does it go? My lean: `components/`, with sg-layout being the exception.

2. **How many versions before consumers can use it?** The brief proposes 7 (v0.1.0-v0.1.6) with no consumer migration until v0.2.0. I propose 4 (v0.1.0-v0.1.3) with consumer migration possible at v0.1.0 for read-only use cases (SG/Send, SG/Workspace). Does the faster path to consumer value outweigh the cleaner consolidation?

3. **Complete-file IFD or surgical patches?** Given the `_latest` layering incompatibility, should we confirm Option B (each version is a complete file, following sg-layout's actual pattern)? This is my strong recommendation.

4. **Virtual scrolling priority.** The largest real tree today is SG/Vault, which typically has <200 nodes. Is virtual scrolling (v0.1.2 in the brief) a real requirement, or should it be deferred to when someone actually has a 5000+ node tree?

5. **Cross-tree drag scope.** The brief includes cross-tree drag (v0.1.5) as a pre-consolidation feature. Is there a known use case for dragging nodes between two sg-tree instances? If not, this should be deferred post-v0.2.0.
