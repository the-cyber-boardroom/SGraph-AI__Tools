## The qa.send.sgraph.ai Model

The SG/Send QA pipeline is a 5-stage system:

```
1. Playwright tests → 2. Screenshot capture → 3. Visual diff → 4. Docs generation → 5. Jekyll site deploy
```

Key properties:
- **Playwright** drives headless Chromium against live environments
- **Screenshots** at 1280×720 with full metadata at every workflow step
- **Pixel-diff** via Pillow — changes < 1% threshold filtered as rendering noise
- **Auto-generated docs** — test metadata + screenshots scaffold into Markdown
- **GitHub Actions** orchestrates everything; commits with `[skip ci]`
- **Living documentation** — qa.send.sgraph.ai IS the test report

The result: every feature has visual proof that it works, every regression is caught as a pixel diff, and the documentation writes itself.

## Proposed Architecture: qa.tools.sgraph.ai

### Principle: Same Pipeline, Adapted for tools.sgraph.ai

```
qa.tools.sgraph.ai/
  pages/
    pipeline/                    # How this QA site works
    core/
      sg-image/                  # Unit tests + canvas output screenshots
      sg-video/                  # FFmpeg tests + processing screenshots
      sg-send-crypto/            # Crypto test vectors + derivation verification
    components/
      image-editor/              # Component state screenshots
      image-crop/                # Crop overlay screenshots
      image-redact/              # Redaction mode screenshots
      image-text/                # Text overlay screenshots
      video-splitter/            # Split/Trim/Extract mode screenshots
      send-drop/                 # All 6 states screenshot
    tools/
      image-tools/               # Full E2E workflow screenshots
      video-tools/               # Full E2E workflow screenshots
    cross-browser/               # Chrome vs Firefox vs Safari diffs
  _data/
    test_results.json            # Aggregated pass/fail + timestamps
  assets/
    screenshots/
      current/                   # Latest screenshots
      baseline/                  # Approved baselines
      diffs/                     # Pixel diff images
```

### Three Test Layers

```
Layer 1: Unit Tests (core modules)
  ├── Deterministic: test vectors, known inputs → expected outputs
  ├── Run in Node.js OR browser (canvas polyfill for Node)
  ├── Fast: < 5 seconds total
  └── Screenshot: canvas output comparisons (for sg-image)

Layer 2: Component Tests (Web Components)
  ├── Mount component in isolation with test fixtures
  ├── Simulate user interactions (pointer events, clicks, input)
  ├── Capture screenshot at each meaningful state
  ├── Medium: < 30 seconds per component
  └── Screenshot: every UI state, every tool mode

Layer 3: E2E Tests (tool pages)
  ├── Navigate to tool page
  ├── Complete full user workflow (load file → process → export)
  ├── Capture screenshot at every step
  ├── Slow: < 2 minutes per tool (FFmpeg load dominates video)
  └── Screenshot: full page at every workflow milestone
```

**test-sg-send-crypto.html** — test with known vectors from SG/Send:
```javascript
// Test token pattern
assert(isFriendlyToken('royal-stamp-1234') === true);
assert(isFriendlyToken('not-valid') === false);
assert(isFriendlyToken('UPPER-case-1234') === false);

// Test transfer ID derivation (deterministic — compare with SG/Send)
const id = await deriveTransferId('test-token-1234');
// SHA-256("test-token-1234") → first 12 hex chars — verify against known value
assert(id.length === 12, 'transfer ID length');
assert(/^[0-9a-f]+$/.test(id), 'transfer ID is hex');

// Test idempotency
const id2 = await deriveTransferId('test-token-1234');
assert(id === id2, 'derivation is deterministic');

// Test key derivation produces a CryptoKey
const key = await deriveKey('test-token-1234');
assert(key.algorithm.name === 'AES-GCM', 'key algorithm');
assert(key.algorithm.length === 256, 'key length');

// Test SGMETA envelope structure
const content = new TextEncoder().encode('hello');
const envelope = buildSgmetaEnvelope(content.buffer, 'test.txt');
assert(envelope[0] === 0x53, 'SGMETA magic S');
assert(envelope[1] === 0x47, 'SGMETA magic G');

// Test encrypt produces IV + ciphertext
const encrypted = await encrypt(new Uint8Array([1, 2, 3]), key);
assert(encrypted.length > 12, 'encrypted has IV + ciphertext');

// Test round-trip: encrypt then decrypt
const iv = encrypted.slice(0, 12);
const ciphertext = encrypted.slice(12);
const decrypted = await crypto.subtle.decrypt(
    { name: 'AES-GCM', iv }, key, ciphertext
);
const original = new Uint8Array(decrypted);
assert(original[0] === 1 && original[1] === 2 && original[2] === 3, 'round-trip');
```

### Phase 3: Visual Diff Pipeline (Week 3)

**Screenshot comparison script** (following qa.send.sgraph.ai pattern):

```python
# scripts/qa/compare_screenshots.py

from PIL import Image
import json, os, sys

THRESHOLD = 0.01  # 1% pixel difference threshold

def compare(baseline_path, current_path):
    """Compare two screenshots. Return diff percentage."""
    baseline = Image.open(baseline_path)
    current = Image.open(current_path)

    if baseline.size != current.size:
        return 1.0  # 100% different if sizes don't match

    pixels_b = list(baseline.getdata())
    pixels_c = list(current.getdata())
    diff_count = sum(1 for a, b in zip(pixels_b, pixels_c) if a != b)
    return diff_count / len(pixels_b)

def run_comparison(screenshots_dir, baseline_dir, output_dir):
    """Compare all screenshots against baselines."""
    results = []
    for root, _, files in os.walk(screenshots_dir):
        for f in files:
            if not f.endswith('.png'):
                continue
            current = os.path.join(root, f)
            relative = os.path.relpath(current, screenshots_dir)
            baseline = os.path.join(baseline_dir, relative)

            if not os.path.exists(baseline):
                results.append({ 'file': relative, 'status': 'new', 'diff': 1.0 })
                continue

            diff = compare(baseline, current)
            status = 'pass' if diff < THRESHOLD else 'fail'
            results.append({ 'file': relative, 'status': status, 'diff': round(diff, 4) })

            if status == 'fail':
                # Generate visual diff image
                generate_diff_image(baseline, current,
                    os.path.join(output_dir, 'diffs', relative))

    return results
```

## Adapting to tools.sgraph.ai Constraints

### Constraint: No Build Step

The QA pipeline itself CAN use build tools (Playwright, Python scripts) — these run in CI, not in production. The constraint is that the **code under test** has no build step. This is fine — Playwright tests import nothing from the codebase, they just drive a browser against served files.

### Constraint: No Node.js Test Runners for Production Code

Again, Playwright is a CI tool, not a production dependency. The existing browser-based HTML test pages remain the primary developer-facing tests. Playwright automates what a developer would do manually: open the page, interact, verify.

### Constraint: Vanilla JS Components with Shadow DOM

Shadow DOM makes Playwright selectors slightly harder. Use `page.locator('sg-image-editor').locator('internal:shadow=button.crop')` or pierce the shadow root:

```javascript
// Pierce shadow DOM
const editor = page.locator('sg-image-editor');
const cropBtn = editor.locator('css=* >> css=button[data-tool="crop"]');
```

Or use the `>> shadow=` selector engine that Playwright provides.

### Constraint: FFmpeg WASM Load Time

Video tests will be slow (~30-60 seconds for first FFmpeg load). Mitigate:
- Cache FFmpeg WASM in CI between test runs (GitHub Actions cache)
- Run video tests in a separate job with higher timeout
- Use a tiny test video (10 seconds, minimal codec) to minimize processing time

1. **Create `tests/playwright/` directory** with config + fixtures
2. **Write `test-sg-send-crypto.html`** — pure unit test, no Playwright needed, runs in browser like existing tests
3. **Write `test-sg-image.html`** — canvas output verification, browser-based
4. **Write first Playwright spec**: `send-drop.spec.js` — simplest component, 6 states to screenshot
5. **Add `qa-tools.yml` workflow** — start with unit tests only, add E2E later
6. **Create baseline screenshots** — run once, commit as approved baselines

This gets the pipeline running with minimal effort, then we expand coverage incrementally.
