# Architect Review: Bootstrap Plan vs Implementation

**Version:** v0.1.0
**Date:** 5 Mar 2026
**Author:** Architect (Explorer team)
**Scope:** Compare the human briefs (v0.11.08) against the actual bootstrap implementation

---

## 1. Plan Summary

Two briefs defined the plan:

**Architecture Brief** (`team/humans/dinis_cruz/briefs/v0.11.08__arch-brief__tools-canonical-component-library.md`) established tools.sgraph.ai as the canonical component library for the SGraph ecosystem. Key elements:

- **Dependency inversion** — tools.sgraph.ai becomes the source; send, vault, workspace, and Chrome extension become consumers.
- **Three-tier structure** — `core/` (pure JS, no UI), `components/` (reusable UI), `tools/` (standalone pages composing core + components).
- **Folder-based versioning** — each module independently versioned (`core/crypto/v1.0.0/`), with `latest/` aliases.
- **CDN serving** — S3 + CloudFront, immutable cache headers for pinned versions, 5-minute cache for latest.
- **Per-module CI/CD** — changes to one module do not trigger rebuilds of others.
- **Migration path** — five phases from setup through full ecosystem migration.
- **Planned core modules** — crypto, api-client, i18n, file-detect, markdown-parser, llm-client, video, audio, ssh (9 total).
- **Planned components** — upload-dropzone, file-preview, access-gate, header, footer, tree-view, api-logger, events-viewer, messages-panel, transparency (10 total).
- **Planned tools** — video-splitter, ssh-keygen, llm-client, audio-transcription, file-hasher (5 total).

**Dev Brief** (`team/humans/dinis_cruz/briefs/v0.11.08__dev-brief__tools-briefing-pack.md`) specified the session bootstrap system:

- A `BRIEF_PACK.md` with 10 defined sections to bootstrap any new session from zero.
- Module registry table tracking all modules with versions, exports, and status.
- Architecture decisions table with source references.
- Deployment instructions (local dev, module versioning, cache headers).
- First task definition with clear steps and definition of done.

## 4. Gaps

### Critical Gaps

1. **No deployment infrastructure.** The entire CDN-serving model (S3, CloudFront, cache headers, CORS) is absent. This is the core value proposition of the architecture brief: other projects importing from tools.sgraph.ai via URL. Until deployment exists, the dependency inversion is theoretical only.

2. **No `latest/` aliases.** The brief specifies `latest/` folders (or S3 redirects) for each module. None exist. This affects the consumption model for tools on tools.sgraph.ai itself, which are supposed to use `latest`.

3. **No CI/CD.** No GitHub Actions workflows, no per-module pipelines. The brief specifies independent IFD per module.

### Significant Gaps

4. **7 of 9 planned core modules missing.** api-client, i18n, file-detect, markdown-parser, llm-client, video, and audio do not exist. Of these, api-client and llm-client are the highest priority for the ecosystem (Chrome extension and workspace both need them).

5. **8 of 10 planned components missing.** upload-dropzone, file-preview, access-gate, tree-view, api-logger, events-viewer, messages-panel, transparency. These are needed for the migration of send and vault.

6. **3 of 5 planned tools missing.** video-splitter, llm-client, audio-transcription. The video splitter had its own dedicated brief.

7. **No migration started.** Phase 3 of the migration (send.sgraph.ai imports from tools.sgraph.ai) has not begun. No cross-project import has been tested.

### Minor Gaps

8. **Components lack separate CSS files.** The architecture brief shows each component having both a `.js` and `.css` file (e.g., `header.js` + `header.css`). The implemented header and footer use inline `<style>` within the component. This works but limits external CSS override (theming per-project), which the brief explicitly calls out as a feature.

9. **Landing page does not use shared components.** `tools/index.html` has its own inline header/footer rather than using `sg-header` and `sg-footer`. The ssh-keygen tool correctly uses both components, but the landing page does not follow the same pattern.

10. **File naming inconsistency with brief.** The architecture brief uses `crypto.js`, `header.js`, etc. The implementation uses `sg-crypto.js`, `sg-header.js`, etc. The `sg-` prefix is mentioned in the dev brief and CLAUDE.md conventions, so the implementation is arguably more consistent, but it diverges from the architecture brief's examples and import paths.

## 5. Architectural Observations

### 5.1 Module API Design

**sg-crypto.js** is well-structured. The API surface is clean: key generation, import/export, encrypt/decrypt, plus base64url utilities. The `isAvailable()` and `requireSecureContext()` guards are good defensive patterns. One concern: `importKey()` restricts the imported key to `['decrypt']` only, which means a round-tripped key (generate -> export -> import) cannot be used for encryption. This is intentional for the send.sgraph.ai use case (recipient only decrypts) but limits reuse. A future version may need an `importKey()` variant that allows both operations, or an options parameter.

**sg-ssh.js** exports only one function (`generateSSHKeyPair`), which is appropriate for its scope. The internal helpers (`formatSSHPublicKey`, `formatSSHPrivateKey`, `uint32BE`, `concatBuffers`, `arrayBufferToBase64`) are correctly kept as non-exported functions. The module handles the full OpenSSH format correctly, including the private key padding and check integers.

### 5.2 Component Design

Both `SgHeader` and `SgFooter` use Web Components (`extends HTMLElement`) with `customElements.define()`. This is a reasonable choice, but there are concerns:

- **No Shadow DOM.** Both components inject styles and HTML via `innerHTML` in `connectedCallback`. Without Shadow DOM, the styles leak into and are affected by the host page. The BEM-style class names (`sg-header__brand`, `sg-footer__link`) mitigate collision risk, but do not eliminate it.

- **No attribute change handling.** `SgHeader` reads `tool-name` in `connectedCallback` but does not implement `observedAttributes` or `attributeChangedCallback`. If the attribute is set after the element is connected, the header will not update. This is unlikely to matter for static pages but violates Web Component best practices.

- **Inline styles prevent theming.** The architecture brief states: "Components are themeable -- the consuming project can override the CSS to match its own look." With styles embedded in the component's `innerHTML`, the consuming project cannot easily override them without `!important` or knowing the exact selectors. Separating styles into external CSS files (as the brief specifies) would make theming straightforward.

### 5.3 Composition Pattern

The SSH keygen tool (`tools/ssh-keygen/index.html`) demonstrates the intended composition pattern well:

```
sg-header (component) + sg-ssh.js (core) + sg-footer (component) + tool-specific UI
```

The tool imports `generateSSHKeyPair` from the core module and uses the header/footer components via script tags. The tool-specific code is approximately 80 lines of wiring logic. This validates the brief's assertion that tools should be composable with minimal tool-specific code.

However, the tool uses absolute paths (`/core/ssh/v1.0.0/sg-ssh.js`, `/components/header/v1.0.0/sg-header.js`). This works when served from the root of tools.sgraph.ai but will not work if the repo is served from a subdirectory. For local development, this requires serving from the repo root.

### 5.4 Versioning Structure

The folder-based versioning (`core/crypto/v1.0.0/`) is in place but untested. No module has been published at more than one version, so the versioning workflow (creating v1.1.0 alongside v1.0.0, updating latest) has not been exercised. The immutability contract (content at a pinned version URL never changes) is stated but not enforced by any mechanism.

### 5.5 Dependency Direction

The fundamental dependency inversion (tools as source, everything else as consumer) is architecturally sound and the code does not violate it. No core module imports from components or tools. No component imports from tools. The dependency graph is strictly:

```
tools -> components -> core
```

This is correct.

## 6. Recommendations

### Immediate (Next Session)

1. **Deploy to S3 + CloudFront.** This is the single highest-priority gap. The architecture's value is in cross-project imports, which require deployment. At minimum:
   - Create S3 bucket for tools.sgraph.ai
   - Set up CloudFront distribution
   - Configure cache headers (immutable for versioned paths, 5-min for latest)
   - Verify a cross-origin import works from another *.sgraph.ai domain

2. **Create `latest/` aliases.** For each existing module, create the `latest/` folder containing a copy of the current version. This enables tools to use the `latest` path as specified in the brief.

3. **Separate component CSS.** Extract the inline styles from `sg-header.js` and `sg-footer.js` into `sg-header.css` and `sg-footer.css` respectively. This matches the brief's specified structure and enables the theming model.

4. **Make landing page use shared components.** `tools/index.html` should import `sg-header` and `sg-footer` instead of having its own inline header/footer. This is a simple change that validates the composition model at the directory level.

### Short-Term (Next 2-3 Sessions)

5. **Build the Video Splitter.** This has its own dedicated brief and is the flagship demo tool. It requires `sg-video.js` (FFmpeg WASM wrapper) in core, plus the upload-dropzone component. Building it will exercise the full composition pattern with a non-trivial core module.

6. **Extract sg-api-client.js.** This is the most broadly needed core module (used by send, vault, workspace, and Chrome extension). Extract it from the send repo as the second migrated module.

7. **Set up CI/CD.** Create GitHub Actions workflows with per-module path triggers. Even a minimal pipeline (lint + deploy to S3) validates the independent-module CI/CD model.

8. **Add `importKey()` encrypt capability.** Either add an `operations` parameter to `importKey()` or create a separate `importKeyForEncryption()` function. The current decrypt-only restriction will be a problem when other consumers need round-trip crypto.

### Medium-Term

9. **Begin send.sgraph.ai migration.** Once crypto and api-client are deployed and importable, update send.sgraph.ai to import from tools.sgraph.ai (pinned versions). This is the proof that the dependency inversion works in production.

10. **Extract upload-dropzone from vault.** This is the most reusable component from vault and validates the component migration path.

---

## Summary

The bootstrap implementation establishes the correct architectural foundation: three-tier structure, ES module conventions, folder-based versioning, and the composition pattern. The code quality is solid -- modules follow conventions, APIs are clean, and JSDoc is present throughout.

The primary gap is infrastructure: no deployment, no CDN, no CI/CD, no latest aliases. The architecture's value proposition depends entirely on cross-project imports via CDN URLs, and none of that infrastructure exists yet. The code is correct but unreachable by consumers.

Secondary gaps are breadth (2 of 9 core modules, 2 of 10 components, 1 of 5 tools) and the component theming model (inline styles rather than external CSS).

The implementation is a valid Phase 1 skeleton. Deployment infrastructure should be the immediate priority to unlock Phase 2 (tools importing from CDN) and Phase 3 (send.sgraph.ai migration).
