# Architect Review — Tool Manifest Specification

**Version:** v0.20.38
**Date:** 8 Apr 2026
**Author:** Architect (Explorer team)
**Status:** PROPOSED — does not exist yet

---

## 1. Problem

Every tool is an HTML page with hardcoded import paths. There is no structured metadata about what a tool depends on, what version it is, or what category it belongs to. This causes three problems:

1. **The landing page is hand-maintained HTML.** Adding a tool means editing `index.html` and copying card markup. 24 tools x 8 lines of HTML = fragile.
2. **No dependency visibility.** You cannot answer "which tools use sg-llm-request v0.1.2?" without grepping HTML files.
3. **No machine-readable tool catalogue.** External consumers (Chrome extension, workspace) cannot discover tools programmatically.

---

## 2. manifest.json Schema

Each tool gets a `manifest.json` in its folder (e.g. `tools/v0/v0.1/v0.1.22/en-gb/chat/manifest.json`).

### 2.1 Full Schema

```jsonc
{
  // ── Identity ──────────────────────────────────────────────────
  "name":        "Chat",                          // Display name (required)
  "slug":        "chat",                          // URL slug, matches folder name (required)
  "description": "Multi-turn chat with any LLM.", // One-liner for cards (required)
  "icon":        "💬",                             // Single emoji for card/nav (required)

  // ── Classification ────────────────────────────────────────────
  "version":  "0.1.22",          // Tool version — matches IFD folder (required)
  "status":   "live",            // "live" | "experimental" | "dev" | "new" (required)
  "category": "llm",             // "utilities" | "llm" | "vault-vfs" | "dev" (required)

  // ── Search ────────────────────────────────────────────────────
  "keywords": ["conversation", "history", "attachments", "images", "files"],

  // ── Dependencies ──────────────────────────────────────────────
  "dependencies": {
    "core": [
      { "module": "sg-layout",      "path": "/core/sg-layout/v0.1.0/sg-layout.js" }
    ],
    "components": [
      { "module": "sg-llm-events",        "path": "/components/llm/sg-llm-events/v0/v0.1/v0.1.0/sg-llm-events.js" },
      { "module": "sg-llm-request",       "path": "/components/llm/sg-llm-request/v0/v0.1/v0.1.3/sg-llm-request.js" },
      { "module": "sg-llm-chat-history",  "path": "/components/llm/sg-llm-chat-history/v0/v0.1/v0.1.10/sg-llm-chat-history.js" }
    ],
    "shared": [
      { "module": "sg-site-header", "path": "/components/site-header/v1/v1.0/v1.0.2/sg-site-header.js" },
      { "module": "tools.css",      "path": "/_common/css/tools.css" }
    ],
    "external": []
  }
}
```

### 2.2 Field Reference

| Field | Type | Required | Notes |
|-------|------|----------|-------|
| `name` | string | yes | Human-readable display name |
| `slug` | string | yes | Must match folder name. Used for URL construction |
| `description` | string | yes | Max 160 chars. Used in tool cards and meta tags |
| `icon` | string | yes | Single emoji. Rendered in cards and nav |
| `version` | string | yes | Semver without `v` prefix. Matches IFD folder |
| `status` | enum | yes | `live`, `experimental`, `dev`, `new` |
| `category` | enum | yes | `utilities`, `llm`, `vault-vfs`, `dev` |
| `keywords` | string[] | no | Extra search terms beyond name/description |
| `dependencies.core` | array | no | Core modules (`/core/...`) |
| `dependencies.components` | array | no | UI components (`/components/...`) |
| `dependencies.shared` | array | no | Shared resources (`/_common/...`, site header/footer) |
| `dependencies.external` | array | no | CDN resources (e.g. FFmpeg WASM, Pyodide) |

Each dependency entry has:
- `module` (string, required) — human-readable identifier
- `path` (string, required) — absolute path from site root, or full URL for external
- `version` (string, optional) — extracted semver, useful for external deps

### 2.3 Design Decisions

**Why not `package.json`?** This is not npm. The schema is purpose-built for static HTML tools with folder-based versioning and no build step.

**Why absolute paths in dependencies?** The import paths in HTML are already absolute. Storing them verbatim means zero transformation and easy diffing against actual imports.

**Why a flat dependency list, not a tree?** Tools import modules directly. There is no transitive resolution. The manifest records what the HTML file actually imports, nothing more.

**Why `slug` when the folder name exists?** The manifest must be self-describing. When the landing page fetches 24 manifests, it needs the slug to build hrefs without parsing file paths.

## 3. IFD Compatibility

The manifest participates in IFD layering like any other file.

### Rules

1. **Each delta folder MAY contain a manifest.json.** If present, it completely replaces the previous version (JSON is not deep-merged).
2. **`build_ifd_latest.py` treats it like any file.** No special handling needed — the last writer wins.
3. **The `version` field MUST match the IFD folder.** If `v0.1.24/en-gb/infographic-gen/manifest.json` exists, its `version` field must be `"0.1.24"`.

### Example IFD layering

```
v0.1.6/en-gb/infographic-gen/manifest.json   ← base (first version of this tool)
v0.1.12/en-gb/infographic-gen/manifest.json  ← override (new deps added)
v0.1.24/en-gb/infographic-gen/manifest.json  ← override (generation timing fix)
```

After `build_ifd_latest.py --up-to v0.1.24`, the `_latest/en-gb/infographic-gen/manifest.json` will be the v0.1.24 version.

## 4. Landing Page Integration

The landing page (`en-gb/index.html`) currently has 24 hardcoded tool cards across 4 sections. The manifest enables a data-driven approach.

### 4.1 Tool Registry

A new file `_common/js/sg-tool-registry.js` fetches and caches all manifests:

```js
/**
 * Fetch all tool manifests from a known list of slugs.
 * @param {string} basePath - locale-relative base (e.g. '')
 * @param {string[]} slugs - tool folder names
 * @returns {Promise<Object[]>} array of parsed manifests
 */
export async function loadManifests(basePath, slugs) {
    const results = await Promise.allSettled(
        slugs.map(slug =>
            fetch(`${basePath}${slug}/manifest.json`)
                .then(r => r.ok ? r.json() : null)
        )
    );
    return results
        .filter(r => r.status === 'fulfilled' && r.value)
        .map(r => r.value);
}

/**
 * Group manifests by category, preserving display order.
 * @param {Object[]} manifests
 * @returns {Map<string, Object[]>}
 */
export function groupByCategory(manifests) {
    const order = ['utilities', 'llm', 'vault-vfs', 'dev'];
    const groups = new Map(order.map(c => [c, []]));
    for (const m of manifests) {
        const bucket = groups.get(m.category) || groups.get('dev');
        bucket.push(m);
    }
    return groups;
}
```

### 4.2 Rendering

The landing page replaces hardcoded cards with a fetch-and-render loop:

```js
import { loadManifests, groupByCategory } from '../_common/js/sg-tool-registry.js';

const SLUGS = [
    'ssh-keygen', 'file-hasher', 'file-encryptor', 'key-generator',
    'vault-browser', 'image-tools', 'video-tools', 'pyodide-repl',
    'vault-pyodide', 'sg-send-cli',
    'chat', 'one-shot-chat', 'infographic-gen', 'llm-dev',
    'multi-agent-chat', 'openrouter', 'agentic', 'model-compatibility',
    'vault', 'vfs-dev', 'vfs-tree-demo', 'send-sim',
    'folder-editor', 'sg-tree-demo'
];

const manifests = await loadManifests('', SLUGS);
const groups = groupByCategory(manifests);

// Render each group into the existing section-group containers
for (const [category, tools] of groups) {
    const grid = document.querySelector(`#group-${category} .tools-grid`);
    if (!grid) continue;
    grid.innerHTML = '';
    for (const t of tools) {
        grid.innerHTML += `
            <a href="${t.slug}/" class="tool-card"
               data-search="${(t.keywords || []).join(' ')}">
                <div class="card-top">
                    <span class="tool-card__icon">${t.icon}</span>
                    <span class="tool-card__title">${t.name}</span>
                </div>
                <p class="tool-card__desc">${t.description}</p>
                <div class="card-footer">
                    <span class="tool-card__status status--${t.status}">${t.status}</span>
                </div>
            </a>`;
    }
}
```

### 4.3 Fallback Strategy

The SLUGS array is still hardcoded, but that is intentional. A slug list is 24 strings (stable, rarely changes). The card content, descriptions, statuses, and deps come from manifests. If a manifest fetch fails, that tool is simply omitted from the grid — no broken card.

Future: the SLUGS array itself could become a `tools-index.json` at the tools root, but that is a Phase 2 concern.

## 5. sg-tool-manifest Web Component

A shared web component that any tool can embed to show an info panel (dependency list, version, status).

### 5.1 API

```html
<!-- In any tool's index.html -->
<script type="module" src="/_common/js/sg-tool-manifest.js"></script>
<sg-tool-manifest src="manifest.json"></sg-tool-manifest>
```

### 5.2 Behaviour

1. Fetches the JSON from the `src` attribute (relative to current page).
2. Renders a collapsible panel showing: name, version, status badge, category, description, and a dependency table.
3. Shadow DOM — no style leakage.
4. Graceful degradation — if fetch fails, the element stays empty (no layout shift).

### 5.3 Rendered Output (sketch)

```
┌─────────────────────────────────────────────┐
│  💬 Chat  v0.1.22  [Live]                   │
│  Multi-turn chat with any LLM.              │
│                                              │
│  ▸ Dependencies (14)                         │
│    Core: sg-layout v0.1.0                    │
│    Components: sg-llm-events v0.1.0,         │
│      sg-llm-request v0.1.3, ...             │
│    Shared: sg-site-header v1.0.2, tools.css │
└─────────────────────────────────────────────┘
```

### 5.4 File Location

`sgraph_ai_tools__static/tools/v0/v0.1/{version}/_common/js/sg-tool-manifest.js`

This follows the existing `_common/js/` pattern alongside `sg-nav.js`.

## 7. Migration Plan

### Phase 1 — Seed manifests (1 session)

1. Write a script (`scripts/generate_manifests.py`) that parses each tool's `index.html`, extracts `<script src>` and `import` paths, and generates a draft `manifest.json`.
2. Manually review and fill in `name`, `description`, `icon`, `status`, `category`, `keywords` from the existing landing page HTML.
3. Commit manifests alongside existing tools. No behaviour change.

### Phase 2 — Landing page reads manifests (1 session)

1. Create `_common/js/sg-tool-registry.js` with `loadManifests()` and `groupByCategory()`.
2. Refactor `en-gb/index.html` to fetch manifests and render cards dynamically.
3. Keep the static HTML as a `<noscript>` fallback or remove it once verified.
4. Update the IFD build to include manifests in `_latest/`.

### Phase 3 — sg-tool-manifest component (1 session)

1. Build `_common/js/sg-tool-manifest.js` web component.
2. Add `<sg-tool-manifest src="manifest.json">` to 2-3 pilot tools (chat, infographic-gen, ssh-keygen).
3. Roll out to remaining tools.

### Phase 4 — DevOps integration (ongoing)

1. CI script that validates every `manifest.json` against the schema.
2. CI script that checks `dependencies.*.path` entries resolve to actual files.
3. Dependency matrix report: which tools use which module versions.

### Adoption is incremental

- Tools without a `manifest.json` continue to work unchanged. The landing page falls back to the SLUGS list (no manifest = no card, but the tool itself is unaffected).
- A tool can add a manifest in any IFD delta. It does not need to wait for all tools to adopt.
- The `sg-tool-manifest` component is optional per-tool. It renders nothing if the fetch fails.

## 8. Open Questions

1. **Should `tools-index.json` replace the SLUGS array?** A single JSON file at the tools root listing all slugs would make the landing page fully data-driven. Trade-off: one more file to maintain vs. removing the last hardcoded list.

2. **Locale-specific manifests?** Current tools share the same manifest across locales. If `name`/`description` need translation, manifest would need a `locale` field or per-locale files. Not needed for v1.

3. **Should the component web component also render a "back to all tools" link?** This could replace the `sg-nav.js` "All Tools" entry for tools that embed the manifest panel.
