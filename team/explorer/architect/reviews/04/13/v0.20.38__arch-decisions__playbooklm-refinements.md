## Decision A — Manifest-Driven Dependency Loading

### The Proposal

`index.html` becomes a near-static shell. A `manifest-loader.js` reads `manifest.json` at runtime and dynamically imports JS modules and injects CSS files. IFD version bumps update `manifest.json` (and their delta files) — `index.html` does not change.

### Technical Analysis

**How it works with ES modules:**

Dynamic `import()` is a first-class ES module feature. `import('/path/to/module.js')` returns a Promise and works from any async context, including inside a loaded script. CSS cannot be `import()`-ed directly by the browser unless the module system supports it (Chrome supports `import ... assert { type: 'css' }` experimentally but it is not broadly deployed). The safe approach is `document.createElement('link')` for CSS, `import()` for JS modules.

**Loading order:**

CSS has no side-effect ordering problem — all sheets can be injected in parallel. JS modules have ordering constraints in two cases: (1) a module uses a custom element defined by a prior module, and (2) `sg-layout` must be present before any panel building code runs. The manifest must encode the ordering constraint explicitly. Use a `"phase"` field: `1 = core/layout`, `2 = components (custom elements)`, `3 = tool JS`. The loader runs each phase as a `Promise.all()` batch, sequencing phases with `await`.

**Manifest `dependencies` extension:**

Add a `"loader"` sub-key alongside the existing `"core"`, `"components"`, `"shared"` groups. The loader reads `dependencies.loader` exclusively; the existing groups remain as static documentation for `sg-tool-api-manifest` and the landing page. This avoids breaking any existing consumer.

```jsonc
"dependencies": {
    "core": [ ... ],           // static documentation — unchanged
    "components": [ ... ],     // static documentation — unchanged
    "shared": [ ... ],         // static documentation — unchanged
    "loader": [                // NEW — read by manifest-loader.js at runtime
        { "type": "css", "path": "/core/sg-layout/v0.1.0/sg-layout.css",  "phase": 1 },
        { "type": "css", "path": "./styles/playbooklm.css",                 "phase": 1 },
        { "type": "css", "path": "./styles/pipeline.css",                   "phase": 1 },
        { "type": "js",  "path": "/core/sg-layout/v0.1.0/sg-layout.js",    "phase": 1 },
        { "type": "js",  "path": "/core/sg-tool-api/v0/v0.1/v0.1.0/sg-tool-api.js", "phase": 1 },
        { "type": "js",  "path": "/components/site-header/...",             "phase": 2 },
        { "type": "js",  "path": "/components/llm/sg-llm-request/...",      "phase": 2 },
        { "type": "js",  "path": "./api/pipeline-state.js",                 "phase": 3 },
        { "type": "js",  "path": "./api/pipeline-api.js",                   "phase": 3, "entry": true }
    ]
}
```

The `"entry": true` flag marks the module the loader should treat as the tool's main entry point — its default export (or named `init` export) is called once all phases are complete.

**IFD update flow:**

A new IFD version (e.g. v0.1.40) ships only:
- `manifest.json` (updated `loader` array with new paths where files changed)
- The changed delta files (e.g. `api/pipeline-api.js` if the API changed)

`index.html` is identical across all IFD versions. The shell has zero tool-specific knowledge. This is the strongest possible IFD separation.

**Interaction with `sg-tool-api`, `sg-layout`, and external CDN deps:**

`sg-tool-api` and `sg-layout` are phase-1 imports — they arrive before any component or tool JS. This is correct because custom elements registered in phase 2 may need `sg-layout` during their `connectedCallback`. External CDN deps (e.g. `jsPDF`) that do not use ES module syntax must be loaded as phase-1 non-module `<script>` tags injected by the loader. Add `"module": false` to the loader entry to signal this:

```jsonc
{ "type": "js", "path": "https://unpkg.com/jspdf@...", "phase": 1, "module": false }
```

The loader creates a `<script src="...">` element and awaits its `load` event before proceeding.

**Should this become `core/manifest-loader/`?**

**Yes.** The loader has zero tool-specific logic — it reads a manifest, resolves phases, injects CSS, and calls `import()`. It belongs in `core/manifest-loader/v0/v0.1/v0.1.0/manifest-loader.js`. Every future tool that wants a static HTML shell can use it. The loader itself is the only JS reference in `index.html`.

### Decision

**APPROVED — implement manifest-driven loading for PlaybookLM as the first tool to use it.**

1. Create `core/manifest-loader/v0/v0.1/v0.1.0/manifest-loader.js` — a new core module.
2. `index.html` loads only the manifest loader via a single `<script type="module">` tag, passing the manifest URL as a `data-manifest` attribute on the script tag or as a hard-coded relative path.
3. Add a `"loader"` array to the PlaybookLM `manifest.json` with the phase-grouped dependency list.
4. Phase ordering: `1 = CSS + core JS + non-module externals`, `2 = components (custom elements)`, `3 = tool-specific JS modules`.
5. The entry module (`"entry": true`) is dynamically imported last; its exported `init()` function is called with a context object (the manifest data + any element refs the shell exposes).
6. The existing `"core"`, `"components"`, `"shared"` groups in `dependencies` remain unchanged — they are documentation consumed by `sg-tool-api-manifest`, not by the loader.
7. `sg-tool-api` v0.1.0 requires **no changes** for this pattern.

### Constraints

- The loader must handle fetch failures gracefully: if `manifest.json` fetch fails, render an error message in the shell body.
- Relative paths in the loader array are resolved relative to `manifest.json`'s location (the tool directory), not the loader module's location. The shell must pass the base URL.
- The loader is a progressive enhancement. Existing tools (`infographic-gen`) do not need to be migrated — they continue with static `<script>` imports in `index.html`.

## Decision B — Folder Structure

### Design

The original brief proposed a flat layout (all JS at the tool root). The human has requested logical subfolders. The following structure is the Architect's decision for `tools/v0/v0.1/v0.1.39/en-gb/playbooklm/`:

```
tools/v0/v0.1/v0.1.39/en-gb/playbooklm/
│
├── index.html                      ← Static shell: loads manifest-loader only
├── manifest.json                   ← Identity + dependencies (static) + loader (runtime)
│
├── api/                            ← JS API layer (pure logic, no DOM)
│   ├── pipeline-state.js           ← PipelineState object, getters/setters, serialisation
│   ├── pipeline-steps.js           ← Step execution logic (step2, step3, step4, step5 fns)
│   ├── pipeline-api.js             ← SgToolApi registration + activate(); calls init(api, state)
│   └── pipeline-events.js          ← SGA_PLAYBOOK event name constants (tool:slide:complete etc)
│
├── ui/                             ← UI panel builders (DOM construction + event wiring)
│   ├── ui-shell.js                 ← Top-level layout construction (sg-layout setup, dev panel)
│   ├── ui-sources.js               ← Step 1 panel: upload, role assignment, source list
│   ├── ui-presentation.js          ← Step 2 panel: generate button, editable markdown view
│   ├── ui-briefs.js                ← Step 3 panel: brief cards, add/edit/remove
│   ├── ui-generation.js            ← Step 4 panel: per-slide generate controls + image display
│   └── ui-export.js                ← Step 5 panel: PDF, source pack, vault export controls
│
├── styles/                         ← CSS files, one per concern
│   ├── playbooklm.css              ← Tool-level layout variables and overrides
│   ├── pipeline.css                ← Pipeline step cards, status badges, progress indicators
│   ├── slide-grid.css              ← Slide thumbnail grid and result tabs
│   └── export.css                  ← Export panel styling
│
└── skills/                         ← SKILL instruction files
    ├── SKILL-human.md              ← User guide
    ├── SKILL-browser.md            ← Playwright automation guide
    └── SKILL-api.md                ← JS API capability spec
```

### Rationale for Each Folder

**`api/`** — The JS API layer must be separable from the UI. This is the "JS-API first" requirement's structural enforcement. All business logic, state, and SgToolApi registration live here. The UI modules import from `api/` but never vice versa. A headless test (Playwright) that never touches the DOM should be able to drive the tool entirely via `window.__tool`, whose implementation lives in `api/`.

`pipeline-state.js` owns only state shape and accessors. `pipeline-steps.js` owns the LLM call logic for each step. `pipeline-api.js` is the glue: it imports both, creates the `SgToolApi` instance, calls `register()` for each method, and calls `activate()`. It is the entry module (`"entry": true` in the loader manifest).

`pipeline-events.js` is a constants file analogous to `sg-tool-api-events.js`. It exports string constants for all PlaybookLM-specific window events so that consumers can import the constants rather than hardcoding strings.

**`ui/`** — Each panel builder is a function module. It takes DOM element references and the `api` object and returns an object of refs (elements, getters) that the next builder may need. No UI module holds state independently — all state lives in `pipeline-state.js`.

**`styles/`** — CSS is extracted per concern. `playbooklm.css` is the root file (CSS custom properties, body-level layout). `pipeline.css` owns the step card chrome. `slide-grid.css` owns the right-panel result display. `export.css` owns the export panel. This allows IFD delta updates to ship only the CSS file(s) that changed.

**`skills/`** — Moved to a dedicated subfolder. The manifest references these with relative paths: `./skills/SKILL-human.md`. The `SgToolApi` constructor receives `skills: { human: './skills/SKILL-human.md', ... }`. This is a cosmetic change only — no functional impact.

**`index.html` and `manifest.json` stay at root.** The index.html URL is the tool's address. Moving it would break the URL. manifest.json stays beside index.html because `SgToolApi` receives `manifest: './manifest.json'` which resolves relative to the page.

### IFD Delta Compatibility

Each subfolder's files are independent artefacts. A new IFD version that only changes `api/pipeline-steps.js` ships exactly that one file plus an updated `manifest.json`. The loader array in `manifest.json` points to the new path for the changed file; unchanged files continue pointing to the prior version's path (cross-version path reference). This is the existing IFD pattern and it works cleanly with subfolders.

## Decision C — JS-API First Architectural Implications

### What "JS-API First" Means

The JS API (`window.__tool`) must be fully operational before any UI panel renders its first pixel. A Playwright script that calls `window.__tool.connect({ apiKey })` immediately after `DOMContentLoaded` (or after `tool:ready` fires) must be able to drive the entire pipeline without touching the DOM.

This has two concrete implications:

**1. Registration order in `pipeline-api.js`:**

```
1. Import pipeline-state.js (synchronous — creates state object)
2. Import pipeline-steps.js (synchronous — loads step functions)
3. Create SgToolApi instance (synchronous)
4. Call api.register() for every method (synchronous)
5. Call api.activate() ← window.__tool is now set, tool:ready fires
6. Call init(api, state) to build the UI (async — DOM construction)
```

`activate()` is called **before** `init()`. The UI is a consumer of the already-live API. This is the inversion the human is asking for. The current `infographic-gen.js` does this correctly (the SgToolApi block is at the bottom, after all imports and DOM refs are wired). For PlaybookLM, we must enforce this explicitly by separating `api/pipeline-api.js` (which owns `activate()`) from `ui/ui-shell.js` (which owns DOM construction).

The manifest loader calls `pipeline-api.js`'s `init(context)` export as its final step. Inside `init`, the sequence is: (1) call `api.activate()`, (2) then build the UI. The loader waits for all phase-1 and phase-2 imports to resolve before calling `init`, so all custom elements are already defined when the UI builders run.

**2. `sg-tool-manifest` footer and the API contract exposure:**

`sg-tool-manifest` (the collapsible footer bar at `tools/v0/v0.1/v0.1.26/_common/js/sg-tool-manifest.js`) renders dependency information from `manifest.json`. It does not render the API schema. That is the job of `sg-tool-api-manifest` (the component at `components/tool-api/sg-tool-api-manifest/`), which is the "Manifest" tab in the dev panel.

For PlaybookLM, the bottom section contains three dev panel tabs (Explorer / Console / Manifest) wired via `sg-tool-api-explorer`, `sg-tool-api-console`, and `sg-tool-api-manifest`. The `sg-tool-api-manifest` component auto-binds to `window.__tool` via the `tool:ready` event and renders:
- **Identity tab:** name, slug, version, status, dependencies from `manifest.json`
- **API tab:** all registered methods with their param/return schemas from `manifest.json`'s `api.actions` section
- **Skills tab:** rendered SKILL file contents (human / browser / api guides)

This is already shipped in `infographic-gen` v0.1.33+. No changes to `sg-tool-api-manifest` are required.

**What changes (if any) to `sg-tool-api` v0.1.0?**

No breaking changes are needed. `sg-tool-api` v0.1.0 already supports the JS-API-first pattern — `register()` is called before `activate()`, and `activate()` fires `tool:ready` synchronously. The only addition that would improve PlaybookLM's headless use is an explicit `panelId: 'root'` in the constructor call, since PlaybookLM will not be mounted inside an sg-layout panel (it is the top-level tool). Passing `panelId: 'root'` explicitly is already supported; this is a usage pattern, not a code change.

**One optional enhancement:** `SgToolApi` could expose a `whenReady()` Promise (resolves when `activate()` has been called) so that consumers waiting for the API can do `await window.__tool?.whenReady()` without listening to the DOM event. This is a non-breaking addition to v0.1.0 that the Dev role can implement. If not shipped for PlaybookLM MVP, `tool:ready` window event is sufficient.

### Summary

| Question | Answer |
|---|---|
| Must `window.__tool` be usable before UI renders? | Yes. `activate()` is called in `pipeline-api.js` before `init()` hands off to `ui-shell.js`. |
| How does `sg-tool-manifest` expose the API? | It doesn't — it shows dependency metadata. `sg-tool-api-manifest` (dev panel) exposes the API contract. |
| What changes to `sg-tool-api` v0.1.0? | None required. Optional: add `whenReady()` Promise helper. |
| Registration order? | `pipeline-state.js` → `pipeline-steps.js` → `SgToolApi constructor` → `register()` × N → `activate()` → `ui-shell.js init()` |

## Decision D — Default Model (Gemini 3.1)

### Source Evidence

From `components/infographic/sg-infographic-model-picker/v0/v0.1/v0.1.0/sg-infographic-model-picker.js`, the model list as of the current codebase:

```
google/gemini-3.1-flash-image-preview   ← DEFAULT (TOP_3_MODELS[0])
google/gemini-2.5-flash-image
google/gemini-3-pro-image-preview
google/gemini-2.0-flash-001
openai/gpt-5-image-mini
...
```

The existing codebase already uses `google/gemini-3.1-flash-image-preview` as the `DEFAULT_MODEL` in `sg-infographic-model-picker`. This is the top-recommended model and is pre-selected in infographic-gen.

The human asked for "gemini 3.1 as default." There is no `google/gemini-3.1-flash` (text-only) model ID in the existing codebase. The model IDs are:

| Task | Model ID | Notes |
|------|----------|-------|
| Steps 2–3 (text: extract essence, decompose to briefs) | `google/gemini-2.5-flash-preview` | Preferred text model — not yet in model picker but a valid OpenRouter ID pattern. Alternative: use the same flash-image model in text-only mode. |
| Step 4 (image generation per slide) | `google/gemini-3.1-flash-image-preview` | Confirmed in codebase. Top recommended. ~$0.10/img. |

**Gemini 3.1 naming clarification:**

"Gemini 3.1" in the human's request maps to the image-generation variant `google/gemini-3.1-flash-image-preview` that is already the default in the infographic picker. There is no separate `google/gemini-3.1-flash` text-only model ID confirmed in this codebase. The most plausible text model for "gemini 3.1" would be `google/gemini-2.5-flash-preview` (the text-only counterpart to the flash family at this capability tier), but this should be validated against the OpenRouter model catalogue before using it.

**Pragmatic recommendation for PlaybookLM:**

- **Steps 2 and 3 (text LLM):** Default to `google/gemini-2.5-flash-preview`. This is a capable text model in the same family. Make it configurable — `generatePresentation({ model? })` and `generateSlideBriefs({ model? })` both accept a model override.
- **Step 4 (image generation):** Default to `google/gemini-3.1-flash-image-preview`. This matches the existing infographic-gen default and the human's stated preference.
- **Model storage in PipelineState:** Store separate `textModel` and `imageModel` fields to support per-step overrides cleanly.

### Decision

```javascript
// PipelineState defaults
const DEFAULT_TEXT_MODEL  = 'google/gemini-2.5-flash-preview';
const DEFAULT_IMAGE_MODEL = 'google/gemini-3.1-flash-image-preview';
```

The PlaybookLM `manifest.json` records both defaults:

```jsonc
"api": {
    "defaults": {
        "textModel":  "google/gemini-2.5-flash-preview",
        "imageModel": "google/gemini-3.1-flash-image-preview"
    }
}
```

The `connect()` API method accepts `{ apiKey, textModel?, imageModel? }` to allow overriding both at connection time.

**IMPORTANT — Validate before development:** The Dev role must confirm `google/gemini-2.5-flash-preview` is a live OpenRouter model ID before the first code commit. If unavailable, fall back to `google/gemini-2.0-flash-thinking-exp` (the model the human mentioned) or `anthropic/claude-haiku-4-5-20251001` (confirmed in codebase). The image model `google/gemini-3.1-flash-image-preview` is confirmed live in the codebase.
