## Executive Summary

The JS API Primitive concept is architecturally sound and overdue. The "API is the tool, UI is a consumer" framing is exactly right. The implementation brief correctly identifies that all reusable machinery must live outside the infographic generator. Phase 1 (window events only) delivers immediate, high-value ROI in one day and should be prioritised above all else.

Seven specific issues require resolution before development starts. None are blockers for Phase 1. Three are blockers for Phase 2. The rest are conditions on Phase 4–5.

## 1. Three-Tier Structure Assessment

**APPROVED.** The tier placement is correct.

`core/sg-tool-api/` is the right home. The proposed files — `sg-tool-api.js`, `sg-tool-api-events.js`, `sg-tool-api-registry.js` — contain zero UI, zero DOM manipulation, and no component registration. They are pure-JS orchestration: a class, event constants, and a registry helper. This matches exactly what `sg-vfs-core.js`, `sg-tree.js`, and `sg-vault-client.js` establish as the core tier pattern.

The six UI components under `components/tool-api/` are correctly tier-placed. They consume `core/sg-tool-api` and render DOM; they belong in `components/`.

Dependency direction is clean: tools → components/tool-api → core/sg-tool-api. No violations.

**One correction required on versioning path format.** The impl brief proposes:

```
core/sg-tool-api/v0/v0.1/v0.1.0/
```

This matches the `sg-tree` and `sg-vfs` pattern (triple-nested: major / minor / patch). However, `sg-layout` uses a flat single-folder path (`core/sg-layout/v0.1.0/`), and `vault-client` uses double nesting (`v1/v1.0/v1.0.0/`). There is no consistent standard across existing core modules. For a brand-new module starting at v0.1.0, the triple-nested format is correct — it anticipates minor-version grouping across `v0.1.x` as the module matures, as sg-tree demonstrated going from v0.1.0 through v0.1.6 and then to v0.2. **Use triple nesting. Do not flatten to match sg-layout's legacy path.**

## 2. Reconciliation with the Manifest Spec (08 Apr)

This is the most important architectural issue in the review.

**Two manifest concerns exist and they are distinct problems.**

### 2.1 The manifest.json schema conflict

The 08 Apr manifest spec defines `manifest.json` with identity fields (`name`, `slug`, `description`, `icon`), classification fields (`version`, `status`, `category`, `keywords`), and a `dependencies` block listing which modules a tool imports.

The new briefs want `manifest.json` to also carry **method schemas**: parameter names, types, return shapes, async flags, environment constraints (`browser` vs `browser+node`), and test definitions consumed by `sg-tool-api-tester`.

These are fundamentally different concerns:

- The 08 Apr manifest is **static metadata** — it describes what a tool is and what it imports. It is read by the landing page, `sg-tool-registry.js`, and `sg-tool-manifest` web component. It does not change when the tool's API changes.
- The method schema is **API contract metadata** — it describes what the tool's JavaScript API does. It is read by `sg-tool-api-explorer`, `sg-tool-api-tester`, and `sg-tool-api-console`. It changes when methods are added, renamed, or their signatures change.

**Decision: split these into two files.**

- `manifest.json` — the existing schema from 08 Apr, unchanged. Static tool identity and dependency graph.
- `api.json` — new file, OpenAPI-inspired, carrying the method schema: name, description, params (name/type/required/default), returns (shape), async, events, environment, and optionally test definitions.

**Why split:**
1. `manifest.json` is already being adopted across all tools (08 Apr spec). Polluting it with method schemas means every tool needs a method schema to have a valid manifest, which is backwards.
2. `sg-tool-api-explorer` fetching `manifest.json` and finding no `methods` key is a runtime failure waiting to happen. A distinct `api.json` makes the contract explicit: if `api.json` exists, the tool implements the JS API Primitive.
3. The manifest validator CI script (08 Apr Phase 4) validates one schema. If method schemas are merged in, that validator needs to handle optional method schema sections — needless complexity.
4. Independent versioning: `manifest.json` changes when deps change; `api.json` changes when the API surface changes. These are different cadences.

**`meta.getManifest()` must return the combined view.** The `SgToolApi` class should load both files and merge them in memory. The explorer component sees the full picture. Neither file is burdened with the other's concerns.

**Decision verdict:** CHANGE REQUIRED. The impl brief conflates these. The developer must implement `api.json` as a separate file alongside `manifest.json`, and `SgToolApi` fetches both.

### 2.2 The `sg-tool-api-manifest` component vs `sg-tool-manifest` from 08 Apr

The 08 Apr spec defines `sg-tool-manifest` (in `_common/js/`) as a per-tool info panel showing name, version, status, deps.

The impl brief proposes `sg-tool-api-manifest` as a viewer with syntax highlighting, collapsible sections, validation indicators, and links to SKILL files.

These are **not duplicates** — they serve different audiences:
- `sg-tool-manifest`: shown to end-users. A simple info panel. Ships as a footer element.
- `sg-tool-api-manifest`: shown to developers/agents. Shows the full API contract including method schemas and SKILL file links. Part of the developer tooling tier.

Keep both. Name them clearly. `sg-tool-manifest` stays in `_common/js/` per the 08 Apr spec. `sg-tool-api-manifest` lives in `components/tool-api/sg-tool-api-manifest/` per the new brief. No rename needed.

## 3. Component Structure Critique

### 3.1 Naming

All six proposed component names follow the established `sg-*` pattern and are descriptive. No renaming needed.

The grouping path `components/tool-api/` is consistent with how `components/llm/` groups all LLM components and `components/openrouter/` groups all OpenRouter components. **Approved.**

### 3.2 Versioning

The impl brief specifies component paths without version numbers:
```
components/tool-api/
    sg-tool-api-explorer/
    sg-tool-api-console/
    ...
```

This is incomplete. Every component in this codebase uses triple-nested folder versioning, e.g.:
```
components/llm/sg-llm-events/v0/v0.1/v0.1.0/sg-llm-events.js
components/openrouter/sg-openrouter-generation/v0/v0.1/v0.1.0/sg-openrouter-generation.js
```

The full paths must be:
```
components/tool-api/sg-tool-api-explorer/v0/v0.1/v0.1.0/sg-tool-api-explorer.js
components/tool-api/sg-tool-api-console/v0/v0.1/v0.1.0/sg-tool-api-console.js
components/tool-api/sg-tool-api-tester/v0/v0.1/v0.1.0/sg-tool-api-tester.js
components/tool-api/sg-tool-api-logger/v0/v0.1/v0.1.0/sg-tool-api-logger.js
components/tool-api/sg-tool-api-footer/v0/v0.1/v0.1.0/sg-tool-api-footer.js
components/tool-api/sg-tool-api-manifest/v0/v0.1/v0.1.0/sg-tool-api-manifest.js
```

**CHANGE REQUIRED.** The developer must use these versioned paths in all import statements and in the tool's `manifest.json` dependencies block.

### 3.3 `sg-tool-api-footer` name collision risk

The existing `components/footer/v1/v1.0/v1.0.0/sg-footer.js` is the site-wide page footer (privacy message, SG/Send link). The proposed `sg-tool-api-footer` is a tool-status bar (version, deps, skills). These are different components with different purposes.

The name `sg-tool-api-footer` is fine — it is clearly scoped with the `tool-api` prefix. No collision. However, avoid naming its custom element `<sg-footer>` (already taken). Use `<sg-tool-api-footer>`.

### 3.4 Core file split: `sg-tool-api-registry.js`

The impl brief lists `sg-tool-api-registry.js` as a core file alongside `sg-tool-api.js` and `sg-tool-api-events.js`. The registry manages `window.__tools` and `window.__tool`. This is correct — keeping registration logic isolated from the base class is the right separation.

However, the registry will need to write to `window`. This is acceptable in `core/` for this specific case: the registry's entire purpose is the `window.__tools` namespace. The constraint "no localStorage in core modules" stands; window property assignment is a different concern and is appropriate here. Document it explicitly in the file's JSDoc.

## 4. `window.__tool` / `window.__tools` Registration

### 4.1 Single-tool assumption

The arch brief states:
```javascript
window.__tools['infographic-generator'] = { ... };
window.__tool = window.__tools['infographic-generator'];
```

`window.__tool` (singular) is a convenience alias for the last-registered tool on a page. This works correctly on a single-tool page. It breaks silently on pages with two tools, where `window.__tool` gets overwritten by the second `activate()` call.

The current tools site serves one tool per HTML page — this is not a problem today. But the arch brief's "multi-tool" acceptance criterion and the `window.__tools` map exist precisely because multi-tool pages are anticipated.

**Decision:** `window.__tool` must only be set if it is currently undefined (i.e., the first tool to activate). Set `window.__tool` only when no other tool has claimed it yet. Document this behaviour in the JSDoc.

### 4.2 Cross-frame access

The brief mentions Playwright using `page.evaluate(async () => { await __tool.connect() })`. This works as long as the tool is in the top-level browsing context and not inside an iframe.

`sg-sandbox.js` (in `core/sg-sandbox/`) runs inside a sandboxed iframe with `null` origin. If any future tool uses `sg-sandbox` to run untrusted code, `window.__tool` inside the sandbox is a different window object. **Flag for future tools: do not assume `window.__tool` is accessible from sandboxed iframes.** No action needed for the infographic generator MVP.

### 4.3 Event namespace collision

The arch brief proposes these window events: `tool:ready`, `connected`, `disconnected`, `generation:started`, `generation:complete`, `generation:error`.

`connected` and `disconnected` are dangerously generic names for window-level events. Any third-party script, browser extension, or future tool component that listens for `connected` on `window` will collide. The existing LLM events use namespaced strings (`llm:connected`, `llm:disconnected`).

**CHANGE REQUIRED:** All `window.__tool` events must be namespaced with `tool:` prefix:
- `tool:ready` (already correct — keep)
- `tool:connected` (change from `connected`)
- `tool:disconnected` (change from `disconnected`)
- `tool:generation:started` (change from `generation:started`)
- `tool:generation:complete` (change from `generation:complete`)
- `tool:generation:error` (change from `generation:error`)

Update `sg-tool-api-events.js` accordingly. Freeze the object as `SGA_TOOL` (SGraph Automation — Tool). Expose on window: `window.SGA_TOOL = SGA_TOOL` (consistent with `window.SGL_LLM = SGL_LLM`).

### 4.4 Event constant naming convention

Existing convention: `SGL_LLM`, `SGL_VFS`, `SGT_EVENTS`. Recommend `SGA_TOOL` (SGraph Automation — Tool) to make the automation context clear. Export as a frozen object; expose on window as `window.SGA_TOOL`. Document in `sg-tool-api-events.js`.

## 5. Implementation Sequence Assessment

### 5.1 Phase 1 is correct as the first step

Phase 1 (create `sg-tool-api` core module + add window events to infographic generator) is the right first step and should be treated as the minimum shippable unit. It delivers the highest ROI: Playwright can immediately listen for `tool:generation:complete` instead of polling.

The actual Phase 1 work is:
1. Create `sg-tool-api.js` with `SgToolApi` class (register, activate, _emit, _log, meta API stubs)
2. Create `sg-tool-api-events.js` with frozen event constants
3. Create `sg-tool-api-registry.js` with `window.__tools` management
4. Wire the infographic generator's SEND interceptor to instantiate `SgToolApi`, register a stub `generate` method, call `activate()`, and emit `tool:generation:started` / `tool:generation:complete` on the existing completion paths

The meta API stubs in Phase 1 can return empty/placeholder data. They are fleshed out in Phase 2.

**Phase 1 acceptance gate: `window.__tool` exists and fires `tool:generation:complete` with `{ generationId, duration }` on every generation. Playwright can listen for this event.** Nothing else is required for Phase 1 to be done.

### 5.2 Phase 2 ordering concern

Recommended inner order within Phase 2:

1. `connect()` first — smallest change, establishes the `SgToolApi.register()` pattern
2. `setTemplate()` second — trivial, 4 lines
3. `getCost()` third — wraps `sg-openrouter-generation.fetchGeneration()` with no UI coupling
4. `exportPng()` fourth — Canvas/blob, browser-only
5. `generate()` last — most complex; decoupling from tab creation is a significant refactor

For `generate()` extraction: **write the `renderUI: false` path first as a test harness before touching the existing `renderUI: true` path.** Otherwise the risk of breaking the live tool is high.

**Note on `getCost()` implementation:** `fetchGeneration()` is a method on a `SgOpenrouterGeneration` instance, not a standalone export. Do not couple `getCost()` to the component. Instead, inline the 15-line fetch call directly in `getCost()` to avoid the dependency.

### 5.3 Phase 3 should be parallelised with Phase 2

Writing SKILL files and `api.json` does not depend on Phase 2 being complete. SKILL-human.md can be written from the existing UI immediately. SKILL-browser.md can be written from current Playwright patterns. Content work should run in parallel with method extraction.

### 5.4 Phase 4–5 component build order

**Phase 4 revised order:** logger → footer → explorer

The logger is simpler (read from execution log array, render as list), does not require manifest parsing, and is immediately useful for debugging Phase 2 extractions. Explorer requires full manifest/api.json loading and the "Try it" invocation form — build it last within Phase 4.

**Phase 5 revised order:** manifest → tester → console

The manifest viewer is a read-only renderer of `api.json`. The tester needs test definitions parsed from `api.json`. The console needs autocomplete from `api.json`. Both depend on the manifest viewer's loading logic being stable — build it first.

### 5.5 Phase 6 validation is correctly scoped

The NotebookLM slide deck workflow using `__tool.generate({ await: true })` instead of the polling loop is the correct integration test. Parallel generation with `Promise.all()` across 3 models is the correct stress test.

Do not block the infographic generator release on vault tool adoption. Run vault adoption in a separate session after infographic generator ships.
