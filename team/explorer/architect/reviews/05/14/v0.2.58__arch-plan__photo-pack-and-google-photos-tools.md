## 1. The problem (from the brief)

A user takes photos/videos on an iPhone synced to Google Photos. Selecting a mix of
photos + videos in Google Photos and downloading them produces a messy ZIP:

- **HEIC images** that render as binary garbage in browsers (and in SG/Send's gallery).
- **Live Photos** that come down as *paired* HEIC still + MOV/MP4 files.
- **Large `.MOV` (QuickTime/HEVC) videos** — one was 30 MB.
- **~60 MB total for 10 items** — far too heavy for "simple file sharing".

We want **two new browser-based tools** plus **shared components**:

1. **`photo-pack`** — clean up a messy photo/video pack: convert HEIC, collapse Live
   Photos, extract a still frame from videos (with the option to pick a different
   frame), compress/resize, repackage, and hand off to SG/Send.
2. **`google-photos-connector`** — pull a selection straight from Google Photos and
   feed it into the `photo-pack` pipeline.

## 2. Research findings — read before building

### 2.1 Google Photos API — assumption was outdated ⚠️

As of **31 March 2025** Google removed the broad read scopes (`photoslibrary`,
`photoslibrary.readonly`, `photoslibrary.sharing`). A third-party OAuth app **can no
longer browse or enumerate a user's existing library** — those calls return
`403 PERMISSION_DENIED`. The legacy Library API now only returns content the app
itself uploaded.

**The only supported path is the new Picker API:** Google hosts the selection UI, the
user picks items, and the app receives only those selected items (plus their
`baseUrl` for download). You cannot browse the library inside our tool.

**Decision (confirmed with user): use the Picker API.** Tool #2's UX is "Connect →
launch Google's picker → user selects → we import the picked items".

### 2.2 HEIC

No browser natively renders HEIC — not even Safari. Conversion is **mandatory**.
Best client-side, no-build-step options: `libheif-js` (raw WASM, ESM build via CDN)
or `heic2any` (single UMD file). WASM payload is ~1.5–3 MB — **lazy-load only when a
HEIC file is actually present**. This must be de-risked with a probe page before
committing (Phase 0).

### 2.3 Live Photos

Google Photos stores the iOS Live Photo still and motion separately, so a download
gives two files. **Decision (confirmed): flatten to still-only by default** — output
just the converted JPEG/WebP still, drop the motion clip.

### 2.4 Video frame extraction

iPhone `.MOV` is HEVC (H.265). Chrome/Firefox on Linux/Windows generally **cannot**
decode HEVC in a `<video>` element, so the fast `<video>`+`currentTime`+`drawImage`
path fails for exactly the files the user has. **Frame extraction must use the
FFmpeg WASM path** (`-ss <time> -frames:v 1`) via the existing `sg-video` loader for
`.mov`; the `<video>` path is only safe for already-web-friendly `.mp4`.

**Decision (confirmed): for real videos, offer BOTH a still frame AND a
transcoded/compressed MP4** of the full video as output options. (Note: in-browser
transcode via FFmpeg WASM is slow — show progress.)

### 2.5 Where SG adds value

Prior art (Wormhole.app) already proves the no-account, client-side-encrypted
sharing model — which is what SG/Send is. **Nothing on the market is
iPhone-media-aware.** SG's genuine differentiator is the **pre-processing /
normalization layer**: HEIC convert, Live Photo flatten, resize/compress, video
thumbnailing — all client-side, before the encrypt-and-share step. Don't reinvent
encrypted transfer; the novelty is "iPhone media just works for the recipient".

## 5. Shared components — responsibilities

**`core/sg-heic`** — `decodeHeic(file) → Promise<{canvas,width,height}>`,
`isHeic(file)` (sniff `ftyp` box / extension), `heicToBlob(file,{format,quality})`.
Wraps a CDN ESM library, lazy-loaded. Returns a canvas so `sg-image` does the resize/export.

**`core/sg-video-frames`** — `getFrameAt(file,timeSec) → {canvas,blob}`,
`getThumbnailStrip(file,count) → Array<{time,blob}>`. FFmpeg WASM path primary (for
HEVC `.mov`); `<video>` path only for web-safe `.mp4`. Generate the strip in a single
FFmpeg pass (`-vf fps=...`), not N seeks.

**`core/sg-live-photo`** — `detectPairs(items) → {pairs:[{still,motion}], singles:[]}`.
Pure logic: group by normalised basename, pair HEIC/JPG with sibling MOV/MP4.

**`core/sg-photo-pack`** (the shared engine — 3 files, each < 300 lines):
- `sg-photo-pack-model.js` — the `PhotoPackItem` shape
  (`{id, kind:'image'|'video'|'live', sourceBlob, sourceName, decoded, chosenFrameTime, output, include, settings}`),
  `createPack()` factory + mutation helpers.
- `sg-photo-pack-zip.js` — `ingestZip(file)`, `ingestFiles(fileList)`, `repackZip(items,opts) → Blob`.
- `sg-photo-pack-pipeline.js` — `processItem(item,settings)` orchestrates
  HEIC→decode→resize→export / video→frame-pick (+ optional transcode)→export /
  pass-through web-safe images. `processPack(pack,onProgress)`. **Processes items
  sequentially** to bound memory.

**`core/sg-google-photos`** (tool #2 only) — `requestPhotosAccess(clientId)`
(delegates to the `requestAccess` pattern with the Picker scope),
`createPickerSession()`, `pollSession(id)`, `listPickedItems(sessionId)`,
`downloadMediaBytes(item)` (uses `baseUrl` `=d` download param). Mirrors `YouTubeApi`.

**`components/sg-video-frame-picker`** — interactive scrubber; consumes a video blob,
emits chosen `{time,blob}`. Used by both tools.

**`components/sg-photo-pack-grid`** — renders `pack.items`, per-item include toggle +
kind badge + thumbnail; emits `sg-pack-item-changed`.

## 8. Technical risks

1. **HEIC decoding (highest risk).** No native support. No-build / ESM-only rules out
   npm-bundled `heic2any`, but CDN ESM builds exist. Recommended: `libheif-js` WASM ESM
   from CDN, lazy-`import()` + blob-URL-worker (same technique proven in `sg-video.js`
   for FFmpeg). Risk: ~2–3 MB WASM; 10-bit/HDR variants decode imperfectly. Mitigate:
   lazy-load only on HEIC detection; clear "couldn't decode" item state on failure.
   **De-risk in Phase 0.**
2. **Video frame extraction.** iPhone `.MOV` is HEVC; Chrome/Linux/Windows can't decode
   it in `<video>`. Frame extraction must use FFmpeg WASM for `.mov`. Slow — show
   progress; single-pass strip generation.
3. **Google Photos Picker API.** OAuth itself is low-risk (`requestAccess` works). New
   App ID setup: enable Photos Picker API, add the Picker scope to the consent screen,
   add the user's email as a test user, register the tool origin as an authorised JS
   origin. **CORS on `baseUrl` downloads needs a probe** (mirror the `linkedin-publisher`
   CORS-probe approach) — flag as a Phase 0 task.
4. **Memory.** All client-side, in-memory. Process pipeline items **sequentially**
   (decode→resize→export→release) — don't hold all decoded canvases at once. FFmpeg WASM
   holds input+output in its virtual FS. `<sg-send-drop>`'s ChunkedUploader handles large
   uploads already.
5. **No build step.** All three CDN deps (libheif, FFmpeg, JSZip) must load as ESM-from-CDN
   or classic-script-from-CDN. FFmpeg + JSZip are proven in-repo; **libheif is the
   unproven one — Phase 0 probe gates everything.**

## 11. Resolved configuration decisions (2026-05-14)

| Question | Decision |
|---|---|
| Default output target size | **2048 px long edge, JPEG/WebP q80 for stills; 1080p H.264 for transcoded video.** |
| Output ZIP structure | **Flat list** of converted files — input folder structure is not preserved. |
| Compressed-video transcode cost | **Acceptable with a progress bar** — no hard cap on duration/resolution; just surface progress. |
| Google App ID | Tool #2 gets **its own dedicated OAuth client ID**, distinct from the youtube one. User (Dinis) configures the Google Cloud project, consent screen, and test users. |

### Google Cloud setup the user needs to do (tool #2)

- **API to enable** (Cloud Console → APIs & Services → Library): **"Photos Picker API"**.
  Do NOT enable the legacy "Photos Library API" — it no longer grants library read access.
- **OAuth scope to request**: `https://www.googleapis.com/auth/photospicker.mediaitems.readonly`
  — this is the only scope the tool needs; it covers creating a picker session and
  reading the items the user picked.
- **OAuth client type**: Web application. Add **Authorised JavaScript origins** for the
  tool's hosting origin (`https://tools.sgraph.ai`) and `http://localhost:<port>` for
  local dev. No redirect URI is needed — the tool uses the GIS token-client
  (`initTokenClient`) implicit flow, same as the youtube tool.
- **OAuth consent screen**: External user type; add the scope above; while unverified,
  add the user's Google account(s) as **test users**.
- **Verification**: a `photospicker.mediaitems.readonly`-only app is low-sensitivity;
  full Google verification is only needed once it goes public beyond test users.
