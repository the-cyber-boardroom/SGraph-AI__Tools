# Architect Review — Deep Review of LLM Tools and Components

**Version:** v0.2.54
**Date:** 2026-05-12
**Role:** Architect (Explorer team)
**Scope:** Every LLM-related core module, component, and tool in `sgraph_ai_tools__static/`
**Branch:** `claude/review-llm-tools-r4zLz`

---

## 1. Executive Summary

The LLM stack is a **well-structured event-driven system** built on a small set of pure-JS core modules, 18 LLM UI components, 10 OpenRouter integrations, and 6 agentic components, consumed by ~10 tools.

Strengths:
- **Unified event bus** (`[data-llm-bus]`) — loose coupling across all components
- **Provider abstraction** at the request layer (OpenRouter, Ollama, Anthropic, OpenAI behind one interface)
- **Multimodal** support (images, PDFs, audio, video) with provider-specific translation
- **Tool calling + agentic loops** for autonomous workflows
- **Bundle system** ("Git for prompts") with fork-tree persistence

Critical concerns:
- **`sg-llm-chat-history` bloat** (1,147 lines — 5.7× the median)
- **Attachment-handling duplication** between `sg-llm-attachments`, `sg-llm-attachment-manager`, and `sg-llm-chat-input` (~1,500 combined lines)
- **Scattered multimodal translation** across `sg-llm-request` builders
- **No shared conversation abstraction** — each tool reimplements message assembly
- **Versioning drift** — older tools still consume v0.1.0–v0.1.2 components while latest is v0.1.6–v0.1.10

Architecture grade: **B+** — cohesive, but several components are at or over the 500-line ceiling defined in `.claude/CLAUDE.md`.

## 3. Component Deep Dives

### 3.1 `sg-llm-chat-history` (1,147 lines) — the headline problem

Eleven distinct responsibilities in one component: turn array ownership, message assembly, streaming display, image rendering, lightbox, image-bubble buttons, attachment tracking, system-prompt editor, markdown rendering, markdown export, 200+ lines of inline CSS.

Tight coupling via:
- `llm:chat-message` listener (chat-input)
- Attachment-manager events
- Streaming events from sg-llm-request
- Shadow-DOM workaround: `bus.__sgLlmChatHistory = this`

**Recommended split:**
- `sg-llm-turn-manager` — core logic (turn array, assembly) ≈ 300 lines
- `sg-llm-turn-view` — streaming + markdown display ≈ 400 lines
- `sg-llm-image-bubble` — image rendering + lightbox + buttons ≈ 250 lines

### 3.2 Attachment duplication (~1,500 lines across 3 components)

| Component | Mode | Cache | Use case |
|---|---|---|---|
| sg-llm-chat-input | Inline | Local | Multi-turn chat |
| sg-llm-attachments | Drop zone | Owns | One-shot (auto context block) |
| sg-llm-attachment-manager | Standalone | Owns | Composable panel |

**Recommendation:** Merge into one `sg-attachment-manager` with `mode: 'inline' | 'standalone' | 'editor'` and `autoContextBlocks` flag.

### 3.3 `sg-llm-request` architecture (split v0.1.5+)

Three files: `sg-llm-request-builders.js` (headers/body per provider), `sg-llm-request-parsers.js` (SSE delta + usage + image + tool-call parsing), `sg-llm-request.js` (Web Component, 122 lines). Multimodal translation lives inside builders — images, PDFs, audio each get provider-specific encoding. Hard to extend or debug.

**Recommendation:** Extract `SgLlmContentTranslator` with `toProviderFormat(content[], provider)` / `fromProviderResponse(response, provider)`.

### 3.4 Token-accounting duplication (sg-llm-stats vs sg-llm-token-viz, 1,052 lines)

Both hardcode 14-model pricing and consume the same SEND / REQUEST_COMPLETE events.

**Recommendation:** Merge into `sg-llm-accounting` with tabs (Summary / Breakdown / History / Pricing). Move pricing into a new `sg-llm-pricing` core module that fetches OpenRouter `/v1/models` and caches locally.

### 3.5 Bundle inspector bloat (1,031 lines across 2 components)

Both reinvent JSON-tree and markdown-table rendering inline.

**Recommendation:** Extract `sg-json-tree` (~150 lines) and `sg-markdown-table` (~80 lines), shrinking bundle-list to ~250 and bundle-viewer to ~200.

## 6. Inconsistencies

**Versioning drift** (critical) — see §4. Notably, one-shot-chat and llm-dev still ship with request v0.1.0 (buggy streaming, no PDFs, no tool calling).

**Event naming** — three styles in use: `llm:chat-message` (kebab), `SGL_LLM.SEND` (UPPER constant), `tool:generation:started` (namespaced). Standardise via sg-llm-events constants pointing to a single `llm:*` kebab form.

**Component registration anti-patterns:**
- `querySelector('sg-llm-bundle')` — fragile, breaks across shadow DOM (used by bundle-list)
- `bus.__sgLlmChatHistory = this` — pollutes bus object (chat-history, bundle)
- Event-driven registration (`llm:bundle-inspect-requested`) — clean, used by bundle-viewer

Adopt the event-driven pattern everywhere; add a `bus.getComponent(tagName)` helper for the rare cases that need a direct ref.

---

## 7. Gaps

1. **No shared conversation module** — chat, one-shot-chat, agentic, playbooklm all reimplement message assembly. Propose `core/sg-llm-conversation/v0.1.0/` with turn array, system prompt, `toJSON`/`fromJSON`.
2. **No streaming abstraction** — SSE handling spread across request, chat-history, token-viz, response-inspector. No unified cancel/pause/resume; multi-stream merging for multi-agent is bespoke.
3. **No cost/pricing aggregator** — 14-model pricing table hardcoded in two components; new models silently cost $0. Propose `core/sg-llm-pricing/`.
4. **No tool-definition schema registry** — agentic tool definitions are ad-hoc. Propose `core/sg-llm-tool-schema/` with `validate`, `normalize`, `getUiType`.

## 8. Prioritised Recommendations

### High impact

1. **Merge attachment handlers** — single `sg-attachment-manager` with mode option. Saves ~1,500 lines, ends the three-way drift. ~3–4 days.
2. **Split `sg-llm-chat-history`** into turn-manager / turn-view / image-bubble. ~5–6 days. Unblocks reuse in multi-agent-chat.
3. **Fix versioning drift** — bump all tools to latest component versions; add a compatibility matrix and a manifest validator. ~1–2 days. Immediately fixes PDF + tool-calling in one-shot-chat and OpenRouter tool.
4. **Extract `sg-json-tree` + `sg-markdown-table`** — shrinks bundle-list / bundle-viewer by ~60%, reusable in PlaybookLM and agentic. ~2–3 days.

### Medium impact

5. **Standardise event naming** via sg-llm-events constants. ~1 day.
6. **Merge sg-llm-stats + sg-llm-token-viz** into `sg-llm-accounting`; extract `sg-llm-pricing` core module fetching OpenRouter `/v1/models`. ~3–4 days.
7. **Create `sg-llm-conversation` core module**; port chat, one-shot-chat, agentic. ~4–5 days.
8. **Replace `bus.__component` anti-pattern** with `bus.getComponent(tagName)` helper + event-driven discovery. ~2 days.

### Backlog

- `sg-llm-streaming` unified protocol (cancel/pause/resume, multi-stream merge)
- `sg-llm-tool-schema` registry
- Audit coupling between consumers and `sg-llm-events` versioning

---

## 9. Conclusion

The LLM stack is architecturally sound: event-driven, provider-abstracted, multimodal-capable, with working tool-calling and agentic loops. The risk is **complexity creep** — six LLM components and five OpenRouter components are now over the 500-line ceiling, and three tools are running components ≥ 4 minor versions behind.

The 2–3-sprint refactor outlined above (recommendations 1–4 first, then 5–8) restores headroom before new LLM tools are added. Doing it now is materially cheaper than waiting.
