## 1. Context: Two manifest.json Schemas Now Exist

Before reviewing the proposed schema, note that a **dependency manifest** already exists in the
codebase and is in production at `v0.1.25/en-gb/vault/manifest.json`. That schema was designed by
the Architect in `v0.20.38__arch-review__tool-manifest-spec.md` (in `reviews/04/08/`).

That existing schema covers: `name`, `slug`, `description`, `icon`, `version`, `status`,
`category`, `keywords`, `dependencies`. It is used by `sg-tool-manifest.js` (the collapsible footer
component) and the landing page.

The briefs now propose extending `manifest.json` to also describe the **JavaScript API** — methods,
parameters, return types, events, environment compatibility. This is an OpenAPI-inspired addition,
not a replacement.

**Architectural question:** one file or two?

**Recommendation: one file, two sections.** The dependency metadata and the API metadata describe
the same artefact from different angles. Two files create synchronisation risk and doubles the
fetches. Extend the existing schema with an `api` top-level key:

```jsonc
{
  // Existing (dependency manifest) fields unchanged:
  "name": "Infographic Generator",
  "slug": "infographic-gen",
  "version": "0.1.25",
  "status": "live",
  "category": "llm",
  "dependencies": { ... },

  // NEW: API section (only present if tool implements SgToolApi)
  "api": {
    "version": "0.1.0",
    "actions": { ... },
    "events": [ ... ],
    "skills": { ... }
  }
}
```

Tools without a JS API simply omit the `api` key. `sg-tool-manifest.js` already ignores unknown
keys. `SgToolApi.meta.getManifest()` returns the full file; consumers check for `manifest.api`.

## 2. OpenAPI Inspiration: What to Adopt and What to Drop

The arch brief says "OpenAPI-inspired." That is appropriate framing — adopt the spirit, not the
syntax. OpenAPI is designed for REST endpoints over HTTP; this is for JavaScript method calls in a
browser. Three OpenAPI concepts that directly apply:

| OpenAPI concept | Applied here as |
|-----------------|-----------------|
| `operationId` | `actions` key name (e.g. `"generate"`) |
| `parameters` object | `params` per action |
| `responses` / schema | `returns` per action |

Three OpenAPI concepts to drop:

| OpenAPI concept | Why drop |
|-----------------|----------|
| `$ref` and component schemas | No JSON Schema resolution in a browser tool |
| HTTP verb + path | Not applicable; methods are called by name |
| Security schemes | Auth is tool-specific (apiKey param), not a transport concern |

## 3. Proposed `api.actions` Schema

```jsonc
"actions": {
  "connect": {
    "description": "Validate an OpenRouter API key and set the active model.",
    "params": {
      "apiKey": { "type": "string", "required": true, "secret": true },
      "model":  { "type": "string", "required": false }
    },
    "returns": {
      "connected": { "type": "boolean" },
      "model":     { "type": "string" },
      "models":    { "type": "array", "items": { "type": "string" } }
    },
    "async": true,
    "environment": ["browser", "node"],
    "errors": [
      { "code": "INVALID_KEY",    "when": "API key rejected by OpenRouter" },
      { "code": "NETWORK_ERROR",  "when": "fetch failed" }
    ]
  },
  "generate": {
    "description": "Generate an infographic from a prompt.",
    "params": {
      "prompt":       { "type": "string", "required": true },
      "model":        { "type": "string", "required": false },
      "template":     { "type": "string", "required": false, "enum": ["executive","architecture","timeline","comparison","process","stats","mindmap"] },
      "systemPrompt": { "type": "string", "required": false },
      "await":        { "type": "boolean", "required": false, "default": false },
      "renderUI":     { "type": "boolean", "required": false, "default": true }
    },
    "returns": {
      "generationId": { "type": "string" },
      "image":        { "type": "object", "when": "await: true" },
      "duration":     { "type": "number", "when": "await: true" }
    },
    "async": true,
    "environment": ["browser"],
    "events": ["generation:started", "generation:complete", "generation:error"],
    "errors": [
      { "code": "NOT_CONNECTED",  "when": "connect() not called first" },
      { "code": "EMPTY_PROMPT",   "when": "prompt is blank" }
    ]
  }
}
```

### Critical addition: `"secret": true` on params

The `connect.params.apiKey` has `"secret": true`. This is the signal to the execution log's
sanitise hook (see the core design review) to mask the value. It must also suppress the value in
`sg-tool-api-explorer`'s "Try it" invocation form — show a password input, not a plain text field.
Without this flag, the schema does not support safe tooling.

## 4. What the Brief Got Wrong or Overlooked

### 4.1 The brief omits `getState()` from the manifest

The impl brief defines `__tool.getState()` returning
`{ connected, model, activeGenerations[], templates[], mode }`. This method is not mentioned in the
`manifest.json` examples. It should appear in `actions` with `async: false` and no required params.
If it is not in the manifest, `getMethods()` will not list it, and the tester cannot exercise it.

### 4.2 No error code taxonomy

The arch brief shows `e.code === 'NOT_CONNECTED'` in QA tests. The manifest schema needs a canonical
list of error codes per action. The examples above include `errors[]` for this reason. Without it,
error-contract testing is not machine-readable — the tester cannot assert on the right error code.

### 4.3 The `skills` section is under-specified

The arch brief mentions three SKILL files. The impl brief shows:

```javascript
skills: {
    human:   '/en-gb/infographic-gen/SKILL-human.md',
    browser: '/en-gb/infographic-gen/SKILL-browser.md',
    api:     '/en-gb/infographic-gen/SKILL-api.md',
}
```

These are passed to `SgToolApi` constructor but how they appear in `manifest.json` is not shown.
Recommendation: embed them as URLs in the `api` section:

```jsonc
"api": {
  "skills": {
    "human":   "./SKILL-human.md",
    "browser": "./SKILL-browser.md",
    "api":     "./SKILL-api.md"
  }
}
```

Relative URLs (relative to `manifest.json` location) are preferable over absolute paths because
they survive moves between IFD versions without editing the manifest.

### 4.4 Version mismatch: brief targets v0.1.24 but latest is v0.1.25

The impl brief title says:
> **MVP tool** Infographic Generator (`tools/v0/v0.1/v0.1.24/en-gb/infographic-gen/`)

The codebase is at v0.1.25. The reality document confirms this. Implementation should target
v0.1.25 (or create a v0.1.26 delta). The brief's reference to "lines 1044-1069" and
"lines 857-1029" are also stale — the current `infographic-gen.js` is 607 lines total (the
orchestration code; bulk of logic is in `panels.js` and components). These line-number references
should not be used as implementation anchors.

### 4.5 `test` section in manifest is missing

The impl brief shows the tester reading test definitions from "the manifest or a `tests.json`
file." This is undecided. Decide now: put tests in `manifest.json` under a `tests` key (keeps
everything in one fetch) or in a separate `tests.json` (keeps manifest focused). Recommendation:
separate `tests.json` in Phase 5. The manifest is already doing two jobs (dependency catalogue +
API schema). Adding test cases makes it three. Tests change more frequently than the API contract.

## 5. Backward Compatibility with Existing manifest.json

The vault tool and all 24 tools with manifests must not break. The extension is safe because:

1. The `api` key is new — existing parsers (`sg-tool-manifest.js`, `loadManifests()`) ignore it.
2. No existing field changes meaning.
3. Tools without a JS API simply have no `api` key.

The only risk: if someone hardcodes `Object.keys(manifest)` to validate the schema. There is no
such validation currently.
