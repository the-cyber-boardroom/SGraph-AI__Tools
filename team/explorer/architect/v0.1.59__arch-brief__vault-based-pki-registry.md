## 1. The idea in one paragraph

A PKI registry usually means a **central directory** that *stores* keys. This
thread inverts that on two axes at once. First, **the registry is itself a
vault** — so it holds only public keys, metadata, hashes, and key-encrypted
payloads; there is *nothing in it worth stealing*, and it inherits the vault's
distribution, encryption, and provenance "for free" (explicitly **replacing an
earlier FastAPI server-side prototype** — that prototype is the v0.5.0 admin
PoC mapped in `…__pki-from-send__migration-map.md`). Second, **it stores clues,
not data**: the load-bearing content is the *relationships between keys* — a
**graph database** of trust edges — not a trove of records. On top of that sits
a **two-level trust model** (downward explicit + upward self-declared, never
self-granting), **federation** (registers of registers + connectors to DNS /
GitHub / OAuth), and a **caller-side resolver** that walks the graph and returns
*graded, partial* trust. The whole thing is the first concrete building block of
a larger **"PKI instead of secrets" / NHI 2.0** paradigm.

## 3. The registry brief itself (v0.32.4) — the load-bearing concepts

### 3.1 Scope: public keys only
Two parts — *PKI creation* (the private key) and *public-key management*. **Only
the second is in scope.** Private keys stay with whoever created them; the
registry never stores or manages a private key.

### 3.2 Clues, not storage
"Not a place that has all the information — a place that holds **clues** that let
you find the right information. Meaning through connectivity." The registry is a
map of pointers + relationships, not a data warehouse.

### 3.3 The register is a vault — nothing worth stealing
It holds **only** public keys, metadata, hashes, mappings, and *data encrypted to
specific keys it does not hold*. Every payload is indexed by the public key
needed to decrypt it. The register can read none of its own encrypted content.

### 3.4 It is a graph database
Nodes = public keys (+ metadata + encrypted-payload pointers). Edges = trust
relationships. Resolving trust = traversing the graph.

### 3.5 Two-level trust + vouching signals

| Trust | Direction | Asserted by | Lives in |
|---|---|---|---|
| **Downward (explicit)** | A trusts B | A | A's own key dataset |
| **Upward (self-declared)** | "B should be trusted by A" | B | B's own declaration |

**Self-declaration grants nothing** — it's a *request* the named party confirms
or denies. Verifying it produces graded signals: confirmed link · pending
(eventually-trusted) · one-way · **explicit distrust** (a valid, useful signal).
(Example: every key declares it connects to SGraph — downward — without SGraph
having to reciprocate.)

### 3.6 Replaces server-side complexity
"In the past I built a prototype with FastAPI and all this server-side
complexity. Now the registry is **just a vault**" — inheriting distribution +
encryption + provenance, plus monitoring. *(That prototype = the v0.5.0
key-discovery admin lambda.)*

### 3.7 Federation + connectors
Registers connect to registers (vaults of vaults); **connectors** draw identity
from DNS, GitHub, Google Auth, OAuth — anything that asserts an identity
property. More connections → more of the multi-dimensional trust graph → more
establishable trust. "Live off the land" for identity.

### 3.8 Resolution is the caller's responsibility
The vault stores clues; a **resolver service/API** (the caller) walks the
fractal, recursive graph with depth/cycle limits and returns a **trust-graph
object** — explicitly supporting **partial results** ("I got this far, gained
this much trust, stopped because I lack the keys").

## 4. The NHI 2.0 frame (why this matters beyond a key lookup)

- **Accountability at provisioning time** — authorising an agent *is* assigning
  its keys; "the model hallucinated" is not an excuse, over-provisioning is the
  bug. This reframes agent safety from "control behaviour" (unsolved) to
  "control privileges" (a cryptographic, tractable problem).
- **Chain of authenticity** — signed keys, TLS-like hash-of-signatures, **not
  blockchain**, rooted in a *curated* set of root authorities (the identity
  providers) rather than thousands of public CAs.
- **Web of trust** — multi-dimensional, makes rogue identities expensive; agent
  **trust scores** earned over time on a cryptographic trail.
- **Vault as the agent's keyring** + **key-controlled memory** — an agent reads
  only what its keys decrypt; governing keys governs memory/context (and cuts
  token cost).

The registry is the **shared substrate** these depend on: where public keys,
their metadata, and their trust edges live.

## 5. The inbox — the first consumer (receiving side)

The 7-Jun vault-inbox brief is the concrete first use of the registry: a vault
declares which **public keys it accepts** (a key per agent); inbound messages are
organised by sending key; the inbox is a **main UI section checked on refresh**,
**outside version control** by design, with **vault-app methods gated by the
permission mapping**. It's the receiving half of vault-to-vault comms and the
primitive that makes **Email-FS-lite** real. The accepted-keys configuration *is*
a slice of the registry's trust data.

## 6. Capability tiers (the transport mechanics, from the dev_pack)

For completeness — the append-comms layer the inbox rides on (`dev_packs/v0.32.1`):
append-token `H(pubkey)` (non-secret write address) · `enum_key` (list/fetch/
mark-processed, no decrypt) · per-vault private key (decrypt, a file *inside* the
vault) · `write_key` (purge/write tree). The relay that moves the most traffic
holds the *least* secret. This is the *plumbing*; §3–§4 are the *trust model*.

  append/inbox endpoints; the **public-key-controlled inbox** across CLI/UI/app.
- Agent **trust scores**, web-of-trust resolution, key-controlled memory.

## 8. Relationship to this (tools) repo's PKI plan

This thread **resolves the open backend question** in
`…__pki-from-send__migration-map.md` (§B.4 / §B.7-#1): the registry is **not a
server** — it is a **vault + a caller-side resolver**, which fits this repo's
static/CDN, no-server-processing rule precisely. Concretely it adds, on top of
the migration map's PROPOSED `core/pki` modules:

- `core/pki/sg-pki-trust-graph.js` — nodes (keys + metadata) + edges (downward/
  upward trust), serialised as vault content; vouching-signal grades.
- `core/pki/sg-pki-resolver.js` — caller-side graph walk with depth/cycle limits,
  partial/graded results.
- `core/pki/sg-pki-connectors/` — thin per-provider connectors (DNS, GitHub, OAuth).
- `<sg-pki-trust-graph>` / `<sg-pki-resolver-view>` components; reuse
  `vault-schema-pki-key` for node display.
- `<sg-vault-inbox>` component + a `pki-registry` / `vault-inbox` tool
  (SgToolApi + SKILL files), reusing `core/vault-client` as the vault substrate.

It also confirms the **X25519 + Ed25519** direction over the PoC's RSA/EC, and the
**"vault is the keyring / private key stays in the vault"** storage answer.
