## 1. The core idea in one paragraph

Today a PKI registry means a **central directory**: you publish your public key
to a server, it hands back a lookup handle, others query the server to find you.
SGraph already has that — the implemented **key-discovery registry** (Send admin
lambda, `XX-XXXX` codes, append-only transparency log; see §3.1). The new idea
**inverts the storage**: the registry is **not a server table, it is the set of
vaults themselves**. Each vault owns a key pair; its **public key is the
discovery address** (`append_token = H(public key)`); its **private key is a file
inside the vault**, decryptable only by holders of that vault's read access. Key
distribution, addressing, and message delivery all reduce to *vault operations* —
the server stores opaque bytes and never holds, derives, or inspects a key. The
"registry" becomes a thin, verifiable index over vault-resident public keys
rather than the source of trust.

## 3. EXISTS vs PROPOSED (be honest about the build size)

Drawn directly from the v0.32.1 build ledger (`00__README.md` §"Build ledger")
and the v0.5.0 debrief.

### 3.1 EXISTS today (in Send)

- **Centralized key-discovery registry** — publish/lookup/unpublish/list/log, `XX-XXXX` codes, transparency log, fingerprint de-dup (`v0.5.0`, implemented; mapped in `…__pki-from-send__migration-map.md`).
- **`vault_pointer.json` manifest**, `write_key_hash`, write/delete double-gating (User Lambda `Routes__Vault__Pointer.py`).
- **CAS storage + tombstone/purge** model.
- **HKDF derivation family** — `structure_key = HKDF(read_key, …)` (the sibling pattern the new `enum_key` slots into).
- **Deterministic-id credential → capability** pattern (P-177 ro-token).
- **Cross-language derivation parity tests** (public-preview precedent).

### 3.2 PROPOSED — no code yet

- **Per-vault PKI key pair** (X25519 encrypt; Ed25519 sign later) with the private key stored *inside* the vault — `v0.32.1 §02.3`, "P-155/P-157", referenced as "doc 422 — Vault Discovery and Public Keys". **Does not exist.**
- **Encrypt-to-vault** (ECDH→HKDF→AES-256-GCM sealed box; payload `ephemeral_pubkey || iv || ciphertext || tag`).
- **`enum_key = HKDF(read_key, info='sg-vault-v1:inbox-enum-key')`** + `H(enum_key)` / `H(append_token)` manifest fields.
- **append / inbox / processed / purge** endpoints; write-side capacity cap.
- **Template-vault provisioning** + the drain loop + blind-relay topology.

> Net: the vault-PKI registry is effectively **"P-157 encrypt-to-vault" + a new
> append/inbox transport + a vault-resident key directory.** None of the three
> halves is built yet.

## 4. The capability model (why "registry" stops meaning "trusted server")

From `v0.32.1/02__crypto-keys-and-pki.md` + `00__README.md` — the four
non-overlapping tiers, each gated separately:

| Capability | Form | Holder | CAN | CANNOT |
|---|---|---|---|---|
| **append token** | `H(recipient pubkey)` — deterministic, non-secret | any sender / relay | append ciphertext to inbox | list · fetch · decrypt · purge |
| **enum key** | `HKDF(read_key, 'sg-vault-v1:inbox-enum-key')` | drainer / relay | list · fetch · mark-processed | decrypt · purge |
| **private key** | per-vault key, a **file inside the vault** | recipient only | decrypt (client-side) | — (never a server gate) |
| **write_key** | EXISTS — PBKDF2, hash in `vault_pointer.json` | vault owner | purge · write the real tree | — |

The security result (stated in the README): **the component that handles the
most traffic — a relay — holds the least secret (no private key).** A registry
built this way never has to be trusted with reads: it routes by a **non-secret
address** and stores opaque bytes. "You cannot write unencrypted" is a property
of the honest client, **not** server-enforced — the server cannot tell ciphertext
from plaintext.

## 5. How a "registry" actually works in this model

Synthesised from `v0.32.1/03__provisioning-and-topologies.md`:

1. **Identity = vault + key pair.** Provisioning a vault generates its X25519 key
   pair; the private key is written *into* the vault (encrypted under its own read
   tree), the public key is publishable.
2. **The public key is the address.** `append_token = H(pubkey)` simultaneously
   (a) authorises who may write, (b) names the destination inbox folder, and
   (c) tells the recipient which key pair decrypts what landed there.
3. **Discovery is a vault read, not a server query.** A vault can expose its
   public key the same way public-vault-previews expose content — so "look up
   Alice's key" becomes "read Alice's vault's published public key," with the
   transparency-log / KAT machinery providing verifiability.
4. **Self-bootstrapping trust.** A first message carries the sender's own public
   key inside the encrypted payload; after decrypt the recipient can reply. The
   directory is **emergent from conversations**, not a prerequisite for them.
5. **Transport is interchangeable.** Because a message is opaque ciphertext
   addressed by a non-secret token, even a plain SMTP server can relay it — proof
   the transport never needs to decrypt.

## 6. Relationship to this (tools) repo's PKI plan

This concept is the **"why"** behind the migration plan in
`…__pki-from-send__migration-map.md`. Concretely it reshapes that plan's open
backend decision (B.4 / B.7-#1):

- The migration map asked: *client-only registry, reuse Send's lambda, or new
  service?* The vault-based model gives a **fourth answer**: the registry is
  **vaults + a thin verifiable index**, which fits this repo's static/CDN, "no
  server processing" rule far better than a centralised key table.
- It strengthens the **Ed25519/X25519 direction** (B.7-#2): per-vault X25519 for
  encryption + Ed25519 for signing aligns with this repo's existing `sg-ssh`
  Ed25519 keygen and the auth-mvp Phase 2 vault identity key, and with the vault
  client (`core/vault-client`) as the private-key container.
- It reuses pieces already mapped: `vault-schema-pki-key` (display),
  `core/vault-client` (encrypted private-key storage), `sg-crypto` (AES-GCM data
  layer for the sealed box).

**PROPOSED tools-repo shape** (extends the migration map; does not exist yet):
- `core/pki/sg-pki-vault-keys.js` — per-vault X25519/Ed25519 keygen; store/load private key as a vault file.
- `core/pki/sg-pki-seal.js` — encrypt-to-vault (ECDH→HKDF→AES-GCM) + open.
- `core/pki/sg-pki-address.js` — `append_token = H(pubkey)` + `enum_key` derivation (with the mandatory domain-separation label + KAT vectors).
- `<sg-pki-vault-directory>` — discover/verify a vault's published public key (reusing `vault-schema-pki-key` for display).
- A `pki-registry` tool composing the above with the existing publish/lookup/log components.

## 7. Open questions (need a human call)

1. **Centralised vs vault-native registry** — does the tools repo target the
   vault-native model directly, keep the `XX-XXXX` central registry as a
   convenience index over it, or support both?
2. **Encryption curve** — X25519 (as the v0.32.1 brief specifies) vs the admin
   PoC's RSA-OAEP/ECDH-P256. The vault thread says X25519; the implemented PoC
   says RSA/EC. Pick one identity curve for the tools repo (recommend X25519 +
   Ed25519 to match the vault thread and `sg-ssh`).
3. **KAT scope** — the cross-language (JS↔Python) KAT is "non-optional" in the
   Send brief; in a JS-only static repo it becomes JS-only, but we should still
   pin exact framing (`ephemeral_pubkey || iv || ciphertext || tag`, 12-byte IV)
   to stay wire-compatible with sgit-ai. Confirm we want that interop.
4. **First consumer** — vault-chat (`v0.27.80`) is the obvious first user. Build
   the registry against a concrete chat slice, or as a standalone primitive first?
