# Arch Brief — Running models in the browser (no Ollama, no server)

**Version:** v0.2.75 · **Date:** 13 Aug 2026 · **Role:** Architect
**Question:** how do we run models locally in the browser, what do we already have, what does the 2026 ecosystem look like, and what is Chrome actually shipping?
**Status of §2 (what we have):** ✅ code-verified, exists today. **Status of §5–§9 (proposals):** 🟡 **PROPOSED — does not exist yet.**

---

## TL;DR

1. **We already run models in the browser today** — two shipped MVPs: **`sg-whisper`** (speech-to-text, ONNX/transformers.js) and **`sg-tts`** (Kokoro-82M TTS, ONNX, 8-worker pool), plus `core/pyodide` (CPython in WASM) and `sg-wasm-cache` (weight persistence).
2. **But we run zero *language* models in the browser.** Everything local is speech. There is no WebLLM, no text generation, no `navigator.gpu` request anywhere in the codebase.
3. **We are leaving 10–100× on the table:** both MVPs run **WASM-only**. Neither passes `device: 'webgpu'`. And `sg-whisper` pins **`@xenova/transformers@2.17.2`** — a package scope that is now frozen; the maintained line is **`@huggingface/transformers@4.2.0`** (verified against npm today).
4. **Chrome shipped a built-in LLM.** `LanguageModel` (Gemini Nano) is in **Chrome 148 stable, desktop only**, with a whole API family beside it. It is excellent as the *first tier of a fallback chain* and unusable as a *sole* dependency.
5. **Recommendation:** build **`core/sg-local-llm`** — one provider interface over a fallback chain **Chrome built-in → WebLLM (WebGPU) → wllama (WASM)** — and pay off the two cheap upgrades in §8 first.

| **`tests/kokoro-probe.html`** | `tests/` | The **probe pattern**: step-by-step CDN reachability → dynamic import → export shape → generation, each with timings. Exactly how to de-risk a new runtime. |

**Empirical numbers we already measured** (recorded in the `sg-tts` header, probe dated 2026-04-15):
- Kokoro on **WASM**: ~**0.14–0.45× realtime per worker**; **~0.85× aggregate at 8 workers**.
- **Wall clock ≈ the longest single sentence** → split text aggressively for throughput.
- `esm.sh` rewrites transitive bare specifiers automatically; jsDelivr would need an import map.

**The honest gaps:**
- **No LLM.** Speech in, speech out — no text generation, no chat, no embeddings.
- **No WebGPU anywhere.** `sg-tts`'s worker calls `KokoroTTS.from_pretrained(..., { dtype: 'q8' })` with no `device`; `sg-whisper` calls `pipeline()` with no `device`. Both are CPU/WASM.
- **`kokoro-js` is imported unpinned** (`https://esm.sh/kokoro-js`) — a floating dependency against the repo's immutable-versioning rule, and a supply-chain surface. Current release is 1.2.1.

## 3. The 2026 landscape — five ways to run a model in a browser tab

Versions below verified directly against the npm registry today; status/perf figures are from the cited sources.

| Runtime | Backend | Format | Size range | Speed | Catalogue | Choose when |
|---|---|---|---|---|---|---|
| **WebLLM** `@mlc-ai/web-llm` **0.2.84** | WebGPU | MLC-compiled (q4f16) | 78 MB – 5.06 GB | **~71 tok/s** (Phi-3.5-mini), ~41 tok/s (Llama-3.1-8B) on M3 Max | 32 curated | **Default for chat.** Latency matters, users have WebGPU |
| **Transformers.js** `@huggingface/transformers` **4.2.0** | **WebGPU + WASM fallback** | ONNX (q4/fp16) | 120 MB – 3 GB | 40–60 tok/s on WebGPU | 16 curated + any ONNX on the Hub | **Already our stack.** Vision input, custom models, automatic fallback |
| **wllama** `@wllama/wllama` **3.5.1** | WASM (CPU), optional WebGPU | **GGUF** | 70 MB – 5.41 GB | 5–15 tok/s CPU | 30 curated + **160k+ GGUF on the Hub** | **Universal fallback.** Any device, any fine-tune, WebGPU blocked |
| **LiteRT-LM** (Google, early preview) | WebGPU (Gemma 4); CPU for Qwen3-0.6B | `.litertlm` | 614 MB – 3.0 GB | — | 3 (Gemma 4 E2B/E4B, Qwen3 0.6B) | Experimenting with Gemma 4 via Google's own engine |
| **Chrome built-in AI** | Chrome-managed (Gemini Nano) | n/a | **zero app-side download** | — | 1 | **First tier of a fallback chain** (see §4) |

**The finding that shapes our design:** all five converge on essentially the **same `LanguageModel`-shaped interface**, which is why a thin provider abstraction over them is cheap rather than speculative.

**Memory nuance worth knowing:** WebLLM loads the whole model into **JS heap** before handing it to the GPU; wllama streams from **OPFS** into GPU buffers through small transfer buffers — materially more memory-efficient on constrained devices. GGUF can also ship as a single file, whereas ONNX and MLC weights are mandatorily sharded.

**Platform substrate:**
- **WebGPU** — W3C **Candidate Recommendation, March 2026**; **>84% global support**. This is now a reasonable default with a fallback, not a bet.
- **WebNN** (`navigator.ml`, NPU access) — **Chrome origin trial M147–M149**, CR Jan 2026, no Safari/Firefox. **Not production; realistic default ~2027.** Track it, don't build on it.

## 4. Chrome and embedded LLMs — what's actually going on

You remembered correctly: this started as a Canary/flag experiment. It has since **shipped**.

**Status:** the **Prompt API** landed behind a flag in **Chrome 138**, ran as an Origin Trial, and the `LanguageModel` global is **supported from Chrome 148 (May 2026)** on **desktop only — Windows, macOS, Linux, Chromebook Plus**. **Not implemented in Edge, Firefox, or Safari.**

**It is a whole family, not one API** — all backed by **Gemini Nano**, all built into the browser:

| API | Purpose |
|---|---|
| **`LanguageModel`** (Prompt API) | General-purpose prompting — the one that matters to us |
| `Summarizer` | Summaries in several formats |
| `Translator` / `LanguageDetector` | In-browser translation + language ID |
| `Writer` / `Rewriter` | Generate / re-tone / re-length text |
| `Proofreader` | Grammar and readability |

**The `LanguageModel` surface** (this is genuinely well-designed):

```js
if (!('LanguageModel' in self)) { /* fall through to WebLLM */ }

// 'available' | 'downloadable' | 'downloading' | 'unavailable'
const status = await LanguageModel.availability();

const session = await LanguageModel.create({
  initialPrompts: [{ role: 'system', content: 'You are a log analyst.' }],
  expectedInputs:  [{ type: 'text' }, { type: 'image' }, { type: 'audio' }],
  monitor: m => m.addEventListener('downloadprogress', e => ui(e.loaded)),
});

const answer = await session.prompt('…', {
  responseConstraint: { type: 'object', properties: { … } },  // JSON Schema-enforced output
  signal: controller.signal,
});
for await (const chunk of session.promptStreaming('…')) { … }

session.contextUsage; session.contextWindow;   // token accounting
const forked = session.clone();                // branch a conversation cheaply
session.destroy();                             // free device memory
```

Notably it supports **multimodal input (text, image, audio)**, **JSON-Schema-constrained output** (`responseConstraint`), response prefilling, abort signals, and context accounting — a better-specified surface than most hosted APIs.

**The strategic read.** The appeal is enormous: **your app ships and downloads zero model bytes**, and inference is free and private. But it is **one vendor, one browser, desktop-only, browser-gated availability, and a small fixed model you cannot choose**. `availability()` can return `unavailable` on perfectly good hardware. So:

> **Use Chrome built-in as the opportunistic first tier of a fallback chain — never as the sole engine.** Design the abstraction first; treat Gemini Nano as a free fast path when it happens to be there.

## 5. 🟡 PROPOSED — recommended architecture

```
                    core/sg-local-llm  (NEW — one interface, four providers)
                             │
   ┌──────────────┬──────────┴──────────┬───────────────────┐
   ▼              ▼                     ▼                   ▼
Chrome AI      WebLLM              Transformers.js       wllama
(Gemini Nano) (WebGPU, chat)      (ONNX, WebGPU+WASM,   (WASM/GGUF,
 0 bytes       fast                vision, ours already)  universal)
   │              │                     │                   │
   └──────────────┴─────────┬───────────┴───────────────────┘
                            ▼
              core/sg-model-cache  (NEW — OPFS + Cache API, multi-GB)
                            ▼
              sg-wasm-cache (EXISTS) · sg-vfs/IndexedDB (EXISTS)
```

**`core/sg-local-llm`** — provider-agnostic, mirroring the shape the ecosystem already converged on:

```js
const llm = await createLocalLlm({
  prefer: ['chrome-ai', 'webllm', 'wllama'],   // ordered fallback
  model:  'qwen3-1.7b-q4',                     // ignored by chrome-ai
  onProgress: ({ stage, loaded, total }) => …,
});
llm.provider;                    // which tier actually won
await llm.prompt(text, { responseConstraint });
for await (const c of llm.promptStreaming(text)) { … }
await llm.capabilities();        // { webgpu, webnn, vram, quota, multimodal }
```

Deliberately adopt **Chrome's `LanguageModel` vocabulary** (`availability()`, `create()`, `prompt()`, `promptStreaming()`, `responseConstraint`) as our interface, so the Chrome provider is a near-passthrough and the others are adapters. That is standards-alignment for free.

**`core/sg-model-cache`** — `sg-wasm-cache` handles *versioned library modules*; multi-GB *weights* need more: **OPFS** for large sharded files, `navigator.storage.persist()` to resist eviction, `navigator.storage.estimate()` for quota UX, resumable downloads, and per-model eviction. Note transformers.js and WebLLM already cache weights internally — our layer is for *visibility, quota control, and pre-warming*, not for replacing them.

## 6. 🟡 PROPOSED — model shortlist (you said a large download is acceptable)

| Model | ~q4 size | Why |
|---|---|---|
| **Qwen3 0.6B / 1.7B** | ~0.4 / ~1.1 GB | Best small-end quality-per-byte; 1.7B fits comfortably on 6 GB devices |
| **Gemma 3 1B / 4B** | ~0.8 / ~2.6 GB | 4B is multimodal (text+image), 128K context, 140+ languages |
| **Gemma 4 E2B / E4B** | 614 MB – 3.0 GB | Released **2 Apr 2026**: MoE, trimodal on the small sizes, **Apache 2.0**. Available via LiteRT-LM |
| **SmolLM3-3B** | ~1.9 GB | Beats Llama-3.2-3B and Qwen2.5-3B at 3B scale; competitive with 4B-class |
| **Phi-4-mini (3.8B)** | ~2.4 GB | Reported as the smartest model still usable on flagship phones (~13–18 tok/s) |
| **Llama 3.2 1B** | ~0.8 GB | Widely pre-compiled for WebLLM; safe baseline |

**Default proposal:** **Qwen3-1.7B-q4** as the shipped default (fits nearly everything, genuinely useful), with **Phi-3.5-mini / Llama-3.1-8B** offered as "big download, best quality" options for desktop WebGPU users, and **Gemini Nano free** whenever Chrome offers it.

## 7. The hard problems

| Problem | Reality | Mitigation |
|---|---|---|
| **First-load is gigabytes** | 1–5 GB before the first token | Reuse the **`voice-memo` staged health-check UX**; per-shard progress; resumable; make it an explicit opt-in with the size shown up front |
| **Storage eviction** | Browsers evict Cache/OPFS under pressure — a 3 GB download silently vanishing is the worst possible UX | `navigator.storage.persist()`, show `estimate()`, verify-before-use, cheap re-warm |
| **WebGPU absent** (~16% of users) | No GPU path at all | wllama WASM tier; be honest about tok/s in the UI |
| **Memory ceilings** | WebLLM stages the whole model through the JS heap; iOS tabs are tightly capped | Prefer wllama/OPFS streaming on mobile; cap model size by device |
| **wllama multithreading wants COOP/COEP** | Same cross-origin-isolation trap we deliberately dodged for FFmpeg WASM | Run wllama **single-threaded** by default — keep the static-CDN deploy model intact. Do not adopt COOP/COEP for this |
| **Chrome AI is unpredictable** | `availability()` can say `unavailable` on capable hardware | Never branch UI on the provider; always have tier 2 warm |
| **Background tabs throttle** | Long generations stall when backgrounded | Workers + progress + resumability; warn on navigate-away |
| **WebNN is not ready** | Origin trial only, no Safari/Firefox | Track for 2027; do not design around it |

## 8. Cheap wins on what we already ship (do these first)

These are small, high-value, and independent of the LLM work:

1. **Migrate `sg-whisper` to `@huggingface/transformers@4.2.0` + `device: 'webgpu'` + `dtype: 'q4'`.** We are pinned to `@xenova/transformers@2.17.2` — an abandoned scope, two majors behind, **pre-WebGPU**. WebGPU support landed in v3 (Oct 2024) and is reported as up to **100× faster than WASM**. Keep WASM as automatic fallback, which v3+ does for us. This is likely the single biggest performance change available anywhere in the repo.
2. **Pin `kokoro-js`** to `https://esm.sh/kokoro-js@1.2.1` — the current unpinned import violates our immutable-versioning rule and can break without a commit. Then try `device: 'webgpu'` against the measured WASM baseline (0.14–0.45× realtime/worker) — we have a real before-number, which makes this a clean experiment.
3. **Add a `capabilities()` probe** (`navigator.gpu`, `navigator.ml`, `LanguageModel` in self, `storage.estimate()`) to the existing health-check flow, so every tool can degrade knowingly.

## 10. Open decisions for you

1. **Default model** — Qwen3-1.7B-q4 as proposed, or bias larger (Phi-3.5-mini / Llama-3.1-8B) given "a big download is fine"?
2. **Mobile** — support it (constrains us to ≤2 GB and wllama/OPFS), or desktop-first?
3. **Provider order** — is Chrome-AI-first right? It is free and instant but the least controllable and least reproducible; a case exists for WebLLM-first so behaviour is consistent for everyone.
4. **Scope** — chat/generation only, or also **local embeddings** (transformers.js does these well today and would enable offline semantic search over the VFS)?
