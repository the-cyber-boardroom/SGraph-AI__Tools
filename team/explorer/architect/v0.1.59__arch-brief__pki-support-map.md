## 0. Why this document exists

PKI-relevant capability in this repo is **real but fragmented**. There was no
single place tying together SSH key generation, the vault PKI schema/renderer,
the `sgit pki` CLI skill, and the unbuilt auth-mvp Phase 2 identity-key work.
This brief is that single place: a code-verified map of what exists today, what
does **not** exist, and the recommended direction.

> **Reality-document rule applies.** Everything in §2 is verified against the
> code in the tree as of 6 June 2026. Everything in §4 (Roadmap) is labelled
> **PROPOSED — does not exist yet.**

---

## 1. Executive summary

| Question | Answer |
|---|---|
| Is there real public-key crypto in the repo? | **Yes** — Ed25519 key generation (SSH tool + planned vault identity key). |
| Is there classical X.509 / CA / CSR PKI? | **No.** No certificate, CSR, CA, or chain-validation code exists anywhere. |
| Is most of the "crypto" actually PKI? | **No.** The bulk is **symmetric** AES-256-GCM (file/vault/Send encryption). |
| Is there a CLI PKI story? | **Documented only** — the external `sgit pki` subcommands (skill doc), not implemented in this repo. |
| Is there a vault identity key? | **Planned, not built** — auth-mvp Phase 2 spec defines an Ed25519 vault identity key; the renderer for it exists, generation does not. |

**One-line takeaway:** the platform has the building blocks for an
**Ed25519-based identity/signing PKI** (browser Web Crypto + a vault to hold the
private key + a renderer to display public keys), but the key-generation glue,
signing/verification, and any X.509 interop are not yet built.

## 2. What exists today (code-verified)

### 2.1 Core modules

| Asset | Path | PKI relevance |
|---|---|---|
| `sg-ssh.js` | `core/ssh/v1/v1.0/v1.0.0/sg-ssh.js` | **Closest thing to PKI code.** `generateSSHKeyPair()` generates an **Ed25519** key pair via Web Crypto (`crypto.subtle.generateKey({name:'Ed25519'})`), exports the public key in **OpenSSH wire format** and the private key as an **OpenSSH PEM** (`openssh-key-v1`, `none` cipher). All in-browser; private key never leaves the device. Ed25519 only (Send also supports RSA-4096 — not ported here). |
| `sg-crypto.js` | `core/crypto/v1/v1.0/v1.0.0/sg-crypto.js` | **Not PKI.** AES-256-GCM symmetric file encryption. Listed only to mark the boundary: this is the bulk of the "crypto" surface and it is symmetric. |
| `sg-send-crypto.js` (+ `sg-send-upload.js`, `wordlist.js`) | `core/send-crypto/v1/v1.0/v1.0.0/` | **Not PKI.** PBKDF2-SHA256 + AES-256-GCM token/transfer crypto for SG/Send interop. |
| `sg-vault-client.js` | `core/vault-client/v1/v1.0/v1.0.0/sg-vault-client.js` | **Not PKI**, but the **container** that will hold the PKI identity key (PBKDF2 + HMAC-SHA256 + AES-256-GCM vault). |

> **No module** anywhere does X.509 parsing/building, CSR generation, CA
> issuance, certificate chain validation, OCSP/CRL, or RSA key handling.

## 3. The gap — what does NOT exist

This list is the value of the map: it states the absences explicitly so no brief
or agent assumes these are shipped.

1. **No Ed25519 *identity*-key generation.** `sg-ssh.js` generates SSH-formatted
   keys; nothing generates the vault identity key in the `pki` schema shape. The
   `generateUserKeyPair()` snippet lives only in the Phase 2 plan.
2. **No signing / verification.** No `sign(data, privateKey)` /
   `verify(data, sig, publicKey)` module exists. The `sgit pki sign/verify`
   verbs are documented but not implemented in-repo.
3. **No asymmetric encryption / E2E messaging.** No "encrypt to recipient public
   key" path. (All shipped encryption is symmetric AES-GCM.)
4. **No X.509 / CSR / CA / chain validation.** Zero classical PKI: no
   certificate parsing or building, no CSR generation, no CA issuance, no
   trust-chain or revocation handling, no RSA.
5. **No fingerprint utility.** The schema renders `fingerprint` /
   `signing_fingerprint` but there is no shared `sha256` fingerprint helper that
   produces them (the Phase 2 plan references `sha256Hex` as a TODO dependency).
6. **No public-key directory / distribution.** No mechanism to publish or look up
   a user's public key by fingerprint (the messaging/verification consumer side).

## 4. Roadmap — PROPOSED (does not exist yet)

A coherent path that turns the building blocks into a usable Ed25519 identity
PKI, ordered cheapest-first. **All items below are PROPOSED.**

1. **`core/sg-pki` module (PROPOSED).** A single home for the asymmetric
   primitives the schema and CLI already imply:
   - `generateIdentityKeyPair()` → Ed25519 JWK + PEM + `sha256` fingerprint
     (lift the Phase 2 `generateUserKeyPair()` snippet out of the plan).
   - `sign(bytes, privateJwk)` / `verify(bytes, sig, publicJwk)`.
   - `fingerprint(publicKeyRaw)` — the shared helper §3.5 is missing.
   - Mirror the `sg-ssh.js` style (pure JS, Web Crypto, no UI, named exports).
2. **Wire `sg-vault-picker` Stage 3 to `sg-pki` (PROPOSED).** `createVault()`
   generates the identity key into the vault `pki` schema. The
   `<vault-schema-pki-key>` renderer already displays the result — close the
   loop generate → store → render.
3. **auth-mvp checks 8–11 (PROPOSED).** Light up the already-specified
   PKI-key-generation / vault-write / vault-read checks against the real module.
4. **Asymmetric messaging + public-key distribution (PROPOSED).** The
   `encrypt --recipient <fp>` / `decrypt` half of the `sgit pki` feature set,
   plus a way to resolve a fingerprint to a public key.
5. **X.509 interop (PROPOSED, lowest priority).** Only if a concrete consumer
   needs certificates (code signing, S/MIME). Currently **no** driver for it —
   do not build speculatively.
