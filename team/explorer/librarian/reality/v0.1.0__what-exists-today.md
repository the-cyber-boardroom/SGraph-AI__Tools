## How this document is organised

The reality document was split into three parts on 26 Apr 2026 because the single file had grown to ~568 lines / ~220 KB. New entries should be appended to the part that matches what changed; the four-row cover table below is the entry point.

| Part | Scope | When to update it |
|---|---|---|
| **[Part 1 — Libraries](./v0.1.0__what-exists-today__1__libraries.md)** | Deployable folder layout, core modules, skills library, components | Adding/changing a `core/` module or a `components/` web component |
| **[Part 2 — Tools, Manifests, Tests](./v0.1.0__what-exists-today__2__tools.md)** | Standalone tools, shared assets, i18n, manifest schemas, per-tool manifests, build scripts, browser tests | Adding/changing a `tools/` entry, a manifest, or a test page |
| **[Part 3 — Operations and Plans](./v0.1.0__what-exists-today__3__operations.md)** | CI/CD, SEO, team folder structure, configuration, sgraph.ai reuse plan | Touching CI/CD workflows, root files, team structure, or `pyproject.toml` |

## Rules

1. **Update the matching part in the same commit as the code change.** This is the existing rule from `.claude/CLAUDE.md`; only the file path changed.
2. **Cross-link if a change affects more than one area.** A new component plus the tool that uses it should land in both Parts 1 and 2 with a one-line reference.
3. **The "Verified by" paragraph above is the cumulative summary across all three parts.** Append a short fragment whenever you bump any of the three files so a reader can see the recent direction of travel without opening every part.
