## 1. Critical Structural Problem: Missing `sgraph_ai_tools__static/` Base Folder

**What the brief says:** The arch brief (section "Phase 1: Set Up the Structure") says to create the `sgraph_ai_tools__static` repo with the three-tier folder structure. The technical bootstrap guide (v0.11.12) shows the structure explicitly as `sgraph_ai_tools__static/` containing `core/`, `components/`, and `tools/`.

**What exists today:** The code sits directly in the repo root:
```
/core/crypto/v1.0.0/sg-crypto.js      <-- WRONG
/components/header/v1.0.0/sg-header.js <-- WRONG
/tools/index.html                       <-- WRONG
```

**What it should be (using IFD nested version paths):**
```
/sgraph_ai_tools__static/core/crypto/v1/v1.0/v1.0.0/sg-crypto.js
/sgraph_ai_tools__static/components/header/v1/v1.0/v1.0.0/sg-header.js
/sgraph_ai_tools__static/tools/index.html
```

**Why this matters:** Every SG project follows the convention of `{package_name}/` as the base folder for deployable code:
- SG/Send: `sgraph_ai_app_send__ui__user/`, `sgraph_ai_app_send__ui__vault/`, `sgraph_ai_app_send__ui__workspace/`
- SG/Website: `sgraph_ai__website/`

The `sgraph_ai_tools__static/` folder is what gets synced to S3. Everything else (team/, briefs/, .claude/, .github/) stays in the repo but never deploys. Without this separation, you can't write a clean CI/CD pipeline that says "sync this folder to S3".

**Action required:** Move all `core/`, `components/`, and `tools/` folders under a new `sgraph_ai_tools__static/` directory, and restructure version folders to use the IFD nested path convention (`v{major}/v{major}.{minor}/v{major}.{minor}.{patch}/`).

## 2. Critical Structural Problem: Version Paths Must Follow IFD Convention

**What exists today:**
```
core/crypto/v1.0.0/sg-crypto.js       <-- WRONG: flat version folder
```

**What it should be:**
```
sgraph_ai_tools__static/core/crypto/v1/v1.0/v1.0.0/sg-crypto.js    <-- IFD nested path
```

**This is how every SG project versions folders.** The IFD nested path convention is `v{major}/v{major}.{minor}/v{major}.{minor}.{patch}/`:

| Version | IFD Path |
|---------|----------|
| `v1.0.0` | `v1/v1.0/v1.0.0/` |
| `v1.0.1` | `v1/v1.0/v1.0.1/` |
| `v1.1.0` | `v1/v1.1/v1.1.0/` |
| `v0.2.0` | `v0/v0.2/v0.2.0/` |

**Reference:** The `deploy_static_site.py` script in SG/Send uses `version_to_ifd_path()` which converts versions this way:
```python
def version_to_ifd_path(version):
    # v0.2.0 -> v0/v0.2/v0.2.0
    # v1.2.3 -> v1/v1.2/v1.2.3
```

This nesting matters because:
- It groups all minor versions under their major version folder
- It groups all patch versions under their minor version folder
- S3 paths match: `websites/sgraph-tools/dev/releases/v0/v0.1/v0.1.0/`

## 3. Critical Missing Piece: `.github/workflows/` CI Pipeline

**What exists today:** No `.github/` folder at all.

**What the SG/Send project has (that you should replicate):**

The Send project has a mature CI pipeline pattern:

| Workflow | What It Does |
|----------|-------------|
| `ci-pipeline.yml` | Base pipeline: run tests, auto-increment tag, deploy Lambda |
| `ci-pipeline__dev.yml` | Dev branch trigger — calls base pipeline |
| `ci-pipeline__main.yml` | Main branch trigger — calls base pipeline with different params |
| `deploy-ui-user.yml` | Deploys User UI to S3 + CloudFront (path-scoped trigger) |
| `deploy-ui-vault.yml` | Deploys Vault UI to S3 + CloudFront |
| `deploy-ui-workspace.yml` | Deploys Workspace UI to S3 + CloudFront |
| `deploy-website.yml` | Deploys sgraph.ai static site |

**Key patterns the Tools project MUST adopt:**

### 3a. Path-Scoped Triggers
Each workflow triggers only on changes to its folder:
```yaml
on:
  push:
    branches: [dev, main]
    paths:
      - 'sgraph_ai_tools__static/**'
      - '.github/workflows/deploy-tools.yml'
```

### 3b. S3 Path Isolation by Environment
```
websites/sgraph-tools/dev/     — dev branch (automatic on push)
websites/sgraph-tools/main/    — main branch (automatic on push)
websites/sgraph-tools/prod/    — production (manual workflow_dispatch)
```

### 3c. Python Deploy Script (Reuse Existing)
SG/Send uses `scripts/deploy_static_site.py` which handles:
- Content-type detection
- Cache-Control headers (HTML: 300s, CSS/JS: 86400s, images: 604800s)
- Release versioning: `websites/{site}/{env}/releases/{ifd_path}/`
- **`latest/` alias:** `websites/{site}/{env}/latest/` — **created in CI only via `aws s3 sync` from the release folder, never in the git repo**
- CloudFront invalidation

**This script can be copied directly from the Send repo and reused.** Don't write a new one.

### 3d. i18n Page Generation in CI
Send has `scripts/generate_send_i18n_pages.py` which generates locale-specific HTML at CI time. The Tools project should have an equivalent. Key details:
- Source locale: `en-gb/` (in git)
- Generated locales: `en-us/`, `fr-fr/`, `de-de/`, `es-es/` (CI-generated, never in git)
- Start with en-gb + 3-4 locales first, expand to full 17 once working
- Generated folders go in `.gitignore`

### 3e. Auto-Tagging
Send uses `owasp-sbot/OSBot-GitHub-Actions/.github/actions/git__increment-tag@dev` for auto-tagging after tests pass. The Tools project should use the same.

### 3f. Version File
The repo needs a `version` file at the root containing `v0.1.0` (or current version). The CI pipeline reads this to determine the deployment version.

**Minimum viable `.github/workflows/` for Tools:**

```
.github/
  workflows/
    ci-pipeline.yml           # Test + auto-tag
    deploy-tools__dev.yml     # Dev branch trigger
    deploy-tools__main.yml    # Main branch trigger
scripts/
  deploy_static_site.py       # Copied from Send
  generate_tools_i18n_pages.py  # Adapted from Send
```

## 4. The `latest/` Folder: CI-Only, Never in Git

**IMPORTANT:** The `latest/` folder is a CI/deployment concept only. It does NOT exist in the git repository.

**How it works in production:**
1. CI deploys versioned files to S3: `websites/sgraph-tools/{env}/releases/v0/v0.1/v0.1.0/`
2. CI then copies that folder to: `websites/sgraph-tools/{env}/latest/`
3. The `latest/` folder in S3 is overwritten on every deploy

**The deploy script does this (from `deploy_static_site.py`):**
```python
release_prefix = f"s3://{bucket}/websites/{site}/{env_segment}releases/{ifd_path}/"
latest_prefix  = f"s3://{bucket}/websites/{site}/{env_segment}latest/"
run_cmd(["aws", "s3", "sync", release_prefix, latest_prefix, "--delete"])
```

**The repo should NOT have `latest/` folders.** Only versioned folders exist in git.

## 5. IFD Methodology: What the Tools Team Needs to Know

The current code shows the team created files from scratch rather than following IFD principles. Here's what IFD means for the Tools project:

### 5a. What IFD IS
- **Iterative Flow Development** — rapid AI-assisted development preserving developer flow state
- **Folder-based versioning** — `v1/v1.0/v1.0.0/` are physical folders on disk (using nested IFD path convention)
- **Surgical minor versions** — `v1/v1.0/v1.0.1/` contains ONLY the delta from `v1.0.0/`, not a full copy
- **Once deployed, never modified** — content at a pinned version URL is immutable forever

### 5b. What's Missing in the Current Repo
- Flat version folders (`v1.0.0/`) instead of IFD nested paths (`v1/v1.0/v1.0.0/`)
- No `manifest.json` for any module (Send uses these to declare what gets deployed)
- No understanding that minor versions are surgical overrides, not full copies

### 5c. What the Folder Structure Should Look Like

Reference: this matches the Send UI pattern (see `sgraph_ai_app_send__ui__user/v0/v0.2/v0.2.0/` for the canonical example).

```
sgraph_ai_tools__static/
  core/
    crypto/
      v1/
        v1.0/
          v1.0.0/
            sg-crypto.js
            manifest.json         <-- declares exports, dependencies, version
  components/
    header/
      v1/
        v1.0/
          v1.0.0/
            sg-header.js
            sg-header.css
            manifest.json
  tools/
    v0/
      v0.1/
        v0.1.0/
          _common/                <-- shared assets (JS, CSS, images)
            css/
            js/
          en-gb/                  <-- source locale (in git)
            index.html            <-- landing page
            ssh-keygen/
              index.html
          i18n/                   <-- translation JSON files (in git)
            en-us.json
            fr-fr.json
            de-de.json
            es-es.json
          404.html
          index.html              <-- locale redirect
          manifest.json
          robots.txt
          sitemap.xml
```

## 8. Header and Footer Components Need Work

The current `sg-header.js` and `sg-footer.js` are newly created web components. They're reasonable first drafts, but they don't match the Send/Vault patterns:

**Send's component pattern:**
- Each component has separate `.js`, `.html`, and `.css` files
- Components load their template from the `.html` file
- Styles are in a separate `.css` file (not inline in JS)
- Components follow a base class pattern (`send-component.js`)

**What the Tools components do:**
- Inline all CSS inside the JS via template literals
- No separate `.css` files
- No external template loading

**Recommendation for MVP:** The current approach (inline styles in JS) is actually simpler and works fine for these basic components. Don't refactor these now. But when extracting components from Send/Vault (upload-dropzone, file-preview, etc.), follow Send's pattern of separate `.js` + `.css` + `.html` files.

## 9. i18n / Multi-Language Support

**Start small, get it working, then expand.** Don't attempt all 17 locales on day one.

**How Send does it:**
- `en-gb/` folder contains source HTML pages (in git)
- `i18n/*.json` files contain translations per locale (in git)
- CI script generates locale-specific folders (never in git)
- `index.html` at root does locale detection and redirects
- `_common/` holds shared assets (NOT duplicated per locale)

**Starting locale set for Tools MVP:**
```
en-gb    (source template — in git)
en-us    (CI-generated)
fr-fr    (CI-generated)
de-de    (CI-generated)
es-es    (CI-generated)
```

Get these 5 working first. The full 17-locale list can be added later once the i18n pipeline is proven.

**Not all modules need i18n.** Core JS libraries (`sg-crypto.js`, `sg-ssh.js`) don't have HTML to translate. Components with visible text (header, footer) may need i18n JSON files. Tools with full UI pages (ssh-keygen, landing page) need the full `en-gb/` + `i18n/` folder structure with CI-generated locale pages.

**Deciding when a module needs i18n:**
- If the module has HTML that needs to be hydrated into language-specific versions → needs `en-gb/` + `i18n/` + CI generation
- If the module imports translated text from an `i18n/*.json` file at runtime → needs `i18n/` folder only
- If the module is pure JS with no user-facing text → no i18n needed
