## 1. Critical Structural Problem: Missing `sgraph_ai__tools/` Base Folder

**What the brief says:** The arch brief (section "Phase 1: Set Up the Structure") says to create the `sgraph_ai__tools` repo with the three-tier folder structure. The technical bootstrap guide (v0.11.12) shows the structure explicitly as `sgraph_ai__tools/` containing `core/`, `components/`, and `tools/`.

**What exists today:** The code sits directly in the repo root:
```
/core/crypto/v1.0.0/sg-crypto.js      <-- WRONG
/components/header/v1.0.0/sg-header.js <-- WRONG
/tools/index.html                       <-- WRONG
```

**What it should be:**
```
/sgraph_ai__tools/core/crypto/v1.0.0/sg-crypto.js
/sgraph_ai__tools/components/header/v1.0.0/sg-header.js
/sgraph_ai__tools/tools/index.html
```

**Why this matters:** Every SG project follows the convention of `{package_name}/` as the base folder for deployable code:
- SG/Send: `sgraph_ai_app_send__ui__user/`, `sgraph_ai_app_send__ui__vault/`, `sgraph_ai_app_send__ui__workspace/`
- SG/Website: `sgraph_ai__website/`

The `sgraph_ai__tools/` folder is what gets synced to S3. Everything else (team/, briefs/, .claude/, .github/) stays in the repo but never deploys. Without this separation, you can't write a clean CI/CD pipeline that says "sync this folder to S3".

**Action required:** Move all `core/`, `components/`, and `tools/` folders under a new `sgraph_ai__tools/` directory.

## 2. Critical Missing Piece: `.github/workflows/` CI Pipeline

**What exists today:** No `.github/` folder at all.

**What the SG/Send project has (that you should replicate):**

The Send project has a mature CI pipeline pattern:

| Workflow | What It Does |
|----------|-------------|
| `ci-pipeline.yml` | Base pipeline: run tests, auto-increment tag, deploy Lambda |
| `ci-pipeline__dev.yml` | Dev branch trigger — calls base pipeline |
| `ci-pipeline__main.yml` | Main branch trigger — calls base pipeline with different params |
| `deploy-ui-user.yml` | Deploys User UI to S3 + CloudFront (path-scoped trigger) |
| `deploy-ui-vault.yml` | Deploys Vault UI to S3 + CloudFront |
| `deploy-ui-workspace.yml` | Deploys Workspace UI to S3 + CloudFront |
| `deploy-website.yml` | Deploys sgraph.ai static site |

**Key patterns the Tools project MUST adopt:**

### 2a. Path-Scoped Triggers
Each workflow triggers only on changes to its folder:
```yaml
on:
  push:
    branches: [dev, main]
    paths:
      - 'sgraph_ai__tools/**'
      - '.github/workflows/deploy-tools.yml'
```

### 2b. S3 Path Isolation by Environment
```
websites/sgraph-tools/dev/     — dev branch (automatic on push)
websites/sgraph-tools/main/    — main branch (automatic on push)
websites/sgraph-tools/prod/    — production (manual workflow_dispatch)
```

### 2c. Python Deploy Script (Reuse Existing)
SG/Send uses `scripts/deploy_static_site.py` which handles:
- Content-type detection
- Cache-Control headers (HTML: 300s, CSS/JS: 86400s, images: 604800s)
- Release versioning: `websites/{site}/{env}/releases/{version}/`
- Latest alias: `websites/{site}/{env}/latest/`
- CloudFront invalidation

**This script can be copied directly from the Send repo and reused.** Don't write a new one.

### 2d. i18n Page Generation in CI
Send has `scripts/generate_send_i18n_pages.py` which generates locale-specific HTML at CI time. The Tools project should have an equivalent. Key details:
- Source locale: `en-gb/` (in git)
- Generated locales: `en-us/`, `pt-pt/`, `pt-br/`, `de-de/`, etc. (CI-generated, never in git)
- 17 locales total (see Send's `manifest.json` for the full list)
- Generated folders go in `.gitignore`

### 2e. Auto-Tagging
Send uses `owasp-sbot/OSBot-GitHub-Actions/.github/actions/git__increment-tag@dev` for auto-tagging after tests pass. The Tools project should use the same.

### 2f. Version File
The repo needs a `version` file at the root containing `v0.1.0` (or current version). The CI pipeline reads this to determine the deployment version.

**Minimum viable `.github/workflows/` for Tools:**

```
.github/
  workflows/
    ci-pipeline.yml           # Test + auto-tag
    deploy-tools__dev.yml     # Dev branch trigger
    deploy-tools__main.yml    # Main branch trigger
scripts/
  deploy_static_site.py       # Copied from Send
  generate_tools_i18n_pages.py  # Adapted from Send
```

## 3. IFD Methodology: The Tools Team Doesn't Understand It Yet

The current code shows the team created files from scratch rather than following IFD principles. Here's what IFD means for the Tools project:

### 3a. What IFD IS
- **Immutable Forward Deployment** — every version folder is a frozen snapshot
- **Folder-based versioning** — `v1.0.0/`, `v1.0.1/`, `v1.1.0/` are physical folders on disk
- **Surgical minor versions** — `v1.0.1/` contains ONLY the delta from `v1.0.0/`, not a full copy
- **`latest/` alias** — a copy of (or redirect to) the current stable version
- **Once deployed, never modified** — content at a pinned version URL is immutable forever

### 3b. What's Missing in the Current Repo
- No `latest/` folders alongside the version folders
- No `manifest.json` for any module (Send uses these to declare what gets deployed)
- No understanding that minor versions are surgical overrides, not full copies

### 3c. What the Folder Structure Should Look Like
```
sgraph_ai__tools/
  core/
    crypto/
      v1.0.0/
        sg-crypto.js
        manifest.json         <-- declares exports, dependencies, version
      latest/
        sg-crypto.js          <-- copy of v1.0.0
  components/
    header/
      v1.0.0/
        sg-header.js
        sg-header.css
        manifest.json
      latest/
        sg-header.js
        sg-header.css
  tools/
    index.html
    ssh-keygen/
      index.html
```

## 4. Don't Write New Crypto or SSH Code — Use What We've Shipped

**This is the most important section of this debrief.**

The `sg-crypto.js` and `sg-ssh.js` files currently in the Tools repo were written from scratch. While `sg-crypto.js` looks functionally equivalent to Send's `SendCrypto`, and the wire format appears compatible, **we should not be starting with new implementations of security-critical code**.

### What to do instead:

**For the MVP, import crypto and SSH directly from `static.sgraph.ai` or the deployed Send/Vault sites.** These files are already battle-tested and serving real users.

The production code lives at:
- `send.sgraph.ai/_common/js/crypto.js` — the crypto module that's encrypting real files for real users
- The SSH keygen tool already exists at `send.sgraph.ai/tools/ssh-keygen/` in the Send repo

**When we're ready to make these shared libraries (later, not for the MVP):**
1. Copy the exact production file from the Send repo's `_common/js/crypto.js`
2. Convert to ES module (exactly as the bootstrap guide describes)
3. Verify wire-format compatibility with a cross-module test
4. Only then replace Send's bundled copy with a CDN import from Tools

**For the MVP, the Tools site should reference the existing deployed code, not create new versions.** The `sg-crypto.js` that was written may be correct, but it hasn't been through the same testing cycle as the production `SendCrypto`. Same for `sg-ssh.js`.

**Code that should be deleted or clearly marked as "not yet verified against production":**
- `core/crypto/v1.0.0/sg-crypto.js` — replace with exact copy from Send when ready
- `core/ssh/v1.0.0/sg-ssh.js` — the Send version supports both Ed25519 AND RSA-4096; this one only does Ed25519

## 5. What the MVP Should Actually Look Like

The MVP should be simple and focused. Here's what "done" looks like:

### Must Have (MVP)
1. **`sgraph_ai__tools/` base folder** with `core/`, `components/`, `tools/` inside it
2. **`.github/workflows/`** — CI pipeline that: runs tests (even if minimal), auto-tags, deploys to S3
3. **`scripts/deploy_static_site.py`** — copied from Send repo
4. **`version` file** — contains `v0.1.0`
5. **Landing page** at `sgraph_ai__tools/tools/index.html` — lists available tools
6. **SSH Keygen tool** — working, imports from components
7. **Header and Footer components** — shared across tools pages
8. **i18n support structure** — `en-gb/` as source locale, CI generates others
9. **`manifest.json`** per module — declares what the module contains
10. **`latest/` folders** — alongside every version folder

### Should NOT Have (for MVP)
- New crypto implementations (use Send's proven code or link to it)
- Video Splitter (requires FFmpeg WASM — complex, do this after infra is solid)
- LLM Client (requires extraction from workspace — do after infra is solid)
- New components that aren't already proven in Send/Vault

### The Priority Order
1. Fix the structure (sgraph_ai__tools/ folder, latest/ aliases, manifests)
2. CI pipeline (.github/, scripts/, version file)
3. Landing page + SSH keygen tool (working tools that prove the composition model)
4. i18n support (match Send's locale convention)

## 6. Header and Footer Components Need Work

The current `sg-header.js` and `sg-footer.js` are newly created web components. They're reasonable first drafts, but they don't match the Send/Vault patterns:

**Send's component pattern:**
- Each component has separate `.js`, `.html`, and `.css` files
- Components load their template from the `.html` file
- Styles are in a separate `.css` file (not inline in JS)
- Components follow a base class pattern (`send-component.js`)

**What the Tools components do:**
- Inline all CSS inside the JS via template literals
- No separate `.css` files
- No external template loading

**Recommendation for MVP:** The current approach (inline styles in JS) is actually simpler and works fine for these basic components. Don't refactor these now. But when extracting components from Send/Vault (upload-dropzone, file-preview, etc.), follow Send's pattern of separate `.js` + `.css` + `.html` files.

## 7. i18n / Multi-Language Support

Send already supports 17 locales. The Tools project needs to match this from day one.

**How Send does it:**
- `en-gb/` folder contains source HTML pages (in git)
- `i18n/*.json` files contain translations per locale (in git)
- CI script generates `en-us/`, `pt-pt/`, `de-de/`, etc. folders (never in git)
- `index.html` at root does locale detection and redirects

**The locale list (from Send's manifest.json):**
```
en-gb, en-us, pt-pt, pt-br, de-de, de-ch, es-es, es-ar, es-mx,
fr-fr, fr-ca, it-it, nl-nl, pl-pl, hr-hr, ro-ro, tlh
```

**For the Tools MVP:**
- Tools pages should be in `sgraph_ai__tools/tools/en-gb/ssh-keygen/index.html`
- Or adopt a simpler structure: `sgraph_ai__tools/tools/ssh-keygen/en-gb/index.html`
- The CI script generates locale variants
- A root `index.html` handles locale redirect

The exact folder structure for i18n in the Tools context needs an architecture decision. But the principle is: match Send's locale list, generate at CI time, never commit generated files.
