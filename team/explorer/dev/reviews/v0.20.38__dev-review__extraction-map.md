## `__tool.connect({ apiKey, model? }) → Promise<{ connected, model, models[] }>`

**Brief says:** wraps lines 1044-1069. **Actual lines:** 572-606.

The connect handler lives in `connectBtn.addEventListener('click', ...)` at line 572. It:
1. Reads `apiKeyEl.value` and `modelPicker.getModel()` from DOM (lines 573-574)
2. Calls `fetch('https://openrouter.ai/api/v1/models', ...)` (line 581)
3. Dispatches `SGL_LLM.CONNECTED` on the `bus` div (lines 589-592)
4. Calls `savePrefs({ apiKey, model })` which writes to localStorage (line 586)

**Extraction complexity: medium.** The logic is straightforward to extract — the fetch call is already self-contained. Two entanglements to resolve:
- DOM read: `apiKeyEl.value` and `modelPicker.getModel()` must become parameters instead.
- Side effect: `savePrefs()` writes to localStorage; the API method should not do this by default (per project rule 7). The impl brief ignores this — the extracted function should either skip the save or accept an `{ persist: true }` option.
- The brief does not return `models[]` — the current code fetches `/models` but discards the list. Returning it would require parsing `res.json()` which is not done today. This is an API surface expansion, not a simple extraction.

## `__tool.setTemplate({ template }) → { applied, prompt }`

**Brief says:** wraps lines 426-430. **Actual lines:** 315-330 (template button click handlers).

There is no `setTemplate` function. Templates are applied by click handlers attached to buttons created in a `TEMPLATES.forEach()` loop (lines 315-330). Each handler sets `textarea.value = tmpl.prompt` and calls `savePrefs()`.

**Extraction complexity: trivial.** The `TEMPLATES` array is exported from `constants.js` (line 16). The extracted function needs only:
```javascript
function setTemplateImpl({ template }) {
    const t = TEMPLATES.find(t => t.id === template);
    if (!t) throw new Error(`Unknown template: ${template}`);
    // set internal state (prompt), not DOM
    return { applied: true, prompt: t.prompt };
}
```
No DOM access required. The brief's line reference (426-430) is wrong for this version — those lines no longer exist as a discrete block in v0.1.25. The constants are all in constants.js.

## `__tool.generate({ prompt, model?, template?, systemPrompt?, await?: true, renderUI?: false }) → Promise<{ generationId, image?, duration? }>`

**Brief says:** wraps lines 857-1029 (SEND interceptor). **Actual lines:** 434-557.

The SEND interceptor (`bus.addEventListener(SGL_LLM.SEND, async e => { ... })`) runs from line 434 to line 557. This is the most complex extraction.

**What the SEND interceptor does (summarised):**
- Lines 434-448: reads model, apiKey, validates inputs from DOM state
- Lines 449-468: creates a new tab in the right panel via `layout.addTabToStack()` — this is the UI creation step
- Lines 466-468: calls `setupResultFractal()` and `setupLoadingState()` from panels.js — more UI setup
- Lines 473-488: creates a fresh `miniBus` div, appends `sg-llm-request`, fires `SGL_LLM.CONNECTED`
- Lines 491-507: `SGL_LLM.REQUEST_COMPLETE` handler — extracts image, updates UI, extracts `genId`, schedules `detailsCtl.showGeneration()`
- Lines 510-520: error and cancel handlers
- Lines 522-524: stores `cancelFn` in `activeRequests` Map
- Lines 527-556: assembles `messages` array (handles text/image/pdf/text modes), fires `SGL_LLM.SEND` on miniBus

The `renderUI: false` path requires bypassing lines 461-468 entirely (no tab, no fractal layout, no loading state). The `await: true` path requires wrapping the `REQUEST_COMPLETE` listener in a Promise that resolves. Neither of these modes exists today — they are not extractions, they are new code paths.

**The genId capture** (lines 503-506) is non-trivial:
```javascript
const genId = ev.detail?.rawResponse?.id
           ?? ev.detail?.rawChunks?.find(c => c?.id)?.id
           ?? null;
```
This is the only place genId is extracted. It must be part of the returned value from `generate()`.

**Extraction complexity: high.** This is a full refactor, not an extraction. The UI creation and the LLM request logic are tightly coupled in one 123-line handler. `renderUI: false` requires separating them cleanly.

## `__tool.exportPng({ generationId? }) → Promise<{ url, blob, filename, sizeBytes }>`

**Brief says:** wraps lines 898-905 + imgSrcToBlob. **Actual lines:** in `sg-infographic-export.js`, not in infographic-gen.js.

The `imgSrcToBlob()` function lives in:
`components/infographic/sg-infographic-export/v0/v0.1/v0.1.0/sg-infographic-export.js` (lines 27-44)

In infographic-gen.js, export is handled by calling `detailsCtl.setExportSource(src, filename)` (line 507), which delegates to `exportEl.setSource(src, filename)` inside `setupDetailsPanel()` in panels.js (line 258). The actual PNG blob creation is behind the export component's button click — it is not exposed as a programmatic API today.

**Extraction complexity: medium.** `imgSrcToBlob()` is clean and extractable. However, the `src` (image data URL) is held inside the `img` element within a specific `imgPanel` DOM node, identified only by which tab was created. There is no registry of `generationId → imageSrc` today. The `generate()` extraction must create and maintain this registry for `exportPng()` to work.

## `__tool.getCost({ generationId }) → Promise<{ totalCost, model, ... }>`

**Brief says:** wraps `sg-openrouter-generation.fetchGeneration()`.

`fetchGeneration()` lives at line 353 of `sg-openrouter-generation.js` v0.1.1. It is a method on the `SgOpenerouterGeneration` Web Component. Currently it:
1. Sets the value of an `<input>` inside its Shadow DOM
2. Calls `this._fetch(id)` which renders HTML into the Shadow DOM

`_fetch()` does make the actual `GET /api/v1/generation?id=` call (lines 457-490) and stores the result in `this._data`. It returns the data, but currently only renders it into the DOM.

**Extraction complexity: medium.** A clean `getCost()` API could call the OpenRouter generation endpoint directly — a simple `fetch()` with the generation ID and API key. This does not need to go through the Web Component at all. The Web Component is a viewer; the network call is reusable. A standalone helper function would be a cleaner approach than wrapping the component.

## `__tool.getState() → { connected, model, activeGenerations[], templates[], mode }`

No equivalent exists. This is entirely new code. State is currently held in scattered module-level variables:
- `currentMode` (line 88) — 'text' | 'document'
- `currentDoc` (line 89) — loaded document object
- `activeRequests` Map (line 348) — panelEl → cancelFn
- Connection state is implicit: `apiKeyEl.value` is the only source of truth

**Extraction complexity: low (new code).** Creating `getState()` requires reading these variables. The challenge is they are module-level closures, not a class instance. When refactoring to `SgToolApi`, they need to be accessible to the registered method.
