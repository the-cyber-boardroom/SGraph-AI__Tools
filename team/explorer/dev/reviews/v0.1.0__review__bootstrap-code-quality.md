## 2. Module API Design

### sg-crypto.js API

Exports: `ALGORITHM`, `KEY_LENGTH`, `IV_LENGTH`, `isAvailable()`, `requireSecureContext()`, `generateKey()`, `exportKey()`, `importKey()`, `encryptFile()`, `decryptFile()`, `bufferToBase64Url()`, `base64UrlToBuffer()`

**Well-designed.** The API covers the complete encrypt/decrypt lifecycle: generate key, export/import key for storage/transfer, encrypt data, decrypt data. Utility functions for base64url encoding are also exported for consumers who need them.

**Issue — importKey() is decrypt-only (line 82):**
`importKey()` at line 82 creates a key with `['decrypt']` usage only. This means a key imported via `importKey()` cannot be used to call `encryptFile()`. This is a significant API limitation. If a consumer stores a key string (via `exportKey()`), then imports it later (via `importKey()`), they can only decrypt, not encrypt.

This may be intentional for the SG/Send use case (the recipient only decrypts) but it is undocumented. The JSDoc at line 74 says "Imported key (decrypt-only)" which is correct but could easily be missed. A consumer calling `encryptFile(importedKey, data)` will get a cryptic Web Crypto error at runtime, not a clear message.

**Recommendation:** Either add a second parameter to control usages, or provide an `importKeyForEncryption()` function, or at minimum add a prominent warning in the JSDoc.

**Missing export:** There is no `encrypt()`/`decrypt()` pair for arbitrary data (strings, JSON). `encryptFile()` and `decryptFile()` work on `ArrayBuffer`/`Uint8Array`. A consumer wanting to encrypt a string must manually encode with `TextEncoder`. Consider adding convenience functions or renaming to make the ArrayBuffer requirement clearer (though "File" in the name does hint at binary data).

### sg-ssh.js API

Single export: `generateSSHKeyPair(options)`

**Well-designed for its scope.** The options pattern is extensible. The return type `{publicKey, privateKey}` is clean.

**Missing exports that may be needed later:**
- No way to parse or validate an existing SSH key
- No RSA key generation (the BRIEF_PACK.md at line 88 mentions "Ed25519/RSA SSH key generation" but only Ed25519 is implemented)
- No key fingerprint calculation (the SSH keygen tool calculates it inline at lines 297-303 of the tool HTML, duplicating logic that should be in the module)

**Recommendation:** Extract the fingerprint calculation from `tools/ssh-keygen/index.html` lines 297-303 into `sg-ssh.js` as an exported function like `calculateFingerprint(publicKeyString)`.

### sg-header.js / sg-footer.js API

Each exports a single Web Component class. The component self-registers via `customElements.define()` at the module level.

**Concern — side effects on import (lines 95 and 62 respectively):** Importing the module immediately registers the custom element as a side effect. This means you cannot import the class without registering it. If a consumer wanted to extend or wrap the class before registration, they cannot. This is a common Web Components pattern and acceptable, but worth noting.

## 3. Crypto Module Assessment

### Extraction Fidelity

The module header (line 2-3) states it was "Extracted from SG/Send (v0.2.0), converted to ES module." Without access to the original SG/Send source, I cannot verify extraction fidelity directly. However, the API surface matches what the architecture brief describes at line 15-16 (crypto operations: encrypt, decrypt, generate key).

### API Quality

The encryption scheme is sound:
- **AES-256-GCM** (line 19): Authenticated encryption. Good choice. GCM provides both confidentiality and integrity.
- **12-byte IV** (line 25): Standard for AES-GCM. Correct.
- **Random IV per encryption** (line 93): `crypto.getRandomValues()`. Correct. Each encryption gets a unique IV.
- **IV prepended to ciphertext** (lines 99-102): Standard pattern. The decryption side correctly extracts the IV (lines 113-114).

### Potential Issues

**No input validation.** None of the functions validate their inputs:
- `encryptFile()` (line 92): Does not check if `key` is a valid CryptoKey or if `plaintext` is an ArrayBuffer/Uint8Array. Will throw a generic Web Crypto error.
- `decryptFile()` (line 111): Does not check if `encrypted` has at least `IV_LENGTH` bytes. If passed a buffer shorter than 12 bytes, `ciphertext` at line 114 would be an empty array, leading to an opaque decryption error.
- `importKey()` (line 76): Does not validate the base64url string. `base64UrlToBuffer` will silently produce garbage from malformed input, and `importKey` will then throw.
- `bufferToBase64Url()` (line 127): Does not check if `buffer` is actually an ArrayBuffer. Will throw "bytes is not iterable" or similar.

**Recommendation:** Add input validation with clear error messages for at least `encryptFile`, `decryptFile`, and `importKey`. These are the functions most likely to receive bad input from consumers.

**No error wrapping.** Web Crypto API errors are notoriously unhelpful ("The operation failed for an operation-specific reason"). Wrapping these in more descriptive errors would improve the developer experience.

## 4. SSH Module Assessment

### Ed25519 Key Generation Correctness

The key generation at lines 26-29 uses `crypto.subtle.generateKey({ name: 'Ed25519' })` which is correct for browsers that support it (Chrome 113+, Edge 113+, not yet in Firefox as of early 2026).

**Browser compatibility concern:** Ed25519 support in Web Crypto is not universal. The module does not check for Ed25519 availability before attempting generation. Firefox and Safari have limited/partial support. The `isAvailable()` function in sg-crypto.js checks for `crypto.subtle` generally, but there is no equivalent check in sg-ssh.js for Ed25519 specifically. A call to `generateSSHKeyPair()` in an unsupported browser will throw an opaque error.

**Recommendation:** Add an `isEd25519Available()` check, or a try/catch with a clear error message.

### OpenSSH Public Key Format (lines 51-67)

The format is correct: `ssh-ed25519 <base64-blob> <comment>`. The wire format blob correctly uses SSH length-prefixed strings:
- 4-byte big-endian length of key type string
- key type string ("ssh-ed25519")
- 4-byte big-endian length of public key
- 32-byte raw public key

This matches the OpenSSH wire format specification. **Correct.**

### OpenSSH Private Key Format (lines 76-150)

This is the most complex part of the module. Walking through it:

1. **PKCS#8 seed extraction (line 78):** `privateKeyPkcs8.slice(privateKeyPkcs8.length - 32)` extracts the last 32 bytes as the private seed. This works for Ed25519 PKCS#8 encoding where the structure is a fixed prefix followed by the 32-byte seed. However, this is fragile — it assumes a specific PKCS#8 encoding layout. Different browsers or future WebCrypto changes could alter the PKCS#8 structure. A more robust approach would parse the ASN.1 structure.

2. **Check integers (line 84):** Random 4-byte check integers, written twice (lines 100-101). Both must match during decryption to verify the key was decrypted correctly. **Correct per the OpenSSH format.**

3. **Ed25519 key blob (lines 94-95):** Concatenation of seed (32 bytes) + public key (32 bytes) = 64 bytes. This is the standard Ed25519 "expanded" private key representation. **Correct.**

4. **Padding (lines 113-119):** Pads to 8-byte block size with incrementing bytes (1, 2, 3...). This matches the OpenSSH specification for the "none" cipher. **Correct.**

5. **Auth magic (line 122):** `openssh-key-v1\0` with null terminator. **Correct.**

6. **Cipher and KDF (lines 123-125):** Both set to "none" (unencrypted). **Correct for unencrypted keys.**

7. **PEM wrapping (lines 138-149):** Base64 encoded with 70-character line wrapping, wrapped in `-----BEGIN OPENSSH PRIVATE KEY-----` / `-----END OPENSSH PRIVATE KEY-----`. **Correct.**

### Security Concerns

**No passphrase protection.** The private key is generated unencrypted (cipher: "none", kdf: "none"). This is fine for a browser-based generator where the user will save and protect the key, but it should be documented clearly. The tool UI does not warn users to protect their private key or suggest adding a passphrase after downloading.

**Private key displayed in textarea (tools/ssh-keygen/index.html line 251):** The private key is shown in a `<textarea>` in the DOM. This is inherent to the tool's purpose but the key remains in memory until the page is navigated away. There is no "clear keys" button.

**Recommendation:** Add a "Clear Keys" button that zeroes out the textarea values and the in-memory key material. Add a warning about protecting the private key.

**PKCS#8 seed extraction fragility (line 78):** As noted above, `privateKeyPkcs8.slice(privateKeyPkcs8.length - 32)` relies on the assumption that the last 32 bytes of the PKCS#8 encoding are the raw seed. This is true for the current Ed25519 PKCS#8 format across Chromium browsers, but should be documented as an assumption with a reference to the ASN.1 structure.

## 5. Component Quality

### SgHeader (`components/header/v1.0.0/sg-header.js`)

**Structure:** Web Component using `connectedCallback()` to inject HTML via `innerHTML`. Styles are scoped inline within the component's HTML output.

**Issues:**

1. **Styles are NOT scoped via Shadow DOM.** The component uses `this.innerHTML` (lines 23-91) which places styles in the light DOM. Class names like `.sg-header` use BEM-style prefixing to avoid collisions, which is acceptable, but any parent page CSS could override these styles. If the component used Shadow DOM (`this.attachShadow({ mode: 'open' })`), styles would be truly encapsulated.

2. **No Shadow DOM means style leakage both ways.** The component's `.sg-header__link:hover` at line 64 will not interfere with other elements (due to class specificity), but a global `a { color: red; }` rule on the consuming page would affect the header's links.

3. **`tool-name` attribute is read once (line 22).** If the attribute changes after the component is connected, the UI will not update. There is no `attributeChangedCallback()` or `observedAttributes` static getter. For a header that is set once, this is fine. But it means the component is not reactive.

4. **Inline `style` attribute on line 79:** `<div style="display:flex;align-items:center;">` mixes inline styles with the CSS block above. Minor inconsistency.

5. **Hardcoded URLs (lines 87-88):** The "All Tools" link points to `/tools/` and "SG/Send" to `https://send.sgraph.ai`. These are not configurable via attributes. A consuming project (e.g., vault.sgraph.ai) importing this header would get links pointing to tools.sgraph.ai paths, which may not be desired.

**Recommendation:** Consider making nav links configurable via attributes or slots, or at minimum document that this header is designed specifically for tools.sgraph.ai pages.

### SgFooter (`components/footer/v1.0.0/sg-footer.js`)

Same structural pattern as the header. Same light DOM / no Shadow DOM approach.

**Issues:**

1. **Same style scoping concern as header.** No Shadow DOM.
2. **Hardcoded content.** The privacy message and SG/Send link are baked in. No attributes to customize the message. This limits reusability outside tools.sgraph.ai.
3. **No configurable year or copyright.** The footer contains no copyright date or version information.

Both components are functional for the tools.sgraph.ai context but have limited reusability outside this specific site, which somewhat contradicts the "reusable components" goal from the architecture brief.

## 6. Tool Quality

### SSH Key Generator (`tools/ssh-keygen/index.html`)

**Functionality:** Generates Ed25519 SSH key pairs, displays them, supports copy-to-clipboard and download.

**UX Assessment:**
- Clean layout with clear labeling
- Comment field is optional and clearly marked
- Generate button shows loading state ("Generating..." at line 284)
- Copy feedback with "Copied!" text swap (lines 329-333)
- Download uses correct filenames: `id_ed25519.pub` and `id_ed25519` (lines 338, 342)
- Fingerprint is calculated and displayed (lines 297-303)
- Error handling shows user-friendly messages (lines 308-311)
- Info box explains how it works (lines 255-265)

**Issues:**

1. **Clipboard API lacks error handling (lines 319-322, 324-327):** `navigator.clipboard.writeText()` can fail (denied permissions, insecure context). The `await` call has no try/catch. A clipboard failure will result in an unhandled promise rejection with no user feedback.

2. **No key regeneration warning.** Clicking "Generate Key Pair" again replaces the previous keys without warning. If a user generated keys, forgot to save them, and clicked generate again, the old keys are lost.

3. **No "Clear Keys" button.** As noted in the security section.

4. **Download creates/revokes URL synchronously (lines 345-352):** `URL.revokeObjectURL(url)` is called immediately after `a.click()`. In some browsers, the download may not have started before the object URL is revoked. A small `setTimeout` before revoking would be safer.

5. **The landing page (`tools/index.html`) does NOT use the shared header/footer components.** It has its own inline footer (lines 209-215) and hero section instead of using `<sg-header>` and `<sg-footer>`. This means the landing page's footer could drift from the shared component's footer. The brief specifically intended components to be reused across all tool pages.

6. **Fingerprint calculation is in the tool, not the module (lines 297-303).** This logic belongs in `sg-ssh.js`. If another tool or consumer needs to calculate an SSH key fingerprint, they would have to duplicate this code.

### Landing Page (`tools/index.html`)

**Assessment:** Well-designed landing page with tool cards. Responsive grid layout. Coming-soon items are properly grayed out with `pointer-events: none`.

**Issue — tool cards use HTML entities for icons (lines 159, 169, 179, 189, 199):** Characters like `&#128273;` (key emoji), `&#127916;` (movie camera) depend on OS emoji support. These may render as empty boxes on older systems or in some fonts. SVG icons would be more reliable, but this is a minor concern.

## 8. Bugs or Issues

### BUG: importKey() creates decrypt-only key

**File:** `core/crypto/v1.0.0/sg-crypto.js`, line 82
**Severity:** Medium
**Description:** `importKey()` specifies `['decrypt']` as the only key usage. A consumer who exports a key, stores it, and later imports it will be unable to encrypt with it. This is not immediately obvious and the error from Web Crypto will be unhelpful.

### BUG: verify-imports.html decrypt test does not use importKey()

**File:** `tools/verify-imports.html`, lines 60-72
**Severity:** Low (test coverage gap)
**Description:** The verification test works around the `importKey()` limitation by generating a fresh key with `crypto.subtle.generateKey()` directly instead of testing the actual `importKey()` -> `decryptFile()` round-trip. This means the test does not actually verify the module's own import/export/decrypt flow.

**File:** `tools/ssh-keygen/index.html`, lines 319-327
**Severity:** Low
**Description:** `navigator.clipboard.writeText()` is awaited without try/catch. Will produce unhandled promise rejection if clipboard access is denied.

**File:** `core/ssh/v1.0.0/sg-ssh.js`, line 78
**Severity:** Low (works today, future risk)
**Description:** Extracts the last 32 bytes of PKCS#8 output as the Ed25519 seed. Correct for current Chromium implementations but not robust against PKCS#8 format variations.

### ISSUE: BRIEF_PACK.md claims RSA support exists

**File:** `briefs/BRIEF_PACK.md`, line 88
**Severity:** Low (documentation error)

## Summary

The bootstrap code is clean, well-structured, and follows all coding conventions. The crypto module extraction looks faithful and the SSH key generation correctly implements the OpenSSH wire format. The two web components are functional if limited in reusability. The SSH keygen tool provides a solid UX.

The main gaps are: (a) no infrastructure (CI/CD, S3, CloudFront, `latest/` aliases), (b) none of the three priority tools (Video Splitter, LLM Client, Audio Transcription) are built, and (c) some API design decisions in the crypto module (decrypt-only import, no input validation) that should be addressed before other projects start consuming these modules.

The foundation is solid. The next session should focus on the items in "Fix Now" followed by building the Video Splitter tool, which is the highest-value deliverable from the original briefs.
