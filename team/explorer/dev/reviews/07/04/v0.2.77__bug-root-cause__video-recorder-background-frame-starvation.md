# Bug Root Cause — Video Recorder: composite video drops to ~1 frame / 2 s when the shared tab has focus

**Date:** 2026-07-04
**Repo version:** v0.2.77 · **Tool:** video-recorder v0.1.48 (live)
**Reported by:** Dinis Cruz (screenshot: camera+screen+mic, 1 stream, 2.5 Mbps,
Vertical Shorts 9:16, recorded on dev.tools.sgraph.ai)
**Symptom:** recording starts fine; as soon as focus moves to the window/tab being
shared, **audio stays perfect but the composited video advances ~1 frame every
~2 seconds**. Returning focus to the recorder tab restores smooth video.
**Companion doc:** `v0.2.77__dev-review__video-recorder-in-depth.md` (finding F1/F2).

---

## 1. TL;DR

The camera+screen composite is drawn by a **main-thread `setInterval` loop** feeding
`canvas.captureStream(fps)` (`api/merge-vertical.js:196` for Shorts,
`core/sg-capture/v0.1.0/sg-capture.js:158` for Landscape PiP). Focusing the shared
tab hides the recorder tab, and Chrome then:

1. **Throttles all main-thread timers to at most one wake-up per second** — the
   code's own comments assume `setInterval` (unlike rAF) is exempt; it is not.
2. Applies **budget throttling** on top: each ~1080×1920 draw (two `drawImage`
   video blits + shadow blur + text) costs more CPU than a hidden page's budget
   accrues, stretching the effective tick to **~2 s** — exactly the reported rate.
3. Delivers `canvas.captureStream()` frames via the page's rendering pipeline,
   which is also idle for hidden tabs — so even the ticks that do fire may not
   emit a frame promptly.

Audio is unaffected because MediaRecorder pulls audio straight off the live tracks
with no timers involved. Separate (non-composited) camera/screen track recorders
are equally unaffected — **only canvas-composited outputs starve**.

---

## 2. Evidence

- **The screenshot itself:** the elapsed timer shows **119 s** for a recording whose
  final status line says **3 m 53 s (233 s)**. That timer is a second, independent
  main-thread `setInterval` that increments a counter per tick
  (`ui-controls.js:403`), so it ran at 119/233 ≈ **0.51 Hz while hidden** — the same
  ~1-tick-per-2-seconds rate as the reported frame cadence. Two unrelated timers
  degrading identically is the fingerprint of tab-level timer throttling, not of
  encoder/CPU overload.
- **Audio OK, video slideshow** — matches a starved canvas source, not a starved
  MediaRecorder (which would corrupt/stall both).
- **Modes without compositing don't lag** — screen-only / camera-only recordings
  write raw `getDisplayMedia`/`getUserMedia` tracks directly.
- **The codebase already met this bug once:** `sg-audio-viz` (rAF-driven) freezes
  when hidden, which is why `wasHidden` + the "Regenerate Viz" flow exist. The
  composite path has the same disease with no warning and no regen path.
- Both compositors carry comments claiming the opposite of reality:
  - `sg-capture.js:155` — "*setInterval instead of requestAnimationFrame: rAF is
    throttled to ~1fps when the tab is in the background*" (rAF is fully **paused**
    when hidden; setInterval is **also throttled**).
  - `merge-vertical.js:13` — "*uses setInterval (not rAF) so it keeps drawing at
    the configured fps even when the recording tab is in the background*" (false).

### Chrome throttling rules that apply here

| Page state | rAF | setTimeout/setInterval | canvas.captureStream(fps) |
|---|---|---|---|
| Visible | 60 Hz | as scheduled | on paint, up to fps |
| Hidden < 5 min | paused | aligned to **1 s**, minus CPU budget (→ ~2 s here) | sporadic (no compositing) |
| Hidden ≥ 5 min | paused | **intensive throttling: 1 wake-up per minute** | sporadic |

Holding a getUserMedia/getDisplayMedia capture exempts the tab from *freezing and
discard*, *not* from timer throttling. Playing audible audio would exempt it, but
the recorder tab captures audio; it plays none.

**Testable prediction:** a combined recording left in the background for **more than
5 minutes** should degrade further, to roughly **one frame per minute** (intensive
throttling). Worth confirming when validating the fix.

## 3. Why each layer fails

```
mic/tab audio track ──────────────────────────────► MediaRecorder('combined')  ✅ no timers
camera video ─► <video> ─┐                      ▲
                          ├─ draw() every tick ─ canvas ─ captureStream(30) ───┘
screen video ─► <video> ─┘        ▲
                                  └── setInterval(draw, 33ms)  ❌ main thread, throttled to ~0.5 Hz
```

1. **Tick starvation** — `setInterval(draw, 1000/fps)` on the main thread of a
   hidden page fires ~once per 1–2 s (once per minute after 5 min).
2. **Frame-delivery starvation** — `captureStream(fps)` (with an fps argument)
   emits a new frame when the canvas is repainted *and* the capture pipeline runs;
   hidden pages skip compositing, so even completed draws can sit unemitted. The
   explicit-control variant — `captureStream(0)` + `track.requestFrame()` after
   each draw — bypasses this.
3. The `<video>` elements feeding `drawImage` are fine: live `srcObject` playback
   is not paused for hidden tabs, so whenever `draw()` runs it gets current pixels
   — which is why the output is a *slideshow of correct frames* rather than a
   frozen image.

## 4. Fix plan (recommended)

### 4a. Primary fix — worker-driven tick + explicit frame push
Web-Worker timers are **not** visibility-throttled, and `postMessage` delivery to
the main thread is not a throttled timer task. Vanilla JS, no build step, ~25 lines,
fixes Landscape + Shorts + any future compositor.

```js
// core/sg-capture v0.1.1 — shared by mergeAsPiP and mergeAsShorts
function startBackgroundSafeTicker(fps, onTick) {
    const src = `let id=null;
        onmessage = e => {
            if (e.data === 'stop') { clearInterval(id); close(); return; }
            id = setInterval(() => postMessage(0), e.data);
        };`;
    const url    = URL.createObjectURL(new Blob([src], { type: 'text/javascript' }));
    const worker = new Worker(url);
    URL.revokeObjectURL(url);
    worker.onmessage = onTick;
    worker.postMessage(Math.max(4, Math.round(1000 / fps)));
    return () => worker.postMessage('stop');
}
```

In both compositors:
```js
const canvasStream = canvas.captureStream(0);              // was captureStream(fps)
const videoTrack   = canvasStream.getVideoTracks()[0];
const stopTicker   = startBackgroundSafeTicker(fps, () => {
    draw();
    videoTrack.requestFrame();                             // force emission, paint-independent
});
// stop() → stopTicker() instead of clearInterval(intervalId)
```

Versioning (immutable-version rule): new `core/sg-capture/v0/v0.1/v0.1.1/`, updated
`merge-vertical.js` inside a new tool version folder; bump manifest pins.

### 4b. Same-commit secondary fixes
- **Timer display** (`ui-controls.js`): compute the label from
  `Date.now() - state.startedAt - pausedMs` per tick instead of `elapsed++`
  (fixes 119 s-vs-233 s lying timer; the same throttling makes any counting
  timer wrong).
- **Shorts footer clock** (`merge-vertical.js:177`): subtract paused time.
- **Insurance banner**: on `visibilitychange` during a camera+screen combined
  recording, surface a status note (mirrors the viz `wasHidden` pattern) — cheap
  detection if some browser still throttles.

### 4c. Alternatives considered (and why not now)
- **OffscreenCanvas + MediaStreamTrackProcessor fully in a worker** — the most
  robust (zero main-thread dependency), but `MediaStreamTrackProcessor` is
  Chromium-only and it's a rewrite of both compositors. Right long-term shape,
  wrong hotfix.
- **AudioWorklet/AudioContext clock as tick source** — unthrottled but heavier and
  indirect; the worker ticker is simpler and equally exempt.
- **`documentPictureInPicture` to keep the tab "visible"** — user-visible UX
  change, permission-gated, Chromium-only; could be a nice *feature* later
  (floating self-view) but not a fix.

### 4d. Risk notes for 4a
- If a future browser stops decoding hidden-tab live `<video>` elements, `draw()`
  would blit stale pixels; the escalation path is 4c. Not observed in current
  Chrome/Edge/Safari.
- Safari doesn't implement `CanvasCaptureMediaStreamTrack.requestFrame()` on all
  versions — feature-detect and fall back to `captureStream(fps)` + worker ticker
  (worker ticks alone already restore ~full rate there).

## 5. Verification plan

1. **Manual repro parity:** camera+screen, 1 stream, Shorts, 2.5 Mbps — record
   ≥ 6 min with the shared tab focused the whole time. The burned-in footer clock
   makes frame cadence measurable: step through the output and confirm consecutive
   frames advance ~1/30 s (before the fix they advance ~2 s, and ~60 s after the
   5-minute mark).
2. **Headless smoke** (tests/ has none for this tool — see review F5): launch with
   `--use-fake-device-for-media-stream --use-fake-ui-for-media-stream`, start a
   camera+screen recording, open+focus a second tab for 30 s, stop, then assert
   combined blob size ≈ foreground-recorded size (starved video shrinks the
   stream dramatically at fixed bitrate).
3. Regression: pause/resume durations, Landscape PiP, viz modes, per-track
   downloads, WebM duration patch.
