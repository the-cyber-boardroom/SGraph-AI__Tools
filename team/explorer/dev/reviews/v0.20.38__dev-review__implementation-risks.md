# Dev Review — Implementation Risks: v0.20.38 JS API Primitive
**version** v0.20.38
**date** 2026-04-09
**role** Dev (Explorer team)
**scope** Entanglements, async complexity, things the brief underestimated

---

## Risk 1: The mini-bus pattern is not compatible with renderUI:false without a refactor

**What the brief says:** `generate({ renderUI: false })` skips tab creation.

**What the code actually does:**

The SEND interceptor (infographic-gen.js lines 434-557) interleaves UI creation and network logic in a single `async` block with no clean separation point. The sequence is:

1. Lines 461-462: `layout.addTabToStack()` → creates a UI tab
2. Lines 464-468: `await setupResultFractal(panelEl, model)` → creates inner sg-layout (async, awaited)
3. Lines 467-468: `setupLoadingState(imgPanel, model)` → populates loading state
4. Lines 473-477: creates `miniBus` div, appends `sg-llm-request`
5. Lines 479-481: fires `SGL_LLM.CONNECTED` on miniBus
6. Lines 491-524: wires REQUEST_COMPLETE / REQUEST_ERROR / REQUEST_CANCEL handlers — all of which reference `imgPanel` and `detailsCtl`, which are UI objects

The `imgPanel` and `detailsCtl` references are captured in closures on the mini-bus event listeners. With `renderUI: false`, there is no `imgPanel` and no `detailsCtl`. The event handlers must be completely rewritten for the headless path. This is not a flag — it is two different code paths.

**Impact:** Phase 2, item 3 in the impl brief cannot be "extract generate() from lines 857-1029." It requires writing a new headless execution path and refactoring the UI path to call it. Estimated additional effort: 0.5 days.

## Risk 2: Top-level await blocks module restructuring

**What the code does:** Line 64 in infographic-gen.js:
```javascript
await outerReady;
```

This is top-level `await` inside an ES module. All code after line 64 executes after the layout is ready. The module cannot be restructured into a class body or an initialisation function without handling this carefully — `class` bodies do not allow `await` at the property level, and wrapping in an `async init()` function changes the timing of when `window.__tool` is registered.

**Impact:** When wiring infographic-gen to `SgToolApi.activate()`, the `activate()` call must happen after the layout is ready. This is solvable (call it at the end of the module after all awaits), but the timing of `tool:ready` must be considered. Agents listening for `tool:ready` before the layout is set up will try to call APIs that fail because the UI state is not initialised.

**Recommendation:** Fire `tool:ready` after all async initialisation is complete, not when the SgToolApi instance is created. The brief does not address this.

## Risk 3: The genId extraction is fragile and affects multiple API methods

**The current code (lines 503-506):**
```javascript
const genId = ev.detail?.rawResponse?.id
           ?? ev.detail?.rawChunks?.find(c => c?.id)?.id
           ?? null;
```

This is the only place in the codebase where a generation ID is extracted from an LLM response. It handles two response shapes: direct response with `.id`, or streaming chunks array.

For `getCost({ generationId })` to work, the caller needs the `generationId` that was assigned by OpenRouter. For `exportPng()` to work programmatically (without clicking a button), the image `src` must be stored against that `generationId`. Neither registry exists today.

**What needs to be created:**
- A `Map<generationId, { src, model, prompt, duration }>` to store generation results
- Logic to populate it in the REQUEST_COMPLETE handler
- The `generate()` API method must return this `generationId` in its resolved value

The brief acknowledges this in the `generate()` return type (`{ generationId, image?, duration? }`) but does not flag the implementation gap.

## Risk 4: getCost is a network call, not a data extraction

**What the brief implies:** Extract `getCost()` from `sg-openrouter-generation.fetchGeneration()`.

**What `fetchGeneration()` actually does:** It calls `this._fetch(id)` which renders HTML into the component's Shadow DOM. The structured data is in `this._data` but there is no method to return it — it is rendered and discarded as a return value. The `_fetch()` method is `async` and does `return this._fetch(id, ...)` on retry, but the top-level call does not return the data — the component itself is a viewer, not a data service.

**Correct approach:** Implement `getCost()` as a direct `fetch()` call to `https://openrouter.ai/api/v1/generation?id={id}` with the API key. This is 5 lines. Do not try to wrap the Web Component. The retry logic from `sg-openrouter-generation._fetch()` (3 retries, 2s/4s/6s backoff on 404) should be replicated or extracted as a standalone utility.

**Risk to the brief's timeline:** Low, because the clean approach is straightforward. But the brief's description ("wraps sg-openrouter-generation.fetchGeneration()") is misleading and will waste time if taken literally.

## Risk 5: SgToolApi as a class vs. the current procedural module style

**Current pattern:** infographic-gen.js is a procedural ES module with top-level code that runs on load. There are no classes, no instances. State is in module-level variables.

**Proposed pattern:** Import `SgToolApi`, create an instance, `register()` methods, `activate()`.

**The problem:** The registered method implementations (`connectImpl`, `generateImpl`, etc.) need access to the module's state variables (`apiKeyEl`, `textarea`, `currentMode`, `activeRequests`, etc.). When these are module-level closures, the registered functions can close over them. This is fine.

But the `generate()` implementation in headless mode (`renderUI: false`) needs no DOM access at all. This means the implementation needs to branch on `renderUI` and conditionally access DOM elements. If DOM elements are not present in a test harness or Node.js environment, the code throws.

**Recommendation:** Define two separate implementations: `generateHeadless()` (no DOM refs) and `generateWithUI()` (DOM-coupled). The registered `generate()` dispatches to one or the other. The brief does not address this split.

## Risk 6: Parallel generation with Promise.all — the activeRequests Map

**The brief's parallel generation example (from arch brief):**
```javascript
const results = await Promise.all(
  models.map(model => window.__tool.generate({ prompt, model, await: true }))
);
```

**Current constraint:** The `activeRequests` Map (line 348) maps `panelEl → cancelFn`. With `renderUI: false`, there is no `panelEl`. With multiple parallel calls, each call creates its own `miniBus`, its own `sg-llm-request`, its own event listeners — this already works in the current UI because each call creates a separate tab with a separate mini-bus.

**The new risk:** With `await: true` and parallel execution, multiple Promises are pending simultaneously. Each mini-bus fires `SGL_LLM.REQUEST_COMPLETE` on the mini-bus itself (not on window), so there is no cross-talk between them. This is correct and parallel generation should work.

**However:** The current mini-bus pattern appends to `document.body` (line 476: `document.body.appendChild(miniBus)`). With 5 parallel requests, 5 invisible divs are appended to the body. They are removed after completion (line 488: `setTimeout(() => miniBus.remove(), 0)`). This is slightly untidy but functional. Not a blocker.
