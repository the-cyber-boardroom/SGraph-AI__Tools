# Dev Brief — Video Recorder: Capture Audio From the Shared Screen / Tab

**Version:** v0.2.58
**Date:** 2026-05-14
**Author:** Dev (Explorer team)
**Session:** `claude/add-pause-resume-recording-VMXcm`
**Tool:** `tools/v0/v0.1/v0.1.48/en-gb/video-recorder/`
**Status:** PROPOSED — does not exist yet
**Revision:** v2 — mic and screen audio are mutually exclusive (human feedback 2026-05-14).
v1 proposed mixing both sources simultaneously; that requirement was rejected.

---

## 1. Goal

Let the user capture the **audio coming out of the screen / tab they are sharing** instead of
their microphone. Today the Audio toggle only requests mic audio. If you screen-share a video
call, a YouTube clip, or a terminal with sound, that audio is silent in the recording.

**Design constraint (v2):** the user picks **one** audio source — either mic or the shared
screen/tab — never both at once. This eliminates any audio mixing complexity.

---

## 2. What Is Actually Possible (browser reality)

`getDisplayMedia()` accepts an `audio` constraint. What the browser does depends on what the
user picks in the OS source picker and the platform:

| Source the user shares | `{ audio: true }` result | Notes |
|------------------------|--------------------------|-------|
| **Browser tab** | ✅ Tab audio captured | Chrome shows a "Share tab audio" checkbox in the picker. Best-supported path. |
| **Entire screen** | ⚠️ System audio on Windows; **not** on macOS without third-party routing; mixed on Linux | Chrome on Windows offers "Share system audio". |
| **Application window** | ❌ No per-window audio on any platform | Browsers cannot isolate one app's audio stream. |

**Bottom line:** tab audio capture is reliable. Window-specific audio is not achievable.
The UI copy must say "tab / screen audio", never "window audio".

We do not control the OS picker. If the user unticks the audio checkbox in the picker, the
screen stream arrives with no audio track and we record as if "Audio Off" was selected — no
error, silent degradation.

---

## 3. Current State (code-verified)

- `core/sg-capture/v0/v0.1/v0.1.0/sg-capture.js` — `getScreenStream({ audio, preferCurrentTab })`
  already forwards `audio` to `getDisplayMedia()`. **No change to the core module.**
- `api/recorder-pipeline.js` — `startPipeline()` hard-codes `getScreenStream({ audio: false })`.
  This is the single line that suppresses screen audio today.
- `api/recorder-pipeline.js` — `audioTracks` is assembled from camera audio + standalone mic only.
  Screen audio tracks are never collected.
- `api/recorder-state.js` — `RecordingConfig` has no audio-source field.
- `ui/ui-controls.js` — the Audio column is a binary Off | On toggle (On = mic only).

---

## 4. Design — Mutual Exclusion, No Mixing

Because only one audio source is active at a time, **no Web Audio mixing is needed**. The
pipeline simply routes from the selected source:

| `audioSource` | What is requested | How `audioTracks` is built |
|--------------|-------------------|---------------------------|
| `'none'` | Nothing | `[]` |
| `'mic'` | `getAudioStream()` or camera mic (current behaviour) | mic tracks only |
| `'screen'` | `getScreenStream({ audio: true })` | `rawScreen.getAudioTracks()` |

The existing `audioTracks` variable in the pipeline feeds all downstream recorders unchanged.
The `'screen'` path simply populates it from a different source than before.

---

## 5. Proposed Changes

### 5a. Config — `recorder-state.js`

Replace the implicit "audio = boolean from mode string" with an explicit source field:

```javascript
/** Which audio source to record.
 *  'mic'    — microphone / camera audio (current behaviour)
 *  'screen' — audio from the shared tab/screen (getDisplayMedia audio constraint)
 *  'none'   — no audio
 * @type {'mic'|'screen'|'none'} */
this.audioSource = 'mic';
```

> `'mic'` as default preserves existing behaviour — no breaking change for current users
> or scripts that call `setConfig`.

### 5b. Pipeline — `recorder-pipeline.js`

Three targeted edits only:

**Acquisition block** — replace the hard-coded `audio: false`:

```javascript
// was: rawScreen = await getScreenStream({ audio: false });
rawScreen = await getScreenStream({ audio: config.audioSource === 'screen' });
```

**Standalone audio block** — gate on `audioSource === 'mic'` (was just `flags.audio && !flags.camera`):

```javascript
// Standalone mic — only when mic is the selected source
if (flags.audio && config.audioSource === 'mic' && !flags.camera) {
    rawAudio = await getAudioStream();
}
```

**`audioTracks` assembly** — add screen audio tracks:

```javascript
const audioTracks = config.audioSource === 'screen'
    ? (rawScreen ? rawScreen.getAudioTracks() : [])
    : [
        ...(rawCamera ? rawCamera.getAudioTracks() : []),
        ...(rawAudio  ? rawAudio.getAudioTracks()  : []),
      ];
```

No new recorder names, no new blobs, no mixer to tear down. The `audio` blob in the output
is mic audio or screen audio depending on the source — the recording tab UI label should
reflect which it was (see §5d).

`_watchTracks` requires no change — a dropped screen-audio track already dispatches
`TRACK_LOST` with `kind: 'audio'` and correctly does not auto-stop.

### 5c. API — `recorder-api.js`

`getConfig` / `setConfig` pass `audioSource` through generically — no new methods needed.

Update `SKILL-api.md`: add `audioSource` to `RecordingConfig` type.

### 5d. UI — `ui-controls.js` + `controls.css`  *(the UI change)*

The **Audio column** in the mode builder changes from a binary Off | On toggle to a
**3-state selector** matching the pattern of the Camera/Viz column:

```
┌─ MODE ─────────────────────────────────────────────────┐
│  🖥 SCREEN        🎙 AUDIO            📷 CAMERA / VIZ   │
│  ┌──────────┐    ┌─────┬─────┬──────┐  ┌───┬──────┬───┐│
│  │   On     │    │ Off │ Mic │ Tab  │  │Off│Camera│Viz││
│  └──────────┘    └─────┴─────┴──────┘  └───┴──────┴───┘│
│                           ↑                              │
│                   "Tab" greyed out when Screen is Off    │
└────────────────────────────────────────────────────────┘
```

**Button labels:** Off | Mic | Tab
- "Tab" (short for "Tab / Screen audio") — disabled when Screen is Off; tooltip: *"Captures
  audio from the tab or screen you share. Works best when sharing a browser tab — tick 'Share
  tab audio' in the browser picker."*

**Mode derivation** — `_deriveMode` currently takes `(useScreen, useAudio, camViz)`. Change the
second parameter from a boolean to `audioSource: 'none'|'mic'|'screen'`:

```javascript
function _deriveMode(useScreen, audioSource, camViz) {
    const useAudio = audioSource !== 'none';
    // rest of the logic unchanged — useAudio drives the same mode strings as before
    ...
}
```

`config.audioSource` is set directly from the button press. `_applyModeState()` reads it to
highlight the active button.

**`_lockModeBuilder`** — disable all three Audio buttons during recording/pause, same as other
mode controls.

**Recording tab download label** — the `audio` blob label in `ui-recording-tab.js` should read
"Audio (mic)" vs "Audio (tab)" depending on the `audioSource` that was active when recording
started. Pass `config.audioSource` into the tab metadata at `RECORD_START` time (add it to the
event detail or snapshot config at that moment).

## 6. Acceptance Criteria

| # | Criterion |
|---|-----------|
| 1 | Audio column shows three buttons: Off | Mic | Tab |
| 2 | "Tab" is disabled (greyed) when Screen is Off |
| 3 | Selecting Mic → `config.audioSource === 'mic'`; behaviour identical to today |
| 4 | Selecting Tab → `config.audioSource === 'screen'`; `getScreenStream` called with `{ audio: true }` |
| 5 | Selecting Off → `config.audioSource === 'none'`; no audio track in the recording |
| 6 | If the user shares a tab **with** audio (ticks the picker checkbox): recording contains tab audio |
| 7 | If the user shares without audio (unticks picker): recording proceeds silently, no error |
| 8 | Mic and Tab cannot be selected simultaneously — they are mutually exclusive buttons |
| 9 | All three Audio buttons are disabled while recording or paused |
| 10 | Recording tab download label distinguishes "Audio (mic)" from "Audio (tab)" |
| 11 | `getConfig()` returns the correct `audioSource` value |
| 12 | `SKILL-human.md` and `SKILL-api.md` updated; reality document updated in the same commit |
| 13 | Existing Mic behaviour unchanged — no regression for current users |
| 14 | Works in Chrome (tab audio) and Edge; degrades cleanly in Safari/Firefox |

---

## 7. Risks

| Risk | Severity | Mitigation |
|------|----------|-----------|
| User expects per-window audio; browser can't do it | **MED** | Label says "Tab", not "Window". Tooltip and SKILL-human set expectations. |
| User shares a tab but forgets to tick the picker's audio checkbox → silent | **LOW** | Expected; criterion #7. Consider a post-start warning if the audio track count is 0 when `audioSource === 'screen'`. |
| macOS entire-screen audio silently fails | **LOW** | Expected per §2; same silent-degradation path. |
| "Tab" becoming enabled when Screen turns On mid-session (state management) | **LOW** | `_applyModeState()` must re-evaluate the disabled state of the Tab button on every Screen toggle. |
