**Version:** v0.2.58

**Author:** Dev (Explorer team)

**Status:** PROPOSED — does not exist yet

---

## 1. Goal

Let the user capture the **audio coming out of the screen / tab / window they are sharing** —
not just their microphone. Today the video recorder only records mic audio; if you screen-share
a video call, a YouTube clip, or a terminal demo with sound, that sound is lost.

This is the natural companion to the pause/resume work in the same session: the user wants a
single recording that captures *everything in one view*, including what they can hear.

---

## 2. What Is Actually Possible (browser reality)

`getDisplayMedia()` accepts an `audio` constraint. What the browser does with it depends on
**what the user picks in the OS source picker** and **the platform**:

| Source the user shares | `{ audio: true }` result | Notes |
|------------------------|--------------------------|-------|
| **Browser tab** | ✅ Tab audio captured | Chrome shows a "Share tab audio" checkbox in the picker. Best-supported path. |
| **Entire screen** | ⚠️ System audio on Windows; **not** on macOS without third-party routing (BlackHole/Loopback); mixed on Linux | Chrome on Windows offers a "Share system audio" checkbox. |
| **Application window** | ❌ No per-window audio on any platform | Browsers cannot isolate one app's audio. On Windows it falls back to system audio; elsewhere nothing. |

**Bottom line:** we can reliably deliver **tab audio capture** (and opportunistically system audio
where the OS allows it). Window-specific audio is **not achievable** with web APIs — the brief
should set that expectation in the UI copy, not promise it.

We do **not** control the OS picker — we only set `audio: true` and the browser does the rest.
If the user does not tick the picker's audio checkbox, the screen stream simply arrives with no
audio track and we record mic-only as before. No error path needed; just degrade silently.

## 3. Current State (code-verified)

- `core/sg-capture/v0/v0.1/v0.1.0/sg-capture.js` — `getScreenStream({ audio, preferCurrentTab })`
  **already** forwards `audio` to `getDisplayMedia()`. No change needed in the core module for the
  basic path.
- `api/recorder-pipeline.js` line ~291 — `startPipeline()` hard-codes `getScreenStream({ audio: false })`.
  This is the single line that suppresses screen audio today.
- `api/recorder-pipeline.js` builds an `audioTracks` array from **camera audio + standalone mic
  audio only**. Screen audio tracks are never collected.
- `api/recorder-state.js` — `RecordingConfig` has no field for this option.
- `ui/ui-controls.js` — the 3-column mode builder (Screen | Audio | Camera/Viz) has no control for it.

So the feature is ~1 line away from *acquiring* the track, but correctly *recording* it (especially
alongside mic audio) and *exposing it in the UI* is the real work.

## 4. The Hard Part — Mixing Two Audio Sources

A `MediaStream` can hold multiple audio tracks, but **`MediaRecorder` only encodes the first
audio track**. If the user has both mic ON and screen audio ON, naively appending both tracks
to the combined stream will silently drop one.

To get mic + screen audio into **one** combined file, they must be mixed into a **single track**
via the Web Audio API:

```
AudioContext
  ├─ MediaStreamAudioSourceNode(mic stream)      ┐
  ├─ MediaStreamAudioSourceNode(screen stream)   � → GainNode(s) → MediaStreamAudioDestinationNode
  └─ ...                                          ┘                    │
                                                    .stream.getAudioTracks()[0]  ← single mixed track
```

**Proposed:** add a small helper to `sg-capture.js` (additive, → `v0.1.1`):

```javascript
/**
 * Mix multiple audio-bearing MediaStreams into a single mixed audio track.
 * Returns the mixed track plus a stop() that closes the AudioContext.
 * @param {MediaStream[]} streams
 * @returns {{ track: MediaStreamTrack, stop: () => void }}
 */
export function mixAudioTracks(streams) { ... }
```

Mirror the existing viz-clone caveat already documented in `recorder-pipeline.js`: a background
tab's `AudioContext` can be suspended — call `audioCtx.resume()` and clone source streams so the
mixer never starves the `MediaRecorder` feeding the raw tracks.

### Recording-mode interaction

The tool already has a 3-way output mode (`combined` / `combined+separate` / `separate`):

- **Combined output** — screen audio is mixed with mic audio (if present) into the one combined
  file via `mixAudioTracks()`.
- **Separate output** — screen audio becomes its **own blob**. Add a new recorder name
  `screen-audio` to the `RecordingSession` (the `NAMES` array in `stopAll()` and the
  `tool:record:stop` `tracks` detail both need the extra key).

## 5. Proposed Changes

### 5a. Config — `recorder-state.js`
Add to `RecordingConfig`:
```javascript
/** Capture audio from the shared screen/tab (getDisplayMedia audio constraint). */
this.captureScreenAudio = false;
```

### 5b. Pipeline — `recorder-pipeline.js`
- `startPipeline()`: `getScreenStream({ audio: config.captureScreenAudio })`.
- After acquisition, collect `rawScreen.getAudioTracks()` into a new `screenAudioTracks` array.
- `_watchTracks('screen', …)` already watches all tracks — a dropped screen-audio track will
  dispatch `TRACK_LOST` with `kind: 'audio'` and (correctly) **not** auto-stop. No change needed,
  but confirm the UI banner copy reads sensibly for this source.
- Combined recorder: when both mic and screen audio exist, mix via `mixAudioTracks()`; when only
  one exists, use it directly (no mixer overhead).
- Separate recorder: start a `screen-audio` recorder when `config.recordingMode !== 'combined'`
  and `screenAudioTracks.length > 0`.
- `disposeAll()` / `stopPipeline()`: stop the mixer's `AudioContext` alongside the existing
  `_pipStop` / `_vizAudioClone` teardown.

### 5c. API — `recorder-api.js`
- `getConfig` / `setConfig` already pass the field through generically — no new method required.
- `tool:record:stop` `tracks` detail gains an optional `screenAudio: number|null` key.
- Update `SKILL-api.md` (`RecordingConfig` type + event detail).

### 5d. UI — `ui-controls.js` + `controls.css`  *(the "another UI change")*
Add a **sub-toggle inside the Screen column** of the mode builder, revealed only when Screen is On:

```
┌─ MODE ──────────────────────────────────────────────┐
│  🖥 SCREEN        🎙 AUDIO       📷 CAMERA / VIZ      │
│  ┌──────────┐    ┌────────┐    ┌────┬──────┬─────┐  │
│  │   On     │    │  Off   │    │Off │Camera│ Viz │  │
│  └──────────┘    └────────┘    └────┴──────┴─────┘  │
│  ☑ + screen audio   ← NEW: only visible when Screen On│
└──────────────────────────────────────────────────────┘
```

- Label: **"+ screen audio"** with a tooltip: *"Captures audio from the tab/screen you share.
  Works best when sharing a browser tab — tick 'Share tab audio' in the picker."*
- Wire it like the existing toggles: flips `config.captureScreenAudio`, re-runs `_applyModeState()`.
- Hidden when Screen is Off; state preserved so toggling Screen back on restores the choice.
- Locked (disabled) during recording, same as the other mode controls (`_lockModeBuilder`).
- **Alternative placement considered:** the `<details>` Options panel. Rejected — the user
  explicitly wants this discoverable, and the Options panel is for advanced/rarely-touched
  settings. Sub-toggle under Screen keeps it next to the thing it modifies.

## 6. Acceptance Criteria

| # | Criterion |
|---|-----------|
| 1 | When Screen is On, a "+ screen audio" sub-toggle is visible in the Screen column; hidden when Screen is Off |
| 2 | Toggling it sets `config.captureScreenAudio`; reflected by `getConfig()` |
| 3 | With it ON, `getScreenStream` is called with `{ audio: true }` and the OS picker offers the audio checkbox |
| 4 | If the user shares a tab **with** audio: the recording contains the tab's audio |

| 9 | Mixer `AudioContext` is closed on stop / reset / error — no leaked audio graph |
| 10 | The sub-toggle is disabled while recording or paused |
| 11 | `SKILL-human.md` and `SKILL-api.md` updated; reality document updated in the same commit |
| 12 | Works in Chrome (tab audio) and Edge; degrades cleanly in Safari/Firefox where unsupported |

## 7. Risks

| Risk | Severity | Mitigation |
|------|----------|-----------|
| User expects per-**window** audio; browser can't do it | **MED** | UI copy says "tab/screen", tooltip sets expectations; never label it "window audio" |
| `MediaRecorder` drops 2nd audio track if not mixed | **HIGH** | `mixAudioTracks()` is mandatory for the combined path — covered in §4 |
| Background-tab `AudioContext` suspends → silent mix | **MED** | `resume()` the context; clone source streams (same pattern as the existing viz clone) |
| Acoustic echo: mic picks up speakers while screen audio also captured | **LOW** | Out of scope for MVP; note in SKILL-human ("use headphones to avoid echo") |
| macOS entire-screen audio just silently fails | **LOW** | Expected per §2; criterion #5 covers graceful mic-only fallback |
| Mixer adds CPU on low-end hardware | **LOW** | Only instantiated when *both* sources are present; single source bypasses the mixer |
