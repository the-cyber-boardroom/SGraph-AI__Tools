# Dev review — does the graphs.sgit.ai interop brief apply to our vault modules?

**Reviewing:** *Brief: sgit-CLI and the browser vault modules no longer speak the same vault format*
(from the graphs.sgit.ai site agent, 24 Aug 2026)
**Against:** `sgit-ai 0.16.0` (from PyPI) and the vault modules in this repo
**Method:** every claim re-run against a local KV store — real `sgit init/commit/push`, real published
browser modules. Harness committed at `sgraph_ai_tools__static/tests/interop/`.

---

## Verdict

**Yes, it applies — but only one of the three reported deltas is real, and it is a four-line fix
rather than a format divergence.** The two implementations already agree on crypto, derivation
domains, object schemas and directory layout. What broke is that the browser never learned about
the `sgit_private_vault_` key prefix sgit started printing, so it feeds a different string into
PBKDF2 and derives a different everything.

| # | Brief's claim | Verdict |
|---|---|---|
| 1 | Directory layout diverged (`bare/indexes` vs `bare/idx` vs `bare/data`) | **Real, ours.** Three answers in our code; sgit has one. Not what breaks the open, though. |
| 2 | Ref-ID derivation diverged | **Real, but misdiagnosed.** The derivation is byte-identical. The *input* differs: an unstripped key prefix. |
| 3 | CLI wrapped branch keys the browser can't unwrap | **Not real.** There is no key-wrapping layer. `key-rnd-imm-*` are PKI signing keys, encrypted with the same read key as everything else. |
| — | "blocks interop in both directions" | **Not real.** Browser → CLI works today, unmodified. Only CLI → browser is broken. |

Two further gaps the brief did not report are in **Also found** below — one of them breaks the
documented public-vault embed pattern.

## The root cause

`sgit_ai/crypto/Vault__Crypto.py` stamps a self-identifying prefix onto every credential it prints,
and strips it again on input:

```python
VAULT_KEY_PREFIX = 'sgit_private_vault_'      # read AND write capability

def strip_key_prefix(self, key: str) -> str:  # the single normalisation point for key input
    for prefix in KEY_PREFIXES:
        if key.startswith(prefix):
            return key[len(prefix):]
    return key
```

Our side has never heard of it. `sg-vault-connect` v0.1.3 splits the pasted key on the last colon
and nothing else:

```js
const lastColon  = rawKey.lastIndexOf(':');       // sg-vault-connect.js:248
const passphrase = rawKey.slice(0, lastColon);
const vaultId    = rawKey.slice(lastColon + 1);
keys = await deriveWriteKeys(passphrase, vaultId);
```

So `sgit_private_vault_hunter2:k8hbjt8x` yields the passphrase `sgit_private_vault_hunter2`, not
`hunter2`. That string goes into PBKDF2, which produces a different read key, which HMACs to a
different ref file ID — and the vault is unreachable. `grep -r sgit_private` across
`sgraph_ai_tools__static/` returns **zero hits**; the prefix is simply absent from our stack.
`parseVaultKey()` in every `vault-client` version has the same gap.

That is the whole of delta 2. Derivation domains, salts and iteration counts are already identical
on both sides:

| | sgit-ai 0.16.0 | our modules |
|---|---|---|
| read salt | `sg-vault-v1:{vault_id}` | `sg-vault-v1:{vaultId}` |
| write salt | `sg-vault-v1:write:{vault_id}` | `sg-vault-v1:write:{vaultId}` |
| KDF | PBKDF2-HMAC-SHA256, 600 000, 32 bytes | same |
| named ref | `ref-pid-muw-` + HMAC(read_key, `sg-vault-v1:file-id:ref:{vault_id}`)[:12] | same |
| branch index | `idx-pid-muw-` + HMAC(read_key, `sg-vault-v1:file-id:branch-index:{vault_id}`)[:12] | same |
| branch ref | HMAC(read_key, `sg-vault-v1:file-id:branch-ref:{vault_id}:{branch}`)[:12] | same |

## Delta 1 — the index directory (real, ours, three-way)

sgit stores indexes at `bare/indexes/` — from its own constants, not observation:

```python
BARE_INDEXES = 'indexes'                                     # sgit_ai/storage/Vault__Storage.py:12
file_id = f'bare/indexes/{index_id}'                         # …/push/Vault__Sync__Push.py:725
```

We give three different answers:

| Module | Resolves `idx-*` to | |
|---|---|---|
| `vault-client` v1.1.0, v1.2.0 | `bare/indexes/` | correct |
| `vault-client` v1.2.1, v1.2.2 | `bare/idx/` | **regression** |
| `vault-cache` v1.0.0 `cachedFetchRaw` | `bare/data/` | never routed through `fileIdToPath()` |

`vault-cache` hardcodes `bare/data/${objectId}` for anything not already a `bare/` path, and
`vault-session.open()` reads the branch index through it — which is exactly the
`GET …/bare/data/idx-pid-muw-…` the brief observed.

Verified against a real CLI vault:

```
FAIL  vault-cache v1.0.0 (bare/data)    → 404
FAIL  vault-client v1.2.1 (bare/idx)    → 404
OK    CLI layout       (bare/indexes)   → schema=branch_index_v1 branches=2
      named.head_ref_id = ref-pid-muw-b8d0bd5845d3   (equals our HMAC-derived refFileId ✓)
```

**Where the regression came from.** Our reality document records the v1.2.1 change as *"fixed `idx`
bare path to `bare/idx`"* — and it was a fix, against
`v0.20.47__tech-ref__vault-protocol-1-crypto-and-object-model.md` (a vault-team brief in
`team/humans/dinis_cruz/briefs/04/15/from-team__vault/`), which documents `bare/idx/{id}`. Our own
`team/explorer/dev/v0.1.14__design__sgit-vault-write.md:39` says `bare/indexes/{id}`, and the CLI
agrees with that one. The tools team followed the wrong document. Note that sgit's source *already
names this divergence* and tolerates it — `Step__Clone__Download_Index.py` says the web "reads from
`bare/idx/`, the CLI from `bare/indexes/`", citing an `04/16 vault-docs-review-part-1` that is not
in this repo (presumably the vault team's).

**Impact is smaller than it looks.** The index read is wrapped in a bare `catch {}` and falls back to
the HMAC-derived named ref, which is correct for a single-branch vault. So this costs a wasted
round-trip today rather than blocking the open — which is precisely why it stayed hidden. It does
have one hard consequence: a CLI clone branch's head ref is **random**, not derived —

```python
ref_id = head_ref_id or ('ref-pid-snw-' + secrets.token_hex(6))   # Vault__Branch_Manager.py:57
```

— and is discoverable *only* through the branch index. Until we read `bare/indexes/`, a browser
client can never see a CLI session's working branch, only the published named HEAD. Fine for the
universe chat's use case; not fine for anything multi-branch.

## Delta 3 — the wrapped branch keys (not real)

The brief says the CLI's `key-rnd-imm-*` objects are "random per-branch keys, wrapped", and that
the browser "could not decrypt a CLI-encrypted branch without implementing unwrap". It cannot,
because there is no such layer. Every `crypto.encrypt(...)` call in sgit that touches a stored
object passes `read_key` — commits, trees, blobs, refs, the branch index, and the key objects
themselves. Decrypting **every object** in a CLI-made vault with the plain read key:

```
bare/refs/ref-pid-muw-b8d0bd5845d3        keys=commit_id
bare/refs/ref-pid-snw-b1a86ff37133        keys=commit_id
bare/indexes/idx-pid-muw-e8683e4c3598     schema=branch_index_v1
bare/data/obj-cas-imm-8496658abe0d        schema=commit_v1
bare/data/obj-cas-imm-4158bd75b784        schema=tree_v1
bare/data/obj-cas-imm-ea186f6f4b09        (binary blob, 49 bytes)
bare/keys/key-rnd-imm-01fab7d6eb1b36fa    keys=pem,type      ← PKI signing keypair
```

Nothing failed to decrypt. `key-rnd-imm-*` are `{type, pem}` — per-branch signing keypairs
referenced from the branch index as `public_key_id` / `private_key_id`, used for commit
attestation. They are irrelevant to reading content and need no unwrap. The successful tree walk
above is the practical proof: it decrypted a full CLI vault while ignoring `bare/keys/` entirely.

## "Both directions" — browser → CLI already works

Unmodified, today: mint with `vault-init.createVault`, write through `vault-mutations.addFile`,
`session.commit()`, `session.push()`, then `sgit clone`:

```
▸ Downloading vault index
▸ No branch index on server — single-branch fallback (named ref)
▸ Walking commits: 4 commits · Walking trees: 4 trees · Downloading blobs 6/6
Read-only clone ready: cloned/
  from-browser.md → "# Written in the browser"
  note.txt        → "browser round-trip"
```

sgit 0.16.0 ships a documented single-branch fallback precisely for vaults the web made, and it
works. The brief's acceptance criterion "a browser-minted vault → `sgit clone` checks out its
files" **already passes**. Only the CLI → browser half is broken.

One genuine constraint, unrelated to the reported deltas: **the two sides mint vaults with
different key families.** `vault-init.createVault` only accepts a simple token (`word-word-NNNN`,
`vault_id = SHA-256(token)[:12]`); sgit has no simple-token support at all (`grep` for
`sgraph-send-v1` in `sgit_ai/` returns nothing). So a browser-minted vault can only be cloned
read-only via its `{read_key_hex}:{vault_id}` form. Read-write both ways needs one side to gain the
other's key family — worth a decision, not a bug.

## Also found (not in the brief)

**a. The embed stack cannot accept a CLI read key.** `importReadKey()` expects base64url; sgit
emits hex behind a `sgit_public_read_` / `sgit_private_read_` prefix:

```
FAIL  CLI hex read key          → importReadKey: expected 32 bytes, got 48
FAIL  CLI prefixed read key     → Invalid character
OK    base64url of same bytes
```

This breaks the documented vault-peek pattern in `library/api/v0.1.92__vault__quick-start.md`
(`<sg-vault-key read-key="…">`) for anyone publishing a vault from the CLI — the exact workflow the
`sgit_public_read_` prefix exists to support.

**b. Our commit schema claim is stale.** `sg-vault-write.js`'s header says its schemas match the
CLI "exactly". The CLI writes `commit_v1` with `attestations`, `author_key_id` and
`author_signature`; we write `commit_v2` without them. Both sides read each other fine — readers
only need `tree_id` and `parents` — so this is a comment to correct, not a break. Same for the
clone-ref mutability label: we derive `ref-pid-muw-*` for a branch ref where the CLI writes
`ref-pid-snw-*` (the label is not hashed, and each client uses its own branch name, so they never
collide).

**c. `settingsFileId` has no CLI counterpart.** `deriveVaultKeys()` derives `file-id:settings` and
`file-id:index` domains that sgit does not implement; `fetchSettings()` will always 404 against a
CLI vault, which stores settings as a `.vault-settings` entry in the tree instead.

**d. Why our existing cross-check missed all of this.** `vault-pyodide` already compares Python and
JS derivation against known vectors — and one of its vectors (`pass:with:colons:deadbeef` →
`a903fc42…`) still matches sgit 0.16.0 exactly. But every vector uses a **bare** passphrase, so the
suite was structurally incapable of catching a key-prefix bug. That is the gap the new vectors fill.

## What to change

Four items, smallest first. Items 1 and 2 together restore CLI → browser interop.

1. **Strip the sgit key prefix on input.** A mirror of `strip_key_prefix()` applied in
   `parseVaultKey()` (`vault-client`) and at the `lastIndexOf(':')` sites in `sg-vault-connect` and
   `sg-vault-manager`. Accept all five prefixes — `sgit_private_vault_`, `sgit_private_read_`,
   `sgit_public_read_`, and the legacy `sgit_vk1_` / `sgit_rk1_`. Cheap and strictly additive: bare
   keys are unaffected.

2. **One answer for `idx-*` → `bare/indexes/`.** Revert `vault-id-utils` to `bare/indexes`, and
   route `vault-cache.cachedFetchRaw` through `fileIdToPath()` instead of hardcoding `bare/data/`.
   Then correct the vault team's tech-ref, which is the source of the wrong value.

3. **Accept hex read keys in the embed stack.** Let `importReadKey()` take hex or base64url after
   prefix-stripping, so a CLI-published read key works in `<sg-vault-key>`.

4. **A named error instead of a silent one** (the brief's ask 2). `"Vault not found: named HEAD ref
   missing"` cost someone a day. Worth noting that a format-version marker would *not* have helped
   here — the format never diverged; the key parsing did. The useful message is at the point of
   failure: report the ref ID that 404'd and that a `sgit_…` prefix was seen and stripped (or not).
   A vault-level version marker is still worth having, but as a separate, cheaper conversation:
   there is no such marker today (refs carry no schema field at all; `commit_v1`/`tree_v1`/
   `branch_index_v1` are per-object tags).

Landed as new pinned versions. Every existing version folder is untouched, so nothing pinned to a
current URL changes behaviour:

Verified end to end: a vault made by `sgit init && sgit commit && sgit push` now opens with the key
pasted **exactly as sgit prints it**, and the branch index read resolves to `bare/indexes/` and
returns 200 — so the named HEAD comes from the index rather than the HMAC fallback:

```
  refFileId        : ref-pid-muw-b8d0bd5845d3
  branchIndexFileId: idx-pid-muw-e8683e4c3598
  GET k8hbjt8x/bare/indexes/idx-pid-muw-e8683e4c3598   200
  /readme.md → "# From the CLI\n"
  /docs/n.md → "nested\n"
```

**Backwards compatibility.** No existing key form changes:

- Every current version folder is byte-identical — anything pinned to `v1.2.2`, `v0.1.3`, tools
  `v0.1.53` behaves exactly as today. This is additive publishing, not mutation.
- Bare keys (`hunter2:a1b2c3d4`), colon-containing passphrases, simple tokens and base64url read
  keys all derive identically through old and new modules — asserted by `key-compat.test.mjs`.
- Stripping only matches a prefix at the **start**, so `my_sgit_private_vault_x:abcd1234` is
  untouched.
- The `bare/idx` → `bare/indexes` move orphans nothing: no browser module has ever *written* an
  index object, so there was never data at `bare/idx/`. The read simply moves from a path that
  always 404'd to the one that holds the data.
- Routing `vault-cache` through `fileIdToPath()` is a no-op for every ID type in use except `idx-*`
  — `obj-*`, unrecognised IDs and explicit `bare/` paths resolve exactly as before, and no caller
  passes a `ref-*` into the cache (refs go through `fetchRef`).

**The one edge case**, stated plainly: a vault whose passphrase genuinely *begins* with
`sgit_private_vault_` (or another sgit prefix) now derives differently. Such a vault could never
have interoperated with sgit anyway — the CLI strips the same string — and
`parseVaultKey(key, { stripSgitPrefix: false })` recovers it.

Item 4 (the named error) is **not** done — it is a message change with no interop consequence, and
worth doing alongside the format-marker conversation rather than inside this fix.

## The interop test (the brief's ask 3)

We do not need theirs; ours is committed at `sgraph_ai_tools__static/tests/interop/`.

```bash
node sgraph_ai_tools__static/tests/interop/sgit-derivation-parity.test.mjs   # ~1s, no deps
node sgraph_ai_tools__static/tests/interop/key-compat.test.mjs               # old keys unchanged
./sgraph_ai_tools__static/tests/interop/run-roundtrip.sh                     # full round trip
```

The fast test compares the published modules against golden vectors generated by sgit's own crypto
(`regenerate-vectors.py`), and is the one to wire into CI. It reports **24 passed, 0 failed**
against the new versions, and failed 5 of those cases against the ones that shipped before them. The round-trip script
runs a real `sgit init/commit/push` against a ~145-line local KV store, opens the result with the
real browser modules, then does the reverse and `sgit clone`s it — no credentials, nothing beyond
localhost. `STRIP_PREFIX=0` reproduces the brief's failure exactly.

When sgit publishes a new version, regenerate the vectors and read the diff: empty means the format
held.

## Reply to graphs.sgit.ai, in short

The universe chat's vault drawer does not need to wait for a format migration. The blocker is that
our components do not strip sgit's key prefix, so they derive the wrong file IDs from a correct
key — a four-line fix on our side, no change to the wire format, no unwrap to implement. Their
delta 3 is a misreading: `key-rnd-imm-*` objects are PKI signing keys, and everything in a
CLI-made vault decrypts with the plain read key. Browser-minted vaults already clone with sgit
0.16.0 today, so the "both directions" framing overstates it. The fix has now landed as
`vault-client` v1.2.3 and friends (see **Status** above), so once those versions deploy the drawer
can pin them and drop the web-format-only caveat. Until then, removing the `sgit_private_vault_`
prefix by hand before pasting works against the currently published modules.
