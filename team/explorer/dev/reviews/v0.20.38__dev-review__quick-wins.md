## The Three Lines (window event emission)

The impl brief says Phase 1 includes "3 lines — highest impact change": adding window-level event emission to the infographic generator. Here is what those 3 lines actually are:

In `infographic-gen.js`, in the `SGL_LLM.REQUEST_COMPLETE` handler (lines 491-507), after `finish()` is called, add:

```javascript
// Line A: generation:complete
window.dispatchEvent(new CustomEvent('generation:complete', {
    detail: { generationId: genId, model, image: { src }, duration: (Date.now() - t0) / 1000 }
}));
```

In the `SGL_LLM.REQUEST_ERROR` handler (lines 510-514), add:

```javascript
// Line B: generation:error
window.dispatchEvent(new CustomEvent('generation:error', {
    detail: { generationId: null, model, error: ev.detail?.error }
}));
```

At the end of the SEND interceptor setup (after line 524, when `activeRequests.set()` is called), add:

```javascript
// Line C: generation:started
window.dispatchEvent(new CustomEvent('generation:started', {
    detail: { generationId: null, model, prompt: textarea.value.trim() }
}));
```

**Reality check:** These are more than 3 lines each, but the conceptual change is 3 event dispatches. However, `t0` (start time for duration) and `model` (the model used) must be captured in the right closure scope. Both are already in scope in the SEND interceptor handler. The `genId` is not known at `generation:started` time — it comes from the response. This is a minor API mismatch with the brief's event table.

**Risk:** Very low. These are additive changes. Existing functionality is unchanged. Playwright automation can immediately switch from polling to event-driven detection. This is the highest-value, lowest-risk change in the entire brief.

## sg-tool-manifest footer in infographic-gen/index.html

**How much work:** 2 lines of HTML, 1 CSS block.

Vault's `index.html` (lines 38-41) shows the exact pattern:

```html
<div id="manifest-bar">
    <script type="module" src="../../_common/js/sg-tool-manifest.js"></script>
    <sg-tool-manifest src="manifest.json"></sg-tool-manifest>
</div>
```

Plus the CSS to pin it to the bottom (from vault's style block):
```css
#manifest-bar { flex-shrink: 0; padding: 0 0.75rem 0.5rem; }
```

Infographic-gen's `index.html` is currently 29 lines, has no `<style>` block, and uses `<div id="layout-wrap">` for the main content. The body would need `display:flex; flex-direction:column; height:100%` similar to vault, plus the manifest bar at the bottom.

**One complication:** infographic-gen sets its layout height via JavaScript (`bus.style.cssText` sets `height:100%`). Adding the manifest bar footer requires the body layout to flex-column so the bar gets its natural height and the tool content fills the rest. This is a CSS layout change, not just a copy-paste. Estimated 20 minutes including testing.

**Risk:** Low. The manifest component fails silently. The CSS change is isolated to `index.html`.

## Phase 1 feasibility: 1 day?

The brief's Phase 1 scope is:
1. Create `core/sg-tool-api/v0/v0.1/v0.1.0/sg-tool-api.js` — the full `SgToolApi` class
2. Add 3 window event dispatches to infographic-gen.js
3. Wire infographic-gen to use `SgToolApi`

Items 2 (window events) and the manifest.json + footer are genuinely 1-2 hours combined.

Item 1 (creating `sg-tool-api.js`) is a full day on its own given the scope: `register()`, `activate()`, `_emit()`, `_log()`, meta API (6 methods), execution log, window registration. None of this exists today (PROPOSED — does not exist yet).

Item 3 (wiring infographic-gen to use SgToolApi) cannot start until item 1 is done and requires restructuring the module from procedural top-level script to something that can call `api.register()` and `api.activate()`. The current script uses `await` at top level (line 64) which works in a module context but makes wrapping harder.

**Recommendation:** Ship window events + manifest.json + footer as Phase 1a (< 2 hours, zero risk). Create `sg-tool-api.js` as Phase 1b (1 day, no infographic-gen changes). Wire them together as Phase 2.
