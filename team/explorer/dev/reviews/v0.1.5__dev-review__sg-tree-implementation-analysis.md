## 1. Implementation Feasibility: The Surgical Override Pattern

The architect brief proposes that v0.1.1 through v0.1.6 each contain an `sg-tree.js` file of ~50-130 lines that patches `SgTree.prototype` methods defined in v0.1.0's full class. The loading model described is:

```html
<script type="module" src=".../v0.1.0/sg-tree.js"></script>
<script src=".../v0.1.1/sg-tree.js"></script>
<script src=".../v0.1.2/sg-tree.js"></script>
```

**This has two separate problems.**

### 1.1 ES Modules and Prototype Patching Are Incompatible

The v0.1.0 file is loaded as `<script type="module">`. ES modules have their own scope — the `SgTree` class exported from v0.1.0 is not on `window`. The v0.1.1 file is loaded as a plain `<script>` (no `type="module"`), so it runs in global scope. It cannot access `SgTree.prototype` because `SgTree` was never placed on `window`.

To make prototype patching work, you need one of:

- **Option A:** v0.1.0 explicitly sets `window.SgTree = SgTree` after defining the class, then v0.1.1+ are plain scripts that reference `window.SgTree.prototype`. This breaks the ES module convention used everywhere else in this codebase.
- **Option B:** v0.1.1+ are also ES modules that `import { SgTree } from '../v0.1.0/sg-tree.js'` and then mutate the prototype. This works because ES module exports are live bindings — if v0.1.1 imports `SgTree` and patches its prototype, all other importers of that same module see the patched prototype. But this means v0.1.1's `sg-tree.js` must import from a relative path to v0.1.0, creating a cross-version dependency.
- **Option C:** All override files are plain `<script>` tags (not modules), including v0.1.0. This abandons ES modules entirely for sg-tree.

The brief's loading example (section 10.3) mixes `type="module"` for v0.1.0 and plain `<script>` for v0.1.1+. This will not work. The override scripts cannot see the class.

### 1.2 The send-browse v0.3.1 Precedent Is Different

The brief cites `send-browse-v031.js` as the proven pattern. But that file operates on a globally-scoped `SendBrowse` class. The SG/Send browse component is loaded as a plain script that registers a custom element, making its constructor available via `customElements.get('send-browse')`. That is why prototype patching works there.

If sg-tree follows the same pattern (plain scripts, global constructor, custom element registration in v0.1.0), the prototype patching will work. But this contradicts the ES module import syntax shown in section 5.1 of the brief (`import { SgTree } from '...'`).

**Verdict:** The surgical override pattern is feasible, but only if we commit to ONE of: (a) all plain scripts with global `SgTree`, or (b) all ES modules where v0.1.1+ import from v0.1.0 and mutate the imported class. We cannot mix the two.

## 2. The Filename Collision Problem

This is the hard blocker. Our IFD layering system (`build_ifd_latest.py` and `run-locally.sh`) copies files from each version folder in order into `_latest/`, with later versions overwriting earlier ones by filename. If v0.1.0 and v0.1.1 both contain `sg-tree.js`, then `_latest/sg-tree.js` will be v0.1.1's 80-line override — the 800-line base class is destroyed.

The IFD system was designed for tools (HTML pages, CSS, images) where a later version's `index.html` is a complete replacement for the earlier one. It was never designed for a "load both files in sequence" pattern.

### Option A: Version-Stamped Filenames

```
v0.1.0/sg-tree.js              → _latest/sg-tree.js
v0.1.1/sg-tree--patch-0.1.1.js → _latest/sg-tree--patch-0.1.1.js
v0.1.2/sg-tree--patch-0.1.2.js → _latest/sg-tree--patch-0.1.2.js
```

**Pros:** IFD layering works unchanged. Each file lands in `_latest/` without collision. Clear what each file is.

**Cons:** Consumers must know the exact patch filenames and load them in order. The loading boilerplate grows to 7 script tags with version-specific filenames. If a patch is added or removed, all consumers must update.

**My assessment:** Workable but ugly. The version-stamped names leak IFD internals to consumers.

### Option B: All-in-One File Per Version (Cumulative)

```
v0.1.0/sg-tree.js  → 800 lines (base)
v0.1.1/sg-tree.js  → 880 lines (base + editor mode)
v0.1.2/sg-tree.js  → 940 lines (base + editor + virtual scroll)
...
v0.1.6/sg-tree.js  → ~1200 lines (everything)
```

Each version's `sg-tree.js` is the complete, self-contained class up to that version. IFD layering works perfectly — `_latest/sg-tree.js` is always the most complete version. Consumer loads ONE file.

**Pros:** IFD layering works exactly as designed. Single script tag for consumers. No cross-version import dependencies. Each version is independently testable. The v0.2.0 consolidation step becomes trivial (v0.1.6 IS effectively v0.2.0).

**Cons:** Larger diffs between versions (the full file changes, not just the delta). Harder to see what changed between v0.1.2 and v0.1.3 in a code review — you'd need to diff the two complete files. Duplicates code across version folders (but this is how IFD already works for HTML/CSS in our tools).

**My assessment:** This is the right approach. It matches how every other module in our codebase works. The image editor (`sg-image-editor.js`) is a single file. The video module (`sg-video.js`) is a single file. Nobody loads 7 incremental patches.

### Option C: Keep Surgical Overrides But Change Where They Live

The override files get different names (e.g., `sg-tree-editor.js`, `sg-tree-virtual-scroll.js`) and live in the SAME version folder as the base:

```
v0.1.0/
  sg-tree.js           ← base class
  sg-tree-editor.js    ← editor mixin (imports SgTree, patches prototype, re-exports)
  sg-tree-virtual.js   ← virtual scroll mixin
  ...
```

Consumer picks what they need:

```js
import { SgTree } from '/core/sg-tree/v0/v0.1/v0.1.0/sg-tree.js';
import '/core/sg-tree/v0/v0.1/v0.1.0/sg-tree-editor.js';   // patches SgTree
import '/core/sg-tree/v0/v0.1/v0.1.0/sg-tree-virtual.js';   // patches SgTree
```

**Pros:** No IFD collision. Consumer can load only what they need (send-browse doesn't need editor mode). True modularity.

**Cons:** All files in one version folder — doesn't use IFD versioning at all. Can't ship editor mode independently from the base. Prototype mutation via side-effect imports is surprising.

**My assessment:** Interesting but abandons the IFD model the architect laid out. Better to do Option B and let consumers import the version that has the features they need (v0.1.0 for read-only, v0.1.1 for editable, etc.).

## 3. Comparison With How We Built Image/Video Tools

### Image editor pattern (sg-image-editor.js)

```js
import { getImageInfo, supportsAvif, renderOperations, exportImage, flattenTransparency }
    from '/core/image/v1/v1.0/v1.0.0/sg-image.js';

import './sg-image-crop.js';
import './sg-image-redact.js';
import './sg-image-text.js';
```

The image editor is a single orchestrator file that imports sub-components from the same folder. The core image library (`sg-image.js`) is a separate pure-JS module in `core/`. The sub-components (`sg-image-crop.js`, etc.) are sibling files in the same version folder, not in separate version folders.

Key differences from the sg-tree proposal:

| Aspect | Image editor | sg-tree (as proposed) |
|--------|-------------|----------------------|
| File structure | One orchestrator + sub-components in same folder | Base class + patches in separate version folders |
| Import model | ES module imports from same directory | Prototype patching across version boundaries |
| IFD interaction | No collision — different filenames | Collision — same filename across versions |
| Loading | Single entry point imports everything | Consumer loads 7 separate scripts in order |
| Versioning | Full file per version | Incremental deltas per version |

### Video module pattern (sg-video.js)

Single file, ~30 lines of exports at the top, everything self-contained. This is the simplest pattern and it works well for core libraries.

### Which is better?

The image editor pattern is better for sg-tree because:

1. It works with our IFD system without modification
2. It follows the ES module import chain that every other component uses
3. Sub-components as sibling files is proven (crop, redact, text)
4. A single entry point means consumers write one import statement

If sg-tree needs to be modular (some consumers want drag-and-drop, others don't), Option C from section 2 is the image-editor pattern applied to sg-tree: one base file plus optional feature files in the same folder.

## 4. Practical Concerns

### 4.1 Loading 7 Scripts in Production

The brief proposes consumers load 7 separate `<script>` tags before v0.2.0 consolidation. This means:

- 7 HTTP requests (even with HTTP/2 multiplexing, there's overhead)
- Strict ordering dependency — if v0.1.3 loads before v0.1.2, the prototype state is wrong
- No guarantee of execution order with `<script type="module">` (modules are deferred by default and execute in document order, but plain scripts block and execute immediately)
- If ANY script fails to load (CDN hiccup, typo in URL), the component is in a partially-patched state with no error handling

This is fragile for production use. The brief acknowledges this by saying consumer migration happens at v0.2.0, but then shows the 7-script loading pattern in section 10.3 as if it's a real deployment strategy.

### 4.2 `<script>` vs `<script type="module">`

The brief mixes these (section 10.3). This is not just a stylistic choice — it changes execution semantics:

- `<script type="module">`: deferred, own scope, strict mode, can use `import`/`export`
- `<script>`: synchronous, global scope, non-strict by default

For prototype patching to work, all override scripts MUST either:
- All be modules that import the class from v0.1.0 (creating cross-version import dependencies)
- All be plain scripts where v0.1.0 puts `SgTree` on `window` (abandoning ES modules)

### 4.3 Bundle Size

The brief estimates v0.1.0 at 800-1000 lines, with the full v0.1.6 state at roughly 800 + 80 + 60 + 50 + 100 + 40 + 50 = ~1180 lines. At ~40 bytes/line average, that's ~47KB unminified. Not a concern. Even a cumulative single file at 1200 lines is well within reason for a complex web component.

### 4.4 Caching

With 7 separate files, a change to v0.1.3 invalidates only that file's cache. With a single cumulative file, any change invalidates the entire cache. In practice, this doesn't matter because:

- Versions are immutable (rule 11 in CLAUDE.md) — content at a pinned URL never changes
- CloudFront serves versioned URLs with long cache TTLs
- A new version means a new URL, not a cache bust on an existing URL

The caching argument for separate files is moot given our immutable versioning.

## 5. Recommended Approach

I would build sg-tree using **Option B (cumulative all-in-one)** with one structural change inspired by the image editor pattern.

### File Structure

```
sgraph_ai_tools__static/
  core/
    sg-tree/
      v0/
        v0.1/
          v0.1.0/
            sg-tree.js           ← Full base class (~800-1000 lines)
            sg-tree-events.js    ← Frozen event constants
            sg-tree.css          ← Optional external theme
            README.md
          v0.1.1/
            sg-tree.js           ← COMPLETE class with editor mode baked in (~900 lines)
            sg-tree-events.js    ← Copy from v0.1.0 (unchanged)
            README.md            ← Documents what was ADDED vs v0.1.0
          v0.1.2/
            sg-tree.js           ← COMPLETE class with editor + virtual scroll (~960 lines)
            sg-tree-events.js    ← Copy from v0.1.0 (unchanged)
            README.md
          ...
          v0.1.5/
            sg-tree.js           ← COMPLETE class with everything through multi-tree drag
            sg-tree-events.js    ← Adds CROSS_TREE_DROP (v0.1.5 addition)
            README.md
          v0.1.6/
            sg-tree.js           ← COMPLETE class, all features (~1200 lines)
            sg-tree-events.js    ← Same as v0.1.5 (no new events)
            README.md
        v0.2/
          v0.2.0/
            sg-tree.js           ← Clean rewrite/refactor of v0.1.6, same API
            sg-tree-events.js
            sg-tree.css
            README.md
```

### How It Works With IFD

`build_ifd_latest.py` layers v0.1.0 through v0.1.6. Each version's `sg-tree.js` overwrites the previous. The result in `_latest/` is v0.1.6's complete file — which contains everything. This is exactly how IFD is supposed to work.

### How Consumers Load It

```html
<script type="module">
import { SgTree }     from '/core/sg-tree/v0/v0.1/v0.1.6/sg-tree.js';
import { SGT_EVENTS } from '/core/sg-tree/v0/v0.1/v0.1.6/sg-tree-events.js';
</script>
```

One import. Standard ES modules. No prototype patching. No load-order dependencies.

A consumer that only needs read-only tree can pin to v0.1.0. A consumer that needs editing can pin to v0.1.1. Each version is self-contained.

### Development Workflow

When building v0.1.1:

1. Copy v0.1.0/sg-tree.js to v0.1.1/sg-tree.js
2. Add the editor mode methods directly into the class body
3. Update the README to document what was added
4. v0.1.1's test page loads v0.1.1/sg-tree.js (one file) and runs v0.1.0 assertions + v0.1.1 assertions

The test accumulation strategy from the brief still works perfectly — each version's test page runs all prior tests against its own complete file.

### Why Not Surgical Overrides

The surgical override pattern adds complexity (cross-version imports, prototype mutation, load-order fragility) to solve a problem we don't have. The "problem" it solves is keeping version diffs small, but:

- Git diff between v0.1.0/sg-tree.js and v0.1.1/sg-tree.js shows exactly what was added
- Each version's README documents the delta
- The IFD system was designed for complete-file replacement, not incremental patching

## 6. Questions That Need Answering Before Coding

### Blocking

1. **Does the architect agree to Option B (cumulative files)?** The entire implementation plan changes depending on this. The brief is written around surgical overrides. If the architect insists on that pattern, we need to solve the IFD collision problem first — either by modifying `build_ifd_latest.py` or by using version-stamped filenames.

2. **Where does sg-tree live: `core/` or `components/`?** The brief puts it in `core/sg-tree/`. But sg-tree is a Web Component with Shadow DOM and CSS — it has UI. Every other Web Component in this repo lives in `components/`. The `core/` tier is documented as "Pure JS modules. No UI." (CLAUDE.md). A Web Component with Shadow DOM rendering is not a pure JS module.

3. **ES module or plain script?** The brief shows both patterns. If ES module (which matches our codebase convention), prototype patching across files requires explicit imports. If plain script, we abandon the pattern used by every other module. This must be decided before writing line 1.

4. **What does "latest" mean for sg-tree?** Our tools use "latest" which resolves via IFD layering. If a consumer imports from `_latest/sg-tree.js`, they get the highest version. Is that always desirable? A consumer that only wants read-only tree (v0.1.0) would get drag-and-drop and editor mode they didn't ask for.

### Non-Blocking but Important

5. **Should sg-tree-events.js be truly immutable across versions?** The brief says events are frozen at v0.1.0 but v0.1.5 adds `CROSS_TREE_DROP`. If we use cumulative files, the v0.1.5 events file supersedes v0.1.0's — IFD handles this cleanly. But the "frozen" language in the brief may confuse future developers.

6. **Test runner module:** The brief's question #2 (section 15) about a shared test runner is important. With cumulative files, each test page imports the same sg-tree.js from its own version folder, making test pages simpler. But a shared assertion library (`_test-helpers.js`) still makes sense.

7. **ARIA implementation depth:** The brief says ARIA from v0.1.0 (section 16). How complete? Full `role="tree"` / `role="treeitem"` / `aria-expanded` / `aria-selected` / `aria-level`? Or a subset? ARIA for trees is well-specified (WAI-ARIA Practices) but adds ~50-80 lines to the rendering code.

8. **Virtual scrolling complexity:** The brief puts virtual scrolling at v0.1.2. This is one of the hardest features to implement correctly (intersection observer vs scroll-position-based, row height measurement, keyboard navigation through virtualised rows). Does v0.1.0 need to be structured to accommodate this, or is v0.1.2 allowed to refactor the rendering pipeline?
