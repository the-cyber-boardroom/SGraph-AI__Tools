# Dev Review: sg-tree API Contract v0.19.11

**Date:** 2026-04-04
**Reviewer:** Dev, Explorer Team
**Brief:** `v0.19.11__architect-review__sg-tree-api-contract.md`
**Prior art:** `v0.1.5__dev-review__sg-tree-implementation-analysis.md` (blocking concerns already raised; this review confirms resolution status and adds new detail)

## Implementability Verdict

**NEEDS CLARIFICATION** — The brief resolves the filename-collision problem from the prior dev review (v0.1.5) by adopting version-stamped filenames (`sg-tree--v0.1.1.js`). That fix is correct. However, the ES module execution-order concern is NOT resolved, three public API methods are missing from Section 5.2, and the `window.SgTree` pattern directly contradicts the reference implementation (sg-layout). These require explicit decisions before an implementing agent starts writing code.

---

## What's Well-Specified

**Section 4 — Canonical Data Format.** Complete. The `{id, label, type, children, icon, meta, badge, disabled}` shape has clear rules, required vs optional is explicit, and the uniqueness constraint on `id` is called out. An implementing agent can write the `setData` validation logic directly from this.

**Section 5.4 — CSS Custom Properties.** Ready to copy-paste into the Shadow DOM styles block. All property names follow a consistent `--sgt-` prefix, defaults are supplied, and the theming contract (piercing the shadow boundary via CSS custom properties) matches sg-layout's proven approach.

**Section 6.1 — SGT_EVENTS.** Ready to implement. The `Object.freeze()` requirement is explicit, the event name strings follow a clear `sg-tree:noun-verb` pattern, and the inline payload comments (`// { id, node, path }`) cover all events. The `composed: true` requirement in Section 6.2 is important and correctly specified.

**Section 8.1 — Flat List Rendering.** The decision to render a flat list of rows with `padding-left` for depth (rather than nested DOM) is architecturally sound and clearly motivated. The `_buildVisibleList()` concept (walk the tree, skip collapsed subtrees, emit flat array) gives an implementing agent a concrete algorithm to build toward.

**Section 11 — Version Sequence + Test Accumulation Strategy.** The `tests accumulate, never replace` table is excellent. Each version's test file re-running all prior assertions is the right regression strategy. The scope of each v0.1.x version (what it overrides, what it adds) is detailed enough to start coding.

**Section 12 — v0.1.0 Test Plan.** The 30-assertion table is specific and implementable. Tests 1-23 are mechanical (fire event, check flag, compare value). Tests 24-30 cover the less obvious behaviours (filter, badge, disabled, empty state, performance gate).

## Missing Implementation Detail

**1. (BLOCKING) ES module execution order for surgical overrides is unresolved.**

Section 10.3 shows the multi-script loading pattern. The prior dev review (v0.1.5, Section 1.1) identified that mixing `<script type="module">` for v0.1.0 with plain `<script>` for v0.1.1+ does not work: a module's scope is private, so `window.SgTree` is not set unless explicitly assigned. Section 10.1 does specify `window.SgTree = SgTree;` after `customElements.define()` in v0.1.0. But Section 10.3 still shows v0.1.0 loaded as `<script type="module">` and v0.1.1+ also as `<script type="module">`.

If ALL files are ES modules, prototype patching via `window.SgTree` is unnecessary — the override module can `import { SgTree } from '../v0.1.0/sg-tree.js'` and mutate the prototype directly. If the files are NOT modules, the `export class SgTree` in Section 5.1 and the `import { SgTree }` usage in Section 5.1's HTML example are invalid.

The brief cannot have both. **Decision required:** are surgical override files plain scripts or ES modules?

- If plain scripts: v0.1.0 must NOT use `export`, must set `window.SgTree = SgTree`, and Section 5.1's `import { SgTree }` usage does not apply until v0.2.0.
- If ES modules: `window.SgTree = SgTree` in v0.1.0 is unnecessary, and each override imports from v0.1.0's relative path directly.

**2. (BLOCKING) `window.SgTree` contradicts the sg-layout reference pattern.**

The brief repeatedly cites sg-layout as the pattern to follow. sg-layout does not use `window.SgLayout`. It uses `export { SgLayout, SGL_EVENTS }` at the end of the file (confirmed by reading `sgraph_ai_tools__static/core/sg-layout/v0.1.0/sg-layout.js`). The surgical override method via `window.*` is described as the "v1.3.0 IFD convention" but sg-layout — the explicit reference — does not implement it. If this pattern exists, it needs a different reference example in the codebase, or sg-layout needs to be updated.

An implementing agent following "do what sg-layout does" will produce an ES-module-only file with no `window.SgTree` assignment, which then makes the v0.1.1–v0.1.6 surgical override pattern unworkable.

**3. (BLOCKING) `getScrollTop()` / `setScrollTop()` methods are missing from Section 5.2.**

Section 9 (Serialisation) uses both `tree.getScrollTop()` and `tree.setScrollTop(saved.scrollTop)` in the save/restore example. `getLayoutState()` also internally calls `this._viewport?.scrollTop`. Neither `getScrollTop` nor `setScrollTop` appear in the Section 5.2 public methods table. An implementing agent writing to the contract in Section 5.2 will not know to implement these methods, and the serialisation round-trip will silently fail (the getter returns `undefined`, the setter is not called).

**4. (NEEDS ANSWER) What does `getSelectedId()` return in multi-select mode before v0.1.3?**

Section 5.2 defines `getSelectedId()` returning `string | null`. Section 11 (v0.1.3) says `getSelectedId` is overridden to be backwards-compatible (single select returns `[id]`). But `selectable: 'multi'` is listed as a valid value in Section 5.3's configuration table — it is a v0.1.0 property. If a v0.1.0 consumer sets `selectable="multi"` on the element, what does `getSelectedId()` return when multiple nodes are selected? The v0.1.0 base class does not have `getSelectedIds()`. Does v0.1.0 silently ignore multi-select? Does it throw? Does it return the last selected?

**5. (NEEDS ANSWER) `filter(fn)` is listed in Section 5.2 but implemented in v0.1.6.**

`filter(fn)` appears in the Section 5.2 public methods table (the v0.1.0 contract), and test #26 in Section 12 asserts it works in v0.1.0. But Section 11 (v0.1.6) says `filter(fn)` is added by v0.1.6's surgical override of `_buildVisibleList`. Is v0.1.0 supposed to implement a basic `filter(fn)`, with v0.1.6 only enhancing the rendering of it? Or is test #26 a mistake — should it be a v0.1.6 test? The test count table in Section 11 shows v0.1.0 at 30 assertions, which includes test #26. An implementing agent will build `filter(fn)` in v0.1.0 if they follow the test plan, but then wonder what v0.1.6 actually adds.

**6. (NEEDS ANSWER) `expandPath(id)` scroll behaviour is underspecified.**

Section 5.2 says `expandPath(id)` "Expand all ancestors of a node (useful for 'reveal file')". Test #19 asserts "All ancestors expanded, node scrolled into view". Does `expandPath` also call `scrollTo`? Or does the consumer call `scrollTo` separately? The test name implies scrolling is part of `expandPath`, but the method description does not say so. If scrolling is part of `expandPath`, then `scrollTo` can be called internally and the consumer does not need to call it separately.

**7. (NICE TO HAVE) `_buildVisibleList` is referenced but not specified.**

Multiple sections mention this internal method as the algorithm that produces the flat ordered list for rendering. The brief does not describe its expected output format (array of `{node, depth}` objects? array of node ids with a depth lookup?). This is internal so the implementing agent has latitude, but specifying the shape avoids rework when v0.1.6 overrides it for filter/sort.

## Implementation Risks

**Risk 1: Shadow DOM + `scrollTo` on elements not yet rendered.**

`expandPath(id)` must scroll the revealed node into view. If the render is synchronous (re-render entire flat list on expand), `scrollIntoView()` can be called immediately after. If rendering is batched (via `requestAnimationFrame`), the DOM element may not exist when `scrollTo` is called. The brief does not specify the rendering model (synchronous or batched). v0.1.2's virtual scrolling override will change this fundamentally. The v0.1.0 base must be written with awareness of which approach it commits to.

**Risk 2: Connector lines via `::before` pseudo-elements require per-row context.**

Section 8.2 says connector lines use `::before` pseudo-elements on each row. But a connector line requires knowledge of whether the node is the "last child" of its parent (to draw a corner rather than a T-junction). In a flat list model, each row is a `<div>` at the same DOM depth — the `::before` CSS cannot know if a row is the last sibling. The brief defers connector lines to v0.1.6, but the v0.1.0 `_renderRow` method output shape must already accommodate the `data-is-last-child` attribute (or equivalent) that v0.1.6 will need. If v0.1.0 does not render this attribute, v0.1.6's `_renderRow` override must re-derive it, which means rebuilding parent-child context at render time.

**Risk 3: Multi-select `selectable` config with single-select implementation.**

Section 5.3 lists `selectable: 'single' | 'multi' | 'none'` as a v0.1.0 configuration property. If the v0.1.0 implementation only does single-select (with multi-select deferred to v0.1.3), what happens when `selectable="multi"` is set in v0.1.0? Silent fallback to single-select? Warning log? Throw? An implementing agent must decide. The safest approach: v0.1.0 parses the attribute, stores it, and `multi` behaves identically to `single` in v0.1.0 (with a TODO comment). v0.1.3's surgical override then implements the multi behaviour for real.

**Risk 4: `_renderRow` return type is used by three surgical overrides.**

v0.1.1, v0.1.4, and v0.1.6 all override `_renderRow`. The override pattern (Section 11) shows `_renderRow` returning a DOM element (`return el`). If the v0.1.0 implementation of `_renderRow` mutates the flat list in place (pushes to an array, does not return), the surgical overrides break. The return type of `_renderRow` is a de-facto interface contract that must be established in v0.1.0.

## Surgical Override Concerns

**The `window.SgTree` pattern is not used by sg-layout (the stated reference).**

This is the central concern. sg-layout ends with:
```js
customElements.define('sg-layout', SgLayout);
export { SgLayout, SGL_EVENTS };
```
There is no `window.SgLayout = SgLayout` anywhere in the file. The IFD convention document (`v1.3.0__ifd__surgical-overrides-version-stamped-filenames.md`) is referenced but not available to verify. If sg-tree v0.1.0 exports via `window.SgTree` AND uses `export class SgTree`, that is technically valid — both can coexist in a module. But it is non-standard and means the consuming pattern for surgical overrides (plain scripts reading `window.SgTree`) is fundamentally different from how consumers import sg-layout.

**Concrete consequence for v0.1.1 implementation:**

The brief shows the v0.1.3 override pattern as:
```js
const { SgTree } = window;
const _originalOnNodeClick = SgTree.prototype._onNodeClick;
SgTree.prototype._onNodeClick = function(e, nodeId) { ... };
```

For this to work in a `<script type="module">`:
- `window.SgTree` must be set before this module executes
- `<script type="module">` files are deferred — they execute after the HTML parses, in document order
- v0.1.0's `<script type="module">` and v0.1.1's `<script type="module">` are both deferred, so v0.1.0 executes first (document order), sets `window.SgTree`, then v0.1.1 reads it

This actually works IF both are modules and IF v0.1.0 sets `window.SgTree = SgTree` before its module exits. The key risk is that `window.SgTree` is set at module evaluation time (synchronous, end of v0.1.0), but ANY consumer that imports v0.1.0 directly via `import { SgTree } from '...'` in their own module will get the class BEFORE v0.1.1 has patched it — unless their module executes after v0.1.1. The document `<script>` order controls this, but dynamic imports do not.

**Recommendation:** Pin down the execution model. The safest statement is: "surgical override files must be loaded as `<script type="module">` in the HTML after the base, and consumers must not dynamically import sg-tree before all overrides have loaded."

## Test Plan Gaps

**Gap 1: No test for `SELECTION_CHANGED` event.**

Section 6.1 defines `SELECTION_CHANGED: 'sg-tree:selection-changed'` with payload `{ selectedIds }`. The Section 12 test plan covers `NODE_SELECTED` and `NODE_DESELECTED` but has no assertion that `SELECTION_CHANGED` fires and carries the correct `selectedIds` array. This is especially important as the canonical way for consumers to track selection state without caring about single vs multi mode.

**Gap 2: No test for `DATA_CHANGED` event.**

Section 6.1 defines `DATA_CHANGED: 'sg-tree:data-changed'` with payload `{ root }`. No test in Section 12 verifies this fires when `setData()` is called, or that the payload contains the root node. This is used by v0.1.1 (editor mode calls `DATA_CHANGED` after mutations).

**Gap 3: No test for `READY` event.**

Section 6.1 defines `READY: 'sg-tree:ready'`. Section 12 has no test that this event fires after `connectedCallback`, and no test for what constitutes "ready" (after first render? after `setData` is called?). This ambiguity means v0.1.0 could fire `READY` immediately on connect (before any data) or after first `setData` call, and there would be no regression test to catch a change.

**Gap 4: No ARIA test.**

Section 11 (v0.1.0 scope) explicitly lists "ARIA roles" as a v0.1.0 deliverable. None of the 30 tests in Section 12 check ARIA attributes (`role="tree"`, `role="treeitem"`, `aria-expanded`, `aria-selected`, `aria-level`). The ARIA contract is not testable from a consumer's event listener — it requires querying the shadow DOM. This should be a test assertion.

**Gap 5: No test for `selectable="none"`.**

Section 5.3 lists `selectable: 'none'` as a valid mode. No test verifies that clicking a node when `selectable="none"` does NOT fire `NODE_SELECTED`.

**Gap 6: No test for `expandableTypes` configuration.**

Section 5.3 lists `expandableTypes: string[]` with default `['folder']`. No test verifies that a node with `type: 'entity'` is NOT expandable by default, and that adding `'entity'` to `expandableTypes` MAKES it expandable. This is one of the less obvious features and warrants explicit coverage.

## Suggested First Implementation Steps

These are ordered to unblock the most downstream work first:

**Step 1: Decide the module/script loading model (before writing a single line of sg-tree code).**
Document the decision in the v0.1.0 README: are surgical overrides plain scripts or ES modules? This decision determines whether `window.SgTree = SgTree` is in v0.1.0. Without this decision, the implementing agent cannot write the last 5 lines of `sg-tree.js`.

**Step 2: Add the missing methods to Section 5.2 before implementation.**
Add `getScrollTop()` and `setScrollTop(value)` to the public API table. Decide whether `expandPath(id)` calls `scrollTo()` internally. Update the brief (or raise with Architect to update). This prevents an implementing agent from writing v0.1.0's full class and discovering the serialisation round-trip is broken.

**Step 3: Implement `sg-tree-events.js` first.**
It is the simplest file (15 lines), it is self-contained, and test #1 passes immediately. This gives the implementing agent a working baseline before touching the Shadow DOM complexity.

**Step 4: Implement `_buildVisibleList(node, result = [], depth = 0)` as a standalone function before the class.**
Document its output shape (e.g., `Array<{node: TreeNode, depth: number}>`). Test it with a plain JS tree object before wiring it into the custom element. This is the algorithmic core of the component and is the most likely source of bugs.

**Step 5: Build the Shadow DOM structure and styles (`connectedCallback` + `SHADOW_STYLES`) with no data.**
Verify the component registers, renders its viewport shell, and fires `READY`. Test #2 passes. The component exists in the DOM and can be queried.

**Step 6: Wire `setData` → `_buildVisibleList` → `_renderVisibleRows`.**
Tests #3 and #4 pass (correct row count, folders collapsed by default). Do not implement keyboard nav yet.

**Step 7: Implement click handlers for expand/collapse and selection.**
Tests #5-#9 pass.

**Step 8: Implement keyboard nav.**
Tests #10-#16 pass. This is the most complex behavioural state machine in v0.1.0.

**Step 9: Implement programmatic API methods (`expandAll`, `collapseAll`, `expandPath`, `select`, `scrollTo`, `getExpandedIds`, `setExpandedIds`, `getScrollTop`, `setScrollTop`).**
Tests #17-#22 pass.

**Step 10: Implement configuration properties (`showRoot`, `indentPx`, `iconMap`, `expandableTypes`, `sortFn`) and remaining features (`filter`, `badge`, `disabled`, empty state).**
Tests #23-#30 pass.

**Step 11: Write the v0.1.0 test HTML file.**
The test harness is a simple `assert(condition, label)` function and a `showSummary()` that displays pass/fail counts. Pattern is taken from sg-layout's existing test page.

## Appendix: Live Bug Report — sg-openrouter-generation double registration

**Reported:** 2026-04-04 during the session
**Tool affected:** infographic-gen v0.1.12 (`tools/v0/v0.1/v0.1.12/en-gb/infographic-gen/index.html`)
**Console error:** `Uncaught SyntaxError: Duplicate export of 'SgOpenrouterGeneration'` at `sg-openrouter-generation.js:577`

**Observation:** The browser reports line 577 but the current repo file has 497 lines with a single export. The file is clean in the repo. Root cause is most likely a browser-cached version of the file from a previous session/branch that had a duplicate export.

**Immediate fix applied:** Added `customElements.get()` guard around `customElements.define()` in `sg-openrouter-generation.js` to prevent runtime double-registration errors (commit 8059d6a).

**Remaining work for Dev:**
1. Investigate whether a previous commit on any branch introduced a duplicate export into `sg-openrouter-generation.js` that the browser cached
2. Check if the dev server at localhost:10063 has any caching behaviour that could serve stale files
3. Consider adding `Cache-Control: no-cache` headers for JS files in the dev server config if one exists
4. Verify the `customElements.get()` guard is sufficient for production use (it is — this is the idiomatic pattern)
5. Document in the dev notes: any component that calls `customElements.define()` should use this guard pattern to be safe against module double-loading

The "Duplicate export" SyntaxError (rather than a customElements TypeError) suggests the browser ran a version of the module that literally had `export class SgOpenrouterGeneration` AND `export { SgOpenrouterGeneration }` in the same file — a common mistake when adding a named export block to an already-exported class. The guard won't prevent that SyntaxError (it's caught at parse time), but will prevent the runtime double-define error if the module is somehow evaluated twice.

**User action required:** Hard refresh (`Cmd+Shift+R` / `Ctrl+Shift+R`) to clear browser module cache.
