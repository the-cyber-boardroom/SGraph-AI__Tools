# SGit-Compatible Vault Write — Design Document

**Version:** v0.1.14  
**Date:** 2026-04-03  
**Context:** OpenRouter Tool (tools/v0/v0.1/v0.1.14/en-gb/openrouter/index.html)

---

## 1. What We're Trying to Do

When a user enters their vault key and loads the OpenRouter tool, we read two paths:

- `openrouter/user/config.json` — stores the user's OpenRouter API key
- `openrouter/admin/config.json` — stores the management key for provisioned-key admin

If either file **doesn't exist** in the vault (404 on read), we want to **create it** with an initial JSON payload, then allow the user to save updates to it.

The user requirement is that these writes must be **SGit-compatible** — meaning the vault should contain proper commit/tree/blob objects and branch refs, not bare raw files. This preserves the vault's audit trail and compatibility with other SGit-aware tools (vault-browser, sg-send-cli, etc.).

## 2. What I Know About the Vault Object Model

### 2.1 File ID Format (from `vault-id-utils.js`)

```
{type}-{derivation}-{mutability}-{hex12}
```

| Segment | Values | Meaning |
|---------|--------|---------|
| type | `obj`, `ref`, `key`, `idx` | Object class |
| derivation | `cas`, `pid`, `rnd` | How the ID was derived |
| mutability | `imm`, `muw` | Immutable or mutable-write |

Storage paths (from `fileIdToPath()`):
- `obj-*` → `bare/data/{id}`
- `ref-*` → `bare/refs/{id}`
- `idx-*` → `bare/indexes/{id}`
- `key-*` → `bare/keys/{id}`

### 2.2 Object Schemas

**Blob** — raw content, content-addressed:
```
ID: obj-cas-imm-{sha256[:12]}
Path: bare/data/obj-cas-imm-{hex}
Content: encrypted raw bytes (the config JSON)
```

**Tree** — directory listing, content-addressed:
```json
{
  "schema": "tree_v1",
  "entries": [
    { "path": "config.json", "blob_id": "obj-cas-imm-{hex}", "size": 123 }
  ]
}
```
ID: `obj-cas-imm-{sha256[:12]}` of the tree JSON

**Commit** — snapshot pointer, content-addressed:
```json
{
  "schema": "commit_v1",
  "message": "Add openrouter/user/config.json",
  "tree_id": "obj-cas-imm-{hex}",
  "parents": [],
  "timestamp_ms": 1700000000000,
  "branch_id": "ref-pid-muw-{hex}",
  "author_key_id": null,
  "signature": null
}
```
ID: `obj-cas-imm-{sha256[:12]}` of the commit JSON

**Ref** — branch head pointer, mutable:
```json
{
  "schema": "ref_v1",
  "version": 1,
  "commit_id": "obj-cas-imm-{hex}"
}
```
ID: `ref-pid-muw-{hex}` (derived from vault passphrase — `keys.refFileId`)

### 2.3 Read API (known, working)

```
GET {apiBaseUrl}/api/vault/read/{vaultId}/{encodeURIComponent(path)}
```

Where `path` = `fileIdToPath(fileId)` e.g. `bare/data/obj-cas-imm-abc123`.

Response body: IV (12 bytes) prepended to AES-256-GCM ciphertext.

## 3. What I Don't Know (Need Guidance)

### 3.1 Write API Endpoint

**Assumed:**
```
PUT {apiBaseUrl}/api/vault/write/{vaultId}/{path}
Authorization: Bearer {writeKey}
Content-Type: application/octet-stream
Body: <IV 12 bytes> + <AES-256-GCM ciphertext>
```

**Questions:**
- Is `PUT` correct, or is it `POST`?
- Is `Authorization: Bearer {writeKey}` the correct auth header?
- Is the path format the same as for reads (e.g. `bare/data/obj-cas-imm-abc123`)?
- Is there a different endpoint for mutable files (`bare/refs/`) vs immutable (`bare/data/`)?

### 3.2 Commit Signatures

Commit objects have `author_key_id` and `signature` fields. PKI signing requires a private key.

**Question:** Can browser-originated commits omit signatures (set to `null`) and still be valid/accepted by the vault? Or is there a lightweight signing approach (e.g. HMAC with the write key)?

### 3.3 Tree Structure — Flat vs Nested

For path `openrouter/user/config.json`, should the tree be:

**Option A — Nested trees (full git-style):**
```
root-tree:
  entries: [{ path: "openrouter", tree_id: "..." }]

openrouter-tree:
  entries: [{ path: "user", tree_id: "..." }]

user-tree:
  entries: [{ path: "config.json", blob_id: "..." }]
```

**Option B — Flat tree with full paths:**
```
root-tree:
  entries: [{ path: "openrouter/user/config.json", blob_id: "..." }]
```

**Question:** Which does SGit expect?

### 3.4 Branch / Ref Strategy

**Question:** Should we use the vault's primary `refFileId` (the main branch head), or create a separate named branch ref for `openrouter/`? If the vault already has a main branch with existing commits, we'd need to read the current ref to get the parent commit ID before writing a new commit.

## 4. Proposed Implementation (Browser-Side)

### 4.1 Helper: `encryptObject(key, obj)`

```js
async function encryptObject(key, obj) {
    const iv   = crypto.getRandomValues(new Uint8Array(12));
    const data = new TextEncoder().encode(JSON.stringify(obj));
    const ct   = await crypto.subtle.encrypt({ name: 'AES-GCM', iv }, key, data);
    const out  = new Uint8Array(12 + ct.byteLength);
    out.set(iv);
    out.set(new Uint8Array(ct), 12);
    return out;
}
```

### 4.2 Helper: `sha256Hex(bytes)` for content-addressed IDs

```js
async function sha256Hex(bytes) {
    const hash = await crypto.subtle.digest('SHA-256', bytes);
    return Array.from(new Uint8Array(hash))
        .map(b => b.toString(16).padStart(2, '0')).join('').slice(0, 12);
}
```

### 4.3 Helper: `writeEncrypted(vault, path, encryptedBytes)`

```js
async function writeEncrypted(vault, path, encryptedBytes) {
    const url = `${vault.apiBaseUrl}/api/vault/write/${vault.vaultId}/${encodeURIComponent(path)}`;
    const res = await fetch(url, {
        method: 'PUT',
        headers: {
            'Authorization': `Bearer ${vault.keys.writeKey}`,
            'Content-Type': 'application/octet-stream'
        },
        body: encryptedBytes
    });
    if (!res.ok) throw new Error(`Write failed: ${res.status}`);
}
```

### 4.4 Full SGit Write Flow

```js
async function sgitWriteFile(vault, filePath, content) {
    const aesKey = vault.keys.readKey;   // AES-256-GCM (encrypt + decrypt)

    // 1. Blob
    const blobBytes = new TextEncoder().encode(JSON.stringify(content));
    const blobHex   = await sha256Hex(blobBytes);
    const blobId    = `obj-cas-imm-${blobHex}`;
    const blobEnc   = await encryptObject(aesKey, content);
    await writeEncrypted(vault, `bare/data/${blobId}`, blobEnc);

    // 2. Tree
    const parts    = filePath.split('/');
    const fileName = parts[parts.length - 1];
    const tree     = { schema: 'tree_v1', entries: [{ path: fileName, blob_id: blobId, size: blobBytes.length }] };
    const treeEnc  = await encryptObject(aesKey, tree);
    const treeStr  = JSON.stringify(tree);
    const treeHex  = await sha256Hex(new TextEncoder().encode(treeStr));
    const treeId   = `obj-cas-imm-${treeHex}`;
    await writeEncrypted(vault, `bare/data/${treeId}`, treeEnc);

    // 3. Read current ref for parent commit
    let parentCommitId = null;
    try {
        const refEnc  = await readFile(vault, vault.keys.refFileId);
        const refJson = JSON.parse(new TextDecoder().decode(refEnc));
        parentCommitId = refJson.commit_id || null;
    } catch { /* no existing ref — first commit */ }

    // 4. Commit
    const commit = {
        schema:       'commit_v1',
        message:      `Add ${filePath}`,
        tree_id:      treeId,
        parents:      parentCommitId ? [parentCommitId] : [],
        timestamp_ms: Date.now(),
        branch_id:    vault.keys.refFileId,
        author_key_id: null,
        signature:    null
    };
    const commitEnc = await encryptObject(aesKey, commit);
    const commitStr = JSON.stringify(commit);
    const commitHex = await sha256Hex(new TextEncoder().encode(commitStr));
    const commitId  = `obj-cas-imm-${commitHex}`;
    await writeEncrypted(vault, `bare/data/${commitId}`, commitEnc);

    // 5. Update ref
    const ref    = { schema: 'ref_v1', version: 1, commit_id: commitId };
    const refEnc = await encryptObject(aesKey, ref);
    await writeEncrypted(vault, `bare/refs/${vault.keys.refFileId}`, refEnc);
}
```

**Note:** The AES key from `openVault()` / `deriveVaultKeys()` is currently imported with `['decrypt']` only. For write, we'd need it also with `['encrypt']`. This requires either re-importing the raw key bytes with `['encrypt', 'decrypt']`, or using a separate encrypt call with the raw bytes.
