## Architecture Decisions

### AD-1: Tools pass through llm:send, not a separate event

The simplest extension to the existing request pipeline: callers include `tools` and
`tool_choice` in the `llm:send` event detail. `sg-llm-request` forwards them in the
request body. No new send event needed.

```js
bus.dispatchEvent(new CustomEvent('llm:send', {
  detail: {
    messages: [...],
    tools: [{ type: 'function', function: { name, description, parameters } }],
    tool_choice: 'auto',               // optional, default 'auto'
    response_format: { type: 'json_schema', json_schema: {...} }  // optional
  }
}));
```

### AD-2: Tool calls normalised to OpenAI format across all providers

`sg-llm-request` converts provider-specific tool call formats to a canonical shape:

```js
[{ id: string, type: 'function', function: { name: string, arguments: string } }]
```

Anthropic `tool_use` blocks (where `input` is already an object) are converted:
`arguments = JSON.stringify(input)`.

This means `sg-tool-runner` only needs to handle one format.

### AD-3: Dedicated TOOL_CALLS event in addition to REQUEST_COMPLETE

`sg-llm-request` fires `llm:tool-calls` whenever tool calls are present in a response,
alongside `llm:request-complete`. This lets `sg-tool-runner` act without inspecting
every REQUEST_COMPLETE event.

### AD-4: sg-tool-runner is a headless Web Component on [data-llm-bus]

Placed alongside `sg-llm-request` on the page (not inside sg-layout). Listens for
`llm:tool-calls`, executes tools, emits `llm:tool-results-complete` with all results
and the updated messages array ready for the next `llm:send`.

### AD-5: VFS integration via [data-vfs-bus] ancestor walk

`sg-tool-runner` finds the VFS bus by walking ancestors for `[data-vfs-bus]`, then
dispatches `vfs:*-request` events directly on it (sg-vfs-bus listens there). Responses
come back on the same element. If no VFS bus found, VFS tools return an error.

### AD-6: JS sandbox uses sandboxed iframe + postMessage

Sandboxed iframe with `sandbox="allow-scripts"` (no `allow-same-origin`) gives a null
origin and no access to parent DOM, cookies, or localStorage. Code runs via
`AsyncFunction` constructor. Timeout enforced with `setTimeout` + abort.

Python (Pyodide) deferred to Phase 3.

### AD-7: Agentic loop inline in tool page (Phase 1), extracted later (Phase 2)

Phase 1 embeds the loop logic in the tool page's inline module script. Phase 2 extracts
it to `sg-agentic-loop` with full trace visualisation, human-in-the-loop, and cost
budget.

### AD-8: Anthropic tool definitions converted from OpenAI format

Tools are always authored in OpenAI JSON schema format (the standard). `sg-llm-request`
converts to Anthropic format when the provider is `anthropic`:

| OpenAI field | Anthropic field |
|---|---|
| `function.name` | `name` |
| `function.description` | `description` |
| `function.parameters` | `input_schema` |

- `buildRequestBody()` now has fourth param `opts = {}`
- `_buildOpenAIBody`: adds `tools`, `tool_choice`, `response_format` to body
- `_buildAnthropicBody`: converts OpenAI tool format to Anthropic format
- `_buildOllamaBody`: passes `tools` through unchanged (Ollama uses OpenAI format)

## Phase 2 (Complete) — Agentic Loop Component

### Files to Create

| `components/agentic/sg-tool-definition/v0/v0.1/v0.1.0/sg-tool-definition.js` | Visual tool schema editor |

### sg-agentic-loop behaviour

1. Receives `llm:agentic-start` with task, tool definitions, config
2. Assembles messages array: system prompt + tool definitions + task
3. Sends via `llm:send` with `tools` array
4. On `llm:tool-calls`: sg-tool-runner handles execution automatically, fires `llm:tool-results-complete`
5. On `llm:tool-results-complete`: appends assistant + tool_response messages, sends again
6. On `llm:request-complete` with no tool_calls: loop done, fires `llm:agentic-done`
7. Safety: max iterations (default 10), cost budget, optional human-in-the-loop

### Trace visualisation

Each step appended to a timeline:
- `[User]` — task
- `[LLM]` — tool_call: name(args)
- `[Tool]` — returned: result
- `[LLM]` — final answer

## Event Flow (Full Loop)

```
[Page/sg-agentic-loop] llm:send { messages, tools }
  → [sg-llm-request] HTTP POST to provider
  → [sg-llm-request] llm:request-complete { content, toolCalls, finishReason:'tool_calls' }
  → [sg-llm-request] llm:tool-calls { toolCalls, messages }
    → [sg-tool-runner] executes each tool
    → [sg-tool-runner] llm:tool-result (per tool)
    → [sg-tool-runner] llm:tool-results-complete { results, messages: updatedMessages }
      → [sg-agentic-loop / page] appends tool messages, fires llm:send again
        → ... repeat until finishReason:'stop'
```

## Gemma 4 Notes

- OpenRouter IDs: `google/gemma-4-31b-it` and `google/gemma-4-26b-a4b-it`
- Both support `tools` parameter via OpenAI-compat API on OpenRouter
- Thinking tokens (`<think>` blocks): strip between turns, preserve within tool sequences
- Native token format (`<|tool_call>` etc.) is handled by the API layer — we never see it
- Test with 26B-A4B first (fast, low cost, MoE); use 31B for quality-critical work

## Tool Message Format (OpenAI-compat)

When an LLM returns tool calls, the conversation history must be extended with:

```js
// 1. Assistant message carrying the tool calls
{
  role: 'assistant',
  content: null,
  tool_calls: [{ id: 'call_abc', type: 'function', function: { name: 'list_folder', arguments: '{"path":"/"}' } }]
}

// 2. Tool result message(s)
{
  role: 'tool',
  tool_call_id: 'call_abc',
  content: JSON.stringify(result)
}
```

`sg-tool-runner` produces `results[]` with `{ toolCallId, name, result, error }`.
The caller (sg-agentic-loop or page script) converts these to the above format.
