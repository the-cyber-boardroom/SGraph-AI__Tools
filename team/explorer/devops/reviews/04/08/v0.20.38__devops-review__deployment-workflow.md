# DevOps Review: Deployment Workflow Assessment

**Version:** v0.20.38
**Date:** 8 April 2026
**Role:** DevOps (Explorer team)
**Trigger:** User flagged commit `80bfc79` ("add _latest/ build artifact to .gitignore") as feeling "quite a hack"

---

## Executive Summary

The deployment pipeline is functional but has accumulated technical debt across three layers: (1) build artifacts bleeding into the repo via `.gitignore` band-aids instead of proper build isolation, (2) a hardcoded `UI_VERSION` env var that is already stale (set to `v0.1.22` while the repo contains versions up to `v0.1.24`), and (3) near-identical dev/main workflows that diverge in subtle ways. None of these are breaking today, but each one is a manual-error timebomb.

---

## 1. The "Hack" Problem: `.gitignore` as Build Isolation

### What is happening

The build pipeline generates artifacts *inside the checked-out source tree* and then uses `.gitignore` to prevent them from being committed:

```gitignore
# i18n locale pages (generated by generate_tools_i18n_pages.py)
sgraph_ai_tools__static/tools/*/v*/v*/en-us/
sgraph_ai_tools__static/tools/*/v*/v*/fr-fr/
sgraph_ai_tools__static/tools/*/v*/v*/de-de/
sgraph_ai_tools__static/tools/*/v*/v*/es-es/

# Build version injection
sgraph_ai_tools__static/tools/*/v*/v*/_common/js/build-info.js

# IFD layered output
sgraph_ai_tools__static/tools/v0/v0.1/_latest/
```

### Why it feels hacky

1. **The source tree is not immutable during build.** Scripts mutate `sgraph_ai_tools__static/` in-place, mixing generated files with committed source files. There is no clean boundary between "what is in git" and "what the build produced."

2. **`.gitignore` is not a build system.** Every new generated artifact requires a corresponding `.gitignore` entry. Miss one and CI-generated files get committed. The `_latest/` entry in commit `80bfc79` is a symptom -- it was added *after the fact* because someone ran the build locally and noticed `_latest/` showing up in `git status`.

3. **Local builds contaminate the working tree.** If a developer runs `build_ifd_latest.py` or `generate_tools_i18n_pages.py` locally, generated files linger in the source tree until manually cleaned. There is no `make clean` or equivalent.

4. **The `.gitignore` patterns are fragile.** The glob `sgraph_ai_tools__static/tools/*/v*/v*/en-us/` works for the current structure but will silently fail to match if the nesting changes. The `_latest/` entry is hardcoded to a single path (`tools/v0/v0.1/_latest/`) rather than a pattern.

### Recommended fix: Build into an isolated output directory

All build scripts should write to a dedicated `_build/` directory outside the source tree (or at the repo root, gitignored with a single line). The source tree stays read-only during builds.

**Proposed change to `build_ifd_latest.py`:**

```python
# Instead of:
latest_dir = ifd_base / '_latest'

# Write to:
# _build/tools/v0/v0.1/_latest/
build_root = repo_root / '_build'
latest_dir = build_root / args.ifd_base / '_latest'
```

**Proposed change to `inject_build_version.py`:**

```python
# Instead of writing into the source tree:
target = version_dir / '_common' / 'js' / 'build-info.js'

# Write to:
target = build_root / ifd_path / '_common' / 'js' / 'build-info.js'
```

**Proposed change to `generate_tools_i18n_pages.py`:**

```python
# Instead of:
locale_dir = version_dir / loc['slug']

# Write to:
locale_dir = build_root / ifd_path / loc['slug']
```

**New `.gitignore` (replaces all 6 artifact entries with 1):**

```gitignore
# All CI/local build output
_build/
```

**Impact on `deploy_static_site.py`:**
The deploy script's `--source-dir` and `--clean-urls-source-version` would point to `_build/` output instead of the in-tree generated content. The workflow step becomes:

```yaml
- name: Deploy to S3
  run: |
    python scripts/deploy_static_site.py \
      --source-dir _build/sgraph_ai_tools__static \
      --clean-urls-source-version tools/v0/v0.1/_latest \
      ...
```

This is a medium-effort refactor (4 scripts + 2 workflows) but eliminates the entire class of `.gitignore`-as-build-system problems.

## 2. The Hardcoded `UI_VERSION` Problem

### Current state

Both workflows hardcode:

```yaml
env:
  UI_VERSION: v0.1.22
```

**This is already stale.** The repo contains versions up to `v0.1.24`, meaning deployments from `dev` are 2 versions behind what exists in the source tree. Every new version folder requires a manual update to both workflow files.

The `run-locally.sh` script is even more stale at `UI_VERSION="v0.1.5"`.

### Why this is dangerous

- A developer adds `v0.1.25/` with a critical fix, pushes to `dev`, CI triggers, and the deploy happily builds up to `v0.1.22` -- the fix is silently excluded.
- Two files to update (dev + main) means they can drift. Today they agree, but that is not guaranteed.
- The `run-locally.sh` script has its own copy, already 19 versions behind.

### Recommended fix: Auto-detect the latest version

Add a utility script or a function within `build_ifd_latest.py` that discovers the highest version directory:

**Option A: Script auto-detects (recommended)**

Add `--up-to auto` support to `build_ifd_latest.py`:

```python
def find_latest_version(ifd_base):
    """Find the highest semver version directory in the IFD base."""
    versions = []
    for d in ifd_base.iterdir():
        if d.is_dir() and d.name.startswith('v') and d.name != '_latest':
            v = parse_version_tuple(d.name)
            if v is not None:
                versions.append((v, d.name))
    if not versions:
        return None
    versions.sort()
    return versions[-1][1]  # e.g. "v0.1.24"


# In main():
if args.up_to == 'auto':
    latest = find_latest_version(ifd_base)
    if latest is None:
        print("ERROR: No version directories found")
        sys.exit(1)
    print(f"Auto-detected latest version: {latest}")
    target_version = parse_version_tuple(latest)
else:
    target_version = parse_version_tuple(args.up_to)
```

**Option B: Dedicated resolve script that sets a GitHub Actions output**

```python
#!/usr/bin/env python3
"""Resolve the latest IFD version from the directory structure.

Usage:
    python scripts/resolve_ifd_version.py --ifd-base sgraph_ai_tools__static/tools/v0/v0.1
    # prints: v0.1.24
"""
```

Workflow usage:

```yaml
- name: Resolve latest UI version
  id: ifd
  run: |
    VERSION=$(python scripts/resolve_ifd_version.py \
      --ifd-base ${{ env.SOURCE_DIR }}/tools/v0/v0.1)
    echo "ui_version=$VERSION" >> $GITHUB_OUTPUT
    echo "Resolved UI version: $VERSION"

- name: Build layered IFD content
  run: |
    python scripts/build_ifd_latest.py \
      --source-dir ${{ env.SOURCE_DIR }} \
      --ifd-base tools/v0/v0.1 \
      --up-to ${{ steps.ifd.outputs.ui_version }}
```

**Recommendation:** Option A is simpler and self-contained. Use `--up-to auto` as the default in CI, but keep the explicit version flag for debugging and rollbacks.

Remove `UI_VERSION` from workflow `env:` entirely. If a specific version is needed for rollback, pass it via `workflow_dispatch` input.

**Also fix `run-locally.sh`** to auto-detect using the same `sort -V` pattern it already uses for layering:

```bash
# Replace hardcoded UI_VERSION="v0.1.5" with:
UI_VERSION=$(ls -d "$STATIC_DIR/$IFD_BASE"/v0.1.* 2>/dev/null | sort -V | tail -1 | xargs basename)
```

## 3. Workflow Duplication

### Current differences between dev and main

The `diff` reveals that the two workflows are ~80% identical with these differences:

| Aspect | dev | main |
|--------|-----|------|
| Branch trigger | `dev` | `main` |
| `workflow_dispatch` | absent | present (with environment choice) |
| `increment-tag` job | present (runs before deploy) | absent |
| Environment resolution | hardcoded `dev` | dynamic `main` or `prod` |
| Deploy env | `dev` | `${{ steps.env.outputs.deploy_env }}` |
| CloudFront dist ID | single secret | conditional (main vs prod secret) |

### Why this matters

Every time the build pipeline changes (new script, new step, new argument), both files must be updated in lockstep. This has already caused drift: `run-locally.sh` has `v0.1.5`, the workflows have `v0.1.22`, and the repo has `v0.1.24`.

### Recommended fix: Reusable workflow

Create a single reusable workflow and call it from thin trigger workflows:

**`.github/workflows/_deploy-tools.yml`** (reusable, note the underscore prefix convention):

```yaml
name: Deploy Tools UI to S3

on:
  workflow_call:
    inputs:
      deploy-env:
        required: true
        type: string
        description: "Deployment environment (dev, main, prod)"
      run-increment-tag:
        required: false
        type: boolean
        default: false
    secrets:
      AWS_ACCESS_KEY_ID:
        required: true
      AWS_SECRET_ACCESS_KEY:
        required: true
      SGRAPH_TOOLS__S3_BUCKET:
        required: true
      SGRAPH_TOOLS__CLOUDFRONT_DISTRIBUTION_ID:
        required: true

env:
  AWS_REGION: eu-west-2
  SOURCE_DIR: sgraph_ai_tools__static

jobs:
  increment-tag:
    if: ${{ inputs.run-increment-tag }}
    name: Increment Tag
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: owasp-sbot/OSBot-GitHub-Actions/.github/actions/git__increment-tag@dev
        with:
          release_type: minor

  deploy:
    name: "Deploy Tools to S3 (${{ inputs.deploy-env }})"
    runs-on: ubuntu-latest
    needs: [increment-tag]
    if: ${{ !cancelled() && (needs.increment-tag.result == 'success' || needs.increment-tag.result == 'skipped') }}
    timeout-minutes: 10
    environment: ${{ inputs.deploy-env }}

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'

      - name: Resolve latest UI version
        id: ifd
        run: |
          # Auto-detect highest version directory
          LATEST=$(ls -d ${{ env.SOURCE_DIR }}/tools/v0/v0.1/v0.1.* \
            | sort -V | tail -1 | xargs basename)
          echo "ui_version=$LATEST" >> $GITHUB_OUTPUT
          echo "Resolved UI version: $LATEST"

      - name: Inject build version
        run: python scripts/inject_build_version.py --version ${{ steps.ifd.outputs.ui_version }}

      - name: Generate i18n locale pages
        run: python scripts/generate_tools_i18n_pages.py --version ${{ steps.ifd.outputs.ui_version }}

      - name: Build layered IFD content
        run: |
          python scripts/build_ifd_latest.py \
            --source-dir ${{ env.SOURCE_DIR }} \
            --ifd-base tools/v0/v0.1 \
            --up-to ${{ steps.ifd.outputs.ui_version }}

      # ... AWS credentials + deploy steps (identical) ...
```

**`.github/workflows/deploy-tools__dev.yml`** (thin trigger):

```yaml
name: Deploy Tools UI (dev)
on:
  push:
    branches: [dev]
    paths:
      - 'sgraph_ai_tools__static/**'
      - 'scripts/**'
      - '.github/workflows/**'
      - 'sgraph_ai_tools/version'

jobs:
  deploy:
    uses: ./.github/workflows/_deploy-tools.yml
    with:
      deploy-env: dev
      run-increment-tag: true
    secrets: inherit
```

**`.github/workflows/deploy-tools__main.yml`** (thin trigger):

```yaml
name: Deploy Tools UI (main)
on:
  push:
    branches: [main]
    paths: [...]
  workflow_dispatch:
    inputs:
      environment:
        type: choice
        options: [main, production]
        default: main

jobs:
  deploy:
    uses: ./.github/workflows/_deploy-tools.yml
    with:
      deploy-env: ${{ inputs.environment || 'main' }}
    secrets: inherit
```

This eliminates all duplication. Changes to the build pipeline are made in one file.

## 4. Build Pipeline Assessment: IFD Layering

### The approach is sound

The IFD (Incremental File Delta) model is a good fit for this use case. It keeps version directories small (only deltas), preserves the ability to inspect what changed in each version, and the `build_ifd_latest.py` layering is straightforward `shutil.copy2` in sorted order.

### Edge cases and failure modes

**4.1 File deletions are not representable.**
IFD layering only supports additions and modifications. If a tool needs to be *removed* in a future version, there is no mechanism for that. A later version can overwrite a file but cannot delete one that existed in an earlier version.

- **Risk level:** Low today (no tools have been removed).
- **Future fix:** Support a `.ifd-delete` manifest file per version listing files to remove after layering.

**4.2 The `--up-to` flag silently excludes versions.**
If `--up-to v0.1.22` is passed but `v0.1.24` exists, the script happily builds a `_latest/` that is missing 2 versions of content. There is no warning. Combined with the hardcoded `UI_VERSION`, this is the most likely failure mode.

- **Fix:** When `--up-to` is explicit, print a warning if higher versions exist:
  ```python
  all_versions = [v for v, _ in version_dirs_all]
  if target_version < max(all_versions):
      print(f"WARNING: --up-to {args.up_to} is not the highest version. "
            f"Skipping: {[v for v in all_versions if v > target_version]}")
  ```

**4.3 The `--ifd-base` is hardcoded to `tools/v0/v0.1`.**
When `v0.2.0` arrives, the workflow, the local dev script, and every script invocation will need updating. This is the same class of problem as `UI_VERSION`.

- **Fix:** Auto-detect the IFD base similarly, or derive it from the latest version. Since `v0.2.0` is a breaking change anyway, this is lower priority.

**4.4 No build verification.**
After layering, there is no check that the resulting `_latest/` contains a valid site. A minimum check would be: does `_latest/en-gb/index.html` exist?

- **Fix:** Add a post-build validation step:
  ```python
  expected = latest_dir / 'en-gb' / 'index.html'
  if not expected.is_file():
      print(f"ERROR: Build verification failed — {expected} not found")
      sys.exit(1)
  ```

**4.5 `shutil.copy2` preserves metadata but not symlinks.**
Not a problem today (no symlinks in version dirs), but worth noting.

## 5. Deployment Improvements (S3/CloudFront)

### 5.1 The `--skip-validation` flag is always set

Both workflows pass `--skip-validation` to `deploy_static_site.py`. The validation function checks for files like `product/index.html` and `agents/index.html` which belong to a different site (looks like `sgraph.ai`, not `tools.sgraph.ai`). The validation is irrelevant to the tools site and should be updated rather than skipped.

**Fix:** Create a tools-specific validation function or make the required files list configurable via argument:

```python
parser.add_argument(
    '--required-files', nargs='*', default=[],
    help='Files that must exist in source-dir (e.g. en-gb/index.html)'
)
```

### 5.2 CloudFront invalidation is `/*` (full purge) every time

Every deployment invalidates the entire cache. This is fine for the current scale but becomes expensive at higher deployment frequency (AWS charges per invalidation path after the first 1,000/month).

**Improvement for later:** Generate a list of changed files from the IFD delta version and invalidate only those paths. The build script already knows which version is "new" -- use that file list.

### 5.3 The `s3_sync_by_type` pattern runs 6 sync commands per target

Each deployment runs `aws s3 sync` separately for HTML, CSS, JS, JSON, images, and fonts -- 6 times for releases and 6 times for latest, totalling 12+ sync operations. This is slow.

**Improvement:** Use a single `aws s3 sync` with `--content-type` override via `--metadata-directive REPLACE` and per-file content type detection. Alternatively, use `aws s3 cp --recursive` with a metadata mapping. This would reduce 12 sync operations to 2 (releases + latest).

### 5.4 No rollback mechanism documented

The releases directory on S3 contains every version, so rollback is theoretically possible by re-pointing latest to an older release. But there is no script or workflow to do this.

**Improvement:** Add a `--rollback-to` flag to the deploy script or a separate `rollback.py`:

```bash
python scripts/deploy_static_site.py --rollback-to v0.1.21 ...
```

This would copy `releases/v0/v0.1/v0.1.21/` to `latest/` and invalidate CloudFront.

### 5.5 Credential check pattern is verbose but functional

The `check-creds` step with `if: steps.check-creds.outputs.has-credentials == 'true'` gates are a pragmatic pattern. No change needed, but documenting the intent (allow CI to pass without AWS creds in forks/PRs) would be helpful.

## Summary

The core architecture (IFD versioning, Python build scripts, S3/CloudFront deployment) is solid. The problems are all in the "glue" layer: hardcoded version numbers that require manual maintenance, build artifacts that leak into the source tree, and workflow duplication. The highest-impact fix is removing the hardcoded `UI_VERSION` (items 1-2) -- this is already causing the deploy to miss the latest 2 versions. The build isolation refactor (item 4) is what makes commit `80bfc79` unnecessary -- if build output goes to `_build/`, there is nothing to `.gitignore`.
