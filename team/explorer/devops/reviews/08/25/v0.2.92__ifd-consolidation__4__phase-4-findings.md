## 4f — Root-absolute imports ✅ DONE

Four files reached the shared tiers by counting directories:

```
en-gb/audio-transcribe/ui/ui-chat.js      ../../../../../../../components/llm/sg-llm-events/…
en-gb/audio-transcribe/ui/ui-shell.js     ../../../../../../../core/sg-layout/…
en-gb/sg-video-editor/ui/ui-keyboard.js   ../../../../../../../components/sg-timeline/…
en-gb/heic-decode/heic-probe.js           ../../../../../core/image/…
```

They worked, but only by accident. Served at `/en-gb/{tool}/ui/x.js`, seven `../`
segments overshoot the origin root by four levels; URL normalisation discards the
excess, so the request lands on `/core/…` anyway. The depth was correct for the old
`tools/v0/v0.1/v0.1.53/en-gb/…` path and is now meaningless.

All four are now `/core/…` and `/components/…`. Verified: each file and each of its new
import targets returns 200 from the built tree, and the four browser smoke tests still
pass (125 assertions, 0 failures).

## 4d — Manifests: two latent landing-page crashes ✅ FIXED

`renderToolCard()` in `sg-tool-registry.js` reads:

```js
const statusLabel = manifest.status.charAt(0).toUpperCase() + manifest.status.slice(1);
return `<a href="${manifest.slug}/" …`
```

`auth-mvp` and `vault-mgr` had **no `slug`, no `status` and no `category`**. Adding either
to `TOOL_SLUGS` would have thrown a `TypeError` on `undefined.charAt` and taken down the
**entire landing page render**, not just that card. Both now carry `slug`, `status: "dev"`
and a category, matching how `vfs-dev` and `sg-tree-demo` are classified. Every one of the
51 manifests now has all five required fields.

Two tools still have **no manifest at all** — see 4e.

## 4e — "Superseded demos": the premise was wrong

An earlier note in this session listed seven tools as superseded demos. That list was
inferred from names, not evidence. Checking the manifests, **most of it does not hold**:

| Tool | I assumed | Actually |
|---|---|---|
| `llm-dev` | superseded | `status: live`, listed |
| `one-shot-chat` | superseded | `status: live`, listed |
| `send-sim` | superseded | `status: dev`, listed — a dev tool, deliberately shipped |
| `sg-tree-demo` | superseded | `status: dev`, listed |
| `vfs-dev` | superseded | `status: dev`, listed |
| `vfs-tree-demo` | superseded | `status: dev`, listed |

`status: dev` tools are not dead. The landing page renders a status badge per card

**Owner decision.** Neither is listed, so neither is discoverable; both are reachable by
direct URL and may still be referenced from a brief or debrief.

## 4a — Converging multi-versioned modules is a behaviour change

Part 3 assumed this was a repointing exercise. It is not. **19 modules currently run more
than one version in the same deploy**, and every pair has real code differences:

| Module | Live versions | Diff lines, oldest → newest |
|---|---|---:|
| `components/llm/sg-llm-request` | v0.1.0, v0.1.2, v0.1.4, v0.1.6 | **460** |
| `components/llm/sg-llm-bundle-list` | v0.1.0, v0.1.3 | 186 |
| `core/video-composer` | v0.1.0, v0.1.1 | 226 |
| `core/vault-client` | v1.2.0 … v1.2.3 | 200 |
| `core/sg-tree` | v0.1.0, v0.1.4 | 166 |
| `components/llm/sg-llm-events` | v0.1.0, v0.1.1 | 126 |
| `components/llm/sg-llm-bundle` | v0.1.0, v0.1.7 | 113 |
| `core/sg-video-recorder` | v0.1.0, v0.1.2 | 109 |
| `components/llm/sg-llm-connection` | v0.1.0, v0.1.4 | 97 |
| `components/llm/sg-llm-chat-history` | v0.1.8, v0.1.10 | 81 |
| `core/video` | v1.0.0, v1.0.1, v1.0.2 | 76 |
| `components/site-header` | v1.0.0 … v1.0.3 | 71 |
| 7 more | 2 each | 7–56 |

Moving `multi-agent-chat` from `sg-llm-chat-history` v0.1.8 to v0.1.10 means giving it 81
lines of code it has never run. Doing that for 19 modules across 51 tools, with browser
smoke tests covering **4** of them, would be shipping untested behaviour changes to the
whole catalogue at once.

**Re-planned as 4a′ — one module at a time, newest-consumer-first:**

1. Pick one module. Diff its live versions and read the delta — is it additive, or did an
   API change?
2. Identify the tools pinned to the older version.
3. If any has no smoke test, write one first. That is the real prerequisite, and it is what
   makes this phase worth doing at all.
4. Repoint, run that tool's test, commit as its own reviewable change.

Ordered by leverage: the `sg-llm-*` family first (9 of the 19, and the `chat` /
`multi-agent-chat` / `openrouter` cluster consumes all of it), then `core/video*`, then the
rest. Nothing here blocks the v0.3.0 cutover — multiple live versions is the status quo
today and shipping it unchanged is strictly no worse.

## 4b — Pruning orphans is blocked on an external check

Recomputed against the flat release:

```
leaf version dirs on disk      249
referenced by shipped tools    170
orphaned                        79
```

Of those 79, **15 are published in `library/api/*.md` as pinned URLs for consumer agents** —
they are the documented integration surface for send.sgraph.ai, vault.sgraph.ai, the
workspace and the Chrome extension:

```
components/base/v1/v1.0/v1.0.0            core/pbkdf2/v1/v1.0/v1.0.0
components/key-input/v1/v1.0/v1.0.0       core/sg-sandbox/v0/v0.2/v0.2.0
components/sg-timeline/v0/v0.1/v0.1.0     core/sg-tree/v0/v0.2/v0.2.0
components/vault-embed/sg-vault-fetch/…   core/vault-cache/v1/v1.0/v1.0.1
components/vault-embed/sg-vault-key/…     core/vault-init/v1/v1.0/v1.0.1
components/vault/sg-vault-manager/v0.1.3  core/vault-session/v1/v1.0/v1.0.1
core/vault-write/v1/v1.0/v1.0.0           core/vault-write/v1/v1.1/v1.1.2
core/wordlist/v1/v1.0/v1.0.0
```

**These must not be pruned.** "Unused by our own tools" is not the same as "unused" — that
is precisely what a published pinned URL means.

The remaining 64 are unreferenced by any tool and by any consumer-facing doc in this repo.
That still is not proof they are safe to delete: a consumer could pin a version that was
never written into `library/`. The check that settles it is a grep for `tools.sgraph.ai/core/`
and `tools.sgraph.ai/components/` across the four consumer repos, which this session cannot
reach. Until then, the 64 cost ~8 MB per deploy and nothing else.

## 4c — DROP: normalising `core/sg-layout/` would break consumers

`core/sg-layout/` sits at `v0.1.0/` while all 248 other leaf versions use the three-level
`v0/v0.1/v0.1.0/` nesting. Part 3 proposed normalising it.

It must not be moved. The path is published to consumer agents:

```
library/api/v0.1.92__sg-layout__full-inventory.md:23
    https://tools.sgraph.ai/core/sg-layout/v0.1.0/sg-layout.js
library/api/v0.1.92__sg-layout__full-inventory.md:24
    https://tools.sgraph.ai/core/sg-layout/v0.1.0/sg-layout-events.js
```

107 references inside the tools tree point at it as well. The inconsistency is cosmetic; the
breakage would not be. If it is ever normalised it must be a copy-and-deprecate with both
paths served, never a move — and there is no reason to spend that on a naming preference.
