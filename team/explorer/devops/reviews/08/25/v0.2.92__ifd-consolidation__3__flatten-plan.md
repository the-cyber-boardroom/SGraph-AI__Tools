# Part 3 — Plan: flatten v0.1.x into an independent v0.3.0

**Version:** v0.2.92 · Part 3 of 3
**Status:** PROPOSED — none of this exists yet

---

## 1. Three decisions that shape everything else

### D1 — What "100% independent" can and cannot mean

The new folder must not depend on **any previous tool version folder**. That is achievable and
is the goal.

It must **still** depend on `/core/…` and `/components/…` at their existing root-absolute URLs.
Vendoring them inside the release is the one thing we must *not* do:

- Tool code imports them as `/core/markdown/v1/v1.1/v1.1.0/sg-markdown.js` — root-absolute,
  confirmed across the built tree.
- Per `.claude/CLAUDE.md`, **send.sgraph.ai, vault.sgraph.ai, the workspace and the Chrome
  extension import FROM tools.sgraph.ai**. Those consumers hold pinned `/core/…` and
  `/components/…` URLs. Moving those files under `tools/v1/…` breaks every one of them.

So the plan is deliberately **asymmetric**:

| Tier | Folder-versioning in git | Rationale |
|---|---|---|
| `core/`, `components/` | **Keep** | Public pinned-URL API with external consumers. Immutability is a contract. |
| `tools/` | **Drop** | No external consumer pins into tool internals. The public surface is the clean URL `tools.sgraph.ai/en-gb/{tool}/`. |

**Independence test for v0.3.0:** delete every `tools/v0/v0.1/` folder from the working tree and the
site still builds, deploys and serves all 50 tools identically.

### D2 — Where immutable versions actually live after v0.3.0

Today the repo tries to be its own version-control system: 68 folders whose only purpose is to
record "what changed when". Git already does that, and S3 already stores immutable release
prefixes. The middle layer earns nothing and costs Part 2.

**Proposal — git holds one complete tree; CI materialises immutable releases into S3.**

```
git:  sgraph_ai_tools__static/tools/v0/v0.3/v0.3.0/     ← always the complete, current truth
                                                          556 files, real diffs, real deletes
S3:   releases/v0/v0.3/v0.3.0/  v0.3.1/  v0.3.2/ …      ← immutable snapshots, one per release
```

Immutability is preserved where it is actually consumed (URLs), and dropped where it only
caused harm (the repo). History stays fully recoverable through git:

```bash
git show v0.3.5:sgraph_ai_tools__static/tools/v0/v0.3/v0.3.0/en-gb/chat/index.html
```

**Conservative alternative (D2-alt):** keep delta folders, but make `v0.3.0` a full snapshot and
adopt a written policy to re-base at every major. This preserves the current workflow shape and
costs one extra file: a `_deleted.txt` tombstone list per version that `build_ifd_latest.py`
honours, which is the minimum needed to make P1 fixable. It reintroduces P2/P3 gradually.
Recommend D2; D2-alt only if pinned-per-patch tool URLs turn out to have real consumers
(see Phase 0).

### D3 — Which version number: **v0.3.0**, not v0.2.0

**v0.2.0 is already taken.** There are four separate version namespaces in this repo and they
have to be checked individually:

| Namespace | State of `v0.2.0` | Evidence |
|---|---|---|
| **Git tags** | **OCCUPIED** — tagged 2026-04-23 | `git tag \| grep -c '^v0\.2\.'` → **93 tags**, v0.2.0 … v0.2.92 |
| Doc filename prefixes | **OCCUPIED** — in active use | `v0.2.88__brief__…`, `v0.2.92__…` (this document) |
| `tools/v0/` directories | free | `ls tools/v0/` → only `v0.1` |
| S3 `releases/v0/` prefixes | free | deploy has only ever been passed `ui_version` from the `tools/v0/v0.1/v0.1.*` glob |

**v0.3.0 is free in all four.** `git tag | grep -c '^v0\.3\.'` → **0**. No `v0.3` directory
exists anywhere. No `v1.x` tag exists either.

#### v0.3.0 is also what the pipeline would produce by itself

`increment-tag` with `release_type: major` does **not** bump the leading `0` in this repo — it
bumps the middle component. The tag history proves it:

```
v0.1.118  2026-04-23
v0.1.119  2026-04-23
v0.1.120  2026-04-23     ← last v0.1 tag
v0.2.0    2026-04-23     ← "major" from main, same day
v0.2.1    2026-04-23
```

The workflow runs `release_type: ${{ github.ref_name == 'main' && 'major' || 'minor' }}`, so
**a push to `main` today tags `v0.3.0`** from the current `v0.2.92`. Naming the flattened
release `v0.3.0` means the release folder, the repo version file, and the git tag all land on
the same number at the same moment — which is precisely the reconciliation Phase 3 needs.

#### The collision this avoids

Today the tools-UI directory name and the git tag are two unrelated counters that happen to
share a format, and they have **already collided**:

```
git tag        v0.1.67   → cut 2026-04-08
tools directory v0.1.67  → markdown-viewer + media-probe, the CURRENT UI release (Aug 2026)
```

Same string, four months apart, two entirely different things. Anyone doing
`git checkout v0.1.67` to inspect "the v0.1.67 tools release" gets an April tree that does not
contain it. Choosing `v0.3.0` — the number the tag counter is about to reach anyway — collapses
the two counters into one and ends this class of confusion permanently.

#### Path mapping

`version_to_ifd_path("v0.3.0")` → `v0/v0.3/v0.3.0`, already implemented, no code change needed.
The release lands at `releases/v0/v0.3/v0.3.0/`, a sibling of the existing `releases/v0/v0.1/`
prefixes rather than a replacement — so nothing currently deployed is touched.

> **One Phase 0 verification:** confirm `releases/v0/v0.2/` and `releases/v0/v0.3/` are absent
> from the bucket before committing to the number. The reasoning above says they must be, but
> it is one `aws s3 ls` and this is the cheap moment to be certain:
> `aws s3 ls s3://{bucket}/websites/sgraph-tools/prod/releases/v0/`

```
    │
    ├── shared/                             ← the public pinned API, deployed ONCE not per release
    │   ├── core/…                          166 live versions
    │   └── components/…
    │
    └── latest/                             ← CloudFront origin, mirror of newest release
        ├── _common/ i18n/ en-gb/ …

```

**Two changes from today beyond the flatten:**

1. **The full-repo archive sync disappears.** Today Step 1 mirrors all 20 MB of the repo —
   including all 68 delta folders — into *every* release prefix, then Step 2 copies the served
   content in again on top. The new release prefix contains only what is served.
   ~3,000 objects → ~770. ~26 MB → ~5.2 MB.
2. **`core/` and `components/` move to a `shared/` prefix, uploaded once**, not re-uploaded into
   every release. They are already immutable and content-addressed by version; re-uploading
   them per release buys nothing.

> **Cutover caveat:** `/core/…` and `/components/…` must keep resolving at the *site root*.
> That is a CloudFront behaviour/origin-path change (route `/core/*` and `/components/*` to
> `shared/`), not something the deploy script can do alone. If that change is not wanted in this
> release, keep syncing them into the release prefix — the flatten still delivers everything else.
> **Decision needed from whoever owns the CloudFront distribution.**

### URL compatibility

| URL | Today | After | Action |
|---|---|---|---|
| `tools.sgraph.ai/en-gb/{tool}/` | works | works | none — this is the primary surface |
| `/core/…`, `/components/…` | works | works | CloudFront behaviour if `shared/` is adopted |
| `tools.sgraph.ai/tools/v0/v0.1/v0.1.0/en-gb/ssh-keygen/` | works | **breaks** | 2 in-content refs; leave `releases/v0/…` in S3 untouched so old URLs keep resolving |

Nothing is deleted from S3 in this migration. The old `releases/v0/…` prefixes stay exactly
where they are and keep serving; we simply stop writing to them.

### Phase 2 — Prove byte-equality (the "same features and functionality" gate)  ✅ DONE

Add `scripts/verify_flatten.py`:

```
for every file in build(tools/v0/v0.1/*)         # the old layered result
    assert sha256 == sha256 of tools/v0/v0.3/v0.3.0/<same relative path>
assert file sets are identical
exit non-zero on any difference
```

Run it in CI on every PR for the whole migration window. **Phase 2 must be green before
Phase 3 begins.** This is what makes "identical functionality" a checked fact rather than a
hope. Any intentional removal from Phase 4 is added to an explicit allow-list in this script,
so every deviation is a reviewed line of code.

#### What Phase 3 actually produced (2026-08-25)

The workflow is now `v2.0.0`. `build_ifd_latest.py` is no longer called by CI.

| New / changed | What it does |
|---|---|
| `scripts/build_release.py` | Assembles `build/` = flat release + `core/` + `components/` + the root locale detector. Fails if the version and `RELEASE_DIR` are not the same major.minor series. |
| `scripts/deploy_static_site.py` | New `--flat-release` mode: one typed sync per file type to `releases/{version}/` and `latest/`, each with `Content-Type`, `Cache-Control` **and `--delete`**. The legacy `--clean-urls` path is untouched, so other sites using this script are unaffected. |
| `scripts/verify_flatten.py` | New `--allow-additions` mode for the transition window (below). |
| `.github/workflows/deploy-tools.yml` | `RELEASE_DIR` env var; version read from the root `version` file; build → verify → link-check → browser tests → deploy. |

**Two bugs fixed on the way through**, both found by reading the sync commands:

- *Served assets had no `Cache-Control`.* `_sync_clean_url_content` used bare `aws s3 sync`
  for `_common/`, the locale folders and `i18n/`, so the carefully designed cache strategy
  (1 day for CSS/JS, 1 week for images) was applied only to the nested archive copies, never
  to the copies actually served. Every pass in `--flat-release` sets it.
- *`.md`, `.txt` and `.xml` were uploaded as `text/html` in the archive.* The HTML pass
  excluded CSS/JS/image/font extensions but not these. **Narrower than first stated:** only
  the nested archive copies were affected, and the archive is not served — the served copies
  come from a bare sync where the AWS CLI guesses correctly (`curl -sI …/SKILL-api.md`
  returns `text/markdown` live). Setting the type explicitly beats relying on a guess, but
  this was never a live defect. See Part 5.

**Measured footprint per release** — the estimate in Parts 0–2 was too low; the real numbers
make the case stronger:

```

TODAY  step 2 overlay again:  787 files / 8.8M
TODAY  releases/ total     ≈ 3732 objects / ~44M

NEW    releases/ total     = 1349 objects / 18M
```

#### The transition window, and the gate that protects it

While `tools/v0/v0.1/` still exists, the dangerous mistake is adding a tool the **old** way —
into a new `v0.1.69` folder — which the new pipeline would never ship. CI now runs
`verify_flatten.py --allow-additions` on every deploy, which fails if anything the layered
result serves is missing from or differs in the flat release, while permitting new content in
the flat release. Verified against three simulations:

| Simulation | Result |
|---|---|
| Tool added to `v0.1.69` only | **FAIL** — `en-gb/ghost-tool/index.html` served today but absent from the flat release |
| Existing `v0.1.68` file edited | **FAIL** — content differs |
| New tool added to `v0.3.0` only | **PASS** with `--allow-additions`, FAIL under strict |

The step self-disables once `tools/v0/v0.1/` is deleted at Phase 5.

`.gitignore` needed **no change**: the `_latest` rule is path-specific to

#### Caveat: v0.3.0 is uploaded (though not served) by the current deploy

`deploy_static_site.py` Step 1 syncs the **entire** `source_dir` into the release prefix, so
until Phase 3 lands, every deploy also uploads `tools/v0/v0.3/v0.3.0/` into
`releases/v0/v0.1/v0.1.68/tools/v0/v0.3/v0.3.0/` — about 5.4 MB on top of the existing ~26 MB.

It is **not served**: CloudFront serves the clean-URL overlay at the release root, which is
built from `_latest` and is unchanged. Nothing about the live site changes.

Two consequences worth knowing:

- The extra 5.4 MB per release is harmless but real. It disappears at Phase 3, when the
  full-archive sync is replaced by a release-dir-only sync.
- It is also **useful**: because the origin points at the release root, the flattened tree is
  browsable on the live CDN at
  `https://dev.tools.sgraph.ai/tools/v0/v0.3/v0.3.0/en-gb/{tool}/` after the next dev deploy.
  Root-absolute `/core/…` imports resolve correctly there (the release prefix carries `core/`
  from the same Step 1 sync). That gives a free pre-cutover smoke test of the flattened
  release on real infrastructure, with zero risk to the live site.
