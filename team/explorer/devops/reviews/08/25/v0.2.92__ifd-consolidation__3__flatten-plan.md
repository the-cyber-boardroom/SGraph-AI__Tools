# Part 3 — Plan: flatten v0.1.x into an independent v1.0.0

**Version:** v0.2.92 · Part 3 of 3
**Status:** PROPOSED — none of this exists yet

---

## 1. Three decisions that shape everything else

### D1 — What "100% independent" can and cannot mean

The new folder must not depend on **any previous tool version folder**. That is achievable and
is the goal.

It must **still** depend on `/core/…` and `/components/…` at their existing root-absolute URLs.
Vendoring them inside the release is the one thing we must *not* do:

- Tool code imports them as `/core/markdown/v1/v1.1/v1.1.0/sg-markdown.js` — root-absolute,
  confirmed across the built tree.
- Per `.claude/CLAUDE.md`, **send.sgraph.ai, vault.sgraph.ai, the workspace and the Chrome
  extension import FROM tools.sgraph.ai**. Those consumers hold pinned `/core/…` and
  `/components/…` URLs. Moving those files under `tools/v1/…` breaks every one of them.

So the plan is deliberately **asymmetric**:

| Tier | Folder-versioning in git | Rationale |
|---|---|---|
| `core/`, `components/` | **Keep** | Public pinned-URL API with external consumers. Immutability is a contract. |
| `tools/` | **Drop** | No external consumer pins into tool internals. The public surface is the clean URL `tools.sgraph.ai/en-gb/{tool}/`. |

**Independence test for v1.0.0:** delete every `tools/v0/` folder from the working tree and the
site still builds, deploys and serves all 50 tools identically.

### D2 — Where immutable versions actually live after v1.0.0

Today the repo tries to be its own version-control system: 68 folders whose only purpose is to
record "what changed when". Git already does that, and S3 already stores immutable release
prefixes. The middle layer earns nothing and costs Part 2.

**Proposal — git holds one complete tree; CI materialises immutable releases into S3.**

```
git:  sgraph_ai_tools__static/tools/v1/v1.0/v1.0.0/     ← always the complete, current truth
                                                          556 files, real diffs, real deletes
S3:   releases/v1/v1.0/v1.0.0/  v1.0.1/  v1.0.2/ …      ← immutable snapshots, one per release
```

Immutability is preserved where it is actually consumed (URLs), and dropped where it only
caused harm (the repo). History stays fully recoverable through git:

```bash
git show v1.0.5:sgraph_ai_tools__static/tools/v1/v1.0/v1.0.0/en-gb/chat/index.html
```

**Conservative alternative (D2-alt):** keep delta folders, but make `v1.0.0` a full snapshot and
adopt a written policy to re-base at every major. This preserves the current workflow shape and
costs one extra file: a `_deleted.txt` tombstone list per version that `build_ifd_latest.py`
honours, which is the minimum needed to make P1 fixable. It reintroduces P2/P3 gradually.
Recommend D2; D2-alt only if pinned-per-patch tool URLs turn out to have real consumers
(see Phase 0).

### D3 — Major number

`v1/v1.0/v1.0.0`. The IFD path scheme (`v{major}/v{major}.{minor}/v{major}.{minor}.{patch}`) is
already implemented by `version_to_ifd_path()`, so `v1.0.0` maps cleanly to
`releases/v1/v1.0/v1.0.0/` and is naturally isolated from every existing `v0/` S3 prefix.
If staying pre-1.0 is preferred, `v0/v0.2/v0.2.0` works identically — substitute throughout.

## 3. Target directory structure — in deployment

```
s3://{account}--static-sgraph-ai--eu-west-2/
└── websites/sgraph-tools/{dev|main|prod}/
    │
    ├── releases/v1/v1.0/v1.0.0/            ← immutable snapshot, ~770 objects / 5.2 MB
    │   ├── _common/  i18n/
    │   ├── en-gb/ en-us/ fr-fr/ de-de/ es-es/
    │   └── index.html 404.html robots.txt sitemap.xml manifest.json
    │        (NO nested tools/ archive — the release IS the flattened content)
    │
    ├── releases/v1/v1.0/v1.0.1/            ← next release, same shape
    │
    ├── shared/                             ← the public pinned API, deployed ONCE not per release
    │   ├── core/…                          166 live versions
    │   └── components/…
    │
    └── latest/                             ← CloudFront origin, mirror of newest release
        ├── _common/ i18n/ en-gb/ …
        └── index.html …
```

**Two changes from today beyond the flatten:**

1. **The full-repo archive sync disappears.** Today Step 1 mirrors all 20 MB of the repo —
   including all 68 delta folders — into *every* release prefix, then Step 2 copies the served
   content in again on top. The new release prefix contains only what is served.
   ~3,000 objects → ~770. ~26 MB → ~5.2 MB.
2. **`core/` and `components/` move to a `shared/` prefix, uploaded once**, not re-uploaded into
   every release. They are already immutable and content-addressed by version; re-uploading
   them per release buys nothing.

> **Cutover caveat:** `/core/…` and `/components/…` must keep resolving at the *site root*.
> That is a CloudFront behaviour/origin-path change (route `/core/*` and `/components/*` to
> `shared/`), not something the deploy script can do alone. If that change is not wanted in this
> release, keep syncing them into the release prefix — the flatten still delivers everything else.
> **Decision needed from whoever owns the CloudFront distribution.**

### URL compatibility

| URL | Today | After | Action |
|---|---|---|---|
| `tools.sgraph.ai/en-gb/{tool}/` | works | works | none — this is the primary surface |
| `/core/…`, `/components/…` | works | works | CloudFront behaviour if `shared/` is adopted |
| `tools.sgraph.ai/tools/v0/v0.1/v0.1.0/en-gb/ssh-keygen/` | works | **breaks** | 2 in-content refs; leave `releases/v0/…` in S3 untouched so old URLs keep resolving |

Nothing is deleted from S3 in this migration. The old `releases/v0/…` prefixes stay exactly
where they are and keep serving; we simply stop writing to them.

## 4. Migration phases

### Phase 0 — Establish the safety net (no changes shipped)

- [ ] Tag the current tree: `git tag ifd-v0-final && git push origin ifd-v0-final`.
- [ ] **Confirm nobody pins a per-patch tool URL.** Grep the consumer repos (send, vault,
      workspace, Chrome extension) for `tools.sgraph.ai/tools/v0/`. If hits exist, they pin
      D2-alt semantics and the plan needs an S3 redirect table. *Blocking for D2.*
- [ ] Snapshot the current deploy as the behavioural baseline: build `_latest`, record
      `sha256sum` of all 556 files into `team/explorer/devops/reviews/08/25/baseline-v0.1.67.sha256`.

### Phase 1 — Materialise the flattened folder

```bash
python scripts/build_ifd_latest.py --source-dir sgraph_ai_tools__static \
  --ifd-base tools/v0/v0.1 --up-to auto

mkdir -p sgraph_ai_tools__static/tools/v1/v1.0
cp -a sgraph_ai_tools__static/tools/v0/v0.1/_latest \
      sgraph_ai_tools__static/tools/v1/v1.0/v1.0.0

# drop CI-only artefacts that must not be committed
rm -rf sgraph_ai_tools__static/tools/v1/v1.0/v1.0.0/{en-us,fr-fr,de-de,es-es}
rm -f  sgraph_ai_tools__static/tools/v1/v1.0/v1.0.0/_common/js/build-info.js
```

Then un-ignore the new path in `.gitignore` and commit. **This commit changes nothing about
what is served** — it only adds a materialised copy. Deliberately mechanical and reviewable:
556 file additions, zero edits.

### Phase 2 — Prove byte-equality (the "same features and functionality" gate)

Add `scripts/verify_flatten.py`:

```
for every file in build(tools/v0/v0.1/*)         # the old layered result
    assert sha256 == sha256 of tools/v1/v1.0/v1.0.0/<same relative path>
assert file sets are identical
exit non-zero on any difference
```

Run it in CI on every PR for the whole migration window. **Phase 2 must be green before
Phase 3 begins.** This is what makes "identical functionality" a checked fact rather than a
hope. Any intentional removal from Phase 4 is added to an explicit allow-list in this script,
so every deviation is a reviewed line of code.

### Phase 3 — Parameterise the pipeline

`.github/workflows/deploy-tools.yml`, replacing the five hardcoded `tools/v0/v0.1` paths:

```yaml
env:
  AWS_REGION  : eu-west-2
  SOURCE_DIR  : sgraph_ai_tools__static
  RELEASE_DIR : tools/v1/v1.0/v1.0.0        # single source of truth for the tools tier

# Step A becomes a file read, not a directory glob:
- name: Resolve release version
  run: echo "ui_version=$(cat sgraph_ai_tools/version)" >> $GITHUB_OUTPUT

# Step B (build_ifd_latest.py) is DELETED — there is nothing to layer.

# Steps C/D/F point at $RELEASE_DIR and emit into build/ rather than the source tree:
- run: python scripts/generate_tools_i18n_pages.py --source-dir $SOURCE_DIR/$RELEASE_DIR --out build/
- run: python scripts/generate_manifests.py        --source-dir build/          # NEWLY WIRED
- run: python scripts/inject_build_version.py      --source-dir build/ --version ${{ steps.v.outputs.ui_version }}
- run: python scripts/deploy_static_site.py --site sgraph-tools \
         --version ${{ steps.v.outputs.ui_version }} --source-dir build/ …
```

Also in this phase, fixing P7/P8:

- [ ] Version comes from **`sgraph_ai_tools/version`**, set to `v1.0.0`; reconcile it with the
      root `version` file and make `increment-tag` write it, so the git tag and the deployed
      version become one counter.
- [ ] **Fail the build when AWS credentials are missing** on `dev`/`main` pushes, instead of
      skipping silently.
- [ ] **Drop `--skip-validation`**, enabling `validate_website_files` and `check_broken_links`.
- [ ] **Add `--delete` to the CSS/JS/JSON/image/font sync passes** so removed files leave S3.
      Safe only because releases are now immutable snapshots per version.
- [ ] Add a **test job** running `sgraph_ai_tools__static/tests/playwright/` against the built
      `build/` tree before any upload.

### Phase 4 — Consolidation passes (the actual clean-up)

Each is a separate reviewable PR, each updates `verify_flatten.py`'s allow-list:

| 4a | Converge multi-versioned modules | Pick one version per module for all 16 in P6; repoint imports; add a CI lint that fails on two live versions of one module. |
| 4b | Prune orphans | Delete the 72 unreferenced `core`/`components` versions **only after Phase 0's consumer check clears each one**. |
| 4c | Normalise `core/sg-layout/v0.1.0/` | Move to `core/sg-layout/v0/v0.1/v0.1.0/` to match all 237 other modules; repoint the 107 references. |
| 4d | Rebuild the registry | Regenerate `sg-tool-registry.js` from the 50 tool `manifest.json` files. Strip the layering changelog. Decide per tool whether the 6 unlisted ones (`auth-mvp`, `google-photos-cors`, `heic-decode`, `send-receive`, `vault-mgr`, `video-creator`) get listed or deleted. |
| 4e | Retire superseded demos | `heic-decode` (superseded by `heic-converter`), `sg-tree-demo`, `vfs-tree-demo`, `vfs-dev`, `llm-dev`, `one-shot-chat`, `send-sim` — **this is the first time deleting a tool is even possible**. Owner decision required per tool. |
| 4f | Fix deep relative imports | The 4 remaining `../../../../../core/…` references become root-absolute. |

### Phase 5 — Cutover

1. Deploy `v1.0.0` to **dev** (`releases/v1/v1.0/v1.0.0/`). Old dev origin untouched.
2. Smoke-test all 50 tools on dev, plus the `vault-peek` embedding path and the two
   `dev.sgraph.ai` header dependencies.
3. Repoint the **dev** CloudFront origin to the new release prefix. Verify.
4. Repeat for **main**, then **production**, on separate days.
5. Only after production is stable: delete `tools/v0/` from the working tree.
   `releases/v0/…` in S3 is **never** deleted — old URLs keep resolving.

### Phase 6 — Lock the door

Add to `.claude/CLAUDE.md` and enforce in CI:

- New tools go in `tools/v1/v1.0/v1.0.0/en-gb/{tool}/`. **No new version folders under `tools/`.**
- One live version per shared module; a second one fails the lint.
- The reality document is updated in the same commit as any tool change (already policy —
  now mechanically checkable, because there is one folder to diff).
- Re-base policy for D2-alt, if adopted: never exceed 20 delta layers before a major re-base.

## 5. Rollback

| Phase | Rollback |
|---|---|
| 1–2 | Delete the new folder. Nothing deployed changed. |
| 3 | Revert the workflow commit. The `v0` tree is still present and still builds. |
| 4 | Revert the individual PR. `verify_flatten.py` catches any unintended behaviour change. |
| 5 | Repoint the CloudFront origin back to `releases/v0/v0.1/v0.1.67/`, which is still in S3 and untouched. **Sub-minute rollback.** |
| 6 | Policy only. |

The `ifd-v0-final` git tag makes the entire pre-flatten tree recoverable indefinitely.

## 7. Open decisions for the owner

1. **`v1.0.0` or `v0.2.0`?** Plan is written for `v1.0.0`; substituting is a find-and-replace.
2. **`shared/` prefix for `core`/`components`?** Needs a CloudFront behaviour change. Deferrable
   without affecting the rest of the plan.
3. **D2 or D2-alt?** Blocking answer comes from Phase 0's consumer grep for pinned per-patch
   tool URLs.
4. **Phase 4e retirements** — which of the 7 superseded demos actually go.
5. **Does `latest/` become the CloudFront origin?** `deploy_static_site.py` has populated it "for
   future origin switch" for some time; the flatten is a natural moment to either use it or
   remove it.
