# IFD Consolidation — Flattening v0.1.x into v0.3.0

**Version:** v0.2.92
**Role:** DevOps (with Architect input)
**Date:** 2026-08-25
**Status:** PROPOSED — none of the target structure exists yet

---

## Why this document exists

`sgraph_ai_tools__static/tools/` currently holds **68 delta folders** (`v0.1.0` → `v0.1.67`)
containing **904 files**. The deployable site is not any one of those folders — it is the
result of layering all 68 of them, in order, at CI time. That layered result is **556 files**.

**348 files in the repo (38%) are dead weight**: written once, overwritten by a later layer,
never served to anyone. And there is no way to remove any of them, because the layering
algorithm can only copy — it has no delete primitive.

This document set analyses how the pipeline works today, evidences the problems, and proposes
a flattening into a single independent release folder.

## The release number: v0.3.0

Not `v0.2.0` — that is an existing git tag from 2026-04-23, one of **93 tags** in the `v0.2.x`
range (`v0.2.0` … `v0.2.92`), and the same series is in active use as this repo's document
filename prefix. `v0.3.0` is free in all four version namespaces (git tags, doc prefixes,
`tools/v0/` directories, S3 `releases/v0/` prefixes) and is exactly what `increment-tag`
produces on the next push to `main` — so the flatten is also the moment the repo's two
divergent version counters merge into one. Full evidence in Part 3, section D3.

---

## The one-paragraph summary

The IFD delta-layering model **reimplements version control inside a version-controlled
repository**. Git already stores immutable history; S3 already stores immutable release
prefixes. The 68 folders in between provide neither — they only guarantee that reading the
current state of any tool requires mentally replaying up to 18 layers. The proposal is to
materialise the layered result **once**, into `tools/v0/v0.3/v0.3.0/`, make that folder the
complete and only truth for the tools tier, and let CI keep publishing immutable versioned
releases to S3 from it. `core/` and `components/` keep their folder-versioning — they are a
public pinned-URL API consumed by other SGraph properties — but get their 72 orphaned
version folders pruned.
