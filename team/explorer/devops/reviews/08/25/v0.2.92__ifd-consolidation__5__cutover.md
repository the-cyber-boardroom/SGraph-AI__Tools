# Part 5 — Cutover: what the live site actually told us

**Version:** v0.2.92 · Part 5
**Date:** 2026-08-25

Part 3 planned Phase 5 as a four-step CloudFront origin migration. Probing the live
sites changed that: **no origin repointing is needed at all**, and the real risk turns
out to be somewhere else entirely.

---

## Finding 1 — The origin is already `latest/`, not a versioned path

`deploy_static_site.py` says in three places that "CloudFront origin points to
`releases/{ifd_path}/`" and that `latest/` is built "for future origin switch". **Those
comments are wrong.** Tested against the live dev site:

| URL | Result | Meaning |
|---|---:|---|
| `dev.tools.sgraph.ai/tools/v0/v0.1/v0.1.68/en-gb/` | **404** | the nested versioned archive is not at the origin |
| `dev.tools.sgraph.ai/tools/v0/v0.1/_latest/en-gb/` | **404** | nor is `_latest` |
| `dev.tools.sgraph.ai/en-gb/` | 200 | clean URLs served from the prefix root |
| `dev.tools.sgraph.ai/core/sg-layout/v0.1.0/sg-layout.js` | 200 | shared tiers resolve |

Only `latest/` has that shape. `releases/{version}/` carries the full nested archive,
which would make the first URL a 200. It is a 404, so **the origin is `latest/`**.

**This removes the entire cutover risk.** `--flat-release` already syncs to
`latest/` with `--delete`, so the flattened release goes live the moment this branch
merges to dev. No CloudFront change, no origin repoint, no coordination window.

It also retires the Part 3 open question "does `latest/` become the origin?" — it
already is, and has been for some time.

> **Correction to Part 1.** Its deployment diagram labels
> `releases/v0/v0.1/v0.1.67/` as "CloudFront origin". That was read from the code
> comments and is wrong. The origin is `latest/`; the release prefixes are the
> immutable archive, used for rollback only.

## Finding 2 — Production is four months stale

```
dev.tools.sgraph.ai   uiVersion v0.1.68   built 2026-08-25T13:53Z
tools.sgraph.ai       uiVersion v0.1.53   built 2026-04-24T16:30Z
```

Production has not been deployed since April. Everything from v0.1.54 onward —
`sg-video-editor`, `linkedin-publisher`, `vault-peek`, `mermaid-diagrams`,
`agent-with-tools`, `heic-converter`, `audio-transcribe`, `live-transcribe`,
`video-publisher`, `whatsapp-desk`, `narrated-review`, `markdown-viewer`,
`media-probe`, `youtube-probe` — exists only on dev.

The production cutover is therefore **not** "v0.1.68 → v0.3.0". It is a fifteen-release
jump that happens to also be a pipeline change. Those are two different risks and should
not be taken in one step:

1. Prove v0.3.0 on dev (automatic on merge).
2. Deploy `main`, verify.
3. Only then dispatch `production`, and treat it as the big release it is.

## Finding 3 — `Cache-Control` is missing on every served asset, live

Confirmed on the running site, not merely inferred from the code:

```
$ curl -sI https://dev.tools.sgraph.ai/_common/js/sg-tool-registry.js
content-type: text/javascript
x-cache: Miss from cloudfront
                                     ← no cache-control header at all
```

`_sync_clean_url_content` syncs `_common/`, the locale folders and `i18n/` with bare
`aws s3 sync`, passing neither `--content-type` nor `--cache-control`. So the entire
cache strategy — 1 day for CSS/JS, 1 week for images — has never applied to anything a
visitor actually downloads; those objects fall back to CloudFront's 300s default TTL.

`--flat-release` sets both on every pass. `verify_deployment.py` checks them.

> **Correction to Part 3.** It also claimed `.md` files "were served as `text/html`".
> Only the copies inside the nested archive were, and the archive is not served. The
> served copies come from the bare sync, where the AWS CLI guesses correctly —
> `curl -sI …/SKILL-api.md` returns `text/markdown`. Setting the type explicitly is
> still better than relying on a guess, but it was never a live defect. The
> `Cache-Control` finding above is the real one.

## Finding 4 — A dead module with an import that has never resolved

`verify_deployment.py` found one unresolvable reference out of 186:

```
404  /core/vault-client/v0/v0.1/v0.1.0/sg-vault-client.js
     from en-gb/video-recorder/api/save-vault.js:40
```

Three things are true about it:

- **The path has never existed.** `core/vault-client/` only ever had `v1/v1.0`, `v1/v1.1`
  and `v1/v1.2.0`–`v1.2.3`. There is no `v0`.
- **The class it wants does not exist either.** `save-vault.js` does
  `const { VaultClient } = await import(…)` and calls `new VaultClient(...)`,
  `.connect()`, `.writeFile()`. Nothing in `core/` or `components/` exports a
  `VaultClient`; the shipped v1.2.x module is functional (`parseVaultKey`,
  `deriveVaultKeys`, `importReadKey`), not class-based.
- **It is dead code.** Nothing imports `save-vault.js`. `recorder-api.js` wires
  `save-folder.js` and `save-sg-send.js` only. Because the import is dynamic and the
  module is unreachable, it has never run and no user has ever hit it.

So it is not a live failure — but it is a module that cannot work as written.
`merge-vertical.js` and `camera-warmup.js` in the same folder are also unreferenced.

Recorded in `KNOWN_UNRESOLVED` in `verify_deployment.py` with the full reason, so the
gate is green while the finding stays visible. **Owner decision:** delete `save-vault.js`,
or rewrite it against the real vault API.

## `scripts/verify_deployment.py` — the post-deploy gate

The browser smoke tests prove the build works locally; this proves the CDN serves it.

```bash
python scripts/verify_deployment.py \
  --url https://dev.tools.sgraph.ai \
  --release-dir sgraph_ai_tools__static/tools/v0/v0.3/v0.3.0 \
  --expect-version v0.3.2
```

| Check | What it asserts |
|---|---|
| build-info version | the CDN is serving the release just built, not a stale one |
| tools × 5 locales | every tool in the release returns 200 at its clean URL |
| shared modules | every `/core/…` and `/components/…` path the tools import resolves |
| root files | `index.html`, `404.html`, `robots.txt`, `sitemap.xml`, `manifest.json` |
| locale landing pages | all five locale roots |
| headers | `Content-Type` and `Cache-Control` correct per file type |

Run against live dev today it reports: 49 tools × 5 locales all 200, 185 of 186 shared
modules resolving, all root files and locale pages present — and fails on the two real
defects above (missing `Cache-Control`, the dead `vault-client` import). That is the
correct result: it fails on things that are actually wrong.

## Revised cutover

```
1. Merge this branch to dev.
      The workflow builds tools/v0/v0.3/v0.3.0 and syncs it to latest/ with --delete.
      No CloudFront change. The flat release is live on dev.sgraph.ai immediately.

2. Verify dev.
      python scripts/verify_deployment.py --url https://dev.tools.sgraph.ai \
        --release-dir sgraph_ai_tools__static/tools/v0/v0.3/v0.3.0 \
        --expect-version $(cat version)
      Expect: all checks pass, including the headers that fail today.

3. Soak. Let a few dev releases run through the new pipeline — v0.3.2 … v0.3.7 or so.
      Each one exercises build -> verify -> link-check -> smoke tests -> deploy.

4. main. Merge dev to main; same pipeline, same verification against the main URL.

5. production. Dispatch manually. This is the fifteen-release jump from Finding 2,
      not a routine deploy — verify tool by tool.

6. Only then: delete tools/v0/v0.1/ (69 folders, 936 files).
      Tag the commit before it as ifd-v0.1-final.
      The verify-flatten CI step self-disables when the directory is gone.
      releases/v0/v0.1/* stays in S3 untouched — old URLs keep resolving.
```

**Rollback** at any point before step 6 is `aws s3 sync` of a prior
`releases/v0/v0.1/v0.1.68/` back over `latest/`, or reverting the branch and letting the
old pipeline redeploy. Both are minutes, not hours, and neither needs a CloudFront change.
