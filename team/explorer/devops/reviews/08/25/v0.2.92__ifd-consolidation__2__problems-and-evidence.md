# Part 2 — Problems the flattening solves, with evidence

**Version:** v0.2.92 · Part 2 of 3

Every claim below is reproducible. Run from the repo root unless stated.
`$L` refers to a built `_latest`, produced with:

```bash
python scripts/build_ifd_latest.py --source-dir sgraph_ai_tools__static \
  --ifd-base tools/v0/v0.1 --up-to auto
L=sgraph_ai_tools__static/tools/v0/v0.1/_latest
```

---

## P1 — 38% of the tools tree is dead code that cannot be deleted

**Measured:** 904 files across 68 folders layer down to 556. **348 files are shadowed** —
written, then overwritten by a later layer, never served.

```bash
cd sgraph_ai_tools__static/tools/v0/v0.1
find v0.1.* -type f | wc -l        # 904
find _latest -type f | wc -l       # 556
```

83 of those are **byte-identical duplicates**:

```bash
find v0.1.* -type f -exec md5sum {} + | awk '{print $1}' | sort | uniq -c \
  | awk '$1>1{d+=$1-1} END {print d}'      # 83
```

`_common/css/tools.css` is committed **10 times**, and 9 of the 10 copies are the same bytes:

```bash
find v0.1.* -name tools.css -exec md5sum {} + | sort
# f6f73e4f…  v0.1.0  v0.1.1  v0.1.2  v0.1.3  v0.1.4  v0.1.5  v0.1.12  v0.1.14  v0.1.22
# 301eafbc…  v0.1.53
```

**Why it cannot be fixed in place:** `build_ifd_latest.py` only ever calls `shutil.copy2`.
There is no tombstone, no `.deleted` marker, no manifest of removals. Deleting `v0.1.2/…/foo.js`
from git does not remove it from the deploy if any *other* layer wrote it; and deleting the
only copy silently changes what a "pinned" older release resolves to. The layering model has
no expression for "this file is gone".

**Solved by flattening:** the release folder contains exactly the files that are served.
Deleting a file deletes it.

## P2 — Reading the current state of a tool requires replaying up to 18 folders

```bash
cd sgraph_ai_tools__static/tools/v0/v0.1
for t in infographic-gen chat playbooklm vault video-recorder; do
  echo "$t: $(ls -d v0.1.*/en-gb/$t 2>/dev/null | wc -l) layers"
done
```

| Tool | Layers | Spread across |
|---|---:|---|
| `infographic-gen` | 18 | v0.1.6 → v0.1.53 |
| `chat` | 14 | v0.1.7 → v0.1.53 |
| `playbooklm` | 11 | v0.1.39 → v0.1.53 |
| `vault` | 7 | v0.1.16 → v0.1.53 |
| `video-recorder` | 6 | v0.1.48 → v0.1.64 |

**Consequences observed:**

- No agent or human can answer "what does `infographic-gen` do today?" by reading one directory.
  `.claude/CLAUDE.md` needs a whole mandatory reality-document protocol partly because the code
  itself is unreadable without replaying history.
- `grep` over the repo returns 18 versions of the same function and no indication which one wins.
- IDE "go to definition", static analysis, and dependency scanners all see the wrong file.
- A code review diff on `v0.1.37/…/infographic-gen/api/foo.js` shows a *new file*, not a change,
  because git has no link to the `v0.1.36` copy. **Every IFD change reviews as an addition.**

**Solved by flattening:** one directory per tool, one file per file, real git diffs.

## P3 — Shared files are a serialisation point and a merge-conflict magnet

Files under `_common/` are global, so every version that touches one must ship a **complete
copy**, not a delta.

```bash
cd sgraph_ai_tools__static/tools/v0/v0.1
for d in $(ls -d v0.1.* | sort -V); do
  f=$(find "$d/_common" -type f 2>/dev/null | sed "s|$d/||" | tr '\n' ' ')
  [ -n "$f" ] && echo "$d -> $f"
done
```

| Shared file | Full copies committed | Versions |
|---|---:|---|
| `_common/js/sg-tool-registry.js` | 12 | v0.1.25, 26, 47, 48, 56, 57, 58, 59, 60, 64, 65, 66, 67 |
| `_common/css/tools.css` | 10 | v0.1.0 … v0.1.53 |
| `_common/js/sg-nav.js` | 7 | v0.1.2 … v0.1.52 |
| `404.html` / `index.html` | 9 each | v0.1.0 … v0.1.8 |

The registry is now a 214-line file whose header is a **changelog of its own layering**:

```js
   v0.1.47 changes:  - Added 'misc' category …
   v0.1.48 changes:  - Added 'voice-memo' to TOOL_SLUGS under Media …
   v0.1.56 changes:  - Added 'youtube-editor', 'youtube-upload' …
   v0.1.59 changes:  - Added 'heic-converter' …
```

Two branches that each add a tool both rewrite the whole registry into *their own* version
folder. Git cannot merge that — the files are at different paths, so there is no conflict to
resolve and **the later-numbered branch silently wins**, dropping the other tool from the
landing page.

**Already visible:** 6 tool directories ship but are absent from `TOOL_SLUGS`, so they are
unreachable from the landing page.

```bash
awk '/TOOL_SLUGS *=/,/^\]/' $L/_common/js/sg-tool-registry.js \
  | grep -oE "'[a-z0-9-]+'" | tr -d "'" | sort -u > /tmp/reg.txt
ls $L/en-gb | grep -v '\.html$' | sort > /tmp/dirs.txt
comm -23 /tmp/dirs.txt /tmp/reg.txt
# auth-mvp  google-photos-cors  heic-decode  send-receive  vault-mgr  video-creator
```

(44 slugs listed, 50 directories shipped. Nothing is listed-but-missing, so no broken links —
but 6 tools are invisible.)

**Solved by flattening:** one registry file at one path. Two branches adding a tool produce a
normal, resolvable git conflict on adjacent lines.

## P4 — `manifest.json` generation is not wired into CI, and drifts

`scripts/generate_manifests.py` exists (12 KB) but **is referenced by no workflow and no script**:

```bash
grep -rn "generate_manifests" .github/ scripts/     # no matches outside the file itself
```

Manifests are therefore hand-maintained inside version folders. 48 of the 50 shipped tools have
one; 2 do not — `google-photos-cors` and `heic-decode`.

```bash
ls -d $L/en-gb/*/manifest.json | wc -l     # 48   (of 50 tool dirs)
```

**Solved by flattening + wiring:** with one folder per tool, `generate_manifests.py` can run in
CI and regenerate every manifest deterministically from the tool tree.

## P5 — 72 orphaned core/component versions ship on every deploy

```bash
grep -rhoE '(core|components)/[A-Za-z0-9._-]+(/[A-Za-z0-9._-]+)*\.(js|css)' $L \
  | sed -E 's#/[^/]+\.(js|css)$##' | sort -u > /tmp/used.txt
find sgraph_ai_tools__static/core sgraph_ai_tools__static/components -type d \
  -regextype posix-extended -regex '.*/v[0-9]+\.[0-9]+\.[0-9]+$' | sed 's|^sgraph_ai_tools__static/||' | sort > /tmp/ondisk.txt
comm -23 /tmp/ondisk.txt /tmp/used.txt | wc -l    # 72
```

238 leaf version dirs exist; **166 are referenced by a shipped tool, 72 are not**.
`components/llm/sg-llm-bundle/` alone carries 8 versions of which 2 are live.
`components/llm/sg-llm-chat-history/` carries 11 versions of which 2 are live.

Every one of the 72 is uploaded to S3 on every deploy, to every environment.

**Nuance — this is not purely waste.** Pinned versions are the *public API* of this repo;
external consumers may hold URLs into versions this repo's own tools no longer use. Part 3
proposes verifying against consumers before pruning, not blind deletion.

## P6 — 16 modules run multiple versions simultaneously in one deploy

```bash
comm -12 /tmp/ondisk.txt /tmp/used.txt | sed -E 's#/v[0-9]+\.[0-9]+\.[0-9]+$##' \
  | sort | uniq -c | awk '$1>1' | sort -rn
```

| Module | Live versions |
|---|---:|
| `components/site-header/v1/v1.0` | 4 |
| `components/llm/sg-llm-request/v0/v0.1` | 4 |
| `core/video/v1/v1.0` | 3 |
| `core/vault-client/v1/v1.2` | 3 |
| 12 more | 2 each |

Concretely, two chat tools disagree about the same component:

```
en-gb/chat/index.html              → sg-llm-chat-history/v0/v0.1/v0.1.10
en-gb/multi-agent-chat/index.html  → sg-llm-chat-history/v0/v0.1/v0.1.8
```

A user's browser loads **two different implementations of the same custom element** depending
on which tool they open, and — if both are on a page — whichever registers first wins.
Bug reports become irreproducible across tools.

**Solved by flattening:** the major release is the moment to converge every tool onto one
version of each shared module, with a lint gate to keep it that way.

## P7 — The pipeline is structurally blocked from producing a major release

The `v0/v0.1` path is hardcoded in **five places** in the workflow:

```bash
grep -n "v0/v0.1\|v0\.1\." .github/workflows/deploy-tools.yml
# 78:  LATEST=$(ls -d ${{ env.SOURCE_DIR }}/tools/v0/v0.1/v0.1.* …
# 109: --ifd-base tools/v0/v0.1
# 115: --source-dir ${{ env.SOURCE_DIR }}/tools/v0/v0.1/_latest
# 121: --source-dir ${{ env.SOURCE_DIR }}/tools/v0/v0.1/_latest
# 155: --clean-urls-source-version tools/v0/v0.1/_latest
```

Creating `tools/v1/v1.0/v1.0.0/` today would **not** change the deploy: step A would still glob
`tools/v0/v0.1/v0.1.*`, still resolve `v0.1.67`, and still deploy the old tree. The flatten is
inert until the workflow is parameterised.

Three further version-identity defects compound this:

- The deployed version comes from **`ls | sort -V | tail -1`**, not from a version file. Adding a
  stray directory named `v0.1.99` silently redirects production.
- `increment-tag` runs on `main` with `release_type: major`, bumping a git tag that **nothing in
  the deploy reads**. The tag and the deployed version are unrelated counters.
- `sgraph_ai_tools/version` (`v0.1.0`) and the root `version` (`v0.2.92`) disagree with each
  other and with the deployed `v0.1.67`.

## P8 — Silent-success failure modes

Three ways this pipeline reports green while shipping nothing or shipping wrong:

1. **Missing AWS credentials.** `check-creds` sets `has-credentials=false`, every deploy step is
   `if:`-skipped, the job succeeds. Nothing deployed, no signal.
2. **`--skip-validation` is unconditional.** `validate_website_files`, `validate_keys_json` and
   `check_broken_links` all exist in `deploy_static_site.py` and none of them ever runs.
3. **No test job exists.** `sgraph_ai_tools__static/tests/` holds smoke tests and a
   `playwright/` directory; `grep -rn "pytest\|playwright\|npm test" .github/workflows/` returns
   nothing. Nothing verifies that the layered result actually boots.

Plus one data-loss-shaped issue: only the HTML sync pass uses `--delete`
(`deploy_static_site.py:263,324`). Removed `.js`, `.css`, `.json`, image and font files are
**never** removed from S3 and remain live at their old keys forever.
