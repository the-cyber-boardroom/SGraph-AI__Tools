## 2. Review of the plan and the work

### What held up

- **The byte-equality method worked.** Every phase change was provable: flatten identical
  (578/578), deliberate edits allow-listed one by one, drift caught and folded back with a
  strict check at the end. At no point did "same functionality" rest on belief.
- **Evidence kept correcting the plan, cheaply.** Four plan assumptions died on contact
  with the tree or the live site — v0.2.0 was a taken tag; sg-layout normalisation would
  break published URLs; module convergence is behavioural, not mechanical; the CloudFront
  origin was already `latest/`. Each was caught by a measurement *before* it became a bad
  change. The plan's habit of verifying before acting is the thing to keep.
- **The pipeline gates are real.** build → series guard → verify-flatten → link check →
  125 browser assertions → deploy → CDN verification. The old pipeline had zero checks and
  three silent-success modes.

### What the drift window exposed

- **`--allow-modifications` makes the CI gate blind to exactly what just happened.** The
  gate catches a *new path* added the old way, but v0.1.69's youtube-probe fixes were
  *edits to existing paths* — invisible to it. Had the branch merged before today's manual
  sync, dev.tools.sgraph.ai would have silently regressed youtube-probe to its broken
  v0.1.68 state. The gate is the right shape only if the parallel window is short.
  **Conclusion: merging is now the risk-reduction move, not the risk.** Every additional
  dev release on the old pipeline is another manual fold-in with no automated safety net
  for modified files.
- **P3 (the registry serialisation point) is still live** until merge — two more full
  registry copies in one week, carrying changelog prose that belongs in commit messages.

### Honest debits

- Smoke coverage gating the deploy is 4 tools of 49; 11 of 49 have any automated test.
  The gate proves the release serves and boots, not that 45 other tools work.
- Phase 4's convergence (19 multi-versioned modules) and orphan prune (64 candidates)
  remain open — correctly deferred, but open.
- Production is a 17-release jump whenever it happens, and that only grows.

**Verdict: the refactoring is done and validated up to its merge point, and the merge
point is now overdue.** Nothing outstanding blocks it; everything outstanding is made
worse by waiting.

## 3. The proposed next model — assessment

The proposal from the owner: development moves to **per-tool changes with strong per-tool
test coverage**; per-tool versions where useful; **no more overlay/delta-layering**.

This is the right next step, and the flatten is what makes it possible. Three
observations shape the concrete design:

1. **"Self-contained tool" is now literally true.** After 4f there are zero relative
   escapes from any tool folder: a tool is its own directory plus pinned root-absolute
   `/core/…` and `/components/…` imports. A change to `en-gb/{tool}/` provably cannot
   affect any other tool. That is the property per-tool CI needs, and it holds today.
2. **The IFD *goal* was never wrong — the overlay was.** What IFD wanted was immutable,
   addressable versions. Git tags and the S3 `releases/v0/v0.3/{version}/` archive already
   provide those per release. What the overlay added was the reimplementation of version
   control inside the repo, and Parts 1–2 measured what that cost.
3. **The tool-api pattern makes uniform testing cheap.** Tools expose `window.__tool` and
   fire `tool:ready`; the existing smoke tests all drive that surface. A generic harness
   can therefore give *every* tool a boot-level test without 49 hand-written files.

## 4. The per-tool model, concretely

### Repo shape (unchanged from the flatten — this is the point)

```
tools/v0/v0.3/v0.3.0/en-gb/{tool}/     ← the tool. The only copy. Edited in place.
    api/  ui/  styles/  skills/  index.html  manifest.json
sgraph_ai_tools__static/tests/playwright/{tool}-*.js
```

A tool change is: edit the folder, bump `manifest.json.version`, update/add its tests,
one commit. History is git; the released snapshot is `releases/v0/v0.3/{site-version}/`.

### Per-tool versioning without the overloading technique

- `manifest.json.version` is the tool's own version, bumped per change — already the
  convention (`youtube-probe` went 0.1.0 → 0.1.1 inside one site release).
- Every site release archives every tool at `releases/v0/v0.3/{version}/en-gb/{tool}/` —
  immutable, already built by `--flat-release`. A past tool version is
  *(site version, tool folder)*, recoverable from S3 or `git show`.
- **No folder-per-version inside the repo, ever, for tools.** If an external consumer one
  day needs a pinned *served* tool URL, that is a CloudFront route to the `releases/`
  prefix — an infrastructure decision to take when a real consumer exists, not a repo
  structure to maintain speculatively. (`core/` and `components/` keep folder-versioning;
  they are the pinned public API and that model is correct for them.)

### The test contract (the ratchet)

Three layers, cheapest first:

1. **Generic boot gate — every tool, no authoring.** One harness that walks
   `en-gb/*/manifest.json`, opens each tool, and asserts: page loads, no console/page
   errors, and — where the tool registers `window.__tool` — `tool:ready` fires. Runs
   against the built tree in CI. This is the floor under all 49 tools and it exists the
   week it is written. (External embeds like the dev.sgraph.ai site-header must be
   network-stubbed so third-party outages cannot fail the gate.)
2. **Per-tool smokes — the existing pattern, spread by the ratchet.** The rule that
   grows coverage without a big-bang test-writing project: **CI identifies which tools a
   PR touches (git diff on `en-gb/{tool}/`) and (a) runs those tools' smoke tests, (b)
   fails if a touched tool has none.** You cannot change a tool untested, but nobody has
   to write 38 test files up front. 11/49 tools have tests today; the ratchet converges
   the rest in the order they actually change.
3. **Pure-logic unit tests where the tool has real algorithms** (`tests/node/`, no
   browser) — e.g. caption parsing, crypto, zip assembly. Encouraged per tool, not
   mandated globally.

CI shape: the changed-tools job replaces nothing — the 4-tool deploy gate stays as the
whole-site floor; changed-tools runs on top and is what makes per-tool development safe.

### What retires

- `build_ifd_latest.py` (already out of CI) and the `verify_flatten` step retire fully at
  Phase 5 step 6, when `tools/v0/v0.1/` is deleted.
- The registry changelog habit — gone already; commit messages carry it.
- The "which versions must I replay" question — unaskable in this model.
