# Part 7 — Side-by-side: both pipelines live at once, zero infrastructure change

**Version:** v0.2.92 · Part 7
**Date:** 2026-09-01

Answers three questions from the owner, then records the side-by-side design that came
out of the third.

---

## 1. "Have all the files been consolidated into v0.3.0?"

**Yes, for the tools tier — measured, not assumed.** Layering all 71 delta folders
(v0.1.0 → v0.1.70) produces 582 served files. The flat release contains 577. The
difference is exactly: 5 paths retired on purpose (the two probes, allow-listed), and 6
files whose content deliberately differs (the registry with two live tools listed and
its changelog stripped; the two repaired manifests; the three root-absolute import
fixes). `verify_flatten` in strict mode confirms there is nothing else.

**Deliberately NOT copied into v0.3.0:** `core/` and `components/`. They are the pinned
public API — imported root-absolutely by the tools and by send/vault/workspace/extension
— and they keep their own folder-versioning at the repo root. The deployable artifact is
complete because `build_release.py` assembles all three tiers into `build/` at deploy
time. So: the *tools* are fully consolidated; the *shared tiers* are referenced in place,
by design (Part 3, D1).

## 2. "Previous versions must remain intact"

**They are, bit for bit.** `git diff origin/dev -- tools/v0/v0.1/ core/ components/` is
empty — every consolidation change lives in `tools/v0/v0.3/v0.3.0/`, `scripts/`, docs,
and the new workflow file. The legacy workflow `deploy-tools.yml` has been restored
**verbatim from origin/dev** as part of the side-by-side split below, so after merge the
old pipeline continues exactly as it runs today.

Going forward the freeze is enforced, not just promised: the v3 workflow fails loudly if
a push modifies anything under `tools/v0/v0.1/` ("Enforce the v0.1.x freeze" step). All
changes happen on the new code.

## 3. "Can we run both versions side by side?" — Yes. Here is how.

The one collision is `latest/`: both pipelines want to write it, and it is the
CloudFront origin. Everything else is already disjoint (`releases/v0/v0.1/` vs
`releases/v0/v0.3/`). Resolution: **the v3 pipeline deploys to `latest/v3/`**, a
subfolder the legacy pipeline never touches (all its `latest/` syncs are scoped to its
own subfolders — `core/`, `components/`, `_common/`, locale dirs, `i18n/`, root files —
none with a root-level `--delete`).

```
websites/sgraph-tools/dev/
├── releases/v0/v0.1/{v}/     legacy archive          (legacy pipeline, unchanged)
├── latest/                   ← CloudFront origin      (legacy pipeline, unchanged)
│   ├── core/ components/ _common/ en-gb/ … i18n/     the OLD site, live as today
│   └── v3/                                            the NEW site   (v3 pipeline)
│       ├── core/ components/ _common/ en-gb/ … i18n/
```

Both are then live simultaneously with **no CloudFront change**:

| | URL | Built from |
|---|---|---|
| Old site | `https://dev.tools.sgraph.ai/` | 71-layer IFD merge (frozen at v0.1.70) |
| New site | `https://dev.tools.sgraph.ai/v3/` | `tools/v0/v0.3/v0.3.0` |

### Proven, not assumed

Served the built release under a `/v3/` prefix locally (shared tiers at the root, as the
legacy deploy provides them) and ran the browser suites against `BASE .../v3`:

- `markdown-viewer` — **25/25**, including the landing-page check at `/v3/en-gb/`.
- `whatsapp-desk` — **22/22**. (Its first run failed for a test-harness reason worth
  recording: that test reads its own `WHATSAPP_DESK_URL` env var rather than `BASE_URL`,
  so it was probing the wrong path. The tool itself boots cleanly under the prefix —
  `window.__tool` live, no failed requests. The generic boot harness planned in Part 6
  should normalise this env-var inconsistency.)

Why it works: tool-internal imports are relative; shared imports are root-absolute
`/core/…`, `/components/…`, which the legacy pipeline serves from the same repo —
verified bit-identical between both trees. The three root-absolute `/_common/` strings
in the tree are all doc-comments, not code.

### Known preview-only escapes (cosmetic, documented)

1. `/v3/` root: the locale detector redirects root-absolutely → lands on the old site's
   `/en-gb/`. Enter the preview at `/v3/en-gb/` directly.
2. Footer "All Tools" links (`/en-gb/`) → old site.
3. `video-recorder` → `video-publisher` handoff constant (`/en-gb/video-publisher/`) →
   old site's copy.

None affects a tool's own function; all vanish at the flip, when the release owns the
root. These are left as-is rather than rewritten — churn for a temporary preview is the
wrong trade.

### The mechanics

- `deploy_static_site.py` gains `--latest-subdir` (deploy under `latest/{subdir}/`) and
  `--latest-only` (skip the `releases/` archive).
- `deploy-tools.yml` — **restored verbatim from origin/dev.** Still owns `latest/`,
  `increment-tag`, and the v0.1 archive.
- `deploy-tools-v3.yml` — the flat pipeline in side-by-side mode: freeze guard → build →
  verify-flatten → link check → browser smokes → deploy to `latest/v3/` → CDN
  verification against `…/v3`. No increment-tag (the legacy one owns the counter; the
  version read here may lag one inside a push window, acceptable because the preview
  writes no archive). Distinct concurrency group.

### The flip (one commit, one-line rollback)

When `/v3/` has soaked: in `deploy-tools-v3.yml` set `LATEST_SUBDIR: ''` and
`LATEST_ONLY: 'false'`, move `increment-tag` into it, and disable `deploy-tools.yml`.
The flat release then owns `latest/` and starts the `releases/v0/v0.3/` archive.
Rollback is reverting that commit — the legacy pipeline redeploys the frozen v0.1.70
over `latest/` on its next run. `latest/v3/` is deleted once the flip has held.
