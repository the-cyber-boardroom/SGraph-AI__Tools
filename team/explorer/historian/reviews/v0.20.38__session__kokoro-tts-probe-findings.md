## 2. CDN Strategy — What Works

### Problem
The brief's CDN snippet used a bare npm specifier:
```js
import { KokoroTTS } from "kokoro-js"
```
This fails in a browser module context — bare specifiers are not valid without an import map.

### Candidates tested

| CDN | Result | Reason |
|-----|--------|--------|
| `esm.sh/kokoro-js` | **WORKS** | Rewrites all transitive bare specifiers (`@huggingface/transformers`) to full CDN URLs automatically |
| `cdn.jsdelivr.net/npm/kokoro-js/dist/kokoro.js` | Works with importmap | Requires `<script type="importmap">` in `<head>` resolving `@huggingface/transformers` to its own CDN path |
| `cdn.jsdelivr.net/npm/kokoro-js@1.2.2/...` | **404** | Version 1.2.2 does not exist on npm |
| Pinned `@latest` | Fragile | Breaks on major bumps — never pin to `@latest` in dynamic imports |

### Decision
**Use `esm.sh/kokoro-js` with no version pin for the probe.** For `sg-tts.js` production code, pin to the specific stable semver once confirmed (e.g. `esm.sh/kokoro-js@1.3.1`).

## 3. Kokoro API Shape — What Was Discovered

The Kokoro JS API is not documented well. Findings from probing the live model:

### Model load
```js
const tts = await KokoroTTS.from_pretrained('onnx-community/Kokoro-82M-v1.0-ONNX', { dtype: 'q8' });
```
- `dtype: 'q8'` = quantised 8-bit WASM; no WebGPU required, runs everywhere
- First load: ~2.7s on a warm cache (model files already cached by browser after initial 160MB download)
- Subsequent loads (workers): 4.9–6.5s (parallel, so wall clock = slowest)

### Audio generation
```js
const audio = await tts.generate(sentence, { voice, speed });
// audio shape: { audio: Float32Array, sampling_rate: 24000 }
```
- Returns `{ audio: Float32Array, sampling_rate: number }` — NOT `{ data, sampling_rate }` as assumed
- `sampling_rate` is always 24000 Hz for Kokoro 82M
- `tts.stream()` exists but stalls after the first sentence due to GC pressure on the main thread — do not use on main thread

### Voice list
```js
tts.list_voices()       // returns [] on this version
tts.voices              // object — Object.keys() gives the voice IDs
```
28 confirmed voices: `af_heart`, `af_alloy`, `af_aoede`, `af_bella`, `af_jessica`, `af_kore`, `af_nicole`, `af_nova`, `af_river`, `af_sarah`, `af_sky`, `am_adam`, `am_echo`, `am_eric`, `am_fenrir`, `am_liam`, `am_michael`, `am_onyx`, `am_puck`, `am_santa`, `bf_emma`, `bf_isabella`, `bm_george`, `bm_lewis`, `bf_alice`, `bf_lily`, `bm_daniel`, `bm_fable`

Voice naming convention:
- `af_` = American Female
- `am_` = American Male
- `bf_` = British Female
- `bm_` = British Male

## 4. Main Thread vs Web Worker

### Problem
Running `tts.generate()` on the main thread blocks everything: `setInterval` timers stop, UI freezes, GC stalls. On a WASM build without WebGPU, a single sentence takes 20–30s of synchronous compute.

### Solution: Web Worker with isolated ONNX heap
- Each worker runs its own `KokoroTTS.from_pretrained()` — independent WASM memory
- Zero-copy audio transfer: `postMessage(msg, [samples.buffer])` transfers the `Float32Array` without cloning
- Main thread stays fully responsive (timer ticks smoothly, UI updates work)

### Worker message protocol
```
IN:  { type: 'load',     cdnUrl }
IN:  { type: 'generate', id, sentences: string[], voice, speed }
OUT: { type: 'loading',  message }
OUT: { type: 'ready',    voices: string[] }
OUT: { type: 'progress', id, index, total, sentence }
OUT: { type: 'chunk',    id, index, total, sentence, samples: Float32Array, sampleRate }
OUT: { type: 'done',     id }
OUT: { type: 'error',    id?, message }
```

## 5. Parallel Generation — Performance Benchmark

The probe uses a worker pool (`POOL_SIZE = 8`). Each sentence is dispatched to a different worker simultaneously via `Promise.all`. Results preserve sentence order regardless of completion order.

### Results

All runs on the same machine (WASM, no WebGPU, model cached):

| Sentences | Workers used | Audio out | Wall clock | Realtime ratio | Est. sequential | Speedup |
|-----------|-------------|-----------|-----------|----------------|-----------------|---------|
| 2 (long)  | 2           | 14.47s    | 32.5s     | 0.45×          | ~59s            | **1.8×** |
| 5 (short) | 5           | 17.95s    | 22.1s     | 0.81×          | ~87s            | **~4×** |
| 8 (mixed) | 8           | 25.23s    | 30.1s     | 0.84×          | ~167s           | **~5.6×** |
| 8 (same)  | 8           | 25.23s    | 29.0s     | 0.87×          | ~167s           | **~5.8×** |

The last two rows are the same 8-sentence input run back-to-back — only 1.1s variance (3.5%), confirming generation time is **highly deterministic**.

### Key insight: wall clock = longest sentence

Parallel wall clock time ≈ the generation time of the slowest individual sentence. This is because each worker runs independently and we wait for all to finish. The longest sentence in the 8-sentence tests was sentence 4 (4.72s audio, ~30s to generate) — and that set the ceiling for all runs.

**Design implication:** split text into short sentences aggressively before dispatching. Commas and clause boundaries are worth splitting on, not just `.!?`. Shorter chunks lower the per-worker ceiling and reduce total wall clock.

### Sentence length vs generation time

From the benchmark data, per-sentence generation time is roughly proportional to audio duration, which is roughly proportional to character count. Approximate ratio observed: **~6–7s compute per 1s of audio output** at q8 WASM speed. This is stable enough to surface a pre-generation ETA to users.

### Memory cost

8 workers × ~160MB model ≈ **1.3GB RSS**. Acceptable on modern hardware with a cold-start warning. For `sg-tts.js`, make pool size configurable (default 4 for most machines, 8 for power use).

## 6. Health Check Design (Validated)

The probe's 7-step health check is the pattern to carry into `sg-tts.js` `runHealthCheck()`:

| Step | What it checks |
|------|---------------|
| 1. WebAssembly | `typeof WebAssembly === 'object'` |
| 2. AudioContext | `new AudioContext()` succeeds |
| 3. CDN HEAD | HTTP 200 from CDN URL (confirms network + CORS) |
| 4. Dynamic import | `await import(cdnUrl)` resolves and exports `KokoroTTS` |
| 5. Model load | `from_pretrained()` succeeds on main thread AND all pool workers simultaneously |
| 6. Voice list | `tts.voices` / `tts.list_voices()` returns non-empty array |
| 7. Test generation | Single short word generates valid `Float32Array` |

**Step 5 is the key design decision:** health check does not complete until `Promise.all([mainLoad, ...workerLoads])` resolves. This guarantees the generate buttons are only enabled once the full worker pool is warmed up.

## 7. What Is NOT Confirmed

- **WebGPU path:** All tests ran on WASM (no WebGPU). WebGPU would be significantly faster (~10× or more) but was not tested. The `dtype: 'q8'` option forces WASM. When WebGPU is available, Kokoro should use it automatically — but this needs validation.
- **Safari:** Safari has no WebGPU support and its WASM JIT is slower than Chrome/Firefox. Not tested.
- **SharedArrayBuffer / COOP/COEP:** Some ONNX WASM builds require `Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy: require-corp` headers. The probe ran on localhost (which is exempt). CloudFront must serve these headers for production.
- **Exact kokoro-js version to pin:** `esm.sh/kokoro-js` was used without a version. Before shipping `sg-tts.js`, pin to an explicit semver.
