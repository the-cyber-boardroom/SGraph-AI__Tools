## Two sg-layout Architecture

The original design had a fixed `<aside>` sidebar. We replaced it with two independent `sg-layout` instances. This was a deliberate constraint.

**Why not one full-page sg-layout?**
A single `sg-layout` would require every panel (form, tree, trace, file viewer) to be a custom element managed by the layout. The credentials form is plain HTML with `document.getElementById()` references used by `main.js` — wrapping it in a shadow-DOM custom element would break those lookups. Two sg-layouts let the left column be self-contained with its own resize/collapse, and the right column manage tabs, without any panel needing to know about the other.

**Grid layout:**

```css
.ved-body {
    display: grid;
    grid-template-columns: 300px 1fr;
}
```

The left column is fixed at 300px from CSS. The internal split (Credentials top, Vault Files bottom) is managed by sg-layout's `type: 'column'` with `sizes: [0.38, 0.62]`, giving proper resize handles and collapse buttons between the two panels.

## ved-cred-panel: Non-Shadow Custom Element

The credentials panel (`ved-cred-panel`) is a custom element but deliberately **not** using shadow DOM.

**Why no shadow DOM?**
`main.js` uses `document.getElementById()` to find `#setup-form-container`, `#creds-display`, `#cred-vault-id`, `#switch-vault-btn`, etc. These calls only work on the main document tree. If those elements lived inside a shadow root, `document.getElementById()` would return null.

The element exists only to give `sg-layout` a tag to instantiate. Its `connectedCallback` writes the HTML directly into its own light DOM, then dispatches `ved:cred-panel-ready` so `main.js` knows the DOM is available.

**Bootstrap sequence:**
1. `main.js` calls `initLayout()`
2. `initLayout()` calls `leftLayout.setLayout()` inside a `customElements.whenDefined('sg-layout')` microtask
3. `setLayout()` instantiates `ved-cred-panel` and calls `connectedCallback()`
4. `connectedCallback()` writes form HTML + dispatches `ved:cred-panel-ready`
5. `main.js` listener (registered before the microtask fires) catches the event and bootstraps

This ordering is reliable: the `{ once: true }` listener in `main.js` is registered synchronously at module evaluation time, before any microtask runs.

## Simple Token vs Full Vault Key

Two vault key systems coexist and are now both supported in the form:

### Simple Token (`word-word-NNNN`)
Created by `sg-key-generator` and used by `sg-vault-init` when creating vaults from send.sgraph.ai. The token is the **only** secret — there is no separate vault ID in the string.

Derivation:
```
PBKDF2(token, salt='sgraph-send-v1', 600k iter, SHA-256) → 256 bits
HKDF(bits, info='vault-read-key', SHA-256) → readKeyBytes
vaultId = hex(SHA-256(token))[:12]
```

### Full Vault Key (`passphrase:vaultId`)
Used by `sg-vault-client`'s `deriveVaultKeys`. Vault ID is explicit in the string; passphrase and vault ID are derived separately.

**Detection:** `SIMPLE_TOKEN_RE = /^[a-z]+-[a-z]+-\d{4}$/` — tested before `parseVaultKey` is attempted.

**After derivation:** Both paths produce `{ vaultId, readKey (base64url) }` and flow into the same `buildVaultHandle` (readKey + vaultId mode), which reconstructs all HMAC-derived file IDs using `sg-vault-v1:file-id:*` domain strings. The HMAC format is identical between the two systems.

## Presigned URL Fallback

For large files, the direct API route (`/api/vault/read/{vaultId}/bare/data/{blobId}`) can return 502, 413, or 504 when the file exceeds API gateway limits. The fallback:

```
GET /api/vault/presigned/read-url/{vaultId}/{encodedPath}
→ { url, expires_in }

GET {url}   (plain GET to S3, no auth headers)
→ IV-prepended AES-256-GCM ciphertext

decryptAesGcm(readKey, ciphertext)
→ plaintext bytes
```

Key points:
- The presigned endpoint requires **no auth headers** — the server signs the S3 URL
- The S3 response is still encrypted (IV first 12 bytes, ciphertext remainder)
- `decryptAesGcm` is a local function in `ved-file-viewer.js` for this path, since `readObject()` handles decryption internally for the direct path

The error detection is string-based (`/502|413|504/.test(err.message)`) because `readObject` throws with the HTTP status in its message.

## Shadow DOM and CSS Isolation

`ved-file-viewer` uses shadow DOM (`attachShadow({ mode: 'open' })`). This means:

- **Component styles** in `STYLES` const apply only inside the shadow root — no leakage out
- **External stylesheets** in `document.head` do **not** reach inside the shadow root

This caused the `_page.json` rendering bug: `PageLayoutRenderer` was loaded by adding a `<link>` to `document.head`, but the rendered content lives inside the shadow root. The fix was `_injectPageRendererCSS(endpoint)`:

```js
async _injectPageRendererCSS(endpoint) {
    if (this._shadow.querySelector('.plr-injected-css')) return  // idempotent
    const resp = await fetch(cssUrl)
    if (!resp.ok) return
    const style = document.createElement('style')
    style.className = 'plr-injected-css'
    style.textContent = await resp.text()
    this._shadow.appendChild(style)   // <-- inside the shadow root
}
```

Fetching CSS text and injecting as `<style>` is the standard pattern for getting external styles into shadow DOM.

## Event Bus Pattern

All cross-component communication uses `document.dispatchEvent` with `CustomEvent`:

| Event | Dispatched by | Consumed by |
|-------|--------------|-------------|
| `ved:vault-ready` | `main.js` | `ved-vault-tree`, `ved-file-viewer` (indirectly via layout) |
| `ved:cred-panel-ready` | `ved-cred-panel` | `main.js` |
| `ved:file-open` | `ved-vault-tree` | `ui-layout.js` → `addTabToStack` |
| `sg-vault-fetch:*` | `ved-vault-tree`, `ved-file-viewer` | `sg-vault-trace` |
| `sg-vault-key:key-ready` | `main.js` | `sg-vault-trace` (displays vault ID) |

No component imports any other component directly. The event bus is the only coupling.

## File Size Discipline

`ved-file-viewer.js` grew to ~600 lines during development. The CLAUDE.md rule says to split at ~500. Given that the file has a single clear responsibility (fetch + render one file), the judgment call was to keep it whole rather than split on an artificial boundary. The rendering logic is already structured as a dispatch table (`if mime === 'application/pdf' ... else if ...`).

If the file grows further (e.g. adding video rendering, audio waveforms, spreadsheet support), those rendering branches should be extracted into sibling files: `ved-file-viewer-pdf.js`, `ved-file-viewer-page-json.js`, etc., each exporting a `render(shadow, bytes, entry)` function.
