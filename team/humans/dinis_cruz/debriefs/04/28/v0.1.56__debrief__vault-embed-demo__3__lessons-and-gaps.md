# Debrief: Vault Embed Demo — Part 3: Lessons Learned & Open Gaps

**Version:** v0.1.56
**Date:** 28 April 2026
**Branch:** `claude/create-web-vault-components-aKlgf`

---

## Lessons Learned

### 1. sg-layout does not listen for DOM events

Early implementation dispatched `CMD_ADD_PANEL` as a DOM event to add file viewer tabs. This silently did nothing. `sg-layout`'s public API is imperative:

```js
layout.addTabToStack(stackId, { tag: 'ved-file-viewer', title: 'File', state: { entry, vault } })
```

`addTabToStack` requires a `stackId` captured from `layout.getLayout().id` after `setLayout()` runs. The lesson: always check component APIs against the source, not assumed patterns.

### 2. Shadow DOM isolates stylesheets completely

`<link rel="stylesheet">` added to `document.head` does not cross shadow boundaries. Any CSS needed inside a shadow root must either be:
- Inlined in a `<style>` tag inside the shadow root, OR
- Fetched as text and injected as `<style textContent="...">` into the shadow root

This bit us with `PageLayoutRenderer` — its CSS was added to `document.head` and had zero effect inside `ved-file-viewer`'s shadow root.

### 3. Two vault key systems exist and are incompatible

`sg-vault-client`'s `parseVaultKey` expects `passphrase:vaultId`. The `sg-send-crypto` / `sg-vault-init` system uses `word-word-NNNN` where the vault ID is SHA-256 derived. These are entirely different derivation chains and produce different vault IDs even if you tried to map one to the other.

The form now handles both, but any tool that accepts vault credentials needs to be explicit about which system it supports. A shared `parseAnyVaultKey(input)` utility in `sg-vault-client` would prevent this being re-implemented in every tool.

### 4. The loading flash is a shadow DOM timing issue

`connectedCallback` fires before `setLayoutState` arrives from `sg-layout`. Any message shown in `connectedCallback` will flash briefly before the real content loads. Fix: `connectedCallback` should only inject the `<style>` — not any visible content — for elements that are always instantiated with state.

### 5. Presigned URL path format was wrong on first attempt

Initial implementation guessed the presigned URL format as `/api/vault/presigned/{vaultId}/{path}`. The actual path confirmed by the API team is `/api/vault/presigned/read-url/{vaultId}/{encodedPath}`. The response key is `url` (with `presigned_url` as a fallback alias). The S3 response is still encrypted (not plaintext). Document this in any API reference — it's non-obvious that a "presigned" download still needs local decryption.

## Open Gaps

### A. PDF rendering untested end-to-end

The presigned URL fix was committed but PDF rendering via `<iframe src={blobUrl}>` has not been confirmed working from a user screenshot. PDFs above the API gateway limit need the presigned path; PDFs below it use direct API. The blob URL approach is standard and should work, but it hasn't been verified in this session.

### B. _page.json "x" button mystery

When rendering `_page.json` via `PageLayoutRenderer`, an "x" button sometimes appears in the rendered output. This likely comes from the renderer instantiating modal/navigation controls that expect a `browseStub` or similar context. The current call is `renderer.render(pageWrap, json, '', null, null)` — the nulls suppress context but may not suppress all UI chrome. Needs investigation against the PageLayoutRenderer source.

### C. No error boundary for _page.json CSS fetch

`_injectPageRendererCSS` silently swallows errors on the CSS fetch. If the CSS URL is wrong (e.g. a different endpoint running a different version), the page renders unstyled with no indication why. Should at minimum log a warning to the console.

### D. Simple token detection is pattern-only

`SIMPLE_TOKEN_RE = /^[a-z]+-[a-z]+-\d{4}$/` assumes exactly two words and a 4-digit suffix. The `sg-key-generator` supports configurable `word-count` and `suffix-length` — so a 3-word or 6-digit token would fall through to `parseVaultKey` and fail. A more robust check: attempt simple token derivation if there's no colon, regardless of word count.

### E. No empty-vault state

If a vault has no files (or only `.vault-settings`), the vault tree renders empty. There's no "this vault is empty" message — the tree panel just stays blank. A simple check after `openVaultTree()` that shows a message when `entries.length === 0` would improve the UX.

### F. History does not persist read key securely

Vault history stores the read key in localStorage in base64url form. This is the same read key used to decrypt vault content. Anyone with access to the browser's localStorage can read it. This is acceptable for a demo tool but should be flagged in any production version — at minimum the key should be session-only (sessionStorage) or re-derived from the passphrase on each load.

### G. Switch Vault button position

The "Switch Vault" button appears below the credentials list inside the credentials panel. On small screens or when the credentials panel is collapsed to a small height, this button may not be visible. It should probably be in the panel header or the tab strip, not the scrollable body.

## What Would Make This Production-Ready

1. **Replace manual PBKDF2 chain** in `deriveSimpleTokenKeys` with an import from a shared module (e.g. a new `sg-vault-client` export `deriveReadKeysFromSimpleToken`).
2. **Add `parseAnyVaultKey`** to `sg-vault-client` that handles both formats transparently.
3. **Session-only key storage** — don't persist read keys in localStorage between sessions.
4. **File size display** — decrypt `size_enc` from the tree entry before displaying in the loading card, so users see actual file size before download.
5. **Progress for large files** — the presigned S3 fetch has no progress indication. A streaming download with `ReadableStream` and a progress bar would be a meaningful UX improvement for files over 10MB.
6. **Renderer plugin system** — the MIME dispatch in `_render()` is an inline if-else chain. Extracting each renderer into a plugin (`{ canRender(mime), render(shadow, bytes, entry) }`) would make it easy to add new types without touching the core viewer.
