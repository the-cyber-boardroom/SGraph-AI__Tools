# Debrief: sg-send-cli Running in the Browser via Pyodide

**Date:** 2026-03-16
**Version:** v0.1.2
**Status:** Working — full read/write round-trip between browser and native CLI confirmed

---

## What We Built

A fully functional **browser-based terminal** that runs the real `sg-send-cli` Python package inside the browser using **Pyodide** (CPython compiled to WebAssembly). Users can clone, modify, commit, push, and pull SGraph vaults entirely from a web page — with full interoperability with the native `sg-send-cli` running on macOS/Linux.

## Architecture: How It Works

### Layer Stack

```
┌─────────────────────────────────────────────┐
│  Browser Tab                                │
│  ┌───────────────────────────────────────┐  │
│  │  Terminal UI (xterm.js)               │  │
│  │  - Input parsing, ANSI rendering      │  │
│  │  - Tab management (multiple sessions) │  │
│  └──────────────┬────────────────────────┘  │
│                 │ command string            │
│  ┌──────────────▼────────────────────────┐  │
│  │  SG_Send_CLI_Browser (Python/Pyodide) │  │
│  │  - Command routing (clone/push/pull)  │  │
│  │  - Virtual filesystem (memfs + /tmp)  │  │
│  │  - Vault__Crypto for encryption       │  │
│  │  - Vault__Sync for merge/commit logic │  │
│  └──────────────┬────────────────────────┘  │
│                 │ HTTP calls                │
│  ┌──────────────▼────────────────────────┐  │
│  │  XHR Transport Layer (monkey-patch)   │  │
│  │  - Replaces urllib.request.urlopen    │  │
│  │  - Uses synchronous XMLHttpRequest    │  │
│  │  - Handles JSON + binary responses    │  │
│  └──────────────┬────────────────────────┘  │
│                 │ HTTPS                     │
└─────────────────┼───────────────────────────┘
                  │
    ┌─────────────▼─────────────────┐
    │  dev.send.sgraph.ai (API)     │
    │  - Vault storage backend      │
    │  - Object store (blobs/trees) │
    │  - Branch/ref management      │
    └───────────────────────────────┘
```

### Key Technical Challenges Solved

#### 1. Running CPython in the Browser (Pyodide)

**Problem:** `sg-send-cli` is a Python package with dependencies (`osbot_utils`, `cryptography`, etc.) that normally runs on CPython with OS-level access.

**Solution:** Pyodide compiles CPython 3.11 to WebAssembly. We load the `sg_send_cli` wheel and its dependencies via `micropip.install()` at startup. The Python interpreter runs entirely in the browser — no server-side Python needed.

#### 2. No Filesystem (memfs)

**Problem:** `sg-send-cli` uses the local filesystem heavily — `.sg_vault/` directory, config files, blob storage, working copy files.

**Solution:** Pyodide provides an in-memory filesystem mounted at `/tmp`. The CLI operates within `/tmp/sg_cli_*/` directories. Each tab gets its own working directory. Files exist only in browser memory (lost on page refresh), but remote vaults persist on the server.

#### 3. No Socket/SSL Layer (XHR Monkey-Patch)

**Problem:** Pyodide has no socket implementation. `urllib.request.urlopen()` fails on `https://` URLs with `unknown url type: https`. This blocked all remote operations (clone, push, pull).

**Solution:** We monkey-patch `Vault__API._request()` and `Vault__API._request_bytes()` to use JavaScript's `XMLHttpRequest` in synchronous mode via Pyodide's JS bridge:

```python
from js import XMLHttpRequest

xhr = XMLHttpRequest.new()
xhr.open(method, url, False)  # synchronous
xhr.setRequestHeader(key, value)
xhr.send(data)
```

- **JSON responses:** `xhr.responseText` parsed with `json.loads()`
- **Binary responses:** `xhr.overrideMimeType('text/plain; charset=x-user-defined')` prevents text encoding corruption, then `bytes(ord(c) & 0xFF for c in text)` converts to Python bytes
- **Sending binary data:** `pyodide.ffi.to_js(data)` converts Python bytes to a JS-compatible type for `xhr.send()`

#### 4. Missing Python Packages

**Problem:** Several imports failed because Pyodide doesn't bundle every stdlib/third-party module. Key missing pieces included `dotenv`, `requests`, `paramiko`, and others.

**Solution:** Created `SG_Send_CLI_Browser`, a browser-specific subclass that:
- Stubs out unavailable imports (`dotenv`, `paramiko`, SSH-related modules)
- Only imports the subset of `sg_send_cli` that's relevant (crypto, sync, API)
- Provides mock implementations where needed
- Uses `micropip` to install compatible wheels at load time

#### 5. Terminal UI

**Problem:** Need a convincing terminal experience in the browser — command history, cursor movement, colored output.

**Solution:** xterm.js provides a full terminal emulator. The integration layer:
- Captures keystrokes and builds command strings
- Routes commands to the Python CLI via `pyodide.runPython()`
- Renders output with ANSI color codes
- Supports Up/Down arrow for command history
- Supports multiple tabs (independent vault sessions)

## Significance

This is **the first time sg-send-cli runs in a browser**. The implications:

1. **Zero-install access** — Users can interact with SGraph vaults from any browser, no Python installation required.
2. **Cross-platform parity** — The same vault operations work identically whether invoked from macOS terminal (native CPython) or from a browser tab (Pyodide/WASM).
3. **Full interop** — Changes made in the browser are visible to native CLI users (and vice versa). The screenshots prove a complete browser-push → native-pull cycle.
4. **Client-side only** — All cryptographic operations (AES-256-GCM encryption/decryption) happen in the browser. No plaintext data leaves the client. The server only stores encrypted blobs.
5. **Embeddable** — This terminal can be embedded in tools.sgraph.ai, documentation sites, or any web application that needs vault access.
