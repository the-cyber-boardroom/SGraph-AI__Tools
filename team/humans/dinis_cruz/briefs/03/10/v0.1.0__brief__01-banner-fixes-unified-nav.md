## Fix 1: "English" Link Visible on English Pages (BLOCKING BUG)

### What's wrong

On English locale pages (`/en-gb/`, `/en-us/`), the locale picker shows an "English" text link to the left of the `🇬🇧 EN-GB ▾` dropdown button. This link should be hidden on English pages — it only makes sense as a quick-switch shortcut for non-English users.

### Root cause

In `sg-locale-picker.css`, the class rule:
```css
.locale-picker__english-switch {
    display: inline-flex;
    ...
}
```
overrides the `hidden` HTML attribute on the `<a>` element. In Shadow DOM, component CSS has higher specificity than the browser's user-agent stylesheet (`[hidden] { display: none }`).

### Fix

Add one rule to `sg-locale-picker.css`:

```css
.locale-picker__english-switch[hidden] {
    display: none;
}
```

This is the correct Shadow DOM pattern for respecting `hidden` when component CSS defines a `display` value.

### Correct behaviour after fix

| Page locale | "English" link visible? |
|---|---|
| `en-gb`, `en-us`, any `en-*` | Hidden ✅ |
| `de-de`, `fr-fr`, any non-English | Visible ✅ (quick-switch to English) |

The existing JS in `sg-locale-picker.js` already sets `hidden` correctly in `_renderEnglishSwitch()` — the fix is CSS-only.

### Files to change

- `components/locale-picker/v1/v1.0/v1.0.0/sg-locale-picker.css` — add the `[hidden]` rule

This is a **patch** to v1.0.0 (bug fix, not a feature change). Update the version to `v1.0.1` and document the fix in the file header comment.

## Fix 2: Nav Must Include Cross-Site Links with Environment Awareness

### What nav should look like on tools.sgraph.ai

```
SG/Tools   Product   Pricing   Architecture   Team   All Tools          🇬🇧 EN-GB ▾
```

- **Product, Pricing, Architecture, Team** — cross-site links to `sgraph.ai`
- **All Tools** — in-site link to the tools landing page
- Order: cross-site links first, then in-site link last

### Why cross-site links first

This follows the brand decision: tools.sgraph.ai is part of the SG/Send family, not a standalone product. A user arriving from Google should be able to navigate to Pricing or Product as easily as if they were on sgraph.ai. The nav visually communicates "you are still in SG/Send."

### The cross-site link URLs

The cross-site links must be **environment-aware**. The tools dev environment links to the sgraph dev environment, not production.

| Current hostname | Product link goes to |
|---|---|
| `dev.tools.sgraph.ai` | `https://dev.sgraph.ai/{locale}/product/` |
| `main.tools.sgraph.ai` | `https://main.sgraph.ai/{locale}/product/` |
| `tools.sgraph.ai` | `https://sgraph.ai/{locale}/product/` |

Same pattern for Pricing, Architecture, Team.

### Implementation: environment detection helper

Add a utility function to the tools site (a small JS module or inline in the page template) that resolves the sgraph.ai base URL from the current hostname:

```js
/**
 * Returns the sgraph.ai base URL that corresponds to the current environment.
 * Keeps dev ↔ dev, main ↔ main, prod ↔ prod cross-linked.
 */
function getSgraphBaseUrl() {
    const host = window.location.hostname
    if (host.startsWith('dev.'))  return 'https://dev.sgraph.ai'
    if (host.startsWith('main.')) return 'https://main.sgraph.ai'
    return 'https://sgraph.ai'   // production + localhost fallback
}
```

### Implementation: locale-aware cross-site links

Cross-site links must include the current locale, so a user on `/de-de/ssh-keygen/` who clicks "Pricing" lands on `https://dev.sgraph.ai/de-de/pricing/` — not the default English page.

The locale is available from the URL path. The `sg-locale-picker` component already detects it via `_detectLocale()`. This detection logic should be accessible to nav construction.

### Nav items for tools landing page (`en-gb/index.html`)

The `nav-items` JSON passed to `<sg-site-header>` should be constructed dynamically, not hardcoded — because the sgraph base URL and the locale are only known at runtime.

**Option A: Inline script (simplest, works today)**

```html
<script type="module">
import { SgLocalePicker, SG_LOCALES } from '/components/locale-picker/v1/v1.0/v1.0.1/sg-locale-picker.js'

function getSgraphBase() {
    const h = window.location.hostname
    if (h.startsWith('dev.'))  return 'https://dev.sgraph.ai'
    if (h.startsWith('main.')) return 'https://main.sgraph.ai'
    return 'https://sgraph.ai'
}

function detectLocale() {
    const path = window.location.pathname
    const codes = SG_LOCALES.map(l => l.code)
    const match = path.match(new RegExp('/(' + codes.join('|') + ')(?=/|$)'))
    return match ? match[1] : 'en-gb'
}

const base   = getSgraphBase()
const locale = detectLocale()

document.querySelector('sg-site-header').setAttribute('nav-items', JSON.stringify([
    { label: 'Product',      href: `${base}/${locale}/product/` },
    { label: 'Pricing',      href: `${base}/${locale}/pricing/` },
    { label: 'Architecture', href: `${base}/${locale}/architecture/` },
    { label: 'Team',         href: `${base}/${locale}/agents/` },
    { label: 'All Tools',    href: window.location.origin + '/en-gb/' }
]))
</script>
```

**Option B: Extract to `_common/js/sg-nav.js` (recommended for maintainability)**

Create a shared module that all tools pages import. It exports `buildToolsNav(header)` which sets the nav-items on the passed header element. This avoids duplicating the logic in every page.

The Architect should decide which option ships in v0.1.2. Option A is faster; Option B is cleaner. Either is acceptable for this version.
