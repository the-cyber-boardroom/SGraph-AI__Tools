## What Is PlaybookLM

A NotebookLM competitor built on SGraph. Takes source documents, extracts a presentation document (the "essence" that NotebookLM keeps hidden), decomposes into per-slide briefs, generates infographics for each slide, and exports everything — sources, briefs, prompts, logs, costs, images, assembled deck — into a vault or downloadable pack.

The key differentiator: **you get everything, not just the final slides.**

## The Pipeline Architecture

PlaybookLM has 5 pipeline steps. Each step has inputs, an LLM call (or user action), and outputs that feed the next step. The entire pipeline state is held in a single `PipelineState` object.

### Pipeline State Object

```javascript
const state = {
    // Step 1: Sources
    sources: [
        { name: 'report.pdf', type: 'application/pdf', content: '...', role: 'content' },
        { name: 'brand-guide.pdf', type: 'application/pdf', content: '...', role: 'branding' },
    ],

    // Step 2: Presentation document
    presentationDoc: null,  // string (markdown) — the "essence"

    // Step 3: Per-slide briefs
    slideBriefs: [
        { index: 0, title: 'Executive Summary', template: 'executive', prompt: '...', status: 'ready' },
        { index: 1, title: 'Current Challenges', template: 'stats', prompt: '...', status: 'ready' },
        // ...
    ],

    // Step 4: Generated infographics
    slideResults: [
        {
            index: 0,
            generations: [
                { generationId: 'gen-...', model: '...', duration: 13.2, imageSrc: 'data:...', cost: 0.07 },
                // multiple variants possible per slide
            ],
            selectedGeneration: 0,  // which variant is "active"
        },
    ],

    // Step 5: Export
    exportOptions: { pdf: true, pngs: true, sourcePack: true, vaultPage: true },

    // Meta
    apiKey: null,
    model: 'google/gemini-3.1-flash-image-preview',
    systemPrompt: '...',   // from branding source or default
    connected: false,
};
```

### Step 1 → Step 2: Source Extraction

**Input:** Array of source documents (text, PDF, markdown, images).

**LLM Call:** Send all source content to the LLM with a meta-prompt that asks it to extract the narrative, key points, structure, and recommended slide count. The branding source (if present) is separated and becomes the system prompt layer.

```javascript
// Prompt for Step 2
const step2Prompt = `You are an expert presentation strategist.

Given the following source documents, create a PRESENTATION DOCUMENT that:
1. Identifies the core narrative and key messages
2. Structures the content into a logical flow
3. Recommends ${numSlides} slides with titles
4. Extracts key data points, statistics, and quotes
5. Identifies the target audience and tone

Return as structured markdown with sections:
## Narrative
## Key Messages  
## Recommended Slides
## Data Points
## Audience & Tone

SOURCE DOCUMENTS:
${sourceContents}`;
```

**Output:** `state.presentationDoc` — a markdown document (the "essence").

**Model for this step:** A text model (Claude, GPT, Gemini text) — NOT an image model. This is a text extraction/analysis task. Use `sg-llm-request` with a text-only model.

### Step 2 → Step 3: Brief Decomposition

**Input:** The presentation document from Step 2.

**LLM Call:** Send the presentation document to the LLM and ask it to decompose into N individual slide briefs. Each brief includes: title, recommended template, and a detailed prompt for the infographic generator.

```javascript
// Prompt for Step 3
const step3Prompt = `You are an expert infographic prompt writer.

Given this PRESENTATION DOCUMENT, create ${numSlides} individual SLIDE BRIEFS.
Each brief must be a self-contained prompt for an AI infographic generator.

For each slide, return a JSON array:
[
  {
    "title": "...",
    "template": "executive|architecture|timeline|comparison|process|stats|mindmap",
    "prompt": "A detailed 100-200 word prompt describing exactly what the infographic should show..."
  }
]

The prompts should:
- Start with the template type and title
- Include specific data points from the source
- Name visual elements: boxes, arrows, layers, icons
- Maintain visual consistency across all slides
- Reference the overall narrative for context

PRESENTATION DOCUMENT:
${presentationDoc}`;
```

**Output:** `state.slideBriefs[]` — parsed JSON array of slide objects.

**Model for this step:** Same text model as Step 2. Return format should be JSON (use structured output if available).

### Step 3 → Step 4: Infographic Generation

**Input:** Each slide brief's `prompt` and `template` fields.

**Execution:** For each slide brief, call the infographic generator. This is where we reuse the existing infographic generation infrastructure.

**Two approaches (Architect to decide):**

**Option A — Embedded generation (recommended for MVP):**
PlaybookLM creates its own `sg-llm-request` instances and generates infographics directly, using the same OpenRouter flow the infographic generator uses. The system prompt is composed from three layers:

```
Layer 1 (System): Default infographic style prompt + branding from source docs
Layer 2 (Positioning): The presentation document ("essence") — same for all slides
Layer 3 (Slide): The individual slide brief's prompt
```

The three-layer prompt is concatenated and sent as a single request via `sg-llm-request` to an image-capable model.

**Option B — Cross-tool API call:**
PlaybookLM programmatically calls the infographic generator's `window.__tool.generate()` on a separate page/iframe. This reuses the infographic gen entirely but adds complexity (managing a second page).

**Recommendation: Option A.** The infographic generator's generation logic is simple — it's just an `sg-llm-request` call with an image model. There's no need to load a second tool. The complexity is in the pipeline orchestration, not the generation.

**Output:** `state.slideResults[]` with `generationId`, `imageSrc`, `model`, `duration` per slide.

**Events fired:** `tool:slide:generating`, `tool:slide:complete`, `tool:slide:error` per slide, plus `tool:deck:complete` when all slides are done.

### Step 4 → Step 5: Assembly & Export

**PDF Assembly:** Use `canvas` or a PDF library to combine slide PNGs into a full-bleed PDF. This happens in-browser using something like `jsPDF` or by using the existing `sg-infographic-export` patterns.

**Vault Export:** Package everything into a vault structure:

```
playbooklm-output/
  sources/              ← original source documents
  presentation.md       ← the "essence" document
  briefs/
    slide-01-brief.md   ← per-slide brief
    slide-02-brief.md
    ...
  slides/
    slide-01.png         ← generated infographics
    slide-02.png
    ...
  deck.pdf              ← assembled slide deck
  generation-log.json   ← all generation IDs, models, durations, costs
  _page.json            ← vault page layout (browsable via SG/Send)
```

## JS API Specification

PlaybookLM registers on `window.__tool` via SgToolApi, following the JavaScript API Primitive pattern.

### Methods

| Method | Type | Description |
|--------|------|-------------|
| `connect({ apiKey, model? })` | async | Connect to OpenRouter |
| `loadSources(files[])` | async | Load source documents into pipeline |
| `getSources()` | sync | Return current sources array |
| `removeSource(index)` | sync | Remove a source by index |
| `generatePresentation({ model? })` | async | Step 2: extract the "essence" from sources |
| `getPresentation()` | sync | Return the presentation document text |
| `setPresentation(text)` | sync | Edit the presentation document |
| `generateSlideBriefs({ count?, model? })` | async | Step 3: decompose into per-slide briefs |
| `getSlideBriefs()` | sync | Return slide briefs array |
| `setSlideBrief(index, brief)` | sync | Edit a single slide brief |
| `addSlideBrief(brief)` | sync | Add a new slide brief |
| `removeSlideBrief(index)` | sync | Remove a slide brief |
| `generateSlide(index, { model?, template? })` | async | Step 4: generate infographic for one slide |
| `generateAllSlides({ model?, parallel? })` | async | Step 4: generate all slides (sequential or parallel) |
| `getSlideResults()` | sync | Return all generation results |
| `exportDeck({ format?, includeSource? })` | async | Step 5: assemble and export |
| `getState()` | sync | Full pipeline state snapshot |
| `getPipelineStatus()` | sync | Which steps are complete/pending |
| `stop()` | sync | Cancel all active generations |

### Events

| Event | When | Detail |
|-------|------|--------|
| `tool:ready` | Page load | `{ instanceId, version }` |
| `tool:connected` | OpenRouter connected | `{ model, provider }` |
| `tool:sources:loaded` | Sources added | `{ count, totalSize }` |
| `tool:presentation:complete` | Step 2 done | `{ length, slideCount }` |
| `tool:briefs:complete` | Step 3 done | `{ count, titles[] }` |
| `tool:slide:generating` | Slide generation started | `{ index, model, prompt }` |
| `tool:slide:complete` | One slide done | `{ index, generationId, duration, imageSrc }` |
| `tool:slide:error` | Slide generation failed | `{ index, error }` |
| `tool:deck:complete` | All slides done | `{ count, totalDuration, totalCost }` |
| `tool:export:complete` | Export done | `{ format, size }` |

## Three-Layer Prompt Architecture

For consistent infographic generation across a deck, every generation call composes three prompt layers:

```
┌──────────────────────────────────────────────────────┐
│ SYSTEM PROMPT (same for all slides in a deck)         │
│ Default: "You are a professional infographic designer │
│   ...dark navy background, teal accents..."           │
│ + Branding overrides from brand guide source doc      │
│ + Template selection from slide brief                  │
└──────────────────────────────────────────────────────┘
                        │
┌──────────────────────────────────────────────────────┐
│ POSITIONING PROMPT (same for all slides)              │
│ The presentation document ("essence")                 │
│ "This is slide N of M in a deck about..."             │
│ Overall narrative context, audience, purpose           │
└──────────────────────────────────────────────────────┘
                        │
┌──────────────────────────────────────────────────────┐
│ SLIDE PROMPT (unique per slide)                       │
│ The specific slide brief's prompt text                │
│ What to visualise, what data to include               │
└──────────────────────────────────────────────────────┘
```

In practice, this is sent to `sg-llm-request` as:
- **System message:** Layer 1 (system prompt + branding)
- **User message:** Layer 2 (positioning) + Layer 3 (slide prompt), concatenated

This ensures visual and narrative consistency across all slides while each slide has unique content.

## Open Questions for the Architect

1. **Text model for Steps 2-3:** Which model for the presentation extraction and brief decomposition? Claude Sonnet would produce excellent briefs but costs more. Gemini Flash is cheaper but may produce less structured output. Recommendation: make it configurable, default to a good text model.

2. **File reading:** PDF parsing in-browser is non-trivial. Options: (a) use `pdf.js` to extract text client-side, (b) send the PDF as a base64 image to a multimodal model and ask it to read it, (c) accept text/markdown only for MVP. Recommendation: (c) for MVP, with (b) as a fast follow.

3. **Parallel slide generation:** Should `generateAllSlides()` fire all slides in parallel via `Promise.all()` or sequential? Parallel is faster but may hit rate limits. Recommendation: configurable with `{ parallel: true|false }`, default sequential for MVP.

4. **In-browser PDF assembly:** `jsPDF` can create PDFs from images client-side. Alternative: just download individual PNGs and let the user assemble. Recommendation: include `jsPDF` for the MVP — a single-click "Download PDF Deck" is a core UX requirement.

5. **Vault export:** Should the tool directly call `sgit` (requires the CLI)? Or create a downloadable zip that the user can manually push? Recommendation: create a structured zip/folder for MVP. Vault integration is Phase 2 — it requires server-side sgit.
