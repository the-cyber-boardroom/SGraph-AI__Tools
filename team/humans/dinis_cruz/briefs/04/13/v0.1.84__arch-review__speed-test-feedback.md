## Summary

The dev session delivered solid core modules (`sg-send-upload` v1.1.0, `sg-send-download` v1.0.0) and a working speed-test UI. The core modules are well-designed, follow the project patterns, and have good test coverage. The speed-test tool, however, has three categories of issues:

1. **It doesn't use the modules it shipped alongside.** Zero imports. Reinvents speed tracking, crypto, and measurement logic that already exist.
2. **It targets server endpoints that don't exist.** The UI calls `/api/speed-test/download?size=N` and `/api/speed-test/upload` — neither endpoint exists on `send.sgraph.ai`. Confirmed by 404 errors in production.
3. **It doesn't follow the current tool architecture pattern.** No `sg-layout`, no `SgToolApi`, no bottom developer panel, no SKILL files for browser/API audiences.

The core modules are a **pass**. The speed-test tool needs a v2 that composes the ecosystem properly.

## 2. Bug: `crypto.getRandomValues()` Exceeds 65,536-Byte Limit

**Severity:** Crash — upload test is completely broken.

The upload measurement function calls:

```javascript
const payload = crypto.getRandomValues(new Uint8Array(sizeBytes));
```

Where `sizeBytes` defaults to `2 * 1024 * 1024` (2 MB = 2,097,152 bytes).

The Web Crypto API spec limits `getRandomValues()` to **65,536 bytes** per invocation. The browser throws:

> `Failed to execute 'getRandomValues' on 'Crypto': The ArrayBufferView's byte length (2097152) exceeds the number of bytes of entropy available via this API (65536).`

This is visible in the screenshot — the upload card shows this exact error.

**Fix:** Fill in a loop:

```javascript
const payload = new Uint8Array(sizeBytes);
for (let offset = 0; offset < sizeBytes; offset += 65536) {
    const chunk = Math.min(65536, sizeBytes - offset);
    crypto.getRandomValues(payload.subarray(offset, offset + chunk));
}
```

Note that `sg-send-crypto.js` in this same repo already handles this correctly. The speed-test should import from existing modules rather than reimplementing crypto primitives.

## 3. Bug: Server Endpoints Do Not Exist

The tool constructs URLs:

const dlUrl = `${base}/api/speed-test/download?size=${probeBytes}`;

The speed-test tool was committed in the **same commit** as `sg-send-upload` v1.1.0 and `sg-send-download` v1.0.0. Yet `speed-test.js` contains **zero `import` statements**. It reimplements:

| Concept | Exists in | Reimplemented in speed-test.js |
|---|---|---|
| Speed tracking (rolling window) | `sg-send-upload` v1.1.0 `SpeedTracker` | Local `SpeedTracker` class (lines 41–50) |
| `formatSpeed(bps)` | `sg-send-upload` v1.1.0 | Duplicate `formatSpeed()` (lines 67–72) |
| Chunked upload with progress | `ChunkedUploader` class | Manual `fetch()` loop with 256KB slices |
| Chunked download with progress | `ChunkedDownloader` class | Manual streaming `reader.read()` loop |
| Random payload generation | `sg-send-crypto.js` | Broken `crypto.getRandomValues()` call |

The speed-test tool should be a **thin UI that composes existing core modules**, not a parallel implementation.

## 6. Missing Capability: Offline/Simulated Mode Using sg-send-sim

The tool assumes a live server is always available. When the server endpoints don't exist (as is the case now), the tool is completely non-functional.

**We already have `sg-send-sim`** — a VFS-backed simulation of the SG/Send API that derives vault keys identically to the real server, stores encrypted objects in the VFS, and mirrors the full commit cycle. It was designed precisely for this: running SG/Send operations without a server.

The speed-test should have (at minimum) two modes:

| Mode | How it works | What it measures |
|---|---|---|
| **Local (sim)** | Uses `sg-send-sim` + VFS to simulate encrypt → upload → download → decrypt | Client-side throughput: encryption speed, decryption speed, memory bandwidth. Works offline, no server needed. |
| **Server (live)** | Uses `ChunkedUploader` + `ChunkedDownloader` against a real SG/Send endpoint | Real network throughput including latency, server processing, TLS overhead. |

This is also what the brief means by "independently testable" — the components should work without a live server.

## 7. Design Direction: Three Modes (from the brief)

The original brief (`v0.17.3`) describes three audiences for the speed test:

> 1. A **diagnostic** tool ("is my connection fast enough for this file?")
> 2. A **marketing** tool ("people share speed test results")
> 3. A **baseline measurement** for QA and monitoring systems

These map to three UI modes:

### Mode 1: Simple Diagnostic

For regular users. Show:
- A large speedometer-style gauge (download speed)
- A simple verdict: "Your connection can transfer a 500 MB file in ~3 minutes"
- A "Share" button producing a clean, copy-pasteable result

This is the mode visible at first load. Minimal UI. One button.

### Mode 2: Detailed Transfer View

For power users and the upload UX flow. Show:
- Per-chunk progress (from `ChunkedUploader`/`ChunkedDownloader`)
- Thread count (configurable, from `maxConcurrent` option)
- Rolling speed graph over time
- Encryption/decryption throughput (separate from network)
- Resume state indicator

This is what the brief's "Upload Visibility" section describes: "During upload, show maximum information."

### Mode 3: QA/Developer Dashboard

Uses `sg-layout` with multiple panels:
- Speed-test controls (top)
- Raw measurement data table (right)
- Request/response inspector (bottom-left)  
- SgToolApi explorer (bottom-right)
- History of test runs with statistical comparison

This mode uses the bottom developer panel pattern and `SgToolApi` registration.
