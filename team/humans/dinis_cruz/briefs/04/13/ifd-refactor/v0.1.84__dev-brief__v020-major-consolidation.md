## Objective

Create `tools/v0/v0.2/v0.2.0/` as the first major version consolidation of the v0.1.x IFD stack. The v0.1.x family has reached 39 minor versions (v0.1.0 → v0.1.38) and is overdue for consolidation per the IFD methodology.

**This is a copy-and-fix operation, not a rewrite.** The goal is to produce v0.2.0 with minimum code changes.

---

## Critical Rule: Minimum Code Changes

The v0.1.x → v0.2.0 transition must NOT be a major breaking event. The approach is:

1. **Copy** the flattened tools content + `core/` + `components/` into `tools/v0/v0.2/v0.2.0/`
2. **Fix** only the known structural issues (listed below)
3. **Create NEW deploy scripts** alongside the existing v0.1.x ones
4. **Verify** the new build and local server work
5. **Do NOT modify** any v0.1.x scripts or folders — they stay frozen for rollback
6. **Do NOT refactor, redesign, or improve** any tool's functionality

Any improvements happen later as v0.2.1, v0.2.2, etc. — separate surgical overlays on top of the clean v0.2.0 base.

---

## Key Principle: v0.2.0 Is 100% Self-Contained

v0.2.0 must have **zero dependencies on v0.1.x code**. This means the v0.2.0 folder (after the build step) must include everything the site needs to run:

| Content | Source | Included in v0.2.0? |
|---------|--------|---------------------|
| Tools (26 flattened tools) | `tools/v0/v0.1/_latest/` (build output) | ✅ Yes — copied |
| `_common/` (CSS, JS, favicon) | `tools/v0/v0.1/_latest/_common/` | ✅ Yes — copied |
| `core/` (63 JS modules) | `sgraph_ai_tools__static/core/` | ✅ Yes — copied |
| `components/` (178 JS/CSS files) | `sgraph_ai_tools__static/components/` | ✅ Yes — copied |
| `tests/` (38 test files) | `sgraph_ai_tools__static/tests/` | ✅ Yes — copied |
| Root files (404, robots, sitemap) | `tools/v0/v0.1/_latest/` | ✅ Yes — copied |

The tools import `core/` and `components/` via absolute paths like `/core/sg-layout/v0.1.0/sg-layout.js` and `/components/llm/sg-llm-request/v0/v0.1/v0.1.2/sg-llm-request.js`. Without including these, v0.2.0 cannot deploy independently.

This also means we can **freeze v0.1.x completely** — no further changes to that family. If anything goes wrong with v0.2.x, we revert to the v0.1.x deploy scripts and everything works as before.

---

## Key Principle: New Deploy Scripts (Don't Modify Existing)

Create an `scripts/ifd-releases/` folder structure that holds per-major-version release scripts. This future-proofs the pattern — v0.3.0 is just "copy the v0.2 folder, change the config."

```
scripts/ifd-releases/
  README.md                          ← explains the pattern, how to create v0.3/
  v0.2/
    config.sh                        ← IFD_BASE, version glob, source dirs
    build-latest.sh                  ← builds _latest for v0.2.x (tools + core + components)
    run-locally.sh                   ← local dev server for v0.2.x
.github/workflows/
  deploy-tools__dev.yml              ← v0.1.x (DO NOT MODIFY)
  deploy-tools-v02__dev.yml          ← v0.2.x (NEW — calls scripts/ifd-releases/v0.2/build-latest.sh)
```

The v0.1.x scripts (`scripts/run-locally.sh`, `scripts/build_ifd_latest.py`, `.github/workflows/deploy-tools__dev.yml`) are left **untouched**. We must always be in a position to revert to v0.1.x.

When v0.3.0 comes, the process is:
1. `cp -r scripts/ifd-releases/v0.2 scripts/ifd-releases/v0.3`
2. Edit `v0.3/config.sh` to point at `tools/v0/v0.3`
3. Copy the CI workflow and update its references

The `config.sh` for v0.2 looks like:

```bash
# scripts/ifd-releases/v0.2/config.sh
# IFD release configuration for v0.2.x
IFD_MAJOR="v0.2"
IFD_BASE="tools/v0/v0.2"
STATIC_DIR="sgraph_ai_tools__static"
PORT=10063
```

The `build-latest.sh` sources this config, calls the existing `build_ifd_latest.py` with `--ifd-base $IFD_BASE`, then copies `core/`, `components/`, and `tests/` into the `_latest/` output. The `run-locally.sh` sources the same config and serves the result.

## What Comes Next (v0.2.1+)

This section is context for the v0.2.0 session — **do not execute any of this now**. It explains the plan so the session understands why v0.2.0 deliberately leaves core/ and components/ unflattened.

### v0.2.1: Consolidate core/ and components/ overlay chains

v0.2.0 copies `core/` and `components/` as-is, preserving their internal IFD overlay chains. For example:

- `sg-tree`: v0.1.0 (base) → v0.1.1 (editor mode) → v0.1.2 (virtual scroll) → v0.1.3 (multi-select) → v0.1.4 (drag-and-drop) — 5 layers where each imports the previous
- `sg-tool-runner`: v0.1.0 (base) + v0.1.1 (overlay)
- `sg-llm-chat-history`: v0.1.0 through v0.1.10 — 11 versions
- `sg-llm-chat-input`: v0.1.0 through v0.1.5 — 6 versions

In v0.2.1, a dedicated pass would:

1. For each component/core module with overlay chains, **merge the surgical overrides into a single complete file** at a new version path (e.g. `v0/v0.2/v0.2.0/`)
2. **Update the import paths** in all tools that reference the old overlay chain endpoints
3. Verify the tools still work with the merged modules

This is the tricky part — every tool JS file that says `/components/agentic/sg-tool-runner/v0/v0.1/v0.1.1/sg-tool-runner.js` would need updating to the new merged path. But since v0.2.0 is already self-contained, it's a safe refactor: diff before/after and verify nothing breaks.

The sg-tree chain (5 layers, the most complex) gets its own focused consolidation instead of being mixed in with the tools work. One concern at a time.

### IFD Workflow Gap: core/ and components/ have no build/flatten step

Currently, the IFD tooling only covers the **tools layer**:

| Layer | Has IFD build script? | Has layering/flattening? | Has deploy automation? |
|-------|----------------------|--------------------------|----------------------|
| `tools/` | ✅ `build_ifd_latest.py` | ✅ Layers 39 versions → `_latest/` | ✅ CI workflow |
| `core/` | ❌ None | ❌ No flattening — overlay chains are resolved at runtime by the browser | ❌ Copied as-is to S3 |
| `components/` | ❌ None | ❌ Same — runtime resolution via import chains | ❌ Copied as-is to S3 |

The tools IFD workflow works well: each minor version is a delta, `build_ifd_latest.py` flattens them, and the result is a clean deployable site. But core/ and components/ rely on the browser resolving overlay chains at runtime (v0.1.1 imports v0.1.0 which imports...). This works but means:

- No single "what does this module look like today?" view
- No validation that overlay chains are intact before deploy
- No way to "flatten" a component family without manually merging

**From v0.2.x onwards, we should build equivalent IFD workflows for core/ and components/.** This could mean:
- A `build_component_latest.py` that merges a component's overlay chain into a single file
- A manifest per component family listing the chain order
- Integration into the release scripts so the v0.2.x build produces fully merged core/ and components/

This is future work — not v0.2.0 or even necessarily v0.2.1. But it's the direction.

## IFD Major Version Rules (Quick Reference)

From the IFD Versioning Guide:

- **v0.2.0 is completely self-contained.** No references to v0.1.x files. No dependencies on files outside the v0.2.0 folder.
- **All files are complete** (merged from surgical patches — already done by `_latest`).
- **core/ and components/ are included** — the full site runs from v0.2.0 alone.
- **No functional changes** during consolidation — what was tested IS what ships.
- **v0.2.1+ are surgical overlays** on v0.2.0 — the normal IFD minor version cycle restarts.
