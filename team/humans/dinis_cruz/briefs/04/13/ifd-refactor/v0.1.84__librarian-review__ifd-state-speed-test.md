# Librarian Review: IFD State of v0.1.x and Speed-Test Deployment

**Version:** v0.1.84 | **Date:** 13 April 2026
**Produced by:** Librarian (Tools) + Architect (Tools) — joint IFD review
**Scope:** The entire `tools/v0/v0.1/` overlay stack (39 versions) and the speed-test tool's integration into it

---

## Executive Summary

The v0.1.x IFD overlay stack has reached **39 minor versions** producing **26 tools** from **296 source files** that flatten into **104 deployed files**. The stack is well past the point where a major version consolidation (v0.2.0) is due. The speed-test tool (v0.1.38) integrates correctly into the IFD layering mechanism but has several integration gaps: missing from the tool registry, uses a non-existent category, ignores design tokens, and has an incorrect `_common` path depth.

---

## 1. IFD Layering — How It Works (Verified)

The deployment pipeline is sound and well-implemented:

```
39 version folders  →  build_ifd_latest.py  →  _latest/ (flattened)  →  S3 + CloudFront
     296 files              layer in order          104 files              tools.sgraph.ai
```

The `build_ifd_latest.py` script layers each version folder in ascending semver order. Later files overwrite earlier ones. The `run-locally.sh` script replicates this for local dev on `localhost:10063`. Both work correctly — verified by running the build and inspecting the output.

The CI pipeline (`deploy-tools__dev.yml`) then:
1. Runs `build_ifd_latest.py --up-to auto`
2. Generates i18n locale pages
3. Injects build version
4. Syncs to S3 with clean URLs
5. Invalidates CloudFront

**Verdict: The pipeline is correct. The speed-test's 4 files layer properly into `_latest/en-gb/speed-test/`.**

## 2. Speed-Test IFD Integration Issues

### 2a. Not Registered in TOOL_SLUGS

The landing page at `tools.sgraph.ai/en-gb/` is manifest-driven. It loads manifests for tools listed in `_common/js/sg-tool-registry.js` → `TOOL_SLUGS` array. The speed-test is **not in this array**.

```javascript
// Current TOOL_SLUGS — speed-test is absent
const TOOL_SLUGS = [
    'ssh-keygen', 'file-hasher', 'file-encryptor', 'key-generator',
    'chat', 'one-shot-chat', 'infographic-gen', /* ... */
    'vfs-dev', 'vfs-tree-demo', 'sg-tree-demo', 'send-sim', 'vault-pyodide',
];
```

**Impact:** The speed-test tool does not appear on the landing page. Users can only reach it by knowing the direct URL (`/en-gb/speed-test/`).

**Fix:** Add `'speed-test'` to `TOOL_SLUGS` in a new IFD version and update `_common/js/sg-tool-registry.js`. This also needs a new category (see below).

### 2b. Invalid Category: `"tools"`

The speed-test `manifest.json` declares `"category": "tools"`. The registry only recognises these categories:

| Category ID | Label |
|---|---|
| `security` | Security & Crypto |
| `llm` | AI / LLM |
| `media` | Media |
| `vault` | Vault & Send |
| `code` | Code & Runtime |
| `dev` | Developer Sandbox |

`"tools"` matches none of these. The `groupByCategory()` function would place it in the `dev` (Developer Sandbox) catch-all — wrong for a user-facing diagnostic tool.

**Options:**
1. Change the manifest to `"category": "vault"` (since it tests SG/Send infrastructure) — or —
2. Add a new category: `{ id: 'network', label: 'Network & Diagnostics', audience: 'user' }`

### 2c. Wrong `_common` Path Depth

```html
<!-- speed-test/index.html -->
<link rel="icon" href="../../../_common/favicon.svg">
<link rel="stylesheet" href="../../../_common/css/tools.css">
```

From `en-gb/speed-test/`, `../../../` resolves 3 levels up. The correct depth is 2 levels (`../../_common/`). This accidentally works because browsers normalise path traversal above the URL root — `/../_common/` becomes `/_common/`. But it's wrong.

**Comparison with other tools:**

| Tool | Path to `_common` | Correct? |
|---|---|---|
| infographic-gen (v0.1.34) | `../../_common/` | ✅ |
| chat (v0.1.22) | `../../../_common/` | ❌ (same bug) |
| speed-test (v0.1.38) | `../../../_common/` | ❌ |
| ssh-keygen (v0.1.0) | `/tools/v0/v0.1/v0.1.0/_common/` | ❌ (absolute, legacy) |

This is a pre-existing inconsistency — the speed-test copied the pattern from chat. Both should be `../../_common/`.

### 2d. Zero Design Token Usage

The shared `_common/css/tools.css` defines a complete design token system:

```css
:root {
    --sg-bg:          #0f0f23;
    --sg-bg-card:     #1a1a2e;
    --sg-border:      #1e293b;
    --sg-text:        #f0f0f5;
    --sg-accent:      #4ecdc4;    /* teal */
    --sg-font:        -apple-system, BlinkMacSystemFont, ...;
    --sg-radius:      6px;
    /* ... 14 tokens total */
}
```

The speed-test `<style>` block uses **zero** `var(--sg-*)` references. Instead, it hardcodes its own palette:

| Token | tools.css value | speed-test value | Match? |
|---|---|---|---|
| Background | `#0f0f23` | `#070b14` | ❌ Different |
| Card BG | `#1a1a2e` | `#0d1422` | ❌ Different |
| Border | `#1e293b` | `#1e2a40` | ❌ Close but different |
| Text | `#f0f0f5` | `#c8d0e0` | ❌ Different |
| Accent | `#4ecdc4` (teal) | `#3b82f6` (blue) | ❌ Different colour family |
| Font | system sans-serif | `'Inter', system-ui` | ❌ Different |

The speed-test has **172 CSS declarations** in its inline `<style>` tag — larger than the entire shared `tools.css` (152 lines). This is a self-contained visual island that doesn't respond to any future design token changes.

**Fix:** Refactor the speed-test CSS to use `var(--sg-*)` tokens for all colours, fonts, border radii, and spacing. Tool-specific declarations (meter cards, progress bars, share section) remain inline but inherit from the shared palette.

## 3. v0.1.x Overlay Stack Health

### 3a. Version Count: Consolidation Overdue

The IFD versioning guide states:

> **When to Create a New Major Version**: Minor versions have stabilised; too many surgical patches (loading order getting complex); features are proven and tested; clean slate needed.

At **39 minor versions**, the v0.1.x family is well past this threshold. For comparison:

| Metric | Current | Guideline |
|---|---|---|
| Minor versions | 39 | Consolidate after ~10–15 |
| Total source files | 296 | Grows linearly; flatten to reset |
| Flattened files | 104 | This is the real app |
| Most-overwritten file | `infographic-gen.js` (11 versions) | Merge into single clean file |

### 3b. Not Using Surgical Overrides (Tools Layer)

The IFD guide describes the surgical override pattern for minor versions:

```javascript
// Ideal: 15-line file that overrides one method
ClassName.prototype.methodName = function() { /* fixed */ };
```

**No tool in the entire v0.1.x stack uses this pattern.** Every minor version replaces complete files:

| Tool | Versions contributed | Pattern used |
|---|---|---|
| infographic-gen | 16 versions (v0.1.6–v0.1.37) | Full file replacement each time |
| chat | 7 versions | Full file replacement |
| openrouter | 3 versions | Full file replacement |
| speed-test | 1 version (new tool) | N/A — new files |

The surgical override pattern IS used in `core/sg-tree/` (v0.1.0 → v0.1.4 chain) and the component layer. But the tools layer treats each minor version as a complete file drop, not a surgical patch.

This isn't necessarily wrong — tools are compositions (HTML + JS orchestrators), not class hierarchies with overridable methods. But it means the IFD "delta" benefit is limited to not copying unchanged tools into each version. The build script still layers all 39 versions in order, overwriting files 11 times for infographic-gen.

### 3c. Redundant File Copies

Some IFD versions include files that are identical to the previous version (the dev session included them unnecessarily). This doesn't break anything — the build script just overwrites with the same content — but it inflates the version folder.

### 3d. `_common` Duplication

The `_common` folder was included in **7 different versions** (v0.1.0, v0.1.1, v0.1.2, v0.1.3, v0.1.4, v0.1.5, v0.1.12, v0.1.14, v0.1.22, v0.1.25, v0.1.26). Most of these are identical copies. The IFD pattern handles this correctly (later versions overwrite), but it's wasteful.

## 4. Recommendation: v0.2.0 Consolidation

### What v0.2.0 Should Contain

A merged, self-contained snapshot of the current flattened state:

```
tools/v0/v0.2/v0.2.0/
  _common/
    css/tools.css
    js/sg-tool-registry.js     ← updated with speed-test + voice-memo
    js/sg-tool-manifest.js
    js/sg-nav.js
    favicon.svg
  en-gb/
    index.html                 ← landing page
    speed-test/                ← merged, design-token-compliant
    infographic-gen/           ← all 16 versions merged into clean files
    chat/
    openrouter/
    ... (all 26 tools)
  i18n/
  404.html
  manifest.json
  robots.txt
  sitemap.xml
```

### Consolidation Checklist

| # | Task |
|---|---|
| 1 | Run `build_ifd_latest.py` to produce the merged baseline |
| 2 | Fix `_common` path depth: all tools use `../../_common/` (2 levels) |
| 3 | Add `speed-test` and `voice-memo` to `TOOL_SLUGS` in `sg-tool-registry.js` |
| 4 | Decide category for speed-test (recommend: `vault` or new `network`) |
| 5 | Audit all tool CSS for design token compliance (`var(--sg-*)`) |
| 6 | Verify all tools have `manifest.json` |
| 7 | Remove redundant file copies across merged files |
| 8 | Full test suite against v0.2.0 |
| 9 | Update reality document |

### When to Do It

Not urgently — the current stack works. But before v0.1.50, ideally. The next major feature addition (speed-test v2, for example) is a natural trigger: do the consolidation first, then start v0.2.1 with speed-test v2 as a clean surgical overlay.
