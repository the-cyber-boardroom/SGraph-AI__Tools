# Brief — LinkedIn Publisher · 2/5 Critical Decisions

These three decisions are load-bearing and must be made **before** any code is written. Each is followed by my recommended path and the trade-offs.

---

## Decision 1 — CORS strategy

**The risk:** LinkedIn's `api.linkedin.com` historically does not return permissive CORS headers. Browser-direct calls hit `Access-Control-Allow-Origin` errors and never reach the API. This is the single biggest architectural difference vs. the YouTube tools.

**Verify first.** Before architecting around the worst case, the next session should:
1. Open DevTools at any `tools.sgraph.ai` page.
2. Run `fetch('https://api.linkedin.com/rest/posts', { headers: { 'Authorization': 'Bearer fake', 'Linkedin-Version': '202604', 'X-Restli-Protocol-Version': '2.0.0' } })`.
3. If the error is CORS-related (no response, blocked) → we need a proxy.
4. If the error is `401 Unauthorized` (we got past CORS, just no valid token) → no proxy needed.

**Likely outcome:** CORS-blocked. If so, the options are:

| Option | Description | Cost | Trust profile |
|---|---|---|---|
| **A. Managed proxy** on `tools.sgraph.ai` (Cloudflare Worker / similar) | Tiny stateless proxy. Browser sends `{ url, method, headers, body }`; worker forwards to LinkedIn. **Doesn't store the user's token**, just relays. | Adds one piece of infra. Tied to tools.sgraph.ai operator. | User trusts SGraph operator not to log tokens — same trust they already place when loading tools.sgraph.ai. |
| **B. User-deployed proxy** (template Worker the user forks + deploys to their own Cloudflare account) | Same proxy code, but the user owns the URL. Tool has a "LinkedIn proxy URL" config field. | More setup friction. Best zero-trust story. | User trusts only themselves. Mirrors the "bring your own client ID" pattern we already have for YouTube. |
| **C. Browser extension** | Extension makes the cross-origin call directly via `host_permissions`. | Whole new distribution model. No. | — |
| **D. Direct browser calls** if CORS is permissive after all | The cleanest option. | Verify in step 1. | Same as YouTube. |

**Recommendation:**
- **Verify CORS first** (step 1 above). If permissive, go direct, mirror the YouTube architecture, done.
- If CORS-blocked: **start with Option A** (managed proxy on tools.sgraph.ai). One Cloudflare Worker, ~50 LOC, no state. Document Option B as a future "bring your own proxy" config that swaps the URL the tool uses.
- Either way, the **token cache stays in the browser** (`localStorage['sg-auth-token-linkedin-publisher']`) — the proxy never sees long-lived state, only forwards short-lived bearer tokens on each request.

The proxy MUST be transparent: the API contract the tool sees is identical to LinkedIn's. Test that by swapping between `https://api.linkedin.com` (direct) and `https://proxy.tools.sgraph.ai/linkedin` (proxied) with one config flip.

## Decision 2 — OAuth flow

LinkedIn doesn't have an in-page token-client equivalent of Google Identity Services. The standard flow is:

1. Tool opens `https://www.linkedin.com/oauth/v2/authorization?response_type=code&client_id=…&redirect_uri=…&state=…&scope=…&code_challenge=…&code_challenge_method=S256` in a popup or new tab.
2. User signs in + grants scopes on LinkedIn's site.
3. LinkedIn redirects back to `redirect_uri` with `?code=…&state=…` in the query string.
4. Tool exchanges the code for an access token via `POST https://www.linkedin.com/oauth/v2/accessToken`.

**Two questions to verify:**
- Does LinkedIn support **PKCE for public clients**? (If yes → token exchange can happen browser-side. If no → token exchange must go through the proxy / a backend.)
- Do the OAuth endpoints (`oauth/v2/authorization` for redirect, `oauth/v2/accessToken` for code exchange) allow CORS?

**Recommendation:**
- Use the **popup-with-postMessage pattern**: tool opens a small popup at `linkedin.com/oauth/v2/authorization`, the redirect URL is a small page on tools.sgraph.ai (`/en-gb/linkedin-publisher/oauth-callback.html`) that just reads the `code` from `location.search` and `postMessage`s it back to the opener, then closes itself.
- The opener (the tool) catches the postMessage, exchanges the code via the proxy (or directly if CORS permits), and stores the resulting token in `sg-auth-tokens` provider key `linkedin-publisher`.
- **Use PKCE** even if the proxy could otherwise hold a client secret — keeps the public-client architecture clean and means the proxy never sees the client secret.

The cache + skew handling (60 s) follows the youtube-editor pattern exactly. Re-use `youtube-token-cache.js` as the template; the new file `linkedin-token-cache.js` is a one-line provider-key change.

## Decision 3 — Required scopes

For org posting, the LinkedIn app must be approved for these scopes (configured in the LinkedIn Developer Portal, OAuth 2.0 settings):

| Scope | Why we need it |
|---|---|
| `r_liteprofile` | Identify the signed-in user (their name + avatar for the auth panel). |
| `r_organization_admin` | Discover which organisations this user can administer (so we can offer a picker). |
| `r_organization_social` | List + read posts published as the org. |
| `w_organization_social` | Create posts as the org. |

Approval for `*_organization_*` scopes requires **LinkedIn's verification process** for the app — this is heavier than Google's for `youtube`. The user must apply at the LinkedIn Developer Portal once and wait for approval (days to weeks). Until approved, the app is restricted to "Development tier" with limited testing capability.

**Recommendation:**
- Bundle a default LinkedIn client ID for `tools.sgraph.ai` once approved.
- Allow user override (paste-your-own client ID) like we do for YouTube.
- Document the verification dependency loudly in `SKILL-human.md` so a fork-and-self-host user knows they have to apply for approval too.
