# demo-reel — 2 · Critical decisions

*Eight calls that shape everything else. Each states what it costs if we get it
wrong, because that is the part that is expensive to reverse later.*

---

## Decision 1 — Annotations are DATA, never baked pixels

A callout, arrow, circle, highlight or blur is an entry in a JSON list, rendered
at compose time onto a copy of the screenshot. The screenshot itself is never
modified.

**Why this is the most important decision in the pack:**

- **An agent can author it.** "Circle the vault key field" is a rectangle in
  normalised coordinates. An agent cannot paint pixels, but it can write
  `{type:'circle', at:[0.62,0.31,0.18,0.06], label:'the vault key'}`.
- **Two aspect ratios need it.** The same annotation has to render onto a 16:9
  frame and a 9:16 crop. Baked pixels can only be scaled, and a baked callout in
  the wrong place is worse than none.
- **Blur especially.** A baked blur cannot be un-baked. If it covered the wrong
  field, or the wrong thing was left uncovered, the source is gone. Keeping blur
  as a region means the mistake is one edit away, not one re-record away.
- **Undo, review and diff all come free**, and the reel document stays
  human-readable in a pull request.

**If we get it wrong:** everything downstream becomes an image-editing problem
instead of a data problem, agents can no longer author reels, and the vertical cut
has to be authored by hand a second time.

## Decision 2 — One document, two aspect ratios, via a FOCUS RECT

Every shot declares the region that must survive a crop:

```json
{ "image": "images/shot-03.png", "focus": [0.28, 0.10, 0.44, 0.62] }
```

Landscape renders the whole frame (letterboxed as `video-creator` already does).
Vertical renders a 9:16 window that **must contain the focus rect**, scaled up if
necessary, panning if the rect moves between shots.

**Never author twice.** The moment there are two documents they drift, and the
vertical cut becomes the one that is always out of date.

**The honest limit:** a wide screenshot with detail spread across the full width
cannot be cropped to 9:16 without losing something. When the focus rect is wider
than 9:16 allows, the renderer must **say so** rather than silently shrinking the
whole frame to a stamp in the middle of a vertical video. A warning with the
shot index, and a documented fallback (fit-whole-frame with a coloured surround),
not a silent bad result.

## Decision 3 — On-screen text is a first-class track, not a subtitle

Most people who see these will see them **muted**, in a feed. So the on-screen
text is not derived from the audio — it is authored, has its own duration, and is
laid out to be read.

Two distinct fields per scene, and conflating them is a mistake worth naming:

- `narration` — what the voice says. Full sentences. Feeds TTS.
- `caption` — what appears on screen. Short, punchy, often four to eight words.

They are related, not identical. "The vault key is the only way in — there is no
password reset" is good narration; **"No password reset. Ever."** is the caption.
A tool that shows the narration verbatim on screen produces a wall of text nobody
reads.

**Default behaviour:** if a scene has no `caption`, derive a first-sentence
fallback from `narration` and **mark it as derived**, so a reviewer can see which
captions were written and which were guessed.

---

## Decision 4 — A scene holds MULTIPLE shots under ONE narration block

This is the structural change from `video-creator`, whose model is strictly one
slide ↔ one narration ↔ one audio duration.

```
scene = { shots: [shot, shot, shot], narration: "…", caption: "…" }
```

Shot durations are derived by splitting the scene's audio duration across its
shots — weighted, so a shot can be given more time — because **narration remains
the timing spine**. That keeps `video-creator`'s core assumption (audio decides
duration) rather than fighting it, and it means a scene is never cut off
mid-sentence.

**Minimum shot duration** must be enforced (proposed 800 ms). Five shots under a
four-second narration is a strobe, not a walkthrough, and the tool should refuse
or rebalance rather than produce it.

---

## Decision 5 — The reel document IS the API

`reel.json` is the authoring surface. The UI edits it; an agent writes it; the
renderer consumes it. Same discipline as every other tool here: `SgToolApi`,
`activate()` before UI, everything drivable headlessly.

This is what the memo is really asking for — *"it's mainly to be driven by agents
who can record a video, record a screenshot, create the text"*. An agent that has
to click cannot do that. An agent that writes a JSON document can.

## Decision 6 — Import from narrated-review is a TRANSFORM, not a new authoring step

`session.json` → `reel.json` is a documented mapping:

| narrated-review | demo-reel |
|---|---|
| `moments[i].image` | `scenes[i].shots[0].image` |
| `moments[i].text` | `scenes[i].narration` |
| `moments[i].notes` | `scenes[i].caption` (if present) |
| `moments[i].marks` | **dropped** — uncertain spans are a review artefact, not a script |

One capture becomes one single-shot scene. Merging adjacent captures into a
multi-shot scene is a deliberate edit, not something the import guesses at.

**Do not import the `marks`.** An uncertain span means "we are not sure this
transcription is right" — publishing it as narration would put a
possibly-misheard sentence into a video. The import should **refuse to carry a
capture whose `textSource` is `raw`** unless explicitly forced, and say why.

---

## Decision 7 — Handoff between tools: files and VFS, NOT localStorage

The memo suggests localStorage for moving data between tools. **It will not work
for this**, and the reason is worth stating plainly rather than discovering later:
localStorage is a ~5 MB quota shared across every tool on the origin, and a single
1920×1080 PNG base64s to roughly 2–4 MB. One screenshot could fill it.

The paths that do work, all already shipped:

1. **The zip** — `narrated-review` already exports `session.json` + `images/`.
   Drop it on demo-reel. Works across machines and browsers.
2. **`core/sg-vfs`** on IndexedDB — the shared store `narrated-review` already
   saves sessions to. Same origin, no size problem, no export/import step.
3. **An sgit vault** — for handing a reel to another person or agent.

localStorage is the right store for a small **handoff pointer** (`{tool, sessionId}`)
and for preferences. Not for images.

---

## Decision 8 — Measure the render pacing BEFORE building on it

`video-creator`'s recording loop advances slides with
`await new Promise(r => setTimeout(r, duration * 1000))` while MediaRecorder runs
in real time.

That is fine for a slideshow. For something we publish, it carries three risks we
have **not measured**:

- `setTimeout` drifts, and the drift accumulates across a 20-scene reel.
- A background tab throttles timers, so the video silently changes length.
- MediaRecorder captures at whatever rate the canvas actually paints, so a slow
  frame becomes a visibly long one.

**So Phase 0 is a probe, not a feature.** Render a known reel, measure actual
versus intended duration and frame pacing, and only then decide between keeping
the existing loop, adding a deterministic frame clock, or moving to WebCodecs
`VideoEncoder` where available.

This project has twice shipped a number that nobody had plotted — the 30-second
slices, the `p95 × 1.5` scene threshold. Measuring first is cheap here and the
tooling (`media-probe`) already exists.
