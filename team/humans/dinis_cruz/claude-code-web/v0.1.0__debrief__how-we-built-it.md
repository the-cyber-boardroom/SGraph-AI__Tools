## 1. The starting point

The session was opened with the prompt *"start a new session with a Developer agent (read project guidance and coding patterns)"* followed by *"I want to work on a new tool and component to add to this project"*. No spec, no scope. The first move was discovery, not code.

**Discovery flow (first 3 turns):**

1. Read `.claude/CLAUDE.md` — project rules, tier structure, the reality-document policy, the Git/branch conventions.
2. Read `.claude/explorer/CLAUDE.md` — the Explorer team mission ("Genesis → Custom-Built", minor versions, capture learnings).
3. Read the existing patterns — first via a tight sample (one component end-to-end + one tool end-to-end) rather than the whole codebase. Picked `components/key-input` and `tools/.../file-hasher` as smallest representatives, then upgraded to `tools/.../video-recorder/v0.1.48` once the manifest-driven tool pattern emerged.

**The single biggest payoff** of this discovery phase: spotting that the modern tool pattern was already manifest-driven (`<sg-tool-manifest src="./manifest.json">` + phase-ordered loader + `SgToolApi` registration). Once seen, every subsequent tool-shaped problem mapped onto that template — no time spent reinventing layouts, dev panels, or skill files.

## 2. How decisions were made

The conversation deliberately surfaced architecture choices as questions rather than implementation surprises. Three decision moments shaped the whole arc.

### Decision 1 — what's actually being built

The user's first message said "video upload to YouTube" two messages in. The architectural questions back to the user (recorder integration vs. standalone, where to keep the client ID, namespace under `components/video/upload/...`) were posed BEFORE any file was written. That avoided the most common failure mode — building the wrong thing fast.

### Decision 2 — auth + storage strategy

User flagged the OAuth popup as "weird". Rather than defaulting to "we'll cache the token in localStorage", the conversation surfaced the rule from `.claude/CLAUDE.md`: **no localStorage in core modules**. The resolution — caching lives in the component layer with a one-file adapter (`youtube-token-cache.js`) so a future swap to vault storage is a one-file change — was an explicit architecture decision, not a default.

### Decision 3 — combine vs. ship-and-iterate

When the user later asked for listing + editing, the option set was framed up-front: extend the `youtube-upload` tool, OR create a sibling `youtube-editor`, OR rename. The user picked *"call it 'youtube-editor' since it has more than just upload"*. Importantly, the original tool was kept on disk (URL stability, immutable IFD versions) — the new tool was an additional folder, not a rename.

## 3. The build/test rhythm

Every feature shipped through a tight loop:

```
        Code change(s)
              │
              ▼
       Commit + push
              │
              ▼
      User refreshes live URL
              │
              ▼
   Screenshot or "this didn't work"
              │
              ▼
      Diagnose → fix → repeat
```

The user's screenshots were the test suite. Three of the most important bugs were caught this way:

| Symptom (from a screenshot) | Root cause | Fix |
|---|---|---|
| Editor tab opens with "No video selected" | `setVideoSummary()` ran before `bindElements()` because `SgComponent.connectedCallback` is async | Defer-and-replay pattern + caller awaits `whenReady()` |
| Grid `Cannot set properties of undefined` on reload | Same race in `<sg-youtube-videos>.refresh()` after `_hydrateToken()` | Same fix, applied twice now |
| OAuth popup with bogus client ID | Test page added the GIS script for the live demo, but a leftover test still called `requestAccess('does-not-matter')` | Drop the test (its premise — "GIS is not loaded" — became false) |

The pattern: **the same async-binding race bit us twice**, the second time was caught immediately because the first fix had pre-loaded the mental model. The fix was generalised the second time so other consumers can poke methods immediately after `appendChild` without races.

## 4. Defensive patterns that emerged

A handful of patterns recurred enough to call out as design vocabulary for the next session.

### Defer-and-replay on async-bound elements

`SgComponent.connectedCallback` fetches HTML/CSS templates asynchronously, so any property/method that touches `this.$('#…')` runs into undefined refs if called between `appendChild` and `onReady`.

```js
async refresh() {
    if (!this._gridEl) {              // bindElements hasn't run yet
        this._pendingRefresh = true;
        return;
    }
    /* …real work… */
}

onReady() {
    /* …existing setup… */
    if (this._pendingRefresh) { this._pendingRefresh = false; this.refresh(); }
}
```

Combined with the caller `await component.whenReady()`, this is belt-and-braces: external code is robust, internal methods are robust.

### Optimistic UI with rollback

The playlist-picker checkboxes flip immediately, but if the API call fails, the checkbox snaps back and an inline error appears. Beat the network without lying to the user when the network beats us.

### Graceful scope detection

The analytics features need a different OAuth scope than upload+edit. Rather than refusing to load the tool when the analytics scope isn't granted, we:
1. Request both scopes together
2. Inspect the returned `r.scope` string to find what was actually granted
3. Only instantiate `YouTubeAnalytics` if the scope is present
4. Show a friendly "sign out + reconnect to grant analytics" notice in the spot the analytics card *would* go

The user can use the tool perfectly well without analytics; analytics are additive.

### Pure-fetch core, stateful components

Every core module (`core/youtube-upload`, `core/youtube-api`, `core/youtube-analytics`) is a thin class around `fetch` with no DOM, no localStorage, no UI. Caching, retry, error display all live one layer up in the component or tool. This keeps cores composable for non-UI consumers (Playwright, Claude Agents driving the JS API, future server-side adapters).

## 5. The role of skills + the JS API

Each tool got three skill files from day one:

| File | Audience | Purpose |
|---|---|---|
| `SKILL-human.md` | The person clicking buttons | Setup checklist (Google Cloud project, scopes, test users), what to do when |
| `SKILL-browser.md` | Playwright / browser automation | Route stubs for testing without real network, how to inject fake tokens, how to drive every method |
| `SKILL-api.md` | Other tools / SDK / Claude Agents | Method signatures, event names, storage keys, modules used |

The skills aren't documentation-after-the-fact — they were the contract. Writing the API skill while building the methods caught at least one method-shape inconsistency before it reached the UI.

The JS API itself (via `SgToolApi`) is the single biggest unlock for the workflow vision. Every action a human can do via the UI, an agent can do via `window.__tool['youtube-editor'].uploadVideo(...)`. This makes the YouTube editor immediately usable from a Claude Agent in Chromium — the same pattern infographic-gen already uses.

## 6. Honesty about scope limits

A few things were deliberately punted:

| Punt | Why |
|---|---|
| Original-video download from YouTube | Public Data API doesn't expose it. Studio's button uses internal endpoints we can't legitimately call cross-origin. Resolved with a "Download (Studio)" link + a planned IndexedDB-cache-on-upload feature. |
| Recorder code in v0.1.53 snapshot | The video-recorder snapshot for v0.1.53 was just a stub pointing to v0.1.48. Modified v0.1.48 (the actual code) and didn't restructure the snapshot system. |
| Dedicated tests for new playlist + analytics methods | The first round had stubbed-fetch tests for the original 6 methods; the new 9 methods follow the exact same `_json` helper pattern. Tagged for a follow-up rather than over-testing. |
| Bulk edit, delete UI, captions, scheduling, end-screens | All on the candidate list, all ranked by value/effort, all explicitly deferred when the user said "let's stop here". |

Each punt is documented in the commit message of the relevant commit. The reality doc reflects what *exists*, not what *was discussed*.

## 7. Reality-doc discipline

The CLAUDE.md rule "*update the reality document in the same commit as code*" was honoured for every feature commit. Three sections of the reality doc were touched: Core Modules, Components, Tools. That's it — the "what was discussed but not built" content stayed in the conversation, never the doc.

This matters because the next agent (or the same one in a new session) will read the reality doc as ground truth. If discussion ideas leaked into the doc, the next session would build on a phantom foundation.

## 9. What I'd do the same way next time

- **Discovery first, code second.** The 30 minutes spent reading patterns saved hours of later refactoring.
- **Surface architectural decisions as questions to the user** when they're load-bearing (component path, scope strategy, tool naming). Cheap upstream, expensive downstream.
- **Fix-and-explain commits** rather than "fix typo" commits. Every commit message answered "what was wrong, what's the fix, what's the lesson". Future readers (including future me) get the why.
- **Live testing > unit testing for UI work.** The user's screenshots caught more real bugs than any test suite would have. The unit tests caught the API-shape regressions; the screenshots caught the lifecycle races.

## 10. What I'd do differently

- **Catch the async-bind race once, not twice.** When the editor-tab race showed up, I should have audited every other component that calls a method right after `appendChild` (the videos grid did exactly that). One sweep, not two commits.
- **Write the analytics block markup before the JS that binds to it.** Shipped a commit referencing `#an-tiles` etc. that didn't exist yet — caught immediately by visual inspection, but a 30-second template-first check would have saved the follow-up.
