## Why This Document Exists

We set out to answer a simple question: **can we run `sg-send-cli` — a real Python CLI with compiled cryptography dependencies — entirely in the browser, with zero server and zero installation?**

The answer is yes, but the path there was not straightforward. This debrief records every technical decision, dead end, and workaround so the next team picking this up doesn't repeat the archaeology.

**Read time:** ~15 minutes. Sections 1-3 for the overview, sections 4-8 for the deep technical detail.

## 1. Executive Summary

We shipped **three Pyodide-powered browser tools** and **one shared core module**:

| Deliverable | Path | What It Does |
|---|---|---|
| **sg-pyodide.js** (core) | `core/pyodide/v1/v1.0/v1.0.0/sg-pyodide.js` | Shared module: loads Pyodide, installs packages, captures stdout/stderr |
| **Python REPL** (tool) | `tools/v0/v0.1/v0.1.2/en-gb/pyodide-repl/index.html` | Interactive Python console in the browser |

All three tools load CPython compiled to WebAssembly (~20 MB), install `sg-send-cli` from PyPI at runtime, and execute real vault operations client-side. No server. No Python installation. No credentials.

## 2. The Core Challenge: Installing sg-send-cli in Pyodide

### 2.1 Why This Was Hard

`sg-send-cli` (v0.5.0 on PyPI) has this dependency chain:

```
sg-send-cli
  ├── cryptography >= 43.0.0   ← compiled C extension, no pure-Python wheel
  ├── osbot-utils               ← pure Python, installs fine
  ├── httpx                     ← pure Python, installs fine
  └── pydantic                  ← pure Python, installs fine
```

Pyodide's package manager (`micropip`) only installs pure-Python wheels or Pyodide-specific pre-built packages. The `cryptography` library has no pure-Python wheel — it requires compiled native code. This single dependency blocked the entire installation chain.

### 2.2 Six Iterations to Get It Working

We went through **six distinct approaches** over ~5 hours and 10 commits before finding one that works reliably.

---

**Iteration 1: Direct PyPI install**
```javascript
await micropip.install('sg-send-cli')
```
**Result:** FAILED. micropip tries to resolve `cryptography>=43.0.0`, can't find a pure-Python wheel, throws an error.

---

**Iteration 2: Pre-load cryptography, then install sg-send-cli**
```javascript
await pyodide.loadPackage('cryptography')  // Pyodide has this built-in
await micropip.install('sg-send-cli')
```
**Result:** FAILED. micropip still inspects the wheel's METADATA file and tries to resolve all declared dependencies, even though cryptography is already loaded. It doesn't check what's already installed before attempting resolution.

---

**Iteration 3: Skip dependency resolution with `deps=False`**
```javascript
await micropip.install('sg-send-cli', { deps: false })
```
**Result:** FAILED. This is the critical discovery: **JavaScript objects passed as the second argument to a Pyodide-proxied Python function are NOT automatically converted to Python kwargs.** The `{ deps: false }` object is silently ignored. micropip still resolves dependencies.

---

**Iteration 4: Use Python API directly**
```javascript
await pyodide.runPythonAsync(`
  import micropip
  await micropip.install('sg-send-cli', deps=False)
`)
```
**Result:** FAILED. Nested `await` inside `runPythonAsync` triggers event loop issues. The `micropip.install()` coroutine can't be properly awaited when already inside a Pyodide async context.

---

**Iteration 5: Direct wheel URL from PyPI**
```javascript
const url = 'https://files.pythonhosted.org/.../sg_send_cli-0.5.0-py3-none-any.whl'
await micropip.install(url)
```
**Result:** FAILED. micropip still parses the wheel's METADATA even when given a direct URL. The cryptography dependency check is inescapable through the normal install path.

---

**Iteration 6: JS fetch + virtual filesystem + `callKwargs` (SUCCESS)**
```javascript
// 1. Fetch the wheel via JS (no Pyodide event loop involved)
const meta = await (await fetch('https://pypi.org/pypi/sg-send-cli/json')).json()
const wheelInfo = meta.urls.find(u => u.filename.endsWith('.whl'))
const wheelBytes = new Uint8Array(await (await fetch(wheelInfo.url)).arrayBuffer())

// 2. Write to Pyodide's in-memory filesystem
pyodide.FS.writeFile('/tmp/' + wheelInfo.filename, wheelBytes)

// 3. Install from virtual filesystem using callKwargs
await micropip.install.callKwargs(
  'emfs:///tmp/' + wheelInfo.filename,
  { deps: false }
)
```
**Result:** SUCCESS. This works because:
- **JS `fetch()`** downloads the wheel outside Pyodide's event loop — no async nesting issues
- **`pyodide.FS.writeFile()`** is synchronous — the file is immediately available
- **`emfs://` URI** tells micropip to read from the virtual filesystem synchronously (no HTTP)
- **`.callKwargs()`** is the Pyodide JS proxy method that properly converts `{ deps: false }` to Python `deps=False` — this was the key missing piece from Iteration 3

### 2.3 The Full Installation Sequence (What Ships)

```
Step 1: Download Pyodide from CDN (~20 MB, cached by browser)
Step 2: Initialize Pyodide WASM runtime
Step 3: Load micropip (Pyodide built-in)
Step 4: pyodide.loadPackage('cryptography')     ← Pyodide pre-compiled WASM wheel
Step 5: micropip.install('osbot-utils')          ← pure Python, normal install
Step 6: JS fetch sg-send-cli wheel from PyPI
Step 7: Write wheel to pyodide.FS virtual filesystem
Step 8: micropip.install.callKwargs('emfs:///tmp/wheel.whl', { deps: false })
Step 9: Import all vault modules — ready
```

Total first-load time: ~50-90 seconds (dominated by Pyodide download). Subsequent loads: ~15-30 seconds (Pyodide cached by browser HTTP cache).

## 3. The Core Module: sg-pyodide.js

**Location:** `core/pyodide/v1/v1.0/v1.0.0/sg-pyodide.js`

This is the shared foundation all three tools import. It exports six functions:

| Export | Purpose |
|---|---|
| `loadPyodide(options)` | Load Pyodide from CDN, cache singleton, emit progress callbacks |
| `installPackages(pyodide, packages)` | Install pure-Python packages via micropip |
| `runPython(pyodide, code)` | Execute Python code, return result |
| `runPythonCapture(pyodide, code)` | Execute code with stdout/stderr capture (REPL semantics) |
| `checkVaultCompatibility(pyodide)` | Test that hashlib, hmac, cryptography, httpx, pydantic all work |
| `deriveVaultKeysPython(pyodide, passphrase, vaultId)` | Derive vault keys using Python PBKDF2 |

### 3.1 Singleton Caching

Pyodide is ~20 MB. We cache the instance at module level:

```javascript
let _pyodideInstance = null

export async function loadPyodide(options) {
    if (_pyodideInstance) return _pyodideInstance
    // ... load from CDN ...
    _pyodideInstance = pyodide
    return pyodide
}
```

Multiple tool sections calling `loadPyodide()` get the same instance. No duplicate downloads.

### 3.2 Output Capture (REPL Semantics)

`runPythonCapture()` mimics Python's interactive mode:

1. Try `compile(code, '<stdin>', 'eval')` first — if it compiles as an expression, use `eval()` and return the value (so `2+2` shows `4`)
2. Fall back to `compile(code, '<stdin>', 'exec')` for statements (so `x = 1` shows nothing)
3. Capture stdout and stderr via `io.StringIO` redirection
4. Strip Pyodide-internal traceback frames (paths like `/_pyodide/_base.py`) for clean error messages
5. Return `{ result, stdout, stderr, error }`

### 3.3 PBKDF2 Fallback (Critical Workaround)

**Discovery:** `hashlib.pbkdf2_hmac()` is not available in Pyodide's emscripten build of CPython. The function exists in the standard library source but was not compiled into the WASM binary.

**Solution:** Try/except fallback to the `cryptography` library:

```python
def _derive_pbkdf2(passphrase_bytes, salt_bytes):
    try:
        return hashlib.pbkdf2_hmac('sha256', passphrase_bytes, salt_bytes, 600_000, dklen=32)
    except AttributeError:
        from cryptography.hazmat.primitives.kdf.pbkdf2 import PBKDF2HMAC
        from cryptography.hazmat.primitives import hashes
        kdf = PBKDF2HMAC(algorithm=hashes.SHA256(), length=32,
                         salt=salt_bytes, iterations=600_000)
        return kdf.derive(passphrase_bytes)
```

Both paths produce identical output (verified with test vectors). The vault-pyodide tool proves this by deriving keys via both Python and JavaScript and comparing byte-for-byte.

## 5. MVP 2: Vault (Pyodide) Compatibility Tool

**Path:** `tools/v0/v0.1/v0.1.2/en-gb/vault-pyodide/index.html`

**What it proves:** Python (running in Pyodide) and JavaScript (running via Web Crypto API) produce **byte-identical vault keys** from the same passphrase and vault ID.

**How it works:**

```
Step 1: Load Pyodide
Step 2: Run compatibility check (6 dependencies: hashlib, hmac, json, cryptography, httpx, pydantic)
Step 3: Derive vault keys two ways:
        - Python: deriveVaultKeysPython(pyodide, passphrase, vaultId)
        - JavaScript: deriveVaultKeys(passphrase, vaultId)  (Web Crypto API)
Step 4: Compare read_key, write_key, tree_file_id — must match exactly
```

**Hardcoded test vectors included:**
- `my-secret-passphrase:a1b2c3d4` → expected `read_key_hex: a9cbcf15b4719384...`
- `pass:with:colons:deadbeef` → tests colon-handling in key parsing

**Why this matters:** If Python and JS can produce identical keys, the vault wire format is language-agnostic. A JS-only vault client could interop with the Python CLI without any server-side mediation.

## 6. MVP 3: SG/Send CLI (The Main Event)

**Path:** `tools/v0/v0.1/v0.1.2/en-gb/sg-send-cli/index.html`
**Lines:** ~1,380

This is the most complex MVP. Covered in detail in the companion debrief (`v0.1.2__debrief__sg-send-cli-tool.md`), but the Pyodide-specific aspects:

### 6.1 Package Installation (The Hard Part)

Uses the full Iteration 6 approach (JS fetch + virtual filesystem + `callKwargs`). The installation sequence is:

```
1. Load Pyodide from CDN
2. pyodide.loadPackage('cryptography')
3. micropip.install('osbot-utils')
4. JS fetch sg-send-cli wheel → write to pyodide.FS → callKwargs install
5. Import Vault__Crypto, Vault__Sync, Vault__Inspector, Vault__API__In_Memory
6. Create BrowserCLI instance
```

### 6.2 Scenario System (Python-in-HTML)

Four pre-built scenarios execute real Python code strings via `runPythonCapture()`:

```javascript
const scenarioCode = {
    init: `
        from sg_send_cli.crypto.Vault__Crypto import Vault__Crypto
        from sg_send_cli.api.Vault__API__In_Memory import Vault__API__In_Memory
        ...
        result = sync.init(vault_dir, vault_key='solo-qa-passphrase:solo-qa-vault')
    `,
    commit: `...`,
    push: `...`,
    full: `...`   // Complete init → add → commit → push → modify → commit → push lifecycle
}
```

Each scenario runs against `Vault__API__In_Memory()` — no network calls. State persists across scenarios via Python builtins (`builtins._sg_vault_dir`, `builtins._sg_sync`, etc.).

### 6.3 CLI Terminal (The Final UI)

Replaced the raw Python REPL with a Unix-style terminal that parses `sg-send-cli` commands:

```
$ sg-send-cli init --vault-key my-secret
$ sg-send-cli commit -m "add files"
$ sg-send-cli push
$ sg-send-cli log --oneline
```

The Python `BrowserCLI` class intercepts these commands, routes to handlers, and returns formatted output. Shell builtins (`ls`, `cat`, `tree`, `mkdir`, `cd`, `pwd`) also work against Pyodide's virtual filesystem.

## 7. Issues We Hit and How We Solved Them

### 7.1 Issue Log (Chronological)

| # | Issue | Symptom | Root Cause | Fix | Commits |
|---|---|---|---|---|---|
| 1 | Wrong package name in deploy workflow | CI fails | Typo in workflow YAML | Fix package name | `1374cdb` |
| 2 | cryptography wheel not found | `micropip.install` error | No pure-Python wheel exists for cryptography | Pre-load from Pyodide built-ins: `pyodide.loadPackage('cryptography')` | `864704c` |
| 3 | micropip resolves deps even with `deps=False` | Still fails on cryptography | JS `{ deps: false }` not translated to Python kwargs | Discovered `.callKwargs()` method on Pyodide proxied functions | `defa5ee`, `c47568d` |
| 4 | Nested async in `runPythonAsync` | Event loop error | Can't `await micropip.install()` inside `runPythonAsync` | Move to JS-side fetch + FS write, avoid nested async entirely | `c5a13c4` |
| 5 | Wheel URL hardcoded, breaks on version bump | Fragile | URL was a literal PyPI path | Fetch `https://pypi.org/pypi/sg-send-cli/json`, extract wheel URL dynamically | `34ba57d` |
| 6 | Sporadic install failures | Intermittent | Network timeouts on large wheel download | Added retry loop with backoff | `30622de` |
| 7 | Retry loop made code complex and hard to debug | Complexity | Three fallback paths with different failure modes | Removed retry; single reliable path (JS fetch + FS + callKwargs) | `6a36abc` |
| 8 | `hashlib.pbkdf2_hmac` missing in Pyodide | AttributeError during key derivation | Not compiled into emscripten WASM build | Try/except fallback to `cryptography.hazmat.primitives.kdf.pbkdf2` | `86c959d` |
| 9 | CLI flags (`--help`, `--oneline`) ignored | Commands run without flags | Handlers accepted `args` parameter but never inspected it | Added flag parsing to all handlers | `1b6e10a` |

### 7.2 Key Lesson: The `.callKwargs()` Discovery

This was the single most important technical discovery. Standard Pyodide JS-to-Python function calls **do not** support keyword arguments via JavaScript objects:

```javascript
// DOES NOT WORK — { deps: false } is silently ignored
await micropip.install('pkg', { deps: false })

// WORKS — callKwargs() properly converts JS object to Python kwargs
await micropip.install.callKwargs('pkg', { deps: false })
```

This is documented in Pyodide's API but easy to miss. It cost us several hours and multiple failed approaches before we found it.

### 8.2 Runtime Performance

| Operation | Time |
|---|---|
| PBKDF2-SHA256 (600K iterations) | 200-300ms |

| Push to in-memory API | 200-400ms |

PBKDF2 is the bottleneck — 600K iterations of SHA256 in WASM is comparable to native JavaScript Web Crypto performance.

## 10. Key Decisions

| Decision | Why | Alternative Considered |
|---|---|---|
| Pyodide (CPython-in-WASM) over Brython/Skulpt | Real CPython; runs unmodified `sg-send-cli` package | Brython can't run C extensions; Skulpt is Python 2 |
| JS fetch + FS write over micropip HTTP | Avoids event loop nesting; synchronous FS write | micropip's HTTP path hits async issues |
| `.callKwargs()` over Python `runPythonAsync` | Clean JS-to-Python kwargs; no nested async | `runPythonAsync` with `await micropip.install()` fails |
| Pre-load cryptography from Pyodide built-ins | Available before micropip tries to resolve it | Let micropip handle it (fails — no pure-Python wheel) |
| `Vault__API__In_Memory` over real S3 | No credentials, no CORS, no network dependency | Real S3 would be more realistic but complex |
| Single `sg-pyodide.js` shared module | Three tools share one codebase; DRY | Each tool manages its own Pyodide lifecycle (duplication) |
| PBKDF2 try/except fallback | Works in all environments (Pyodide or native) | Hard-fail if `hashlib.pbkdf2_hmac` missing (would break Pyodide) |
