## Why This Document Exists

The sg-send-cli browser tool went through two major UI iterations in a single session: from a raw Python REPL to a Unix-style CLI terminal. This debrief documents the architectural decisions, the evolution, and provides a detailed technical breakdown of the final implementation — with particular attention to how the in-memory server works and why it exists.

**Read time:** ~15 minutes. Sections 1-3 for the overview, sections 4-9 for the deep technical walkthrough.

---

## 1. Executive Summary

We built a **browser-based sg-send-cli terminal** that runs the real Python `sg-send-cli` package (from PyPI) in the browser via Pyodide, with all vault operations executing against an in-memory server backend.

**What shipped (single file, ~1,380 lines):**

```
sgraph_ai_tools__static/tools/v0/v0.1/v0.1.2/en-gb/sg-send-cli/index.html
```

**Three sections in the UI:**

| Section | What It Does |
|---|---|
| **Step 1 — Load Python** | Downloads Pyodide, installs sg-send-cli, shows progress |
| **Step 2 — Run Scenarios** | Four pre-built demo buttons (Init, Commit, Push, Full Workflow) |
| **Step 3 — CLI Terminal** | Interactive `$ ` prompt where users type `sg-send-cli` commands |

**Key achievement:** Users can type `sg-send-cli init --vault-key my-secret`, `sg-send-cli commit -m "hello"`, `sg-send-cli push`, and `sg-send-cli log --oneline` — the same commands they'd type in a real terminal — and get realistic output, all running client-side with no server.

## 2. UI Evolution: Two Iterations

### 2.1 Iteration 1: Python REPL (Commit 43510ce)

**The first UI** exposed a raw Python console where users typed Python code directly:

```
Section 1: [Load Pyodide]     — "Step 1 — Load Python + Install sg-send-cli"
Section 2: [Scenario Buttons]  — "Step 2 — Run Vault Scenarios"
Section 3: [Python Console]    — "Console" with textarea, Shift+Enter to run
```

**Input method:** Multi-line `<textarea>` with a "Run" button. Shift+Enter to execute.

**What users typed:**
```python
>>> from sg_send_cli.crypto.Vault__Crypto import Vault__Crypto
>>> crypto = Vault__Crypto()
>>> sync = Vault__Sync(crypto=crypto, api=api)
>>> result = sync.init(vault_dir, vault_key='my-secret')
```

**Problem:** This required users to know the Python API — the class names, method signatures, import paths. Not accessible to anyone who just wants to understand what `sg-send-cli` does.

### 2.2 Iteration 2: CLI Terminal (Commit e348d30)

**The redesign** replaced the Python REPL with a Unix-style terminal:

```
Section 1: [Load Pyodide]     — unchanged
Section 2: [Scenario Buttons]  — unchanged
Section 3: [CLI Terminal]      — Single-line input with "$ " prompt, Enter to execute
```

**Input method:** Single-line `<input>` with `$ ` prefix. Enter to execute. Up/Down for history.

**What users type:**
```
$ sg-send-cli init --vault-key my-secret
$ sg-send-cli commit -m "hello"
$ sg-send-cli push
$ sg-send-cli log --oneline
$ ls .sg_vault/bare/
```

**Why the change mattered:**

| Aspect | REPL (v1) | CLI Terminal (v2) |
|---|---|---|
| Knowledge required | Python API, class names, imports | CLI commands (like git) |
| Input style | Multi-line textarea + Shift+Enter | Single-line + Enter |
| Discoverability | None — must read source | `sg-send-cli --help` lists all commands |
| Familiar to | Python developers | Anyone who uses a terminal |
| Error messages | Python tracebacks | Clean one-line errors |

The CLI terminal made the tool accessible to anyone familiar with git-like CLIs, not just Python developers.

**Two storage layers:**

1. **Pyodide Virtual Filesystem** — Where vault files live (`.sg_vault/bare/data/`, `refs/`, etc.). This is an in-memory emscripten filesystem that behaves like a real disk. The `Vault__Sync` module reads/writes encrypted objects here using standard Python `os` and `open()` calls.

2. **`Vault__API__In_Memory`** — The "remote server" that `push` sends to and `pull` would fetch from. It's a Python dict (`self._store = {}`) that stores key-value pairs. In production, this would be `Vault__API__S3` talking to AWS. In the browser, it's a dict.

## 4. The In-Memory Server: Deep Dive

### 4.1 What It Is

`Vault__API__In_Memory` is a class from the real `sg-send-cli` PyPI package (not something we wrote). It implements the same interface as `Vault__API__S3` but stores everything in a Python dictionary.

```python
class Vault__API__In_Memory:
    def setup(self):
        self._store = {}
        self._write_count = 0
        return self

    def put(self, key, data):
        self._store[key] = data
        self._write_count += 1

    def get(self, key):
        return self._store.get(key)

    def list(self, prefix=''):
        return [k for k in self._store if k.startswith(prefix)]
```

### 4.2 How Push Works Against It

When a user runs `sg-send-cli push`:

```
1. Vault__Sync reads all new objects from .sg_vault/bare/data/
2. For each object not yet on the "server":
   - Calls api.put(object_id, encrypted_bytes)
   - This stores the encrypted blob in the Python dict
3. Updates the remote ref:
   - Calls api.put('refs/branch_id', latest_commit_id)
4. Returns { status: 'pushed', objects_uploaded: N, commits_pushed: M }
```

**The encrypted objects in the dict are identical** to what would be uploaded to S3 in production. The crypto layer doesn't know or care where the bytes end up — it encrypts the same way regardless.

### 4.3 Why In-Memory Instead of Real S3

| Concern | In-Memory | Real S3 |
|---|---|---|
| AWS credentials | Not needed | Need IAM keys or Cognito |
| CORS configuration | Not needed | Must configure S3 bucket + CloudFront |
| Network latency | Zero | Variable |
| Network dependency | None | Page breaks if offline |
| Security surface | None | Credentials in browser JS |
| Data persistence | Lost on page reload | Persists in S3 |
| Fidelity | High (same crypto, same format) | Production-identical |

For an MVP demonstrator, the in-memory approach gives us **high fidelity** (the crypto and sync logic are identical to production) with **zero infrastructure** (no AWS, no credentials, no CORS).

### 4.4 What the In-Memory Server Contains After a Session

After the "Full Solo Workflow" scenario:

```

    'data/obj-bf7108cd...': b'\x89\x4a...',   # Encrypted init commit
    'data/obj-2dc06209...': b'\xa3\x12...',   # Encrypted second commit
    'data/obj-...':         b'\xf2\x01...',   # Encrypted tree objects
    'data/obj-...':         b'\x44\x9e...',   # Encrypted file blobs
    'refs/branch-abc123':   'obj-2dc06209...',  # Branch head pointer

```

## 5. The BrowserCLI Class: How Commands Work

### 5.1 Initialisation

When Pyodide finishes loading, the embedded Python code creates a singleton:

```python
class BrowserCLI:
    def __init__(self):
        from sg_send_cli.api.Vault__API__In_Memory import Vault__API__In_Memory
        from sg_send_cli.crypto.Vault__Crypto      import Vault__Crypto
        from sg_send_cli.sync.Vault__Sync          import Vault__Sync
        from sg_send_cli.objects.Vault__Inspector   import Vault__Inspector

        self.api       = Vault__API__In_Memory().setup()
        self.crypto    = Vault__Crypto()
        self.sync      = Vault__Sync(crypto=self.crypto, api=self.api)
        self.inspector = Vault__Inspector(crypto=self.crypto)
        self.vault_dir = None
        self.vault_key = None
        self.home      = '/home/pyodide'

import builtins
builtins._sg_cli = BrowserCLI()
```

The instance is stored on `builtins` so it's globally accessible from any Python scope within Pyodide.

### 5.2 Command Routing

When a user types a command and presses Enter:

**JavaScript side:**
```javascript
async function runCliCommand() {
    const cmd = document.getElementById('cli-input').value.trim()
    // Set the command string as a Python global
    pyodide.globals.set('_cli_cmd', cmd)
    // Execute: call BrowserCLI.run() with the command
    const { stdout, stderr } = await runPythonCapture(pyodide, '_sg_cli.run(_cli_cmd)')
    // Display output in terminal
    appendOutput(stdout || stderr)
}
```

**Python side — `BrowserCLI.run()`:**
```python
def run(self, raw):
    parts = raw.strip().split()
    if not parts:
        return ''

    # Strip "sg-send-cli" prefix if present
    if parts[0] == 'sg-send-cli':
        rest = parts[1:]
        if not rest:
            return self.cmd_help()
        cmd = rest[0]
        rest = rest[1:]
    else:
        cmd = parts[0]
        rest = parts[1:]

    # Route to handler
    handlers = {
        'help': 'cmd_help',    '--help': 'cmd_help',     '-h': 'cmd_help',
        'init': 'cmd_init',    'status': 'cmd_status',
        'commit': 'cmd_commit','push': 'cmd_push',
        'log': 'cmd_inspect_log',
        'inspect': 'cmd_inspect',
        'inspect-tree': 'cmd_inspect_tree',
        'inspect-log': 'cmd_inspect_log',
        'inspect-stats': 'cmd_inspect_stats',
        'derive-keys': 'cmd_derive_keys',
        'branches': 'cmd_branches',
        'cat-object': 'cmd_cat_object',
        # Shell builtins
        'ls': 'cmd_ls',       'cat': 'cmd_cat',
        'pwd': 'cmd_pwd',     'cd': 'cmd_cd',
        'mkdir': 'cmd_mkdir', 'rm': 'cmd_rm',
        'tree': 'cmd_tree',   'touch': 'cmd_touch',
        'write': 'cmd_write',
    }

    handler_name = handlers.get(cmd)
    if not handler_name:
        return f"sg-send-cli: '{cmd}' is not a command. See 'sg-send-cli --help'."

    handler = getattr(self, handler_name)
    return handler(rest) if handler_name not in ('cmd_help', 'cmd_version', 'cmd_pwd') else handler()
```

**Key design choices:**
- The `sg-send-cli` prefix is optional — `init` works the same as `sg-send-cli init`
- Shell builtins (`ls`, `cat`, `tree`, `cd`) work directly, without the `sg-send-cli` prefix
- The `rest` list (everything after the subcommand) is passed as `args` to each handler
- `log` is aliased to `inspect-log` to match the real CLI

### 5.3 Flag Parsing

Two patterns are used:

**Simple flags** (`--help`, `--oneline`, `--graph`) — checked by membership:
```python
def cmd_inspect_log(self, args):
    if '-h' in args or '--help' in args:
        return 'usage: sg-send-cli log [--oneline] [--graph] [directory]'
    # ...
    oneline = '--oneline' in args
    graph   = '--graph'   in args
```

**Value flags** (`--vault-key KEY`, `-m MESSAGE`) — extracted by the `_parse_flag` helper:
```python
def _parse_flag(self, args, flag):
    """Extract --flag VALUE from args, return (value, remaining_args)."""
    rest = []
    value = None
    i = 0
    while i < len(args):
        if args[i] == flag and i + 1 < len(args):
            value = args[i + 1]
            i += 2
        else:
            rest.append(args[i])
            i += 1
    return value, rest
```

Used by `cmd_init` (extracts `--vault-key`) and `cmd_commit` (extracts `-m`).

## 6. The Scenario System

### 6.1 Four Scenarios

Each scenario is a Python code string executed via `runPythonCapture()`. They use the same `Vault__Sync`, `Vault__Crypto`, and `Vault__API__In_Memory` classes as the CLI terminal.

**Scenario 1: Init Vault**
```
- Creates temp directory via tempfile.mkdtemp()
- Runs sync.init(vault_dir, vault_key='solo-qa-passphrase:solo-qa-vault')
- Shows: vault ID, named branch, clone branch, init commit
- Inspects .sg_vault/bare/ structure (data, refs, keys, indexes file counts)
- Inspects commit chain (1 init commit)
- Shows status: clean
```

**Scenario 2: Add Files + Commit**
```
- Creates README.md and configs/EC2.json in the vault directory
- Shows status: 2 new files
- Commits with message "add initial files"
- Inspects commit chain (now 2 commits)
- Inspects tree: shows file paths, blob IDs, sizes
```

**Scenario 3: Push to Server**
```
- Calls sync.push(vault_dir)
- Shows: objects uploaded, commits pushed
- Shows in-memory API store size (entries + total writes)
```

**Scenario 4: Full Solo Workflow** (All steps combined + more)
```
STEP 1: Init vault
STEP 2: Add files + commit
STEP 3: Push to server
STEP 4: Modify README.md, delete configs/EC2.json, commit
STEP 5: Add notes.txt, commit
STEP 6: Second push (delta — only new objects)
FINAL:  Summary with total commits, files, object store stats
```

### 6.2 State Persistence Between Scenarios

After each scenario, state is stored as Python builtins:

```python
import builtins
builtins._sg_vault_dir = vault_dir
builtins._sg_sync      = sync
builtins._sg_crypto    = crypto
builtins._sg_api       = api
builtins._sg_inspector = inspector
builtins._sg_keys      = keys
```

This means:
- Running Scenario 1 (Init) creates the vault
- Running Scenario 2 (Add + Commit) uses the same vault directory
- Running Scenario 3 (Push) pushes that vault's objects
- The CLI terminal can then interact with the same vault

The scenarios and terminal share a single `BrowserCLI` instance with a single `Vault__API__In_Memory` — everything is connected.

    if (e.key === 'Enter') {
        e.preventDefault()
        await runCliCommand()
    } else if (e.key === 'ArrowUp') {
        // Navigate command history backward
        if (historyIndex > 0) {
            historyIndex--
            cliInput.value = history[historyIndex]
        }
    } else if (e.key === 'ArrowDown') {
        // Navigate command history forward
        if (historyIndex < history.length - 1) {
            historyIndex++
            cliInput.value = history[historyIndex]
        } else {
            historyIndex = history.length
            cliInput.value = ''
        }
    }

## 8. Complete Data Flow: A Push Operation

To illustrate how all layers connect, here's what happens when a user types `sg-send-cli push`:

```
1. USER types "sg-send-cli push" and presses Enter

2. JAVASCRIPT
   - Reads input value: "sg-send-cli push"
   - Sets Python global: pyodide.globals.set('_cli_cmd', 'sg-send-cli push')
   - Calls: runPythonCapture(pyodide, '_sg_cli.run(_cli_cmd)')

3. PYTHON (BrowserCLI.run)
   - Splits: ['sg-send-cli', 'push']
   - Strips prefix: cmd='push', rest=[]
   - Routes to: cmd_push(rest)

4. PYTHON (BrowserCLI.cmd_push)
   - Checks: '-h' not in args, '--help' not in args
   - Calls: self._need_vault() → returns vault_dir (e.g. '/home/pyodide/vault')
   - Calls: self.sync.push(vault_dir)

5. PYTHON (Vault__Sync.push) — from real sg-send-cli package
   - Reads .sg_vault/bare/refs/ to find current branch head
   - Reads .sg_vault/bare/data/ to find all objects
   - Compares with what the API already has (api.list())
   - For each new object:
     - Reads encrypted bytes from .sg_vault/bare/data/{object_id}
     - Calls api.put(object_id, encrypted_bytes)
   - Updates remote ref: api.put('refs/{branch}', commit_id)

6. PYTHON (Vault__API__In_Memory.put)
   - self._store[key] = data    ← stored in Python dict
   - self._write_count += 1

7. PYTHON (cmd_push returns string)
   - Returns: "Pushing to in-memory server...\n  Status: pushed\n  Objects uploaded: 3\n  Commits pushed: 1"

8. JAVASCRIPT
   - Receives stdout from runPythonCapture
   - Appends to #cli-output as terminal lines
   - Auto-scrolls terminal to bottom
   - Re-enables input
```

**The encrypted bytes stored in `self._store` are production-identical.** The same bytes would be uploaded to S3 in a real deployment. The only difference is the transport layer (dict assignment vs HTTP PUT).

## 9. What's Different From the Real CLI

| Aspect | Real sg-send-cli | Browser BrowserCLI |
|---|---|---|
| Backend API | `Vault__API__S3` (AWS S3) | `Vault__API__In_Memory` (Python dict) |
| Filesystem | Real OS filesystem | Pyodide emscripten virtual FS |
| Crypto | `hashlib.pbkdf2_hmac` | `cryptography.PBKDF2HMAC` (fallback) |
| Command parsing | `argparse` (Python stdlib) | Custom `run()` + `_parse_flag()` |
| Available commands | Full set including `pull`, `clone`, `merge` | Subset: init, status, commit, push, log, inspect |
| Error handling | Full tracebacks | Clean one-line messages |
| vault_key auto-read | Reads from `.sg_vault/local/vault_key` | Same — virtual FS supports this |
| Persistence | Disk survives reboot | Lost on page reload |

**The crypto is identical.** Objects encrypted by the browser version can be decrypted by the real CLI and vice versa (same PBKDF2 parameters, same AES-256-GCM, same key derivation).

**The command parsing is simpler.** The real CLI uses Python's `argparse` with full subcommand support. The browser version uses manual string splitting and a handler dict. This means some edge cases (quoted strings with spaces, complex flag combinations) won't work in the browser. For the MVP demo scenarios, this is sufficient.

## 10. Key Decisions

| Decision | Why | Alternative Considered |
|---|---|---|
| CLI terminal over Python REPL | Accessible to non-Python users; matches real CLI UX | Keep REPL (requires Python knowledge) |
| Single `<input>` over `<textarea>` | One command per line, Enter to execute — like a real terminal | Textarea with Shift+Enter (REPL pattern) |
| Optional `sg-send-cli` prefix | `push` works same as `sg-send-cli push` — less typing | Always require prefix (more realistic but tedious) |
| Shell builtins (`ls`, `cat`, `tree`) | Users can explore the vault filesystem, not just run vault commands | Only vault commands (limits understanding) |
| Python code embedded in HTML | Single file deployment; no build step; matches project conventions | Separate `.py` file loaded via fetch (adds a request) |
| `builtins._sg_cli` singleton | Globally accessible from any Python scope in Pyodide | Module-level variable (harder to access from JS bridge) |
| Custom `_parse_flag` over argparse | Simpler; argparse requires `sys.argv` patching in Pyodide | Use argparse (more complex, more edge cases) |

## 12. Open Questions

1. **Should `sg-send-cli push` say "in-memory server" or something less confusing?** Users might wonder where "in-memory server" is. Could say "browser storage" or "local vault API" instead.
2. **Should we support `sg-send-cli pull`?** Would demonstrate bi-directional sync but needs a way to simulate "remote changes."
3. **Should shell builtins (`ls`, `cat`) work on real paths outside the vault?** Currently they can `ls /` and see the entire Pyodide virtual FS. Might want to restrict to vault directory.
4. **Should we add tab completion?** Would significantly improve UX but adds complexity.
5. **Should the scenario buttons auto-populate the terminal with the equivalent CLI commands?** Would teach users the CLI by showing what each scenario does step-by-step.
