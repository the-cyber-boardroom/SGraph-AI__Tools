## 2. Cross-Shaped Dock Overlay

### Before

The dock overlay was a 3x3 CSS grid filling the entire target panel with 5 invisible zones. The top and bottom zones spanned all 3 columns, so there was no visual cross shape. Zones were fully transparent (`border: 2px solid transparent`) until one was highlighted — meaning users saw nothing until they happened to hover over a zone boundary.

```css
/* OLD — zones invisible, top/bottom span full width */
.sgl-dock-zone--top    { grid-column: 1 / 4; grid-row: 1; }
.sgl-dock-zone--bottom { grid-column: 1 / 4; grid-row: 3; }
```

### After

The overlay now contains a `.sgl-dock-cross` container centered in the panel, with 5 small (40x40px) zone indicators arranged in a `+` pattern:

```
       [▲]
    [◀][●][▶]
       [▼]
```

Each zone has:
- **Visible border and background** (`rgba(78, 205, 196, 0.08)` base, `0.35` on hover)
- **Directional arrow icons** via CSS `::after` pseudo-elements (literal Unicode: ▲ ◀ ● ▶ ▼)
- **Scale animation** on hover (`transform: scale(1.1)`)

A `.sgl-dock-preview` element shows a dashed rectangle covering the half of the panel where the drop will land (left half, right half, top half, bottom half, or full panel for center).

### Unicode Escape Bug

The initial implementation used CSS content values like `content: '\25B2'` — octal-style escapes that are invalid in JavaScript template literals. Fixed by using the literal Unicode characters directly.

### Structure

```
.sgl-dock-overlay (absolute, covers target panel)
  ├── .sgl-dock-preview (dashed rectangle showing drop destination)
  └── .sgl-dock-cross (centered 3x3 grid of 40px cells)
       ├── .sgl-dock-zone--top    (grid-column: 2, grid-row: 1)
       ├── .sgl-dock-zone--left   (grid-column: 1, grid-row: 2)
       ├── .sgl-dock-zone--center (grid-column: 2, grid-row: 2)
       ├── .sgl-dock-zone--right  (grid-column: 3, grid-row: 2)
       └── .sgl-dock-zone--bottom (grid-column: 2, grid-row: 3)
```

The hit-detection logic (25% edge zones, center middle) is unchanged — only the visual feedback changed.

## 3. Panel Locking

### Problem

Some panels should stay fixed — a navigation tree, a top banner, a status bar. Without locking, any tab could be dragged away or have other tabs dropped onto it.

### Solution

A single `locked` boolean flag on tabs controls three behaviours:

| Behaviour | Locked | Unlocked |
|---|---|---|
| Draggable | No — `_onTabPointerDown` returns early | Yes — normal drag |
| Droppable | No — `isStackLocked()` skips in hit-test | Yes — dock overlay appears |
| Closeable | No — `_closeTab` returns early | Yes — × button works |

### Implementation Details

**Flag propagation:**
- `makeTab(tag, title, state, locked)` — 4th parameter defaults to `false`
- `addPanel({ locked: true })` and `addTabToStack(id, { locked: true })` — public API
- Serialisation: `_serializeNode` includes `locked: true` when set (omitted when false for cleaner JSON)
- Deserialisation: JSON `locked` property survives naturally through tree normalisation

**Stack-level locking:**
- `isStackLocked(stackNode)` returns `true` when ALL tabs in a stack are locked
- A stack with mixed locked/unlocked tabs still accepts drops (the unlocked tabs can be moved)

**CSS:**
- `.sgl-tab--locked` — removes grab cursor (`cursor: default`)
- `.sgl-tab--locked .sgl-tab-close` — hides close button (`display: none`)
- Single-tab titles skip the drag listener entirely when locked

**Public API:**
```javascript
layout.lockPanel(id)       // Lock a panel after creation
layout.unlockPanel(id)     // Unlock it
layout.isPanelLocked(id)   // Check lock state
```

Both `lockPanel` and `unlockPanel` trigger a full re-render to update the CSS classes and event listeners.

### Demo Update

The drag demo (`v0.1.3-drag-demo.html`) locks the Explorer tab:
```javascript
{ type: 'tab', id: 't-explorer', tag: 'div', title: 'Explorer', state: {}, locked: true }
```

Locked panels display a lock emoji and "This panel is locked" instead of the drag instruction.

## 4. Stack Sizing Fix

### Bug

When all panels in a layout were merged into a single stack (e.g. dragging one tab to center of the only other panel), the resulting stack only filled part of the available space, leaving empty dark area.

### Root Cause

When the tree is promoted from a row/column containing one child to just that child stack, the stack becomes a direct child of `.sgl-root` (a flex container). Row/column containers had `flex: 1; width: 100%; height: 100%` but `.sgl-stack` did not — so the stack sized to its content width rather than filling the parent.

### Fix

Added three CSS properties to `.sgl-stack`:
```css
.sgl-stack {
    flex: 1;        /* Fill flex parent when promoted to root */
    width: 100%;
    height: 100%;
}
```

**No side effects:** `flex` only applies to flex children (`.sgl-root`). When stacks are inside grid containers (`.sgl-row`/`.sgl-column`), the grid template controls sizing and `flex` has no effect on grid children.

## 6. Key Decisions

| Decision | Why | Alternative Considered |
|---|---|---|
| Small centered cross vs full-panel zones | Visual clarity — users see exactly where to drop | Keep invisible zones (confusing UX) |
| 40px fixed zone size | Works at any panel size; doesn't scale weirdly on tiny panels | Percentage-based (too small on small panels) |
| Single `locked` flag vs separate `draggable`/`droppable` | Simpler API; the common case is "don't touch this panel at all" | Separate flags (more granular but more complex) |
| Stack-level drop blocking (all tabs locked) | Mixed stacks should still accept drops for the unlocked tabs | Block drops if any tab is locked (too restrictive) |
| `locked` omitted from JSON when false | Cleaner serialised layouts; backwards compatible | Always include (verbose) |
