## What We Built

A browser-based Video Tools page at `tools.sgraph.ai/en-gb/video-tools/` that provides:

1. **Split** — divide a video into clips (fixed-length or custom segments)
2. **Trim** — cut from both ends, keep the middle portion
3. **Extract** — separate audio and video streams into individual files

All processing runs client-side using **FFmpeg compiled to WebAssembly** (~30 MB). No server, no upload.

### Architecture

```
Tool page (index.html)              — thin orchestrator, ~150 lines
  └─ <sg-video-splitter>            — Web Component (Shadow DOM), all UI
       └─ sg-video.js               — core module, manages FFmpeg WASM
            └─ @ffmpeg/ffmpeg@0.12.10  — FFmpeg WASM from unpkg CDN
            └─ @ffmpeg/util@0.12.1     — fetchFile utility
            └─ @ffmpeg/core@0.12.6     — ffmpeg-core.js + ffmpeg-core.wasm
```

### Setup Environment Feature

Added a "Setup Video Editing Environment" button that pre-loads FFmpeg and runs 8 health checks:

1. WebAssembly support check
2. Load FFmpeg WASM
3. Generate test clip (Canvas + MediaRecorder → 2-second WebM with audio+video)

## The Bug: Cross-Origin Worker Failure

### Error Message

```
FFmpeg WASM failed to initialize: Failed to construct 'Worker':
Script at 'https://unpkg.com/@ffmpeg/ffmpeg@0.12.10/dist/esm/worker.js'
cannot be accessed from origin 'http://localhost:10063'.
```

### Root Cause

Browsers block creating a Web Worker from a script on a different origin. FFmpeg WASM creates a Worker internally during `ffmpeg.load()`. When the FFmpeg module is imported from unpkg.com, it resolves `worker.js` relative to its own module URL — which is on unpkg.com, not on localhost (or tools.sgraph.ai).

### How FFmpeg WASM Works (when it works)

```
1. Dynamic import() loads @ffmpeg/ffmpeg from unpkg CDN
2. new FFmpeg() creates the instance (no Worker yet)
3. ffmpeg.load({ coreURL, wasmURL, workerURL }) creates the Worker:
   a. Creates a Web Worker from workerURL
   b. Worker loads ffmpeg-core.js (the Emscripten glue)
   c. ffmpeg-core.js loads ffmpeg-core.wasm (~30 MB WASM binary)
   d. Worker is ready to accept FFmpeg commands
4. ffmpeg.exec([...args]) sends commands to the Worker
5. Worker runs FFmpeg, reads/writes virtual filesystem
```

The problem is step 3a — `workerURL` must be same-origin.

### Fix Attempts

#### Attempt 1: Pass blob URLs to ffmpeg.load() ❌

Used `toBlobURL` from `@ffmpeg/util` to fetch the three cross-origin files, convert to Blob URLs (which are same-origin), and pass them to `ffmpeg.load()`:

```javascript
const { toBlobURL } = await import('@ffmpeg/util@0.12.1');

const coreURL   = await toBlobURL(`${CORE_BASE}/ffmpeg-core.js`,   'text/javascript');
const wasmURL   = await toBlobURL(`${CORE_BASE}/ffmpeg-core.wasm`, 'application/wasm');
const workerURL = await toBlobURL(`...ffmpeg@0.12.10/.../worker.js`, 'text/javascript');

await ffmpeg.load({ coreURL, wasmURL, workerURL });
```

**Result:** Still failed with the same raw unpkg URL in the error. The files were downloaded (visible in Network tab — all 200 OK) but the Worker was still created with the original URL, not the blob URL. Possible explanations:
- `toBlobURL` from the util module may not work correctly via dynamic import from CDN
- The FFmpeg constructor may resolve the worker URL at import/construct time before `load()` is called

#### Attempt 2: Custom `_toBlobURL` implementation ❌

Replaced the util module's `toBlobURL` with our own:

```javascript
async function _toBlobURL(url, mimeType) {
    const response = await fetch(url);
    const buf = await response.arrayBuffer();
    const blob = new Blob([buf], { type: mimeType });
    return URL.createObjectURL(blob);
}
```

Also moved blob URL creation **before** `new FFmpeg()` to ensure URLs are ready before any FFmpeg code runs.

**Result:** Same error. The Network tab shows all three files fetched successfully (200 OK, correct sizes: ffmpeg-core.js 30.7 KB, ffmpeg-core.wasm ~10 MB, worker.js 1.9 KB). But the Worker is still being created with the raw unpkg URL, not the blob URL.

### What the Network Tab Shows

So the files ARE being fetched. The question is why `ffmpeg.load()` ignores the blob URLs and still uses the raw CDN URL for the Worker.

## Hypotheses for the Debug Session

### H1: `ffmpeg.load()` ignores `workerURL` in this version

The `@ffmpeg/ffmpeg@0.12.10` API may have changed how it handles the `workerURL` option. The Worker URL might be computed from the module's `import.meta.url` and the `workerURL` option in `load()` may be ignored or used differently.

**To test:** Inspect the FFmpeg source at `https://unpkg.com/@ffmpeg/ffmpeg@0.12.10/dist/esm/classes.js` — look at the `load()` method to see how it uses `workerURL`.

### H2: Dynamic `import()` from CDN creates module-scoped state

When we `import()` the FFmpeg module from unpkg, the module's `import.meta.url` is on unpkg.com. The FFmpeg class may use `import.meta.url` to resolve relative paths (like `worker.js`), and this happens before our `load()` call.

**To test:** Check if `FFmpeg` class constructor or static properties reference `import.meta.url`.

### H3: The worker URL is resolved during the ES module import chain

The `classes.js` file (which defines the FFmpeg class) might contain code like:

```javascript
const WORKER_URL = new URL('./worker.js', import.meta.url).href;
```

This would resolve at import time, not at `load()` time. The `workerURL` parameter might be used for something else (e.g., the core worker, not the FFmpeg worker).

**To test:** Read the source of `classes.js` and `utils.js` from the CDN.

### H4: We need to use a different loading strategy

Instead of dynamic import from CDN, we could:

a. **Self-host** the FFmpeg files in our repo
b. **Use a different version** of @ffmpeg/ffmpeg that handles cross-origin better
c. **Create a local proxy Worker** that loads the CDN script inside itself
d. **Use the UMD build** instead of ESM (different Worker creation path)

### H5: SharedArrayBuffer / COOP/COEP headers required

FFmpeg WASM's multi-threaded mode requires specific HTTP headers:

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

Without these, SharedArrayBuffer is not available. The single-threaded core (`@ffmpeg/core` not `@ffmpeg/core-mt`) should work without them, but the Worker creation might still be affected.

**To test:** Check if the local server is sending COOP/COEP headers. If not, try adding them to the Python http.server.

## Current State of the Code

### `_doLoadFFmpeg()` (latest version)

```javascript
async function _doLoadFFmpeg(onProgress) {
    if (!isWasmSupported()) {
        throw new Error('WebAssembly is not supported in this browser.');
    }

    let FFmpeg, fetchFile;

    // 1. Import FFmpeg class from CDN
    const ffmpegModule = await import(FFMPEG_CDN_URL);
    FFmpeg = ffmpegModule.FFmpeg;

    // 2. Import fetchFile utility from CDN
    const utilModule = await import(FFMPEG_UTIL_URL);
    fetchFile = utilModule.fetchFile;

    // 3. Fetch cross-origin files → convert to same-origin Blob URLs
    const coreURL   = await _toBlobURL(`${FFMPEG_CORE_BASE}/ffmpeg-core.js`,   'text/javascript');
    const wasmURL   = await _toBlobURL(`${FFMPEG_CORE_BASE}/ffmpeg-core.wasm`, 'application/wasm');
    const workerURL = await _toBlobURL(
        `https://unpkg.com/@ffmpeg/ffmpeg@0.12.10/dist/esm/worker.js`,
        'text/javascript'
    );

    // 4. Create FFmpeg instance
    const ffmpeg = new FFmpeg();
    if (typeof onProgress === 'function') {
        ffmpeg.on('progress', onProgress);
    }

    // 5. Load with blob URLs (THIS IS WHERE IT FAILS)
    await ffmpeg.load({ coreURL, wasmURL, workerURL });

    _ffmpegInstance = ffmpeg;
    _fetchFile = fetchFile;
    return ffmpeg;
}
```

## Other Bugs Fixed in This Session

### 1. Audio Detection False Negative (Fixed)

**Bug:** "No audio stream detected" shown for videos that clearly have audio.
**Cause:** Browser APIs (`audioTracks`, `mozHasAudio`, `webkitAudioDecodedByteCount`) don't work at the `loadedmetadata` stage — they require actual playback.
**Fix:** Changed `getVideoInfo()` to assume `hasAudio = true` for any file with `duration > 0`. Added graceful error handling to `extractAudio()`/`extractVideo()` for when streams don't exist.

### 2. Missing v0.1.5 CI Files (Fixed)

**Bug:** CI pipeline failed with "i18n directory not found".
**Cause:** v0.1.5 was created with only tool pages + _common — missing i18n/, 404.html, manifest.json, robots.txt, sitemap.xml, index.html (locale redirect).
**Fix:** Copied all missing files from v0.1.4.
