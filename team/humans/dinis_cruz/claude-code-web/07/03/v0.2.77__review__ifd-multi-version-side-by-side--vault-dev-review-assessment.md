## Part 1 — The __Tools multi-version model, as it actually works

The repo has converged on five mechanisms that together give "many versions side by side, without clashing, without mass duplication". They are worth stating precisely because each one answers a different failure mode.

### 1.1 Version folders are immutable deltas

Each `vN.N.X/` folder contains **only what that version added or changed**. `tools/v0/v0.1/` has 61 version folders on disk; v0.1.0 is 88 KB (the whole site shell), v0.1.37 is 108 KB (just the infographic-gen files it touched). Nothing ever edits an old folder. The April librarian review measured the effect: 39 versions → 296 source files → flattening to 104 deployed files. History costs roughly the size of the changes, not versions × site-size.

**This is the single most important property.** Old versions are frozen *by construction* — no discipline, checksum, or gate is needed to keep them frozen, because no process ever writes into them.

### 1.2 The build layers; it never regenerates

`scripts/build_ifd_latest.py` sorts version folders ascending and copies each over the previous into a derived `_latest/` directory; later same-name files overwrite earlier ones. Crucially, the build has **no other input** — there is no live `shared/` directory outside the version chain that the build reads. A change to shared code *is itself a new version folder*. That is why rebuilding never mutates the past: building "up to v0.1.37" (`--up-to`) reads only folders ≤ v0.1.37, so any historical state is reproducible byte-for-byte from frozen inputs.

### 1.3 Version-stamped filenames let versions coexist in one namespace

Per the v1.3.0 guide: base files keep canonical names (`sg-tree.js`); surgical overrides are stamped (`sg-tree--v0.1.1.js`, double dash, full semver matching the folder name). After layering, base + every override + even a mid-chain complete rewrite (`sg-tree--v0.1.12.js`, with a guarded `customElements.define`) all coexist in `_latest/`. The HTML page is the composition root: each tool loads the chain it wants, so different tools on the same site pin to different points of the same component's history with zero file duplication. Verified on disk in `core/sg-tree/v0/v0.1/` (v0.1.0 base + `--v0.1.1` … `--v0.1.4` stamped overrides).

### 1.4 Consolidation majors are the deliberate duplication points

Duplication isn't forbidden — it's *scheduled*. A major (`v0.2.0`) merges all minors into complete, self-contained files with no cross-major dependencies; a release (`vX.0.0`) is a byte-exact copy of the last tested major ("what was tested IS what ships"). All duplication happens at these named checkpoints, on purpose, with everything re-verified together.

### 1.5 Pinned immutable URLs for external consumers

`_latest/` serves the site itself; every version folder is also served at its own URL (static.sgraph.ai) and CLAUDE.md rule 11 makes those URLs immutable. Side-by-side across *consumers* is therefore just pinning.

### 1.6 What practice added (the honest caveats)

Two findings from the v0.1.84 librarian review matter for anyone adopting this model:

- **The tools layer never used surgical JS overrides.** Every tool minor was a full-file replacement (infographic-gen was overwritten 11 times across the chain). The review's verdict: acceptable — tools are composition roots (HTML + orchestrators), not class hierarchies. **The delta rule that actually pays is at folder granularity** (don't copy the *unchanged tools*), not line granularity.
- **Drift happens without a gate.** Redundant identical copies crept into version folders, `_common/` was re-included 11 times, and consolidation was overdue at 39 minors (guideline: ~10–15). The mechanism survives sloppiness (overwrite-with-same-content is harmless) but folder bloat and loading-order complexity accumulate until a consolidation resets them.
- The per-tool fractal IFD plan (v0.2.0 architect review — components/tools/sites each with own chain + manifest DAG) was only partially executed: components and core modules got per-entity chains; `tools/` continued as one monolithic site-level chain (now 61 versions). The fractal model is the right target; the monolith shows the cost of deferring it.

## Part 2 — Assessment of the vault Dev Review (Risk Mandate, v0.4.3)

The vault's setup, restated: host `index.html` + `<iframe srcdoc>` per page; each design snapshot is a fully-inlined self-contained HTML artifact; `build.js` rebuilds **every** snapshot from the current `src/shared/*` on every build; snapshots are made by copying the previous snapshot's source tree (~10 files, mostly byte-identical).

### 2.1 The review's diagnosis is correct — and it is exactly the IFD immutability rule

Finding 3.1 ("design snapshots are not frozen") is the right catch, and the evidence given (a v0.4.2 commit mutating `v0/v0.3/v0.3.0/index.html`) is precisely the failure IFD's rules 9–11 exist to prevent. In __Tools terms: **the vault's build reads inputs from outside the version chain** (`src/shared/` is live, unversioned-relative-to-snapshots), so "rebuild" means "retroactively rewrite history". __Tools never hits this because a shared-code change *is* a new version folder, and building any version reads only folders ≤ that version (§1.2 above).

Finding 3.2 (snapshot-by-copy duplication compounding linearly) is the same disease from the other side, and it's the one __Tools' delta-folder rule ("CANNOT copy entire files just to change one method") cures structurally. The v0.1.84 review shows what the vault is heading toward if it keeps copying: the fix-must-be-applied-N-times / silently-forked-snapshots problem the vault review predicts is exactly the `_common`-duplication drift __Tools observed.

So: diagnosis confirmed, and the two findings are one root cause — **the immutability boundary is drawn around outputs when it should be drawn around the set of source inputs per version.**

### 2.2 Where I'd push back: option (a) fixes freezing but buys a new problem

The review recommends (a): freeze superseded snapshots as built artifacts, checksum them in the gate, and **delete their `src/versions/…` trees**. Against __Tools experience, three concerns:

1. **It makes old snapshots unpatchable.** IFD keeps minors within a family patchable (a fix to `window-picker.js` that should reach all three designs becomes one stamped override / one new delta). Under (a), fixing anything in a superseded design means hand-editing a 2 MB inlined HTML blob — in practice it means "never fix old designs". For a marketing site that may be acceptable; say so explicitly if choosing it.
2. **It deletes the source of record.** The built artifact is the *output* of a decision, not the decision. __Tools keeps every version's source delta forever precisely so any state is reproducible and inspectable.
3. **Checksumming is a gate to enforce what structure can give for free.** A checksum gate polices immutability; delta folders make immutability a non-event. Gates that fight the build's natural behavior get disabled under deadline pressure; structure doesn't.

### 2.3 The recommendation I'd make instead: option (d) — layered delta sources

There is a fourth option the review doesn't list, and it's the __Tools model transplanted:

- **Version the shared code into the chain.** `src/` becomes an ordered set of version folders. A snapshot folder contains only its deltas (for v0.4.2 that is literally one template file — the review says so itself). A shared-code change goes into a *new* version folder, never into a folder that already shipped.
- **`build(vX) = layer(all source folders ≤ vX) → emit one inlined HTML`.** The srcdoc/no-bridge constraint is untouched: outputs are still fully self-contained single files. Only the *inputs* become layered. Building all snapshots on every build stays fine — each build now reads only its own frozen prefix, so outputs are byte-stable (the checksum gate becomes a cheap regression tripwire rather than the enforcement mechanism).
- **Don't bother with surgical JS prototype overrides.** The vault's pages are composition roots, exactly like the __Tools tools layer, where full-file replacement per delta folder proved to be the right grain (v0.1.84 §3b). Whole-file deltas: HTML/JSON always full-replacement, JS/CSS full-replacement unless a genuinely shared component emerges — then adopt the `name--vX.Y.Z` stamped convention from IFD v1.3.0.

This solves 3.1 and 3.2 **with the same move**: no duplicated sibling files (deltas), no retroactive shipping of shared-code changes (frozen prefix), everything still rebuildable (unlike (a)), no tripled duplication (unlike (b)), no honesty-by-footnote (unlike (c)). It is also *less* build machinery than (a)'s freeze-and-checksum: the layering loop in `build_ifd_latest.py` is ~30 lines.

If the team wants the absolute minimum change instead, (a) is a defensible second choice for a small marketing site — it matches IFD's *release* semantics ("exact copy, no code changes") — but adopt it knowing old designs become read-only forever, and keep the src trees in git history rather than relying on their deletion commit being findable.

### 2.4 Point-by-point on the rest of the review

- **Host-frame + srcdoc isolation** — endorse, and worth noting it's the *other* valid answer to version coexistence. __Tools shares one page context, so it needs the single-`define()`-plus-guards discipline and stamped chains (v1.3.0). The vault gives each version a fresh window, so it needs none of that. For a design switcher, iframes are the right call; the price is the fully-inlined-artifact constraint, which the vault has already paid deliberately.
- **Two-track versioning** (design snapshots vs release marker) — endorse; it's the same separation __Tools makes between entity versions and the site/release marker, and the review is right that it just needs honest freezing semantics underneath.
- **3.3 (commit the jsdom smokes)** — strongly endorse. A gate that exists only inside a session transcript is not a gate. Cheapest item on the list, already caught two real bugs.
- **3.4 (referential-integrity gate on `library.json`)** — endorse; this is the vault's version of __Tools' `TOOL_SLUGS` lesson (v0.1.84 §2a: a tool shipped invisible because nothing validated the registry). "build.js is the validator" is the correct handoff contract.
- **3.5 (page-weight budget)** and **3.6 (backlog / FedRAMP blocker)** — sensible; no IFD angle. The per-output size print belongs in the same build-log habit as `build_ifd_latest.py`'s per-version file counts.
- **One addition the review misses: schedule consolidation.** The vault is at 3 side-by-side designs and already feeling the strain; __Tools let one family run to 39 minors before the review that called it overdue (guideline ~10–15). Whatever option lands, define now what a "major" means for the vault (e.g. v0.5.0 = new baseline; designs older than the previous major graduate from "switchable" to "archived screenshot/URL") so the switcher list and the build-input set have a bounded size by policy, not by accident.

### 2.5 Bottom line for the vault agent

The review's instincts are right and the ranking is right — 3.1 before v0.5.0 is the correct priority. Change one thing: instead of freezing *outputs* and deleting sources (option a), freeze the *input set per version* by moving `src/` to IFD-style delta folders and making the build layer them. That is the mechanism this repo has run across 61 site versions, ~30 tools, and a component library without clashes, and its two known failure modes (folder bloat, overdue consolidation) are both cheaper than the ones option (a) buys (unpatchable history, deleted sources).
