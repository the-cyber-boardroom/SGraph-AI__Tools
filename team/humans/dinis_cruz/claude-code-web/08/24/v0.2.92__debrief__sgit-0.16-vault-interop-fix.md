# Debrief — sgit 0.16 ↔ browser vault interop: review, fix, and CORS impact

**Date:** 24 Aug 2026
**Branch:** `claude/sgit-browser-vault-compat-0638mg`
**Commits:** `f73a9b8` (review + test harness), `8299931` (the fix)
**Trigger:** the graphs.sgit.ai brief — *"sgit-CLI and the browser vault modules no longer speak the same vault format"*

---

## 1. What the brief claimed, and what was actually true

The brief reported three format divergences blocking vault interop in both directions. I re-ran every
claim against `sgit-ai 0.16.0` from PyPI and the real published modules, driving a local KV store.
One claim held.

| # | Claim | Reality |
|---|---|---|
| 1 | Directory layout diverged (`bare/indexes` vs `bare/idx` vs `bare/data`) | **Real, and ours.** Three answers in our code; sgit has one. Not the thing that broke the open, though. |
| 2 | Ref-ID derivation diverged | **Real, misdiagnosed.** Derivation is byte-identical. The *input* differed. |
| 3 | CLI wraps branch keys the browser can't unwrap | **Not real.** No key-wrapping layer exists on either side. |
| — | "blocks interop in both directions" | **Not real.** Browser → CLI already worked, unmodified. |

### The actual root cause

sgit stamps a self-identifying prefix on every credential it prints, and strips it again on input:

```python
VAULT_KEY_PREFIX = 'sgit_private_vault_'
def strip_key_prefix(self, key):        # the single normalisation point for key input
    for prefix in KEY_PREFIXES:
        if key.startswith(prefix): return key[len(prefix):]
    return key
```

Nothing in `sgraph_ai_tools__static/` had ever heard of it — `grep -r sgit_private` returned **zero
hits**. `sg-vault-connect` split the pasted key on the last colon and nothing else, so
`sgit_private_vault_hunter2:k8hbjt8x` yielded the passphrase `sgit_private_vault_hunter2`. That
string went into PBKDF2 → different read key → different HMAC → different ref file ID → *"Vault not
found: named HEAD ref missing"* against a vault that was plainly there.

Everything else already matched: same salts, PBKDF2-SHA256 at 600 000 iterations, same HMAC domains
for ref / branch-index / branch-ref, same AES-256-GCM, same `tree_v1` object schema.

### Delta 3, disproved

Decrypting **every object** in a CLI-made vault with the plain read key succeeded — including
`bare/keys/key-rnd-imm-*`, which turned out to be `{type, pem}` PKI *signing* keypairs referenced
from the branch index, not content-encryption keys. Nothing needs unwrapping. The successful tree
walk is the practical proof: it read a full CLI vault while ignoring `bare/keys/` entirely.

Published as **new pinned versions only**. Not one existing version folder was modified — verified
against the staged diff, where the only `M` entries were tests and docs.

## 3. Backwards compatibility — proved, not assumed

Three independent guarantees:

1. **Additive publishing.** Every existing version folder is byte-identical. Anything pinned to
   `vault-client` v1.2.2, `sg-vault-connect` v0.1.3, tools v0.1.53 behaves exactly as before.
2. **Old key forms derive identically.** `key-compat.test.mjs` runs the same inputs through old and
   new modules and compares read key, write key, ref ID and index ID:

   ```
   pre-existing passphrase keys — vault-write v1.1.1 vs v1.1.2
     IDENTICAL   hunter2:a1b2c3d4
     IDENTICAL   pass:with:colons:deadbeef
   simple tokens
     IDENTICAL   amber-lantern-4417
   parseVaultKey on keys with no sgit prefix — v1.2.2 vs v1.2.3
     IDENTICAL   my_sgit_private_vault_x:abcd1234
   importReadKey — base64url callers unchanged
     IDENTICAL   base64url 32-byte key
   ```
2. **No orphaned data.** The `bare/idx` → `bare/indexes` move orphans nothing, because no browser
   module has ever *written* an index object — the read simply moves off a path that always 404'd.
   Routing `vault-cache` through `fileIdToPath()` is a no-op for every ID type in use except `idx-*`.

**The one edge case, stated plainly:** a vault whose passphrase genuinely *begins with*
`sgit_private_vault_` (or another sgit prefix) now derives differently. Such a vault could never have
interoperated with sgit anyway — the CLI strips the same string — and
`parseVaultKey(key, { stripSgitPrefix: false })` recovers it. Stripping only matches at the **start**,
so a passphrase merely *containing* a prefix is untouched.

## 4. CORS-enabled files this fix impacts

`tools.sgraph.ai` serves `Access-Control-Allow-Origin: *`, so **every `.js` under `/core/` and
`/components/` is a cross-origin-importable artifact**. Consumers (graphs.sgit.ai, send.sgraph.ai,
vault.sgraph.ai, workspace, the Chrome extension) import these URLs directly. Both hostnames are
affected: `https://tools.sgraph.ai/` (prod) and `https://dev.tools.sgraph.ai/` (dev).

Because the fix is additive, **no existing CORS URL changes behaviour**. What follows is the set of
*new* URLs consumers must repin to in order to get the fix.

## 5. Test harness — `sgraph_ai_tools__static/tests/interop/`

Built because nothing checked that the two implementations still agreed, and the failure mode was
silent. Answers the brief's ask 3 without needing their scripts.

| Suite | Command | Runtime | Result |
|---|---|---|---|
| Derivation parity | `node …/sgit-derivation-parity.test.mjs` | ~1s, zero deps | **24/24** (was 18/23 before the fix) |
| Key compatibility | `node …/key-compat.test.mjs` | ~1s, zero deps | old key forms unchanged |
| Full round trip | `./…/run-roundtrip.sh` | ~30s, installs sgit | both directions green |

The parity suite compares the published modules against golden vectors generated by **sgit's own
crypto** (`regenerate-vectors.py`) — read key, write key, ref ID, branch-index ID, branch refs, plus
the storage layout read from sgit's own constants. The round trip runs a real
`sgit init && sgit commit && sgit push` against a ~145-line local KV store, opens the result with the
real browser modules, then mints a vault in the browser and `sgit clone`s it. No credentials, nothing
beyond localhost. `STRIP_PREFIX=0` still reproduces the original failure, so the guard is live.

**When sgit publishes a new version:** regenerate the vectors and read the diff. Empty means the
format held; anything that moved is a change the browser modules must follow.

`sgit-derivation-parity.test.mjs` is the one to wire into CI — it is fast, hermetic, and would have
caught this.

## 6. Still outstanding

1. **A named error** instead of *"Vault not found: named HEAD ref missing"*. Note a format-version
   marker would *not* have helped here — the format never diverged, the key parsing did. The useful
   message is at the point of failure: report the ref ID that 404'd and whether a `sgit_` prefix was
   seen and stripped.
2. **A vault-level format marker** — none exists today (refs carry no schema field at all;
   `commit_v1` / `tree_v1` / `branch_index_v1` are per-object tags). Worth having, but a separate
   and cheaper conversation than the brief implied.
3. **Key families still don't meet.** `vault-init.createVault()` only mints simple tokens; sgit has no
   simple-token derivation. A browser-minted vault can therefore only be cloned **read-only** via its
   `{read_key_hex}:{vault_id}` form. Read-write both ways needs one side to gain the other's key
   family — a decision, not a bug.
4. **Read-key vault keys in the connect components.** `sg-vault-connect` / `sg-vault-manager` treat
   any `x:y` key as `passphrase:vaultId`, so a read-only `{read_key_hex}:{vault_id}` is PBKDF2'd
   rather than imported. Pre-existing gap, untouched by this fix.
5. **Doc correction, low priority.** `sg-vault-write`'s header claims its schemas match the CLI
   "exactly" — we write `commit_v2`, the CLI writes `commit_v1` with `attestations` /
   `author_key_id` / `author_signature`. Both sides read each other fine (readers need only
   `tree_id` + `parents`), so this is a comment to correct, not a break.

---

## 7. Reply to graphs.sgit.ai, in short

The blocker was never a format divergence — it was that our components didn't strip sgit's key
prefix, so they derived the wrong file IDs from a correct key. Fixed in `vault-client` v1.2.3 and
friends; once deployed, repin and the vault drawer can drop its web-format-only caveat. Their delta 3
was a misreading: `key-rnd-imm-*` are PKI signing keys and everything in a CLI vault decrypts with
the plain read key. Browser-minted vaults already cloned with sgit 0.16.0 before any of this, so
"both directions" overstated it. Against the currently published modules, removing the
`sgit_private_vault_` prefix by hand before pasting still works as an immediate workaround.
