## 1. The use case, stated plainly

> *"I have a number of videos from past presentations I have delivered, that I
> would like to capture and document the core ideas and concepts."*

That is a **corpus** task, not a video task. The unit of value is not "a document
per talk" — it is **the ideas, found across talks, with the slide and the words
that evidence each one**. A speaker who has given fifteen talks over three years
has said the same thing more than once, better each time, and the interesting
output is the set of concepts plus the best articulation of each.

Hold that thought — it changes the architecture in part 3, and it is the reason
this is not simply "narrated-review with a YouTube box".

## 2. Before building: the route that needs no new code

**For a video you uploaded yourself, YouTube Studio will give you the original
file back.** Download it, drop it on `narrated-review`, and `importVideo()`
already does the whole job today: extract the audio, cut it at its own silences,
pick the frame each spoken segment is about, transcribe, clean against the
screenshot, and produce a markdown document with images.

Pin: `tools/v0/v0.1/v0.1.66/en-gb/narrated-review/api/nr-video.js` (v0.1.4+).

**Do this first, with two or three talks, before reading further.** It costs about
$1.90 per 45-minute talk at the measured rates (part 3 §5) and it will tell you
more about what you actually need than this brief can. Specifically it will tell
you whether the frame heuristics survive *talk footage*, which is the open
question this pack exists to answer (Decision 3).

If that route works well enough for fifteen videos, the honest recommendation is:
**do not build this tool.** Build it when the manual loop becomes the bottleneck,
which it will at corpus scale, for the reasons in §4.

## 3. Why a browser cannot simply "open a YouTube URL"

This will be the first thing anyone tries, so it is worth stating exactly where
each obvious approach stops:

| Approach | What happens |
|---|---|
| `<video src="youtube.com/watch?v=…">` | Not a media file. Nothing plays. |
| `fetch()` the video or audio stream | No CORS headers. The browser refuses, and there is no proxy in this architecture by design. |
| YouTube IFrame Player + `canvas.drawImage()` | The iframe is cross-origin. You cannot read pixels out of it — not a bug to work around, a security boundary. |
| `fetch()` the `timedtext` caption endpoint | No CORS. Same wall. |
| A download helper (`yt-dlp` and similar) | Outside the browser-only architecture, and downloading is contrary to YouTube's terms except through features YouTube provides — of which Studio's "download your own video" is one. |

So there are exactly **three legitimate routes**, and the tool's shape is decided
by which of them you take:

```
  A · STUDIO DOWNLOAD          you own it → Studio gives you the mp4
     ▸ works TODAY, zero new code (narrated-review importVideo)
     ▸ best quality frames, full audio
     ▸ manual, one file at a time

  B · CAPTIONS VIA THE API     you own it → captions.download over OAuth
     ▸ the words, WITH timestamps, for FREE — no transcription spend at all
     ▸ needs a small addition to core/youtube-api (it has no captions support)
     ▸ gives you no pictures — pair with A or C
     ▸ ASR-track download is the open question (Decision 2)

  C · TAB CAPTURE              play it, record the tab (screen + tab audio)
     ▸ no download; it is screen recording of playback, as a viewer
     ▸ runs in REAL TIME — a 45-minute talk takes 45 minutes
     ▸ reuses narrated-review's entire LIVE path unchanged
     ▸ frame quality is whatever the player renders
```

**B is the interesting one**, and it is the reason this brief exists rather than
being a paragraph. See §5.

## 4. What actually earns a new tool

Route A already produces a good per-talk document. Three things it does not do,
and each is a real gap for the stated use case:

1. **Talk footage is not a screencast.** Every frame-difference metric in
   `core/sg-media-analysis` was built and tuned for a screencast, where the whole
   frame is the content. A conference recording is a **camera on a moving human**,
   often with the slides as a smaller region, a picture-in-picture, or intercut
   shots. The speaker's movement is continuous low-level change; the slide
   advancing is a localised change in one rectangle. Nothing currently masks the
   speaker out. This is Decision 3 and it is the technical heart of the pack.

2. **You are paying to transcribe words YouTube already transcribed.** Auto-captions
   exist for your videos, with timestamps, at no cost. Transcription is 27% of the
   measured per-capture spend and it is avoidable entirely (§5).

3. **Fifteen talks is not fifteen documents.** Reused slides across talks, the same
   idea explained three ways, and a concept that only becomes visible once you can
   see it recur — none of that exists inside a single-session tool. This is the
   part the user actually asked for: *"document the core ideas and concepts"*, not
   "produce fifteen transcripts".

## 5. The cost case, in measured numbers

From the real `nr-video-n16w` session (9 captures, 4m21s, `google/gemini-3.5-flash`),
pinned in `core/sg-media-analysis/.../plan.js` as `COST_BASIS`:

| | Per capture | Share |
|---|---|---|
| Transcription | $0.0130 | 27% |
| Cleanup (sends the screenshot) | $0.0343 | **73%** |
| Total | $0.0473 | |

For a 45-minute talk with, say, 40 slides:

| Route | Per talk | 15 talks |
|---|---|---|
| Studio download, transcribe + clean (today) | ~$1.89 | ~$28 |
| Captions supply the words, cleanup still runs | ~$1.37 | ~$21 |
| Captions only, no cleanup | $0 | $0 |

**But do not skip cleanup.** It is the expensive lane and it is also where the
value is, for a reason specific to this use case: **auto-captions mishear the
technical vocabulary that is written on the slide behind you.** Grounded cleanup
sends the frame with the text, and the model corrects the transcript against what
is visibly written. That exact effect was observed on the live run — speech saying
"acme vault archive" came back from the recogniser as three words and was corrected
to the on-screen string `acme-vault-archive`.

For a corpus of conference talks full of product names, library names and
acronyms, that correction is the difference between a searchable record and a
pile of near-misses. So the real saving is the 27%, not the 73%.

## 6. Name

**`talk-miner`** (URL: `/en-gb/talk-miner/`).

Says what it does to a corpus rather than to a file. *Alternatives considered:*
`talk-review` (fits the `narrated-review` / video-review family, but wrongly
suggests a single-session tool), `youtube-notes` (ties the name to one platform
when routes A and C work on any recording), `presentation-miner` (accurate,
clumsy).

## 7. Scope of v0.1

**In scope:**
- Sign in with Google, list **your own** uploads (`core/youtube-api` already does
  this — see part 3 §2).
- Fetch captions with timestamps for a video you own, and turn them into segments.
- A **region mask** so frame analysis looks only at the slide area (Decision 3),
  with `media-probe`'s filmstrip as the way to check the mask is right.
- Tab capture as the fallback ingest when no captions and no download exist.
- The corpus layer: many talks, one concept index, slides deduped across talks.
- Full SgToolApi + 3 SKILL files + manifest + boot smoke, as mandated.

**Out of scope for v0.1:** anyone else's videos; downloading video by any route
YouTube does not provide; a server-side proxy; speaker diarisation; translation;
video clipping (stills only); editing anything back on YouTube.

## 8. The one hard prerequisite

**Route A, run by hand, on three real talks.** Not as a formality — as the
measurement that decides Decisions 2 and 3. Part 5 makes it Phase 0 and it is half
a day. Every threshold in this pack is a guess until then, and this project has
now twice shipped a confident number that a real recording immediately falsified.
