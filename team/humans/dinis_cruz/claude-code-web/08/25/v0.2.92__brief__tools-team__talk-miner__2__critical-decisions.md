# Brief — Talk Miner · 2/5 Critical Decisions

Nine decisions. **PROPOSED — none of this exists yet** unless a pin is quoted.
Decisions 2, 3 and 6 are the ones that decide whether the tool is worth building;
the rest are "reuse what already works, and say so".

---

## Decision 1 — Only your own videos, and say so in the UI

**Decide:** the tool signs you in, lists **your** uploads, and works on those. It
never accepts an arbitrary URL for the caption or metadata routes.

**Why:** it is not a moral flourish, it is the design constraint that makes routes
A and B legal *and* technically possible. `captions.download` only returns tracks
for videos you own; Studio only offers the original file to the uploader. A tool
scoped to your own channel is a tool where both routes simply work. One scoped to
arbitrary URLs would need a proxy and a download path, and would be a different —
and prohibited — product.

Tab capture (route C) is the exception and needs its own framing: it records what
is on your screen, as a viewer, which is the same thing a screen recorder does.
Keep it, but do not let it become "paste any URL and we will rip it".

---

## Decision 2 — Prefer captions over transcription, and verify the ASR path FIRST

**Decide:** when a caption track exists, use it as the source of the words.
Transcription becomes the fallback, not the default.

**Why:** it removes 27% of the per-capture cost, it is faster than a model call,
and the timestamps are already there — no VAD, no segmentation, no threshold to
calibrate. The entire class of defect that has bitten this project twice
(an absolute threshold against an unknown distribution) simply does not arise when
the timings come from the caption file.

**The open question, and it is load-bearing.** `captions.list` marks
auto-generated tracks with `trackKind: 'ASR'`. Whether `captions.download` will
return an ASR track to a third-party OAuth client is **not something to assume** —
it has historically been restricted, and behaviour has changed over time. Two
outcomes, both fine, but they lead to different tools:

- **ASR downloads work** → route B is the primary ingest. The tool is mostly
  "fetch captions, pick frames, group into concepts". Cheap and fast.
- **ASR downloads are refused** → only manually-uploaded/edited caption tracks come
  back. Most talk uploads have none. Route B degrades to "use it when it is there",
  and route A or C plus real transcription carries the corpus.

**This is a fifteen-minute check with an OAuth token and one `curl`, and it must
happen in Phase 0 before anything is designed around it.** Do not write the
architecture for the outcome you would prefer.

**Caption caveats worth designing for either way.** Auto-captions have no reliable
sentence punctuation, are wrong on exactly the technical vocabulary a talk is
about, and are timed to *utterances* rather than to *topics*. So captions give you
**words with timings**, not segments — the grouping into slide-sized units is still
this tool's job (Decision 6), and grounded cleanup is still what makes them
accurate (part 1 §5).

## Decision 3 — A talk is not a screencast: mask the slide region

**Decide:** frame analysis runs over an operator-set **region of interest**, not the
whole frame. Default to the whole frame; make setting a mask a first-class, visible
step for talk footage.

**Why:** every metric in `core/sg-media-analysis` assumes the frame *is* the
content. Pin: `core/sg-media-analysis/v0/v0.1/v0.1.0/frame-metrics.js`. A
conference recording violates that in three different ways:

```
   ┌──────────────────────────────┐   ┌──────────────────────────────┐
   │                              │   │  ┌────────────────────────┐  │
   │      [ speaker, moving ]     │   │  │      SLIDE             │  │
   │                              │   │  │                        │  │
   │  ┌───────────┐               │   │  └────────────────────────┘  │
   │  │  SLIDE    │               │   │        [ speaker ] ◄ PiP     │
   │  └───────────┘               │   │                              │
   └──────────────────────────────┘   └──────────────────────────────┘
     slide is a small region            slide dominates, PiP moves

   ┌──────────────────────────────┐
   │   CAMERA CUT: speaker ↔ slide│   every cut is a false "scene change";
   │   the slide did not change   │   the slide behind it may not have moved
   └──────────────────────────────┘
```

In all three, the speaker is **continuous low-level change** and the slide advance
is **an occasional localised change**. `blockMax` — the metric that exists precisely
to catch localised change — will fire on the speaker's hands as readily as on a new
slide. The Otsu split will then place the boundary somewhere inside "human moving",
and the scene list becomes noise.

**Masking is the whole fix, and it is cheap:** crop the signature to the region
before computing any metric. Everything downstream is unchanged.

**How to set the mask without guessing:** `media-probe`'s filmstrip already shows
what was on screen across the recording (pin:
`tools/v0/v0.1/v0.1.67/en-gb/media-probe/ui/ui-timeline.js`). Drag a rectangle on a
thumbnail, and the metrics recompute for that region. Whether the mask is right
becomes visible in one look — the same principle that made the threshold slider
worth building.

**The case a mask cannot save:** intercut footage, where the camera leaves the
slide entirely. A fixed rectangle is meaningless when the shot changes. Detect it
rather than silently producing rubbish: if the masked region's own metric
distribution has no separable classes (`otsuSplit().separation` below the guard),
report *"this looks like intercut footage, a fixed region cannot work"* and fall
back to captions-only with no images. An honest refusal, exactly as `plan()`
already does.

## Decision 4 — Reuse the YouTube client that already exists; add captions to it

**Decide:** extend `core/youtube-api` rather than writing a second client.

What is already built and working (pins):

| Piece | Where |
|---|---|
| `YouTubeApi` class, v3 `channels` / `videos` / `playlists` / `playlistItems` | `core/youtube-api/v0/v0.1/v0.1.0/sg-youtube-api.js` |
| `YOUTUBE_READONLY_SCOPE`, `YOUTUBE_FULL_SCOPE` | same file |
| Browser Google OAuth, token caching, client-id override | `tools/v0/v0.1/v0.1.53/en-gb/youtube-editor/api/youtube-editor-pipeline.js`, `components/video/upload/sg-youtube-upload/.../youtube-token-cache.js` |
| Shared auth context (`getToken('google')`) | `core/auth-context/v0/v0.1/v0.1.0/sg-auth-context.js` |

**Nothing in the repo touches `captions` or `timedtext`** — verified by search. So
the new work is a **v0.2.0 of `core/youtube-api`** adding `listCaptions(videoId)`
and `downloadCaption(id, format)`, plus an SRT/VTT parser. That is a small,
well-bounded addition to a proven client, and it benefits `youtube-editor` too.

`captions.download` needs `youtube.force-ssl`, which is a **wider scope than the
readonly one**. Ask for it only when the user actually chooses the captions route,
not at sign-in — a tool that demands write scope to read a transcript deserves the
suspicion it would get.

## Decision 5 — Tab capture is a real ingest, not a hack

**Decide:** ship route C, reusing the live path unchanged.

`getDisplayMedia({ video: true, audio: true })` can capture a browser tab *including
its audio*. Play the video in a tab, share that tab, and `narrated-review`'s live
capture engine receives exactly what it already handles: a video frame source and a
continuous audio stream. Pin: `core/sg-live-capture/v0/v0.1/v0.1.0/live-capture.js`,
`tools/…/narrated-review/api/nr-capture.js`.

**Honest costs:** it runs in real time (a 45-minute talk takes 45 minutes and the
tab must stay visible); frame quality is whatever the player rendered, not the
original; and it depends on the browser's tab-audio support, which is a Chrome
strength and is weaker elsewhere. State all three in the UI rather than letting a
user discover them 40 minutes in.

**Where it earns its place:** a talk that is not yours to download and has no
usable captions, but that you are entitled to watch and take notes on. That is a
normal thing to want, and screen-recording your own viewing is the normal way to do
it.

## Decision 6 — Segments come from grouping, not from the caption timings

**Decide:** caption cues are **words with timings**, and are far too fine-grained to
be captures. Group them into slide-sized units using the *pictures*.

**Why:** a caption cue is a couple of seconds long. Forty slides in 45 minutes is a
capture roughly every 70 seconds. Treating cues as captures would produce ~1500
"captures" and a cleanup bill of $50 for one talk.

So invert the direction the existing tools run in. `narrated-review` goes
`pauses → boundaries → find the frame`. Here:

```
   slide changes (masked frame analysis)  →  boundaries
   caption cues between two boundaries    →  the words for that slide
```

This is exactly the **video-led** strategy `plan()` already models (pin:
`core/sg-media-analysis/.../plan.js`), and it is the right one here for a reason
worth stating: **a slide boundary is a real event in the talk, whereas a pause is
an accident of breathing.** When the pictures are reliable, they are the better
signal — and for a slide deck they are extremely reliable, once masked.

Fall back to `audio-led` when the mask fails and captions are all you have.

## Decision 7 — The corpus layer is the point, and it is small

**Decide:** a concept index above the per-talk documents, not a bigger document.

A concept is deliberately thin:

```js
{ id, label,                       // "risk chains", "the stop control"
  mentions: [{ talkId, captureId, tMs, confidence }],
  best: { talkId, captureId },     // the clearest articulation, chosen by a human or a model
  slides: [imageRef],              // the same idea, drawn differently across talks
  firstSeen, lastSeen }            // when you started saying it, and last said it
```

**Why this shape:** it is a *view over* captures, holding references rather than
copies, so editing a capture in the per-talk document updates every concept that
cites it and nothing goes stale. `firstSeen`/`lastSeen` is the cheapest field here
and possibly the most interesting output — it shows how an idea entered the
repertoire and how it evolved, which is not visible from any single talk.

**Slide dedupe across talks is nearly free.** The frame signatures in
`frame-metrics.js` already give a per-frame fingerprint; the same slide reused in
three talks produces three near-identical signatures. Group them and you have
"where have I used this diagram?" without a model call. This is the single highest
value-per-line feature in the pack and it falls out of code that already exists.

## Decision 8 — Extraction of concepts is a model job, and must show its evidence

**Decide:** proposing concepts is a model call over the cleaned captures; **every
proposed concept must cite the captures it came from**, and a concept with no
citations is not shown.

**Why:** this is the point where the tool could quietly start inventing. A summary
that reads well and is not anchored to a specific slide-and-sentence is exactly the
failure mode the rest of this project has spent three releases eliminating —
`plan()` refusing rather than fabricating, `gaps_in_analysis` distinguishing "not
measured" from "nothing found", `marks` flagging uncertainty rather than resolving
it. The same rule applies: a claim carries its evidence or it does not appear.

Use the existing agentic-chat plumbing rather than a new lane — `askSession` already
runs a tool-calling loop over the capture list and reports what it changed. Pin:
`tools/…/narrated-review/api/nr-chat.js`.

## Decision 9 — Where the code lives (and the lesson from v0.2.87)

**Decide:**

- `importYouTube()` becomes a **fourth ingest path inside `narrated-review`**,
  alongside live, authored and video. Same capture list, same everything after.
- `core/youtube-api` **v0.2.0** adds captions + a cue parser.
- `core/sg-media-analysis` **v0.2.0** adds the region mask.
- **`talk-miner` is only the corpus layer** — the index across talks, the slide
  dedupe, the concept view.

**Why, and this is the lesson we already paid for once:** the v0.2.87 pack proposed
`video-review` as a separate tool with a `core/sg-review-pairs` extraction to share
the back half. Dinis's question — *"shouldn't this just be a specially import mode
into our image+text captures?"* — was right, the pack was amended, and video import
shipped as a mode with no extraction and no fork.

The same reasoning applies to the ingest here and gives the opposite answer for the
corpus layer. A YouTube ingest is another door into the same room, so it is a mode.
A cross-talk concept index is genuinely *above* the capture list — it holds many
sessions at once, which no mode can — so it is a tool. Splitting on that line is
what stops this becoming a second copy of narrated-review with a YouTube box on it.
