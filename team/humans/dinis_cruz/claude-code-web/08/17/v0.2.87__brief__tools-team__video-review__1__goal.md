## 1. Why now

`narrated-review` shipped this week and does one thing: a person narrates a screen,
presses a key at each moment that matters, and out comes an ordered document of
**image-and-words pairs**. The ask now is the same artefact from the other
direction — **start from a video that already exists** and derive the pairs.

The important observation is not that this is a second tool. It is that **it is
the same tool with a different front end.**

```
narrated-review :  human picks the frame  →  model supplies the words
video-review    :  model picks the frame  ←  transcript supplies the timing
                   ─────────────────────────────────────────────────────
                            both produce the SAME ordered pairs
                   then: review · notes · reorder · insert · chat ·
                         document · PDF · zip · vault   ← identical code
```

Everything after "the pairs exist" already works and is live-verified: the review
pass, per-capture chat, the agentic chat with tools, notes, reordering,
inserting a capture in the middle, the markdown assembler, the PDF, the zip and
the vault write. That is roughly two-thirds of the finished tool, already built.

What is genuinely new is a **front end that produces pairs from a video**:
extract the audio, transcribe it with real timestamps, and choose the frame that
shows what is being talked about.

## 2. Where it fits

```
  a video file                       video-review (tools.sgraph.ai)
  (screencast, call recording,      ┌──────────────────────────────────────────────┐
   talk, demo)                      │ 1. audio out of the container                │
        │  drag & drop              │      core/video extractAudio (FFmpeg) or     │
        ├───────────────────────────►      decode-to-WAV — the publisher's router  │
        │                           │ 2. TIMED segments                            │
        │                           │      core/sg-live-capture VAD cuts at pauses │
        │                           │      → each clip's start/end is EXACT because │
        │                           │        we cut it (not a model's claim)       │
        │                           │ 3. transcribe each clip, in parallel         │
        │                           │      core/sg-transcribe (unchanged)          │
        │                           │ 4. CHOOSE THE FRAME  ← the new work          │
        │                           │      candidates per segment + settle-detect  │
        │                           │      optional model refine (multimodal)      │
        │                           └──────────────────┬───────────────────────────┘
        │                                              ▼
        │                                   ordered image+words PAIRS
        └──────────────────────────────────►  the shared review workspace
                                              (narrated-review's back half)
```

**Human use case:** drop in a 20-minute screencast, walk away, come back to a
document: each thing that was said, beside the frame that shows it. Then do what
you already do in `narrated-review` — fix a frame, add a note, drop in an extra
screenshot, reorder, chat about it, and send it as markdown, a PDF, or a vault.

**Agent use case:** `addVideo → process → getPairs → askSession('summarise the
three problems and add notes')` → `buildDocument`. A recording becomes a
readable, editable artefact with no human in the loop until the review pass.

## 3. Proposed name

**`video-review`** (URL: `/en-gb/video-review/`).

Parallel construction with `narrated-review`: same artefact noun, different
source. The pair reads as a family, which is honest, because they share most of
their code.

*Alternatives considered:* `video-digest` (vaguer about the output),
`screencast-to-doc` (too narrow — a call recording or a conference talk works
just as well), `video-walkthrough` (suggests it plays something back).

## 4. Scope of v0.1

**In scope:**
- **Ingest:** drag/drop or pick a video file (mp4/mov/m4v/webm). No upload — the
  file never leaves the browser except as audio clips and frames sent to the model.
- **Audio extraction:** the three-route ladder `video-publisher` already proved
  (FFmpeg stream-copy remux → decode-to-WAV), so a WebM/Opus screen recording and
  an iPhone `.mov` both work.
- **Timed transcription:** VAD-cut utterances with exact bounds, transcribed in
  parallel via `core/sg-transcribe`. Optional local-Whisper lane for word-level
  timestamps, no API cost.
- **Frame selection:** per segment, extract candidate frames, score them for
  stability, and pick the settled one (Decision 3). **Keep the candidates** so the
  review pass can flip between them instantly.
- **The shared workspace:** the entire back half of `narrated-review` — review,
  notes, reorder, insert, per-capture chat, agentic chat with tools, document,
  PDF, zip, SG/Send, vault.
- **Grouping:** merge adjacent segments whose frame did not change, so a
  three-sentence explanation of one screen is one pair, not three.
- Full SgToolApi + 3 SKILL files + manifest + boot smoke, as mandated.

**Out of scope for v0.1** (ranked in part 5): speaker diarisation; burned-in
subtitle/OCR reading; clipping short video excerpts into the artefact (only
stills in v0.1); YouTube/URL ingest (local files only); re-cutting the video
itself; anything that re-encodes and re-emits the video.

## 5. The one hard prerequisite

None external — no accounts, no new services. The prerequisite is **the shared
extraction landing first** (part 3, Phase R): the pair model and the whole review
workspace move out of `narrated-review` into a shared core module, and
`narrated-review` re-pins onto it with no behaviour change. Building
`video-review` by copying those files would fork the thing this pack exists to
share, and the two would drift within a month.

One practical constraint worth stating early: **long videos**. A 60-minute
recording is fine for audio (VAD cutting means each clip is seconds long, well
under the 25 MB request cap) but produces a lot of segments. Part 2 Decision 5
covers grouping and the cost ceiling, and part 5 makes "a one-hour video" an
acceptance criterion rather than an afterthought.
