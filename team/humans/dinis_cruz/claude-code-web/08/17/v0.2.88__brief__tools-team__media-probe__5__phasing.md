# Brief — Media Probe · 5/5 Phasing & Acceptance

Build incrementally — each phase lands a working, committed slice. Prefer `Edit`
patches over big `Write`s; keep every file under ~300 lines.
**PROPOSED — does not exist yet.**

---

## Phase 0 — One measurement, before writing the tool (½ day)

**This phase decides whether the rest is worth building, and it must not be
skipped.** The failure this pack responds to was found by real input, not by
design, so the first act is to look at real input.

Take the `RiskMandate — MVP — Graph Browser (5 Aug).mp4` recording (13.9 MB,
4m21s, 1280×680 — the one that produced nine 30-second captures) and, in a scratch
script, produce exactly two pictures and one table:

1. The **energy histogram** with the p20/p90 modes and both thresholds (0.01 and
   the calibrated 0.056) drawn on it.
2. The **gap-length histogram** at both thresholds.
3. The **threshold table**: for each of ~8 candidate thresholds, the gap count,
   topic-gap count and `capped` count from replaying the real `createVad`.

**Acceptance:** the three artefacts explain the nine 30-second chunks without
anyone needing the explanation. If they do not — if the histogram is unimodal, or
the topic-gap population is empty at *every* threshold — then this recording
cannot be segmented from audio at all, the v0.1.5 calibration is a partial fix at
best, and Phase 4's strategy selection becomes the primary deliverable rather than
a refinement. Either outcome is worth the half day; **guessing which one it is, is
not.**

Second Phase-0 question, same script: run all four frame metrics over the same
recording and count how many of the human-visible screen changes each one catches.
That is the entire justification for Decision 3 and it is cheap to answer.

## Phase 1 — Audio lane + timeline (1–1½ days)

- `core/sg-media-analysis`: `audio-metrics.js`, `distributions.js`.
- Tool skeleton: SgToolApi + `activate()` before UI, sg-layout shell, drop zone.
- `ui-timeline.js` audio lane; `ui-histograms.js`; draggable threshold that
  re-runs the real `createVad` live.
- `loadVideo`, `analyseAudio`, `findGaps`, `replaySegmentation`, `getProbe`.

**Acceptance:** drop the real recording in, drag the threshold, and watch the
segment count and `capped` count change in real time. Boot smoke green. The tool
is already useful at the end of this phase — it answers "will this segment?"
without a single frame being decoded.

## Phase 2 — Frame lane + strip (1½ days)

- `sampler.js` (two-pass), `frame-metrics.js` (all four), `scenes.js`.
- `ui-strip.js` before/after thumbnails with metric values; `ui-timeline.js` frame
  lanes.
- `analyseFrames`, `findScenes`, `getSceneThumb`.

**Acceptance:** on a 60-minute video the two-pass sweep completes in under two
minutes on a laptop, reports progress, and is cancellable. The strip shows every
change with the metric that fired, so a wrong detection is visibly wrong.

## Phase 3 — Alignment (½ day)

- `align.js`; `ui-align.js` with `narrated-review`'s current 2500/1200 window
  drawn over the measured distribution.
- `alignSignals`.

**Acceptance:** the measured median lead/lag is reported for the real recording,
and the correlation score is low on a deliberately mismatched control (e.g. a
talking-head video with no screen changes) — the tool must be able to say "these
signals do not line up", not just produce a number.

## Phase 4 — `plan()` + compare (1½ days)

- `plan.js` with the four strategies and per-boundary evidence; `estimateCost`
  using the measured per-capture constants ($0.0130 transcribe, $0.0343 cleanup,
  with the source session named in the code).
- `ui-compare.js`: today vs plan — captures, forced cuts, mean segment length,
  sentences split mid-clause, estimated spend.
- `getFindings()` markdown verdict.

**Acceptance:** on the real recording, `plan()` returns a non-`none` strategy whose
boundaries Dinis agrees fall where the topics change; `capped` is 0; every cut
carries evidence; and the compare table states the saving in dollars. On a
deliberately hopeless input (constant background music, no pauses, static screen)
`plan()` returns `strategy: 'none'` with a reason rather than inventing cuts.

## Phase 5 — FFmpeg lane (1 day)

- `ffmpeg-lane.js`: `silencedetect`, `select='gt(scene,N)'`, `ebur128`, with
  defensive stderr parsing and the raw log retained.
- Both lanes plotted on the same axis.

**Acceptance:** for the real recording, FFmpeg's silence intervals and scene scores
are overlaid on ours, and any disagreement is *characterised* — "ours fires 3
frames later because we sample at 4 fps" is a finding; "they differ" is not. A
parse that yields nothing reports `ffmpeg-parse`, never "found nothing". The tool
remains fully usable with the lane switched off.

## Phase 6 — `narrated-review` consumes the plan (1 day, separate commit)

Only after Phases 0–4 have been validated on **at least three** real recordings of
different character (a screencast, a call recording, a talk).

- `narrated-review` gains `importVideo({ plan })` accepting a plan from
  `core/sg-media-analysis`, and optionally computing one itself.
- Default behaviour unchanged unless the option is passed. The existing
  `calibrateVad` stays as the no-plan path.

**Acceptance:** the video smoke still passes untouched; a new assertion covers the
plan path; and re-importing the real recording with a plan produces the boundaries
Phase 4 agreed on.

## Definition of done

- Every file under ~300 lines; `api/`+`ui/` split as mandated.
- SgToolApi with `activate()` before the UI; three SKILL files; manifest with the
  full action and event catalogue; registry entry.
- Boot smoke asserting the action surface and the documented DOM ids.
- A headless analysis smoke that builds a synthetic clip in-page **and** — new
  discipline, learned twice now — one that runs over a clip with a **room-tone
  noise floor above the naive threshold**, because synthetic digital silence is
  precisely what hid both defects.
- Reality document and CHANGELOG updated in the same commit as the code.
- `getProbe()` output committed for the real recording as a fixture, so future
  changes to the metrics can be diffed against a known baseline.

## Risks, and what we do about them

| Risk | Mitigation |
|---|---|
| **The tool's heuristics become the new unexamined truth.** The likeliest failure: `plan()` gets trusted and nobody looks at the plots again. | Every `plan()` boundary carries its evidence and the UI can show it (Decision 1, 8). `gaps_in_analysis` is always present. `getFindings()` states what was *not* measured. |
| Frame sampling is too slow to be used | Two-pass, progress, cancellable, cost estimate shown *before* running (Decision 6). Phase 2 acceptance has a hard wall-clock target. |
| Thresholds tuned to one recording | Phase 6 gated on three recordings of different character. Percentile-based, not absolute, everywhere. |
| FFmpeg stderr parsing rots when a version changes | Retain the raw log; distinguish `ffmpeg-parse` from "found nothing"; the lane is never on the default path. |
| Scope creep into a video editor | Decision 2 (no model calls) and part 3 §7 (no media export) are hard boundaries. It emits numbers and a plan. |
| We build the recommender and skip the instrument | Phase order is not negotiable: 1–3 ship the instrument, 4 adds the recommender. Phase 0 comes before any of it. |

## What this pack does not claim

The four frame metrics, the percentile choices, the strategy thresholds and every
number in the illustrative `getFindings()` output are **starting points, not
findings**. The only measured facts here are the ones from the real session: the
nine 30000 ms segments, three sustained silences in 261 s, a noise floor above
0.01, $0.0130 + $0.0343 per capture, and cleanup at 72% of spend. Everything else
is a hypothesis this tool exists to test — and the tool is worth building mostly
because we currently have no way to test any of it.
