## 1. Why now — we are tuning heuristics blind, and it already cost us

On 17 August a real 4m21s screencast (`RiskMandate — MVP — Graph Browser`) was
imported through `narrated-review` v0.1.4. It produced nine captures of **exactly
30000 ms each**:

```
segment durations (ms): [30000, 30000, 30000, 30000, 30000, 30000, 30000, 30000, 20600]
sustained silences found in 261 s: [3910, 53110, 260190]        ← three. in four minutes.
p01 raw tail: "...and, but this is a fact, right? So this dig here captures the facts in"
p02 raw head: "information, so you can see that you have, uh, both the production estate..."
```

The VAD never saw a silent frame, never endpointed, and force-cut at
`maxUtteranceMs` nine times. Sentences were split mid-clause. The frame search
then dutifully matched a picture to each of those meaningless boundaries. The
document *looked* fine.

The cause was a one-line assumption: `silenceThreshold: 0.01` is an **absolute**
RMS level, and a real recording's noise floor — room tone, mic gain, AAC
compression — sits above it. v0.1.5 fixes that by calibrating from the
recording's own energy percentiles (0.056 on the regression clip, **5.6× the old
fixed value**).

**But the fix is another guess.** 20th percentile for the floor, 90th for speech,
thresholds at 15% and 40% of the range: those numbers are defensible and
untested beyond two clips. The deeper problem is not the constant — it is that
**we cannot see the data we are thresholding.** Nobody could look at that
recording and say "there are no pauses below 0.01 here" because there was nothing
to look at. Two rounds of this tool's defects have now been invisible to
synthetic tests and obvious the moment real input was used.

This pack proposes the missing instrument.

## 2. What it is

A small standalone tool that takes a video and **shows you its structure**:

```
   a video file
        │  drag & drop, never uploaded
        ▼
 ┌──────────────────────────────────────────────────────────────────────┐
 │  MEDIA PROBE  (tools.sgraph.ai)                                      │
 │                                                                      │
 │  ── AUDIO ────────────────────────────────────────────────────────   │
 │  energy over time ▁▂▅█▇▅▂▁▁▂▆█▇▃▁▁▁▂▅█▆▂▁      ← plot, not a number  │
 │  energy HISTOGRAM   ▁▂▅███▅▂▁    ▁▂▃▂▁          ← floor mode, speech │
 │                     └── noise floor ──┘  └ speech ┘   mode, and the  │
 │                                                        gap between   │
 │  gap-length histogram  120ms ███████  400ms ███  1200ms █            │
 │                        └ word gaps ┘  └ sentence ┘ └ topic ┘         │
 │                                                                      │
 │  ── VIDEO ────────────────────────────────────────────────────────   │
 │  frame difference ▁▁█▁▁▁▁▁▁█▁▁▁▁▁▁▁█▁▁▁  (4 metrics, overlaid)       │
 │  scene strip  [▓][▓][▓][▓][▓][▓]        ← every detected change      │
 │                                                                      │
 │  ── ALIGNMENT ────────────────────────────────────────────────────   │
 │  (speech onset − scene change) distribution:   -400ms ▂▅█▅▂ +1800ms  │
 │                       ← the REAL lead/lag for this speaker           │
 │                                                                      │
 │  ── WHAT WOULD narrated-review DO? ───────────────────────────────   │
 │  current:  |──30s──|──30s──|──30s──|──30s──|   9 captures, 8 forced  │
 │  proposed: |─12s─|──21s──|─8s─|────34s────|   6 captures, 0 forced   │
 └──────────────────────────────────────────────────────────────────────┘
```

Two outputs, and they must not be confused:

| | What it is | Who consumes it |
|---|---|---|
| **The instrument** | plots, histograms, distributions, per-metric numbers | a human or an agent choosing parameters |
| **The recommender** | `plan()` → proposed cut points and shot times, with rationale | `narrated-review`, behind an option |

The instrument is the point. The recommender is what makes the instrument pay for
itself, and it must never be the only way to see the data — that is how we got
here.

## 3. Efficiency is a cost number, not a feeling

The user's third ask is "be more efficient about where we take the screenshots
and where we cut the audio". From the real session, that is measurable:

| | Measured on the real 4m21s session |
|---|---|
| Captures | 9 |
| Transcription | $0.1173 total — **$0.0130 per capture** |
| Cleanup | $0.3089 total — **$0.0343 per capture** |
| Cleanup share of spend | **72%** |
| Total | $0.4262 for 4.3 minutes |

Cleanup dominates because it sends **a screenshot per capture**, and images cost
far more than the words. So the cost driver is *the number of captures*, almost
independent of how long each is.

That yields a crisp objective: **one capture per visual state, not one per clock
tick.** If the real recording had six genuine screen states rather than nine
arbitrary slices, the same document would have cost roughly $0.28 instead of
$0.43 — a third less — *and* been better, because no sentence would have been cut
in half. Quality and cost point the same way here, which is rare and worth
exploiting.

Secondary win: audio sent for transcription is currently 260.6 s of a 260.8 s
recording — essentially everything, including the silence. Cutting at real pauses
drops the dead air.

## 4. The insight the instrument is most likely to produce

Today the pipeline runs in exactly one direction:

```
audio pauses  →  segment boundaries  →  search for the frame each segment is about
```

When a recording has no usable pauses — which is the case that broke us — that
chain has no first link, and everything downstream is arbitrary. But such a
recording usually still has perfectly clear **visual** boundaries: the presenter
switched tabs, opened a panel, scrolled to a new section.

So the probable finding is that the direction should be **chosen per recording,
not fixed**:

```
pauses available     →  audio leads:  cut at pauses, then find the frame   (today)
no usable pauses     →  video leads:  cut at scene changes, then take the words
                                       spoken between them
```

A gap-length histogram tells you which you have, in one glance, before spending a
cent on a model. That decision is worth more than any threshold tweak, and it is
not implementable today because nothing measures it.

## 5. Scope

**In scope for v0.1:**
- Load a local video (mp4/webm/mov). Nothing is uploaded; **no model is called at
  all** — this tool costs nothing to run, which is the point of using it *before*
  an import.
- Audio: framewise energy, a percentile noise-floor estimate, silence/gap
  detection at several thresholds simultaneously, gap and speech-run histograms.
- Video: framewise difference under **four** metrics (part 2, Decision 3), scene
  strip, per-scene duration.
- Alignment: the measured lead/lag distribution between scene changes and speech
  onsets.
- The compare view: what `narrated-review` would do today vs what the metrics
  suggest, with the capture count and the estimated model spend for each.
- `plan()` returning cut points + shot times + a rationale string per decision.
- Full SgToolApi + 3 SKILL files + manifest + boot smoke, as mandated.
- A **core module** (`core/sg-media-analysis`) so `narrated-review` can consume
  `plan()` without importing a tool.

**Out of scope for v0.1:** OCR of on-screen text; speaker diarisation; shot-type
classification; any model call; editing or re-encoding the video; URL/YouTube
ingest; real-time analysis of a live stream.

## 6. Prerequisite

None external. One internal constraint: `core/sg-media-analysis` must be a **new,
additive** module. Do not refactor `narrated-review`'s `nr-frames.js` /
`nr-video.js` into it as part of this work — ship the instrument, validate its
numbers against real recordings, and only then re-pin the tool onto whatever
survived. Extracting first would freeze the current guesses into a shared API,
which is the exact mistake this pack exists to stop repeating.
