## 1. Why now

We hold a **Business WhatsApp account on a dedicated SIM**. Today it lives on a phone: reading, replying, and archiving all happen there, none of it is agent-drivable, and nothing connects to the SGraph stack. Meanwhile the repo already owns the two hardest ingredients of a great WhatsApp tool:

- **Voice notes.** WhatsApp `.opus` voice notes are the *headline use case* of `core/sg-transcribe` + `core/sg-audio-decode` (three-tier never-fail decode, works on every browser incl. Safari). Inbound voice notes → transcript → AI-drafted reply is a one-import feature here.
- **The browser-direct + tiny-relay architecture.** The LinkedIn Publisher brief (Decision 1) already worked through exactly the shape this needs: browser-direct API calls where CORS allows, a ~150-LOC stateless worker where the platform demands a server (WhatsApp inbound webhooks do).

Plus the assembled toolkit: SgToolApi + SKILL files for agent driving, `sg-layout` per-conversation tabs (the youtube-editor per-video pattern), `sg-llm-request` for drafted replies, `sg-send-drop` for encrypted conversation export.

## 2. Where it fits

```
                          ┌──────────────────────────────────────────────┐
 Meta WhatsApp            │ whatsapp-desk (tools.sgraph.ai)              │
 Cloud API  ◄──────────── │  send text/template/media (browser-direct)   │
 graph.facebook.com       │  conversations as tabs · 24h-window chip     │
      │                   │  voice note → core/sg-transcribe transcript  │
      │ webhooks          │  AI-drafted replies (sg-llm-request, BYOK)   │
      ▼                   │  export → SG/Send encrypted link             │
 ┌──────────────┐  poll   └──────────────────────────────────────────────┘
 │ whatsapp_relay│ ◄───────  the ONE piece that can't be client-side:
 │ (~150 LOC     │           inbound webhooks land here, held briefly,
 │  stateless    │           pulled by the browser over an authed GET
 │  worker)      │
 └──────────────┘
```

**Human use case:** open one page, see conversations as tabs, reply (typing or with an AI draft), hear/read voice notes as transcripts, know at a glance which chats are inside the free-form 24-hour window and which need a template.

**Agent use case:** a Claude agent drives `window.__tool` — `syncInbound → transcribeVoiceNote → draftReply → sendText` — turning the WhatsApp number into a supervised agent surface.

## 3. Proposed name

**`whatsapp-desk`** (URL: `/en-gb/whatsapp-desk/`).

- "Desk" says what it is: an inbox + composer, a service-desk view of one number — not a bulk-campaign tool ("blaster") and not a site-embed widget.
- Parallel construction with `youtube-editor` / `linkedin-publisher`: platform + the noun for what you do there.

---

## 4. Scope of v0.1

**In scope:**
- Connect with Cloud API credentials (BYOK: WABA id, phone-number id, system-user token) — one Accounts panel, same pattern as the publisher's.
- Send **text** (inside a 24h window), **approved templates** (anytime), and **media** (image/audio/document).
- Inbound via the relay: conversation list, per-chat tabs, delivery/read receipts, the **24-hour window indicator** per chat.
- **Voice-note transcription** (inbound `.ogg`/opus → `core/sg-transcribe`, BYOK OpenRouter) and **AI-drafted replies** with a guidance box (the metadata-gen pattern: typed action, editable output, nothing sends without a click).
- Conversation export: zip + SG/Send encrypted link.
- Full SgToolApi + 3 SKILL files + manifest + boot smoke — the mandated pattern.

**Out of scope for v0.1** (parked): template *creation*/approval flows (link out to Meta's manager), catalogs/payments/WhatsApp Flows, multi-user agent assignment, bulk sends, group-chat management, auto-replies without human confirmation, and any unofficial WhatsApp-Web automation (Decision 1 kills this deliberately).

---

## 5. The one hard prerequisite (human steps, lead time)

Unlike YouTube/the publisher, this needs **Meta-side setup before any code pays off**, and part of it has lead time measured in days:

1. A Meta Business portfolio with **business verification** (days → weeks if not already verified).
2. A Meta app with the WhatsApp product added; a **WhatsApp Business Account (WABA)**.
3. The dedicated SIM's number registered on the **Cloud API** — see Decision 2's warning: the number then *leaves the phone app*; app and API are mutually exclusive.
4. A **permanent system-user token** scoped to `whatsapp_business_messaging` + `whatsapp_business_management`.
5. At least one **approved message template** (hello_world exists by default) for out-of-window messaging.

None of this blocks writing the core module against mocks — but Phase 0's probes need items 2–4 live.
