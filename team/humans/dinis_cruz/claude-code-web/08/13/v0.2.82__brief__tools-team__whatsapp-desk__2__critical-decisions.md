# Brief — WhatsApp Desk · 2/5 Critical Decisions

Five load-bearing decisions. D1 and D2 shape everything; make them first.

---

## Decision 1 — Official Cloud API only; no WhatsApp-Web bridges

Two roads exist for a number on a dedicated SIM:

| Option | Mechanism | Verdict |
|---|---|---|
| **A. Meta Cloud API (official)** | Number registered to a WABA; REST calls to `graph.facebook.com`; webhooks for inbound | **Recommended.** Official, stable contract, template system, receipts. |
| **B. Unofficial WhatsApp-Web bridges** (whatsapp-web.js / Baileys style) | A headless session impersonating the phone's linked device | Rejected. Violates WhatsApp ToS; **ban risk for the number** (real and common); needs a long-running server session (worse infra than the relay); protocol breaks on Meta's schedule. A banned business number is unrecoverable — not a risk to take on the company's number. |

**The trade to say out loud:** registering the number on the Cloud API **removes it from the phone app** — one number lives in exactly one place. Chats on the phone don't migrate. The dedicated SIM keeps receiving the SMS verification codes (that's now its main job). If day-to-day use of the *app* on that number matters, this project changes that workflow — decide knowingly, before Phase 0 step 3.

---

## Decision 2 — Inbound needs one tiny server: the relay

Outbound is browser-shaped: Graph API endpoints take a Bearer token and (to be confirmed in Phase 0, probe 1) serve permissive CORS — same architecture as youtube-upload. **Inbound is not:** the Cloud API only delivers messages by POSTing webhooks to a public HTTPS endpoint. There is no polling API for inbound. A browser tab cannot receive webhooks. This is WhatsApp's exact analogue of LinkedIn's CORS problem, and the same Option-A answer fits:

**`whatsapp_relay` — a ~150-LOC stateless worker** (Cloudflare Worker; `sgraph_bridge/` is the repo precedent for shipping a tiny service):
- `GET /webhook` — Meta's `hub.challenge` verification handshake.
- `POST /webhook` — verify `X-Hub-Signature-256` (app secret), drop the payload into KV with a short TTL (e.g. 72 h), keyed by timestamp.
- `GET /messages?since=<cursor>` — bearer-token-authed pull; the browser polls this (visible-tab interval ~10 s).

Trust profile: the relay **transiently holds message plaintext** (Meta sends it; that's inherent to the platform — WhatsApp E2E encryption terminates at the Cloud API, a fact to state honestly in SKILL-human). It stores no Meta token, no OpenRouter key, nothing long-lived. v0.2 hardening option: the worker encrypts payloads to a public key whose private half lives only in the browser/vault — then the relay's KV is ciphertext and only the webhook handler ever sees plaintext in memory. Deferred, not designed away: it's ~30 extra lines later.

Deployment: user-deployed worker (bring-your-own, config field for URL+token) with our template — mirrors the "bring your own client ID" pattern; a managed instance on tools.sgraph.ai can come later if wanted.

**Reserved for Tier 2 (part 0 §3):** the webhook handler is written so a second consumer — the optional always-on *responder* function running the programmatic/automatic lanes — can subscribe to the same feed, and the KV namespace reserves a `config` key the desk writes (signed JSON: enabled commands, throttles, kill switch). Neither is built in v0.1; the seams are.

## Decision 3 — Credentials: BYOK in localStorage, one Accounts panel

| Credential | Key (new unless noted) | Notes |
|---|---|---|
| System-user token | `sg-whatsapp-token` | Permanent token, `whatsapp_business_messaging` + `_management` scopes only. It's a bearer secret in localStorage — same standing as the OpenRouter key; SKILL-human says so plainly and recommends a dedicated system user with minimal scope. |
| Phone-number id / WABA id | `sg-whatsapp-phone-id`, `sg-whatsapp-waba-id` | Plain ids, not secrets |
| Relay URL + token | `sg-whatsapp-relay-url`, `sg-whatsapp-relay-token` | Decision 2 |
| OpenRouter key | `sg-openrouter-mgmt-key` (existing) | Voice-note transcription + drafted replies — already set for audio-transcribe/publisher users |

## Decision 4 — Model the 24-hour window as first-class state

WhatsApp's rule: free-form messages only within 24 h of the customer's last inbound message; outside it, **approved templates only** (and template sends open billing conversations). Getting this wrong = silent API errors and confused users. So:

- Every conversation tracks `windowExpiresAt` (last inbound timestamp + 24 h, from relay data).
- The composer switches mode on it: inside → free text; outside → template picker with the free-text box disabled and a chip saying why.
- `sendText` outside the window fails **client-side first** with typed `window-expired` (before burning an API call), and the error suggests `sendTemplate`.
- Template *management* stays in Meta's UI for v0.1 — we `listTemplates` (approved only) and send; creation/approval is a Meta-review workflow that doesn't belong in the page yet.

---

## Decision 5 — AI is draft-only; the send is always human/explicitly-confirmed

Reuse the publisher's consent pattern exactly: `draftReply({ conversationId, guidance? })` (sg-llm-request, isolated transport, transcript + recent messages as context) fills the composer — **it never sends**. `sendText`/`sendTemplate` are the only sending actions, and an agent-driven `publish`-style one-shot doesn't exist here in v0.1: messaging real people warrants a per-message decision. Voice notes: `transcribeVoiceNote({ messageId })` runs the existing engine on the downloaded media blob; transcripts render under the bubble and join the draft context.

| # | Decision | Choice |
|---|---|---|
| 1 | API road | Official Cloud API; bridges rejected (ban risk); number leaves the phone app — confirm knowingly |
| 2 | Inbound | ~150-LOC stateless relay worker (webhook → KV(TTL) → authed browser poll); ciphertext-at-rest as v0.2 |
| 3 | Credentials | BYOK localStorage, one Accounts panel; minimal-scope system-user token |
| 4 | 24 h window | First-class per-conversation state; composer mode-switches; typed `window-expired` client-side |
| 5 | AI posture | Draft-only; send is always an explicit separate action |

Phase 0 probes (part 5) verify the two assumptions this rests on: Graph API CORS from the browser, and the webhook→relay→poll round-trip latency.
