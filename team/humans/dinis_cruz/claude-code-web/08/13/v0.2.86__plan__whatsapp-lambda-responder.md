**Date:** 13 August 2026
**From:** Developer agent (claude-code-web session)

## 1. What this is and what it replaces

One AWS Lambda becomes **the** live server for the WhatsApp work: it receives Meta's
webhooks, holds the secrets, sends replies, and serves the desk. It **supersedes the
Cloudflare Worker** (`whatsapp_relay/`) — that stays in the repo as a working reference,
but we consolidate on one runtime rather than maintaining two.

Crucially it keeps the **same two-route contract** the desk already speaks, so
`core/sg-whatsapp`'s `RelayClient` and the whatsapp-desk tool work against it
**with zero code changes** — only the URL in the Accounts panel changes.

```
                       ┌──────────────────── AWS ────────────────────┐
 Meta ──webhook POST──►│ Lambda (Function URL)                       │
                       │  GET  /webhook   → hub.challenge handshake  │
                       │  POST /webhook   → verify → dedupe → store  │
 Meta ◄──Graph send────│                    → M1: reply "pong"       │
                       │  GET  /messages  → desk pull (bearer auth)  │
                       │        │                                    │
                       │   DynamoDB (messages, TTL) · SSM (secrets)  │
                       └─────────────────────────────────────────────┘
 Desk browser ──────pull /messages──────────────────┘
```

## 2. Why Lambda, and why these AWS pieces

| Need | Choice | Why this one |
|---|---|---|
| Public HTTPS endpoint | **Lambda Function URL** | No API Gateway needed; free; fewer moving parts. (Add API Gateway later only if we want WAF, throttling, or a custom domain.) |
| Secrets | **SSM Parameter Store, SecureString** | Standard parameters are free; KMS-encrypted; read once at cold start and cached in module scope. (Secrets Manager is ~$0.40/secret/month — worth it only when we want rotation.) |
| Message store, dedupe, cursor | **DynamoDB, on-demand + TTL** | Free tier covers us many times over; TTL gives the same 72h auto-expiry the Worker had; conditional writes give idempotency for free. |
| Async work (later) | **SQS between two Lambdas** | Not in M1 — see §5 gotcha 3. |
| Logs | CloudWatch | With a rule: **never log message bodies** (§6). |

**Region:** `eu-west-2` (London) — closest to the numbers and the humans.

**Cost at our volume: effectively £0/month.** Lambda free tier is 1M requests, DynamoDB
on-demand free tier is far above our traffic, standard SSM parameters and Function URLs
are free. The only real spend arrives with LLM calls in M3.

## 3. Milestone 1 — ping/pong (the whole point of this plan)

**Scope, deliberately tiny:**

1. `GET /webhook` — Meta's subscription handshake (echo `hub.challenge`).
2. `POST /webhook` — verify `X-Hub-Signature-256`, dedupe by message id, store the payload.
3. **If the inbound text is `ping` (trimmed, case-insensitive) → reply `pong 🏓`** via the
   Graph API, using the token from SSM. Anything else: stored, no reply.
4. `GET /messages?since=` — bearer-authed pull, identical contract to the Worker, so the
   desk keeps working.

**Acceptance test — the thing we're actually buying:**

| # | Action | Expected |
|---|---|---|
| 1 | Meta webhook config saved | Handshake succeeds (Meta shows the subscription as verified) |
| 2 | Send `ping` from a personal phone | `pong 🏓` arrives back in < 5 s |
| 3 | Send `hello` | No reply; the message appears in the desk after a pull |
| 4 | Meta redelivers (or we replay the same payload) | Exactly **one** pong — no duplicate |
| 5 | Tamper with one byte of the signed body | 401, nothing stored |
| 6 | Point the desk's relay URL at the Lambda | Conversations render, no code change |

That single loop proves: Meta app setup, the webhook path, signature verification over the
raw body, secret retrieval + IAM, the Graph send with a live token, idempotency, and the
desk's pull path. **Everything except the intelligence** — which is exactly what we want to
de-risk first, because every later feature rides on this same plumbing.

**M1 commits us to nothing about the agent.** Whether the responder later runs as a browser
(pinned tab / headless — shapes A1/A2 from the VoiceDebrief discussion) or server-side in
the Lambda, this webhook + send + store layer is needed identically. No-regrets step.

## 4. Repo layout (mirrors the relay/bridge pattern — pure handlers, thin transport)

```
whatsapp_lambda/
  src/handlers.js        # PURE: verifyHandshake, handleWebhook, handleMessages, ping policy
  src/secrets.js         # SSM fetch + module-scope cache (one call per cold start)
  src/store.js           # DynamoDB: putMessageOnce (conditional = dedupe), listSince
  src/send.js            # Graph send (reuses core/sg-whatsapp's client)
  src/index.js           # Lambda entry: Function URL event → handler → response
  template.yaml          # SAM: function, URL, table, params, least-privilege IAM
  tests/handlers.test.mjs   # Node tests: mocked store/secrets/fetch — no AWS, no network
  tests/sign-and-post.mjs   # dev helper: POST a correctly-signed fake webhook at any URL
  README.md
```

Same shape as `whatsapp_relay/` and `whatsapp_bridge/`: **all logic in pure handlers with
injected dependencies**, transport-free, so the Node tests need neither AWS nor network.

**Reuse:** `core/sg-whatsapp`'s `sg-whatsapp-parse.js` and `sg-whatsapp-errors.js` are pure
ESM with no DOM dependency — the Lambda imports the *same* webhook parser and error mapper
the browser uses, so there is one implementation of "what a WhatsApp message is."
(If cross-tree bundling proves awkward under SAM/esbuild, fallback is a vendored copy with
a sync check in tests — decide at build time.)

## 5. The four things that actually break this (design for them now)

1. **HMAC must be over the *raw* body — and Function URLs may base64-encode it.**
   The event arrives with `isBase64Encoded: true` in some configurations. Decode to the exact
   bytes Meta sent, HMAC *those*, and do it **before** any JSON parse. This is the single most
   common cause of "the signature never matches." Our Worker already got the ordering right;
   port that discipline.

2. **Meta retries on non-200 or slow responses.** Without idempotency you get double pongs
   (and later, double LLM spend). Dedupe with a DynamoDB conditional put on `message.id`;
   a duplicate is a no-op success.

3. **Return 200 fast.** Meta's webhook timeout is short. Ping/pong inline is ~300 ms — fine.
   An LLM pass is 5–30 s — **not** fine. Target architecture for M3 is
   `webhook Lambda → SQS → worker Lambda`, and M1's handler should be written so that split
   is a wiring change (webhook handler returns a decision object; a dispatcher executes it),
   not a rewrite.

4. **Cold starts** (~300 ms, Node 22) are irrelevant for messaging, but cache the SSM read in
   module scope so we pay it once per container, not per request.

## 6. Secrets, IAM, and the trust shift

| Secret | Where | Used for |
|---|---|---|
| `META_APP_SECRET` | SSM SecureString | Webhook signature verification |
| `META_VERIFY_TOKEN` | SSM SecureString | Subscription handshake |
| `META_ACCESS_TOKEN` | SSM SecureString | **Sending** messages |
| `RELAY_TOKEN` | SSM SecureString | Desk's pull authentication |
| `OPENROUTER_KEY` (M3 only) | SSM SecureString | Responder LLM calls |

**IAM, least privilege:** `ssm:GetParameters` scoped to `/whatsapp/*`, `kms:Decrypt` on that
one key, DynamoDB read/write on that one table, CloudWatch Logs. Nothing else.

**Name the trust shift plainly** (it's flagged in brief part 0 §3): this is the first time we
hold a Meta send-capable token — and later an LLM key — on someone's behalf, server-side.
The browser-holds-everything story stops being universally true the moment M1 deploys. It's
contained (one account, one function, secrets encrypted, nothing user-facing at rest beyond
72 h of messages) but it is a real change and should be an explicit decision, not a drift.

**Logging rule:** log message **ids, types, sizes, and outcomes — never bodies**. CloudWatch
must not quietly become a plaintext archive of customer messages.

## 7. Milestones after ping/pong

| M | What | Depends on |
|---|---|---|
| **M0** | AWS account/region prep; Meta app + WABA + number registered; token minted | Human (Meta verification is the long pole) |
| **M1** | **This plan: webhook + ping/pong + desk pull** | M0 |
| **M2** | Rails: sender allowlist, daily spend cap, kill switch, rate limit — all read from DynamoDB config the desk can write | M1 |
| **M3** | VoiceDebrief responder: voice note → `runPass` → reply; text → `chatExchange` → reply; conversation ↔ session mapping; long-reply chunking | M1 + M2, plus the A1/A2 runtime decision |
| **M4** | Desk "Responder" panel: on/off, allowlist, spend today, recent auto-replies | M2 |

**M2 before M3, deliberately** — the rails must exist before anything unattended can spend
money, and they're cheap to add while the surface is still ping/pong.

## 8. Build + deploy sequence

1. `sam init`-less: hand-write `template.yaml` (function + URL + table + IAM), `sam build`.
2. Put the four secrets in SSM (one `aws ssm put-parameter --type SecureString` each).
3. `sam deploy --guided` → note the Function URL.
4. Meta app → WhatsApp → Configuration → Webhooks: callback = `<url>/webhook`, verify token =
   the SSM value, subscribe to the `messages` field.
5. Run the acceptance table in §3 from a personal phone.
6. Point the desk's relay URL at the Lambda; confirm parity.

**Local dev loop, no AWS:** `node tests/handlers.test.mjs` for logic; `tests/sign-and-post.mjs`
posts a correctly-signed fake webhook at `sam local start-lambda` (or at the deployed URL) so
the signature path is testable without waiting on Meta.

## 9. Open decisions

1. **SAM vs CDK vs Terraform.** Proposing **SAM** (one readable `template.yaml`, minimal
   tooling, matches the repo's low-ceremony style). Say if the org standardises elsewhere.
2. **Keep or retire the Cloudflare Worker?** Proposing: keep in-repo as reference, mark
   superseded in its README, stop developing it.
3. **Reply persona for M1** — plain `pong 🏓`, or echo diagnostics (message id, latency)?
   Diagnostics are more useful for a first live test; I'd do
   `pong 🏓 (msg <id-suffix>, <n>ms)`.
