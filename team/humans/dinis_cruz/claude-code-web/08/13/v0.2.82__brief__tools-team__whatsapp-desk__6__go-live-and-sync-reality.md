**Context:** the "Voice Debrief" number is live on the **WhatsApp Business App** (dedicated SIM). The tool is built for the **Cloud API**. This doc says exactly what can and cannot connect between those two worlds, and the ordered path to live.

## 1. The blunt answer on "syncing this account with this tool"

**There is no sync.** WhatsApp gives one number exactly one home: the phone app *or* the Cloud API — never both, and nothing moves between them. Every capability question about the current app account reduces to that fact:

### ❌ Cannot do (no engineering effort changes these — they're Meta's rules)

| Wish | Why not |
|---|---|
| Mirror/sync the app's existing chats into the tool | The Business App has no API. Nothing can read it except the phone (and its linked companion devices). |
| Run the app AND the tool on the same number | Registration is exclusive. Registering the number on the Cloud API **disconnects the phone app**. |
| Carry chat history across the migration | History lives on the phone. Cloud API registration starts from zero — no import path exists in either direction. |
| Make the tool a "linked device" of the app (the iPad model) | That's the unofficial companion protocol (part 0, road 2) — ToS breach, real ban risk. Ruled out for the business number, permanently. |
| Keep WhatsApp's end-to-end encryption on the API road | E2E terminates at Meta's Cloud API. "Only you and me" becomes "you, me, and Meta's cloud" — the tool's docs say this out loud. |
| Have the tool answer while no browser tab is open | Tier-1 by design. Unattended replies are the Tier-2 responder function (built later, off by default). |

### ✅ Can do (today or as soon as the checklist below completes)

| Capability | Status |
|---|---|
| **Preserve the app history before migrating** — WhatsApp's per-chat *Export Chat* (txt + media) from the phone; archive the exports (SG/Send vault is the natural home) | Manual, do **before** step ☐ D below |
| Try the full tool UX with zero credentials — `🧪 Load demo conversations` | Works the moment the branch deploys |
| After migration: send/receive, per-chat tabs, receipts, 24h-window handling, templates | Built, mock-verified; needs creds + relay |
| Voice notes → transcripts, AI-drafted replies (draft-only, Sonnet default) | Built; needs OpenRouter key |
| Use the desk from several computers | Yes — paste the same token; nothing is device-bound. (Vault credential sync is the nicer v0.2.) |
| Go back to the app later | Possible (delete the number from the Cloud API, re-verify in the app) — but API-era conversations don't follow you back either. It's a door, not a revolving one. |
| Keep Voice Debrief on the app and put the tool on a **second number** | The clean alternative if the app workflow matters — see the decision box. |

## 4. The two-number scenario (13 Aug follow-up): CAN the app number sync like an iPad?

**Yes — technically.** With two numbers (one app, one API), the app number can be linked as a *companion device* — the exact mechanism iPad/desktop/web clients use: QR-scan once, own device keys, full chat visibility with **true E2E preserved**, phone-offline tolerance (~14 days), recent-history backfill at link time (not the full archive). No official API exists for this; it means an unofficial protocol library (Baileys-class) — the part-0 road 2 we ruled out for the business number. **A dedicated second number changes the calculus: a ban costs a SIM, not the business.** This IS part 0's experiment lane, now with a concrete home:

- **`whatsapp_bridge/`** (would-be) — local Node service, `sgraph_bridge` pattern (Docker on laptop/EC2), wrapping the companion protocol; holds the session, serves chats/messages/media/send over localhost HTTP.
- The desk gains a **Bridge mode** next to Cloud API mode — the same `sg-chat-thread`/`sg-chat-composer`/`sg-conversation-list` render the app number's chats (the components were built platform-neutral for exactly this), same transcription + draft flows.
- Attractions: needs **no Meta verification** (works while the API number waits), and is *more* private than the API road — E2E terminates in YOUR bridge, no Meta cloud, no relay.
- Costs, stated plainly: WhatsApp ToS violation with real heuristic ban risk for that number (read-heavy use = lower, never zero); protocol-churn maintenance tax on the library; needs the bridge process running (phone still holds everything; the bridge re-syncs on reconnect, like an iPad); uses one of the 4 companion slots.
- Rule that keeps this safe: **the bridge number is expendable by definition** — nothing business-critical ever depends on it, and the mode is labelled as the experiment lane in the UI.

## 5. What arrives later (so this doc doesn't overpromise)

Ranked v0.2 queue (part 5): the **Tier-2 responder** (the "message the number, get your voice memo transcribed back" product — the first *automatic* behaviour, per-command allowlist + kill switch), **vault credential sync** (multi-device without token-pasting), **vault conversation archive** (durable history + relay ciphertext-at-rest). None of it changes the §1 cannot-do table — those are platform facts.
