## 1. The four roads to a WhatsApp number

| | **Cloud API** (official) | **Companion-device protocol** (unofficial — what iPad/desktop clients speak) | **BSP / managed** (Twilio, 360dialog…) | **App only** (status quo) |
|---|---|---|---|---|
| "A client like my iPad"? | No — different paradigm: number moves OFF the app to Meta's cloud | **Yes** — links as a companion device via QR; full history; app keeps working | No (Cloud API resold) | The app *is* the client |
| True E2E to the phone | No — encryption terminates at Meta's Cloud API | Yes (Signal protocol, multi-device) | No | Yes |
| Official / ToS-safe | ✅ | ❌ — **ban risk on the number** | ✅ | ✅ |
| Inbound to our code | Webhooks → needs the relay | Long-lived socket session → needs an always-on process (or a local bridge) | Their webhooks | ✋ manual |
| Templates / 24 h rule | Yes (both) | No — behaves like a normal client, no template system, no windows | Yes | n/a |
| Agent-drivable | ✅ full | ✅ full (until it breaks/bans) | ✅ | ❌ |
| Infra | ~150-LOC stateless relay | A running Node session (protocol libs are Node/websocket — not static-hostable; browser can't open the socket cross-origin) | None of ours | None |
| Cost | Free service conversations; billed template conversations | Free | Cloud API fees + BSP margin | Free |

**Answers to the memo's client-parity question directly:** yes, a "WhatsApp client like the iPad" is *technically* buildable — that's the companion-device protocol — but only via unofficial libraries, only with an always-on process, and only by accepting real ban risk on the number. **Recommendation stands (part 2, D1): the business number goes Cloud API.** The companion route is worth ONE thing: a clearly-labelled *experiment lane* on a throwaway personal number via a local `sgraph_bridge`-style Node service, to learn the protocol's shape — never on the business SIM, never deployed. Parked, not planned.

BSPs buy easier onboarding for margin + lock-in; with our relay being ~150 LOC, there's little to buy. Revisit only if Meta verification stalls badly.

## 2. The three interaction types (the memo's key distinction)

| | **Programmatic** | **Dynamic** | **Automatic** |
|---|---|---|---|
| Shape | Command in, deterministic pipeline out | Conversation with an LLM/agent in the loop | Reactive rules, no intelligence |
| Examples | "transcribe" + voice note → transcript back; PDF → summary; doc → infographic (infographic-gen pipeline); "make this a YouTube video" → video-publisher handoff | support desk with AI-drafted replies; "discuss this document with me"; agent triage | greeting / out-of-office; ack receipts; routing/labeling; daily digest template |
| Who consents | Pre-declared **per-command allowlist** — safe to run unattended | Human clicks Send (desk), or an agent holds an explicit send policy | Pre-declared rule set |
| Needs LLM key at runtime | Sometimes (transcribe/summarize: yes) | Yes | No |
| Can it run with no browser tab open? | Only in Tier 2 (below) | Desk = tab open; delegated agent = Tier 2/3 | Only in Tier 2 |
| Failure mode | Wrong output — annoying | Wrong *message to a human* — reputational | Spam loop — throttle + kill switch mandatory |

These are **different products** sharing one transport. v0.1 (parts 1–5) ships the *dynamic-supervised* desk + manual everything; the programmatic command lane is the natural v0.2 because it monetizes cleanly (below) and its consent model is simple (allowlist).

## 3. The serverless spectrum (where a server is genuinely unavoidable)

```
Tier 0 — 100% client-side, zero functions:
         outbound only (send text/template/media, browser→graph.facebook.com).
         No inbound AT ALL: webhooks are the only inbound path and a browser
         tab cannot receive them. Honest limit of the pure-static dream.

Tier 1 — relay only (the v0.1 plan):                       [dumb pipe]
         webhook → KV(TTL) → browser polls. ALL logic, keys, and LLM calls
         stay in the browser. Works only while a desk tab is open.

Tier 2 — relay + responder function(s):                    [the memo's "lambdas"]
         small function(s) subscribed to the same webhook stream run the
         PROGRAMMATIC + AUTOMATIC lanes 24/7: command allowlist, per-command
         pipelines (transcribe → reply), throttles, kill switch. Secrets
         shift: the responder needs the Meta token (to reply) and an
         OpenRouter key (for LLM commands) in ITS env — no longer
         browser-only. The desk becomes the supervision/config UI for it.

Tier 3 — server-side agent loop:                            [later, maybe]
         a full conversational agent replying unattended. Only after Tier 2's
         guardrails have history.
```

The memo's instinct is exactly right: **there is always at least one small function** the moment inbound or unattended behaviour matters — and the interesting workflows (voice-memo-in → transcript-back with nobody at a desk) are Tier 2. Design consequence, folded into part 3's architecture: the relay stays a dumb pipe, and the responder is a **separate, optional** function beside it — same webhook feed, independently killable, config pushed from the desk (a signed JSON the desk writes to KV: enabled commands, throttle, kill switch).

## 4. Auth & authorization — the memo's questions, answered

- **What does "connecting a client" look like?** No OAuth dance (unlike Google). You mint a *permanent system-user token* in Meta Business Manager once, paste it into the Accounts panel. That token IS the client authorization.
- **What gets stored, where?** Browser localStorage: Meta token, phone/WABA ids, relay URL+token, OpenRouter key (existing). Relay env: Meta *app secret* (webhook signatures) + its own bearer token. Tier 2 responder env: Meta token + OpenRouter key. Nothing anywhere else.
- **Reusable on multiple computers?** Yes — the token is a bearer credential, not device-bound: paste it on the iPad's browser and the desk works there too. Nicer path (v0.2): store the credential set in an SG/Send vault via the existing **Auth-MVP `sg-credential-store`** components — one encrypted share, every device hydrates from the vault. Multi-device parity, our way.
- **IP-locked?** Not by default (good for browser use — client IPs vary). Meta *offers* server-IP allowlisting for tokens; usable as hardening for a Tier-2 responder's token (fixed egress), pointless for the browser token.
- **Can an agent reply?** Yes — an agent drives the same `window.__tool` actions with the same token. The *policy* is ours: v0.1 = draft-only + explicit send per message; Tier 2 = pre-declared command allowlist; Tier 3 = a real send policy. Authorization here is not a Meta feature — it's our consent design.
- **How do automatic answers get connected?** Never in the browser (tab-dependence makes them unreliable) — they're the Tier-2 responder's job, configured from the desk, off by default.

## 5. Workflow catalog + monetization angles

Wide list to zoom from (★ = strong early candidates):

- ★ **Voice memo → transcript reply** (programmatic; the engine exists) — the "message our number, get your WhatsApp voice notes transcribed" micro-product.
- ★ **Doc/PDF/article → summary or infographic reply** (infographic-gen pipeline exists).
- ★ **Support desk with AI drafts** (the v0.1 dynamic lane itself).
- Send a video → **video-publisher pipeline** → YouTube link back (the two-click publish, over WhatsApp).
- Daily digest / scheduled template sends; chat → SG/Send encrypted archive link; "summarize this conversation"; inbound → vault archive.
- **Monetization shapes:** metered per-command credits (cost = OpenRouter + margin — the sg-api-secrets/spend-cap machinery from the vault work applies directly); the Tier-2 responder as a hosted per-seat product ("your WhatsApp number, with skills"); template packs per vertical. The command lane is the monetizable one precisely because it's deterministic, meterable, and consent-clear.
