# Brief — WhatsApp Desk · 5/5 Phasing & Acceptance

Build incrementally; each phase lands a working committed slice; files ≤ ~300 lines; boot smoke from Phase 1 onward (the publisher's 27-check pattern is the template).

---

## Phase 0 — Meta setup + verification probes (human + ½ day agent; days of Meta lead time)

**Human (Meta Business Manager):** business verification → app + WABA → register the dedicated SIM's number on the Cloud API (**knowing it leaves the phone app** — Decision 1) → mint the minimal-scope system-user token → confirm `hello_world` template.

**Probes (agent, from a tools.sgraph.ai console):**
1. **CORS**: `fetch('https://graph.facebook.com/v21.0/<PHONE_ID>?access_token=…')` and a template send to our own test number. 401-style errors = CORS fine, mirror youtube architecture. Blocked = route *outbound* through the relay too (Decision 2's worker grows ~20 lines; architecture otherwise unchanged).
2. **Relay round-trip**: deploy the worker template, point the app's webhook at it, message the business number from a personal phone, time webhook→KV→poll.
3. **Media fetch**: download a voice-note media id browser-side with the Bearer header (CORS on `lookaside.fbsbx.com` URLs — if blocked, media proxying joins the relay).

Probe results get written into part 2 as amendments before Phase 1 (the linkedin-probe precedent).

## Phase 1 — Core module + outbound MVP (1 session)
`core/sg-whatsapp` (api/parse/events/errors, injectable fetch, Node-mock tests like `tests/audio-transcribe-smoke.js`), tool scaffold, Accounts panel, `connect`, `sendTemplate` + `sendText` to our own number. **DoD:** template message arrives on a real phone, sent from the page; boot smoke green.

## Phase 2 — Relay + inbound + conversations (1–1.5 sessions)
`whatsapp_relay/` worker (+ its own tests: signature check, challenge echo, TTL), poll loop, `wa-state`, `<sg-conversation-list>`, per-chat tabs with `<sg-chat-thread>`, receipts, 24 h window chip + composer mode-switch (`<sg-chat-composer>`). **DoD:** message the business number from a personal phone → bubble appears without reload → free-text reply arrives back; window flips to template-only at expiry.

## Phase 3 — Voice notes + drafts + media (1 session)
`wa-voice` (fetchMedia → decode → transcribe, cached per message), `wa-draft` (thread+transcript context, guidance box), `sendMedia` with dropzone, `downloadMedia`. **DoD:** real WhatsApp voice note → readable transcript under the bubble → drafted reply in the composer → sent on click; costs visible.

## Phase 4 — Export + polish (½–1 session)
`exportConversation` zip + sg-send-drop, unread/ordering polish, empty states, mobile stack. **DoD:** a conversation lands as an SG/Send encrypted link.

## Phase 5 — Skills + reality + registry (½ session)
3 SKILL files (SKILL-human states plainly: relay sees message plaintext transiently; token in localStorage; number-vs-app exclusivity), manifest event catalogue, boot smoke finalized, reality doc Parts 1–3, registry + landing card, CHANGELOG.

**Total: ~5 agent sessions** + Meta verification lead time (starts now, runs in parallel).

## Acceptance criteria for v0.1

| # | Criterion | Verification |
|---|---|---|
| 1 | Inbound message → visible bubble ≤ ~15 s, no reload | live, phone in hand |
| 2 | Free-text reply inside window; template-only outside, enforced client-side with typed `window-expired` | live + mock test |
| 3 | Voice note → transcript → AI draft → human-clicked send, end-to-end on one screen | live |
| 4 | No sending action fires without an explicit `sendText`/`sendTemplate` call — drafts never auto-send | code review + smoke |
| 5 | Relay holds no Meta token; signature-verified webhooks only; browser pull is bearer-authed | relay tests |
| 6 | Full agent run via `window.__tool` (part 4 script) headless | Playwright |
| 7 | Boot smoke: zero boot errors, all ~24 actions Promise-returning, panels render | CI-able smoke |
| 8 | Transcription/draft costs visible per message + rolled up | live |
| 9 | All new files ≤ ~300 lines; engines in `core/`; components js/html/css split | review |
| 10 | Reality doc updated in the same commits | review |

## Dependencies + risks

- **Meta business verification latency** (days–weeks) — start immediately; everything through Phase 1 proceeds on mocks meanwhile.
- **Number ↔ app exclusivity** (Decision 1) — a workflow change, not a code risk; needs an explicit human OK.
- **Conversation-based pricing** — template sends outside the window open billed conversations; surface a per-send hint in v0.1, real cost tracking later.
- **CORS unknowns** (Graph outbound, media CDN) — Phase 0 probes; worst case the relay grows into a thin authenticated proxy for those calls (the LinkedIn Option-A fallback, already designed).
- **History durability** — v0.1 history = in-memory + 72 h relay TTL; the vault-backed encrypted archive (and relay ciphertext-at-rest) is the flagged v0.2.

## What's deliberately out of v0.1

Template creation/approval UI, catalogs/payments/Flows, group management, bulk/broadcast, auto-send agents, multi-seat assignment, unofficial bridges (never), managed relay hosting.
