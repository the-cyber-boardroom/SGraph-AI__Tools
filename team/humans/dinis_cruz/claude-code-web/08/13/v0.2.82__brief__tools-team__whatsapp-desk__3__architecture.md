# Brief — WhatsApp Desk · 3/5 Architecture

Follows the house pattern end-to-end: engine as a versioned `core/` module (the Phase-R lesson — extract first, tools stay thin), reusable UI as `SgComponent` web components (js + html + css sibling files), tool as `api/{state,events,pipeline,api}.js` + one `ui/ui-*.js` per panel, manifest-loader boot, sg-layout shell, every file ≤ ~300 lines.

---

## New core module — `core/sg-whatsapp/v0/v0.1/v0.1.0/`

```
sg-whatsapp-api.js      # Graph client class WhatsAppApi(token, phoneNumberId):
                        #   sendText(to, body), sendTemplate(to, name, lang, components?),
                        #   sendMedia(to, {type, mediaId|link, caption?}), uploadMedia(blob),
                        #   getMediaUrl(id) + fetchMedia(id) (auth'd blob download),
                        #   markRead(messageId), listTemplates(wabaId)
                        #   fetchImpl injectable (Node-testable, mock-friendly)
sg-whatsapp-relay.js    # RelayClient(url, token): pull(sinceCursor) → normalized
                        #   inbound events; verifies nothing (server did); pure fetch+parse
sg-whatsapp-parse.js    # webhook payload → { conversationId, from, type, text?, mediaId?,
                        #   timestamp, receipts } normalizer (shared by relay client + tests)
sg-whatsapp-events.js   # frozen WA_EVENTS constants (the public contract)
sg-whatsapp-errors.js   # HTTP/Graph error codes → typed { code }: auth-invalid,
                        #   window-expired (Graph #131047), rate-limited, template-unapproved,
                        #   recipient-invalid …
manifest.json           # exports declared
```

Pure JS, no DOM, dependency-injected fetch — the same shape that made `core/sg-transcribe` reusable and mockable. **No LLM/transcribe code in here**: voice-note transcription and drafting compose the *existing* cores at the tool layer.

## New components (SgComponent, js/html/css sibling files, shadow DOM)

| Element | What it renders | Deliberately platform-neutral |
|---|---|---|
| `<sg-chat-thread>` | message bubbles (in/out), timestamps, receipt ticks, media slots, an under-bubble transcript slot | Yes — takes a normalized message array + slots; nothing WhatsApp-specific in its contract. Future consumers: vault agent chats, linkedin comment threads. |
| `<sg-chat-composer>` | text box, attach button, send; a `mode` attribute (`free` \| `template-only`) that swaps in a template picker + reason chip | Yes — template picker is a slot/config |
| `<sg-conversation-list>` | conversation rows: name/number, snippet, unread dot, 24h-window chip | Mostly — chip label configurable |

Reused as-is: `sg-layout` (per-chat tabs = the youtube-editor per-video pattern), tool-api trio, `upload-dropzone` (attachments), `sg-llm-request`/`sg-llm-events` (drafts), `core/sg-transcribe` + `core/sg-audio-decode` (voice notes), `sg-send-drop` (export), `sg-openrouter-key-stats`, `sg-pipeline-steps` — not needed here (no linear pipeline; it stays in the publisher).

## Relay — `whatsapp_relay/` at repo root

Cloudflare Worker template + README (the `sgraph_bridge/` precedent: small service, own tests, deploy docs). Endpoints per Decision 2; KV binding with TTL; secrets: Meta app secret (signature check), relay bearer token. **No Meta token ever reaches the relay** — it only receives what Meta pushes and hands it to the authed browser.

## Flow of one inbound voice note (all existing machinery after the relay)

```
Meta webhook → relay KV → wa-pipeline poll → wa-state + wa:message:in
  → ui-chat-tab renders bubble → [📝 Transcribe] → sg-whatsapp-api.fetchMedia
  → core/sg-audio-decode (opus→WAV if needed) → core/sg-transcribe → transcript
  → [✨ Draft reply] → wa-draft (thread + transcript context) → composer filled
  → human reads, edits, clicks Send → sendText → receipt ticks update
```
