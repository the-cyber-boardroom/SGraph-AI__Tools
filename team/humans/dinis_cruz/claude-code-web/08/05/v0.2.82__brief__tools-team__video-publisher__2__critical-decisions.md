# Brief — Video Publisher · 2/5 Critical Decisions

Six decisions are load-bearing. Each is stated with the code-verified facts behind it and a recommendation. Everything referenced here exists today unless marked PROPOSED.

---

## Decision 1 — Compose modules, don't orchestrate tabs

Two ways to "consolidate":

| Option | Description | Verdict |
|---|---|---|
| **A. Handoff chain** | Add `__sgYtHandoff`-style producers/receivers to video-tools and audio-transcribe so the four existing tools pass the blob along. | Rejected. Still four page loads, four UIs, four mental contexts. The handoff global (`window.opener.__sgYtHandoff`) is consume-once and dies if the producer tab closes — chaining it three deep is fragile. Saves clicks, not context switches. |
| **B. One tool composing `api/` modules** | New tool imports the existing DOM-free pipeline modules directly; blob never leaves the page. | **Recommended.** This is exactly how `live-transcribe` was built from `audio-transcribe`'s `api/` modules (documented as the sanctioned pattern in `library/api/v0.1.93__audio-transcribe__integration-and-capabilities.md`). |

The one handoff we keep is the **entry**: video-recorder → video-publisher (one hop, same pattern as the shipped video-recorder → youtube-editor button).

---

## Decision 2 — Audio routing: three routes, tried in order

The transcription engine takes an *audio* blob ≤25 MB (`MAX_ITEM_BYTES`, `audio-transcribe/api/api-source.js:15`), and OpenRouter receives it base64-inlined in a chat completion. Three code-verified routes to get audio from a video:

| Route | Mechanism | Cost | When it works |
|---|---|---|---|
| **1. Native separate audio stream** | video-recorder already records a dedicated `audio/webm;codecs=opus` blob whenever `recordingMode` is `combined+separate` or `separate` (`recorder-pipeline.js:453-455`). Include it in the handoff payload. | Free — zero processing | Fresh recordings only; requires the recorder to run in all-streams mode |
| **2. FFmpeg remux** | `extractAudio()` in `core/video/v1/v1.0/v1.0.0/sg-video.js:598-639` — `-vn -c:a copy` → `.m4a`. Stream copy, no re-encode, WORKERFS-mounted so multi-GB inputs are fine. | ~30 MB WASM download first run (cached) | AAC-in-MP4 imports (the common case for downloaded recordings) |
| **3. Decode → WAV** | `core/sg-audio-decode` `decodeNative()` — `decodeAudioData` accepts mp4/webm blobs' audio tracks → 16-bit WAV via `encodeWav()`. This is what audio-transcribe already does for every `.opus` file. | In-memory decode; WAV is bulky (~2 MB/min mono 16 kHz) | WebM/Opus sources, where route 2's m4a container can fail (`-c:a copy` can't put Opus in m4a — the sg-video health check explicitly skips this case) |

**Recommendation:** pipeline tries 1 → 2 → 3 automatically and reports which route it used. The 25 MB cap is then a *duration* cap, not a video-size cap — a 4-minute recording's audio is ~4 MB either way. If the audio still exceeds 25 MB (roughly >1.5–2 h), fail with a typed error in v0.1; segmented transcription is a v0.2 item.

## Decision 3 — Cut `sg-video` v1.0.2 to heal the version fork

Code-verified fork: video-tools pins **v1.0.0** (WORKERFS mounting — multi-GB safe; no `convertToMp4`), video-recorder and heic-converter pin **v1.0.1** (adds `convertToMp4`, but regressed to heap-copy `writeFile` — ~2 GB ceiling). Neither version has both.

**Recommendation:** cut `core/video/v1/v1.0/v1.0.2/` = v1.0.1's exports + v1.0.0's WORKERFS `_mountInputFile`. Video-publisher pins v1.0.2. Existing tools stay pinned where they are (immutable versions rule); migrating them is optional follow-up.

## Decision 4 — Recording stays in video-recorder; the bridge is the handoff

Embedding the 9-mode recorder (camera warm-up, compositors, background-safe tickers — ~3,000 lines of `api/` + `ui/`) into the publisher would double v0.1's scope for zero new capability.

**Recommendation:** add a **"Publish"** button to video-recorder next to the existing "Send to YouTube Editor". Same protocol, richer payload:

```js
window.__sgYtHandoff = { blob, audioBlob /* route-1, when present */,
                         suggestedTitle: name, filename, sourceTool: 'video-recorder', timestamp };
window.open('/en-gb/video-publisher/', '_blank');
```

Two cleanups while there: (a) video-recorder currently **inlines** the producer code (`ui-recording-tab.js:226-238`) instead of importing `sg-youtube-handoff.js` — move the helper to a shared location (`components/` or the publisher's `handoff/`) and import it from both; (b) register the handoff as an API action (`sendToPublisher`) — today "Send to YouTube Editor" is UI-only, invisible to agents.

Drag-drop import covers every other entry (old recordings, files from other machines).

## Decision 5 — One Accounts panel for three credentials

The pipeline touches three independent credentials, each with a shipped storage pattern:

| Credential | Storage key (existing) | Used for |
|---|---|---|
| OpenRouter API key | `localStorage['sg-openrouter-mgmt-key']` | transcription + metadata generation |
| Google OAuth client ID + token | `localStorage['sg-youtube-client-id']` + `sg-auth-tokens` provider key | upload (default client ID ships in youtube-editor's pipeline) |
| SG/Send access token (optional) | `localStorage['sgraph-send-token']` | optional encrypted share of the video/transcript |

**Recommendation:** one collapsed "Accounts" panel showing three status chips (● connected / ○ not set). Reuse the exact storage keys so credentials configured in the existing tools are **already present** here — a user who has used audio-transcribe and youtube-editor signs into nothing new. Token provider key for OAuth: `video-publisher` (own cache, youtube-editor pattern; the fact that youtube-editor and youtube-upload already run two parallel caches is a known consolidation debt — don't add coupling, just follow the pattern).

## Decision 6 — Metadata generation is a typed action, not a chat

Today the description is produced by free-typing into audio-transcribe's Chat tab and copy-pasting the answer. The engine already has the right primitive: the headless `ask({text, model?, context?})` action (`audio-transcribe-api.js:169-190`) — system prompt carries the transcript, user message carries the instruction.

**Recommendation:** `generateMetadata()` wraps `ask` with a fixed instruction that demands **strict JSON**: `{title (≤100 chars — YouTube's snippet limit, already enforced by the upload core), description, tags[]}`. Parse, validate, drop into three editable form fields. Keep a small free-text "regenerate with guidance" input for tone adjustments ("more emojis", "shorter") — that's the chat use-case, scoped to one field. Default model: `google/gemini-3.5-flash` (the engine's default). Cost surfaces through the existing per-generation cost lookup.

## Decision 7 — YouTube session longevity (the 1-hour annoyance)

The ~1 h lifetime is **Google's fixed access-token TTL** for the Google Identity Services token client (implicit grant) — it cannot be lengthened, and this flow never issues refresh tokens. What we *can* change is how often the human sees a consent popup:

**v0.1 — proactive silent refresh (client-only, ships in this tool):**
- Today's youtube-editor pattern is *reactive*: it waits for a call to hit an expired token, then tries a silent re-grant (`prompt: ''` — popup-free while the browser's Google session is alive and consent was granted), then falls back to the popup.
- The publisher makes it *proactive*: while connected, schedule a silent re-grant at ~T-5 min, and always run one immediately before `upload()` so the single-PUT starts with a full hour on the clock. Result: in Chrome with a live Google session, the user authenticates **once per browser session**, not once per hour — the popup only reappears when the silent path genuinely fails (signed out of Google, or Safari/ITP third-party-cookie blocking).

**v0.2 — real long-lived sessions (needs one tiny piece of infra):**
- Weeks-to-months sessions require the **authorization-code flow with a refresh token**. Google only issues those to confidential clients — the code exchange and refresh calls need the client secret, which must not live in the browser. That means a small stateless worker (the exact shape already designed as Option A in the LinkedIn Publisher brief, Decision 1): browser holds the tokens, worker only performs exchange/refresh.
- Caveat worth knowing before building it: while the Google Cloud OAuth consent screen is in **"Testing"** status, refresh tokens expire after 7 days; "In production" status (with the `youtube` scope verified) is what makes them long-lived.

**Recommendation:** ship v0.1 with proactive silent refresh — zero infra, removes most of the day-to-day annoyance. Park the refresh-token worker as a shared v0.2 item (it would serve youtube-editor, youtube-upload, and linkedin-publisher alike).

## Decision summary cheatsheet

| # | Decision | Choice |
|---|---|---|
| 1 | Consolidation mechanism | One tool composing existing `api/` modules (live-transcribe pattern) |
| 2 | Audio routing | native stream → FFmpeg remux → decode-to-WAV, automatic |
| 3 | sg-video fork | cut v1.0.2 = v1.0.1 exports + v1.0.0 WORKERFS |
| 4 | Recording | stays in video-recorder; richer handoff + shared helper + API action |
| 5 | Credentials | one Accounts panel, reuse the three existing storage keys verbatim |
| 6 | Metadata | typed `generateMetadata` → strict JSON → editable form; guided regenerate |
| 7 | Token longevity | v0.1: proactive silent refresh (T-5 min + before upload); v0.2: refresh-token worker |

Known constraint accepted for v0.1 (inherited, documented, not fixed here): the upload is a **single-PUT** resumable session with no Content-Range chunking — `core/youtube-upload` itself flags chunking as its v0.2. With Decision 7's refresh-before-upload, that's fine for the target use case (5-minute demos, ~50–100 MB).
