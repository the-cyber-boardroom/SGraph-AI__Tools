## 1. Why now

Publishing a recorded video to YouTube today works end-to-end — but it takes **four separate tools, ~20+ clicks, two file downloads, two file re-uploads, and one copy-paste across tabs**, all to move bytes that never needed to leave the browser:

1. **video-recorder** — record, download the MP4 to disk.
2. **video-tools** — re-upload the MP4, Extract Audio Only, download the `.m4a`.
3. **audio-transcribe** — re-upload the `.m4a`, transcribe, open Chat, ask for a YouTube description, copy the text.
4. **youtube-editor** — re-upload the same MP4 a third time, paste the description, set title/privacy, upload.

Every stage is already client-side, already same-origin on tools.sgraph.ai, and already built as reusable modules. The blob could flow through the whole pipeline **in memory** — the friction is purely that the stages live in four different pages with no shared state.

The research behind this brief (see §6 of part 5 for sources) code-verified every stage. Nothing new needs inventing; this is a **composition** project, and the repo already has the precedent for it: `live-transcribe` is a minimal tool built by re-importing `audio-transcribe`'s `api/` modules into a new shell.

## 2. Where it fits in the workflow

```
TODAY (4 tools, 2 downloads, 2 re-uploads, 1 copy-paste)

┌───────────────┐  ⬇ mp4  ┌─────────────┐  ⬇ m4a  ┌──────────────────┐  copy   ┌────────────────┐
│ video-recorder │ ──────→ │ video-tools │ ──────→ │ audio-transcribe │ ──────→ │ youtube-editor │
│   (record)     │  disk   │ (extract)   │  disk   │ (transcribe +    │  paste  │ (re-upload mp4,│
└───────────────┘         └─────────────┘         │  describe in chat)│         │  publish)      │
                                                  └──────────────────┘         └────────────────┘

PROPOSED (1 tool, blob stays in memory)

┌───────────────┐  window.__sgYtHandoff  ┌─────────────────────────────────────────────┐
│ video-recorder │ ─────────────────────→ │ video-publisher                             │
│  "Publish →"   │      (or drag-drop     │ audio → transcript → title/description/tags │
└───────────────┘       an existing mp4)  │ → review → upload → YouTube URL             │
                                          └─────────────────────────────────────────────┘
```

The **human use case**: stop recording, click "Publish", review the generated title + description, click Upload, copy the YouTube URL. Target: **≤5 interactions from stop-to-URL** (vs ~20+ today).

The **agent use case**: one chain of `window.__tool.*` calls — `importFile → transcribe → generateMetadata → connectYouTube → upload` — or the single one-shot `publish()` action. Fully drivable headlessly via Playwright, like the other SgToolApi tools.

## 3. Proposed name

**`video-publisher`** (tool slug + URL: `/en-gb/video-publisher/`).

Reasoning:
- Parallel to `linkedin-publisher` — "publisher" already means "takes finished content to a destination" in this repo's naming.
- Not `youtube-publisher`: the pipeline (audio → transcript → metadata) is destination-agnostic; YouTube is v0.1's only destination, but the LinkedIn Publisher brief already anticipates the same transcript/metadata feeding an org post. The destination step is a pluggable tail.
- Not `youtube-editor` v2: the editor's videos/playlists/analytics management surface stays where it is. This tool is 100% the publish pipeline, nothing else.

## 4. Scope of v0.1

**In scope:**
- Receive a video blob via the existing `window.__sgYtHandoff`-style handoff from video-recorder (new "Publish" button there — ~15-line change), or via drag-drop/file-pick of an existing MP4/WebM.
- Get the audio: use the recorder's native separate audio stream when present, else extract/decode in-browser (three-route strategy — part 2, Decision 2).
- Transcribe via the existing OpenRouter chat-completion path (curated models, BYOK, cost tracking).
- Generate YouTube metadata (title ≤100 chars, description, tags) from the transcript in one click — editable before upload.
- Google sign-in + direct browser→YouTube resumable upload (existing core modules).
- Result panel: YouTube URL + copy button.
- Full SgToolApi registration + three SKILL files + manifest — mandatory pattern.

**Out of scope for v0.1** (parked for v0.2+):
- In-tool recording (video-recorder stays the capture surface; the handoff is the bridge — Decision 4).
- Trim/split before publish (sg-video-editor's job; its handoff into this tool is planned there already).
- Thumbnail generation/upload, chapters from timestamps (current transcription returns plain text, no timestamps).
- Other destinations (LinkedIn post referencing the YouTube URL — natural v0.2 tail, brief already exists).
- Videos/playlists/analytics management — stays in youtube-editor; link out.

## 5. Why this is *easier* than LinkedIn Publisher was

Unlike the LinkedIn brief, there are **no unknown external constraints**:

1. **No CORS question.** Every network call this tool makes (OpenRouter, googleapis.com upload, GIS) is already made browser-direct by a shipped tool today.
2. **No new OAuth flow.** Google Identity Services + `sg-auth-tokens` caching is shipped and tested in youtube-editor; this tool reuses the same provider pattern.
3. **No new upload protocol.** `core/youtube-upload` (resumable single-PUT with XHR progress) is shipped.

The genuinely new work is: the audio-routing decision tree (Decision 2), a small `sg-video` core version merge (Decision 3), the metadata-generation prompt contract (Decision 6), and the UI that strings the steps into one page.
