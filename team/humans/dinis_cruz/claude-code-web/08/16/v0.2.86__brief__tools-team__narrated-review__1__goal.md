## 1. Why now

The source brief's reframe decides the whole design: this is **not a worse screen recording, it is a cheaper way to author a structured document**. The two expensive parts of making a model understand a screen recording — choosing which frames matter, and pairing each frame with the words about it — are done at capture time, for free, by a person pressing a key while narrating. The keypress does three jobs: it **marks a screenshot**, it **bounds an audio segment**, and it **creates the alignment** between the two. The alignment is the product.

And the repo already owns almost all of the machinery:

- **Continuous audio with lookback is a solved problem here.** The Live engine built for audio-transcribe (`api/live-capture.js` + `api/live-vad.js`) already captures continuous PCM via AudioWorklet at 16 kHz with a **pre-roll buffer** (default 300 ms), cuts clean WAV utterances, transcribes them **in parallel**, and reassembles by sequence number. The source brief's "one practical catch" — people speak before they press, so the keypress must be a marker over a continuous recording, not a start/stop switch — is precisely the architecture this engine already implements for VAD boundaries. We swap "VAD decides the boundary" for "the keypress decides the boundary (VAD assists)".
- **Screen frames are cheap.** `core/sg-capture` v0.1.1 acquires the `getDisplayMedia` stream (with the background-tab-safe ticker already battle-tested in video-recorder); a screenshot at the instant of a press is one `drawImage` from the live `<video>` to a canvas.
- **Transcription is an extracted core.** `core/sg-transcribe` v0.1.0 (OpenRouter chat `input_audio` path, isolated per-request transport, typed errors, deferred exact cost) is already consumed by three tools.
- **Screenshot-grounded cleanup is one multimodal call.** `sg-llm-request` v0.1.6 already sends images + text in one message (infographic-gen's attachment path). The 6 Aug finding stands: a text-only corrector roughly **doubled** the word error rate; improvement came from information beyond the text. For screen narration the screenshot is unusually good extra information, because the words most likely to be misheard are written on the screen being discussed.
- **The outputs are assembled from parts we have:** `core/markdown`, JSZip session bundles (audio-transcribe's pattern), `components/send-drop` encrypted send, and `core/vault-write` v1.1.1 for the vault-as-home follow-up.

What is genuinely new is small and specific: the **marker loop**, the **pair data structure**, the **cleanup call's prompt + rolling summary**, the **document assembler**, and the **review pass**. That matches the source brief's estimate: a small amount of new code over a large amount of existing capability.

## 2. Where it fits

```
 the screen being reviewed                narrated-review (tools.sgraph.ai)
 (another window / tab)                  ┌──────────────────────────────────────────────┐
      │  getDisplayMedia video           │  continuous mic PCM (AudioWorklet, pre-roll) │
      ├────────────────────────────────► │  keypress/click = MARKER, never start/stop   │
      │                                  │    → screenshot (canvas grab at the instant) │
 mic  │  continuous audio                │    → segment bounds (VAD-snapped, adjustable)│
      ├────────────────────────────────► │    → THE PAIR { image, words }               │
                                         │  per-segment transcribe  (core/sg-transcribe)│
 OpenRouter (BYOK) ◄──────────────────── │  cleanup: raw + screenshot + rolling summary │
   audio → raw text                      │  assemble: ordered markdown + images         │
   image+text → clean text               │  export: zip · SG/Send link · vault (v0.2)   │
                                         └──────────────────────────────────────────────┘
```

**Human use case:** share a screen, talk through it, tap the marker key each time the thing on screen matters. Press send at the end. Out comes an ordered markdown document — heading, image, the words about that image — that any assistant can read directly, with no video to upload and no cleanup pass owed. The review pass (adjust a boundary, fix a phrase, redo a cleanup) is optional polish, not required repair.

**Agent use case:** a Claude agent drives `window.__tool` — `getPairs → getDocument` to consume a finished review; or headlessly `addRecording → markAt(t) → transcribeAll → cleanAll → buildDocument` to run the same pipeline over an imported narration. The artefact itself is the agent interface: markdown + images is what every assistant handles.

**The acceptance test, adopted literally from the source brief:** *"in the end, I want to just be able to press send and not worry about it."* If a session requires editing before it can be sent, the tool has not worked. Phase 3's plain document of screenshots + raw transcripts is the first thing measured against that bar.

## 3. Proposed name

**`narrated-review`** (URL: `/en-gb/narrated-review/`).

- "Narrated" names the input; "review" names the artefact and the workflow (reviewing a screen, a design, a PR, a document — and producing a review).
- Parallel construction with the media family it joins: `video-recorder`, `audio-transcribe`, `live-transcribe`, `video-publisher`.
- Deliberately **not** "screen-recorder-something": the source brief is explicit that this is a document-authoring tool whose input happens to be narration.

## 4. Scope of v0.1

**In scope:**
- **Capture session:** screen share (frame source only — no video file is recorded), continuous mic audio (PCM ring with pre-roll + a continuous saved take, the Live-engine pattern), marker via keypress/click in the tool window.
- **The pair pipeline:** marker → screenshot at the press instant + VAD-snapped segment boundary → per-segment parallel transcription (`core/sg-transcribe`, BYOK OpenRouter) → **screenshot-grounded cleanup** (raw text + screenshot + rolling summary → cleaned text with `[unsure: …]` marks, never silent resolution).
- **Both transcripts persist** — raw and cleaned, the corpus's source-and-derived discipline. Raw is never overwritten.
- **The document assembler:** one ordered markdown file, one section per pair (heading, image reference, cleaned text; raw text in a collapsible appendix), images alongside.
- **Review pass:** pairs listed image-beside-text; boundaries draggable on the audio timeline; text editable; per-pair re-transcribe / re-clean.
- **Export:** session `.zip` (markdown + images + WAV segments + continuous take + raw transcripts + session.json) and `sg-send-drop` encrypted link.
- Cost everywhere: per-segment transcribe + cleanup cost, session roll-up, spend cap (`sg-transcribe`'s existing cap machinery).
- Full SgToolApi + 3 SKILL files + manifest + boot smoke — the mandated pattern.

**Out of scope for v0.1** (parked, ranked in part 5): the **vault as home** (persistent sessions, memory across reviews — `core/vault-write` makes this v0.2, not v0.1), **annotation** (vector drawing kept + flattened composite shipped), **screenshot-only mode** (same pipeline, different capture front end), a **Document Picture-in-Picture floating marker button** (Chrome-only; Decision 3 explains why v0.1 lives without it), pause-detector-suggested boundaries beyond the VAD snap, and any video recording of the screen.

## 5. The one hard prerequisite

None on the platform side — unlike whatsapp-desk there is no external account setup; OpenRouter BYOK is the only credential and every target user of this tool already has one configured (it is shared via `localStorage['sg-openrouter-mgmt-key']` with the other media tools).

The prerequisite is **interaction honesty**, and it must be settled in Phase 0 before UI work: **the marker key only reaches the tool if the tool's window has focus.** A person narrating usually has the *reviewed* window focused, so "press any key while working in the other app" is not implementable in a browser. Decision 3 resolves this (narrow side-window layout + click-anywhere marker + VAD assist), and Phase 0 probes the two escape hatches (Document PiP, `preferCurrentTab`). This is the narrated-review equivalent of the source brief's lost-first-second catch: found now on paper rather than in the first real session.
