# Brief — Narrated Review · 2/5 Critical Decisions

Nine decisions, each resolved. The source brief (v0.33.59) settles the conceptual ones; the repo's code reality settles the mechanical ones. Everything here is **PROPOSED — does not exist yet** unless a pin is quoted.

---

## Decision 1 — No video file is ever recorded

| Option | Mechanism | Verdict |
|---|---|---|
| **A. Frame-grabs only** | `getDisplayMedia` stream stays live for the session; a screenshot is one `drawImage` at each press; the stream is never fed to a MediaRecorder | **Recommended.** The source brief's whole argument: the video is the expensive, redundant artefact. The pairs ARE the product. |
| B. Record video too | `core/sg-recorder` alongside, video kept for provenance | Rejected for v0.1. Cost, size, and it re-introduces the thing the tool exists to avoid. If provenance demands it later it is one config flag away (the engine exists). |
| C. Record video, sample frames after | The naive pipeline | Rejected. Sampling loses the pairing; the person already chose the frames for free. |

**The trade to say out loud:** with no video there is no way to recover a moment the narrator failed to mark. The continuous **audio** take (Decision 2) is kept precisely so the words are never lost; a missed *image* is genuinely gone. That is acceptable — it is what "the person selects the frames" means.

## Decision 2 — Continuous audio; the keypress is a marker, never a switch

| Option | Mechanism | Verdict |
|---|---|---|
| A. Keypress starts/stops a MediaRecorder | One file per segment | **Rejected.** The source brief's practical catch: people begin speaking before they press. This design loses the first seconds of nearly every segment. |
| **B. Continuous PCM ring + marker timestamps** | The Live-engine pattern (audio-transcribe `api/live-capture.js`): AudioWorklet PCM @16 kHz mono with a pre-roll ring, **plus** a continuous MediaRecorder take of the whole session | **Recommended.** Markers are timestamps over one timeline; segment audio is sliced from the ring; boundaries are adjustable in review because they are data, not file edges. |
| C. Pure VAD segmentation (live-transcribe as-is) | Utterance = boundary | Rejected as the primary — VAD boundaries have no alignment to screenshots, and the alignment is the product. Kept as the **assist** (below). |

**Boundary semantics (the part to get right):** segment *N* runs from `snap(press N)` to `snap(press N+1)` (last segment ends at session stop). `snap(t)` = the nearest VAD-detected silence in the window `[t − lookbackMs, t]` (default `lookbackMs: 4000`, reusing `live-vad.js`'s energy state machine); if no silence is found, fall back to `t − 2000` fixed. Segments may **overlap** — a few duplicated words beat lost ones, and the cleanup pass sees the seams. Both the raw press time and the snapped bounds are stored, so review can always re-snap.

## Decision 3 — Where the keypress lands (the focus problem)

A browser page cannot see keys pressed in another window. The narrator's focus is usually on the *reviewed* window. This is this tool's lost-first-second-class catch, resolved on paper now:

| Option | Mechanism | Verdict |
|---|---|---|
| **A. Narrow side window; any key or click in it is the marker** | The tool's capture view is designed to live in a ~320 px window beside the reviewed screen; the whole window is one big MARK target (`keydown` + `click` anywhere) | **Recommended for v0.1.** Zero platform risk. Imposes the "glance and tap" rhythm the source brief already accepts as the price of alignment. |
| B. Document Picture-in-Picture floating button | Chrome 116+ `documentPictureInPicture` — an always-on-top mini window hosting the MARK button | **Phase-0 probe, ship if trivial.** The genuinely good UX; Chrome-only, so an enhancement, never the requirement. |
| C. `preferCurrentTab` + in-page overlay | Only works when reviewing a page you can inject into | Rejected as the general mechanism (`sg-capture.getScreenStream` already supports the flag; may return as a same-tab mode later). |
| D. Browser extension global hotkey | Real global keys | Out of scope — different deployment surface entirely. |

**VAD assist as the safety net:** while capturing, silences detected by `live-vad` are recorded as *suggested* markers (no screenshot — the screen state at an unmarked moment was not chosen by anyone). In review they show as faint ticks a user can promote. This also answers the source brief's open question "is the keypress the only boundary?" — no, but only the keypress mints a pair.

## Decision 4 — Screenshot mechanics

Grab at the instant of the press: `drawImage(screenVideoEl, …)` onto a canvas sized from the track's `getSettings()`, then `toBlob('image/png')`. Portable (every browser that has `getDisplayMedia`), synchronous with the gesture, and the tool window is focused at press time so there is no background-throttling concern. `ImageCapture.grabFrame()` is Chromium-only and buys nothing here. PNG, full track resolution, no scaling — the consumer is a model reading text off the screen.

## Decision 5 — Per-segment transcription = `core/sg-transcribe` v0.1.0, unmodified

Slice the PCM ring → `encodeWav` → `buildTranscribeMethods` with the isolated transport, **in parallel** (segments are independent), reassembled by `seq` — exactly live-transcribe's contract. Default model `DEFAULT_MODEL` from `audio-models.js`; per-pair model override allowed. Typed errors (`key-invalid`/`budget-exceeded`/`key-exhausted`/`rate-limited`), deferred exact cost, and the session **spend cap** all come free with the module.

## Decision 6 — Screenshot-grounded cleanup, and it marks rather than resolves

The strongest idea in the source brief, with corpus evidence: a **text-only** corrector on noisy recogniser output was measured roughly doubling the word error rate (≈31% → ≈65%, 6 Aug brief), while the fix was information beyond the text — and the memos themselves rendered the product's own name three wrong ways, every one correctable from a screenshot of the page under discussion.

Per segment, one multimodal call (`sg-llm-request` v0.1.6 — image + text in one message, the infographic-gen attachment path):

| Sent | Why |
|---|---|
| Raw transcript of this segment | The thing being corrected |
| **The pair's screenshot** | The words most likely misheard are written on it |
| The rolling summary (Decision 7) | Session vocabulary — fixes a term the first time and keeps it fixed |
| NOT: previous screenshots, NOT: full prior transcript | Quadratic / linear growth; the source brief's cost table says no |

Contract: return strict JSON `{ cleanText, marks: [{ span, note }], summary }` — where the model is unsure it **marks** the span for the review pass instead of choosing confidently (the two-model transcription discipline). A parse failure = `clean-parse` error, raw text stands, pair flagged. **The raw transcript is never overwritten** — both persist, in every export (source-and-derived, applied everywhere else in the corpus).

## Decision 7 — The rolling summary rides the cleanup call

The cleanup response's `summary` field IS the update — one call does correction + summary maintenance, no second request. Seeded empty; capped by prompt at ~1,500 characters ("compress, keep names, terms, and spellings established so far"); stored on the session and included in every export. Cleanup therefore runs **sequentially in pair order** (the summary is order-dependent) — transcription stays parallel; cleanup is the cheap, ordered second lane.

## Decision 8 — Output: markdown + images primary; zip export; vault is the home, later

Decided by who reads it (14 Aug constraint: many agents cannot fetch arbitrary URLs):

| Form | Reaches a model? | v0.1 |
|---|---|---|
| **Markdown + images, ordered, one section per pair** | Always | **Primary — `buildDocument()`** |
| Session `.zip` (document + images + WAVs + take + raws + session.json) | Always, if uploaded | Yes — the audio-transcribe `audio-zip.js` pattern |
| SG/Send encrypted link | If it can fetch | Yes — `components/send-drop` v1.0.0 |
| Vault with read key (sessions, memory, index) | If it can fetch | **v0.2** — `core/vault-write` v1.1.1 exists; the home deserves its own slice, not a corner of this one |

No new container format — a folder shape (`review.md` + `images/` + `audio/` + `raw/` + `session.json`) that is identical inside the zip and, later, inside the vault.

## Decision 9 — Credentials, storage, privacy

- **BYOK OpenRouter** via the shared `localStorage['sg-openrouter-mgmt-key']` — same key the other media tools use, zero re-entry. Spend cap honoured across transcribe + cleanup.
- **Session state is in-memory** for v0.1 (a reload loses an unfinished session; export early, export often — `downloadZip` works mid-session). VFS/IndexedDB persistence is parked with the vault slice.
- **Privacy is the sharp edge:** screenshots of a working screen routinely contain names, emails, tokens. Two rules: (1) nothing leaves the browser except audio segments and — **only when cleanup is enabled** — the pair's screenshot, both solely to OpenRouter under the user's own key; (2) the capture panel carries a persistent "screenshots are sent to your model during cleanup" notice with a per-session toggle (`cleanup: 'grounded' | 'text-only' | 'off'`, default grounded). A redact affordance (`core/image` `redact()`) in the review pass is the v0.2 companion.
