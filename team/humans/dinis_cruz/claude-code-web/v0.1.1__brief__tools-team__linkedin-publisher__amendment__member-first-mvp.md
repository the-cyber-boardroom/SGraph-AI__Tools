# Brief — LinkedIn Publisher · Amendment v0.1.1: Member-first MVP

**Date:** 26 April 2026
**Supersedes (partially):** sections of briefs 1/5 + 2/5 + 5/5
**Trigger:** App created on linkedin.com/developers (`The Cyber Boardroom | Publishing`, Client ID `78tdt0b9upct3u`). The Products catalog gates the org-posting scopes behind **Community Management API** which requires manual LinkedIn approval (days–weeks). The **member** scopes are grantable today.

---

## What changed

The original briefs targeted **org-page posting** as the v0.1 scope. Brief 1/5 §4 explicitly listed *"Personal-profile posts"* as out of scope on the assumption that `w_member_social` was first-party-only. That assumption is **wrong** — `w_member_social` is publicly grantable via the *Share on LinkedIn* product, and we already have it.

So instead of waiting for Community Management API approval before any code, we ship a **member-first MVP** that:

- Uses what we already have (OIDC + `w_member_social`).
- Lets the user (Dinis personally, then anyone with the tool) publish to **their own LinkedIn timeline** end-to-end.
- Proves the entire architecture (PKCE + popup + postMessage + token cache + Posts API contract) on a smaller surface.
- Is **upgradable** to org-posting by flipping a `mode` switch, once Community Management API approval lands.

---

## New v0.1 scope (replaces brief 1/5 §4)

**In scope for v0.1 (member mode):**
- OAuth connect via OIDC (`openid profile email`) + posting (`w_member_social`).
- Show the signed-in user's profile (name + avatar from `/v2/userinfo`).
- Create **text post** for the user's own profile.
- Create **article-link post** (URL + title + description + thumbnail).
- List recent posts authored by the user.
- Read a specific post's details.

**Deferred to v0.1.1 (org mode, unblocked when Community Management API approval lands):**
- Org admin discovery (`r_organization_admin`).
- Org page picker.
- Post + read as the org (`r_organization_social` + `w_organization_social`).
- The YouTube hand-off (Phase 4 in brief 5/5) ships against member-mode first.

**Still out of scope** (unchanged from brief 1/5):
- Image / video / document uploads.
- Update existing post.
- Analytics, scheduling, multi-locale variants.

## Architecture impact

The `mode` is a **single constructor argument** on the core module:

```js
new LinkedInApi({
  clientId: '78tdt0b9upct3u',
  mode: 'member',           // 'member' | 'organization'
  authorUrn: undefined,     // ignored when mode='member' (derived from OIDC sub)
  proxyUrl: undefined,      // depends on Phase 0 CORS findings
})
```

**Member mode endpoints:**

| Operation | Endpoint | Author URN |
|---|---|---|
| Identify user | `GET https://api.linkedin.com/v2/userinfo` (OIDC) | n/a |
| Create text/article post | `POST https://api.linkedin.com/rest/posts` | `urn:li:person:{sub}` (from OIDC) |
| List recent posts | `GET /rest/posts?q=author&author=urn:li:person:{sub}` | filter |
| Read single post | `GET /rest/posts/{urn-encoded-post-id}` | n/a |

**Org mode endpoints (later):** identical shape, swap `urn:li:person:{sub}` for `urn:li:organization:{id}`. That's why the `mode` switch fits cleanly — endpoint contract is the same; only the URN changes.

## Why this is the right call

1. **Eliminates the LinkedIn-approval blocker** from the critical path.
2. **First-class dogfood from session 2** — Dinis can use the tool the day after Phase 2 ships, not "after we get approved someday."
3. **Same architecture** — when org scopes arrive, the diff is one boolean + the org picker component. No throwaway code.
4. **Lower-risk Phase 0** — the CORS reality might still bite, but we'll discover it against endpoints we already have access to, not endpoints we're waiting on.
