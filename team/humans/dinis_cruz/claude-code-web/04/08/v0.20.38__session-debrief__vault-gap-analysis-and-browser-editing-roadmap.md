## Gap Analysis: sgit Spec vs tools.sgraph.ai

### Crypto & Key Derivation — INTEROP VERIFIED

| Aspect | CLI (sgit-ai) | Browser (tools.sgraph.ai) | Match? |
|---|---|---|---|
| Read key derivation | PBKDF2-SHA256, salt=`sg-vault-v1:{vaultId}`, 600k iters | Same (sg-vault-client.js) | **Yes** |
| Write key derivation | PBKDF2-SHA256, salt=`sg-vault-v1:write:{vaultId}` | Same | **Yes** |
| Ref file ID | HMAC-SHA256(readKey, `sg-vault-v1:file-id:ref:{vaultId}`)[:12] | Same | **Yes** |
| Branch index ID | HMAC-SHA256(readKey, `sg-vault-v1:file-id:branch-index:{vaultId}`)[:12] | Same | **Yes** |
| Object ID | `obj-cas-imm-{SHA256(ciphertext)[:12]}` | Same (sg-vault-write.js, sg-send-sim.js) | **Yes** |
| AES-256-GCM wire format | 12-byte IV + ciphertext + 16-byte tag | Same (sg-crypto.js) | **Yes** |
| Simple token derivation | PBKDF2-SHA256, salt=`sgraph-send-v1`, 600k iters | Same (sg-send-crypto.js) | **Yes** |
| Structure key (HKDF) | HKDF-SHA256(readKey, info=`sg-vault-v1:structure-key`) | **Not implemented** | No — needed for encrypted metadata |
| Per-branch ref ID | HMAC-SHA256(readKey, `sg-vault-v1:file-id:branch-ref:{vaultId}:{branchName}`)[:12] | **Not implemented** | No — needed for multi-branch |

### Self-Describing IDs — MOSTLY DONE

| ID Type | Status |
|---|---|
| `obj-cas-imm-*` (blobs, trees, commits) | Done |
| `ref-pid-muw-*` (named HEAD) | Done |
| `ref-pid-snw-*` (clone branch) | Not implemented |
| `idx-pid-muw-*` (branch index) | Derived but not fully used |
| `key-rnd-imm-*` (PKI keys) | Not implemented |

### Object Model — KEY GAPS

| Feature | CLI | Browser | Gap |
|---|---|---|---|
| Sub-tree model (one tree per directory) | **Yes** — each folder is its own tree object | **No** — flat tree with full `path` strings | **CRITICAL** — vaults created by browser have different format than CLI |
| `name_enc` (encrypted file/folder names) | **Yes** — all metadata encrypted | **No** — plaintext `path` field | **CRITICAL** — browser can't read CLI vaults correctly |
| `size_enc`, `content_hash_enc` | **Yes** | **No** | Required |
| `message_enc` (encrypted commit messages) | **Yes** | Partial (sg-send-sim has it) | Small gap |
| commit_v2 with `parents[]` array | **Yes** | **Yes** (sg-vault-write) | Match |
| ref_v1 with `commit_id` | **Yes** | **Yes** | Match |

### Branch Model — NOT IMPLEMENTED

| Feature | Status |
|---|---|
| Named branch (server, shared key) | Partial — single "main" branch, no key pair |
| Clone branch (local, unique ECDSA key pair) | Not implemented |
| Push: re-encrypt clone → named key | Not implemented |
| Pull: re-encrypt named → clone key | Not implemented |
| Branch switching | Not implemented |
| ECDSA P-256 commit signing | Not implemented |

## Roadmap: Full Browser Vault Editing

The goal: **interact with vaults from the browser as easily as from `sgit` CLI**. This means:

### Target Capabilities

| # | Capability | What it means |
|---|---|---|
| 1 | **Open vault / Pull** | Enter vault key → derive keys → fetch ref → commit → root tree → render files. On refresh, re-pull to get latest. |
| 2 | **Edit documents** | Click a file → decrypt → edit in textarea/editor → stage change in memory |
| 3 | **Add documents** | Upload or create new files → stage in working copy |
| 4 | **Create clone branch** | Generate ECDSA P-256 key pair → store private key in localStorage/IndexedDB → register clone branch in vault |
| 5 | **Create commits** | Scan staged changes → hash → build sub-trees → create signed commit → update clone branch ref |
| 6 | **Push** | Compute delta → re-encrypt clone→named key → batch upload → update named branch ref |
| 7 | **Pull** | Fetch named ref → walk commit chain → detect new commits → re-encrypt named→clone key → update working copy |
| 8 | **Visualise commits & trees** | Graph view: ref → commit chain. Tree view: expand folders on demand. Diff view: compare commits. |

### Implementation Phases

#### Phase 1 — Sub-tree model + encrypted metadata (P0, prerequisite for everything)

**Goal:** Browser reads and writes vaults in the same format as the CLI.

| Task | Module | Effort |
|---|---|---|
| Add HKDF-SHA256 structure key derivation | sg-vault-client v1.2.0 | Small |
| Implement `name_enc` encryption/decryption | sg-vault-client v1.2.0 | Small |
| Implement `size_enc`, `content_hash_enc` | sg-vault-client v1.2.0 | Small |
| Rewrite tree building: one tree per directory, `name_enc` only | sg-vault-write v1.1.0 | Medium |
| Implement sub-tree traversal (on-demand folder loading) | sg-vault-client v1.2.0 | Small |
| Update vault browser components to decrypt `name_enc` | sg-vault-tree, sg-vault-viewer | Small |
| Drop plaintext `path`/`name` fields from tree entries | sg-vault-write v1.1.0 | Small |

**Verification:** `sgit clone loft-most-6888`, edit a file in browser, `sgit pull` from CLI — round-trip works.

## Critical Technical Reminders

- **HKDF vs PBKDF2**: The CLI uses PBKDF2 for read/write keys (our browser code matches). HKDF is used only for the structure key and per-file key derivation. We need to add HKDF support via Web Crypto API (`crypto.subtle.deriveBits` with HKDF algorithm).
- **Object ID = SHA256 of ciphertext** (not plaintext) — matches what sg-send-sim and sg-vault-write already do.
- **Clone branch private key NEVER leaves the device** — store in IndexedDB, never push to server.
- **Named branch key is stored encrypted in the vault** (in `bare/keys/`) — decrypt with vault read key.
- **Re-encryption on push/pull**: objects are decrypted with one key and re-encrypted with the other. This is the core of the two-layer branch model.
