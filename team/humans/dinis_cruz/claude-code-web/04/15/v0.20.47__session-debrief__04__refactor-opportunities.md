### Phase 1: Cache + Tree Model (2–3 sessions)

The two foundational modules that everything else depends on.

#### 1a. `core/vault-cache/v1/v1.0/v1.0.0/sg-vault-cache.js`

Cache API integration for immutable blocks. Wraps fetch with read-through caching.

```
Exports:
  cachedFetch(apiBase, vaultId, objectId)  → ArrayBuffer
  warmCache(apiBase, vaultId, objectIds[]) → void
  clearCache(vaultId)                      → void
  getCacheStats(vaultId)                   → { hitCount, missCount, sizeBytes }
```

Design from vault team's `sg-vault-object-store.js`:
- Cache name: `sg-vault-blocks`
- Key: `https://sgvault/{vaultId}/bare/data/{objectId}`
- Guard: only cache IDs matching `-imm-` segment
- `data.slice(0)` copy semantics
- `typeof caches === 'undefined'` graceful degradation
- Storage quota errors silently swallowed

Then integrate into `sg-vault-client.js` — either v1.3.0 (new minor) or as an opt-in wrapper so existing consumers aren't affected.

#### 1b. `core/vault-tree-model/v1/v1.0/v1.0.0/sg-vault-tree-model.js`

Persistent in-memory tree with STUB/LOADED folder states.

```
Exports:
  createTreeModel()                             → treeModel
  treeModel.loadFromCommit(commitData, treeData) → void
  treeModel.loadSubTree(path, treeData)          → void
  treeModel.needsLoading(path)                   → boolean
  treeModel.getNode(path)                        → node | null
  treeModel.insertFile(folder, name, entry)      → void
  treeModel.removeEntry(folder, name)            → void
  treeModel.renameEntry(folder, old, new)        → void
  treeModel.moveEntry(srcFolder, name, destFolder) → void
  treeModel.buildTreeEntries(node)               → entries[]  (preserves stubs)
  treeModel.getRoot()                            → root node
```

The critical invariant from the vault team: `buildTreeEntries()` must pass through unloaded stubs with their original `_tree_id` intact.

**Deliverable:** Two new core modules. Warm-cache vault open drops from ~6 s to ~820 ms. Tree model ready for mutation and commit operations.

### Phase 3: Mutations + Sync (2–3 sessions)

#### 3a. `core/vault-mutations/v1/v1.0/v1.0.0/sg-vault-mutations.js`

All 9 mutations operating on the tree model, plus commit logic.

```
Exports:
  addFile(treeModel, folder, name, content, uploadFn)      → commitResult
  updateFile(treeModel, folder, name, content, uploadFn)   → commitResult
  removeFile(treeModel, folder, name, commitFn)             → commitResult
  renameFile(treeModel, folder, oldName, newName, commitFn) → commitResult
  moveFile(treeModel, srcFolder, name, destFolder, commitFn) → commitResult
  createFolder(treeModel, parent, name, commitFn)           → commitResult
  removeFolder(treeModel, parent, name, commitFn)           → commitResult
  renameFolder(treeModel, parent, oldName, newName, commitFn) → commitResult
  moveFolder(treeModel, srcParent, name, destParent, commitFn) → commitResult
```

Each mutates the tree model then calls a `commitFn` that handles tree-entry building, encryption, and ref update.

#### 3b. `core/vault-session/v1/v1.0/v1.0.0/sg-vault-session.js`

The two-branch orchestrator.

```
Exports:
  createSession(apiBase, vault, treeModel, cache)  → session
  session.open()            → void  (reads named + clone refs, loads root tree)
  session.commit(message)   → void  (advance clone ref only)
  session.push()            → void  (named ref → clone HEAD, 1 PUT)
  session.pull()            → boolean (fast-forward clone HEAD → named HEAD)
  session.getAheadCount()   → number
  session.getBehindCount()  → number
  session.isWritable()      → boolean
```

#### 3c. New components

- **`sg-vault-sync-status`** — ahead/behind badges, push/pull buttons
- **`sg-vault-file-ops`** — delete/rename/move toolbar, context menu for tree items

**Deliverable:** Full read-write-sync cycle in the browser. Users can stage, commit, push, pull. File/folder operations work.

### Phase 4: Advanced Features (2–3 sessions)

#### 4a. Vault create/init

`sg-vault-init.js` — create a new vault from the browser. Generate vault ID, derive keys, create settings, first commit, write both refs.

New component: button in `sg-vault-manager` or standalone `sg-vault-create` form.

#### 4b. Large file support

Add presigned S3 URL path to `sg-vault-cache.js` or `sg-vault-client.js`:
```
if (size > 4MB) → GET presigned URL → fetch from S3 directly → cache
else            → GET via API → cache
```

#### 4c. VFS bridge + iframe viewer

`sg-vault-vfs.js` — postMessage proxy for sandboxed iframes.
`sg-vault-iframe-viewer` component — renders HTML files with VFS bridge active.

#### 4d. Commit history and branch graph

Extract from vault-browser v0.1.4:
- `sg-vault-commit-log` — scrollable commit list with decrypted messages
- `sg-vault-branch-graph` — visual graph

**Deliverable:** Browser-only vault creation. Large file support. HTML rendering from vault. History visualisation.

## 2. Tool Refactor Plan

### Current vault tool (v0.1.25)

```
sg-vault-connect + sg-vault-tree + sg-vault-viewer
(thin composition in sg-layout)
```

### Target vault tool (v0.2.0+)

```
sg-vault-manager (or sg-vault-connect)
  + sg-vault-tree (with tree model, preserved expand state)
  + sg-vault-sync-status (ahead/behind, push/pull)
  + sg-vault-viewer (with file preview delegation)
  + sg-vault-file-ops (delete/rename/move toolbar)
  + sg-vault-nav-history (back/forward)
  + sg-vault-settings (vault name/description editor)
```

All wired via `[data-vault-bus]` event bus using `vault:*` colon-namespaced events.

### Vault-browser tool (v0.1.4 → v0.2.0)

Currently has many features trapped inline. After extraction:
- Replace all inline elements with imported components
- Add commit-log and branch-graph components
- Add keys-inspector component
- Migrate from hyphenated events to `vault:*` convention
- Upgrade from client v1.1.0 to current

### Vault website (`vault.sgraph.ai`)

Becomes a thin shell:
```html
<script type="module" src="https://tools.sgraph.ai/components/vault/sg-vault-manager/..."></script>
<script type="module" src="https://tools.sgraph.ai/components/vault/sg-vault-tree/..."></script>
<!-- etc. -->

<div data-vault-bus>
  <!-- layout + component composition only -->
</div>
```

No vault-specific JS in the vault website — all logic lives in `__Tools` components, served via CDN.

## 3. Handoff to Architect and Developer

**For the Architect:** Design the module dependency graph for the new core modules (cache, tree-model, browse-data-source, mutations, session, init, vfs). Define the public API surface for each. Ensure the three-tier architecture is respected (core = no UI, components = UI + events, tools = thin compositions). Define versioning strategy for the breaking changes (v0.2.0 components, v1.3.0 client, v2.0.0 write).

**For the Developer:** Start with Phase 0 (version drift fixes + regex fix). Then Phase 1 (cache + tree model) — these are pure core modules with no UI, testable in isolation. Use the vault team's reference implementation as the spec: the wire format, schemas, and HTTP calls are already production-proven.
