### Key concepts in one paragraph each

**Wire format.** Every encrypted value is `[12-byte random IV] [N-byte ciphertext] [16-byte GCM auth tag]`. AES-256-GCM via Web Crypto. Fresh IV per call. The server never sees plaintext — it only stores opaque blobs and refs.

**Key derivation.** Two paths. Standard `passphrase:vault_id` runs **two parallel** PBKDF2 chains (600 000 iterations, SHA-256, different salts) — one yields `read_key`, the other `write_key`. Knowing one tells you nothing about the other (zero-knowledge sharing). Simple token `word-word-NNNN` uses a fixed PBKDF2 salt then HKDF×2 + SHA-256(token)[:12 hex] for `vault_id`. From `read_key` bits an HMAC-SHA-256 key derives deterministic file IDs (named ref, branch index, clone ref).

**4-segment ID naming.** `{type}-{derivation}-{mutability}-{hex12}` — e.g. `obj-cas-imm-{sha256[:12]}` is content-addressed immutable, `ref-pid-muw-{hmac[:12]}` is the named HEAD (multi-writer), `ref-pid-snw-{hmac[:12]}` is the per-clone HEAD (single-writer), `idx-pid-muw-{hmac[:12]}` is the branch index.

**Two-branch model.** The vault always has two refs: **named HEAD** (shared/published, advances only on `push()`) and **clone HEAD** (this browser session's local working state, advances on every `commit()` and is created lazily on the first commit). The gap between them is the pending work. `push()` is one PUT. `pull()` (fast-forward only) is 1 GET + 1 PUT + a tree reload.

**Lazy sub-tree loading.** `open()` only fetches the root tree (~1 KB). Every sub-folder becomes a stub `{ type:'folder', children:{}, _tree_id, _loaded:false }`. The stub's tree object is fetched only when the user expands the folder. **Critical invariant:** during `_commit()`, unloaded folders pass through unchanged (their `_tree_id` is preserved verbatim); only loaded folders get new tree objects. This makes a 251 MB / 155-file vault openable in ~6 s cold and ~820 ms warm.

**Cache API as lazy clone.** All `obj-cas-imm-*` blocks are stored in browser Cache API (`sg-vault-blocks`). Because IDs encode SHA-256 of ciphertext, cache entries are permanently valid — no invalidation ever. The cache is the user's local clone, materialised on demand, file-by-file.

**Server knowledge.** Server sees: vault_id, write_key (for auth), object IDs, blob counts, write timestamps. Server does **not** see: file names, sizes, directory structure, file content, commit messages, read_key, passphrase. Object graph topology is visible (which blob references which) but is semantically opaque.

## 3. What "Tools team" means in this context

The vault team is the team that built the working MVP **on the Send repo** (`SGraph-AI__App__Send`, folder `sgraph_ai_app_send__ui__vault`). Their handoff is to the **Tools team** (us — `SGraph-AI__Tools`, the canonical CDN-served component library at `tools.sgraph.ai`).

The expected flow going forward:

```
SGraph-AI__App__Send (vault MVP, proves it works end-to-end)
              │
              │  hand off
              ▼
SGraph-AI__Tools (canonical components: core/vault-*, components/vault/*)
              │
              │  imported via CDN
              ▼
vault.sgraph.ai   send.sgraph.ai   workspace   chrome-ext   any other consumer
```

The vault MVP in Send becomes the **reference implementation**; `__Tools` becomes the **versioned, reusable, CDN-served** version that everyone else imports.
