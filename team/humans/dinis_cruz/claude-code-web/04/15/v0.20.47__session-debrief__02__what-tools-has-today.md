## 1. Core modules (`sgraph_ai_tools__static/core/`)

### `core/vault-client/v1/v1.2/v1.2.0/sg-vault-client.js` — **read side**

The browser vault read client. Pure JS, no UI, no Cache API. Exports:

| Symbol | Purpose |
|---|---|
| `parseVaultKey(vaultKey)` | Parses `passphrase:vaultId`. **Strict regex `/^[0-9a-z]{8}$/` for vaultId.** ⚠ The vault team's `SGVault` accepts 4–24 chars. |
| `deriveVaultKeys(passphrase, vaultId)` | PBKDF2 (600 000 iter, SHA-256, 32-byte) → AES-GCM `readKey` + HMAC-SHA-256 derived `refFileId`, `indexFileId`, `branchIndexFileId`, `settingsFileId`. Returns `{ readKey, readKeyBytes, writeKey, refFileId, indexFileId, branchIndexFileId, settingsFileId, vaultId, derivationTimeMs }`. |
| `deriveFileIdHex(hmacKey, ...)` | Generic HMAC-derived 12-hex file ID |
| `deriveBranchRefFileId(hmacKey, vaultId, branchName)` | `ref-pid-snw-{hmac[:12]}` |
| `openVault(apiBase, vault)` | Reads ref → commit → root tree, returns `{ tree, refFileId }` |
| `openVaultTree(apiBase, vault)` | Convenience wrapper around openVault |
| `readFile(apiBase, vaultId, fileId)` | Reads a single blob (raw ciphertext) |
| `readFileAsJson(apiBase, vaultId, fileId, readKey)` | Reads + decrypts + JSON.parse |
| `batchRead(apiBase, vaultId, fileIds)` | Multi-file fetch helper |
| `fetchSubTree(apiBase, vault, treeId)` | One sub-tree fetch (called on user expand) |
| `fetchSettings(apiBase, vault)` | Reads the `.vault-settings` blob |
| `listFileIds(apiBase, vaultId)` | Lists raw object IDs from server (admin) |
| `deriveFileIdForPath(hmacKey, vaultId, path)` | Path-deterministic file ID |
| `encryptMetadata(...)` / `decryptMetadata(...)` | Field-level AES-GCM helpers |
| `computeObjectId(ciphertext)` | SHA-256(ciphertext)[:12] |
| `walkTree(apiBase, vault, tree, callback)` | Recursive tree walk for client-side expansion |

**Constants:** `KDF_ITERATIONS = 600_000`, `KEY_LENGTH = 32`, `FILE_ID_HEX_LENGTH = 12`, `IV_LENGTH = 12`, `SALT_PREFIX = 'sg-vault-v1'`.

**No state, no caching, no in-memory tree object.** Every call is a fresh fetch+decrypt. The caller is responsible for keeping any state.

### `core/vault-write/v1/v1.1/v1.1.1/sg-vault-write.js` — **write side**

Imports from the `v1.2.0` client. v1.1.1 (vs v1.1.0) adds `accessToken` support via the `x-sgraph-access-token` header. Exports:

| Symbol | Purpose |
|---|---|
| `writeVaultFile(vault, filePath, content, options)` | The whole flow: encrypt blob → read current ref→commit→tree → walk to flat-map → upsert path → `buildSubTrees()` bottom-up → create `commit_v2` → update ref |
| `buildSubTrees(flatMap, readKeyBytes, uploadFn)` | sgit-compatible bottom-up tree construction |
| `deriveWriteKeys(passphrase, vaultId)` | Returns encrypt-capable `readKey` + `writeKey` |
| `deriveWriteKeysFromSimpleToken(token)` | Same but for `word-word-NNNN` simple tokens |

**Notes:**
- Single-ref model. There is no `clone HEAD` — every write advances the named HEAD directly. This is conceptually equivalent to `commit + push` in one operation.
- Fully sgit-compatible at the wire level (commit_v2, tree_v1).
- No in-memory mutation buffer — every write is a full read-walk-write cycle.

### Other vault-related core modules

| File | Purpose |
|---|---|
| `core/sg-vfs/v0/v0.1/v0.1.0/sg-vfs-events.js` | `SGL_VFS` constants (30+ event names) — provider lifecycle, request/response/error pairs for read/write/delete/list/stat/createFolder/copy/rename/exists, write-queue/drain, vault commit, batch generator |
| `core/pyodide/v1/v1.0/v1.0.0/sg-pyodide.js` | Pyodide loader + `checkVaultCompatibility()`, `deriveVaultKeysPython()` for Python↔JS crypto verification |

## 2. Vault components (`sgraph_ai_tools__static/components/vault/`)

Four components, all at v0.1.1.

### `sg-vault-manager/v0/v0.1/v0.1.1/sg-vault-manager.js`

Multi-vault registry. Stores a list of vaults in `localStorage['sg-vault-registry']`. Per-vault config: API base URL, optional remembered key, optional `accessToken`. UI: list of cards with connect/disconnect/forget buttons; "Add vault" form with a "Remember key on this device" checkbox.

**Events emitted (on `[data-vault-bus]` ancestor element):**
- `vault:connected { vault, vaultId, displayName, apiBaseUrl, keys, accessToken, isNew }`
- `vault:disconnected { vaultId }`

**Verifies** a vault by calling `readFile(keys.refFileId)` — proves the key decrypts the named ref.

### `sg-vault-connect/v0/v0.1/v0.1.1/sg-vault-connect.js`

Single-vault connection panel (simpler alternative to the manager). Stores `sg-vault:last-key` and `sg-vault:last-api` in localStorage for convenience.

⚠ **Imports from `sg-vault-write/v1/v1.1/v1.1.0/`** — version drift. v1.1.1 exists (with accessToken support) but this component still pulls v1.1.0.

Same emit pattern as the manager: `vault:connected` / `vault:disconnected`.

### `sg-vault-tree/v0/v0.1/v0.1.1/sg-vault-tree.js`

Tree panel. Listens for `vault:connected`. Calls `openVaultTree()` (= ref → commit → root tree). Renders a folder tree. On folder click, expands lazily by calling `walkTree()` on the sub-tree.

**Lazy state** is only an `entry._loaded` boolean on the in-render-tree node — there is no separate STUB/LOADED model with `_tree_id` retention. When the tree refreshes, the whole expansion state is lost.

**Events emitted:**
- `vault:file-select { path, fileId, size }`
- `vault:folder-select { path }`
- `vault:new-file-request { path }`

**Events consumed:**
- `vault:tree-refresh` — full reload

### `sg-vault-viewer/v0/v0.1/v0.1.1/sg-vault-viewer.js`

Viewer + editor panel. Listens for `vault:file-select`. Fetches blob, decrypts, displays as text or "binary file" notice. Edit mode: textarea + Save. Save calls `writeVaultFile()` which does the full read-walk-write cycle.

⚠ **Also imports `sg-vault-write/v1/v1.1/v1.1.0/`** — same version drift.

**Events emitted:**
- `vault:file-saved { path }`
- `vault:tree-refresh {}` (after save, to make the tree reload)

## 3. Vault tools (`sgraph_ai_tools__static/tools/v0/v0.1/`)

Three vault-related tools, none currently using a Cache API or two-branch model.

### `tools/v0/v0.1/v0.1.25/en-gb/vault/index.html` — **the "native" composition tool**

Uses `sg-layout` for a 2-column page:

```
┌──────────────────────────────────────────────────────────┐
│ Header                                                   │
├──────────────────────────────────┬───────────────────────┤
│  Connection (sg-vault-connect)   │                       │
│  ──────────────────────────────  │                       │
│  Files tree (sg-vault-tree)      │  Viewer/editor        │
│  (left, 28%)                     │  (sg-vault-viewer)    │
│                                  │  (right, 72%)         │
└──────────────────────────────────┴───────────────────────┘
```

This is the **pattern** the user wants more of: small purpose-specific components composed inside a layout. The pattern works; it just needs (a) more components, (b) the runtime upgrades from the vault team.

### `tools/v0/v0.1/v0.1.4/en-gb/vault-browser/index.html` — **the older richer prototype**

Self-contained page with **inline** components: `vault-manager`, `vault-derived-keys`, `vault-nav-history`, `vault-file-list`, `vault-json-view`, `vault-mermaid`, `vault-graph-branches`, `vault-graph-commits`, `vault-file-preview`, plus schema viewers.

⚠ **Imports `sg-vault-client/v1/v1.1/v1.1.0/`** — older than the v1.2.0 the new components use.

⚠ **Different event name convention** — uses hyphenated names `vault-open-request`, `vault-file-select`, `vault-object-navigate` (vs the colon-namespaced `vault:connected`, `vault:file-select` used by the v0.1.1 components).

This tool has more *features* than the native composition tool (key inspector, navigation history, JSON view, mermaid render, branch/commit graphs, file preview, schema viewers) but they're trapped inline. **Goldmine for component extraction.**

### `tools/v0/v0.1/v0.1.4/en-gb/vault-pyodide/index.html` — **Pyodide WASM experiment**

Loads CPython in WASM via `sg-pyodide`, runs vault crypto in Python, compares Python vs JS key derivation. Useful for crypto compatibility verification, not part of the production component story.
