## Gap 10: Version Drift Between Components

Three components/tools import older versions of core modules than what's available:

| Consumer | Currently imports | Should import | What's missing |
|---|---|---|---|
| `sg-vault-connect` v0.1.1 | `sg-vault-write` **v1.1.0** | v1.1.1 | `accessToken` header support |
| `sg-vault-viewer` v0.1.1 | `sg-vault-write` **v1.1.0** | v1.1.1 | `accessToken` header support |
| `vault-browser` v0.1.4 (tool) | `sg-vault-client` **v1.1.0** | v1.2.0 | `openVaultTree`, `walkTree`, updated API surface |

The first two are single-line import path fixes. The vault-browser migration is larger because the v1.1.0→v1.2.0 client surface changed (new functions, different signatures).

**Fix:** Bump the two component imports as part of the refactor prep (before any new work). Vault-browser migration can wait until the component extraction work happens.

## Gap 11: No Push/Pull Status Component

**Vault team has:** `getAheadCount()` and `getBehindCount()` methods on the vault object, used by the UI to decide whether to show push/pull buttons and warn about conflicts.

**Tools has:** No component that shows sync status, ahead/behind counts, or push/pull controls. The vault tool v0.1.25 has no concept of sync — every save writes directly to the shared ref.

**What to build:** `sg-vault-sync-status` component:
- Shows ahead count (local unpushed commits) and behind count (remote unpulled commits)
- Push button (enabled when ahead > 0 and behind == 0)
- Pull button (enabled when behind > 0 and ahead == 0)
- Warning state when both ahead > 0 and behind > 0 (diverged — merge not supported)
- Events: `vault:push-request`, `vault:pull-request`, `vault:sync-status-changed`
- Requires the two-branch model (Gap 3) to exist in core

## Gap 12: No File Operations Panel Component

**Vault team has:** Full mutation suite (add, update, remove, rename, move for both files and folders).

**Tools has:** Only view+edit in `sg-vault-viewer` v0.1.1. No delete, rename, move controls. No folder creation/deletion UI.

**What to build:** `sg-vault-file-ops` component:
- Context menu or toolbar for selected file/folder
- Delete file/folder (with confirmation)
- Rename file/folder (inline edit)
- Move file/folder (drag-drop or picker)
- Create new folder
- Events: `vault:file-deleted`, `vault:file-renamed`, `vault:file-moved`, `vault:folder-created`, `vault:folder-deleted`
- Requires the mutation functions from Gap 4

## Gap 13: No File Preview Component (Extracted)

**Vault team has:** BrowseDataSource + VFS bridge enables rendering vault HTML files with full asset loading.

**Tools has (inline only):** The `vault-browser` v0.1.4 tool has inline `vault-file-preview`, `vault-json-view`, and `vault-mermaid` elements. These render markdown, JSON, images, and mermaid diagrams from vault content. But they're defined inside the tool's `index.html`, not as reusable components.

The reality document explicitly lists "File Preview component — to extract from vault" as a PROPOSED item that does not exist yet (line 435).

**What to build:** Extract from vault-browser v0.1.4 into reusable components:
- `sg-vault-file-preview` — auto-detect content type, render appropriately
- `sg-vault-json-view` — JSON tree view with collapse/expand
- `sg-vault-mermaid-view` — mermaid diagram renderer
- `sg-vault-markdown-view` — markdown renderer
- `sg-vault-image-view` — image display with zoom
- All should accept a `BrowseDataSource` (Gap 8) rather than calling vault-client directly

## Gap 14: No Commit History / Branch Graph Components (Extracted)

**Vault team has:** Full commit chain walking via `loadCommit()` with parent traversal. The protocol supports `git log`-equivalent, `git show HEAD~N:file`, and `git diff` via encrypted object graph traversal.

**Tools has (inline only):** `vault-browser` v0.1.4 has inline `vault-graph-branches` and `vault-graph-commits` elements that visualise the commit graph. Not reusable.

**What to build:** Extract into:
- `sg-vault-commit-log` — list commits with messages (decrypted), timestamps, parent links
- `sg-vault-branch-graph` — visual branch/commit graph (could use mermaid or canvas)
- Both require the commit-walking functions already present in `sg-vault-client.js` v1.2.0

## Gap 15: No Derived Keys Inspector Component (Extracted)

**Tools has (inline only):** `vault-browser` v0.1.4 has `vault-derived-keys` that shows all derived material (read key, write key, HMAC key, ref file IDs, etc.) for debugging/verification.

**What to build:** `sg-vault-keys-inspector` — shows derived keys, file IDs, and derivation timing. Useful for developers and debugging. Low priority for end-user tools.

## Gap 16: No Navigation History Component (Extracted)

**Tools has (inline only):** `vault-browser` v0.1.4 has `vault-nav-history` with back/forward navigation through viewed files/objects.

**What to build:** `sg-vault-nav-history` — breadcrumb or back/forward bar for file navigation. Consumes `vault:file-select` events, maintains a stack, emits `vault:navigate-back` / `vault:navigate-forward`.

## Gap 17: Event Name Convention Split

**Current state:** Two different naming conventions exist:

| Convention | Where used | Examples |
|---|---|---|
| **Colon-namespaced** | Components v0.1.1 (`sg-vault-tree`, `sg-vault-viewer`, `sg-vault-connect`, `sg-vault-manager`) | `vault:connected`, `vault:file-select`, `vault:tree-refresh` |
| **Hyphenated** | `vault-browser` v0.1.4 tool (inline elements) | `vault-open-request`, `vault-file-select`, `vault-object-navigate` |

The colon convention matches the LLM component pattern (`llm:connected`, `llm:response`, etc.) and uses the `[data-vault-bus]` ancestor element for scoping. The hyphenated convention is older and doesn't use a bus element.

**What to do:** Standardise on the colon convention (`vault:*`) with `[data-vault-bus]` scoping. When extracting inline elements from vault-browser, migrate them to the colon convention.

## Gap 18: No Vault Settings UI Component

**Vault team has:** `.vault-settings` is a JSON blob stored in every root tree, containing `vault_name`, `vault_id`, `created`, `version`, `description`. It's re-serialised on every commit.

**Tools has:** `fetchSettings()` exists in `sg-vault-client.js` v1.2.0 but no component surfaces or edits settings.

**What to build:** `sg-vault-settings` — display/edit vault name and description. Requires the write path to re-serialise settings into the tree on commit (which the vault team's `_commit()` already does).

## How the Vault Website Should Consume These

The end-state for `vault.sgraph.ai` (and `dev.vault.sgraph.ai`):

```html
<!-- Import components from tools.sgraph.ai CDN -->
<script type="module" src="https://tools.sgraph.ai/components/vault/sg-vault-manager/v0/v0.2/v0.2.0/sg-vault-manager.js"></script>
<script type="module" src="https://tools.sgraph.ai/components/vault/sg-vault-tree/v0/v0.2/v0.2.0/sg-vault-tree.js"></script>
<script type="module" src="https://tools.sgraph.ai/components/vault/sg-vault-viewer/v0/v0.2/v0.2.0/sg-vault-viewer.js"></script>
<script type="module" src="https://tools.sgraph.ai/components/vault/sg-vault-sync-status/v0/v0.1/v0.1.0/sg-vault-sync-status.js"></script>
<script type="module" src="https://tools.sgraph.ai/components/vault/sg-vault-file-ops/v0/v0.1/v0.1.0/sg-vault-file-ops.js"></script>
<!-- etc. -->

<div data-vault-bus>
  <sg-vault-manager></sg-vault-manager>
  <sg-vault-tree></sg-vault-tree>
  <sg-vault-sync-status></sg-vault-sync-status>
  <sg-vault-viewer></sg-vault-viewer>
  <sg-vault-file-ops></sg-vault-file-ops>
</div>
```

The vault website becomes a **thin layout shell** that composes `__Tools` components, identical to how the chat tool composes `sg-llm-*` components. All logic lives in `__Tools`, served via CDN, versioned and immutable.
