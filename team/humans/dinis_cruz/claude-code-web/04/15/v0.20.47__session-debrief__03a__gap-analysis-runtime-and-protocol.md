## Purpose

This part compares the vault team's reference implementation (in `SGraph-AI__App__Send`) against the `__Tools` repo's current vault stack at the **runtime and protocol** level — the foundational layers that every component sits on top of.

---

## Gap 1: No Cache API Integration

**Vault team has:** Every `obj-cas-imm-*` block goes through a Cache API layer (`sg-vault-blocks` cache name). On first fetch, ciphertext is stored; on subsequent access, the blob is served from cache with zero network. The `-imm-` segment in the ID is the guard — only immutable, content-addressed blobs are cached. `data.slice(0)` copies the ArrayBuffer so callers can transfer ownership without invalidating the cache copy. Graceful degradation: `typeof caches === 'undefined'` guard, storage quota errors silently swallowed.

**Tools has:** Nothing. Every `readFile()` call in `sg-vault-client.js` v1.2.0 is a fresh `GET /api/vault/read/...`. There is no caching at any layer. Opening the same vault twice fetches all the same objects twice.

**Impact:** The vault team measured cold open at ~6 s and warm (cached) at 820 ms for a 251 MB / 155-file vault. Without caching, `__Tools` pays the full 6 s every time. This is the single biggest performance gap.

**What to build:** A `sg-vault-cache.js` core module (or integrate into the existing client) that wraps fetch with Cache API read-through. The module should:
- Use cache name `sg-vault-blocks`
- Key pattern: `https://sgvault/{vaultId}/bare/data/{objectId}`
- Only cache `obj-cas-imm-*` blobs (the `-imm-` guard)
- Copy buffers with `data.slice(0)` before returning
- Degrade silently when Cache API is unavailable

## Gap 2: No In-Memory Tree with STUB/LOADED State

**Vault team has:** The in-memory tree is a persistent object that survives across operations. Each folder node has a state machine:

```
STUB:   { type:'folder', children:{}, _tree_id:'obj-cas-imm-...', _loaded:false }
LOADED: { type:'folder', children:{...populated...}, _loaded:true }  (no _tree_id)
```

On `open()`, only root-level entries are populated; all sub-folders are stubs. `loadSubTreeOnDemand(path)` fetches the sub-tree, populates children, and transitions the node to LOADED. During `_commit()`, unloaded stubs pass through unchanged — their `_tree_id` is preserved verbatim in the new tree, so committing a change to `/README.md` never touches `/archive/` (which might have 100 files).

**Tools has:** `sg-vault-tree` v0.1.1 calls `walkTree()` from the client, which does expand folders — but only for rendering. There is no persistent in-memory tree object with `_tree_id` retention. When the tree refreshes (e.g. after a save), the entire expansion state is rebuilt from scratch.

More critically, `sg-vault-write.js` v1.1.1's `writeVaultFile()` does a full read-walk-write cycle on every save — it re-reads the entire ref→commit→tree chain, builds a flat map, inserts the new file, and rebuilds all sub-trees bottom-up. It doesn't know which folders were loaded vs not, so it must walk everything. This works but is O(total files), not O(changed path depth).

**Impact:**
- No preservation of unloaded sub-trees means writes are heavier than necessary
- Tree refresh after save loses user's expand/collapse state
- Large vaults with deep trees pay proportionally more on every write

**What to build:** A `sg-vault-tree-model.js` core module that owns the in-memory tree with STUB/LOADED states and exposes:
- `loadRoot(commit)` — populate root, stubs for sub-folders
- `loadSubTree(path)` — fetch + populate, transition STUB→LOADED
- `needsLoading(path)` — check if a path is still a stub
- `buildTreeEntries(node)` — commit-time serialisation that preserves stubs
- `getNode(path)` — tree navigation

## Gap 3: No Two-Branch Model (Single-Ref Only)

**Vault team has:** Two refs at all times:
- **Named HEAD** (`ref-pid-muw-{hmac}`) — the shared/published state. Only advances on `push()`.
- **Clone HEAD** (`ref-pid-snw-{hmac}`) — this browser session's working state. Advances on every `commit()`. Created lazily on first commit.

This means local edits are saved immediately (every commit) without touching the shared state. The user explicitly publishes via `push()`. Multiple sessions can work independently.

**Tools has:** `sg-vault-write.js` v1.1.1 writes directly to the named ref on every save. There is no clone HEAD, no local-only commits, no push/pull separation. Every `writeVaultFile()` call is effectively a `commit + push` in one step.

`sg-vault-client.js` v1.2.0 does derive `branchIndexFileId` and can call `deriveBranchRefFileId()`, but these are never used in the write path. The write module doesn't create or read a clone ref.

**Impact:**
- Every save is immediately visible to all other clients (no staging/review)
- No way to batch multiple edits before publishing
- No ahead/behind count — the concept doesn't exist without two refs
- If two sessions save simultaneously, last-write-wins with no conflict detection

**What to build:** Extend the write module (or create `sg-vault-session.js`) with:
- `initCloneRef()` — create clone HEAD on first commit
- `commit(message)` — write to clone ref only
- `push()` — advance named HEAD to match clone HEAD (1 PUT)
- `pull()` — fast-forward clone HEAD to named HEAD (with pre-condition: ahead count must be 0)
- `getAheadCount()` / `getBehindCount()` — walk commit parents

## Gap 4: No Full Mutation Suite

**Vault team has:** 9 mutation operations, all following the same pattern (mutate in-memory tree → `_commit()`):

| Operation | What it does |
|---|---|
| `addFile(folder, name, content)` | Encrypt blob, insert entry, commit |
| `updateFile(folder, name, content)` | Encrypt new blob, replace entry, commit |
| `removeFile(folder, name)` | Delete entry from parent, commit |
| `renameFile(folder, oldName, newName)` | Move entry key in parent.children, commit |
| `moveFile(srcFolder, name, destFolder)` | Remove from src, insert in dest, commit |
| `createFolder(parent, name)` | Insert empty `{type:'folder', children:{}, _loaded:true}`, commit |
| `removeFolder(parent, name)` | Delete entry (recursive), commit |
| `renameFolder(parent, oldName, newName)` | Move entry key, commit |
| `moveFolder(srcParent, name, destParent)` | Remove from src, insert in dest, commit |

Each ends with `await this._commit(message)` which builds tree entries → creates tree objects → creates commit → updates clone ref. HTTP cost: N+3 to N+5 PUTs per commit (N = number of loaded folders).

**Tools has:** Only `writeVaultFile(vault, filePath, content)` — which handles add and update. No remove, rename, move, or any folder operations. The write module reads the full tree, does a flat-map upsert, and rebuilds everything bottom-up.

**Impact:** Users cannot delete, rename, or move files/folders through `__Tools` components. The vault-browser v0.1.4 tool doesn't have these either. The vault tool v0.1.25 has only view+edit.

**What to build:** Extend the write module or create a mutation layer that operates on the in-memory tree model (Gap 2) and calls `_commit()` after each operation.

## Gap 5: No `create()` / Vault Init

**Vault team has:** `SGVault.create(sgSend, passphrase, options)` — generates vault ID (8 random bytes → alphanumeric), derives all keys, creates settings, creates empty in-memory tree, runs first `_commit()`, writes named ref to same commit. 5 PUTs, vault exists.

**Tools has:** Nothing. `sg-vault-write.js` assumes the vault already exists (created by `sgit init` on the CLI). There's no way to create a vault from the browser.

**Impact:** Users must use the CLI to initialise a vault before the web tool can work with it. Browser-only workflows are impossible.

**What to build:** A `createVault(apiBase, passphrase, options)` function in the write module (or a new `sg-vault-init.js` core module).

## Gap 6: No Presigned S3 URL for Large Files

**Vault team has:** Files > 4 MB use a presigned S3 URL path:

```
GET /api/vault/presigned/read-url/{vaultId}/bare/data/{blobId}
→ { "url": "https://s3.amazonaws.com/...?X-Amz-Signature=..." }
→ GET {presigned_url}  (direct from S3, bypasses Lambda 6 MB limit)
→ fallback to direct read if 400
```

**Tools has:** All reads go through `readFile()` which uses the standard `/api/vault/read/...` endpoint. Files > ~6 MB will fail (Lambda response limit) or be very slow.

**Impact:** Users cannot reliably access files > 4–6 MB.

**What to build:** Add a `readFileLarge(apiBase, vaultId, fileId)` function (or a size-aware dispatch in `readFile()`) that tries presigned URL first, falls back to direct.

## Gap 7: No VFS Bridge for Sandboxed Iframes

**Vault team has:** A postMessage-based virtual filesystem bridge that lets HTML files loaded in sandboxed iframes request vault assets. The iframe's `window.fetch` is overridden, `HTMLImageElement.prototype.src` setter is patched, and a MutationObserver catches dynamically added images. A critical `__sgVfs` flag prevents infinite loops (set before VFS request, cleared after blob URL assignment).

**Tools has:** Nothing. HTML files in the vault viewer are displayed as source text, not rendered.

**Impact:** Any vault containing HTML content (dashboards, reports, tools, infographics) cannot render interactively.

**What to build:** A `sg-vault-vfs.js` core module implementing the postMessage protocol, plus an `sg-vault-iframe-viewer` component that renders HTML files inside a sandboxed iframe with VFS bridge active.

## Gap 8: No BrowseDataSource Abstraction

**Vault team has:** A `BrowseDataSource` interface with three methods: `getTree()`, `getFileBytes(path)`, `getFileList()`. This abstraction decouples the viewer/browser UI from the vault protocol — the UI doesn't need to know about refs, commits, trees, or encryption. It just asks for files.

**Tools has:** Components call vault-client functions directly (`openVaultTree`, `readFile`, `walkTree`). The protocol details leak into every component.

**Impact:** Components can't be reused with non-vault data sources (local files, git repos, S3 buckets). Testing requires a vault server.

**What to build:** An abstract `BrowseDataSource` class/interface in core, plus a `VaultBrowseDataSource` adapter that wraps the vault client. Components should consume the interface, not the vault client directly.

---

## Gap 9: Strict 8-Char Vault ID Regex

**Vault team has:** Vault IDs range 4–24 lowercase alphanumeric characters.

**Tools has:** `parseVaultKey()` in `sg-vault-client.js` v1.2.0 enforces a strict `/^[0-9a-z]{8}$/` regex. Any vault with a non-8-char ID (which the vault team's `create()` can produce, and the CLI can create) will be rejected at parse time.

**Impact:** Some existing vaults may not be accessible from `__Tools`.

**What to fix:** Relax the regex to `/^[0-9a-z]{4,24}$/` to match the vault team's implementation.

## Summary: Gap Priority

| # | Gap | Effort | Impact | Priority |
|---|---|---|---|---|
| 1 | Cache API | Medium | Massive perf gain (7× on warm) | **P0** |
| 2 | In-memory tree model | Medium–Large | Enables mutations, preserves expand state | **P0** |
| 3 | Two-branch model | Large | Enables push/pull, local staging | **P1** |
| 4 | Full mutation suite | Medium | Enables delete/rename/move | **P1** |
| 5 | Vault create/init | Small | Enables browser-only workflows | **P2** |
| 6 | Large file presigned URL | Small | Fixes >4 MB file access | **P2** |
| 7 | VFS bridge | Large | Enables HTML rendering from vault | **P2** |
| 8 | BrowseDataSource abstraction | Small | Better architecture, testability | **P1** |
| 9 | 8-char vaultId fix | Trivial | Compatibility | **P0** |
