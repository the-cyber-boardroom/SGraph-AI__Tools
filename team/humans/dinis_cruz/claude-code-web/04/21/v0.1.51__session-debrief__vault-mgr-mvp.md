## What Was Built

A new standalone tool: **Vault Manager** (`vault-mgr`). It implements the full workflow for managing SGraph vault credentials without requiring a native app or CLI. The tool runs entirely in the browser.

### Architecture

```
vault-mgr/
  index.html          ← Entry page (layout, GIS script tag)
  config.json         ← { googleClientId: "..." }
  vault-mgr.js        ← Import orchestrator (components + init)
  api/
    vault-store.js    ← VaultStore class + generateVaultKey()
  ui/
    ui-shell.js       ← Layout bootstrap, shared state, callbacks
    ui-left-panel.js  ← Auth section + Drive Store + Vault List
    ui-right-panel.js ← Vault detail, master key editor, sg-vault-connect
```

### Full UX Flow

1. **Load** → user is signed in (ID token in localStorage) → GIS loads via `<script>` tag → auth context fires `onAuthChange` → silent Drive connect attempted with `prompt: ''` + `login_hint: email`
2. **Signed in + Drive connected (returning user)** → single page load, no popups, vaults list shown immediately
3. **First-time user** → sign in with Google → Drive consent screen → connected
4. **Select vault** → right panel shows vault detail, master key (masked), pre-filled sg-vault-connect form
5. **Connect to vault** → sg-vault-connect derives keys, opens VaultSession, sg-vault-tree appears
6. **Create/import vault** → "+ New" form with editable key field; auto-generates a key or user pastes existing one
7. **Edit vault key** → Edit button on Master Key section → paste new key → Save → persists to Drive

### Key Modules Used / Created

| Module | What it does |
|---|---|
| `core/auth-context/v0.1.0/sg-auth-context.js` | `getUser()`, `isSignedIn()`, `onAuthChange()` singleton |
| `core/drive-appdata/v0.1.0/sg-drive-appdata.js` | `requestAccess()`, `DriveAppData` class |
| `vault-store.js` (local to tool) | Reads/writes `vaults.json` in Drive App Data |
| `sg-vault-connect` v0.1.3 | Key derivation + VaultSession connection |
| `sg-vault-tree` v0.1.3 | Decrypted file/folder tree from session |

### Data Model

`vaults.json` in Drive App Data:
```json
{
  "vaults": [
    {
      "vaultId": "<uuid>",
      "displayName": "my main vault",
      "apiBaseUrl": "https://dev.vault.sgraph.ai",
      "vaultKey": "<48-hex>:<16-hex>",
      "createdAt": "2026-04-20T22:00:00.000Z",
      "lastUsed": "2026-04-20T23:38:48.000Z"
    }
  ]
}
```

## What Was Discovered

### 1. Google Drive App Data Folder

- Scope: `https://www.googleapis.com/auth/drive.appdata` — one of the lowest-privilege Drive scopes
- Files stored in this folder are **invisible** to the user's Drive UI and to other apps
- Protection is the **access token**, not the Client ID or user sub (both of which are public)
- The access token is issued only after OAuth flow on a registered redirect URI — that is the real security boundary
- Google OAuth Client ID is **not a secret** — safe to commit in `config.json`

### 2. Two Separate OAuth Flows in GIS

Google Identity Services (GIS) has two distinct flows:

| Flow | API | Token type | Use |
|---|---|---|---|
| ID Token | `google.accounts.id` / `renderButton` | JWT credential | Authentication (who the user is) |
| Access Token | `google.accounts.oauth2.initTokenClient` | OAuth access token | API authorisation (Drive, etc.) |

These cannot be combined into a single popup using the GIS client-side library alone. Combining them requires a backend authorization code exchange, which is out of scope for this static tool.

### 3. Silent Token Acquisition

`requestAccessToken({ prompt: '' })` combined with `hint: user.email` allows Drive token acquisition without showing an account chooser — IF the user has previously consented to `drive.appdata`. For returning users this is completely seamless (no popup). For first-time users, Google shows a consent screen.

### 4. GIS Load Timing Is Tricky

`google.accounts.oauth2` is loaded by `sg-auth-google.js` in its `connectedCallback`. But `<sg-auth-google>` is only rendered when the user is **not** signed in. On page refresh with existing auth, the element is never mounted → GIS never loads → `requestAccess()` fails indefinitely.

**Fix:** Add `<script src="https://accounts.google.com/gsi/client" async>` directly to `index.html`. GIS must load unconditionally, regardless of auth state.

### 5. Chrome Password Manager Interception

Chrome scans the DOM for password-like fields and `type="password"` inputs. `sg-vault-connect` uses `type="password"` for the vault key input. When `localStorage.setItem('sg-vault:last-key', vaultKey)` is called synchronously before `innerHTML` renders the component, Chrome associates the localStorage write + DOM change with a form submission and offers to save the credential.

**Fix:** Move the `localStorage.setItem` for the vault key into `requestAnimationFrame` (after shadow DOM renders), so Chrome does not observe a password field being pre-filled in the context of a user action.

### 6. GIS `prompt: ''` Opens a Popup When Silent Fails

When `prompt: ''` is used but Google cannot grant the token silently (session expired, first consent), GIS attempts to open a popup. In non-user-gesture context (i.e., from `onAuthChange` on page load), the browser blocks this popup. GIS then fires an error in the callback. We catch this and fall back to showing the "Connect Drive" button.

## What This Enables

- **Cross-device vault registry** — vault entries (name, URL, key) stored in Google Drive App Data, available on any device the user signs into
- **No native app required** — full vault credential management from a browser tab
- **Per-user, per-app isolation** — Drive App Data is sandboxed; no other app or user can see the registry
- **Multiple vaults per user** — each vault is independent (different server URL, different key)
- **Edit/import existing vault keys** — users can paste existing keys rather than only generating new ones
- **Seamless returning-user experience** — after first setup, page load auto-connects Drive silently with one sign-in step

## Issues / Limitations Still Present

### 1. Transient Popup on Page Refresh (Harmless but Visible)

**What happens:** On page refresh with existing auth, the silent Drive connect attempt (`prompt: ''`) sometimes causes GIS to briefly open and immediately close a popup window before completing silently.

**Why:** GIS's internal token refresh mechanism may open a popup channel to verify the session, even when `prompt: ''` is set. This is GIS internal behaviour, not something our code controls.

**Impact:** No user interaction needed — the popup closes itself within ~1 second. But it is visible and confusing.

**Potential fix (not yet implemented):** Use the GIS Authorization Code flow with `access_type=offline` (requires a backend to exchange the code). Client-side-only cannot fully avoid this without a backend.

### 2. Drive Access Token Expires (~1 hour)

The Drive access token obtained via `requestAccess()` has a 1-hour lifetime. The tool does not refresh it automatically. After an hour, Drive API calls will fail with 401.

**Fix needed:** Detect 401 on Drive API calls in `DriveAppData`, call `requestAccess()` again silently, retry the operation.

### 3. sg-vault-connect Pre-Fill via Shadow DOM

We push the vault key directly into the shadow DOM input (`connect.shadowRoot.getElementById('vault-key')`) after the component mounts. This is fragile — it depends on the internal ID not changing across sg-vault-connect versions.

**Better approach:** Add a `vault-key` attribute to `<sg-vault-connect>` and have the component read it on `connectedCallback` / `attributeChangedCallback`.

### 4. Console Noise from Chrome Extensions + GIS COOP

Two classes of harmless but visible console errors:
- `A listener indicated an asynchronous response by returning true, but the message channel closed` — from Chrome extensions (FedCM / password manager) reacting to Google auth events. Not our code.
- `Cross-Origin-Opener-Policy would block the window.postMessage call` — GIS OAuth popup trying to postMessage back. Standard GIS/COOP interaction on localhost.

Neither affects functionality. Both disappear on a properly configured HTTPS deployment with correct COOP/COEP headers.

### 5. The "Add / Import Vault" Form Creates a New Entry, Not a Server Vault

The "Add Vault" button stores the entry in Drive (registry). It does NOT create a vault on the server. If a user enters a key for a vault that doesn't exist server-side yet, they'll get a 404 when trying to connect. The UX does not make this distinction clear.

**Fix needed:** Label the form clearly: "Register a vault entry (the vault must already exist on the server)".

### 6. Drive Connect Shows "Not Connected" on First Render Before Silent Connect Completes

On refresh, the UI renders "Not connected + Connect Drive button" for up to ~500ms while the silent connect resolves. This flicker is minor but noticeable.

**Fix (deferred):** Show "Connecting..." state from the first render when we know a silent connect is in progress.
