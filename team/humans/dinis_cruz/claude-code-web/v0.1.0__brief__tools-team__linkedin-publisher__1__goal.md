**Date:** 25 April 2026
**From:** Developer agent (claude-code-web session, post-YouTube debrief)
**To:** Tools team — Developer (next session), Architect, Designer

## 1. Why now

The YouTube Editor toolchain just shipped end-to-end (record → edit → upload → manage → analytics). The user has already published the first official SGraph video using it. The workflow value is proven; the next question is **where the resulting content goes**.

LinkedIn is the highest-value first additional destination because:
- It's the SGraph organisation's primary professional audience.
- LinkedIn's API supports **org-page posting** (the SG/Send page) via OAuth, which means an agent can publish on behalf of the organisation without manual copy-paste.
- It pairs naturally with the YouTube tool: a freshly-uploaded YouTube video → a LinkedIn post linking to it, with a one-line agent-written commentary, all browser-side.

The **agent use case**: a Claude Agent in Chromium records a demo, uploads to YouTube, gets the YouTube URL, drafts LinkedIn commentary, picks a thumbnail, and publishes the org post — all through one chain of `window.__tool[…]` calls.

The **human use case**: same workflow, but a human clicks through it instead. Either way, the content stays inside `tools.sgraph.ai`.

---

## 3. Proposed name

**`linkedin-publisher`** (tool slug + URL: `/en-gb/linkedin-publisher/`).

Reasoning:
- Parallel to `youtube-editor` — same convention, instantly recognisable.
- "Publisher" captures both **posting new** and **managing what's posted** — matches the API surface (create + read + update).
- Doesn't promise scheduling (LinkedIn's create endpoint requires `lifecycleState: PUBLISHED` only — no native draft state). "Editor" would over-promise.

---

## 4. Scope of v0.1

**In scope:**
- OAuth connect to LinkedIn (org admin's user account).
- Pick which org page to post as (admins may control multiple).
- Create **text post** for the chosen org.
- Create **article-link post** (URL + title + description + thumbnail image).
- List recent posts for the org page.
- Read a specific post's details.

**Out of scope for v0.1** (parked for v0.2+):
- Image / video / document posts (need a separate asset upload step — LinkedIn's media upload protocol is non-trivial).
- Personal-profile posts (LinkedIn restricts this to first-party apps; not viable for a third-party tool today).
- Update post (`POST` with `X-RestLi-Method: PARTIAL_UPDATE`).
- Analytics (impressions, clicks, engagement) — different scope + endpoint.
- Scheduling — not directly supported by the create endpoint; would need local IndexedDB queue + cron-like scheduler.

The cut roughly mirrors the youtube-upload v0.1 → youtube-editor v0.1 path: ship the focused thing first, expand later.

---

## 5. Why this is harder than YouTube was

LinkedIn's API model differs from YouTube's in three ways the next session must understand up-front:

1. **CORS.** LinkedIn's REST API at `api.linkedin.com` historically does **not** send permissive CORS headers. Browser-direct calls likely fail. Needs verification before any code is written; if confirmed, requires a proxy layer (see brief 2/5 for options).

2. **OAuth flow.** LinkedIn uses standard Authorization Code Flow. PKCE support exists for public clients. There's no equivalent of Google Identity Services (GIS) for the in-page popup we use for YouTube — the user is redirected to LinkedIn, comes back via a redirect URL.

3. **API versioning.** Every request requires both `LinkedIn-Version: YYYYMM` AND `X-Restli-Protocol-Version: 2.0.0` headers. The version date pins the contract; LinkedIn rotates supported versions every few months and old ones eventually drop off.

These aren't blockers — just three things that don't exist in the YouTube architecture and must be designed for from the start.
